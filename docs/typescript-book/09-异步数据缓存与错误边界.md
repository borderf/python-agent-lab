# 第09章　异步数据、缓存与错误边界

[上一章](08-React组件与状态.md) · [全书目录](教材目录.md) · [下一章](10-流式AI界面.md)

## 1. 学习目标与前置知识

能区分输入草稿等界面自己的数据，与从服务端取得、可能过期的数据。会为查询设计缓存标识，决定何时重取，避免旧响应覆盖新结果，并用错误边界显示替代界面，限制渲染错误的影响。前置：第8章；第4–5章的校验与取消。

**本章从这里开始：** 搜索页每次输入都发请求，返回顺序不固定；从详情页返回列表，数据已经过期；一个引用卡片抛异常，整页白屏。React 的 `useState` 能保存结果，但不会自动处理“缓存、失效、重试、隔离”。

## 2. 基础知识讲解

### 2.1 客户端状态与服务端状态

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| 客户端状态 | 输入框草稿、展开/收起、主题 | 组件拥有，变化由用户触发 |
| 服务端状态 | 搜索结果、文档详情、用户资料 | 远端拥有，可能过期，需要重新验证 |

服务端状态不要全部塞进 `useState` 手动同步。它需要：缓存 key、过期/失效、重复请求合并、错误重试、取消。可以自己实现最小版本，也可以用 TanStack Query/SWR；本章先手写一个，理解机制后再换库。

判断一个值属于哪一边，不问“它是不是在 React 里”，而问“谁拥有真相、别人会不会改、过期后怎么办”：

```ts
type ClientUi = { draft: string; expanded: boolean };
type RemoteCopy<T> = { data: T; fetchedAt: number; stale: boolean };

const ui: ClientUi = { draft: "预付款", expanded: true };
const copy: RemoteCopy<string[]> = { data: [], fetchedAt: 0, stale: false };
```

`draft` 只存在于当前页面，可随输入立即变化；`copy.data` 是服务端结果的副本，需要标记来源时间与是否过期。两者都不该靠“组件卸载就丢”或“永久保留”处理。只保存副本、不保存验证时间和 key，就无法判断它属于哪个身份与条件。

### 2.2 查询key是副本的归属，不是授权凭据

主线使用第8章query.ts的searchKey：主体、租户、授权版本、索引版本、问题与业务日期共同组成键。客户端不能用这个键向服务端自授权限；服务端仍从可信凭据授权。

先建立一条允许的查询，切换租户但保留相同问题与日期，再让旧请求完成。只在key里写问题和日期，会让两次身份共用范围；只在开始加载时清空，也挡不住迟到回调。

```ts
import { searchKey, type QueryIdentity } from "../../typescript-examples/src/query.js";

const identity: QueryIdentity = {
  subjectId: "u1", tenantId: "a", authVersion: "1", indexVersion: "3",
};
const key = searchKey(identity, "预付款", "2026-07-01");
const otherTenant = searchKey({ ...identity, tenantId: "b" }, "预付款", "2026-07-01");
console.log(key);
console.log(key === otherTenant); // false
```

**预期输出**：

```text
["u1","a","1","3","预付款","2026-07-01"]
false
```

`searchKey` 用 JSON 数组而不是直接拼接 `a-b`，避免字段中的分隔符制造碰撞；数组顺序是契约，不能随意重排。key 相同只表示“可以比较运行归属/缓存副本”，不表示请求被授权。修改 `authVersion` 或 `indexVersion` 也必须得到新 key，否则撤权或索引更新后仍会命中旧副本。

常见错误：把 key 放进请求头让服务端信任它；只对问题做 `trim()` 却保留日期/身份的空白差异；或只清空界面却让旧请求继续写缓存。服务端必须从可信会话重新授权，客户端 key 只做本地隔离。

### 2.3 用同一份Hook组织异步数据

<<< ../../typescript-examples/src/hooks.ts#query-hook

完整导入见[hooks.ts](../../typescript-examples/src/hooks.ts)。Hook使用LatestQuery区分每次运行，并在render时检查当前key。LatestQuery的直接刷新只在相同key下携带previous；当前Hook经retry重跑effect时会先清理旧运行，实际不保留previous，详见下文。退出传null，立即隐藏旧内容。加载器应响应signal；不响应时仍不能越过运行归属检查。

当前默认页面清楚显示加载或错误，不自动重试所有失败。是否保留旧结果、是否展示刷新失败，属于任务与授权约定：401/403/退出不能为减少闪烁继续展示旧授权内容。

`useAsyncData` 的调用与返回要一起读：

| 部分 | 当前实现 | 可观察结果 |
| --- | --- | --- |
| `identity` | `QueryIdentity \| null` | `null` 时 key 为 null，effect 取消并返回 idle |
| `question`/`asOf` | 与身份共同生成 key | 任一影响结果的字段变化都开始新运行 |
| `load(signal)` | 每次 effect 使用最新 ref 中的加载器 | 同一 key 因 `retry` 重跑，不必为了换函数引用反复请求 |
| `retry()` | 只增加 `attempt` | 同一 key 刷新；新 key 首次加载 |
| `state.key` 与当前 key 不同 | `visible` 强制返回 idle | 身份切换的那次 render 就隐藏旧数据 |

直接连续调用 `LatestQuery.run("B")` 且中间不取消时，它会把同 key 的成功数据放进 `loading.previous`。但 `useAsyncData.retry()` 是通过增加 `attempt` 重跑 effect：旧 effect 的 cleanup 先调用 `cancel(false)`，把内部状态置为 idle，所以当前 Hook 的实际重试从不带 previous 的 loading 开始。第 4 节直接演示的是 `LatestQuery` 的能力，不代表 Hook 已实现刷新保留。失败时当前实现也进入不带 previous 的 `error`；“失败仍显示旧数据”需要扩展状态与清理流程。跨 key 时连 `loading.previous` 也不能携带旧结果。

```ts
function visibleState<T>(state: QueryState<T>, currentKey: string | null): QueryState<T> {
  return currentKey !== null && state.status !== "idle" && state.key === currentKey
    ? state
    : { status: "idle" };
}
```

这段独立函数与源码的 `visible` 判断等价，可直接用于 reducer 测试。常见错误是直接返回内部 `state`，或在 loading 时无条件显示 `previous`，把跨租户旧数据当成刷新占位。

### 2.4 缓存与失效

先使单个组件的数据流正确，再按真实重复读取需求引入缓存。当前主线没有跨组件缓存，不能称为已经实现SWR。

| 变化 | 应有动作 |
| --- | --- |
| 同一身份同一key刷新 | 可保留明确标记的旧数据，重新验证 |
| 上传或资料更新 | 失效相应索引版本和查询 |
| 退出、换租户、撤权 | 隐藏旧范围内容，取消旧运行并清理该范围缓存 |
| TTL到期 | 重新验证；TTL不能代替撤权处理 |
| 网络暂时失败 | 保留输入，按约定呈现失败，不自动称旧结果仍有效 |

缓存中存入unknown再用as T读出，不会生成运行时校验。缓存入口应只接收已验证的值，键、类型、容量和失效策略共同设计。

“缓存命中”至少有三种含义，不能都显示成新鲜成功：

| 命中类型 | 是否请求 | 推荐显示 | 何时可标为新鲜 |
| --- | --- | --- | --- |
| fresh | 否 | 成功数据 | 未过 TTL，且没有收到失效事件 |
| stale，后台重验 | 是 | 旧数据 + “正在刷新” | 重验成功并写入新时间戳 |
| stale，但不能重验 | 否或等待用户 | 旧数据 + “可能已过期” | 不能仅凭旧副本宣称新鲜 |

同一身份、同一 key 的一次刷新，**预期状态顺序**是：

```text
success(data=旧结果)
→ loading(key=K, previous=旧结果)
→ success(data=新结果)
```

刷新失败时有两种明确产品选择：清空后显示错误，或保留旧结果并显示“刷新失败，数据可能已过期”。当前 `QueryState` 的 error 分支没有 previous，所以第二种选择必须先扩展类型和 reducer，不能在渲染层偷偷从缓存再取一份。上传后应主动失效相关 key；只等 TTL 到期会继续展示旧索引。

### 2.5 重复请求与共享取消

共享Promise只适合相同身份、相同条件的只读查询。若两个组件共享请求，一个组件卸载时直接abort底层请求，会影响另一个；需安排订阅者生命周期或使用经过验证的查询库。写动作的幂等不能用这种前端去重代替。

本章把共享缓存作为深化任务，不给一个没有取消/失效约定的Map宣称完整实现。下面只演示“相同 key 合并进行中的只读请求 + 最后一个订阅者离开才取消”，不包含缓存、重试和失效：

```ts
function shareReads<T>(load: (key: string, signal: AbortSignal) => Promise<T>) {
  type Entry = { promise: Promise<T>; users: number; abort: AbortController };
  const pending = new Map<string, Entry>();
  return (key: string, signal?: AbortSignal) => {
    let entry = pending.get(key);
    if (!entry) {
      const abort = new AbortController();
      entry = {
        users: 0,
        abort,
        promise: Promise.resolve().then(() => {
          if (abort.signal.aborted) throw abort.signal.reason;
          return load(key, abort.signal);
        }),
      };
      pending.set(key, entry);
      const created = entry;
      const removeSettled = () => {
        if (pending.get(key) === created) pending.delete(key);
      };
      void created.promise.then(removeSettled, removeSettled);
    }
    entry.users += 1;
    let active = true;
    const release = () => {
      if (!active) return;
      active = false;
      entry.users -= 1;
      signal?.removeEventListener("abort", release);
      if (entry.users === 0) {
        if (pending.get(key) === entry) pending.delete(key);
        entry.abort.abort();
      }
    };
    if (signal?.aborted) release();
    else signal?.addEventListener("abort", release, { once: true });
    const result = { promise: entry.promise, release };
    if (entry.users === 0) void result.promise.catch(() => {});
    if (signal?.aborted) {
      return { promise: Promise.reject(signal.reason), release };
    }
    return result;
  };
}
```

调用形式是 `const a = acquire(key, signalA); const b = acquire(key, signalB)`。还有订阅者时，两者获得同一个 `promise`，但各自调用 `release()` 或通过自己的 signal 离开；最后一个离开才 abort，一个组件卸载不会误伤另一个。已经离开的调用方拿到本地拒绝的Promise，不等同于底层请求已经停止。

```ts
import assert from "node:assert/strict";

let calls = 0;
const acquire = shareReads(async (key, signal) => {
  calls += 1;
  if (signal.aborted) throw signal.reason;
  return "结果";
});
const first = new AbortController();
const a = acquire("K", first.signal);
const b = acquire("K");
assert.equal(a.promise, b.promise);
first.abort();
assert.equal(await a.promise, "结果");
console.log(await b.promise, calls);
b.release();

const cancelledBeforeStart = new AbortController();
let cancelledCalls = 0;
const acquireCancelled = shareReads(async () => {
  cancelledCalls += 1;
  return "不应执行";
});
const c = acquireCancelled("K2", cancelledBeforeStart.signal);
cancelledBeforeStart.abort();
await assert.rejects(c.promise, { name: "AbortError" });
assert.equal(cancelledCalls, 0);
```

这里从 `node:assert/strict` 默认导入 `assert`。**预期输出**为 `结果 1`：第二个订阅者接手后，即使第一个订阅者已经取消，底层共享请求仍只调用一次并完成，两个调用方得到同一结果；启动前就取消的订阅得到 `AbortError`，加载器调用次数保持0。返回前检查调用方的`signal.aborted`：调用时已经取消的订阅得到本地拒绝；已经发出去的共享Promise不因其中一个订阅者离开而改成拒绝，其他订阅者仍可接收同一结果。没有订阅者时附加的拒绝处理只避免“无人接收”的未处理拒绝，不吞掉调用方收到的错误。编译先运行 `pnpm exec tsc --noEmit`；这个最小实现要求加载器响应 `signal`，且同一个 key 的调用方约定返回同一 `T`。完成回调和 `release` 都比较 `entry` 身份，避免旧轮次迟到后删掉同 key 的新请求。`load` 前的 `aborted` 检查不能替代加载器自身的取消响应，只关闭“尚未启动的请求”；已开始的请求是否停止，仍取决于真实 `fetch`/SDK 和加载器。常见错误是用全局 Map 让不同资源类型共享 key，或请求完成后不删除 pending，导致后续一直拿到旧 Promise。

### 2.6 错误边界

React 的错误边界是一个类组件，捕获子树渲染/生命周期中的异常：

```tsx
import { Component, type ErrorInfo, type ReactNode } from "react";

type BoundaryProps = { fallback: ReactNode; children: ReactNode };
type BoundaryState = { failed: boolean };

export class ErrorBoundary extends Component<BoundaryProps, BoundaryState> {
  state: BoundaryState = { failed: false };

  static getDerivedStateFromError(): BoundaryState {
    return { failed: true };
  }

  componentDidCatch(error: Error, info: ErrorInfo): void {
    console.error("面板渲染失败", error, info.componentStack);
  }

  render(): ReactNode {
    return this.state.failed ? this.props.fallback : this.props.children;
  }
}
```

错误边界捕获渲染期异常，不捕获事件处理器、异步回调、`setTimeout` 里的异常。异步错误要在数据层转成 `error` 状态，或由调用方 `try/catch` 后 `setState`。一个引用卡片崩溃，不应让整个页面白屏；用边界包住列表项或面板。

最小调用形式：

```tsx
function CitationPanel() {
  return <blockquote>引用内容</blockquote>;
}

<ErrorBoundary key={queryKey} fallback={<p role="alert">引用面板加载失败。</p>}>
  <CitationPanel />
</ErrorBoundary>
```

`queryKey` 变化时 key 变化，React 会卸载旧边界并挂载新边界，`failed` 因此重置；不提供 reset 按钮时，这是最简单的“换查询后重试渲染”。示例假定 `ErrorBoundary` 与 `queryKey` 已由调用处提供。边界应该包住可独立失败的面板，而不是只包一个必然抛错的叶子后让整页失去操作入口。

### 2.7 错误分类与重试

| 错误 | 是否重试 | UI |
| --- | --- | --- |
| 输入不合法 422 | 否 | 标出字段 |
| 未认证 401 | 否 | 跳登录/提示授权 |
| 无权限 403 | 否 | 显示无权限，不泄露资源 |
| 限流 429 | 是，按 `Retry-After` | 倒计时/退避 |
| 超时/网络 | 是，有限次 | 重试按钮 |
| 5xx | 视 `retryable` | 重试/联系支持 |

重试要保留用户输入，不能把表单清空；是否保留上次成功数据取决于同一身份、同一任务和错误类别；不能把所有失败都按保留旧内容处理。

### 2.8 渲染错误与异步错误分别处理

```tsx
import { useState } from "react";

export function RunButton({ run }: { run: () => void }) {
  const [error, setError] = useState<string | null>(null);
  return <button type="button" onClick={() => {
    try {
      run();
      setError(null);
    } catch (cause) {
      setError(cause instanceof Error ? cause.message : "操作失败");
    }
  }}>{error ?? "执行"}</button>;
}
```

点击后如果 `run` 抛出 `Error("保存失败")`，**预期界面**从“执行”变为“保存失败”；不会触发外面的 `ErrorBoundary`。如果 `run` 返回 Promise，应改成 `async` 处理器并 `await`，否则拒绝不会被这个同步 `try/catch` 捕获。请求错误通常不必抛到事件层，由数据 Hook 返回 `error` 状态更利于统一显示。

| 错误来源 | 推荐承接位置 | 重试时保留什么 |
| --- | --- | --- |
| 子树渲染抛错 | `ErrorBoundary` 的 fallback | 输入与 key；通过新 key/reset 重挂载 |
| 点击处理同步抛错 | 事件处理器 `try/catch` + 状态 | 用户已填写内容 |
| 请求 Promise 拒绝 | 数据层 catch + `QueryState.error` | 输入；旧数据仅在同身份同 key 且产品允许时保留 |
| 定时器/订阅回调 | 回调自身 catch 或统一错误队列 | 按任务判断，不能指望边界 |

`Retry-After` 可能是秒数，也可能是 HTTP 日期；解析失败时采用有上限的退避，不要无限等待。401/403 不保留旧授权内容，429 重试前仍要检查当前身份与 key 是否变化。

## 3. 原理讲解与推导

### 3.1 服务端状态是“副本”，不是真相

前端缓存只是远端数据的副本。它可能过期、被撤权、被其他人修改。UI 要能表达“这是旧数据”“正在刷新”“刷新失败”，而不是把缓存当成永远正确。

### 3.2 失效策略比缓存时间更重要

TTL 只能处理“自然过期”，处理不了“用户刚审批/刚上传”。写操作后要主动失效相关查询；无法精确失效时，至少刷新当前列表并提示其他页面可能过期。

### 3.3 错误边界是隔离，不是恢复

边界阻止错误扩散，给用户一个可操作的 fallback；它不修复数据，也不自动重试。fallback 要提供“重试/返回/联系支持”，并把错误 ID 带进日志。

## 4. 示例与逐步走查

继续使用[第8章同一页面](08-React组件与状态.md)，不再维护另一套SearchResult。先跑已有身份隔离与旧结果回归，再增加一次刷新体验：

1. 让当前查询成功，按同一条件刷新，核对key未变。
2. 让本次刷新失败，选择清除旧结果或明确标记过期，并写出理由。
3. 改为退出或换租户，旧内容必须立即隐藏，不能沿用上一步的保留策略。
4. 让旧加载器忽略取消后返回，确认它不能覆盖新身份结果。

扩展previous展示时补相同key刷新测试；当前React回归已经验证切换身份、退出和迟到完成。

用本地可控 Promise 可以把这些步骤写成确定性回归，不需要浏览器或网络：

```ts
import { LatestQuery, type QueryState } from "../../typescript-examples/src/query.js";

function deferred<T>() {
  let resolve!: (value: T) => void;
  const promise = new Promise<T>((done) => { resolve = done; });
  return { promise, resolve };
}

async function inspectRuns(): Promise<void> {
  const seen: QueryState<string>[] = [];
  const query = new LatestQuery<string>((state) => seen.push(state));
  const old = deferred<string>();
  const current = deferred<string>();
  const first = query.run("A", () => old.promise);
  const second = query.run("B", () => current.promise);
  current.resolve("B-result");
  await second;
  old.resolve("A-result"); // 即使加载器不响应取消，也不能覆盖 B
  await first;
  console.log(seen.map((state) => state.status).join(","));

  const refresh = query.run("B", () => Promise.resolve("B-new"));
  console.log(seen.at(-1));
  await refresh;
  console.log(seen.at(-1));
  query.cancel();
  console.log(seen.at(-1));
}
void inspectRuns();
```

**预期输出**：

```text
loading,loading,success
{ status: 'loading', key: 'B', previous: 'B-result' }
{ status: 'success', key: 'B', data: 'B-new' }
{ status: 'idle' }
```

执行过程：先 `pnpm exec tsc --noEmit`，再运行转译模块。这个例子证明的是运行归属与同 key previous，不是跨组件缓存；每次新建 `LatestQuery` 都会从 idle 开始。若把 `query.run("A")` 的完成放在 `query.run("B")` 之前，最终成功数据就会是 A，因此测试必须明确完成顺序，不能只断言“最后有结果”。

## 5. 练习

### 练习一：跟写

利用当前 `useAsyncData` 的identity=null停用机制，给调用处增加空输入保护：输入为空时不请求且返回idle。再讨论是否需要单独的enabled参数，并验证取消后迟到完成不能重新显示结果。

### 练习二：改造

实现按 key 去重：两个组件同时请求同一 `searchKey`，只发一次网络请求；其中一个取消时，另一个仍能拿到结果。说明为什么写操作不能这样合并。

### 练习三：独立

给搜索结果加“刷新”按钮：刷新时保留旧数据、显示 loading、失败时保留旧数据并提示；写一个 reducer 测试覆盖 idle→loading→success→loading→error 的顺序。

## 6. 验收与自测

**行为验收：** 当前基线检查key、身份切换、取消和重试；完成扩展后再验同key刷新保留旧数据、缓存失效与局部错误隔离。跨key或跨身份始终隐藏旧结果；不能把扩展目标算作当前Hook已实现。

| 场景 | 可观察断言 |
| --- | --- |
| 两订阅者同 key，取消其中一个 | 加载调用计数为 1；剩下订阅者仍收到结果；其 signal 未 aborted |
| 最后一个订阅者离开 | 底层 signal 变为 aborted；迟到完成不发布成功 |
| 同 key 刷新成功（扩展） | 经历 `success → loading(previous) → success`，旧数据只在刷新期出现 |
| 同 key 刷新失败（扩展） | 明确进入 error，并按所选契约清空或标记旧数据过期 |
| 退出/换租户/撤权 | 当前 render 立即 idle；旧内容不可见；旧运行不能写回 |
| 面板子树抛错 | 该面板显示 fallback，页面其他操作仍可用 |
| 事件处理器抛错 | 不被边界捕获；由事件层转为可见错误状态 |
| TTL 到期但未收到主动失效 | 标记 stale 并重验，不继续标为新鲜 |

**原理验收：** 能解释客户端/服务端状态、缓存失效与 TTL、错误边界的捕获范围；能说出一个“缓存 key 漏字段”的事故。

### 6.1 先预测，再查看解释

错误边界能捕获 `onClick` 里 `throw new Error()` 吗？

<details>
<summary>完成预测后查看解释</summary>

不能。错误边界只捕获渲染、生命周期和构造函数中的异常；事件处理器、异步回调和定时器里的异常不会触发它。事件处理器要自己 `try/catch` 并更新错误状态，或让数据层返回 `error`。

</details>

## 7. 面试问答与参考回答

**问：客户端状态和服务端状态怎么区分？**

客户端状态由组件拥有（输入草稿、展开状态）；服务端状态是远端数据的副本（搜索结果、用户资料），需要缓存 key、失效、重试和并发控制。两者混在一个 `useState` 里会导致同步 bug。

**问：缓存 key 应该包含什么？**

所有影响结果的输入：查询词、日期、租户/身份、模型/索引版本、分页/过滤条件。漏掉身份会把数据串租户；漏掉版本会把旧制度答案给新版本。

**问：错误边界能替代 try/catch 吗？**

不能。它只捕获子树渲染期异常，不捕获事件处理器和异步回调。异步错误要在数据层转成状态，或显式 `try/catch`；边界用于隔离 UI 崩溃。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 服务端数据只是副本，什么时候能复用缓存、什么时候必须重新取，一个卡片崩溃又该由谁接住？

**一条主线：**

```text
查询 key（身份/租户/日期/版本）→ 去重与取消 → 缓存与 previous → 失效/刷新 → 错误分类 + 错误边界隔离
```

**三个关键词：** 副本、失效、隔离。服务端状态只是副本，失效策略决定它何时还可信，错误边界把渲染崩溃限制在一个面板内。

**最容易错：**

- 把查询 key 当授权凭据，换租户或退出后仍显示旧范围内容。
- 只设 TTL 不主动失效，审批或上传后继续读旧索引。
- 把错误边界当恢复手段，或以为它能捕获 `onClick`、异步回调和 `setTimeout`。
- 共享请求时一个组件卸载就 abort，误伤其他订阅者；缓存里存 `unknown` 再 `as T` 读出。

**与前后章：** 上一章的 effect 与 cleanup 给出挂载、取消和退出清理；下一章需要把流式 token、引用和待复核状态接进同一页面。

**学完应能：**

- 设计包含身份、租户、日期和索引版本的查询 key，并验证换身份立即隐藏旧结果；
- 用同一 key 刷新并保留旧数据，失败时明确标记过期而不是假装成功；
- 用错误边界包住引用列表，让一个卡片崩溃不白屏整页；
- 按 401/403/429/超时分别决定重试与是否保留旧数据。
