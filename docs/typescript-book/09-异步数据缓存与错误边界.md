# 第09章　异步数据、缓存与错误边界

[上一章](08-React组件与状态.md) · [全书目录](教材目录.md) · [下一章](10-流式AI界面.md)

## 1. 学习目标与前置知识

能区分客户端状态与服务端状态，能为查询设计稳定 key，处理缓存、失效、重试、竞态和空状态，能用错误边界阻止一个组件崩溃拖垮整页。前置：第 8 章；第 4–5 章的校验与取消。

**本章从这里开始：** 搜索页每次输入都发请求，返回顺序不固定；从详情页返回列表，数据已经过期；一个引用卡片抛异常，整页白屏。React 的 `useState` 能保存结果，但不会自动处理“缓存、失效、重试、隔离”。

## 2. 基础知识讲解

### 2.1 客户端状态与服务端状态

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| 客户端状态 | 输入框草稿、展开/收起、主题 | 组件拥有，变化由用户触发 |
| 服务端状态 | 搜索结果、文档详情、用户资料 | 远端拥有，可能过期，需要重新验证 |

服务端状态不要全部塞进 `useState` 手动同步。它需要：缓存 key、过期/失效、重复请求合并、错误重试、取消。可以自己实现最小版本，也可以用 TanStack Query/SWR；本章先手写一个，理解机制后再换库。

### 2.2 查询key是副本的归属，不是授权凭据

主线使用第8章query.ts的searchKey：主体、租户、授权版本、索引版本、问题与业务日期共同组成键。客户端不能用这个键向服务端自授权限；服务端仍从可信凭据授权。

先建立一条允许的查询，切换租户但保留相同问题与日期，再让旧请求完成。只在key里写问题和日期，会让两次身份共用范围；只在开始加载时清空，也挡不住迟到回调。

### 2.4 缓存与失效

先使单个组件的数据流正确，再按真实重复读取需求引入缓存。当前主线没有跨组件缓存，不能称为已经实现SWR。

| 变化 | 应有动作 |
| --- | --- |
| 同一身份同一key刷新 | 可保留明确标记的旧数据，重新验证 |
| 上传或资料更新 | 失效相应索引版本和查询 |
| 退出、换租户、撤权 | 隐藏旧范围内容，取消旧运行并清理该范围缓存 |
| TTL到期 | 重新验证；TTL不能代替撤权处理 |
| 网络暂时失败 | 保留输入，按约定呈现失败，不自动称旧结果仍有效 |

缓存中存入unknown再用as T读出，不会生成运行时校验。缓存入口应只接收已验证的值，键、类型、容量和失效策略共同设计。

### 2.5 重复请求与共享取消

共享Promise只适合相同身份、相同条件的只读查询。若两个组件共享请求，一个组件卸载时直接abort底层请求，会影响另一个；需安排订阅者生命周期或使用经过验证的查询库。写动作的幂等不能用这种前端去重代替。

本章把共享缓存作为深化任务，不给一个没有取消/失效约定的Map宣称完整实现。

### 2.6 错误边界

React 的错误边界是一个类组件，捕获子树渲染/生命周期中的异常：

```tsx
import { Component, type ErrorInfo, type ReactNode } from "react";

type BoundaryProps = { fallback: ReactNode; children: ReactNode };
type BoundaryState = { failed: boolean };

export class ErrorBoundary extends Component<BoundaryProps, BoundaryState> {
  state: BoundaryState = { failed: false };

  static getDerivedStateFromError(): BoundaryState {
    return { failed: true };
  }

  componentDidCatch(error: Error, info: ErrorInfo): void {
    console.error("面板渲染失败", error, info.componentStack);
  }

  render(): ReactNode {
    return this.state.failed ? this.props.fallback : this.props.children;
  }
}
```

错误边界捕获渲染期异常，不捕获事件处理器、异步回调、`setTimeout` 里的异常。异步错误要在数据层转成 `error` 状态，或由调用方 `try/catch` 后 `setState`。一个引用卡片崩溃，不应让整个页面白屏；用边界包住列表项或面板。

### 2.7 错误分类与重试

| 错误 | 是否重试 | UI |
| --- | --- | --- |
| 输入不合法 422 | 否 | 标出字段 |
| 未认证 401 | 否 | 跳登录/提示授权 |
| 无权限 403 | 否 | 显示无权限，不泄露资源 |
| 限流 429 | 是，按 `Retry-After` | 倒计时/退避 |
| 超时/网络 | 是，有限次 | 重试按钮 |
| 5xx | 视 `retryable` | 重试/联系支持 |

重试要保留用户输入，不能把表单清空；是否保留上次成功数据取决于同一身份、同一任务和错误类别；不能把所有失败都按保留旧内容处理。

## 3. 原理讲解与推导

### 3.1 服务端状态是“副本”，不是真相

前端缓存只是远端数据的副本。它可能过期、被撤权、被其他人修改。UI 要能表达“这是旧数据”“正在刷新”“刷新失败”，而不是把缓存当成永远正确。

### 3.2 失效策略比缓存时间更重要

TTL 只能处理“自然过期”，处理不了“用户刚审批/刚上传”。写操作后要主动失效相关查询；无法精确失效时，至少刷新当前列表并提示其他页面可能过期。

### 3.3 错误边界是隔离，不是恢复

边界阻止错误扩散，给用户一个可操作的 fallback；它不修复数据，也不自动重试。fallback 要提供“重试/返回/联系支持”，并把错误 ID 带进日志。

## 4. 示例与逐步走查

继续使用[第8章同一页面](08-React组件与状态.md)，不再维护另一套SearchResult。先跑已有身份隔离与旧结果回归，再增加一次刷新体验：

1. 让当前查询成功，按同一条件刷新，核对key未变。
2. 让本次刷新失败，选择清除旧结果或明确标记过期，并写出理由。
3. 改为退出或换租户，旧内容必须立即隐藏，不能沿用上一步的保留策略。
4. 让旧加载器忽略取消后返回，确认它不能覆盖新身份结果。

扩展previous展示时补相同key刷新测试；当前React回归已经验证切换身份、退出和迟到完成。

## 5. 练习

### 练习一：跟写

利用当前 `useAsyncData` 的identity=null停用机制，给调用处增加空输入保护：输入为空时不请求且返回idle。再讨论是否需要单独的enabled参数，并验证取消后迟到完成不能重新显示结果。

### 练习二：改造

实现按 key 去重：两个组件同时请求同一 `searchKey`，只发一次网络请求；其中一个取消时，另一个仍能拿到结果。说明为什么写操作不能这样合并。

### 练习三：独立

给搜索结果加“刷新”按钮：刷新时保留旧数据、显示 loading、失败时保留旧数据并提示；写一个 reducer 测试覆盖 idle→loading→success→loading→error 的顺序。

## 6. 验收与自测

**行为验收：** 当前基线检查key、身份切换、取消和重试；完成扩展后再验同key刷新保留旧数据、缓存失效与局部错误隔离。跨key或跨身份始终隐藏旧结果；不能把扩展目标算作当前Hook已实现。

**原理验收：** 能解释客户端/服务端状态、缓存失效与 TTL、错误边界的捕获范围；能说出一个“缓存 key 漏字段”的事故。

## 7. 面试问答与参考回答

**问：客户端状态和服务端状态怎么区分？**

客户端状态由组件拥有（输入草稿、展开状态）；服务端状态是远端数据的副本（搜索结果、用户资料），需要缓存 key、失效、重试和并发控制。两者混在一个 `useState` 里会导致同步 bug。

**问：缓存 key 应该包含什么？**

所有影响结果的输入：查询词、日期、租户/身份、模型/索引版本、分页/过滤条件。漏掉身份会把数据串租户；漏掉版本会把旧制度答案给新版本。

**问：错误边界能替代 try/catch 吗？**

不能。它只捕获子树渲染期异常，不捕获事件处理器和异步回调。异步错误要在数据层转成状态，或显式 `try/catch`；边界用于隔离 UI 崩溃。

## 8. 本章小结与参考

- 服务端状态是副本；key、失效、重试、取消缺一不可。
- 查询 key 必须包含身份、日期和版本。
- 加载保留旧数据；错误分类驱动重试；写后主动失效。
- 错误边界隔离渲染崩溃，不处理异步异常。
