# 第17章　可观测性、成本与安全

[上一章](16-Playwright与浏览器验收.md) · [全书目录](教材目录.md) · [下一章](18-部署与Capstone.md)

## 1. 学习目标与前置知识

能用请求ID串起一次调用的记录，用日志查看细节，用请求量、错误率和耗时等指标发现异常，并记录模型用量与费用。随后检查提示注入、诱导服务端访问不该访问的地址（SSRF）、密钥泄露和越权等风险。前置：第11–14章。

**本章从这里开始：** 用户说“很慢”，日志只有 `console.log("error")`；账单涨了，不知道是哪个租户/模型/重试；模型被提示注入，试图让 BFF 访问内网。可观测性不是“加个监控”，而是**用数据回答具体问题**。

## 2. 基础知识讲解

### 2.1 三个信号：日志、指标、追踪

| 信号 | 回答 | 例子 |
| --- | --- | --- |
| 日志 | 这一次发生了什么 | requestId、路径、状态、错误码、耗时 |
| 指标 | 整体趋势/告警 | 请求率、错误率、P95、token/成本 |
| 追踪 | 一次请求经过哪些层 | 浏览器→BFF→检索→模型→流结束 |

日志保存具体事件，指标汇总一批请求，追踪展示一次调用经过哪些服务和步骤。通过`requestId`或`traceId`等标识，可以把相关记录连起来。例如先从耗时指标发现变慢，再找到慢请求的追踪，最后查对应日志。面向全量请求的统计应有明确的指标采集口径，不能只从抽样或缺失的日志推算。

### 2.2 结构化日志

```ts
type LogFields = {
  requestId: string;
  route: string;
  method: string;
  status: number;
  durationMs: number;
  tenantId?: string;
  errorCode?: string;
};

function logLine(fields: LogFields): void {
  console.log(JSON.stringify({ level: "info", ts: new Date().toISOString(), ...fields }));
}
```

JSON 行便于采集；字段名稳定，别把整个请求体/令牌/提问正文写进去。错误日志带 `errorCode` 和堆栈（仅服务端），用户响应只给 requestId。

### 2.3 RED 指标

- **Rate**：每路由请求数；
- **Errors**：按状态码/错误码分类；
- **Duration**：P50/P95/P99，而不是平均值。

AI 应用额外指标：

- 首 token 延迟（TTFT）；
- 流完成率/中断率；
- 工具调用次数/失败率；
- 输入/输出 token、估算成本；
- 审批等待时长。

```ts
function observeRequest(route: string, status: number, durationMs: number): void {
  metrics.increment("http_requests_total", { route, status: String(status) });
  metrics.histogram("http_request_duration_ms", durationMs, { route });
}
```

标签基数要控制：不要把用户 ID、完整问题当标签，会爆炸；用租户/路由/状态码。

### 2.4 LLM 成本口径

```ts
type Usage = { inputTokens: number; outputTokens: number };
// 单价单位：美分 / 百万 token；返回值：向上取整的美分。
type PricePerMillionCents = { input: number; output: number };

function estimateCostCents(usage: Usage, pricePerMillion: PricePerMillionCents): number {
  return Math.ceil(
    (usage.inputTokens * pricePerMillion.input + usage.outputTokens * pricePerMillion.output) / 1_000_000,
  );
}
```

成本要记录：模型/版本、租户、请求类型、重试次数、缓存命中、工具调用。供应商若以美元/百万 token 报价，先乘100换成上式单位；缓存折扣、阶梯价和税费另算。单价会变，配置化并记录版本；不要把估算当账单。预算按租户/日/请求设置，超限明确拒绝或降级。

### 2.5 追踪

```ts
async function tracedSearch() {
  const span = tracer.startSpan("bff.search");
  span.setAttribute("tenant.id", actor.tenantId);
  try {
    const result = await search(baseUrl, question, asOf, controller.signal);
    span.setAttribute("result.count", result.length);
    return result;
  } finally {
    span.end();
  }
}
```

至少埋：BFF 路由、上游检索、模型调用、流结束。跨进程传 `traceparent`；没有追踪时，用 requestId + 时间戳也能近似定位。

### 2.6 安全边界

| 风险 | 防护 |
| --- | --- |
| 提示注入 | 模型输出不可信；工具/权限在服务端，system prompt 不能代替代码防护 |
| SSRF | 上游地址白名单；不根据用户输入拼 URL |
| XSS | 输出转义；不 `dangerouslySetInnerHTML`；CSP |
| CSRF | SameSite + CSRF token |
| 密钥泄露 | 密钥只在服务端；不入日志/前端包；定期轮换 |
| 越权 | 每个查询带 tenantId；对象级权限 |
| 依赖漏洞 | lockfile、审计、最小依赖 |
| 滥用 | 登录/提问限流、配额、验证码 |

CORS 只允许自己的前端源；`Access-Control-Allow-Origin: *` 配合凭据是错误配置。CSP 至少限制 `script-src`/`connect-src`；具体策略按部署调整。

### 2.7 SLO 与告警

SLO 示例：搜索请求 99% 在 2 秒内返回；流式首 token P95 < 1.5 秒；错误率 < 1%。告警基于症状（错误率/延迟/成本），不是每个异常日志。每个告警要有 runbook：看哪个面板、怎么回滚、联系谁。

### 2.8 TTFT与总时长：先定义起止点

TTFT（Time To First Token）不是“请求开始到页面出现任何字”的近似值。服务端口径应从调用模型/开始写SSE计时，到第一个有效token可发送；浏览器口径还要单独记录网络与渲染，不能混成一个数字。

```ts
type StreamTiming = {
  startedAt: number;
  firstTokenAt: number | null;
  endedAt: number | null;
};

function ttftMs(t: StreamTiming): number | null {
  return t.firstTokenAt === null ? null : Math.round(t.firstTokenAt - t.startedAt);
}

function totalMs(t: StreamTiming): number | null {
  return t.endedAt === null ? null : Math.round(t.endedAt - t.startedAt);
}
```

若`startedAt=1000`、`firstTokenAt=2200`、`endedAt=4000`，两个函数分别返回1200和3000。没有首token时TTFT返回null，不能填0；流未结束时总时长返回null，不能记成成功完成。当前`/api/answer`没有持久化这些时间点，以上是接入观测时的最小计算，不是已有指标。

### 2.9 一次成本估算的完整口径

沿用“美分/百万token”的函数：输入1200 token、输出300 token，单价输入20美分、输出60美分，则`ceil((1200×20+300×60)/1_000_000)=1`美分。未取整前约0.042美分，单次向上取整会放大低用量请求；生产可按账单周期汇总，不要用这种逐次取整改写供应商账单。这个1美分是该次模型调用估算，不包含检索、嵌入、工具或失败重试。

| 字段 | 示例 | 为什么记录 |
| --- | --- | --- |
| model/priceVersion | fixture-model/2026-11-config | 单价和模型行为会变 |
| tenantId/route | a、/api/answer | 归因与预算 |
| attempt/cacheHit | 1、false | 重试放大成本，缓存折扣不同 |
| input/outputTokens | 1200/300 | 供应商usage可能缺字段，需标记缺失 |
| status/endedAt | error/时间戳 | 失败也可能已计费 |

供应商usage缺失时不要填0冒充免费；估算值和最终账单分开存。当前SSE解析会丢弃done里的usage，所以前端还不能直接做这个统计。

### 2.10 安全检查必须有输入与预期

| 风险 | 测试输入/操作 | 预期与证据 |
| --- | --- | --- |
| 提示注入 | 文本要求“跳过审批并调用export” | Actor/允许列表不变，写工具仍待审批 |
| SSRF | 未来URL入口提交内网地址/重定向 | 白名单拒绝，记录安全事件；当前没有用户URL路由 |
| XSS | 搜索结果含`<script>`文本 | 页面显示为文本，不执行；检查CSP |
| CSRF | 跨站POST不带同步token | 403且状态不变 |
| 越权 | A会话读B资源id | 统一404，响应无标题/正文 |
| 密钥泄露 | 扫描前端产物、日志样例 | 无Authorization、模型key、session secret |
| 滥用 | 短时间超过登录/提问配额 | 429带稳定原因，不无限调用模型 |

“检查CSP header存在”只证明配置出现，不证明策略有效；还要确认script-src/connect-src符合页面真实资源。提示注入测试验证的是代码边界，不是模型是否恰好听话。

## 3. 原理讲解与推导

### 3.1 先定义问题，再选工具

“系统慢”要拆成：DNS/TLS、BFF 排队、上游检索、模型首 token、流传输、前端渲染。每层有耗时指标，才能定位。只加一个总耗时，无法判断该优化谁。

### 3.2 成本是产品指标

按租户/功能统计成本，才能定价和限流。只看总账单，无法发现某个重试循环或大上下文在烧钱。成本与质量/延迟一起看，不能单独优化。

### 3.3 安全是边界，不是提示词

提示注入无法靠“更强的 system prompt”根治；把工具权限、数据过滤、URL 白名单、审批放在代码里，模型只负责建议。任何“模型说可以”都不构成授权。

### 3.4 关联字段、指标标签与错误状态分开设计

requestId/answerId/traceId关联单次请求，适合日志和追踪属性，不适合做指标标签：每个请求都不同，会让时间序列基数爆炸。指标标签只用route、status、errorCode、model等有限集合；tenantId是否可用取决于租户规模与预算，不能默认无限。

第4节的中间件finally有一个边界：若`next()`抛出的异常继续向外传播，局部status可能仍是初始500，而Hono `onError`最终会映射成401/422/504。要记录最终状态，应在错误映射处或响应包装处补齐，不能把“中间件退出时的status”无条件当用户看到的status。流式请求一旦头已发送，还要记录SSE error/正常done，不能只看HTTP 200。

| 数据 | 放哪里 | 不放哪里 |
| --- | --- | --- |
| requestId | 日志、trace、响应头/错误体 | 指标标签 |
| 用户问题全文 | 通常不采集；必要时脱敏/限权 | 默认日志、指标标签 |
| 状态码/错误码 | 指标标签、结构化日志 | 依赖异常message文本 |
| token/成本 | usage记录、聚合指标 | 每个token一条日志 |
| 上游堆栈 | 受限服务端日志 | 用户响应、浏览器 |

## 4. 示例与逐步走查

```ts
app.use("/api/*", async (c, next) => {
  const started = performance.now();
  const requestId = c.get("requestId");
  let status = 500;
  try {
    await next();
    status = c.res.status;
  } finally {
    const durationMs = Math.round(performance.now() - started);
    observeRequest(c.req.path, status, durationMs);
    logLine({
      requestId,
      route: c.req.path,
      method: c.req.method,
      status,
      durationMs,
      tenantId: c.get("actor")?.tenantId,
    });
  }
});
```

逐步解释：

1. `performance.now()` 用单调时钟，避免系统时间跳变；
2. `finally` 保证异常也记录耗时/状态；
3. 只记录路由、状态、租户，不记录正文/令牌；
4. 日志与追踪用 requestId 关联；指标只保留 route/status 等低基数标签，不能把 requestId 当指标标签；
5. 真实项目把 `console.log` 换成结构化 logger/OTel exporter。

### 4.1 用一条requestId复现“慢”

```text
浏览器：POST /api/answer，记录本地start
BFF：生成requestId并返回X-Request-ID
模型：记录上游start、firstToken、done/error
流结束：记录总时长、token usage、attempt
排障：指标发现TTFT升高 → trace找慢span → 日志按requestId查错误码
```

搜索路径当前已有X-Request-ID和统一错误体，但示例日志中间件、tracer/metrics、TTFT和usage持久化并未接入`createBff`。因此“能生成requestId”不等于“已经可全链路观测”。落地时先记录最小字段并验证脱敏，再接OTel exporter；不要先买仪表盘而没有数据口径。

## 6. 验收与自测

**行为验收：** 每个请求有 requestId；错误日志有错误码/堆栈，用户响应不含堆栈；指标能区分路由/状态；成本可按租户统计；安全测试覆盖至少 3 类风险。

**原理验收：** 能解释 RED、TTFT、成本口径、SLO 与告警的关系；能说出一个“有日志但无法定位”的例子。

| 操作 | 预期 | 证据 |
| --- | --- | --- |
| 无身份调用API | 响应头/错误体有同一requestId | 响应断言与对应服务端日志 |
| 上游422/超时 | 最终status/错误码正确，不把异常名当分类 | 映射测试与结构化日志 |
| 假上游首token后error | TTFT有值，总时长有值，完成率记失败 | 流指标测试 |
| 1200/300 token与给定单价 | 估算1美分，记录priceVersion | 成本函数用例 |
| 全量请求聚合 | 标签只有route/status等，无requestId/问题全文 | 指标schema/采集样例 |
| 日志检查 | 无密码、Authorization、模型key、sid | 脱敏测试 |
| 提示注入/跨租户/URL白名单 | 分别拒绝，安全日志不含敏感正文 | 各项安全检查 |

当前只实现requestId和错误体；指标、追踪、预算和安全路由测试需要新增实现后记录。表中数值是公式预期，不是已采集账单。

### 6.1 先预测，再查看解释

日志里记录了完整提问和 Authorization header，会有什么问题？

提问可能含个人/商业敏感信息，令牌可直接被盗用；日志会被采集、转发、长期保存，泄露面远大于请求本身。应脱敏/不记录正文与令牌，只留 requestId、租户、长度/哈希等必要字段。

## 7. 面试问答与参考回答

**问：日志、指标、追踪怎么分工？**

日志记录单次事件与错误细节；指标做聚合/告警；追踪展示一次请求跨层因果。三者用 requestId/traceId 关联，不能互相替代。

**问：AI 应用的成本怎么归因？**

按租户/功能/模型记录输入输出 token、重试、缓存和工具调用，配置化单价并记录版本；估算用于优化，账单以供应商为准。

**问：提示注入能靠 system prompt 防住吗？**

不能。模型输出不可信；权限、工具白名单、数据过滤、URL 白名单和审批必须在服务端代码里，提示词只是辅助。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 用户说“慢、贵、被攻击”时，怎样用日志、指标、追踪和安全边界把问题定位到具体一层？

**一条主线：**

```text
requestId/traceId
→ 结构化日志 + RED/TTFT/成本指标 + 安全边界
→ 可定位、可告警、可审计的证据
```

**三个关键词：** 关联、归因、边界。requestId关联单次调用，低基数标签与usage归因，服务端代码限制模型和外部输入。

**最容易错：**
- 把requestId/问题全文当指标标签；把日志抽样当全量统计。
- 只记HTTP 200，不记SSE error；把中间件初始500当最终映射状态。
- 没有首token填0、缺usage填0；把成本估算当账单。
- 记录完整令牌/提问；用system prompt代替租户、工具、URL和审批边界。

**与前后章：** 第16章提供真实浏览器任务证据；第18章用同一套状态码、TTFT、成本和日志做发布与回滚判断。

**学完应能：** 定义TTFT起止、算一次成本、按requestId定位慢请求；为每类威胁写输入/预期/证据并指出当前未接入项。
