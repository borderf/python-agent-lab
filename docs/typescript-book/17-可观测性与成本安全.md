# 第17章　可观测性、成本与安全

[上一章](16-Playwright与浏览器验收.md) · [全书目录](教材目录.md) · [下一章](18-部署与Capstone.md)

## 1. 学习目标与前置知识

能给 BFF/前端加请求 ID、结构化日志、RED 指标和 LLM 成本口径；能定位慢在 BFF、上游还是模型；能列出 AI 应用的注入、SSRF、密钥泄露与越权风险，并给出可验证的防护。前置：第 11–14 章。

**本章从这里开始：** 用户说“很慢”，日志只有 `console.log("error")`；账单涨了，不知道是哪个租户/模型/重试；模型被提示注入，试图让 BFF 访问内网。可观测性不是“加个监控”，而是**用数据回答具体问题**。

## 2. 基础知识讲解

### 2.1 三个信号：日志、指标、追踪

| 信号 | 回答 | 例子 |
| --- | --- | --- |
| 日志 | 这一次发生了什么 | requestId、路径、状态、错误码、耗时 |
| 指标 | 整体趋势/告警 | 请求率、错误率、P95、token/成本 |
| 追踪 | 一次请求经过哪些层 | 浏览器→BFF→检索→模型→流结束 |

三者用同一个 `requestId`/`traceId` 关联。日志是事件，指标是聚合，追踪是因果链；不要用日志做全量统计。

### 2.2 结构化日志

```ts
type LogFields = {
  requestId: string;
  route: string;
  method: string;
  status: number;
  durationMs: number;
  tenantId?: string;
  errorCode?: string;
};

function logLine(fields: LogFields): void {
  console.log(JSON.stringify({ level: "info", ts: new Date().toISOString(), ...fields }));
}
```

JSON 行便于采集；字段名稳定，别把整个请求体/令牌/提问正文写进去。错误日志带 `errorCode` 和堆栈（仅服务端），用户响应只给 requestId。

### 2.3 RED 指标

- **Rate**：每路由请求数；
- **Errors**：按状态码/错误码分类；
- **Duration**：P50/P95/P99，而不是平均值。

AI 应用额外指标：

- 首 token 延迟（TTFT）；
- 流完成率/中断率；
- 工具调用次数/失败率；
- 输入/输出 token、估算成本；
- 审批等待时长。

```ts
function observeRequest(route: string, status: number, durationMs: number): void {
  metrics.increment("http_requests_total", { route, status: String(status) });
  metrics.histogram("http_request_duration_ms", durationMs, { route });
}
```

标签基数要控制：不要把用户 ID、完整问题当标签，会爆炸；用租户/路由/状态码。

### 2.4 LLM 成本口径

```ts
type Usage = { inputTokens: number; outputTokens: number };

function estimateCostCents(usage: Usage, pricePerMillion: { input: number; output: number }): number {
  return Math.ceil(
    (usage.inputTokens * pricePerMillion.input + usage.outputTokens * pricePerMillion.output) / 1_000_000,
  );
}
```

成本要记录：模型/版本、租户、请求类型、重试次数、缓存命中、工具调用。单价会变，配置化并记录版本；不要把估算当账单。预算按租户/日/请求设置，超限明确拒绝或降级。

### 2.5 追踪

```ts
async function tracedSearch() {
  const span = tracer.startSpan("bff.search");
  span.setAttribute("tenant.id", actor.tenantId);
  try {
    const result = await search(baseUrl, question, asOf, controller.signal);
    span.setAttribute("result.count", result.length);
    return result;
  } finally {
    span.end();
  }
}
```

至少埋：BFF 路由、上游检索、模型调用、流结束。跨进程传 `traceparent`；没有追踪时，用 requestId + 时间戳也能近似定位。

### 2.6 安全边界

| 风险 | 防护 |
| --- | --- |
| 提示注入 | 模型输出不当指令；工具/权限在服务端，系统提示不可信 |
| SSRF | 上游地址白名单；不根据用户输入拼 URL |
| XSS | 输出转义；不 `dangerouslySetInnerHTML`；CSP |
| CSRF | SameSite + CSRF token |
| 密钥泄露 | 密钥只在服务端；不入日志/前端包；定期轮换 |
| 越权 | 每个查询带 tenantId；对象级权限 |
| 依赖漏洞 | lockfile、审计、最小依赖 |
| 滥用 | 登录/提问限流、配额、验证码 |

CORS 只允许自己的前端源；`Access-Control-Allow-Origin: *` 配合凭据是错误配置。CSP 至少限制 `script-src`/`connect-src`；具体策略按部署调整。

### 2.7 SLO 与告警

SLO 示例：搜索请求 99% 在 2 秒内返回；流式首 token P95 < 1.5 秒；错误率 < 1%。告警基于症状（错误率/延迟/成本），不是每个异常日志。每个告警要有 runbook：看哪个面板、怎么回滚、联系谁。

## 3. 原理讲解与推导

### 3.1 先定义问题，再选工具

“系统慢”要拆成：DNS/TLS、BFF 排队、上游检索、模型首 token、流传输、前端渲染。每层有耗时指标，才能定位。只加一个总耗时，无法判断该优化谁。

### 3.2 成本是产品指标

按租户/功能统计成本，才能定价和限流。只看总账单，无法发现某个重试循环或大上下文在烧钱。成本与质量/延迟一起看，不能单独优化。

### 3.3 安全是边界，不是提示词

提示注入无法靠“更强的 system prompt”根治；把工具权限、数据过滤、URL 白名单、审批放在代码里，模型只负责建议。任何“模型说可以”都不构成授权。

## 4. 示例与逐步走查

```ts
app.use("/api/*", async (c, next) => {
  const started = performance.now();
  const requestId = c.get("requestId");
  let status = 500;
  try {
    await next();
    status = c.res.status;
  } finally {
    const durationMs = Math.round(performance.now() - started);
    observeRequest(c.req.path, status, durationMs);
    logLine({
      requestId,
      route: c.req.path,
      method: c.req.method,
      status,
      durationMs,
      tenantId: c.get("actor")?.tenantId,
    });
  }
});
```

逐步解释：

1. `performance.now()` 用单调时钟，避免系统时间跳变；
2. `finally` 保证异常也记录耗时/状态；
3. 只记录路由、状态、租户，不记录正文/令牌；
4. 指标与日志共用 requestId，能互相跳转；
5. 真实项目把 `console.log` 换成结构化 logger/OTel exporter。

## 5. 练习

### 5.1 跟写

给 `/api/chat/stream` 增加 TTFT、总时长、完成/中断计数；用假 SSE 上游测三个指标。

### 5.2 改造

实现按租户的日预算：累计 token/成本，超限返回 429/降级；记录拒绝原因，不让预算检查拖慢主路径。

### 5.3 独立

列一张威胁表：提示注入、SSRF、XSS、越权、密钥泄露，各写一个可执行测试/检查（例如 URL 白名单拒绝内网、跨租户 404、CSP header 存在）。

## 6. 验收与自测

**行为验收：** 每个请求有 requestId；错误日志有错误码/堆栈，用户响应不含堆栈；指标能区分路由/状态；成本可按租户统计；安全测试覆盖至少 3 类风险。

**原理验收：** 能解释 RED、TTFT、成本口径、SLO 与告警的关系；能说出一个“有日志但无法定位”的例子。

## 7. 面试问答与参考回答

**问：日志、指标、追踪怎么分工？**

日志记录单次事件与错误细节；指标做聚合/告警；追踪展示一次请求跨层因果。三者用 requestId/traceId 关联，不能互相替代。

**问：AI 应用的成本怎么归因？**

按租户/功能/模型记录输入输出 token、重试、缓存和工具调用，配置化单价并记录版本；估算用于优化，账单以供应商为准。

**问：提示注入能靠 system prompt 防住吗？**

不能。模型输出不可信；权限、工具白名单、数据过滤、URL 白名单和审批必须在服务端代码里，提示词只是辅助。

## 8. 本章小结与参考

- 日志/指标/追踪三信号，用 requestId 关联。
- RED + TTFT/成本/工具指标；标签控制基数。
- 成本按租户/功能归因，预算与降级。
- 安全靠边界与测试，不靠提示词。
