## 1. 学习目标与前置知识

能把第 6 章的 SSE 事件接到 React 状态机，边收边渲染文本与引用，支持停止、失败保留部分结果、引用去重和可访问性；能解释为什么不能每个 token 都触发一次重渲染。前置：第 6、8–9 章。

**本章从这里开始：** 模型回答逐段到达，引用可能在中途才出现；用户点“停止”后，已经显示的文字不能消失；一个引用重复出现，列表不能重复。流式界面不是“把字符串拼起来”，而是**事件 → 状态 → 增量 UI**。

第6章、附录B和工程使用相同事件。类型位于stream-state.ts，业务解析位于stream-events.ts；数据从event行取得事件名，citation携带嵌套的来源、版本和引文，done携带answerId与needsReview。

### 2.4 文本与引用怎样渲染

当前组件使用普通文本和pre-wrap，引用动作用button交给已授权的来源入口，不猜一个尚未实现的链接。模型文本不能直接交给dangerouslySetInnerHTML。同一来源的多段引文各有条目，不能仅按来源+版本丢弃后续证据。

状态节点使用status/alert；正文不每token播报，完成后才提示状态。视觉、焦点与读屏体验仍需第16章在真实浏览器验证。

### 2.5 停止、失败与重试

停止保留已收文本；error事件标记未完成，同时让streamAnswer拒绝Promise，控制器不会重复覆盖已进入的error终态。只有done表示协议完成；业务内容正确仍需核对证据。

浏览器abort不证明服务端或供应商已经停止生成、计费。重试或续传要有服务端协议；仅在done才取得answerId时，不能用它恢复中途断线。

## 3. 原理讲解与推导

### 3.1 事件顺序与状态机

SSE 可能交错 `token` 和 `citation`；`done` 之后不应再有 token。reducer 对乱序事件要保守：`done` 后收到 token 可以忽略并记录，而不是继续追加。真实服务应在协议层保证顺序，前端仍要防御。

### 3.2 增量渲染与一致性

文本、引用、状态必须来自同一个 reducer。分别用三个 `useState` 更新会出现“文字已到、引用还没到”的中间态；这不是 bug，但 UI 要能表达。引用可能在文本之后到达，所以完成前允许引用列表为空；`done` 后再做完整性校验。

### 3.3 工具轨迹

Agent 回答还会发工具事件：

```ts
type ToolTrace = {
  name: string;
  status: "start" | "finish";
  detail?: string;
};
```

工具轨迹应显示“调用了什么、参数摘要、结果状态”，不要显示完整敏感参数。它和 token 一样是事件，但通常立即渲染、不做 50ms 合并；审批按钮属于单独的动作状态，不能因为文本流结束就自动批准。

## 6. 验收与自测

**行为验收：** 首 token 尽快出现；停止保留文本；中途失败保留部分内容；引用按来源、版本和引文去重；完成前不误判成功；卸载后不再更新状态。

**原理验收：** 能解释事件→reducer→UI 的数据流、批量更新与 `aria-live` 的取舍；能说出“每个 token 一次 setState”的代价。

### 6.1 先预测，再查看解释

`done` 事件已经到达，但最后 30ms 的 token 还在缓冲区，直接 dispatch `done` 会怎样？

最后一段文字会丢失，因为 `done` 先把状态设为完成，缓冲区里的 token 之后才被 flush，而 reducer 在 `done` 状态会忽略 token（或需要额外处理）。应在 dispatch `done` 前先 flush，保证文本完整。

## 7. 面试问答与参考回答

**问：流式回答为什么不能每个 token 都 setState？**

每个 token 触发一次渲染和协调，token 密集时会造成大量重复工作、输入卡顿和电量消耗。用时间窗口/帧合并，同时保证 `done`/`error` 立即处理。

**问：停止和失败有什么区别？**

停止是用户主动取消，属于正常结果，保留已生成内容即可；失败是生成中断，需要错误提示和是否可重试。两者都不能把已显示文本清空。

**问：为什么以 `done` 事件而不是流关闭判断成功？**

流关闭可能是网络断开、代理超时或服务端异常；`done` 带业务完成信号和 `answerId`，才能区分“完整回答”和“半截文本”。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 怎样把逐段到达的 SSE 事件，变成可停止、可失败、可追溯的界面状态？

**一条主线：**

```text
token/citation/done/error 事件
→ 单 reducer + 每轮独立 buffer/timer/signal
→ 文本 + 去重引用 + stopped/error/done 终态
```

**三个关键词：** 状态机、批量冲刷、引用去重。reducer 只允许合法转换，批量冲刷控制渲染节奏，引用去重保证证据列表不重复。

**最容易错：**
- 用多个 `useState` 分别维护文本、引用和状态，出现“文字已到、引用未到”或终态后继续追加 token。
- 先 dispatch `done` 再 flush，最后一段缓冲丢失；应在 `done` 前冲刷当前轮文本。
- A/B 切换后让旧 `catch`/`finally` 共享清理函数，删掉 B 的新缓冲；每轮必须有自己的 Run。
- 只按来源+版本去重，丢掉同源不同引文；流关闭不等于 `done`，前端 abort 也不等于服务端停止计费。

**与前后章：** 第 9 章的缓存数据与错误边界提供稳定读取面；第 11 章需要把这个流式 endpoint 收进 BFF，补认证、稳定错误码与 SSE 透传。

**学完应能：**
- 能实现 event→reducer→UI，并让终态拒绝迟到事件。
- 能在停止、失败、A/B 切换和卸载时保留正确文本，引用按来源/版本/引文去重。
- 能用注入 runner 的测试复现取消竞态，并解释每 token setState 的代价。
- 能把模型文本按纯文本渲染，不交给 `dangerouslySetInnerHTML`。
