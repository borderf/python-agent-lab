# 第10章　流式 AI 界面：token、引用与待复核

## 1. 学习目标与前置知识

能把第 6 章的 SSE 事件接到 React 状态机，边收边渲染文本与引用，支持停止、失败保留部分结果、引用去重和可访问性；能解释为什么不能每个 token 都触发一次重渲染。前置：第 6、8–9 章；React/事件循环不熟先读[附录D](附录D-JavaScript与浏览器基础.md)。

**本章从这里开始：** 模型文字逐段到达，引用可能稍后出现。收到文字时追加显示，收到引用时加入来源列表，用户停止时保留已收到的内容。我们先定义界面有哪些状态，再为每种事件规定怎样更新，这就是本章要实现的状态机。

## 2. 基础知识讲解

### 2.1 先定义事件，再定义状态

先把事件看成服务端发来的几种消息：新增文字、新增引用、回答完成或出错。第6章、附录B和配套工程使用同一套格式：SSE的`event`行说明事件名；`citation`的内容包含来源、版本和引文；`done`包含`answerId`与`needsReview`。类型定义见`stream-state.ts`，接收后检查消息内容的代码见`stream-events.ts`。

### 2.2 reducer只处理当前运行允许的转换

<<< ../../typescript-examples/src/stream-state.ts

回答已经完成、失败或停止后，后到的事件不应再改变它；尚未开始时，也不能仅凭一条`done`就显示完成。这些转换由reducer检查，也就是根据“当前状态＋事件”计算新状态的函数。运行控制器还要检查消息属于哪一次请求，防止旧请求更新新回答。引用只有在来源、版本和引文都相同时才去重，同一来源的不同引文仍保留。

### 2.3 每轮拥有自己的缓冲、定时器与取消信号

<<< ../../typescript-examples/src/stream-controller.ts

用连续搜索A、B来检查：开始B之前，先把A标记为已失效，并清理A的计时器。B使用自己的文字缓冲区。即使A稍后报错或进入`finally`，也只能清理A的Run对象；否则旧请求可能把B尚未显示的文字删掉。因此必须先判断是哪次请求，再操作它的缓冲区。

零碎文字先暂存在当前请求的缓冲区，再成批更新界面。处理引用、完成或错误事件之前，先把这批文字显示出来，避免事件顺序与文字顺序错开。用户点击停止时，也先显示已收到的末尾文字，再记录`stopped`并取消请求。组件卸载时的`dispose`只做清理，不再更新组件；StrictMode重新建立effect后，仍应能启动新请求。

React只绑定这一个控制器，不再复制另一份异步算法：

完整导入见[hooks.ts](../../typescript-examples/src/hooks.ts)。scope须包含当前主体、租户、授权版本等身份范围；传null表示退出。scope或端点变化时，render立即隐藏不属于当前范围的内容，effect清理旧运行。

### 2.4 文本与引用怎样渲染

当前组件使用普通文本和pre-wrap，引用动作用button交给已授权的来源入口，不猜一个尚未实现的链接。模型文本不能直接交给dangerouslySetInnerHTML。同一来源的多段引文各有条目，不能仅按来源+版本丢弃后续证据。

状态节点使用status/alert；正文不每token播报，完成后才提示状态。视觉、焦点与读屏体验仍需第16章在真实浏览器验证。

### 2.5 停止、失败与重试

停止保留已收文本；error事件标记未完成，同时让streamAnswer拒绝Promise，控制器不会重复覆盖已进入的error终态。只有done表示协议完成；业务内容正确仍需核对证据。

浏览器abort不证明服务端或供应商已经停止生成、计费。重试或续传要有服务端协议；仅在done才取得answerId时，不能用它恢复中途断线。

### 2.6 正常序列：事件、缓冲、reducer与UI逐行对应

先记住四个对象各自负责什么：`streamAnswer`把字节解码成事件；`StreamController`决定本轮是否有权接收事件并管理缓冲；`reduceAnswer`只根据状态和动作生成新状态；`AnswerPage`读取同一份状态渲染。下面用一条很短的回答走完四层。时间只是说明调度顺序，不是要求服务端按这个频率发送。

```text
t=0   用户点击开始（本地动作，不是SSE事件）
t=10  收到 token，text="预"
t=60  50ms批量窗口到期
t=70  收到 citation，sourceId="policy-a"，version="2"，quote="预付款≤20%"
t=75  收到 token，text="款"
t=85  收到 done，answerId="A1"，needsReview=true
```

| 时刻 | 控制器动作 | 本轮buffer | reducer后的状态 | 页面可见结果 |
| --- | --- | --- | --- | --- |
| t=0 | `start`建立新Run并dispatch start | `""` | `connecting`，text/citations为空 | 显示“正在连接…”，正文为空 |
| t=10 | token只追加buffer并启动定时器 | `"预"` | 仍为`connecting` | 不新增渲染，正文仍为空 |
| t=60 | 定时器flush，dispatch tokens | `""` | `streaming`，text=`"预"` | 正文出现“预” |
| t=70 | 非token先flush，再dispatch citation | `""` | `streaming`，text=`"预"`，引用1条 | 正文不变，来源条目出现 |
| t=75 | 新token重新启动定时器 | `"款"` | 仍为`streaming`，text=`"预"` | 暂时的落后是批量策略，不是丢字 |
| t=85 | 先flush `"款"`，再dispatch done | `""` | `done`，text=`"预付款"`，answerId=`A1` | 正文完整，显示完成/待复核状态 |
| t=90 | 迟到token被控制器丢弃；直接喂给reducer也会被终态拒绝 | `""` | 保持`done` | 不追加、不改状态 |

关键不是“收到token就setState”，而是**先归入本轮buffer，再在窗口边界或非token事件前发布**。如果t=85错误地先dispatch done、后flush，reducer会因终态忽略tokens，最后的“款”就丢失。

### 2.7 反例一：停止时先保留末尾，再取消

```text
t=0   start → connecting
t=10  token "你" → buffer="你"，页面仍为空
t=20  用户停止 → flush "你" → streaming(text="你") → stopped(text="你") → abort
t=30  旧连接迟到 token "好" → 丢弃
```

预期状态是`stopped`且text仍为`"你"`，不是idle，也不是done。停止按钮在connecting/streaming之外应禁用；再次停止没有当前Run，因此不改变终态。用户停止后即使旧Promise resolve，`finally`也只清自己的Run，不会把停止状态改成成功。

### 2.8 反例二：失败保留部分结果，但不冒充完成

```text
t=0   start → connecting
t=10  token "半句" → buffer="半句"
t=20  event: error，message="上游断开"，retryable=true
```

控制器先flush，页面立即显示“半句”，再进入`error`。`streamAnswer`随后拒绝Promise；控制器catch再次尝试发布error，但reducer看到已是终态，返回原状态。因此错误提示不会把文字清空，也不会重复追加。`retryable=true`只表示可以给用户重试入口，不表示已经自动重试，更不表示半句内容已经核验。若失败后迟到done，仍保持error；只有用户显式开始新一轮，才通过start清空旧文本。

### 2.9 反例三：迟到事件与A/B请求都不能跨轮写入

```text
A start → A收到token "旧"（仍在A的buffer）
B start → A立即失效，A的timer/buffer清理
B收到token "新" → B的buffer="新"
A迟到error或resolve → 只清理A，不发布、不动B
B收到done → 先flush "新"，再进入done
```

这里有两道门：控制器用`this.current === run`检查运行归属；reducer用`status`检查状态归属。前者防跨请求，后者防同请求终态后追加。只关AbortController不够，因为忽略signal的旧runner仍可能回调；只在reducer里判断terminal也不够，因为旧请求可能发生在B尚未done时。

### 2.10 反例四：引用去重必须比较完整证据

```text
citation(policy-a, v2, "条款甲")
citation(policy-a, v2, "条款乙")
citation(policy-a, v2, "条款甲")
```

预期 citations 为`[条款甲, 条款乙]`，长度2。完全相同的来源、版本、引文才算重复；同源同版本的另一段引文要保留，同源不同版本也要保留。去重键可以用`JSON.stringify([sourceId, version, quote])`，与页面列表key一致。不能用sourceId或“sourceId+version”单独去重，否则会丢掉后续证据。引用去重也不代表内容支持结论，`needsReview`仍按协议显示。

## 3. 原理讲解与推导

### 3.1 事件顺序与状态机

SSE 可能交错 `token` 和 `citation`；`done` 之后不应再有 token。reducer 对乱序事件要保守：`done` 后收到 token 可以忽略并记录，而不是继续追加。真实服务应在协议层保证顺序，前端仍要防御。

### 3.2 增量渲染与一致性

文本、引用、状态必须来自同一个 reducer。分别用三个 `useState` 更新会出现“文字已到、引用还没到”的中间态；这不是 bug，但 UI 要能表达。引用可能在文本之后到达，所以完成前允许引用列表为空；`done` 后再做完整性校验。

### 3.3 工具轨迹

Agent 回答还会发工具事件：

```ts
type ToolTrace = {
  name: string;
  status: "start" | "finish";
  detail?: string;
};
```

工具轨迹应显示“调用了什么、参数摘要、结果状态”，不要显示完整敏感参数。它和 token 一样是事件，但通常立即渲染、不做 50ms 合并；审批按钮属于单独的动作状态，不能因为文本流结束就自动批准。

### 3.4 为什么缓冲不能放进reducer

reducer应是可重复的纯计算：同一state和action得到同一结果，不读时钟、不启动定时器。50ms窗口、AbortController和“哪一轮”都属于控制器副作用。若把缓冲塞进reducer，测试就要伪造时间，stop/error也很难保证先发布尾字。

一次事件的实际调用边界如下：

```text
SSE字节 → parser → parseStreamEvent → receive(event)
  token:     run.buffer += text；需要时设置timer
  非token:   flush(run)；publish(event)；done/error标记run.terminal
flush:      读取并清空run.buffer；仅当前轮且text非空时dispatch tokens
publish:    reduceAnswer(state, action) → emit(state, scope) → React渲染
```

`clear(run)`先清buffer再发布，避免flush重入；`publish`即使reducer忽略动作也会emit，因此React可能多一次渲染，但状态内容不会错。优化emit属于后续测量，不能为此改变终态顺序。

## 6. 验收与自测

**行为验收：** 首 token 尽快出现；停止保留文本；中途失败保留部分内容；引用按来源、版本和引文去重；完成前不误判成功；卸载后不再更新状态。

**原理验收：** 能解释事件→reducer→UI 的数据流、批量更新与 `aria-live` 的取舍；能说出“每个 token 一次 setState”的代价。

## 7. 面试问答与参考回答

**问：流式回答为什么不能每个 token 都 setState？**

每个 token 触发一次渲染和协调，token 密集时会造成大量重复工作、输入卡顿和电量消耗。用时间窗口/帧合并，同时保证 `done`/`error` 立即处理。

**问：停止和失败有什么区别？**

停止是用户主动取消，属于正常结果，保留已生成内容即可；失败是生成中断，需要错误提示和是否可重试。两者都不能把已显示文本清空。

**问：为什么以 `done` 事件而不是流关闭判断成功？**

流关闭可能是网络断开、代理超时或服务端异常；`done` 带业务完成信号和 `answerId`，才能区分“完整回答”和“半截文本”。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 怎样把逐段到达的 SSE 事件，变成可停止、可失败、可追溯的界面状态？

**一条主线：**

```text
token/citation/done/error 事件
→ 单 reducer + 每轮独立 buffer/timer/signal
→ 文本 + 去重引用 + stopped/error/done 终态
```

**三个关键词：** 状态机、批量冲刷、引用去重。reducer拒绝非法转换，控制器负责缓冲与运行归属，完整证据键防止误删引用。

**最容易错：**
- 收到token立即setState，或先done后flush，造成渲染风暴/尾字丢失。
- 旧Run的catch/finally清理新Run；终态后仍接受迟到事件。
- 只按sourceId或sourceId+version去重；把流关闭、前端abort当成服务端完成或停止计费。
- 把模型文本当HTML，或把打开来源按钮当成已实现授权原文页。

**与前后章：** 第9章提供身份范围与错误显示；第11章负责把流式请求接入BFF，并区分HTTP错误与已开始流内的错误。

**学完应能：** 按事件顺序推导buffer/state/UI；为停止、失败、迟到和去重各写一个反例；用真实Hook测试证明旧轮不能覆盖新轮。
