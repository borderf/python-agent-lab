# 第04章　运行时校验与错误边界

[上一章](03-对象泛型与契约.md) · [全书目录](教材目录.md) · [下一章](05-异步并发与取消.md)

## 1. 学习目标与前置知识

能把所有外部输入收进 `unknown`，用可组合的校验器变成可信类型，用明确的错误类型区分“输入错、网络错、服务错”，并让调用方必须处理失败。前置：第 1–3 章。

**本章从这里开始：** 后端返回 200，`JSON.parse` 成功，但 `citations` 是 `null`；TypeScript 不会在运行时检查。错误应该在哪一层被拦住，调用方怎样知道“能不能重试”？

## 2. 基础知识讲解

### 2.1 边界只有少数几个

一个前端应用的外部输入通常来自：

- `fetch` 的响应体；
- `localStorage`/`sessionStorage`；
- URL 查询参数；
- 用户表单；
- 第三方 SDK 回调。

这些位置的值都应先当作 `unknown`。组件内部、纯函数之间的值可以依赖类型契约，因为它们是同一进程里构造出来的。

```ts
async function loadAnswer(url: string): Promise<unknown> {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json(); // 运行时是任意 JSON
}
```

`response.json()` 的返回类型是 `Promise<any>`；不要直接 `as Answer`。先把 `any` 收敛成 `unknown`，再走校验。

### 2.2 手写校验器：小、可组合

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null && !Array.isArray(value);
}

function parseString(value: unknown, field: string): Result<string, string> {
  if (typeof value !== "string" || !value.trim()) {
    return { ok: false, error: `${field} 必须是非空字符串` };
  }
  return { ok: true, value: value.trim() };
}

function parseInteger(value: unknown, field: string): Result<number, string> {
  if (typeof value !== "number" || !Number.isInteger(value) || value < 0) {
    return { ok: false, error: `${field} 必须是非负整数` };
  }
  return { ok: true, value };
}
```

`Result` 把失败变成返回值，调用方必须检查 `ok`。它与异常不是互斥的：边界解析用 `Result` 收集字段错误，底层 I/O 仍可抛异常；在边界统一转成 `Result` 或 `ApiError`。

### 2.3 错误分类与可重试性

```ts
type AppError =
  | { kind: "input"; message: string; field?: string }
  | { kind: "network"; message: string; retryable: true }
  | { kind: "server"; message: string; retryable: boolean }
  | { kind: "auth"; message: string; retryable: false };
```

错误分类要能驱动 UI：输入错显示字段，网络错给重试，认证错跳登录，服务错按 `retryable` 决定。不要把所有失败压成 `"请求失败"`，那会让用户和日志都无法判断。

### 2.4 `Error` 与 `cause`

```ts
class ValidationError extends Error {
  constructor(message: string, readonly field?: string, options?: ErrorOptions) {
    super(message, options);
    this.name = "ValidationError";
  }
}

try {
  JSON.parse("{bad");
} catch (error) {
  throw new ValidationError("响应不是合法 JSON", undefined, { cause: error });
}
```

`cause` 保留底层异常，日志能同时看到业务层和解析层。`instanceof` 只在同一运行时/同一类构造器下可靠；跨 iframe、跨包副本可能失效，必要时用 `name` 或错误码辅助。

## 3. 原理讲解与推导

### 3.1 校验器必须覆盖“结构 + 值 + 跨字段”

只检查 `typeof` 不够：`amountCents: -1` 类型正确但业务非法；`citations: []` 结构合法但“无引用必须待复核”是跨字段规则。校验顺序通常是：

1. 形状：对象、数组、字段存在；
2. 类型：字符串、数字、布尔；
3. 值域：非空、非负、枚举；
4. 跨字段/业务：引用与复核、版本与权限。

每一步给出具体字段和原因，避免只返回 `false`。

### 3.2 校验失败的策略

- 整个响应不可用：返回一个 `ApiError`，不进入业务层；
- 单条记录坏：可以跳过并记录，但必须让调用方知道有丢弃；
- 字段坏但可修复：明确默认值与审计，不静默修复。

“跳过坏记录”不是默认正确；对合规/审查场景，丢弃可能比报错更危险。

### 3.3 类型与 schema 的单一来源

手写校验器容易和类型漂移。可以用 schema 库（如 Zod）从 schema 推断类型，但库的版本、错误信息和打包体积要评估。本书示例不依赖第三方库；关键是边界只有一个入口，类型和校验在同处维护。

## 4. 示例与逐步走查

```ts
type Citation = { sourceId: string; quote: string };
type Answer = { answer: string; citations: Citation[]; needsReview: boolean };

function parseCitation(value: unknown, index: number): Result<Citation, string> {
  if (!isRecord(value)) return { ok: false, error: `citations[${index}] 不是对象` };
  const sourceId = parseString(value.sourceId, `citations[${index}].sourceId`);
  if (!sourceId.ok) return sourceId;
  const quote = parseString(value.quote, `citations[${index}].quote`);
  if (!quote.ok) return quote;
  return { ok: true, value: { sourceId: sourceId.value, quote: quote.value } };
}

function parseAnswer(value: unknown): Result<Answer, string> {
  if (!isRecord(value)) return { ok: false, error: "回答必须是对象" };
  const answer = parseString(value.answer, "answer");
  if (!answer.ok) return answer;
  if (!Array.isArray(value.citations)) {
    return { ok: false, error: "citations 必须是数组" };
  }
  const citations: Citation[] = [];
  for (const [index, item] of value.citations.entries()) {
    const parsed = parseCitation(item, index);
    if (!parsed.ok) return parsed;
    citations.push(parsed.value);
  }
  if (typeof value.needsReview !== "boolean") {
    return { ok: false, error: "needsReview 必须是布尔值" };
  }
  if (citations.length === 0 && !value.needsReview) {
    return { ok: false, error: "没有引用时必须标记待复核" };
  }
  return { ok: true, value: { answer: answer.value, citations, needsReview: value.needsReview } };
}
```

逐步解释：

1. 每个字段错误带路径（`citations[0].quote`），用户和日志能定位。
2. 先解析 `sourceId`，失败立即返回，不继续读 `quote`；避免级联空值。
3. 最后检查跨字段规则；类型正确但业务非法仍被拒绝。
4. 返回新对象，不保留原 `unknown` 的引用；后续代码只接触已验证值。

将 `citations` 改为 `[{"sourceId":"a","quote":""}]`，确认错误落在 `citations[0].quote`；把 `needsReview` 改成 `"false"`，确认不被当作真值。

## 5. 练习

### 练习一：跟写

为 `parseInteger` 增加最大值参数，错误信息包含字段、实际值和上限；用 `Number.isSafeInteger` 判断安全整数。

### 练习二：改造

把 `parseAnswer` 改成“收集所有字段错误”而不是遇到第一个就返回；返回 `{ok:false, errors: string[]}`。比较两种策略在表单和 API 响应中的适用性。

### 练习三：独立

写 `parseApiError(value: unknown): AppError`，识别 `input/network/server/auth`，未知形状归为 `server` 且 `retryable:false`；记录原始值供日志，但不要把敏感字段写入用户提示。

## 6. 验收与自测

**行为验收：** 坏 JSON、缺字段、空字符串、负数、错误枚举、无引用未复核都被拒绝；错误路径具体；合法输入返回新对象。

**原理验收：** 能说明“类型正确但业务非法”的例子；能解释 `unknown`、`Result`、`cause` 各自解决什么；能说出为什么不能只用 `as`。

### 6.1 先预测，再查看解释

`JSON.parse` 成功但 `response.json()` 返回 `null`，为什么不能直接进入 `parseAnswer(null)` 后访问 `.answer`？

<details>
<summary>完成预测后查看解释</summary>

`parseAnswer` 的第一行检查 `isRecord(value)`，`null` 会返回错误，不会继续访问 `.answer`。如果跳过这层检查，`null.answer` 会在运行时抛 `TypeError`；类型系统看不到网络返回的真实值。

</details>

## 7. 面试问答与参考回答

**问：TypeScript 类型能替代运行时校验吗？**

不能。类型在编译后擦除，网络、存储、用户输入不受编译器控制。外部输入要用 `unknown` 加校验器；类型只约束内部已验证值。

**问：为什么用 `Result` 而不是全部抛异常？**

`Result` 让失败成为显式返回值，调用方必须处理；适合边界解析和可预期错误。异常适合不可恢复或跨层中断；两者可以组合，但不能让失败静默消失。

**问：错误分类为什么重要？**

UI、重试和日志依赖错误类型：输入错不该重试，网络错可退避重试，认证错要重新登录，服务错要看可重试标记。统一字符串会丢失这些决策信息。

## 8. 本章小结与参考

- 外部输入先进入 `unknown`，用结构化校验器变成可信类型。
- 校验覆盖形状、类型、值域和跨字段规则，错误带路径。
- `Result` 让失败显式；错误分类驱动 UI、重试和日志。
- 类型与 schema 尽量同源，避免两份定义漂移。
