# 第05章　异步、并发、取消与超时

[上一章](04-运行时校验与错误边界.md) · [全书目录](教材目录.md) · [下一章](06-HTTP与流式响应.md)

## 1. 学习目标与前置知识

能区分顺序等待与并发执行，能用 `Promise.allSettled` 保留部分失败，用 `AbortController` 取消，用超时与有限重试避免无限等待，并知道哪些操作不能盲目重试。前置：第 1–4 章。

**本章从这里开始：** 页面要同时加载文档、引用和模型状态；一个请求很慢，用户离开页面后请求还在跑。并发、取消、超时和重试如果混在一起，很容易留下未处理 Promise 或重复写入。

## 2. 基础知识讲解

### 2.1 Promise 表示“未来的一次结果”

```ts
async function fetchJson(url: string): Promise<unknown> {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}
```

`async` 函数总是返回 Promise；`await` 等待结果，失败会抛出。不要忘记 `await`：一个未等待的 Promise 可能产生未处理拒绝，也可能在页面卸载后继续写状态。

```ts
const pending = fetchJson("/api/search");
// 这里没有 await；错误不会被当前 try/catch 捕获
```

### 2.2 顺序与并发

顺序等待适合“后一步依赖前一步”：

```ts
const me = await fetchJson("/api/me");
if (typeof me !== "object" || me === null || !("id" in me) || typeof me.id !== "string") {
  throw new Error("me 响应缺少字符串 id");
}
const documents = await fetchJson(`/api/users/${me.id}/documents`);
```

彼此独立的请求应并发，否则总耗时相加：

```ts
const [documents, citations] = await Promise.all([
  fetchJson("/api/documents"),
  fetchJson("/api/citations"),
]);
```

`Promise.all` 在任一失败时整体拒绝，其他 Promise 仍会继续执行（不会自动取消）。需要保留成功项时用 `Promise.allSettled`：

```ts
const results = await Promise.allSettled([
  fetchJson("/api/documents"),
  fetchJson("/api/citations"),
]);
for (const result of results) {
  if (result.status === "fulfilled") console.log(result.value);
  else console.error(result.reason);
}
```

### 2.3 取消：`AbortController`

```ts
async function loadWithSignal(url: string, signal: AbortSignal): Promise<unknown> {
  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

const controller = new AbortController();
const task = loadWithSignal("/api/search", controller.signal);
controller.abort();
await task.catch((error) => {
  if (error instanceof DOMException && error.name === "AbortError") return;
  throw error;
});
```

取消是协作请求：`fetch` 会中止，但你自己写的循环、`setTimeout` 或第三方库不一定响应。长任务要检查 `signal.aborted`，并在清理函数里释放定时器、监听器和流读取器。

`AbortSignal.timeout(ms)` 可以生成超时信号；需要同时响应外部取消时用 `AbortSignal.any([signal, AbortSignal.timeout(ms)])`（新运行时支持）。不支持时手写 `setTimeout` + `controller.abort()`。

### 2.4 超时与重试

```ts
async function withTimeout<T>(run: (signal: AbortSignal) => Promise<T>, ms: number): Promise<T> {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), ms);
  try {
    return await run(controller.signal);
  } finally {
    clearTimeout(timer);
  }
}
```

重试只适合**可重试**且**幂等**的操作。GET 可以重试；POST 如果没有幂等键，超时后可能已经写入，重试会重复。重试要有上限、退避和抖动：

```ts
async function retry<T>(run: () => Promise<T>, attempts = 3): Promise<T> {
  let last: unknown;
  for (let index = 0; index < attempts; index += 1) {
    try {
      return await run();
    } catch (error) {
      last = error;
      if (index === attempts - 1) break;
      const delay = 200 * 2 ** index + Math.random() * 100;
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
  throw last;
}
```

重试前要判断错误类型：认证失败、输入错误不应重试；网络抖动、429、5xx 才可能。`Retry-After` 要遵守。

## 3. 原理讲解与推导

### 3.1 事件循环与阻塞

JavaScript 主线程是单线程事件循环。`await` 让出执行权，但不是多线程；CPU 密集循环、同步解析大 JSON、同步加密仍会阻塞界面。CPU 工作要移到 Worker，Node 端可用 Worker Threads 或子进程；I/O 用异步 API。

### 3.2 并发不是越多越好

同时发 100 个请求会压垮后端、触发限流、增加内存。用并发上限：

```ts
async function mapLimit<T, R>(
  items: readonly T[],
  limit: number,
  run: (item: T) => Promise<R>,
): Promise<R[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError("limit 必须是正整数");
  }
  const results: R[] = new Array(items.length);
  let next = 0;
  async function worker(): Promise<void> {
    while (next < items.length) {
      const index = next++;
      // index 一定小于 items.length；T 本身可以是 undefined，
      // 所以不能按“值是否为 undefined”跳过，否则会漏掉合法元素。
      results[index] = await run(items[index] as T);
    }
  }
  const workers = Math.min(limit, items.length);
  await Promise.all(Array.from({ length: workers }, worker));
  return results;
}
```

`next++` 在单线程事件循环里是安全的；每个 worker 取一个索引，完成后继续取，形成有界并发。错误处理要明确：一个失败是否停止全部、是否保留已完成结果。`limit` 为零、负数或非整数应直接拒绝；`items` 里的 `undefined` 是合法值，不能当“没有元素”跳过。

`withTimeout` 只能**通知**回调取消，不能强制停止一个不响应 `signal` 的回调。回调若忽略信号，仍可能继续执行并在稍后修改外部状态；要让它真正可中止，必须把信号传到底层 I/O，或在边界做隔离/丢弃结果。`Promise.race` 也不会取消输掉的一方。

`retry` 能否安全执行，取决于接收方契约，而不只是“有网络错误”或“带幂等键”：要确认动作身份、载荷、当前授权、预算和重复执行的业务后果。没有幂等键的写操作、权限已变化、载荷已过期时，不应自动重试。

### 3.3 取消与资源清理

取消不是“把 Promise 丢掉”，而是让底层操作停止并清理。需要清理的包括：定时器、事件监听、流读取器、WebSocket、Worker。`finally` 是统一清理位置。

## 4. 示例与逐步走查

下面并发加载三个独立资源，允许部分失败，并给整体超时：

```ts
type Loaded<T> = { ok: true; value: T } | { ok: false; error: string };

async function loadDashboard(signal: AbortSignal): Promise<{
  documents: Loaded<unknown>;
  citations: Loaded<unknown>;
  model: Loaded<unknown>;
}> {
  const tasks = [
    ["documents", "/api/documents"],
    ["citations", "/api/citations"],
    ["model", "/api/model/status"],
  ] as const;
  const settled = await Promise.allSettled(
    tasks.map(async ([key, url]) => {
      const response = await fetch(url, { signal });
      if (!response.ok) throw new Error(`${key}: HTTP ${response.status}`);
      return [key, (await response.json()) as unknown] as const;
    }),
  );
  const output = {
    documents: { ok: false, error: "未加载" } as Loaded<unknown>,
    citations: { ok: false, error: "未加载" } as Loaded<unknown>,
    model: { ok: false, error: "未加载" } as Loaded<unknown>,
  };
  settled.forEach((result, index) => {
    const key = tasks[index][0];
    output[key] = result.status === "fulfilled"
      ? { ok: true, value: result.value[1] }
      : { ok: false, error: String(result.reason) };
  });
  return output;
}
```

逐步解释：

1. `allSettled` 不会因一个资源失败而丢弃其他成功结果；每个资源单独映射为 `Loaded`。
2. `tasks` 用 `as const` 保留键的字面量，`output[key]` 才能被正确索引。
3. `signal` 传给每个 `fetch`；外部取消时所有请求一起中止。
4. 实际项目还要给整体加超时、对错误分类，并在组件卸载时 abort。

## 5. 练习

### 练习一：跟写

给 `retry` 增加 `shouldRetry(error): boolean` 参数，只对网络错误和 5xx 重试；认证错误立即抛出。

### 练习二：改造

把 `mapLimit` 改成“任一失败即停止并取消其他任务”，用 `AbortController` 传递取消；比较“保留部分结果”和“全有或全无”的适用场景。

### 练习三：独立

实现 `withTimeout`，要求超时错误带 `timeout` 标记，且 `finally` 清理定时器；写一个测试：回调响应 `signal`，超时后不再写外部状态。再写一个反例：回调忽略 `signal` 时仍会继续完成，说明 `withTimeout` 只能通知取消，不能强制停止。

## 6. 验收与自测

**行为验收：** 独立请求并发；部分失败保留成功项；取消后无后续状态写入；超时清理定时器；重试只发生在可重试错误上。

**原理验收：** 能解释事件循环、`Promise.all` 与 `allSettled` 的差异、取消的协作性；能说出一个“不能重试”的 POST 例子。

### 6.1 先预测，再查看解释

`await Promise.all([a(), b()])` 中 `a()` 失败后，`b()` 会立即停止吗？

<details>
<summary>完成预测后查看解释</summary>

不会。`Promise.all` 在第一个拒绝时让外层 Promise 拒绝，但已经启动的 `b()` 仍继续执行；它不会自动取消。需要取消时传同一个 `AbortSignal`，并让 `b()` 响应信号。

## 7. 面试问答与参考回答

**问：`Promise.all` 和 `Promise.allSettled` 怎么选？**

需要全部成功才继续时用 `all`；需要展示部分成功/部分失败时用 `allSettled`。`all` 失败不会取消其他任务，需要额外 `AbortController`。

**问：取消一个 Promise 会发生什么？**

Promise 本身不可取消；取消要传给底层操作（`fetch`、流、定时器）。被取消的操作通常以 `AbortError` 拒绝，调用方要识别并清理资源，不能只忽略 Promise。

**问：哪些请求可以重试？**

幂等且错误可重试的请求：GET、带幂等键的写操作、429/5xx/网络抖动。无幂等键的 POST 超时后可能已执行，重试会重复写入；应先查询或对账。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 页面同时加载文档、引用和模型状态，用户离开后请求还在跑——谁负责取消、超时和收尾？

**一条主线：**

```text
独立请求 → allSettled + 并发上限 → AbortSignal 传播取消 → 超时、退避与有限重试 → finally 清理
```

**三个关键词：** Promise、取消、并发上限。Promise 表示未来的一次结果，`AbortSignal` 把取消传到 I/O，并发上限和重试策略决定失败时的成本。

**最容易错：**

- 忘记 `await`，留下未处理拒绝，或卸载后继续写状态。
- 以为 `Promise.all` 一失败就会取消另一个请求（不会，要传同一个 signal）。
- 把 `withTimeout` 当强制终止：回调不响应 signal 时仍会跑完并改外部状态。
- 对无幂等键的 POST 超时后直接重试，或让 `mapLimit` 把合法的 `undefined` 元素跳过。

**与前后章：** 上一章的错误分类告诉哪些失败可重试；下一章需要把 signal 和断流处理接到 SSE reader 上，边收边渲染。

**学完应能：**

- 用 `Promise.allSettled` 让三个资源独立成败，并给整体超时；
- 取消后确认没有后续状态写入，定时器和监听器都清掉；
- 写 `mapLimit` 并拒绝零、负数和非整数 `limit`；
- 说出一个不能自动重试的写操作，以及重试前要核对哪些条件。
