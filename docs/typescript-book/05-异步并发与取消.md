# 第05章　异步、并发、取消与超时

[上一章](04-运行时校验与错误边界.md) · [全书目录](教材目录.md) · [下一章](06-HTTP与流式响应.md)

## 1. 学习目标与前置知识

能区分顺序等待与并发执行，能用 `Promise.allSettled` 保留部分失败，用 `AbortController` 取消，用超时与有限重试避免无限等待，并知道哪些操作不能盲目重试。前置：第 1–4 章；Promise/事件循环不熟先读[附录D](附录D-JavaScript与浏览器基础.md)。

**本章从这里开始：** 页面要同时加载文档、引用和模型状态；一个请求很慢，用户离开页面后请求还在跑。并发、取消、超时和重试如果混在一起，很容易留下未处理 Promise 或重复写入。

## 2. 基础知识讲解

### 2.1 Promise 表示“未来的一次结果”

```ts
async function fetchJson(url: string): Promise<unknown> {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}
```

`async`函数返回Promise，用它表示将来成功得到的值或失败原因。执行`await`时，当前异步函数等待这个结果；如果Promise拒绝，`await`这一处会抛出错误。如果启动了Promise却没有等待或安排错误处理，失败可能无人处理；请求也可能在组件已卸载后才回来，继续尝试更新状态。

```ts
const pending = fetchJson("/api/search");
// 这里没有 await；错误不会被当前 try/catch 捕获
```

### 2.2 顺序与并发

顺序等待适合“后一步依赖前一步”：

```ts
const me = await fetchJson("/api/me");
if (typeof me !== "object" || me === null || !("id" in me) || typeof me.id !== "string") {
  throw new Error("me 响应缺少字符串 id");
}
const documents = await fetchJson(`/api/users/${me.id}/documents`);
```

彼此独立的请求应并发，否则总耗时相加：

```ts
const [documents, citations] = await Promise.all([
  fetchJson("/api/documents"),
  fetchJson("/api/citations"),
]);
```

`Promise.all` 在任一失败时整体拒绝，其他 Promise 仍会继续执行（不会自动取消）。需要保留成功项时用 `Promise.allSettled`：

```ts
const results = await Promise.allSettled([
  fetchJson("/api/documents"),
  fetchJson("/api/citations"),
]);
for (const result of results) {
  if (result.status === "fulfilled") console.log(result.value);
  else console.error(result.reason);
}
```

### 2.3 取消：`AbortController`

```ts
async function loadWithSignal(url: string, signal: AbortSignal): Promise<unknown> {
  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

const controller = new AbortController();
const task = loadWithSignal("/api/search", controller.signal);
controller.abort();
await task.catch((error) => {
  if (error instanceof DOMException && error.name === "AbortError") return;
  throw error;
});
```

取消是协作请求：`fetch` 会中止，但你自己写的循环、`setTimeout` 或第三方库不一定响应。长任务要检查 `signal.aborted`，并在清理函数里释放定时器、监听器和流读取器。

`AbortSignal.timeout(ms)` 可以生成超时信号；需要同时响应外部取消时用 `AbortSignal.any([signal, AbortSignal.timeout(ms)])`（新运行时支持）。不支持时手写 `setTimeout` + `controller.abort()`。

### 2.4 超时与重试

```ts
async function withTimeout<T>(run: (signal: AbortSignal) => Promise<T>, ms: number): Promise<T> {
  if (!Number.isFinite(ms) || ms <= 0) throw new RangeError("ms 必须是正数");
  const controller = new AbortController();
  let timer: ReturnType<typeof setTimeout> | undefined;
  const timeout = new Promise<never>((_resolve, reject) => {
    timer = setTimeout(() => {
      const error = new DOMException(`操作超过 ${ms}ms`, "TimeoutError");
      controller.abort(error);
      reject(error);
    }, ms);
  });
  try {
    // race只决定调用方何时收到拒绝；底层run仍须自己响应signal。
    return await Promise.race([run(controller.signal), timeout]);
  } finally {
    if (timer !== undefined) clearTimeout(timer);
  }
}
```

重试只适合**可重试**且**幂等**的操作。GET 可以重试；POST 如果没有幂等键，超时后可能已经写入，重试会重复。重试要有上限、退避和抖动：

```ts
async function retry<T>(
  run: () => Promise<T>,
  shouldRetry: (error: unknown) => boolean,
  attempts = 3,
): Promise<T> {
  if (!Number.isInteger(attempts) || attempts < 1) throw new RangeError("attempts 必须是正整数");
  let last: unknown;
  for (let index = 0; index < attempts; index += 1) {
    try {
      return await run();
    } catch (error) {
      last = error;
      if (index === attempts - 1 || !shouldRetry(error)) throw error;
      const delay = 200 * 2 ** index + Math.random() * 100;
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
  throw last;
}
```

重试前要判断错误类型：认证失败、输入错误不应重试；网络抖动、429、5xx 才可能。`Retry-After` 要遵守。这个最小实现还没有把取消信号与总时限传入重试等待，接入项目前必须补上，避免用户取消后背避仍在继续。

### 2.5 Promise 并发、部分失败与取消对照

下面用本地 Promise 复现结果差异，不访问网络：

```ts
async function comparePromises(): Promise<void> {
  try {
    await Promise.all([Promise.resolve("文档"), Promise.reject(new Error("引用失败"))]);
  } catch (error) {
    console.log("all:", error instanceof Error ? error.message : String(error));
  }
  const settled = await Promise.allSettled([
    Promise.resolve("文档"),
    Promise.reject(new Error("引用失败")),
  ]);
  console.log("allSettled:", settled.map((item) => item.status).join(","));
}
void comparePromises();
```

**预期输出**：

```text
all: 引用失败
allSettled: fulfilled,rejected
```

| 写法 | 等待谁 | 失败时返回值 | 是否自动取消其他任务 |
| --- | --- | --- | --- |
| 顺序 `await a(); await b()` | 先 a 完成，再启动 b | 在失败处抛出 | 没有启动的任务不会启动 |
| `Promise.all([a, b])` | 全部成功；任一拒绝时提前结束等待 | 第一个拒绝原因 | 否 |
| `Promise.allSettled([a, b])` | 全部进入 fulfilled/rejected | 两个结果组成的数组 | 否 |
| `mapLimit(items, 2, run)` | 最多同时运行两个 worker | 数组或首个 worker 拒绝 | 否，本章版本没有 controller |

编译时先运行 `pnpm exec tsc --noEmit`；运行转译产物时观察 `settled` 的判别字段。`Promise.allSettled` 的拒绝结果中 `reason` 是 `any`，记录日志前仍应按 `unknown` 处理。常见错误是看到 `allSettled` 就认为所有请求都成功，或看到 `all` 失败就以为 `b()` 被终止。

### 2.6 取消、超时与重试不是同一件事

| 机制 | 谁发起 | 对正在运行任务的影响 | 调用方拿到什么 |
| --- | --- | --- | --- |
| `controller.abort()` | 用户离开、查询切换 | 通知响应 signal 的操作；不强制终止 | 操作通常以 `AbortError` 拒绝 |
| `AbortSignal.timeout(ms)` 或 `withTimeout` | 计时器 | 到点通知取消；忽略 signal 的代码继续跑 | `TimeoutError` 或超时 Promise 拒绝 |
| `retry` | 捕获到错误后的策略 | 再调用一次 `run`，产生新操作 | 成功值或最终错误 |

```ts
const controller = new AbortController();
console.log(controller.signal.aborted); // false
controller.abort();
console.log(controller.signal.aborted); // true
```

**预期输出**为 `false`、`true`。`abort()` 的返回类型是 `void`，不会返回“Promise 已停止”的确认。`withTimeout` 的 `Promise.race` 只让调用方先收到拒绝；回调若忽略 `signal`，之后仍可能修改变量，所以必须用运行归属或代次标记丢弃迟到结果。重试则必须新建操作并重新检查幂等性，不能把超时和取消也当成普通失败再次执行。

## 3. 原理讲解与推导

### 3.1 事件循环与阻塞

JavaScript 主线程是单线程事件循环。`await` 让出执行权，但不是多线程；CPU 密集循环、同步解析大 JSON、同步加密仍会阻塞界面。CPU 工作要移到 Worker，Node 端可用 Worker Threads 或子进程；I/O 用异步 API。

### 3.2 并发不是越多越好

同时发 100 个请求会压垮后端、触发限流、增加内存。用并发上限：

```ts
async function mapLimit<T, R>(
  items: readonly T[],
  limit: number,
  run: (item: T) => Promise<R>,
): Promise<R[]> {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError("limit 必须是正整数");
  }
  const results: R[] = new Array(items.length);
  let next = 0;
  async function worker(): Promise<void> {
    while (next < items.length) {
      const index = next++;
      // index 一定小于 items.length；T 本身可以是 undefined，
      // 所以不能按“值是否为 undefined”跳过，否则会漏掉合法元素。
      results[index] = await run(items[index] as T);
    }
  }
  const workers = Math.min(limit, items.length);
  await Promise.all(Array.from({ length: workers }, worker));
  return results;
}
```

`next++` 在单线程事件循环里是安全的；每个 worker 取一个索引，完成后继续取，形成有界并发。错误处理要明确：一个失败是否停止全部、是否保留已完成结果。`limit` 为零、负数或非整数应直接拒绝；`items` 里的 `undefined` 是合法值，不能当“没有元素”跳过。

`mapLimit` 的返回值按原索引写回，所以即使第二个任务先完成，结果顺序仍与输入一致。配套实现位于 `map-limit.ts`；用 `[1, undefined, 3]`、并发上限 `2`、异步回调 `String(value)` 调用时，**预期返回值**是 `["1", "undefined", "3"]`，调用次数为 3，观测到的最大并发数为 2。空输入不启动 worker，返回 `[]`；`limit` 为 `Infinity`、`0.5` 或 `-1` 时抛出 `RangeError`。常见错误是把结果写成 `push`，让完成顺序替换输入顺序。

`withTimeout` 会及时拒绝调用方并**通知**回调取消，但不能强制停止一个不响应 `signal` 的回调。回调若忽略信号，仍可能继续执行并在稍后修改外部状态；要让它真正可中止，必须把信号传到底层 I/O，或在边界做隔离/丢弃结果。`Promise.race` 也不会取消输掉的一方，因此超时后的迟到结果必须丢弃。

`retry` 能否安全执行，取决于接收方契约，而不只是“有网络错误”或“带幂等键”：要确认动作身份、载荷、当前授权、预算和重复执行的业务后果。没有幂等键的写操作、权限已变化、载荷已过期时，不应自动重试。

### 3.3 取消与资源清理

取消不是“把 Promise 丢掉”，而是让底层操作停止并清理。需要清理的包括：定时器、事件监听、流读取器、WebSocket、Worker。`finally` 是统一清理位置。

## 4. 示例与逐步走查

下面并发加载三个独立资源，允许部分失败，并接受外部取消信号（本例不包含整体超时，见下文第 4 点）：

```ts
type Loaded<T> = { ok: true; value: T } | { ok: false; error: string };

async function loadDashboard(signal: AbortSignal): Promise<{
  documents: Loaded<unknown>;
  citations: Loaded<unknown>;
  model: Loaded<unknown>;
}> {
  const tasks = [
    ["documents", "/api/documents"],
    ["citations", "/api/citations"],
    ["model", "/api/model/status"],
  ] as const;
  const settled = await Promise.allSettled(
    tasks.map(async ([key, url]) => {
      const response = await fetch(url, { signal });
      if (!response.ok) throw new Error(`${key}: HTTP ${response.status}`);
      return [key, (await response.json()) as unknown] as const;
    }),
  );
  const output = {
    documents: { ok: false, error: "未加载" } as Loaded<unknown>,
    citations: { ok: false, error: "未加载" } as Loaded<unknown>,
    model: { ok: false, error: "未加载" } as Loaded<unknown>,
  };
  settled.forEach((result, index) => {
    const key = tasks[index]![0];
    output[key] = result.status === "fulfilled"
      ? { ok: true, value: result.value[1] }
      : { ok: false, error: String(result.reason) };
  });
  return output;
}
```

逐步解释：

1. `allSettled` 不会因一个资源失败而丢弃其他成功结果；每个资源单独映射为 `Loaded`。
2. `tasks` 用 `as const` 保留键的字面量，`output[key]` 才能被正确索引；`allSettled` 保证结果数与输入数相同，因此 `tasks[index]!` 的不为空断言依据这一 API 不变式。
3. `signal` 传给每个 `fetch`；外部取消时所有请求一起中止。
4. 实际项目还要给整体加超时、对错误分类，并在组件卸载时 abort。

在离线测试中给三个 URL 注入可控 `fetch`：文档返回 `{"id":"D1"}`，引用返回 500，模型状态返回 `{"ready":true}`。调用 `loadDashboard(new AbortController().signal)` 的**预期结构**为：

```text
documents.ok = true，documents.value = { id: 'D1' }
citations.ok = false，citations.error = "citations: HTTP 500"
model.ok = true，model.value = { ready: true }
```

返回对象的键顺序可能受运行环境影响，应逐项断言，不比较整个 JSON 字符串。这里没有整体超时，所以“某个 fetch 永远 pending”会让 `allSettled` 永远等待；这正好说明 `allSettled` 解决部分失败，不解决总时限。

## 5. 练习

### 练习一：跟写

给 `retry` 增加可取消的退避等待与总时限：外部取消或预算到期时立即停止，清理定时器；用测试证明取消后不会发起下一次调用。

### 练习二：改造

把 `mapLimit` 改成“任一失败即停止并取消其他任务”，用 `AbortController` 传递取消；比较“保留部分结果”和“全有或全无”的适用场景。

### 练习三：独立

验证 `withTimeout`：超时错误名称为 `TimeoutError`，`finally` 清理定时器；回调响应 `signal` 时不再写外部状态。再写一个反例：回调忽略 `signal` 时仍会继续完成，说明超时只通知取消，调用方必须丢弃迟到结果，不能把它当强制终止。

## 6. 验收与自测

**行为验收：** 独立请求并发；部分失败保留成功项；取消后无后续状态写入；超时清理定时器；重试只发生在可重试错误上。

**原理验收：** 能解释事件循环、`Promise.all` 与 `allSettled` 的差异、取消的协作性；能说出一个“不能重试”的 POST 例子。

### 6.1 先预测，再查看解释

`await Promise.all([a(), b()])` 中 `a()` 失败后，`b()` 会立即停止吗？

<details>
<summary>完成预测后查看解释</summary>

不会。`Promise.all` 在第一个拒绝时让外层 Promise 拒绝，但已经启动的 `b()` 仍继续执行；它不会自动取消。需要取消时传同一个 `AbortSignal`，并让 `b()` 响应信号——共享 signal 只保证一起收到取消通知，不会自动终止已经开始的底层操作。

</details>

## 7. 面试问答与参考回答

**问：`Promise.all` 和 `Promise.allSettled` 怎么选？**

需要全部成功才继续时用 `all`；需要展示部分成功/部分失败时用 `allSettled`。`all` 失败不会取消其他任务，需要额外 `AbortController`。

**问：取消一个 Promise 会发生什么？**

Promise 本身不可取消；取消要传给底层操作（`fetch`、流、定时器）。被取消的操作通常以 `AbortError` 拒绝，调用方要识别并清理资源，不能只忽略 Promise。

**问：哪些请求可以重试？**

幂等且错误可重试的请求：GET、带幂等键的写操作、429/5xx/网络抖动。无幂等键的 POST 超时后可能已执行，重试会重复写入；应先查询或对账。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 页面同时加载文档、引用和模型状态，用户离开后请求还在跑——谁负责取消、超时和收尾？

**一条主线：**

```text
独立请求 → allSettled + 并发上限 → AbortSignal 传播取消 → 超时、退避与有限重试 → finally 清理
```

**三个关键词：** Promise、取消、并发上限。Promise 表示未来的一次结果，`AbortSignal` 把取消传到 I/O，并发上限和重试策略决定失败时的成本。

**最容易错：**

- 忘记 `await`，留下未处理拒绝，或卸载后继续写状态。
- 以为 `Promise.all` 一失败就会取消其他请求：需要在失败处理里主动调用 abort，并让底层操作响应共享的 signal；仅传同一个 signal 不会自动触发取消。
- 把 `withTimeout` 当强制终止：回调不响应 signal 时仍会跑完并改外部状态。
- 对无幂等键的 POST 超时后直接重试，或让 `mapLimit` 把合法的 `undefined` 元素跳过。

**与前后章：** 上一章的错误分类告诉哪些失败可重试；下一章需要把 signal 和断流处理接到 SSE reader 上，边收边渲染。

**学完应能：**

- 用 `Promise.allSettled` 让三个资源独立成败，并给整体超时；
- 取消后确认没有后续状态写入，定时器和监听器都清掉；
- 写 `mapLimit` 并拒绝零、负数和非整数 `limit`；
- 说出一个不能自动重试的写操作，以及重试前要核对哪些条件。
