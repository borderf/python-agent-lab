# 第13章　认证、多租户与权限

[上一章](12-SQL与Drizzle事务.md) · [全书目录](教材目录.md) · [下一章](14-AI-SDK与工具调用.md)

## 1. 学习目标与前置知识

能设计 BFF 的会话/令牌认证，使用 HttpOnly Cookie、CSRF 防护和密码哈希；能从可信身份得到租户与角色，保证查询/写入不越权；能区分认证、授权和对象级权限。前置：第 11–12 章；熟悉 Spring Security 更佳。

**本章从这里开始：** 前端把 `tenant_id` 放进请求体就能读别家资料；令牌放 `localStorage` 被 XSS 偷走；用户 A 猜到用户 B 的资源 ID 就能打开。认证解决“你是谁”，授权解决“你能做什么”，多租户解决“数据属于谁”——三者不能混成一个中间件。

本章是第11章教学Bearer之上的设计与实现练习。下方省略的sessionStore、用户认证、角色变更、报告仓储与路由宿主需要自己实现；这些片段不属于当前已编译回归模块。先实现一条登录/读取/登出闭环，再扩JWT与审批，不把示意路由当现成服务。

## 2. 基础知识讲解

### 2.1 先分开传递方式、令牌格式与撤销策略

| 方式 | 存储 | 优点 | 风险 |
| --- | --- | --- | --- |
| HttpOnly Cookie 会话 | 浏览器 Cookie | JS 读不到，易撤销 | CSRF、跨站策略 |
| Bearer JWT | Header/内存 | 无状态、跨服务 | 泄露、撤销难、过期策略 |
| Bearer opaque token | 服务端会话表 | 可撤销、可审计 | 每次校验查存储 |

表中是常见组合，不是互斥类别：Cookie和Authorization Header描述如何传递，JWT描述令牌格式，服务端会话表描述状态与撤销。JWT也能放在HttpOnly Cookie中，不透明令牌也能用Bearer发送；HttpOnly不自动带来撤销，JWT也不自动决定存在哪里。

浏览器应用优先 **HttpOnly + Secure + SameSite Cookie**；不要把长期令牌放 `localStorage`。机器调用/服务间可以用 Bearer。BFF 负责把浏览器会话转成内部身份。

### 2.2 会话表与 Cookie

```ts
import { getCookie, setCookie, deleteCookie } from "hono/cookie";
import { randomUUID, createHash } from "node:crypto";

type SessionRow = {
  id: string;
  userId: string;
  tenantId: string;
  roles: string[];
  expiresAt: number;
};

// 只存 token 的哈希，数据库泄露也不能直接复用
function hashToken(token: string): string {
  return createHash("sha256").update(token).digest("hex");
}

async function createSession(user: { id: string; tenantId: string; roles: string[] }) {
  const token = randomUUID() + randomUUID();
  const session: SessionRow = {
    id: hashToken(token),
    userId: user.id,
    tenantId: user.tenantId,
    roles: user.roles,
    expiresAt: Date.now() + 1000 * 60 * 60 * 8,
  };
  await sessionStore.insert(session);
  return token;
}
```

登录成功后设置 Cookie：

```ts
app.post("/api/login", async (c) => {
  const body = await c.req.json();
  // 校验 body、查用户、验证密码（Argon2id/bcrypt）
  const user = await authenticate(body.email, body.password);
  if (!user) throw new HTTPException(401, { message: "邮箱或密码错误" });
  const token = await createSession(user);
  setCookie(c, "sid", token, {
    httpOnly: true,
    secure: true,
    sameSite: "Lax",
    path: "/",
    maxAge: 60 * 60 * 8,
  });
  return c.json({ ok: true });
});
```

`HttpOnly`阻止JS直接读取Cookie，却不能阻止已执行的恶意脚本以用户身份发请求；`Secure`限制HTTPS传递。SameSite是CSRF的补充防线，不能代替状态变更请求的CSRF校验。登出要删除服务端会话，而不只是清Cookie。参见[OWASP会话指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

### 2.3 认证中间件：从会话得到 Actor

```ts
type Actor = {
  userId: string;
  tenantId: string;
  roles: readonly string[];
};

app.use("/api/*", async (c, next) => {
  const token = getCookie(c, "sid");
  if (!token) throw new HTTPException(401, { message: "未登录" });
  const session = await sessionStore.find(hashToken(token));
  if (!session || session.expiresAt <= Date.now()) {
    deleteCookie(c, "sid", { path: "/" });
    throw new HTTPException(401, { message: "会话已过期" });
  }
  c.set("actor", {
    userId: session.userId,
    tenantId: session.tenantId,
    roles: session.roles,
  });
  await next();
});
```

`Actor` 是后续授权与数据过滤的唯一身份来源。不要在路由里重新读 `body.tenantId`；也不要把 `actor` 放进可被请求覆盖的对象。

BFF 若要继续以 Bearer 调 Python，会话表需要保存**服务端使用的上游令牌**（加密/受限读取），不能把长期令牌放进浏览器；示例为聚焦认证流程省略了这一列。更稳的做法是 BFF 用服务凭据换短期内部令牌，且 Python 必须验证该凭据，不能只信 `X-Internal-Tenant`。

### 2.4 多租户：过滤在数据层，不在 UI

```ts
async function getDocument(actor: Actor, documentId: string) {
  const row = await db.select().from(documents).where(and(
    eq(documents.id, documentId),
    eq(documents.tenantId, actor.tenantId),
  )).limit(1);
  return row[0] ?? null;
}
```

跨租户访问返回 **404**，不是 403：403 会泄露“这个 ID 存在但你没权限”。所有查询、更新、删除都带 `tenantId`；不要只在列表页过滤。

### 2.5 授权：角色与对象级检查

```ts
type Action = "document:read" | "document:write" | "report:approve";

function can(
  actor: Actor,
  action: Action,
  resource: { ownerId?: string; tenantId?: string },
): boolean {
  if (action === "document:read") return resource.tenantId === actor.tenantId;
  if (action === "document:write") {
    return resource.tenantId === actor.tenantId && actor.roles.includes("editor");
  }
  if (action === "report:approve") {
    return resource.tenantId === actor.tenantId
      && actor.roles.includes("approver")
      && typeof resource.ownerId === "string"
      && resource.ownerId !== actor.userId;
  }
  return false;
}
```

RBAC 适合粗粒度；对象级权限（owner、租户、审批人）要单独检查。“有 approver 角色”不等于“能批准自己创建的报告”。Java 的 `@PreAuthorize` 可表达规则，但数据过滤仍要进 repository/query。

### 2.6 JWT 校验：不要只 decode

如果使用 JWT：

```ts
import { jwtVerify } from "jose";

const { payload } = await jwtVerify(token, publicKey, {
  issuer: "https://auth.example.com",
  audience: "docpilot-console",
  algorithms: ["RS256"], // 本示例的发行方与公钥采用RS256；由可信配置决定
  requiredClaims: ["sub", "exp"],
});
```

必须验证签名、发行方、受众，并按应用策略要求主体和过期声明存在；“若有exp则检查”不等于“缺exp也拒绝”。上例显式要求sub/exp并限制算法；验签后仍要检查业务主体与租户的有效映射。不要用decode代替verify，也不从不可信Header决定允许算法或密钥来源。kid只能在可信密钥集合内选键；撤销与权限版本另行设计。[jose验证选项](https://github.com/panva/jose/blob/main/docs/jwt/verify/interfaces/JWTVerifyOptions.md)说明了requiredClaims与algorithms；接入时锁定实际版本后验证。

### 2.7 CSRF、XSS 与限流

- Cookie 会话的状态变更请求加 CSRF token（双提交或同步令牌）；
- 所有用户内容转义；不要 `dangerouslySetInnerHTML`；
- 登录/提问/导出接口限流，按用户和 IP；
- 失败次数过多加延迟/验证码，不要只返回“密码错误”无限尝试；
- 日志不记录密码、完整令牌、完整提问中的敏感内容。

## 3. 原理讲解与推导

### 3.1 认证、授权、租户隔离是三层

1. 认证：请求属于哪个 Actor；
2. 授权：Actor 能否执行该动作；
3. 租户隔离：查询/写入是否只触及该 Actor 的租户数据。

只在路由做认证，忘了 repository 过滤，仍会越权。三层都要有测试：无令牌 401、无角色 403、跨租户 404。

### 3.2 会话撤销与 JWT 的取舍

纯本地验签JWT不查会话状态，权限变化与撤销就不会自动立即传播；短寿命降低窗口，立即撤销需要在线状态、拒绝列表或权限版本。服务端会话表便于集中控制，但仍要处理缓存失效与可用性。Cookie只是传递方式，不负责这些状态语义。

### 3.3 权限检查的位置

粗粒度在路由/服务入口，细粒度在数据查询条件里。不要把权限只放前端按钮：按钮隐藏是 UX，不是安全。也不要把所有权限塞进一个 `isAdmin` 布尔值；角色会增长，动作要显式。

## 4. 示例与逐步走查

```ts
app.get("/api/documents/:id", async (c) => {
  const actor = c.get("actor");
  const row = await getDocument(actor, c.req.param("id"));
  if (!row) throw new HTTPException(404, { message: "文档不存在" });
  if (!can(actor, "document:read", { tenantId: row.tenantId })) {
    throw new HTTPException(403, { message: "无权读取" });
  }
  return c.json({ id: row.id, title: row.title, version: row.version });
});

app.post("/api/reports/:id/approve", async (c) => {
  const actor = c.get("actor");
  const body: unknown = await c.req.json().catch(() => null);
  // isRecord复用第4章的对象守卫；只接收用户确认时展示的版本与摘要。
  if (!isRecord(body) || Object.keys(body).sort().join(",") !== "expectedHash,expectedVersion"
      || typeof body.expectedVersion !== "number" || !Number.isSafeInteger(body.expectedVersion)
      || body.expectedVersion < 1 || typeof body.expectedHash !== "string"
      || !/^[0-9a-f]{64}$/.test(body.expectedHash)) {
    throw new HTTPException(422, { message: "需要展示时的版本与载荷摘要" });
  }
  const report = await getReport(actor, c.req.param("id"));
  if (!report) throw new HTTPException(404, { message: "报告不存在" });
  if (!can(actor, "report:approve", {
    tenantId: report.tenantId, ownerId: report.createdBy,
  })) {
    throw new HTTPException(403, { message: "无权批准" });
  }
  if (body.expectedVersion !== report.version || body.expectedHash !== report.payloadHash) {
    throw new HTTPException(409, { message: "报告已变化，请重新确认" });
  }
  await approveReport(actor, report.id, body.expectedVersion, body.expectedHash);
  return c.json({ ok: true });
});
```

权限函数只回答“谁能做”，不保证“批准的是用户刚看到的版本”。请求须携带展示时的版本/摘要，不能让服务器默默采用重新读取的最新版。approveReport还必须在事务中按租户、版本、摘要与waiting_approval条件更新并检查受影响行数，防止读后又变化；记录批准人和批准范围。后续效果执行也需核对批准与载荷，并使用稳定动作键。可先完成Python第25章的恢复契约，再迁移此边界。

逐步解释：

1. 先按租户取资源；不存在/跨租户统一 404。
2. 再做动作授权；角色不够或自批返回 403。
3. 写操作记录 actor、时间、旧/新状态，便于审计。
4. 修改载荷后旧批准失效；进入executing后冻结待对账动作，不要把“有角色”当成“这次载荷可批准”。

## 6. 验收与自测

**行为验收：** 无会话 401；过期会话清除 Cookie；跨租户 404；无角色 403；自批 403；登出后旧会话失效；日志不含令牌/密码。

**原理验收：** 能解释认证/授权/租户隔离三层、Cookie 与 JWT 的取舍、CSRF 与 XSS 的边界。

### 6.1 先预测，再查看解释

用户 A 用自己的有效会话请求用户 B 的文档 ID，为什么返回 404 而不是 403？

<details>
<summary>完成预测后查看解释</summary>

404 不泄露“该 ID 是否存在”。403 会告诉攻击者“这个资源存在，只是你没权限”，可用于枚举。跨租户资源应表现得像不存在；只有同一租户内、存在但无动作权限时才用 403。

## 7. 面试问答与参考回答

**问：Cookie 会话和 JWT 怎么选？**

先分开两件事：Cookie是传递方式，JWT是格式，可以组合。浏览器可用HttpOnly Cookie携带不透明会话ID，由BFF维护撤销；服务间可用受限、短寿命JWT。选择取决于主体、信任边界、撤销时效和维护成本，不能由“JWT更先进”决定。

**问：认证和授权有什么区别？**

认证确认“你是谁”（登录、会话、令牌）；授权确认“你能做什么”（角色、对象级权限）。多租户还要确认“数据属于谁”，并在查询层过滤。

**问：为什么跨租户返回 404？**

避免泄露资源存在性，降低枚举风险。同一租户内存在但无权限才返回 403；两种响应的语义要统一。

## 8. 本章小结与参考

- 浏览器优先 HttpOnly Cookie 会话；密码用 Argon2id/bcrypt。
- Actor 来自可信会话；租户过滤进查询，不只做 UI 隐藏。
- 认证 401、授权 403、跨租户 404；三层分别测试。
- JWT 必须验签、iss/aud/exp；撤销与轮换要设计。
