## 1. 学习目标与前置知识

能解释 ESM 与 CommonJS 的差异，能配置 `package.json`/`tsconfig`，能用 pnpm 管理依赖与 workspace，能区分 `tsc` 类型检查与打包器构建，能让 CI 在干净环境复现。前置：第 1–6 章；有 Maven/Gradle 经验即可。

**本章从这里开始：** 代码在本机能跑，换一台机器就报 `Cannot find module`；`tsc` 通过，`vite build` 却失败；本地装了依赖，CI 因 lockfile 不一致挂掉。Java 的 classpath、Maven 多模块和编译插件，在 TypeScript 里分别对应什么？

## 2. 基础知识讲解

### 2.1 ESM 与 CommonJS

Node 有两套模块系统：

- **CommonJS（CJS）**：`require()` / `module.exports`，同步加载，历史上是 Node 默认。
- **ES Modules（ESM）**：`import` / `export`，静态分析，浏览器原生支持。

新项目优先 ESM。`package.json` 写 `"type": "module"`，`.ts` 编译成 `.js` 后按 ESM 解释；需要 CJS 的文件用 `.cjs`，需要 ESM 的用 `.mjs`。

```ts
// src/money.ts
export type Cents = number;

export function formatCents(cents: Cents): string {
  return `¥${(cents / 100).toFixed(2)}`;
}
```

```ts
// src/index.ts
import { formatCents } from "./money.js";

console.log(formatCents(1990));
```

注意导入路径写 `./money.js`，不是 `./money.ts`：TypeScript 编译后运行时找的是 `.js`。`moduleResolution: "NodeNext"` 会按 Node 的 ESM 规则解析，允许源码里写 `.js` 并映射到 `.ts`。Vite 项目常用 `"Bundler"` 解析，可以省略扩展名，但库/Node 项目不要依赖打包器的宽松规则。

`import type` 只导入类型，编译后消失：

```ts
import type { Cents } from "./money.js";
import { formatCents } from "./money.js";

const amount: Cents = 1990;
console.log(formatCents(amount));
```

打开 `verbatimModuleSyntax` 后，类型导入必须写 `import type`，避免运行时残留一个不存在的导出。Java 的 `import` 只影响编译期名称解析；TypeScript 的 `import` 可能产生运行时副作用，两者不能直接类比。

### 2.2 `package.json` 是契约，不只是依赖清单

一个可交付的包至少说明：

```json
{
  "name": "@docpilot/console",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "packageManager": "pnpm@9.12.0",
  "engines": { "node": ">=22" },
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "vite build",
    "test": "vitest run"
  },
  "dependencies": {},
  "devDependencies": {}
}
```

- `private: true` 防止误发布；
- `packageManager` 固定 pnpm 版本，CI 用 Corepack；
- `engines` 说明 Node 下限；
- `dependencies` 是运行时依赖，`devDependencies` 只用于开发/构建/测试；
- `scripts` 是团队和 CI 的入口，不要求每个人记住长命令。

库还要写 `exports`，明确哪些路径是公开 API：

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "files": ["dist"]
}
```

`exports` 是包边界：未列出的内部文件不能被外部 import。Java 的 `module-info.java`/包可见性也表达边界，但 npm 包的边界默认更松，必须显式收。

### 2.3 `tsconfig`：类型检查的编译契约

应用和库的配置不同。应用常用：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "verbatimModuleSyntax": true,
    "noEmit": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

库/Node 项目把 `module`/`moduleResolution` 改成 `NodeNext`，并设置 `declaration: true`、`outDir: "dist"`、`rootDir: "src"`，由 `tsc` 产出 `.js` 与 `.d.ts`。

几个容易混淆的选项：

- `noEmit`：只检查，不产出；应用交给 Vite/Rollup 打包时常这样。
- `skipLibCheck`：跳过依赖声明文件的类型检查，能加速，但不能掩盖自己代码的错误。
- `paths` 别名：`@/*` 只在类型检查/打包器配置一致时才有效；Node 运行时不会自动认识，库不要依赖别名。
- `isolatedModules`：保证每个文件可独立转译；Vite/esbuild 需要，避免 `const enum` 等跨文件假设。

`tsc --noEmit` 是类型检查，不是打包；`vite build` 是打包，不负责完整类型检查（Vite 用 esbuild 转译，类型错误可能不阻塞）。CI 要两条都跑。

### 2.4 构建：类型检查与打包分开

```text
源码 .ts/.tsx
  ├─ tsc --noEmit        类型检查、生成 .d.ts（库）
  └─ Vite/Rollup/esbuild 转译、打包、压缩、source map
```

应用构建通常输出 `dist/`，由静态服务器托管；库构建输出 ESM（必要时 CJS）和 `.d.ts`，并写 `exports`。source map 用于线上定位，但不要把含密钥的源码映射公开。

Java 的 `javac` 同时编译和产出 class；TypeScript 把“类型检查”和“打包”拆成两条工具链，这是常见困惑来源。不要指望 `vite build` 失败来发现所有类型错误。

### 2.5 pnpm、lockfile 与 workspace

```powershell
corepack enable
pnpm install
pnpm add -D typescript vite vitest
pnpm typecheck
pnpm build
```

`pnpm-lock.yaml` 必须提交；CI 用 `pnpm install --frozen-lockfile`，锁文件与 `package.json` 不一致时直接失败。Java 的 `pom.xml`/`build.gradle` 锁版本，npm 生态需要 lockfile 才能复现。

多包仓库用 workspace：

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
```

```json
{
  "dependencies": {
    "@docpilot/contracts": "workspace:*"
  }
}
```

`workspace:*` 表示使用本地包，不发布也能联调。包之间通过 `exports` 暴露公共 API，不互相深入 `src`。小项目不要为了“看起来像大厂”上 monorepo；一个包能解决就先一个包。

### 2.6 环境变量与配置

Node 读 `process.env`，Vite 浏览器侧只暴露 `import.meta.env.VITE_*`。**只有 `VITE_` 前缀的变量会进入浏览器包**，不要把模型密钥写成 `VITE_OPENAI_KEY`。

```ts
/// <reference types="vite/client" />
// src/config.ts

function required(name: string): string {
  const value = import.meta.env[name as keyof ImportMetaEnv];
  if (typeof value !== "string" || value.length === 0) {
    throw new Error(`缺少环境变量 ${name}`);
  }
  return value;
}

export const config = {
  apiBaseUrl: required("VITE_API_BASE_URL"),
};
```

配置在启动时校验，失败就明确报错，不要等到第一次请求才出现 `undefined/api`。Node BFF 的密钥只放服务端环境变量，前端永远不接触。

## 3. 原理讲解与推导

### 3.1 模块解析是“按规则找文件”

Node ESM 解析 `import "./money.js"` 时按相对路径找文件；裸导入 `import "zod"` 先查 `node_modules`，再看包的 `exports`。缺 `exports` 时可能落到 `main`，行为随包版本变化。**库的公开入口要写 `exports`，应用不要依赖内部路径。**

### 3.2 类型导入与运行时导入是两件事

`import type` 完全擦除；普通 `import` 可能保留副作用。一个只被类型使用的导入如果写成普通导入，打包器可能保留它，造成循环依赖或运行时错误。`verbatimModuleSyntax` 让这类问题在编译期暴露。

### 3.3 依赖方向与包边界

Java 多模块用 Maven 依赖表达方向；TypeScript workspace 也用依赖方向。区别是 npm 包默认可以深层导入，必须靠 `exports`、lint 规则和 code review 约束。不要让 `apps/web` 直接 import `packages/core/src/internal.ts`；只走包入口。

## 4. 示例与逐步走查

下面是一个最小应用的文件结构：

```text
docpilot-console/
  package.json
  tsconfig.json
  index.html
  src/
    main.ts
    config.ts
    api/client.ts
```

`src/api/types.ts` 沿用第 3 章的契约，这里只保留示例字段：

```ts
export type SearchHit = {
  sourceId: string;
  version: string;
  quote: string;
};
```

`src/api/client.ts`：

```ts
import type { SearchHit } from "./types.js";

export async function search(
  baseUrl: string,
  question: string,
  asOf: string,
  signal: AbortSignal,
): Promise<SearchHit[]> {
  const response = await fetch(`${baseUrl}/api/search`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question, as_of: asOf }),
    signal,
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  const payload: unknown = await response.json();
  // 这里应调用第4章的校验器；示例先断言形状
  if (typeof payload !== "object" || payload === null || !Array.isArray((payload as { items?: unknown }).items)) {
    throw new Error("search 响应格式不合法");
  }
  return (payload as { items: SearchHit[] }).items;
}
```

`src/main.ts`：

```ts
import { config } from "./config.js";
import { search } from "./api/client.js";

const controller = new AbortController();
const hits = await search(config.apiBaseUrl, "预付款", "2026-07-01", controller.signal);
console.log(hits.length);
```

命令：

```powershell
pnpm install
pnpm typecheck
pnpm build
```

逐步解释：

1. `package.json` 的 `type: module` 让 `.js` 按 ESM 解释；导入路径写 `.js`。
2. `tsconfig` 的 `moduleResolution: "Bundler"` 适合 Vite；如果这是 Node 库，改成 `NodeNext` 并产出 `dist`。
3. `tsc --noEmit` 先过类型；`vite build` 再过打包。两条都绿才算构建成功。
4. 环境变量在 `config.ts` 启动时校验；浏览器只拿 `VITE_API_BASE_URL`，不拿密钥。
5. `fetch` 的 `signal` 从中断控制器传入；取消会以 `AbortError` 结束。

## 6. 验收与自测

**行为验收：** 干净环境 `pnpm install --frozen-lockfile` 成功；`typecheck` 与 `build` 都通过；库的 `exports` 只暴露公共入口；缺失环境变量在启动时报错。

**原理验收：** 能解释 ESM/CJS、`import type`、`moduleResolution`、`tsc` 与打包器分工；能说出 lockfile 和 `exports` 各自解决什么。

### 6.1 先预测，再查看解释

`tsc --noEmit` 通过，`vite build` 也通过，为什么运行时仍可能 `Cannot find module "./money.js"`？

<summary>完成预测后查看解释</summary>

## 7. 面试问答与参考回答

**问：ESM 和 CommonJS 的核心区别？**

ESM 是静态模块系统，导入导出在编译期可分析，浏览器原生支持；CJS 用 `require` 同步加载，运行时解析。新项目优先 ESM，混用时注意 `.mjs/.cjs`、默认导出互操作和 `exports` 条件。

**问：`tsc` 和 Vite 各自做什么？**

`tsc` 做类型检查，库项目还生成 `.js`/`.d.ts`；Vite 负责转译、打包、开发服务器和静态资源。Vite 用 esbuild 转译，不等同完整类型检查，CI 要两条都跑。

**问：lockfile 为什么必须提交？**

它固定整棵依赖树的精确版本与解析结果，保证本机、CI、部署环境安装出同一套依赖。只写 `^1.2.3` 不能复现；CI 用 `--frozen-lockfile` 防止锁文件漂移。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 代码在本机能跑、换机器就 `Cannot find module`，`tsc` 通过而 `vite build` 失败——模块究竟按什么规则被找到？

**一条主线：**

```text
源码 import → package.json（type/exports）→ tsconfig 解析规则 → tsc 检查 + 打包器产出 → 目标环境按真实文件系统加载
```

**三个关键词：** exports、解析、构建。`exports` 收住包的公开边界，解析规则保证源码和运行时指向同一路径，构建把类型检查与产物分开。

**最容易错：**

- 只在 `paths` 别名或打包器的宽松解析下跑通，发布后没有 `exports`，或路径大小写在 Linux 上不匹配。
- 类型导入写成普通 `import`，留下不存在的运行时导出或循环依赖。
- 把 `tsc --noEmit` 当打包、把 `vite build` 当完整类型检查，CI 只跑其中一条。
- 不提交 `pnpm-lock.yaml`、不用 `--frozen-lockfile`，或把密钥写成 `VITE_` 前缀送进浏览器。

**与前后章：** 上一章的 SSE 解析器要作为一个模块被引用；下一章需要在包边界内导入 React 组件与 hooks，并保持构建可复现。

**学完应能：**

- 用 `exports` 和 `files` 发布只暴露入口的库，再从独立目录 import 验证边界；
- 让 `pnpm typecheck` 与 `pnpm build` 在干净环境都通过；
- 解释 `import type`、`verbatimModuleSyntax`、NodeNext 与 Bundler 的差别；
- 在启动时校验 `VITE_API_BASE_URL`，缺配置就明确报错。
