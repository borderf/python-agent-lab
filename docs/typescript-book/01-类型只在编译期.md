# 第01章　类型只在编译期：TypeScript 的边界

[上一章](00-导读与学习方法.md) · [全书目录](教材目录.md) · [下一章](02-联合收窄与状态.md)

## 1. 学习目标与前置知识

能解释 TypeScript 类型在编译后发生了什么，能区分“编译期形状”和“运行时值”，并用 `unknown` 与类型守卫处理外部输入。前置：会一种后端语言，能读 JSON；不要求 JavaScript 精通。

**本章从这里开始：** 后端返回一段 JSON，TypeScript 说它是 `Answer`，浏览器却可能收到 `null`、字段缺失或类型不同。类型检查通过了，为什么运行时仍会崩？这一章先建立“类型在编译期、值在运行时”的边界。

## 2. 基础知识讲解

### 2.1 TypeScript 先编译，再运行

`.ts` 文件不能直接被浏览器执行。`tsc` 做两件事：检查类型，然后把类型擦除，输出 `.js`。运行时看到的是 JavaScript，类型注解、`interface`、`type` 都不存在。

```ts
interface Citation {
  readonly sourceId: string;
  readonly quote: string;
}

function formatCitation(citation: Citation): string {
  return `${citation.sourceId}: ${citation.quote}`;
}

console.log(formatCitation({ sourceId: "policy-a", quote: "20%" }));
```

编译后的 JavaScript 大致是：

```js
function formatCitation(citation) {
  return `${citation.sourceId}: ${citation.quote}`;
}
```

`Citation` 没有进入运行时。调用方传 `{ sourceId: 1, quote: null }` 时，`tsc` 会报错；但如果数据来自 `JSON.parse`、网络或 `localStorage`，编译器看不到真实值，必须在运行时检查。

`tsconfig.json` 决定检查严格程度。学习阶段至少打开：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noEmit": true
  }
}
```

`strict` 打开 `strictNullChecks`、`noImplicitAny` 等一组检查；`noUncheckedIndexedAccess` 让 `array[0]` 可能是 `undefined`；`exactOptionalPropertyTypes` 区分“没有这个属性”和“属性值是 undefined”。先用 `npx tsc --noEmit` 只检查，不产出文件。

### 2.2 结构化类型：形状匹配就能赋值

TypeScript 主要按形状比较，不要求 `implements`：

```ts
type HasId = { id: string };
type Order = { id: string; amountCents: number };

const order: Order = { id: "A", amountCents: 1990 };
const withId: HasId = order; // 多出的字段可以赋值给更窄的形状
```

这带来灵活性，也带来误判：一个对象“看起来像”订单，不代表它的金额、状态和来源已经可信。结构类型只描述形状，不描述业务不变量。

反过来，`Order` 需要的字段少了会报错：

```ts
const incomplete: Order = { id: "B" }; // 缺少 amountCents
```

对象字面量还会触发“多余属性检查”，但把对象先赋给变量再传入，检查会放松。不要依赖多余属性检查来验证外部数据。

### 2.3 `any`、`unknown` 与类型守卫

`any` 关闭检查，值可以随意使用；`unknown` 表示“现在不知道”，使用前必须收窄。外部输入应该先进入 `unknown`，再通过守卫变成可信类型。

```ts
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null && !Array.isArray(value);
}

function isAnswer(value: unknown): value is {
  answer: string;
  sourceIds: string[];
  needsReview: boolean;
} {
  if (!isRecord(value)) return false;
  return (
    typeof value.answer === "string" &&
    value.answer.trim().length > 0 &&
    Array.isArray(value.sourceIds) &&
    value.sourceIds.every((id) => typeof id === "string" && id.length > 0) &&
    typeof value.needsReview === "boolean"
  );
}
```

`value is T` 是用户定义类型守卫。守卫返回 `true` 时，调用方在分支内获得 `T` 的类型；返回 `false` 时不应假定字段存在。`typeof` 能收窄原始类型，`in` 能检查属性，`instanceof` 只对类等运行时构造器可靠；JSON 对象不是类实例。

`as` 是断言，不是转换：它只告诉编译器“相信我”，不会在运行时检查，也不会改变值。`as Answer` 用在外部输入上，等于把校验责任丢掉。

### 2.4 `type` 与 `interface` 的选择

两者都能描述对象形状。日常规则：

- 需要联合、交叉、映射、条件类型时用 `type`；
- 需要声明合并或给类实现契约时用 `interface`；
- 同一项目不要为同一形状同时维护两份。

```ts
// Citation 沿用本章开头的 interface；这里只演示 type 描述 Answer。
type Answer = {
  answer: string;
  citations: Citation[];
  needsReview: boolean;
};
```

`readonly` 只阻止通过该类型重新赋值属性，不冻结对象，也不阻止数组内容变化；运行时仍可能被其他引用修改。

## 3. 原理讲解与推导

### 3.1 类型检查发生在运行之前

TypeScript 检查的是“在当前代码里，值的可能类型是否兼容”，不是“运行时一定收到这个类型”。编译器无法知道网络返回什么，也无法阻止别的进程写数据库。因此：

- 内部函数之间可以用类型契约；
- 外部边界必须把 `unknown` 变成已验证值；
- `JSON.parse` 的返回类型是 `any`，应立刻当作 `unknown` 处理。

```ts
const raws: unknown = JSON.parse('{"answer":"20%","citations":[],"needsReview":true}');
if (!isAnswer(raws)) throw new Error("回答格式不合法");
const answer = raws; // 这里才是 Answer
```

如果直接把 `JSON.parse(text) as Answer`，编译器会满意，运行时仍可能拿到 `null`。这是本章最重要的边界。

### 3.2 类型擦除带来两个后果

第一，运行时没有类型信息，不能靠 `typeof value === "Answer"` 判断业务类型；只能检查结构、字段和值。第二，类型不会自动生成文档或校验器，二者要单独维护，最好由同一份 schema 生成。

### 3.3 类型系统的能力边界

TypeScript 能检查：属性是否存在、类型是否兼容、联合是否穷尽、泛型约束是否满足。它不能检查：字符串是否是合法日期、金额是否与原文一致、用户是否有权限、外部服务是否真的返回了这个结构。这些属于运行时和业务规则。

## 4. 示例与逐步走查

下面把一个“后端回答”从 `unknown` 收窄成可信对象，并保持错误可定位：

```ts
// 复用本章 2.4 的 Citation/Answer；这里只补运行时守卫。
function isCitation(value: unknown): value is Citation {
  return (
    isRecord(value) &&
    typeof value.sourceId === "string" &&
    value.sourceId.length > 0 &&
    typeof value.quote === "string" &&
    value.quote.length > 0
  );
}

function parseAnswer(value: unknown): Answer {
  if (!isRecord(value)) throw new Error("回答必须是对象");
  const { answer, citations, needsReview } = value;
  if (typeof answer !== "string" || !answer.trim()) {
    throw new Error("answer 不能为空");
  }
  if (!Array.isArray(citations) || !citations.every(isCitation)) {
    throw new Error("citations 格式不合法");
  }
  if (typeof needsReview !== "boolean") {
    throw new Error("needsReview 必须是布尔值");
  }
  if (citations.length === 0 && !needsReview) {
    throw new Error("没有引用时必须标记待复核");
  }
  return { answer, citations, needsReview };
}
```

逐步解释：

1. `isRecord` 排除 `null` 和数组，保证后续能按字符串键读取。
2. `isCitation` 检查每个引用；`every` 在遇到第一个 `false` 时返回 `false`，不会访问不存在的字段。
3. 先检查类型，再检查业务规则“无引用必须待复核”；类型系统和业务规则是两层。
4. 返回新对象，不把原对象直接断言成 `Answer`。

尝试把 `parseAnswer(JSON.parse('null'))`、`parseAnswer({answer:"20%",citations:[],needsReview:false})` 和缺字段的输入分别运行，记录错误发生在哪一层。再把 `needsReview` 改成字符串 `"false"`，确认它被拒绝，而不是被当成真值。

## 5. 练习

### 练习一：跟写

为 `Citation` 写 `isCitation`，覆盖 `sourceId` 为空、`quote` 不是字符串、多余字段三种输入。多余字段是否允许由契约决定，不接受“TypeScript 没报错”作为理由。

### 练习二：改造

把 `parseAnswer` 改为返回 `Result<Answer, string>`，不抛异常；调用方必须处理 `ok: false`。保留原有错误信息，不把不同失败压成一个 `"invalid"`。

### 练习三：独立

写一个 `parsePage<T>(value: unknown, parseItem: (item: unknown) => T): { items: T[]; nextCursor: string | null }`。要求 `value` 必须是对象，`items` 必须是数组，`nextCursor` 必须是字符串或 `null`；坏输入给出具体字段。

## 6. 验收与自测

**行为验收：** `npx tsc --noEmit` 通过；三类坏输入分别被拒绝；合法输入得到新对象；错误信息能指出字段。

**原理验收：** 能解释类型擦除、结构化类型和 `as` 的风险；能举一个“编译通过但运行失败”的输入，并说明运行时守卫在哪一步拦住它。

### 6.1 先预测，再查看解释

`const value: unknown = JSON.parse('{"answer":"20%"}'); if (typeof value === "object" && value !== null) { console.log(value.answer) }` 为什么仍可能报错或得到 `undefined`？

<details>
<summary>完成预测后查看解释</summary>

`typeof value === "object"` 只排除原始类型，`value` 仍是 `object` 或 `null`（已排除），但 TypeScript 不会因此知道它有 `answer` 字段。需要 `isRecord` 或 `"answer" in value` 进一步收窄；即使字段存在，也要检查它是不是非空字符串。

</details>

## 7. 面试问答与参考回答

**问：TypeScript 的类型在运行时存在吗？**

不存在。类型在编译后被擦除，运行时是 JavaScript。类型检查只覆盖编译期能看到的代码；网络、文件、数据库和用户输入必须运行时校验。

**问：`any` 和 `unknown` 有什么区别？**

`any` 关闭检查，可以随意读写；`unknown` 要求先收窄再使用。外部输入应进入 `unknown`，通过类型守卫变成可信类型，而不是用 `as` 跳过检查。

**问：结构化类型有什么风险？**

形状匹配不代表业务不变量成立。一个对象字段齐全，仍可能是旧版本、空字符串或伪造来源；结构类型只保证编译期形状，业务规则要另测。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 类型检查都通过了，为什么网络返回的 JSON 仍可能在运行时崩？

**一条主线：**

```text
类型标注 → tsc 检查后擦除 → 外部值先收进 unknown → 类型守卫收窄 → 可信的 Answer
```

**三个关键词：** 擦除、结构化类型、类型守卫。擦除说明类型不是运行时证据，结构化类型只比形状、不比业务事实，类型守卫负责把 unknown 变成可用的值。

**最容易错：**

- 用 `as Answer` 接 `JSON.parse` 的结果：断言只让编译器闭嘴，运行时不检查任何字段。
- 以为 `typeof value === "object"` 就能读 `value.answer`，忘了 `null`、数组和缺失字段。
- 把 `readonly` 当运行时冻结，或认为形状匹配就等于金额、状态和来源可信。
- 关掉 `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`，把边界问题留到运行时。

**与前后章：** 上一章（导读）给出 DocPilot 场景与 `pnpm typecheck` 的读法；下一章需要本章结论——类型只约束代码内部——才能把任务状态写成字面量联合。

**学完应能：**

- 用 `unknown` 加 `isAnswer` 把一段 `JSON.parse` 结果收窄成 `Answer`，坏输入报出具体字段；
- 举出一个“编译通过、运行失败”的输入，并指出守卫在哪一步拦住它；
- 解释 `interface`/`type`、`readonly` 和结构化类型各保证什么、不保证什么；
- 在开启 strict 的配置下用 `npx tsc --noEmit` 复现一次边界错误。
