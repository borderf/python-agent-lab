# 第03章　对象、泛型与接口契约

[上一章](02-联合收窄与状态.md) · [全书目录](教材目录.md) · [下一章](04-运行时校验与错误边界.md)

## 1. 学习目标与前置知识

能用 `interface`/`type` 描述 API 契约，用泛型表达“对多种类型成立的同一操作”，用 `keyof`/工具类型减少重复，并判断何时不该继续抽象。前置：第 1–2 章。

**本章从这里开始：** 后端有分页、搜索结果、错误响应和多种资源；如果每种资源都复制一遍分页字段，改一个字段就要改十几处。哪些部分应该泛型化，哪些应该保持具体？

## 2. 基础知识讲解

### 2.1 `interface` 与 `type`

```ts
interface Citation {
  readonly sourceId: string;
  readonly quote: string;
}

type Answer = {
  answer: string;
  citations: Citation[];
  needsReview: boolean;
};
```

`interface` 可以声明合并，适合给类实现、给库扩展；`type` 可以表达联合、交叉、映射和条件类型。同一形状选一种，不要为了“看起来像 Java”到处建 interface。

`readonly` 是编译期约束：不能通过该类型重新赋值字段，但对象仍可能被其他引用修改；数组用 `readonly string[]` 才阻止 `push`。

### 2.2 泛型：把类型当参数

分页结构对多种资源都一样：

```ts
type Page<T> = {
  items: T[];
  nextCursor: string | null;
};

type CitationPage = Page<Citation>;
type AnswerPage = Page<Answer>;

function firstOrNull<T>(items: readonly T[]): T | null {
  const first = items[0];
  return first === undefined ? null : first;
}
```

`T` 是类型参数，调用时由实参推断。`readonly T[]` 接受普通数组和只读数组，不修改输入。泛型的目标是“同一操作对多种类型成立”，不是“让代码看起来高级”。

约束用 `extends`：

```ts
type HasId = { id: string };

function indexById<T extends HasId>(items: readonly T[]): Map<string, T> {
  const result = new Map<string, T>();
  for (const item of items) {
    if (result.has(item.id)) throw new Error(`重复 id: ${item.id}`);
    result.set(item.id, item);
  }
  return result;
}
```

`T extends HasId` 保证能读 `item.id`；返回值保留具体类型，不会退化成 `HasId`。

### 2.3 `keyof` 与工具类型

`keyof T` 是 T 的键的联合：

```ts
type AnswerKeys = keyof Answer; // "answer" | "citations" | "needsReview"

function pick<T, K extends keyof T>(value: T, keys: readonly K[]): Pick<T, K> {
  const result = {} as Pick<T, K>;
  for (const key of keys) result[key] = value[key];
  return result;
}

const answer: Answer = {
  answer: "预付款比例不得超过20%。",
  citations: [{ sourceId: "policy-a", quote: "不得超过20%" }],
  needsReview: false,
};

const summary = pick(answer, ["answer", "needsReview"]);
```

`Pick<T, K>`、`Omit<T, K>`、`Partial<T>`、`Required<T>`、`Record<K, V>` 是常用工具类型。它们只在类型层工作，不复制运行时值。

`Record<string, unknown>` 适合“键未知的对象”；`Record<string, Citation>` 表示每个值都必须是 Citation。不要用 `object` 当“任意对象”，它不能安全读取属性；用 `Record<string, unknown>` 或具体接口。

### 2.4 函数类型与回调

```ts
type ModelCall = (prompt: string, signal?: AbortSignal) => Promise<string>;

async function withRetry(call: ModelCall, prompt: string): Promise<string> {
  try {
    return await call(prompt);
  } catch (error) {
    return await call(prompt);
  }
}
```

函数类型要写清参数、返回值和可选参数；`Promise<string>` 表示异步结果。回调参数用 `unknown` 接收外部错误，不要假设 `Error`。

## 3. 原理讲解与推导

### 3.1 泛型在编译后被擦除

`Page<T>` 不会生成运行时类；`T` 只参与检查。运行时无法判断 `items` 是不是 `Citation[]`，因此分页数据从网络进入时仍要逐项校验。

### 3.2 契约应表达“谁负责什么”

一个 API 类型至少说明：

- 必填与可选字段；
- 字段的单位和含义（`amountCents` 而不是 `amount`）；
- 错误形状（错误码、消息、可重试标记）；
- 版本与来源（`version`、`sourceId`）。

类型名和字段名是契约的一部分，不要用 `data`、`info`、`result` 掩盖业务含义。

### 3.3 抽象的边界

如果两个类型只是字段名不同、行为完全一致，可以用泛型；如果业务规则不同，先保留具体类型。过早泛型会让错误信息变长、调用方需要写更多类型参数。判断标准：抽象后是否减少了重复，同时没有隐藏业务差异。

## 4. 示例与逐步走查

下面为 DocPilot 的搜索与错误响应建模：

```ts
// Page<T> 复用 2.2 的定义，避免同一形状声明两次。
type SearchHit = {
  chunkId: string;
  sourceId: string;
  version: string;
  title: string;
  text: string;
  start: number;
  end: number;
};

type ApiError = {
  code: "unauthorized" | "invalid_input" | "timeout" | "internal";
  message: string;
  retryable: boolean;
};

type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: ApiError };

function unwrap<T>(result: ApiResult<T>): T {
  if (result.ok) return result.data;
  throw new Error(`${result.error.code}: ${result.error.message}`);
}

function mergePages<T>(pages: readonly Page<T>[]): T[] {
  return pages.flatMap((page) => page.items);
}
```

逐步解释：

1. `SearchHit` 把来源、版本、标题、原文片段和偏移都写进契约，前端不能只拿一段文本；UI 的 `quote` 是 `text` 的展示名，不是后端字段。
2. `Page<T>` 让搜索结果和文档列表复用分页，不复制 `items/nextCursor`。
3. `ApiError.code` 用字面量联合，UI 可以按错误码分支；`retryable` 是业务判断，不由 HTTP 状态码单独推断。
4. `unwrap` 把失败转成异常，调用方要决定是否捕获；也可以让调用方直接分支，不强迫抛异常。

尝试给 `ApiError` 增加 `"forbidden"`，观察哪些 `switch` 需要补分支；再给 `SearchHit` 增加 `page: number | null`，确认所有构造点都收到编译提醒。

## 5. 练习

### 练习一：跟写

为 `Document`、`Citation`、`Answer` 写类型，字段名与 Python 后端契约一致；金额用 `amountCents`，日期用 ISO 字符串，不用 `Date` 作为网络类型。

### 练习二：改造

把 `unwrap` 改成 `Result<T, E>` 风格，不抛异常；调用方必须处理 `ok: false`。比较两种风格在 UI 层的差异。

### 练习三：独立

实现 `groupBy<T, K extends string>(items: readonly T[], key: (item: T) => K): Map<K, T[]>`。要求空输入返回空 `Map`，不修改输入；说明为什么不用 `Record<K, T[]>`：`K` 是联合时，空对象 `{}` 不满足“每个键都存在”的完整 `Record`，而 `Map` 可以自然表达“没有这个键”。

## 6. 验收与自测

**行为验收：** 泛型函数保留具体返回类型；错误码联合能驱动分支；字段单位在类型名中可见；`readonly` 不被误当运行时冻结。

**原理验收：** 能解释类型参数擦除、`keyof` 和工具类型的作用；能说出一个“不该泛型化”的例子。

### 6.1 先预测，再查看解释

`function first<T>(items: T[]): T { return items[0]; }` 在 `noUncheckedIndexedAccess` 下为什么不能通过？

<details>
<summary>完成预测后查看解释</summary>

`items[0]` 的类型是 `T | undefined`，空数组时没有元素。返回类型写 `T` 会丢掉 `undefined`。应返回 `T | undefined`，或先检查长度并抛错，让“空输入”成为显式契约。

</details>

## 7. 面试问答与参考回答

**问：`interface` 和 `type` 怎么选？**

需要联合、交叉、映射或条件类型时用 `type`；需要声明合并或类实现契约时用 `interface`。同一项目对同一形状保留一种来源，避免两份定义漂移。

**问：泛型解决了什么问题？**

它让同一操作对多种类型成立，同时保留具体类型信息，减少复制和 `any`。泛型不适合掩盖业务差异；如果不同资源的规则不同，应先写具体类型。

**问：`readonly` 能防止运行时修改吗？**

不能。它只约束通过该类型的编译期赋值；对象仍可能被其他引用修改。运行时不可变需要 `Object.freeze` 或复制，且要承担相应代价。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 分页、搜索结果和错误响应形状相似又不相同，怎样只写一份契约，又不把业务差异藏进泛型？

**一条主线：**

```text
具体字段形状 → 泛型参数（Page<T>、ApiResult<T>）→ extends 约束 + keyof/工具类型派生 → 编译期契约
```

**三个关键词：** 泛型、契约、派生。泛型把类型当参数复用形状，契约写清字段单位、版本与错误码，`keyof` 和工具类型从既有类型派生而不复制。

**最容易错：**

- 泛型不写 `extends` 约束，函数体里无法安全访问任何字段。
- 为“通用”过早抽象，把业务规则不同的两种类型硬套一个泛型。
- 用 `data`、`info`、`result` 命名，把金额单位、版本和来源藏起来。
- 以为 `Page<T>` 会生成运行时校验，或把 `readonly` 当运行时冻结。

**与前后章：** 上一章的判别联合给出状态形状；下一章要把这些契约变成可执行校验器，让失败带字段路径和可重试标记。

**学完应能：**

- 用 `Page<T>`、`ApiResult<T>` 给搜索和错误响应建模，不复制 `items/nextCursor`；
- 写 `mergePages<T>` 与 `groupBy<T, K extends string>`，返回类型保留具体元素；
- 判断一个形状该泛型化还是保留具体类型，并说出理由；
- 解释 `interface`/`type` 的选择、`keyof`、工具类型和 `readonly` 在编译期做什么、运行时不做什么。
