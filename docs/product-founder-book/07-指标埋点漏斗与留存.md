# 第7章　指标、埋点、漏斗与留存

[上一章](06-全栈开发与最小产品交付.md) · [本书目录](教材目录.md) · [下一章](08-实验设计与产品迭代.md)

## 1. 目标、前置与问题

前置：第4、6章。能定义可计算指标并检查数据质量。问题：访问量翻倍，为什么产品价值可能没有增加？

**本章主线：** 从用户结果倒推事件，统一主体、时间窗口和去重规则，再用同一队列计算漏斗、激活与留存。读数之前先验证埋点是否忠实记录真实任务。

## 2. 概念与基础

### 2.1 结果指标、过程指标与护栏

**结果指标**接近用户真正获得的价值，例如独立找到正确原文；**过程指标**记录达成结果的步骤，例如提交问题、返回来源；**护栏指标**限制不能以其他损失换来的改善，例如关键错误、总耗时或费用。

访问量属于过程指标。访问翻倍可能来自渠道曝光，也可能来自同一批人反复重试，并不自动增加任务完成。

| 指标类型 | DocPilot例子 | 回答的问题 | 不能替代什么 |
| --- | --- | --- | --- |
| 结果 | task_completed | 用户是否完成正确查证 | 付费与持续经营 |
| 过程 | question_submitted | 用户是否尝试 | 是否找到正确原文 |
| 质量 | critical_error | 错误后果是否可接受 | 完成数量 |
| 成本 | support_minutes | 服务需要多少人工 | 用户价值 |
| 护栏 | total_task_time | 是否用更长时间换正确率 | 任务是否成功 |

### 2.2 事件字典与去重

**事件**是对一次发生的业务事实的记录；**事件字典**规定名称、触发点、主体、对象、时间、属性、来源和去重方式。埋点不是把每个点击都记录下来，而是记录能回答明确问题的证据。

最小字段包括：`event_id`、`event_name`、`occurred_at`、`account_id`、`task_id`、`request_id`、`event_version`。不同事件使用不同主体时，必须在字典中写清。

**去重**是按约定标识消除重复记录，而不是任意删除看起来相似的事件。重复上报、客户端重试和服务端重放可能需要不同的去重键。

### 2.3 漏斗与统一口径

**漏斗**是同一批主体在约定顺序和窗口内，从一个阶段进入下一阶段的比例。每一步都要回答：分子是谁、分母是谁、观察多久、允许跳过哪些步骤。

用户、账户、团队和企业不是同一单位。本月访问数除以上月付款数也不是转化率，因为主体和时间都不一致。

| 口径项 | 示例 | 改变后的风险 |
| --- | --- | --- |
| 主体 | 账户 | 换成点击会放大重试用户 |
| 窗口 | 邀请后7天 | 换成自然月会混入不同队列 |
| 顺序 | 导入后才能激活 | 时间倒置会制造假转化 |
| 去重 | 每个账户只计首次激活 | 不去重会重复计数 |
| 成功 | 独立打开正确原文 | 改成来源返回会高估价值 |

### 2.4 激活、留存与队列

**激活**是用户首次达到产品核心价值的事件。它必须由任务结果定义，而不是只注册或登录。对DocPilot，激活是首次按验收样本独立找到并打开正确原文。

**留存**是某个起始队列中的用户，在后续约定窗口再次表现目标行为的比例。**队列**是按共同起始事件和时间固定的一批主体，例如“本周首次激活的8个账户”。

低频产品还要记录**任务机会**：用户在窗口内是否真的遇到需要完成的任务。没有任务机会与有任务但未使用是不同原因，应分别报告，不能悄悄改变原留存分母。

## 3. 机制与推导

### 3.1 从事件到指标的计算链

指标不是图表，而是一条可复算的规则：

```text
业务结果定义 → 事件与触发点 → 清洗和去重 → 主体与窗口 → 分子/分母
```

例如“邀请到激活40%”必须来自20个邀请账户中8个在窗口内激活，而不是8个激活者除以本月全部访问。每个数字都应能下钻到账户或事件明细。

预期结果：另一名同事拿到同一份事件表，可以按字典复算相同结果。若需要口头解释“大概哪些人”，口径还不完整。

### 3.2 漏斗流失与数据故障的区分

完成事件突然减少，可能是产品变差，也可能是埋点漏报。先拿一条已知完成任务，核对浏览器、服务端和事件表，再判断产品。

| 现象 | 数据质量检查 | 产品检查 |
| --- | --- | --- |
| 某阶段突然为0 | 事件是否改名、版本是否部署 | 功能是否真的整体失败 |
| 转化率突然升高 | 分母是否漏报、窗口是否变化 | 用户结构是否改变 |
| 同一任务多次完成 | 去重键是否只用用户ID | 是否确实重新完成不同任务 |
| 时间倒置 | 时钟、时区与重放 | 是否允许真正的跨窗口行为 |
| 分渠道差异大 | 渠道标签是否可靠 | 渠道是否带来不同人群 |

归因标签只能说明记录来源，不能证明渠道导致结果变化。

### 3.3 留存分母与机会校正

标准队列留存保持原分母不变。例如8个激活者中次周5人再次完成任务，标准留存是5/8。即使其中只有3人遇到新任务，也不能直接把分母改成3。

换一个独立情景：同样8个激活者，次周只有1人再次完成任务，标准留存是1/8；若其中3人遇到新任务，且这1个完成者属于有机会者，则有机会者留存是1/3。两个指标必须同时报告，并定义机会、窗口和判定来源；有机会者留存是辅助指标，不能替换标准值。

常见错误是为了让数字好看，事后排除不活跃账户。这样做测到的是另一个问题。

## 4. 案例逐步推演

**输入**：同一周的邀请、导入、激活与再次完成事件。**判断**：主体、顺序、窗口和去重必须一致，来源返回不能替代任务完成。**输出**：40%、66.7%、62.5%三组口径及逐事件核对表。**失败信号**：重复事件被多计、完成事件无法追溯、没有任务机会者被移出分母；出现时先修数据再解释产品。

教学数据统一为：邀请20个授权账户，12个导入资料，8个经任务样本核对完成首次查证，次周其中5个再次完成任务。所有账户和数字均虚构。

| 指标 | 公式 | 解释 |
| --- | --- | --- |
| 邀请到激活 | 8/20=40% | 邀请队列中完成首次任务 |
| 导入后激活 | 8/12≈66.7% | 已导入队列的后续完成 |
| 激活队列次周留存 | 5/8=62.5% | 首次激活者次周重复完成 |

再定义事件：question_submitted 在服务端接受合法请求后记录；sources_returned 在授权结果生成后记录；source_opened 在完整原文展示成功后记录；task_completed 在按验收样本确认用户独立找到正确原文后记录。只有摘要面板时另记 source_previewed，不能计作原文打开或任务完成。事件包含去重ID、主体、任务ID、版本与时间，避免把正文和敏感材料写进分析事件。

若完成事件突然少了，先拿一条已知完成任务检查漏报，再判断是否需要改产品。

### 4.1 用集合亲手核对留存分母

```python
# track-example: P07
invited = set(range(1, 21))
imported = set(range(1, 13))
activated = set(range(1, 9))
returned = {1, 2, 3, 4, 5}
assert activated <= imported <= invited
assert returned <= activated
assert len(activated) / len(invited) == 0.4
assert len(returned) / len(activated) == 0.625
```

这里的编号是虚构账户，不是企业。真实事件还要限定窗口与先后顺序，集合例子只解释同一队列的分子分母。去掉时间条件会把很久以前的任务混进本周。

如果次周只有3个激活者遇到新任务、其中1个继续使用，应同时报告标准队列1/8与有机会者1/3，并解释机会如何判定；不能把后者无说明替换成原留存定义。低频产品更需要任务频率的背景。

事件字典示例：task_completed主体为账户，关联task_id，按任务验收样本核对正确原文后触发，同一完成事件按event_id去重；“来源打开”另列。用户自报task_confirmed只作辅助，不能替代正确性核对。数据能否支持判断，比事件数多更重要。

### 4.2 逐事件核对一条任务链

假设账户A07在周内产生以下事件。先按event_id去重，再检查时间顺序与任务ID。

| 顺序 | 事件 | 关键字段 | 是否进入漏斗 |
| --- | --- | --- | --- |
| 1 | question_submitted | A07、T21、09:00 | 是，首次提交 |
| 2 | sources_returned | A07、T21、09:02 | 是，授权来源返回 |
| 3 | source_opened | A07、T21、09:03 | 是，完整原文打开 |
| 4 | task_completed | A07、T21、09:04 | 是，按样本核对成功 |
| 5 | task_completed重放 | 同一event_id、09:04 | 否，重复上报 |
| 6 | source_previewed | A07、T22、09:05 | 否，不是原文打开 |

输入判断：同一task_id的核心步骤应满足先后关系；重复event_id只保留一条。输出：A07在T21上完成一次激活，T22只算预览。

失败信号：source_opened缺少原文版本、task_completed缺少正确性核对、事件时间早于邀请时间。出现这些情况先修数据，不急着解释转化下降。

## 5. 分层练习

1. **基础**：为切片写四条事件字典，包含触发、主体、去重、时间、窗口和指标用途。
2. **改造**：用五条手工任务核对浏览器、服务端和事件表，故意制造一次重复与一次漏报，说明怎样识别。
3. **独立**：计算一组同队列漏斗和次周留存；再补充任务机会指标，保留原分母并解释两种结果为何不同。

每个比例都保存分子与分母明细，不只交一张图。

## 6. 自测与参考推导

<details><summary>完成独立任务后查看诊断</summary>

- 若把来源返回当任务完成，会高估价值。
- 若同一个用户重试三次被算三次激活，去重规则有问题。
- 若没有新任务的人被悄悄从留存分母删除，指标已与原定义不同。
- 若完成事件减少却只看产品，可能尚未排除漏报与版本变化。

</details>

**自问：** 为什么留存下降不一定意味着产品变差？

**参考推导：** 队列可能没有遇到新任务，渠道可能带来不同用户，事件也可能漏报。标准留存、任务机会、用户结构和数据质量要分开检查，才能判断原因并选择动作。

## 7. 项目交付与验收

保存 `product/measurement.md` 的指标字典和一次核对表。原文页未实现时，可先报告提交、返回与摘要预览等过程指标；任务完成与激活仍未验证，不能用来源返回补位。下一章使用这份口径设计实验，避免看完结果才改目标。

| 操作 | 预期结果 | 应保留的证据 |
| --- | --- | --- |
| 走一条已知成功任务 | 浏览器、服务端、事件表可对齐 | task_id、时间、event_id |
| 重放同一事件 | 只计一次 | 原始与去重后明细 |
| 计算邀请漏斗 | 主体、顺序、窗口一致 | 20、12、8的账户集合 |
| 计算次周留存 | 5/8且分母不随机会改变 | 队列名单与再次完成记录 |
| 补充机会分析 | 1/8与1/3同时可解释 | 机会定义、3人名单、结果 |
| 检查敏感字段 | 分析事件不含不必要正文 | 字段清单与保留范围 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 访问量翻倍，为什么产品价值可能没有增加？

**一条主线：**

```text
用户结果 → 事件字典与去重 → 同一队列的漏斗、激活与留存
```

**三个关键词：** 任务完成、口径一致、数据质量。点击只是尝试，分母和窗口没写清就谈不上转化率。

**最容易错：**

- 把sources_returned当任务完成。
- 同一账户重试三次被算三次激活。
- 拿本月访问数除以上月付款数。
- 为了让留存好看，事后删除没有任务机会的人。

**与前后章：** 第6章的真实切片提供事件触发点；本章的口径，第8章用来预设主指标与护栏。

**学完应能：**

- 写四条事件字典并核对一条完整任务链。
- 用集合复算漏斗与留存。
- 同时报告标准队列与机会校正，并解释为何不能替换分母。

[GOV.UK衡量服务](https://www.gov.uk/service-manual/measuring-success)提供结果衡量入口；配套离线算例见附录A。
