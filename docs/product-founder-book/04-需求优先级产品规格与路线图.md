# 第4章　需求优先级、产品规格与路线图

[上一章](03-市场定位价值主张与商业假设.md) · [本书目录](教材目录.md) · [下一章](05-交互设计可用性与无障碍.md)

## 1. 目标、前置与问题

前置：第2–3章。能从证据选择最小验证范围，写出开发与验收共用的规格。问题：只有两周，你保留什么？

**本章主线：** 把定位改写成用户结果，用优先级方法显式取舍，再把范围、异常、数据与验收写成同一份规格。路线图只承诺近期有证据的工作，不把所有反馈变成永久日期。

## 2. 概念与基础

### 2.1 用户结果、需求与功能

**用户结果**是用户完成任务后可观察的变化；**需求**是为达到结果必须满足的条件；**功能**只是实现需求的一种手段。

“做一个知识库”是功能方向。“新人能独立找到发布当日有效的回退规定”才是本轮结果。一个结果可能由搜索、来源卡片和权限检查共同满足，也可能用更简单的目录治理达到。

| 层次 | DocPilot例子 | 验证方式 |
| --- | --- | --- |
| 用户结果 | 独立打开正确版本原文 | 陌生任务观察 |
| 需求 | 按业务日期过滤并保留可核对来源 | 正常与边界样本 |
| 功能 | 日期选择、搜索、来源卡片 | 页面与接口测试 |
| 技术任务 | 日期过滤、引用定位、授权 | 自动化测试与日志 |

为什么先写结果？因为功能失败不一定代表结果失败，功能成功也不一定代表用户完成。规格需要同时保留这两层。

### 2.2 优先级、RICE与硬门槛

**优先级**是在当前目标下对工作顺序的显式选择。RICE是一种评分方法：`Reach × Impact × Confidence ÷ Effort`，分别表示覆盖人数、影响程度、信心和投入。

评分前必须统一时间窗口、影响等级和投入单位。主观输入会制造假精确，所以分数用于比较，不用于证明真实收益。

**硬门槛**是即使评分高也不能绕过的条件，例如无授权资料、无法满足合同、关键安全缺陷或不可接受的错误后果。先过门槛，再排序。

| 因素 | 要问的问题 | 常见问题 |
| --- | --- | --- |
| 覆盖 | 本轮有多少目标用户遇到？ | 用全平台用户代替目标人群 |
| 影响 | 对关键任务改善多少？ | 把开发难度当用户影响 |
| 信心 | 有多少直接证据？ | 把热情当高信心 |
| 投入 | 需要哪些角色和持续成本？ | 只算编码，不算审核与维护 |
| 依赖 | 不先做什么就无法验收？ | 忽略资料负责人和权限条件 |

### 2.3 产品规格与验收条件

**产品规格**是产品、设计、开发和验收共同使用的约定，至少包含：服务对象、问题证据、本轮目标、范围、主流程、异常、数据约束、测量和明确不做。

**MVP**（最小可行产品）是用最小范围验证关键假设的可运行产品，不是砍掉安全与验收的半成品；**原型**用于快速表达交互和获取反馈，不承诺真实数据、性能或持续运行；**PRD**（产品需求文档）把目标、范围、规则与验收写成团队共同使用的规格，不等于包含所有未来功能的产品路线图。

| 产物 | 主要回答 | 最小完成标准 | 常见误用 |
| --- | --- | --- | --- |
| 原型 | 用户能否理解并操作这条路径 | 关键交互可走通，未实现处明确标注 | 把演示效果当生产证据 |
| MVP | 关键假设是否成立 | 真实任务可运行，范围与验收明确 | 为赶时间删掉权限和异常处理 |
| PRD | 本轮到底交付什么、怎样算完成 | 范围、规则、异常和验收一致 | 写成没有取舍的功能清单 |
| 路线图 | 先做什么、证据满足后再做什么 | Now/Next/Later有依赖与停止条件 | 把未验证愿望承诺成日期 |

验收条件推荐写成“**给定**某种资料与身份，**当**执行某动作，**则**得到可观察结果”。例如：“给定6月30日付款问题与两版制度，当查询时，则展示6月30日适用版本的日期、来源和可打开原文入口。”

这比“搜索准确、体验好”更可实现，也更难在联调时临时改口径。

### 2.4 来源验收与引用契约

当产品返回带依据的回答时，需要一份**引用契约**：回答与来源之间必须满足的结构约定。它不是“放一个链接”，而是对证据关系的共同约定。

最小字段可包括：回答ID、来源文档ID、文档版本、适用区间、定位信息、**quote**（从原文逐字截取的依据片段）和是否支持该结论的人工或规则判定。quote用于定位与核对，不自动证明结论正确。

| 契约要求 | 不满足的后果 | 首轮处理 |
| --- | --- | --- |
| 来源与版本存在 | 用户无法知道依据属于哪份资料 | 不展示该回答 |
| quote能在指定版本原文找到 | 引用可能伪造或来自旧版 | 标记引用失败 |
| 适用日期与业务日期匹配 | 找到原文但版本不适用 | 拒答或提示缺资料 |
| 结论与quote语义一致 | 数值、条件和对象可能被改写 | 人工复核或规则校验 |
| 当前身份仍有权限 | 已撤权内容继续泄露 | 返回无权限，不泄露标题 |

为什么需要契约？因为界面、接口、检索和验收必须对“什么算有依据”使用同一套字段；否则每层都自称成功，组合结果却无法核对。

### 2.5 Now、Next、Later路线图

**路线图**是按问题与证据安排工作的视图。Now写本轮要验证什么，Next写证据满足后可能做什么，Later只保留方向与未知，不承诺具体日期。

| 时间层 | 应包含 | 不应包含 |
| --- | --- | --- |
| Now | 目标、范围、负责人、验收、停止条件 | 无法估计的完整平台 |
| Next | 前置证据、候选主题、依赖 | 已提前承诺的所有客户愿望 |
| Later | 机会方向和需要研究的问题 | 精确到周的虚构交付日 |

## 3. 机制与推导

### 3.1 先定最短路径，再分配预算

首轮若验证能否找到有效来源，聊天记忆和多角色并不是前置。先画“进入→输入日期与问题→得到授权来源→打开原文→确认结果”的最短路径，再选择闭合这条路径的工作。

每项任务估算用相对点数即可，但必须包含设计、开发、测试、资料准备和观察。点数不是人日，也不自动等于日历时间。

教学预算8点的分配可以是：搜索2、来源定位2、状态反馈2、任务反馈1、教学身份适配1。历史聊天3点暂缓。若客户任务必须导出，应重新比较范围，而不是再叠3点却维持原交期。

### 3.2 正常、异常与恢复共同构成规格

正常路径说明系统能做什么，异常路径说明系统不能做什么时用户怎么办。至少覆盖：无匹配、无权限、依赖超时、会话失效和结果不可核对。

| 状态 | 用户需要知道 | 可用动作 | 验收信号 |
| --- | --- | --- | --- |
| 无匹配 | 当前范围没找到 | 改日期、问题或补资料 | 不编造确定答案 |
| 无权限 | 当前身份不能访问 | 重新认证或申请权限 | 不泄露标题与片段 |
| 超时 | 哪一步不可用 | 重试、查看来源或稍后再来 | 不把超时当无证据 |
| 引用失败 | 依据无法核对 | 查看原文、反馈问题 | 不把失败显示为绿色通过 |

### 3.3 变更控制与范围债务

**变更控制**是让新需求进入目标、预算和验收的同一决策，而不是口头“顺便加上”。每项变更至少说明：支持哪条任务、需要什么证据、挤掉什么、是否改变风险。

没有进入本轮的需求放入候选池，不立即消失，也不默认承诺。若一项需求连续出现且影响关键任务，再调整路线图。

边界：安全与权限不是可选范围。若时间不足，应缩小任务或资料范围，而不是交付一个没有边界的产品。

## 4. 案例逐步推演

**输入**：定位、证据、两周范围和8点教学预算。**判断**：授权与日期过滤是硬门槛，其余能力按本轮任务和点数取舍。**输出**：一页规格、四类异常验收和明确不做项。**失败信号**：必须导出却没有预算、引用无法核对、用户只能读摘要；出现时重排范围，不把原文打开或任务完成记为通过。

一份首版规格可以直接写成：用户是已有授权资料的专员；问题是难以确认业务日期适用原文；目标是独立完成给定查证任务；主流程为选择日期→输入问题→查看来源→打开原文→确认是否解决。

| 情况 | 应有行为 | 验收输入 |
| --- | --- | --- |
| 有有效来源 | 展示正文、版本和适用日期 | 一份旧版与一份新版 |
| 无证据 | 说明未找到并给下一步 | 无匹配问题 |
| 无权限 | 不展示他人标题或片段 | 替换来源ID |
| 生成超时 | 保留可访问来源并标识 | 模型超时替身 |
| 引用不一致 | 标识不可核对并允许查看原文 | quote与版本不匹配样本 |

教学预算8点：搜索2、来源定位2、状态反馈2、任务反馈1、教学身份适配1，恰好8点。历史聊天3点本轮暂缓。如果客户任务必须导出，应重新比较范围，而不是再叠3点却维持原交期。

这份规格的自动验收可以保护过滤和引用；用户是否理解日期、能否独立完成，要在第5章观察。

### 4.1 把验收写成一次完整任务

正常样本：给定专员A和有权访问的两版制度，当输入6月30日付款问题时，系统返回旧版来源与日期；改成7月1日时返回新版。验收者必须能打开对应原文，不只看到20%或30%的答案。

异常样本：给定无匹配问题，展示未找到及可调整的问题/日期；给定未知身份，提示重新建立会话；给定越权来源，不能泄露标题；给定模型超时，保留授权来源并标识摘要不可用。

这些验收同时指导界面状态、接口字段、服务端检查和埋点。实现任务可以拆成核心过滤、接口和来源展示，但每个增量尽量让一条用户路径可验证。这里定义的是产品目标；若第6章先交付来源摘要面板，只能确认定位链路，不能把“打开原文”或任务完成记为通过。

规格中的不做范围也要有理由：“不做长期聊天记忆，因为本轮验证一次查证；不做自动提交，因为尚无动作需求；不做任意文件格式，因为解析能力未验证。”下一轮出现新证据时再重新排序。

### 4.2 让8点预算真正形成取舍

下面的算例只比较本轮任务，不代表通用优先级。授权和日期过滤是硬门槛，所以先保留；其余候选按“预计覆盖÷点数”排序。

```python
# track-example: P04
candidates = {
    "搜索": {"points": 2, "value": 8, "required": True},
    "来源定位": {"points": 2, "value": 8, "required": True},
    "状态反馈": {"points": 2, "value": 6, "required": False},
    "任务反馈": {"points": 1, "value": 2, "required": False},
    "身份适配": {"points": 1, "value": 3, "required": True},
    "历史聊天": {"points": 3, "value": 3, "required": False},
}
budget = 8
required_points = sum(x["points"] for x in candidates.values() if x["required"])
assert required_points == 5

optional = sorted(
    (name for name, x in candidates.items() if not x["required"]),
    key=lambda name: candidates[name]["value"] / candidates[name]["points"],
    reverse=True,
)
selected = [name for name, x in candidates.items() if x["required"]]
for name in optional:
    used = sum(candidates[item]["points"] for item in selected)
    if candidates[name]["value"] > 0 and used + candidates[name]["points"] <= budget:
        selected.append(name)

assert set(selected) == {"搜索", "来源定位", "状态反馈", "任务反馈", "身份适配"}
assert sum(candidates[name]["points"] for name in selected) == budget
assert "历史聊天" not in selected
```

预期结果：先保留5个硬门槛点，再按比率加入状态反馈2点和任务反馈1点，总计8点；历史聊天不进本轮。推导：如果任务反馈价值变成0，入选条件会直接排除它，预算可能留空，而不是为了凑满点数加入无价值功能。

边界：value是教学假设，不能替代真实影响与信心；若导出成为硬门槛，应把它加入required并重新比较，而不是在8点之外偷偷追加。

## 5. 分层练习

1. **基础**：把一个功能词改写成用户结果，并列出结果依赖的两项资料条件和一项人的动作。
2. **改造**：用RICE比较三个候选，至少引入一个硬门槛；解释为什么高分项仍可能被排除。
3. **独立**：写一页首版规格，限制最多三个主要能力，包含无证据、无权限、超时和引用失败；再处理一条“加历史记录”的变更。

规格必须让开发与验收使用同一字段和同一完成定义，不能一边说“找到原文”，一边只测“返回文本”。

## 6. 自测与参考推导

<details><summary>完成独立任务后查看诊断</summary>

- 若每项都是最高优先级，说明尚未按目标取舍。
- 若验收只写正常页面，无证据、无权限与超时会留到联调时现场发明。
- 若引用只检查链接存在，quote、版本、日期和结论一致性仍可能出错。
- 若8点已满还叠3点，预算已失去约束作用。

</details>

**自问：** 为什么“来源返回成功”不能直接作为产品验收通过？

**参考推导：** 来源返回只证明服务找到了某些结果，还没有证明日期正确、原文可访问、引用支持结论或用户能独立完成。接口成功、引用契约和任务结果是三个不同层次的验收。

## 7. 项目交付与验收

保存 `product/spec.md`，后续原型、代码和埋点都引用这份任务与验收。下一章先在低成本原型中验证用户是否能走通。

| 操作 | 预期结果 | 应保留的证据 |
| --- | --- | --- |
| 定义结果与最短路径 | 功能都能追溯到任务 | 结果句、路径图、条件依赖 |
| 过门槛并排序 | 安全与关键依赖不被平均掉 | 门槛清单、评分假设、预算 |
| 写正常与异常验收 | 每个状态有输入和可观察输出 | 样本、预期、失败动作 |
| 写引用契约 | 回答与来源可按版本核对 | 字段、quote、日期与权限规则 |
| 记录不做与变更 | 新需求不会绕过预算 | 候选池、理由、重排决定 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 只有两周，你保留什么？

**一条主线：**

```text
任务与证据 → 硬门槛和优先级 → 范围、异常、引用契约与可观察验收
```

**三个关键词：** 取舍、最短路径、验收。优先级取决于本轮要减少哪个未知，而不是谁的声音更大。

**最容易错：**

- 每项都是最高优先级。
- 只测正常页面，不定义失败与恢复。
- 把quote存在当结论正确。
- 8点排满后，用口头变更继续加范围。

**与前后章：** 第3章的定位与排除项在这里变成范围；本章的状态与验收，第5章先用低成本原型验证能否走通。

**学完应能：**

- 写一页规格，包含目标、范围、异常、引用契约与验收。
- 解释RICE分数和硬门槛怎样共同决定取舍。
- 收到新增需求时，说明它支持哪条任务、挤掉什么、凭什么进本轮。

配合第5–6章将规格落为界面与开发任务；[原项目规格](../project-practice/项目实践规格.md)提供接口与状态约束，新增产品范围不得默默改变安全契约。
