# 第1章　产品型工程师与机会判断

[导读](00-导读与学习方法.md) · [本书目录](教材目录.md) · [下一章](02-用户研究访谈与证据整理.md)

## 1. 目标、前置与问题

前置：有基本软件开发经验。能从用户任务发现机会，区分工程交付与产品结果。问题：做完一套功能，为什么仍没有人愿意使用？

## 2. 概念与基础

产品型工程师参与问题定义、方案、开发、上线和效果改进。创业者还承担获客、现金和组织风险；两种角色有共同能力，但承担责任不同。可以先在现有工作中练习产品能力，不必立刻成立公司。

用户问题需说明谁在什么情境下完成什么任务、遇到什么障碍、现在怎么解决、后果如何。使用者、购买者、管理者和数据所有者可能是不同的人。访谈中的请求是线索，不自动成为产品规格。

## 3. 机制与推导

产品型工程师首先对一个用户结果负责。技术选择只有放到任务里才有意义：专员要确认某天适用的制度，困难可能是搜索不好，也可能是无人确认版本。若根因是后者，增加聊天窗口未必减少等待。

从结果倒推四类假设：问题是否反复发生、方案是否改善、技术与资料是否可交付、采用与购买是否可行。最危险的不一定是模型质量，也可能是客户无权提供资料，或现有目录加日期就足够。

全栈能力服务于贯通这条链。保持一个技术深度，同时能完成界面、接口、数据与部署，使你可以独立做小切片、观察真实行为、修正问题。团队可以分工；你仍应理解数据怎样流动、失败由谁处理、用户结果如何验收。

```mermaid
flowchart LR
    A[具体任务与阻碍] --> B[关键假设]
    B --> C[最小验证]
    C --> D[实际行为与反例]
    D --> E[继续缩小或停止]
    E --> A
```

产品思维的日常训练不是背模型：每天选一个任务重建行为，每周写一条可以被推翻的假设，每轮用新证据改一次决定。仅把想法换成专业术语，没有改变判断。

## 4. 案例逐步推演

本书贯穿案例采用虚构材料：一位采购专员核对制度花30分钟，其中20分钟等待负责人确认版本。目前替代方式是共享目录、聊天询问与截图。

先填问题卡：用户是负责准备材料的专员；任务是找到业务日期适用原文；阻碍是版本不清与确认等待；后果是返工；证据目前只有一次虚构任务记录。初始想法是生成报告，但现有证据只足以支持调查“怎样更快确认来源”。

于是第一轮不开发完整审查系统，只做可展示生效日期、版本和来源的搜索原型。成功不是用户说喜欢，而是能否在陌生题上独立找到正确原文。这个缩小决定同时降低全栈开发量和验证成本。

### 4.1 将四种假设写成能够被否定的问题

| 假设 | 当前仅有的信息 | 下一步怎样减少未知 |
| --- | --- | --- |
| 问题重要 | 一次30分钟查证记录 | 观察其他最近任务与顺利案例 |
| 方案改善 | 想展示日期和来源 | 用陌生任务测试原型 |
| 可以交付 | 能做搜索，但资料维护未知 | 找维护者核对授权与更新 |
| 可以采用 | 专员感兴趣 | 了解购买者与现有流程要求 |

此时最便宜的验证不是训练模型，而是了解版本确认为什么需要负责人。若原因是职责要求，产品应帮助确认与留痕；若是文件命名混乱，目录治理也可能解决。两种解释对应不同范围。

产品型工程师在这里运用技术判断减少无效开发：知道搜索原型可快速完成，也知道模型无法替客户决定哪个版本有效。创业进一步问谁愿意为持续维护和支持付费；两类问题在同一任务上发生，但需要不同证据。

## 5. 分层练习

先完成：选一个自己熟悉的工作任务，分开写用户目标、现有行为、阻碍、后果与证据，再列三个不同解释。用一次过去事件访谈或流程观察检验其中一个解释，先不提出功能。
