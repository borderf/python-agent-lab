# 第1章　产品型工程师与机会判断

[导读](00-导读与学习方法.md) · [本书目录](教材目录.md) · [下一章](02-用户研究访谈与证据整理.md)

## 1. 目标、前置与问题

前置：有基本软件开发经验。能从用户任务发现机会，区分工程交付与产品结果。问题：做完一套功能，为什么仍没有人愿意使用？

**本章主线：** 先定义一个具体的用户结果，再把支持这个结果的想法拆成四类可被推翻的假设，最后选择最便宜、最有判别力的下一步。全书使用虚构的 DocPilot 场景练习，所有数字都是教学假设，不是市场调查结果。

学完应留下 `product/problem.md`：一页问题卡、三种问题解释、四类假设和一轮验证计划。

## 2. 概念与基础

### 2.1 产品型工程师负责什么

**产品型工程师**是能把问题定义、方案设计、开发交付和效果观察连起来的人。他不一定独自完成所有工作，但必须能说明一项功能为什么存在、数据怎样流动、失败由谁处理、用户结果怎样验收。

| 角色 | 主要责任 | 完成的表现 | 容易混淆的表现 |
| --- | --- | --- | --- |
| 工程师 | 按约定实现并保证质量 | 规则、异常和运行路径可验证 | 接口返回成功就认为任务完成 |
| 产品型工程师 | 选择值得解决的问题并验证结果 | 用户行为因方案发生预期变化 | 把更多功能当作更多价值 |
| 创业者 | 在不确定中组织资源并承担经营风险 | 有人持续采用、有人付费、交付可持续 | 有作品就认为商业成立 |

为什么需要这种连接？因为工程问题通常是“怎样把它做出来”，产品问题还包括“为什么做它、为谁做、做了是否有用”。只完成前半句，会出现功能齐全但无人使用的产品。

最小例子：采购专员要核对某日适用的制度。工程师可以做出聊天框，产品型工程师还要发现真正的20分钟可能花在等待版本确认，而不是生成文字。前者交付组件，后者寻找能改变任务结果的机会。

### 2.2 用六要素写用户问题

**用户问题**不是一句“大家需要知识库”，而是对一次具体困境的记录。至少写清：谁、在什么情境、要完成什么任务、遇到什么阻碍、现在怎样应对、造成什么后果。

以虚构任务为例：“采购专员准备月度材料，需要确认6月30日付款条款；目录里有两版文件，现任负责人正在休假；他在群里等确认，最后拿截图交付，下午因版本可能错误而返工。”这句话包含人物、日期、任务、阻碍、替代和后果，可以指导研究。

| 要素 | 应记录的内容 | 不应写的内容 |
| --- | --- | --- |
| 谁 | 角色、经验、责任边界 | “所有用户” |
| 情境 | 触发任务的时间、设备和流程位置 | 与任务无关的背景 |
| 任务 | 用户试图完成的动作和完成标准 | 产品功能名称 |
| 阻碍 | 具体无法继续或做错的步骤 | “体验不好” |
| 现有办法 | 手工、表格、询问、外包或放弃 | 只有竞品名单 |
| 后果 | 返工、延迟、风险或额外成本 | 未经测量的夸张损失 |

边界：一次任务记录不能证明问题普遍存在。它适合形成假设，不适合直接写“80%的采购人员都遇到此问题”。

### 2.3 四类关键假设

**关键假设**是“如果它为假，当前方案或投入就不成立”的判断。机会判断至少同时检查四类，而不是只检查技术能否实现。

1. **问题假设**：这类用户是否反复遇到这个问题，后果是否值得处理？
2. **方案假设**：所提改变能否实际减少阻碍，而不是只让页面看起来更聪明？
3. **交付假设**：资料、权限、维护和运行条件是否允许稳定交付？
4. **采用与购买假设**：谁会改变行为，谁会批准预算，是否有可接受的替代方案？

例如，“给制度加日期标签”只触及方案假设。即使标签显示正确，负责人仍可能要求人工确认，购买者也仍可能拒绝采购。四类假设要分别收集证据。

### 2.4 机会、想法与证据强度

**机会**是值得投入有限资源去检验的问题与条件组合；**想法**只是其中一种可能解法。两者不能互换。证据也分强弱：口头兴趣、过去行为、可重复观察和真实承诺提供的信息量不同。

| 材料 | 最多能支持什么 | 下一步 |
| --- | --- | --- |
| “这个想法不错” | 对方理解或愿意礼貌回应 | 不问态度，重建最近一次任务 |
| 一次真实任务记录 | 该障碍确实发生过 | 找其他角色和顺利完成案例 |
| 多角色一致的可观察行为 | 某个机制可能重复出现 | 用原型或小试点检验改变 |
| 真实付费与持续使用 | 特定条件下存在采用和购买 | 核对交付成本与可复制性 |

常见错误是把证据强度跳级：从一句称赞直接跳到市场规模，再跳到辞职创业。每一级都需要新的材料。

## 3. 机制与推导

### 3.1 从用户结果倒推技术选择

倒推时先写结果，再列达到结果的必要条件，最后才选技术。结果“专员能独立确认某日适用原文”至少包含：资料可访问、日期语义正确、来源可定位、权限有效、用户能理解状态。

如果根因是无人维护版本，搜索模型再强也只能在错误资料中找答案；如果根因只是新人不会用目录，一次信息架构调整可能比新建系统更有效。

推导步骤：

1. 写一句可观察的结果，不写“提升效率”。
2. 列出结果依赖的事实、权限和人的动作。
3. 为每个依赖标注当前证据与未知。
4. 只在未知会阻断结果时安排开发。

### 3.2 最小验证与可推翻条件

**最小验证**是用当前阶段最小的成本，获得能改变下一步决定的证据。它不是“尽量少做功能”，而是“用足够小的实验回答最关键的问题”。

一份有效计划同时写输入、判断、输出和失败信号：

- 输入：谁能参加、使用什么资料、完成哪类任务。
- 判断：什么结果算问题得到改善，什么结果算方案被推翻。
- 输出：继续、缩小、改方向或停止。
- 失败信号：找不到合适参与者、资料不能授权、任务无法判定。

例如，首轮不训练模型，只展示版本、日期和来源。若新人仍无法确认版本，说明仅改善检索不够；若现有目录加日期已经足够，新建产品的价值假设就被削弱。

### 3.3 用反例避免确认偏误

**确认偏误**是只寻找支持自己想法的材料。每周主动写一条“什么观察会让我改变主意”，能减少事后把所有结果都解释成成功的倾向。

对 DocPilot 可以预先写：

- 若熟练专员用现有目录已能快速完成，则新人易用性可能不是首要机会。
- 若负责人要求每次确认是制度规定，则产品应支持复核与留痕，而不是绕过确认。
- 若客户无法提供授权资料，则技术原型再完整也不能进入该客户。

这些反例不会自动宣判产品死亡，但会改变服务对象、范围或交付方式。

## 4. 案例逐步推演

虚构材料：一位采购专员核对制度花30分钟，其中20分钟等待负责人确认版本。目前使用共享目录、聊天询问与截图。先把它当作一条待检验记录，而不是普遍结论。

1. **输入**：一次30分钟任务记录、两种版本的文件名、专员自述。
2. **判断**：任务目标是确认适用原文；等待是最大阻碍，但等待原因尚不清楚。
3. **输出**：问题卡与四类假设；首轮验证“怎样更快确认来源”。
4. **失败信号**：找不到其他真实任务、负责人无法解释流程、资料不能授权。出现任一项都先补研究，不扩大开发。

第一轮只做可展示生效日期、版本和来源的搜索原型。成功不是用户说喜欢，而是能否在陌生题上独立找到正确原文。这个缩小决定同时降低开发量和验证成本。

### 4.1 将四种假设写成能够被否定的问题

| 假设 | 当前仅有的信息 | 下一步怎样减少未知 |
| --- | --- | --- |
| 问题重要 | 一次30分钟查证记录 | 观察其他最近任务与顺利案例 |
| 方案改善 | 想展示日期和来源 | 用陌生任务测试原型 |
| 可以交付 | 能做搜索，但资料维护未知 | 找维护者核对授权与更新 |
| 可以采用 | 专员感兴趣 | 了解购买者与现有流程要求 |

此时最便宜的验证不是训练模型，而是了解版本确认为什么需要负责人。若原因是职责要求，产品应帮助确认与留痕；若是文件命名混乱，目录治理也可能解决。两种解释对应不同范围。

产品型工程师在这里运用技术判断减少无效开发：知道搜索原型可快速完成，也知道模型无法替客户决定哪个版本有效。创业进一步问谁愿意为持续维护和支持付费；两类问题在同一任务上发生，但需要不同证据。

### 4.2 把等待时间变成可核对的假设

以下数字**均为教学假设**：每周4次同类任务，每次30分钟，其中20分钟用于等待。等待时间不是都能被产品消除，先按三个情景计算。

```python
# track-example: P01
from fractions import Fraction

tasks_per_week = 4
minutes_per_task = 30
waiting_minutes = 20
weekly_wait_hours = Fraction(tasks_per_week * waiting_minutes, 60)
assert weekly_wait_hours == Fraction(4, 3)

reducible_share = {"low": Fraction(1, 4), "mid": Fraction(1, 2), "high": Fraction(3, 4)}
saved_hours = {
    name: weekly_wait_hours * share
    for name, share in reducible_share.items()
}
assert saved_hours == {
    "low": Fraction(1, 3),
    "mid": Fraction(2, 3),
    "high": Fraction(1),
}
```

预期结果：每周等待80分钟；若只减少四分之一、一半、四分之三，分别约省20、40、60分钟。推导不是“产品一定节省60分钟”，而是“可消除比例是必须验证的关键乘数”。如果制度要求每次人工确认，低情景更合理；如果等待主要来自找不到版本，中、高情景才可能成立。

边界：这里没有计算学习、接入和维护时间，也没有证明任务频率。要把等待时间转成收益，必须观察真实基线、可消除比例和额外成本。

## 5. 分层练习

1. **基础**：选一个熟悉任务，用六要素写问题卡，至少保留一个具体日期、一次实际动作和一种后果。
2. **改造**：为同一任务写三种不同解释，并给每种解释配一条反例和一条需要的证据。
3. **独立**：把四类假设写成一页验证计划，明确输入、判断、输出、失败信号；只用现有条件安排最便宜的一轮。

不要先画页面。练习产出应能让另一人判断：哪项观察出现后，你会继续、缩小或停止。

## 6. 自测与参考推导

<details><summary>完成独立任务后查看诊断</summary>

- 问题卡若只有“用户需要AI助手”，仍是在描述方案。
- 假设若不能被任何观察推翻，就没有约束下一步。
- 计划若只有开发排期，可能漏掉授权、维护和购买条件。
- 数字若没有单位、窗口和假设来源，不能用来比较机会。

</details>

**自问：** 为什么技术最难的部分不一定是机会最大的部分？

**参考推导：** 技术难度描述实现成本，机会大小取决于问题频率、后果、替代方案和交付条件。一个容易解决的版本确认问题，可能比复杂的多智能体更有价值；反之，技术可行也不代表客户有权提供资料或愿意购买。

## 7. 项目交付与验收

保存 `product/problem.md`。下一章只围绕其中最不确定的一项收集证据，不另起一个产品。

| 操作 | 预期结果 | 应保留的证据 |
| --- | --- | --- |
| 写六要素问题卡 | 能定位到一次具体任务 | 人物、情境、任务、阻碍、替代、后果 |
| 列三种解释 | 解释不同，需要的证据也不同 | 每种解释的反例与访谈对象 |
| 拆四类假设 | 技术可行不等于商业可行 | 问题、方案、交付、采用的分别状态 |
| 安排首轮验证 | 成本有限且结果能改变决定 | 输入、判断、输出、失败信号 |
| 核算等待时间 | 数字可复算且注明假设 | 频率、时长、可消除比例与单位 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 功能都做完了，为什么还是没有人愿意使用？

**一条主线：**

```text
具体任务与阻碍 → 四类关键假设 → 最小验证 → 继续、缩小或停止
```

**三个关键词：** 用户结果、关键假设、最小验证。技术选择只有挂在这条链上，才谈得上意义。

**最容易错：**

- 把“用户需要AI助手”当问题描述。
- 把一次任务记录当总体比例。
- 只验证技术，不验证资料授权、维护责任和购买者。
- 用节省时间乘数代替真实观察。

**与前后章：** 导读给出从任务出发的方法；本章留下问题卡与四类假设，第2章只挑其中最不确定的一项收集证据。

**学完应能：**

- 用六要素写一页问题卡。
- 为同一任务给出三种解释及对应反例。
- 把等待时间拆成可验证乘数，而不是承诺固定收益。
