# 上线发布与推广实验：从可运行到有人持续使用

[本书目录](教材目录.md) · [全栈实作](附录E-全栈产品交付实操.md) · [经营模板](附录A-工作簿与模板.md)

## 一、三个目标分别验收

技术上线确保可访问、可完成任务、可观测和恢复；产品发布让适配用户理解价值并开始使用；获客与经营验证持续采用、付款和可交付成本。首批用户接触可以在开发前开始，但对外承诺须对应已实现范围。

本手册是流程与实作要求，未替你创建云资源、域名、付款渠道或发布内容。具体托管平台和命令按选定技术栈核验；本地标准库样例不直接用于公网部署。

## 二、技术上线：先在测试环境走通

选择已实现的Web应用和适合生产的应用服务器。基本拓扑为浏览器→HTTPS入口→应用→数据库/对象存储及必要外部服务；静态资源可同源或独立托管，分别说明认证、缓存和跨域配置。

1. 构建固定版本，记录依赖、配置项、环境变量与启动方式；密钥不进前端、仓库或镜像。
2. 先在测试环境准备数据迁移、依赖、readiness和关键用户路径。
3. 配置域名解析及TLS，核对证书、转发、超时和上传大小；数据库不因应用上线而默认公开。
4. 检查服务端授权、输入、日志、依赖、配额和备份，使用虚构或已授权测试资料。
5. 以新浏览器会话验收桌面/窄屏、成功/失败、会话过期和重复请求。
6. 写监控、支持负责人、停止条件与回退；先小范围开放再扩大。

```text
版本与时间：
环境、依赖和配置位置：
迁移及兼容性：
健康、关键任务、错误、延迟与成本：
备份、恢复与已知限制：
发布步骤 / 成功证据 / 停止 / 回退或前向修复：
负责人及支持方式：
```

架构第9、11章负责恢复机制与兼容发布；产品第12章负责用户交付和支持。共享发布记录，不重复维护相互矛盾的清单。

## 三、设计落地页：让用户判断是否适合

按用户决策顺序组织：给谁、解决什么任务、结果例子、怎样开始、可信依据、适用限制、价格/试点及下一步。早期可以只有一个主要行动，如申请试点或开始授权演示。

```text
标题：为[明确人群]完成[具体任务]
说明：当前问题与解决方式，避免空泛效率口号
演示：经授权/虚构资料下的前后流程，注明性质
适用：支持范围、依赖与主要限制
行动：开始试用 / 申请试点（按实际选择）
常见问题：数据、部署、成本、人工复核和支持
```

不要虚构客户标志、评价或收益数字。页面文案可A/B比较，但先验证理解和人群。搜索相关优化包括清晰标题、可理解内容、可抓取结构与基础监测；[Google SEO指南](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)不保证收录或流量，具体地区与搜索渠道需另行选择。

## 四、发布包与渠道选择

发布包包含简短定位、任务演示、开始说明、截图/视频、适用限制、价格或试点、反馈入口。演示先给任务与结果，再讲技术，避免把架构图当用户介绍。

| 场景 | 可先测试的方式 | 观察重点 |
| --- | --- | --- |
| 企业采购工具 | 目标客户演示、转介绍、授权试点 | 购买者、接入、任务收益、销售周期 |
| 开发者工具 | 技术内容、示例、社区反馈 | 实际安装/使用、问题和重复采用 |
| 个人效率工具 | 任务内容、社区、搜索等小实验 | 适配访问、激活与持续价值 |

渠道是待验证假设，不是统一清单。选一到两个能触达用户的方式，以有限时间和预算测试。真实发送、发布、投放或联系由你在具备授权时执行，教材不会自动代发。

## 五、渠道实验与归因

```text
目标人群、问题与信息：
渠道、入口、版本与时间：
投入（时间/现金）与上限：
合适访问 / 试用 / 激活 / 持续任务 / 试点或付费：
来源参数、去重、主体与观察窗口：
拒绝/放弃原因、支持成本与护栏：
继续、调整或停止的条件：
```

来源参数只是归因线索，用户可能跨设备或分享链接；不能把归因当因果证明。先统一指标口径，再比较渠道。少量试点结论写探索性，不对短期涨幅作保证。

虚构案例：触达100、试用20、完成2。先检查数据，若真实完成率低，观察入门和失败，而不是直接扩大投放。若完成多却不续用，调查频率、价值和替代。企业购买者拒绝还要看预算、流程和风险。

## 六、从试点走到持续经营

试点写用户、购买者、资料负责人、范围、时长、双方责任、成功标准、收费/免费条件、支持和退出。将首次价值任务安排得简单可完成，但不绕过必要权限。

每轮复盘用户任务、故障、反馈、渠道、成本及续用；将问题回写定位、规格、优先级和技术计划。重度客户的人工成本单独观察，判断是否应改善入门、标准化接入或调整交付模式。

### 一个小规模试点怎样记账和决策

沿用“新人查发布规范”。先约一个能触达研发负责人的渠道、一种邀请信息和一个观察窗口。邀请可写成：“带一条你最近查过的发布规范，试用时请独立找出适用版本和原文；我们记录完成情况并约一次回访。”先标记邀请来自哪个渠道，经同意记录匿名主体与必要事件；名单保留在授权范围内。

| 观察窗口 | 要记的事实 | 它能支持的决定 |
| --- | --- | --- |
| 首次触达至首次任务 | 目标团队数、愿意试用数、能独立找到正确依据数、失败在哪一步 | 触达少先检验渠道；愿意试却做不完，回到入门流程或质量问题 |
| 下一次同类需求 | 首轮完成者中有多少遇到了新任务、多少回来完成、多少改回旧流程 | 按原始队列报告续用，并另列当期有机会续用的人数及原因，避免挑选活跃者 |
| 试点结束 | 谁能决定续约、同意的价格与范围、模型/基础设施增量费用、支持与接入工时 | 用观测到的成本写报价；购买者的口头兴趣、试点承诺与实际收款分别记录 |

**算一笔再做决定。** 假设一次试点报价 1200 元，增量模型及托管成本 180 元，人工支持 6 小时，估算每小时 120 元。试点贡献为 1200 − 180 − 720 = 300 元。若每个新客户还需要 4 小时一次性接入，则首期贡献变为 −180 元；如果报价尚未被接受，这两项都属于预测。列出接入减少到几小时首期能持平，再选择提高价格、标准化接入或缩小范围的一项来验证。区分预估贡献、固定开支与到账现金。

**用事实决定推广节奏。** 如果团队愿意复用但单次支持成本过高，先做一次自助接入实验；如果体验顺畅却没人带第二项任务，回访任务频率和现有替代。为下轮预先填下“愿意继续的负责人、下一次任务、最多投入的工时、到期怎样退出”。把实验结果和一次被放弃的功能写回产品规格；这份决定是创业训练的交付物。

## 七、上线与推广的累计验收

提交可复现发布说明、测试环境记录、落地页草稿、发布包、一次渠道实验设计、入门与支持流程和结果复盘。没有实际发布或客户时明确为设计/模拟；正式运行、真实采用与付费分别确认，不能凭公网能打开就认定产品成立。
