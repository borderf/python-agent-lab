# 第06章　推理：采样、KV cache 与成本

## 1. 学习目标与前置知识

能说明模型怎样从候选分数中选出下一个token，比较温度等解码设置；再沿“先处理输入、后逐步生成”的顺序，理解KV缓存、量化和批处理怎样影响等待时间与资源。前置：第1、4章。

**本章从这里开始：** 同一模型、同一提示，为什么有时回答稳定、有时发散？为什么首 token 很慢、后面很快？为什么量化后显存降了，质量可能没明显降，也可能明显降？

## 2. 基础知识讲解

### 2.1 从 logits 到 token

词表中的每个候选token，都会得到一个实数分数，这些分数叫**logits**。分数本身还不是概率：可能为负，也不要求总和为1。softmax把整组分数转换成非负、总和为1的概率：

```text
p_i = exp(z_i) / sum_j exp(z_j)
```

取 `z=[2,1,0]`，代入后 `exp(z)=[7.389,2.718,1]`，总和 11.107，所以概率约为 `[0.665,0.245,0.090]`。预期概率非负且总和为 1。实现先减最大值 `[0,-1,-2]` 再 exp，比例不变，但能避免大 logit 溢出。

应用通常还会调整候选的选择方式：温度缩放改变分数之间的差距，top-k或top-p限制参与选择的候选范围，最后再采样。可以先沿“分数→概率→选一个token”理解，再分别观察各个参数改变了哪一步。

### 2.2 解码策略

| 策略 | 做什么 | 特点 |
| --- | --- | --- |
| greedy | 每步选最高概率 | 稳定、易重复、缺少多样性 |
| beam search | 保留多个候选序列 | 质量可能更好，成本高，开放对话不一定合适 |
| temperature | 缩放 logits | <1 更尖锐，>1 更平坦；不改变事实 |
| top-k | 只保留前 k 个候选 | 限制长尾，k 难统一 |
| top-p | 保留累计概率 ≥p 的最小集合 | 动态候选数，常用 |
| repetition penalty | 惩罚重复 token | 缓解复读，可能伤害必要重复 |

`temperature=0` 通常近似贪心，但不保证跨版本/硬件完全复现。

### 2.3 小数字例子

候选概率 `0.6/0.3/0.1`（这里先看未加温度的概率）：

- 贪心总选 0.6；
- 按分布采样，约 60% 选第一个；
- top-k=2 保留前两个并归一化为 `2/3、1/3、0`；
- top-k=1 等价贪心；
- top-p=0.9 保留 0.6+0.3，去掉 0.1；若阈值改为 0.85，也保留使累计概率首次达到/超过阈值的最小集合，即前两项，再归一化。

温度 0.5 会让 0.6 对应的 logit 相对差距扩大，因此它更占优。注意应用顺序通常是**先温度缩放，再截断，最后采样**；不能拿温度前的 0.6/0.3/0.1 直接代替温度后的候选概率。边界：top-k 大于候选数时等于不截断，top-p=1 也应保留全部非零概率候选。

练习还会比较分布的熵。对离散概率 `p_i`，熵定义为 `H=-Σ p_i ln p_i`，单位是 nats；若用 `log2` 则单位是 bits。它衡量分布的不确定性：概率越集中熵越低，越平坦熵越高。它不同于第5章的交叉熵，交叉熵还需要真实目标分布或正确 token。

### 2.4 prefill 与 decode

一次生成分两段：

- **prefill**：先处理输入的prompt，为历史位置计算并保存K/V。输入较长时，这一步通常更费时，会影响用户等到第一个token的时间（TTFT）；排队等环节也可能影响TTFT。
- **decode**：开始输出后，逐步计算新token，并复用已保存的历史K/V。用户看到后续token逐段出现，这部分的速度常用每输出token耗时（TPOT）等指标观察。

```text
prefill: 输入 n 个 token -> 并行计算 -> 首 token
decode: 新 token + 历史 KV -> 下一个 token -> ...
```

输入越长，prefill 越贵；输出越长，decode 越久。流式界面看到的“逐字出现”就是 decode 过程。

设一次请求 prefill 800 ms，平均每个输出 token 40 ms，生成 20 个 token：TTFT 约 800 ms，且已经包含首 token；首 token 之后还有 19 个间隔属于 decode，约 `19×40=760 ms`，总时长约 `800+760=1560 ms`，TPOT 约 40 ms。不要把首 token 再算一次 `20×40`。这里忽略排队、网络和工具调用。若输入 token 翻倍，不能只凭这个玩具式线性关系断言 TTFT 精确翻倍，但方向是 prefill 更贵；若输出翻倍，串行 decode 时间会增加。

### 2.5 KV cache

生成下一个token时，还需要用到历史位置的K和V。如果每一步都重算，会重复做很多工作。**KV cache**就是把这些历史结果保存下来，新生成一个token时再补入它的K/V。省掉重复计算的代价是占用显存，下面估算它要保存多少数据：

```text
KV bytes ≈ 2（K和V） × 层数 × KV头数 × 每头维度
           × 序列长度 × 批大小 × 每元素字节数
```

例如 32 层、8 个 KV 头、每头 128 维、4096 token、FP16（2 字节）、批大小 1：

```text
2 × 32 × 8 × 128 × 4096 × 2 ≈ 512 MiB
```

逐项代入：`2×32×8×128=65,536`，再乘 4096 得 268,435,456 个元素，FP16 每元素 2 字节，即 536,870,912 字节 = 512 MiB。**预期：序列长度或批大小单独翻倍，缓存约翻倍；两者都翻倍则约变 4 倍。** 这还没算激活、临时缓冲和并发请求。

**KV 头数不一定等于注意力头数**：MQA 让所有查询头共享一组 K/V，GQA 让若干查询头共享一组 K/V，目的都是减少缓存和带宽；具体收益取决于模型结构与实现。缓存大小随层数、KV 头数、上下文、批大小和并发增长，是长上下文/高并发的主要显存成本之一。

前缀复用（prefix cache）只在“相同模型、相同前缀 token、相同 KV 配置”等条件成立时有效；它不是业务长期记忆，也不能跨模型/跨版本直接复用。请求结束通常释放缓存；多轮对话要重新发送或保存必要历史，不能假设服务端替你永久记住。缓存命中率是性能指标，不是事实正确性或权限的证明。

### 2.6 量化与批处理

- **权重量化**：用更低比特存权重，降显存/带宽；
- **激活/KV 量化**：进一步省资源，但更易影响精度；
- **批处理**：把多请求一起算，提高吞吐，但可能增加单请求延迟/显存；
- **投机解码**：小模型草稿 + 大模型验证，可能加速，但依赖实现/负载。

量化效果取决于方法、硬件、模型和任务；不能只看“4bit”标签承诺质量。

最小形状账：70 亿参数若理想地按 4 bit 存权重，权重本体约 `7×10^9×4/8=3.5 GB`；再加量化元数据、KV cache、激活和运行时缓冲，总显存会更高。质量边界可用固定题观察：量化前 100 题答对 86 题，量化后答对 83 题，下降 3 个百分点；是否可接受要按业务阈值，而不是看权重变小就判定无损。批处理同样可能提高吞吐却恶化单请求 P95，第 3.3 节用数字说明。

## 3. 原理讲解与推导

### 3.1 为什么首 token 慢、后续快

prefill 要处理整段输入并建立缓存；decode 每步只处理一个 token（加缓存），单步计算小，但串行、受内存带宽和采样开销影响。长输入 TTFT 高，长输出总时长高。

### 3.2 为什么温度不修复事实

温度只改变分布形状/采样随机性；它不改变客观事实，也不保证提升事实性，但会改变本次生成的答案，可能让原本“碰巧答对”的采样变成答错，反之亦然。如果模型对错误答案给高概率，降低温度只会更稳定地重复错误；事实要靠检索、工具、校验和评测。

### 3.3 吞吐 vs 延迟

批处理提高 GPU 利用率/吞吐，但请求要排队，单请求延迟可能变差。SLO 要分别定义 TTFT、TPOT、P95/P99，而不是只看平均吞吐。

用两组示意测量：批大小 1 时吞吐 20 请求/秒、P95 首 token 1.2 秒；批大小 4 时吞吐 60 请求/秒、P95 首 token 2.8 秒。吞吐变成 3 倍，但 P95 恶化 1.6 秒。若业务 SLO 是 P95≤2 秒，这组配置不能采用；可减小批大小、限制排队或扩容。数字只用于说明取舍，真实结果必须在相同负载下测量。

## 4. 示例与逐步走查

```python
# runnable
import math

def softmax_with_temperature(logits, temperature=1.0):
    if temperature <= 0:
        raise ValueError("temperature 必须大于 0")
    scaled = [value / temperature for value in logits]
    maximum = max(scaled)
    exps = [math.exp(value - maximum) for value in scaled]
    total = sum(exps)
    return [value / total for value in exps]

def top_p(probabilities, threshold):
    if not 0 < threshold <= 1:
        raise ValueError("top-p 必须在 (0,1]")
    order = sorted(range(len(probabilities)), key=probabilities.__getitem__, reverse=True)
    kept, cumulative = [], 0.0
    for index in order:
        kept.append(index)
        cumulative += probabilities[index]
        if cumulative >= threshold:
            break
    total = sum(probabilities[index] for index in kept)
    result = [0.0] * len(probabilities)
    for index in kept:
        result[index] = probabilities[index] / total
    return result

logits = [2.0, 1.0, 0.0]
probabilities = softmax_with_temperature(logits)
print("输入:", {"logits": logits, "top_p": 0.9})
for temperature in (0.5, 1.0, 2.0):
    print("中间结果:", {"temperature": temperature, "probabilities": softmax_with_temperature(logits, temperature)})
truncated = top_p(probabilities, 0.9)
kv_mib = 2 * 32 * 8 * 128 * 4096 * 1 * 2 / (1024 ** 2)
print("输出:", {"top_p_result": truncated, "kv_cache_MiB": kv_mib,
                "latency_ms": {"TTFT": 800, "TPOT": 40, "total_20_tokens": 800 + 19 * 40}})
assert abs(sum(truncated) - 1) < 1e-12
assert truncated[2] == 0
assert abs(truncated[0] - 0.7310585786300049) < 1e-12
assert kv_mib == 512
```

逐步解释：

1. logits 先除温度；
2. 减最大值只为数值稳定；
3. exp/归一化得概率；
4. 温度低→分布尖；温度高→分布平；
5. top-p 保留累计达到 0.9 的最小集合，前两项累计约 0.910，所以去掉第三项并重新归一化；
6. 采样还要随机数；本块不采样，因此结果确定，可重复核对。

## 5. 练习

### 练习一：跟写

对 logits `[2,1,0]` 计算 temperature=0.5/1/2 的分布，比较熵/最大值。完成标准：最大概率约 0.867/0.665/0.506，熵约 0.441/0.832/1.020；温度越高熵越大，三者概率和均为 1。

### 练习二：改造

实现 top-p：按概率降序累加，保留累计达到 p 的最小集合，重新归一化；说明 p=1 与不截断的关系。完成标准：对 `[2,1,0]`、温度 1、p=0.9，结果约为 `[0.731,0.269,0]`；p=1 保留全部候选，概率不变。

### 练习三：独立

为流式问答定义 TTFT、TPOT、P95 三个指标；给出一个“批处理提高吞吐但恶化 P95”的场景和取舍。完成标准：TTFT 从请求发出到首 token，TPOT 为输出阶段平均每 token 时间；P95 按延迟升序取第 95 百分位附近，不能用平均值代替。

## 7. 面试问答与参考回答

**问：temperature、top-k、top-p 的区别？**

温度缩放整个分布；top-k 固定保留前 k 个；top-p 按累计概率保留动态集合。它们都改变采样候选/形状，不改变模型事实能力。

**问：prefill 和 decode 有什么区别？**

prefill 并行处理输入、建立 KV cache，决定首 token 延迟；decode 逐步生成、复用缓存，决定每 token 时间。两者成本随输入/输出长度变化。

**问：KV cache 为什么省时间又费显存？**

它复用历史 K/V，避免每步重算旧 token；但缓存随层数、上下文、并发增长，长上下文/高并发会吃显存。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 同一模型同一提示，为什么有时稳定有时发散，首 token 又为什么明显更慢？

**一条主线：**

```text
prompt → prefill 并行计算并建 KV cache → 逐 token decode → logits/温度/截断采样 → 流式输出
```

**三个关键词：** 采样、prefill/decode、KV cache——采样决定这一步选哪个 token，prefill/decode 把延迟分成两段，KV cache 用显存换掉重复计算。

**最容易错：**

- 以为调低 temperature 或设 0 就能消除幻觉、保证跨环境复现；
- 把 top-k 和 top-p 混为一谈：固定个数 vs 累计概率的动态集合；
- 把 KV cache 当服务端永久记忆，多轮对话不重发必要历史；
- 只看平均吞吐，不分别定义 TTFT、TPOT 和 P95/P99。

**与前后章：** 上一章产出训练好的参数，本章回答固定参数下每次生成怎样发生、成本落在哪；下一章处理结果不可靠，把证据从参数搬到上下文。

**学完应能：**

- 从 logits 算出不同温度下的分布，说明分布怎样变尖、变平；
- 实现 top-p 截断，说明 p=1 与不截断的关系；
- 区分 prefill 与 decode，解释首 token 慢、后续 token 快；
- 估算 KV cache 随层数/上下文/并发的增长，并为流式问答定 TTFT、TPOT。
