## 1. 学习目标与前置知识

从可运行代码走向可复现工程。前置：第7、9、10、12章。

**承接与本章主线：** 把已通过行为验收的程序变成可复现安装与配置的工程；后续HTTP和API复用同一业务规则。

**本章从这里开始：** 代码在你的电脑能跑，换目录或换一台机器却失败。原因往往不在业务算法，而在解释器、依赖、入口、配置和资源未成为明确输入。

## 2. 基础知识讲解

### 2.1 一个项目由哪些可复现要素组成

源码在开发机运行成功，可能只是因为当前目录、全局包或个人配置刚好满足条件。换一台机器就失去这些隐含输入。工程交付要把解释器、依赖、资源和入口变成显式材料，并在离开源码目录后验证。分层同样是在显式管理依赖，避免一次网络协议变化迫使业务规则一起改动。

同伴拿到订单源码，却提示找不到某个库。先依次确认四件事：正在使用哪个Python、项目声明了什么依赖、锁文件选定哪些版本、这些版本是否装进当前环境。对应地，解释器决定运行行为，pyproject保存项目声明，锁文件保存解析结果，虚拟环境保存实际安装内容。查清这条链后再使用uv管理它们，避免靠反复安装猜原因。

uv帮助管理这些环节，但不会让不一致的配置自动变合理。添加依赖、同步环境和运行程序是不同动作；每次升级应观察锁文件变化并重新执行相关检查。

#### 案例推进：先区分四种容易混淆的东西

pyproject描述项目与依赖要求，锁文件记录一次解析的具体选择，虚拟环境保存实际安装结果，wheel是构建产物。环境里碰巧有一个库，不表示项目声明了它；提交锁文件，也不表示数据库和配置已经准备好。应用通常需要锁定环境，作为库发布时则还要声明合理依赖范围。

本仓库已有src布局、uv_build和命令入口，先读懂实际配置再扩展。不要把教材中的示意目录直接覆盖现有项目。

```text
入口 CLI / API
    ↓ 解析配置并装配
业务服务 → 领域计算
    ↓ 依赖契约
文件 / HTTP / 数据库适配器
```

领域计算不读环境变量、不启动连接，才能在CLI、API与工具间复用。入口知道使用哪个实现，业务只知道需要什么能力。依赖注入在这里就是将协作者作为参数或构造依赖提供，不必先引入容器框架。

### 2.2 从入口到业务规则确定依赖方向

CLI和HTTP接口负责接收输入，业务服务组织用例，领域函数表达订单规则，适配器处理文件、数据库和模型调用。内层不应反过来依赖某个具体路由或网络响应对象。

以“新增一种数据来源”为例，理想变化集中在适配器和配置，金额计算无需重写。这不是要求小项目必须分四层文件夹，而是要求变化边界清楚。用普通函数、模块或类都可以达成。

### 2.3 配置有来源和覆盖顺序

命令行参数、环境变量、配置文件与默认值必须规定优先级。加载后先验证格式与范围，再交给业务；不在导入模块时悄悄固定一份难以替换的全局配置。测试传入独立Mapping，不修改真实账号或凭据。

#### 案例推进：配置覆盖也应可运行地说明

```python
# study-example: S13A
def read_concurrency(cli, environment):
    raw = cli if cli is not None else environment.get("CONCURRENCY", "3")
    if isinstance(raw, bool):
        raise ValueError("不接受bool")
    text = str(raw)
    if not text.isascii() or not text.isdecimal() or int(text) <= 0:
        raise ValueError("并发必须为正整数")
    return int(text)

assert read_concurrency(None, {}) == 3
assert read_concurrency(None, {"CONCURRENCY":"4"}) == 4
assert read_concurrency(2, {"CONCURRENCY":"4"}) == 2
```

使用is not None保留显式传入值，再按契约验证，而不是用or偷偷处理0。函数接收映射，所以测试不污染真实环境；最终入口才传入实际环境。密钥来自受控配置，不硬编码进源码、演示数据或日志。

### 2.4 公共接口比内部实现稳定

公共函数说明输入、返回值、异常、副作用和资源责任。内部可以从列表扫描改为字典索引，只要契约和行为检查仍成立。需要不兼容变化时，记录迁移方式，不能只改实现让调用方自行猜测。

### 2.5 交付沿着构建链逐步验证

先运行风格/类型检查和行为测试，再构建安装包，在独立环境、非源码目录验证导入和入口。开发依赖和运行依赖分开，临时目录和本地路径不应成为隐式前提。

每版保留启动命令、样例、失败复现与变更说明。架构演进记录要回答上版有什么问题、本版改变什么、证据是否支持继续采用。

#### 案例推进：从安装产物验证交付

构建后在独立环境安装wheel，从非源码目录运行关键入口，核对包资源是否包含、配置缺失是否明确、错误退出是否一致。记录解释器和真实命令，再补Ruff、类型检查、pytest与构建的CI步骤。持续集成不负责替你选择正确断言，它负责在一致条件下执行这些检查。

公共函数签名、结果单位、异常类别和数据Schema属于接口，内部循环与缓存属于实现。修改接口需要考虑调用者和版本兼容；只换内部实现也要通过原有行为回归。把变更传播范围说清楚，才算理解分层。

#### 为当前仓库选择实际入口命令

```powershell
uv sync --frozen --inexact
uv run --frozen python --version
uv run --frozen python -m pytest
uv build
```

这些命令分别同步锁定依赖、确认解释器、运行默认发现的测试和构建。练习目录的checks_文件仍需显式指定，默认pytest成功不证明它们都运行了。构建后安装到新的临时环境，再从其他目录导入已安装包；不要把临时验证环境当作全局Python修改。

日常学习的 `.venv` 可能还有给编辑器或 Notebook 安装的包。上面的 `--locked` 检查锁文件与项目声明是否一致，`--inexact` 允许额外的包共存。要验证项目能否只靠已声明依赖运行，在独立干净环境做 `uv sync --frozen` 和入口测试；这能发现本机偶然装好的包掩盖的遗漏。[uv 同步行为](https://docs.astral.sh/uv/concepts/projects/sync/#handling-of-extraneous-packages)

Git保留源码、配置与锁文件的可审查版本，虚拟环境、密钥和临时输出按实际需求排除；提交前看diff确认内容。CI在干净环境复现检查，依赖更新单独审查和回归。学习阶段先保持小模块与清楚依赖方向，避免为目录层数本身设计抽象。

## 3. 原理讲解与推导

### 3.1 可复现性来自显式输入

机器状态、环境变量、工作目录和网络都可能影响结果。把必要输入声明并记录，才能让“同一份代码”接近“可比较的一次运行”；锁文件只覆盖其中的依赖维度。

### 3.2 分层的价值是控制变化传播

高内聚使同一种规则集中，依赖反向或重复规则会扩大变更范围。用一次真实新增来源或修改金额规则的任务，检查哪些文件应改、哪些不应改，比统计目录数量更有意义。

## 4. 示例与逐步走查

### 从源码到交付的走查

```text
声明依赖 → 更新锁文件 → 同步项目环境 → 检查/测试 → 构建wheel
→ 临时环境安装 → 非源码目录运行 → 记录版本与命令
```

第一个失败点可能是依赖解析，第二个是测试发现规则错误，第三个是wheel漏打包。把三个阶段分开记录，不用“本机能跑”代替全部验收。

### 4.1 沿输入到结果逐步解释

依赖解析成功说明声明可以得到一组版本，不说明业务行为正确；测试成功说明已覆盖的行为成立，不说明构建包带全了代码和资源。因此构建链需要分段观察。

在源码目录导入可能误用当前文件，掩盖wheel漏包。独立安装后换到非源码目录运行，才会迫使程序依赖实际交付产物。若此时失败，应先查构建和入口，而非重新调试已经通过的业务规则。

将配置和命令一同记录，是为了让下一人能够复现条件，而不是依赖开发者机器上未说明的包与路径。

## 5. 动手练习

### 本章累计任务：固定可复现条件

**未通过时怎样定位：** 源码目录成功而安装后失败时先查包与资源；依赖解析、测试、构建与运行分别检查。

### 练习一：环境与入口可复现

整理现有pyproject、依赖锁与包入口，不先改写已正确的业务函数。用独立临时环境安装构建产物，从非源码目录执行一条正常订单命令和一条失败命令。记录解释器、安装命令与输出，证明未隐式依赖工作目录中的源码。

### 练习二：可测试配置

约定优先级为命令行覆盖环境，环境覆盖默认值。超时默认5秒，并发默认3；空白、非有限数、非正数等非法配置明确失败。配置解析接收传入映射以便测试，不在模块导入时改变真实环境。

验收：缺省、覆盖、非法值分别有检查；日志可以定位字段但不暴露密钥；导入纯业务模块不启动网络或读取真实文档。

### 练习三：一次边界变更

将文件来源替换为内存仓储，核心报告不修改。画出入口、业务与适配器依赖方向，解释哪个模块拥有资源。提交一页变更记录，包含问题、选择、验证和代价。

## 8. 本章小结与参考

### 8.1 主要知识点总结

- 解释器、项目声明、锁文件和实际环境共同决定运行条件。
- 入口、业务、适配器和配置有不同职责，依赖方向要支持替换与测试。
- 配置来源、覆盖顺序和合法范围需要显式确定。
- 构建与交付要保存可复现命令和版本，升级后执行相关验证。

### 8.2 日常工作注意事项

- 先核对实际解释器与环境再安装依赖，避免一个终端安装、另一个环境运行导致找不到包。
- 密钥与环境差异通过配置注入，不写死在业务代码或提交到仓库；日志也不要输出完整配置中的凭据。
- 新增依赖或升级时同步核对锁文件和检查结果；配置为空、非法或超范围时尽早报告错误。
