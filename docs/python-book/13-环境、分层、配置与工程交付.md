## 2. 基础知识讲解

### 2.1 声明、锁、环境与构建产物各管一件事

`pyproject.toml` 声明项目与依赖范围；`uv.lock` 记录一次解析选定的版本；虚拟环境保存实际安装内容；wheel 是构建产物。环境里碰巧有包，不代表项目已经声明它。

解释器版本是另一维：`requires-python` 约束兼容范围，`.python-version` 供 uv 选择本地解释器，虚拟环境只固定一个解释器及其包。锁文件不能替你安装 Python，也不能抹平操作系统、架构和 C 运行库差异。

构建隔离让构建后端在独立环境按 `[build-system].requires` 安装，不借用运行虚拟环境；构建依赖与运行依赖因此要分别声明。锁定输入、工具版本和干净构建环境能提高可复现性，但 ZIP 元数据、时间戳或路径等仍可能使两次 wheel 不是 bit-for-bit；验收应比较内容清单和安装行为，不把字节完全相同当作唯一标准。

开发依赖与运行依赖分开。添加或升级依赖后检查锁文件差异，再用锁同步环境；不要把本机额外安装的包当作项目可复现条件。

`uv.lock` 还会纳入解析到的传递依赖和项目依赖组；直接依赖不变也可能因兼容版本解析而变动，审查锁差异时不能只看顶层包名。
`--locked` 要求锁与声明一致，适合 CI；`--frozen` 只要求按现有锁安装，不检查声明是否变化。两者都不会顺手升级锁。日常环境可能还有编辑器额外安装的包，因此“同步成功”仍不等于“项目只靠声明依赖运行”；干净环境与入口测试提供更强证据。

先用一份固定清单区分“声明允许”与“实际装的是锁定的版本”。它不读取本机包，因此任何机器都能得到同一个结果；真实环境再用 `python -c "import sys; print(sys.version); print(sys.prefix)"` 与 `uv pip list` 核对。

```python
python_version = (3, 12, 7)
requires_python = (3, 12)
locked = {"httpx": "0.28.1"}
installed = {"httpx": "0.27.0"}

print("python-compatible", python_version >= requires_python)
print("lock-match", installed == locked)
print("undeclared", sorted(set(installed) - set(locked)))
```

预期输出为 `python-compatible True`、`lock-match False`、`undeclared []`。解释器满足声明范围，包版本也满足顶层范围，但实际安装与锁不一致，所以仍不能宣称环境可复现；`undeclared` 为空只说明这份快照没有额外包，不证明传递依赖正确。

### 2.2 依赖方向从入口指向业务

CLI 或 API 解析配置并装配依赖，业务服务组织用例，领域函数表达订单规则，适配器处理文件、HTTP 或数据库。内层不读取环境变量，也不创建具体客户端。

新增数据来源时，理想变化集中在适配器和配置；`build_report` 不应重写。分层不需要很多文件夹，只需要每条变化都有明确归属。

公共接口比内部实现稳定：`build_report` 的入参、报告字段和异常语义是跨入口契约，可以被子任务和测试依赖；适配器内部函数则应允许重构。不要让 CLI 或 HTTP 模型反向渗入核心，否则一个入口的字段变化会迫使所有入口一起改。

依赖方向还要检查实际 import 图：业务层为创建具体客户端而反向导入适配器，会形成循环并让测试被迫加载外部框架。把装配移回入口，或让内层定义 Protocol、外层实现；不要在函数内临时 import 掩盖循环。新增依赖边时同时检查运行依赖、测试依赖与打包内容，避免“目录分层了但 import 仍反向”。
依赖注入只是把协作者从参数或构造边界传入，不必先引入容器框架。入口负责选择真实实现，测试传入内存替身；只要契约一致，核心函数不需要知道替身是否存在。

分层是否成立，可以检查允许的 import 边，而不是数文件夹。下面固定四层依赖图，再故意加入一条 `core → adapters` 反向边。

```python
imports = {
    "cli": ["service"],
    "service": ["core"],
    "core": [],
    "adapters": ["core"],
}
allowed = {("cli", "service"), ("service", "core"), ("adapters", "core")}

def violations(graph):
    return [f"{source} -> {target}" for source, targets in graph.items()
            for target in targets if (source, target) not in allowed]

print("core imports", imports["core"])
print("direction", violations(imports) or "OK")
imports["core"].append("adapters")
print("after reverse edge", violations(imports))
```

预期输出为 `core imports []`、`direction OK`、`after reverse edge ['core -> adapters']`。执行过程把每条 import 边与允许方向比较；反向边出现时，测试核心就可能被迫加载 HTTP 或数据库适配器。修复方式是把装配移回入口，或让核心定义 Protocol、由适配器实现，不是在核心里临时 import 隐藏循环。

### 2.3 配置要有来源、优先级和范围校验

约定命令行覆盖环境变量，环境变量覆盖默认值。加载后立即验证格式与范围，再传给业务；测试接收独立映射，不修改真实环境。密钥来自受控配置，不写进源码、样例或日志。

若引入配置文件，要明确它排在默认值、环境变量和命令行的哪一层，并固定搜索路径；同一来源出现多次时还要定义后者是否覆盖前者。不要从多个不可见位置同时加载，否则“覆盖顺序”无法复现。

空字符串是已提供的值：数值和必填文本应校验失败，只有明确允许为空的字段才转成 `None`；不能用 `or` 把空值恢复成默认值。布尔字符串、大小写和首尾空白也应由统一解析器处理，避免不同入口各接受一种格式。

密钥放进 secret manager 或已忽略的本地 `.env`，样例只放占位符；不要嵌入依赖 URL、`pyproject`、锁文件、测试快照或日志。`.gitignore` 只防止后续误跟踪，已经提交的密钥必须轮换并按泄漏流程处理，CI 日志脱敏也不能替代轮换。

#### 案例推进：显式 0 不能被默认值掩盖

```python
# study-example: S13A
def read_concurrency(cli, environment):
    raw = cli if cli is not None else environment.get("ORDER_CONCURRENCY", "3")
    if isinstance(raw, bool):
        raise ValueError("不接受bool")
    text = str(raw)
    if not text.isascii() or not text.isdecimal() or int(text) <= 0:
        raise ValueError("并发必须为正整数")
    return int(text)
assert read_concurrency(None, {}) == 3
assert read_concurrency(None, {"ORDER_CONCURRENCY": "4"}) == 4
assert read_concurrency(2, {"ORDER_CONCURRENCY": "4"}) == 2
for bad in (0, True, "2.5", ""):
    try:
        read_concurrency(bad, {})
    except ValueError:
        pass
    else:
        raise AssertionError("非法配置应拒绝")
```

使用 `is not None` 保留显式传入值，再用 `or` 会把 0 错当缺省。入口负责传入真实环境，纯函数只接收映射。
配置解析还要说明哪些值可以缺省、哪些必须显式提供。超时和并发影响资源上限，密钥缺失应让入口明确失败；不要用开发默认值悄悄连接真实外部系统。配置来源也要写入交付记录。

若增加配置文件，本章固定优先级为“默认值 < 配置文件 < 环境变量 < 命令行”。下面把四层放进一个纯函数，并故意让环境变量提供空字符串。

```python
def resolve_concurrency(cli, environment, file_values):
    raw = cli if cli is not None else environment.get(
        "ORDER_CONCURRENCY", file_values.get("concurrency", "3"))
    if isinstance(raw, bool):
        raise ValueError("并发必须为正整数")
    text = str(raw)
    if not text.isascii() or not text.isdecimal() or int(text) <= 0:
        raise ValueError("并发必须为正整数")
    return int(text)

print("default", resolve_concurrency(None, {}, {}))
print("file", resolve_concurrency(None, {}, {"concurrency": "5"}))
print("env", resolve_concurrency(None, {"ORDER_CONCURRENCY": "4"}, {"concurrency": "5"}))
print("cli", resolve_concurrency(2, {"ORDER_CONCURRENCY": "4"}, {"concurrency": "5"}))
try:
    resolve_concurrency(None, {"ORDER_CONCURRENCY": ""}, {"concurrency": "5"})
except ValueError as exc:
    print("invalid", str(exc))
```

预期输出为 `default 3`、`file 5`、`env 4`、`cli 2`、`invalid 并发必须为正整数`。执行过程逐层选择第一个“已提供”的值，空字符串已经提供，因此不会退回文件中的 5；显式 0 与布尔值也会失败。边界是密钥不能采用开发默认值，配置文件搜索路径必须固定，否则同一入口仍会读到不同来源。

## 3. 原理讲解与推导

### 3.1 可复现性来自显式且受控的输入

机器状态、环境变量、工作目录和网络都会影响运行。声明依赖、锁定版本、注入配置并记录命令后，两次运行才具备可比较的条件；锁文件只覆盖依赖维度，不能证明包内容、外部服务或业务结果正确。
因此交付记录要同时保留解释器版本、锁文件、配置来源、实际命令和退出码。wheel 安装成功只证明产物可解析和入口可发现，报告正确仍要由固定输入与失败输入证明。

把三次运行放在同一张数据流表里，能看到哪些条件必须相同、哪些差异是允许的：

| 运行 | 解释器与锁 | 实际安装 | 配置 | 预期观察 |
| --- | --- | --- | --- | --- |
| A | Python 3.12.7 / L1 | 与 L1 一致 | 并发 3 | 峰值不超过 3，报告 1990 |
| B | Python 3.12.7 / L1 | 与 L1 一致 | 并发 4 | 峰值不超过 4，报告仍为 1990 |
| C | Python 3.12.7 / L1 | 某包为旧版本 | 并发 3 | 不能宣称复现，即使报告碰巧相同 |

A 与 B 说明配置变化应改变资源行为而不改变业务结果；C 说明业务输出相同不能反推环境一致。验收证据必须同时包含环境清单、配置来源和报告，不能只保存最后一张截图。

## 4. 示例与逐步走查

### 4.1 锁定并同步项目环境

#### 案例推进：把解析、安装和测试分开

在第12章项目根目录执行。先生成锁，再严格按锁同步；测试发现的是行为问题，不是安装问题。

```bash
uv lock
uv sync --locked
uv run --locked python -m pytest
```

`uv sync --locked` 不会顺手更新锁文件。若声明与锁不一致，应先审查并更新锁，再重新运行，不能靠忽略差异掩盖问题。

这三条命令分别留下不同证据：`uv lock` 成功后可检查 `uv.lock` 及其差异；`uv sync --locked` 成功后再用 `uv pip list` 核对实际安装；`uv run --locked python -m pytest` 的输出必须包含测试数量与通过/失败结果。任何一步失败都要保留首个错误，不能把后续测试通过当作前两步成功。

### 4.2 让配置穿过入口而不是散落全局

#### 案例推进：同一构建在不同环境改变并发

把 `read_concurrency` 放入配置模块，由 CLI 或查询入口调用，再把结果传给 `query_orders`。测试只验证映射输入与覆盖顺序；`core.py` 保持无环境读取、无网络副作用。

最小装配数据流为 `CLI 参数/环境映射 → read_concurrency → Settings(concurrency=4) → query_orders(..., concurrency=4)`。把环境值从 3 改成 4 后，预期报告仍为 1990，但查询峰值记录的上限变为 4；`core.py` 的搜索范围应找不到 `os.environ` 或 `getenv`。这条证据分别验证配置覆盖、资源行为和依赖方向。

### 4.3 构建 wheel 并离开源码目录

#### 案例推进：用安装产物重新生成报告

```bash
uv build --wheel
uv venv .verify-venv
uv pip install --python .verify-venv/Scripts/python.exe dist/order_service-0.1.0-py3-none-any.whl
```

构建成功后，切换到任意空目录，用该虚拟环境中 `order-report` 的绝对路径运行，并把第12章 `orders.jsonl` 的绝对路径作为参数。正常结果仍应是 1990；若失败，先查 wheel 内容、入口和资源路径，不要重改已经通过的业务规则。

可观察输出应包含安装成功信息，以及从空目录运行后的 `{"input_count": 3, "order_count": 2, "paid_amount_cents": 1990}`。执行顺序是构建、创建独立环境、安装 wheel、离开源码目录、运行入口；任何一步失败都不能用上一次可编辑安装的结果替代。

## 7. 面试问答与迁移

**问：分层是不是越细越好？**
答：不是。只有当变化需要被隔离、资源需要明确所有者或契约需要替换时才增加边界。小项目用模块和函数即可；目录数量不能替代依赖方向与测试。

**问：配置默认值为什么容易出错？**
答：因为“没提供”和“提供了假值”常被 `or` 混为一谈。先区分 `None`，再验证类型与范围；测试覆盖缺省、覆盖、0、布尔值和非法文本。
