## 2. 基础知识讲解

### 2.1 将需求变成可观察的断言

一个测试先准备输入，再执行动作，最后观察结果。订单去重不仅要检查数量，还要检查保留了哪条、顺序、冲突是否报错和输入是否改变。断言越贴近真实需求，越能防止“输出碰巧正确”。

正常、空、边界和错误案例分别承担作用。不要把测试写成实现的逐行复述；如果两者复制了同一个错误，测试也可能通过。



#### 案例推进：先把口头需求拆成行为

“规范化订单”至少有四件事：结果去掉两端空白，保留大小写，拒绝空ID，原输入不变。只检查结果数量，无法证明其他三项。测试期望应从需求手算，避免把实现里的同一表达式复制成答案。

下面代码保存为一个test_开头的独立文件后，用项目pytest执行；函数体为教学被测对象，测试函数才是检查。

```python
# pytest-example: T10
from copy import deepcopy
import pytest

def normalize(rows):
    result = []
    for row in rows:
        cleaned = dict(row)
        cleaned["id"] = row["id"].strip()
        if not cleaned["id"]:
            raise ValueError("id不能为空")
        result.append(cleaned)
    return result

def test_result_and_input_are_both_checked():
    raw = [{"id": " A ", "amount_cents": 10}]
    snapshot = deepcopy(raw)
    assert normalize(raw) == [{"id": "A", "amount_cents": 10}]
    assert raw == snapshot

@pytest.mark.parametrize("order_id", ["", " ", "\t"])
def test_empty_id_is_rejected(order_id):
    with pytest.raises(ValueError, match="id"):
        normalize([{"id": order_id}])
```

### 2.2 组织可重复的pytest测试

test_文件/函数方便发现测试；参数化复用相同案例结构，fixture提供每次所需准备，tmp_path隔离临时文件。可变样例要避免测试之间共享未清理状态，否则运行顺序可能影响结果。

用raises表达预期异常，并核对有意义的类型或字段；不要捕获一切异常后无条件通过。覆盖率帮助找没执行的路径，但不能证明断言充分或业务正确。



#### 案例推进：用小改动检验测试是否有辨别力

暂时把cleaned = dict(row)改成cleaned = row，测试应因输入改变而失败；恢复后再运行。再去掉空ID检查，参数化错误案例应失败。这种有目的的小故障能说明断言抓住了需求，不以测试数量或覆盖率替代实际辨别力。

fixture用于准备共享方式，tmp_path提供隔离的临时路径，monkeypatch可在正确作用域替换环境或对象。patch应针对使用处的绑定；若模块已from其他模块导入函数，只改原模块同名绑定未必影响使用处。这仍是第一章的对象绑定问题。

### 2.3 替换边界，不替换要检验的规则

网络、时间、模型和随机来源可以注入替身，使结果可控；计算、去重和规则本身应真实执行。单元测试关注局部契约，集成测试观察模块协作，真实服务检查另记录网络与配置条件。



#### 案例推进：替换外部依赖，保留正在检查的规则

测试报告计算时注入固定仓储，真实金额计算继续执行；测试HTTP适配时用受控响应，真实状态检查、解析和校验继续执行。若把被测计算也mock成期望答案，测试只证明替身设置成功。

遇到失败时保留最小输入、运行命令和traceback；先定位差异发生在哪一层，再修改。日志记录关联ID与阶段，异常让调用方决定流程。最终把失败样例变成回归，调试过程才不会随着临时print删除而失去价值。

### 2.4 调试与日志各自提供什么

traceback说明错误经过的调用路径，异常链保留底层原因；断点检查某个时刻的局部状态。日志保存运行事件，应包含可关联标识、阶段、耗时和错误类别，而不是随意打印所有参数。

日志不代替抛错，print调试不代替稳定断言。处理凭据和敏感原文时，采集前就应定义脱敏和保留规则。

### 2.5 工程工具是不同验证环节

pyproject声明项目和依赖，锁文件记录解析结果，虚拟环境容纳实际安装。Ruff检查一类代码问题，静态检查分析类型关系，pytest验证案例，构建与安装验证交付形式。它们互补，不能用一个“全绿”替代其余环节。

构建wheel后，从非源码目录、独立环境导入，才能发现包漏文件或隐式路径依赖。README必须记录真实可运行命令，而不是只写理想目录。



#### 案例推进：工具链各自回答什么

Ruff检查代码问题和格式，静态检查器分析类型关系，pytest检验行为，构建与安装检查交付，集成测试观察真实组合。通过某一项不能代替其他项。持续集成在干净环境运行约定步骤，把本地隐藏依赖暴露出来；具体命令应与项目实际配置一致。

## 3. 原理讲解与推导

### 3.1 测试只证明观察到的行为

排序结果正确与输入不变是两项独立要求。若仅断言结果，第一个要求通过不能推导第二个成立。设计测试时先列出状态和副作用，再决定哪些观察是必要的。

### 3.2 替身改变了证据范围

替换数据来源后，能证明业务函数在固定数据下如何处理，不能证明真实服务永远返回该格式。把业务函数也替换成固定答案，会进一步失去对核心行为的检验。每次使用mock都应说明仍在验证哪一段。

### 3.3 故障敏感性比测试数量更有价值

故意改错一条核心规则，相关测试应失败；恢复后再通过。这样能验证测试确实约束了规则，而非只检查代码可以运行。

### 3.4 机制验证：预测、运行与回看

先读上面的机制，再逐行预测下列实验的结果与副作用。E编号是保留的实验索引，不是章节编号；其中涉及后续协议的细节可在相应章节二次回看。

#### 验证实验 E21

```python
# experiment: E21
from copy import deepcopy
def sorts_in_place(rows):
    rows.sort(key=lambda row: row["cents"])
    return rows
rows = [{"id": "A", "cents": 20}, {"id": "B", "cents": 10}]
before = deepcopy(rows)
result = sorts_in_place(rows)
assert [row["id"] for row in result] == ["B", "A"]
assert rows != before  # 输出正确，但违反了本课程输入不变约定
def report_amount(fetch):
    return sum(row["cents"] for row in fetch())
assert report_amount(lambda: [{"cents": 7}, {"cents": 3}]) == 10
```



## 4. 示例与逐步走查

```python
# book-example: B10
def read_limit(environment):
    value = int(environment.get("LIMIT", "3"))
    if value <= 0:
        raise ValueError("LIMIT must be positive")
    return value
assert read_limit({}) == 3 and read_limit({"LIMIT":"2"}) == 2
```

### 4.1 沿输入到结果逐步解释

read_limit从注入的字典读取配置，缺省使用字符串3并转为整数；显式2得到2；零或负数触发错误。因为不在函数内部读取全局环境，测试可精确控制每个输入，也不会污染其他测试。
