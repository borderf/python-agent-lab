# 第17章　部署、可观测性与可靠性

## 1. 学习目标与前置知识

理解启动、故障、回滚与运维边界。前置：第13–16章。

**承接与本章主线：** 组合服务、依赖和持久数据，验证运行、诊断与恢复；为后续模型依赖和完整项目保留同一观测及可靠性边界。

**本章从这里开始：** 服务终于启动了，但用户仍说慢、任务偶尔消失。部署只是开始：要能知道哪里慢、什么失败、重启后怎样恢复，并用实际演练证明。

## 2. 基础知识讲解

### 2.1 部署的是一个有依赖的运行过程

服务进程还活着，用户却可能查不到资料：数据库不可用、模型超时或恢复数据不完整，都不会必然导致进程退出。可靠性要观察用户任务经过的整条路径。先说明哪些能力就绪，再记录阶段与错误，最后用实际恢复演练证明故障后的状态，而不是只验证能启动。

镜像打包应用运行环境，配置在部署时注入，数据库和索引等持久数据使用明确存储。启动顺序、版本、网络、端口和资源上限都是运行条件，不能只提交一个Dockerfile就认为系统可复现。

先运行最小API与必需数据库/索引，再按需求接MCP或追踪平台。每个新增组件都带来配置、资源和故障面，应有加入理由。

#### 案例推进：部署进程、共享状态和任务不是同一层

镜像包含程序与运行依赖，环境配置提供部署差异，卷或外部存储承接持久数据。增加多个worker会增加进程数，每个进程自己的内存字典与连接池未必共享；不能把内存任务状态当作多实例一致数据库。

存活检查观察进程，就绪检查观察接收流量的条件。优雅关闭应停止接收新工作，按预算等待或取消在途任务并关闭资源；未完成工作由持久状态恢复。重试、熔断和降级分别缓解不同问题，降级回答也必须表达能力受限。

### 2.2 健康与就绪分别观察什么

存活检查说明进程基本运行，就绪检查说明当前是否具备接服务条件。模型或数据库不可用时，应明确哪些接口仍可用、哪些应拒绝或降级。不要把依赖暂时慢误处理成不断重启进程，进一步扩大负载。

#### 案例推进：就绪与降级要有明确返回

```python
# study-example: S17B
def service_status(database_ok, model_ok):
    if not database_ok:
        return 503, {"status": "not_ready", "reason": "database"}
    if not model_ok:
        return 200, {"status": "degraded", "reason": "model",
                     "capabilities": ["search", "read_source"]}
    return 200, {"status": "ready", "capabilities": ["search", "read_source", "answer"]}

assert service_status(True, True)[0] == 200
assert service_status(False, True)[0] == 503
code, body = service_status(True, False)
assert code == 200 and body["status"] == "degraded"
assert "answer" not in body["capabilities"]
```

数据库不可用时返回503，让流量避开该实例；模型不可用时进程仍可提供检索和原文，因此返回200并明确降级能力。具体状态码按服务契约决定，关键是不要让客户端把“降级”误读成“完整回答可用”。liveness不应依赖模型或数据库，否则上游抖动会引发无意义重启。

#### 案例推进：降级状态要落到具体请求

```python
# study-example: S17C
def search_endpoint(capabilities):
    if "search" not in capabilities:
        return 503, {"error": "search_unavailable"}
    return 200, {"items": ["policy-a v2"]}

def answer_endpoint(capabilities):
    if "answer" not in capabilities:
        return 503, {
            "error": "answer_unavailable",
            "retryable": True,
            "fallback": "/search",
        }
    return 200, {"answer": "20%", "citations": ["policy-a v2"]}

degraded = ["search", "read_source"]
assert search_endpoint(degraded)[0] == 200
assert answer_endpoint(degraded)[0] == 503
assert answer_endpoint(degraded)[1]["fallback"] == "/search"
```

就绪检查返回200只说明“这个实例还能接一部分流量”，不说明所有路由都完整可用。客户端或网关应把 `/answer` 的 503/降级响应与 `/search` 的可用性分开处理；负载均衡是否把流量发到该实例，要和路由级健康/能力声明配合，不能用一个全局 readiness 布尔值承诺全部接口。

### 2.3 三类观测数据互补

日志记录离散事件，指标聚合趋势，trace连接一次请求中的步骤。request_id/task_id把API、检索、模型、工具、审批和持久化关联起来。记录之前就设计脱敏、访问范围和保留期，而不是事后删除泄漏数据。

#### 案例推进：从现象走到证据

指标先发现某类异常增多，trace关联一次请求跨模块的阶段，日志补充受控上下文。记录request_id、job_id、阶段、耗时、错误类别和版本，避免把密钥及全文原文当作调试材料到处复制。高基数标签和日志保留也有资源成本。

### 2.4 把延迟拆开再优化

排队、检索、首次输出片段、完整输出、工具与写入的耗时不同（模型服务的首token在第18章定义）；并行span可能重叠，不能简单求和。平均值隐藏尾部，p50/p95也需带样本数、环境、负载和冷启动条件。

#### 案例推进：先画请求的时间账本

```python
# study-example: S17A
stages = {"queue_ms":30, "retrieve_ms":40, "model_ms":200, "persist_ms":10}
sequential_ms = sum(stages.values())
assert sequential_ms == 280
assert max(stages, key=stages.get) == "model_ms"
```

这些是假设的单次顺序阶段数据，不是项目实测。总延迟包含排队、外部等待、计算和写入；并行分支不能直接把耗时全部相加。平均延迟还可能掩盖尾部请求，应分别看分位数、错误率和样本窗口。

### 2.5 可靠性措施对应不同故障

限流约束接收压力，超时限制等待，重试应对特定临时故障，熔断减少持续访问坏依赖，隔离降低故障传播，降级降低服务能力。每项都要定义触发、恢复、结果语义与代价，不是把开关全部打开。

### 2.6 恢复能力需要演练

备份存在不等于能够恢复。实际启动新环境，恢复样例，重启等待审批的任务，制造外部依赖超时，核对数据和客户端反馈。Compose适合学习和限定部署，不能由启动成功推导高可用或真实生产容量。

#### 案例推进：验证备份能否真正使用

在隔离环境恢复一份已知快照，核对任务、来源与结果，再演练重启和依赖不可用。RPO/RTO分别表达可接受的数据丢失范围和恢复时间目标，应按需求制定并实测。只有备份文件存在，不能说明恢复流程正确。

## 3. 原理讲解与推导

### 3.1 可靠性来自明确的故障行为

系统无法保证依赖永远成功，但可以规定失败怎样反馈、何时停止、哪些状态保留、如何恢复。可观察、可限制、可恢复和可验证共同组成这套能力。

### 3.2 优化可能改变正确性

缓存可能过期或跨权限，重试可能重复写，降级可能缺少关键证据。评价措施不仅看成功率，还要核对结果是否仍满足业务契约。模型不可用时返回证据列表可以是合理降级，假装审查已完成则不合理。

## 4. 示例与逐步走查

### 分解一次任务耗时

```json
{"task_id":"T1","queue_ms":5,"retrieve_ms":20,"model_ms":300,"tool_ms":30,"persist_ms":5,"status":"completed"}
```

这些数字仅为格式示例，不是项目实测。实际trace要说明是否含并行、重试与重叠区间，不能机械相加所有span就得到端到端耗时。模型错误时保留错误阶段，脱敏后再导出。

### 4.1 沿输入到结果逐步解释

样例分别记录排队、检索、模型、工具和持久化阶段。用户看到总等待时，先找最长阶段及其上游原因，而不是直接增加进程或更换模型。

若检索与另一工具并行，两段时间重叠，不能简单相加当端到端耗时；若模型重试，要把等待和失败也计入完整路径。只有带时间关系的记录才能解释实际延迟。

一次快请求只能证明这次行为。负载、尾延迟、依赖故障和恢复还需各自实验，日志字段齐全并不自动意味着系统可靠。

## 5. 动手练习

### 本章累计任务：交付并演练恢复

从干净环境启动服务，分别检查进程存活、必需依赖就绪与实际任务。模拟依赖超时，恢复一份隔离备份，核对数据与未完成动作。

**未通过时怎样定位：** health返回200不证明数据可用；备份成功不证明还原成功；日志耗时相加前先检查重叠和重试。

### 练习一：启动与就绪

提供最小部署说明，写清依赖、环境配置、启动顺序和健康检查。模拟数据库或模型不可用，区分进程活着、服务就绪及受限模式，接口不假装完整功能可用。

## 7. 面试问答与迁移

readiness 与 liveness 有什么区别？模型慢时如何避免重试雪崩？

**参考回答：**

1. readiness决定当前实例是否接流量；liveness判断实例是否已进入需要重启才能恢复的故障，不只是检查进程号存在。外部模型短暂不可用时重启本地实例通常无助，还可能放大故障；探针应对应实际故障和恢复动作，慢启动可另用启动探针。
2. 先观察慢在排队、连接还是模型执行，再限制总截止时间、并发和队列。仅把超时调大可能积压更多请求；每层各重试三次还可能成倍放大上游调用。只在剩余预算允许时有限退避重试，写操作同时满足幂等约定。
3. 降级要保留用户任务与权限，例如返回可核对原文并说明生成暂不可用。缓存需要租户、版本和业务日期等正确边界；熔断与资源隔离要有触发、恢复和验证条件，不能作为无需测量的工具清单。

**换条件自测：** 注入慢模型与上游失败，记录排队量、尾延迟、超时与恢复；确认系统没有无限排队，也没有因为共享上游故障反复重启所有实例。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 服务启动后，怎样知道它哪里慢、什么失败、重启后能否恢复？

**一条主线：**

```text
镜像、配置与持久数据 → 就绪与降级、日志指标追踪、恢复演练 → 可解释、可限制、可恢复的服务
```

**三个关键词：** 就绪、观测、恢复——就绪决定实例是否接流量，观测把请求拆到阶段与证据，恢复演练证明备份和状态真的可用。

**最容易错：**
- 把 liveness 和 readiness 混成一个检查；依赖变慢时重启进程只会放大故障。
- health 返回 200 就认为所有接口可用；降级要按路由声明能力，不能把 `degraded` 当完整回答。
- 把并行 span 的耗时直接相加当端到端延迟；平均值还会掩盖尾部请求。
- 备份文件存在就认为能恢复；必须在隔离环境实际恢复并核对数据。

**与前后章：** 上一章留下可恢复的状态与动作记录；本章部署并验证诊断与恢复；下一章接入概率输出的模型，沿用同一观测与失败边界。

**学完应能：**
- 区分存活、就绪与降级，为数据库和模型故障写出明确响应。
- 用 `request_id`/`task_id` 把入口、检索、模型与持久化串起来定位一次超时。
- 拆分排队、检索、模型、工具与写入耗时，说明哪些区间重叠、不能直接相加。
- 在隔离环境完成一次备份恢复与重启演练，记录可核对的数据与未完成任务。

### 8.2 日常工作注意事项

- 数据库和索引放在明确的持久存储中，重启或重建容器后核对数据；不要把容器临时目录当作备份。
- 健康检查要能支持所需的存活与就绪判断，依赖失败时观察真实请求行为，而不只看进程是否存在。
- 发布前在隔离环境验证恢复与回退，尤其区分代码回滚与数据迁移恢复；日志按请求标识串起故障过程。
