能把第16章的订单服务放入可复现环境，并用一次请求记录定位故障、用一次重启验证恢复。前置：第13–16章。

**本章从这里开始：** 服务能启动，不代表用户任务能完成。数据库不可用、外部接收方超时或动作结果未知时，接口要说明发生了什么，运维记录也要能找到同一条任务。

## 2. 基础知识讲解

### 2.1 部署包括程序、配置和持久数据

镜像封装程序与运行依赖，环境变量提供部署差异，数据库和索引放在明确持久存储中。容器重建后，临时目录里的数据会消失；多worker也不会共享各自的内存字典。

启动顺序、端口、资源上限和依赖版本都属于运行条件。先部署最小API与必要数据库，再按需要增加模型、队列或追踪组件；每增加一个依赖，也增加一类故障。

**滚动发布与优雅停机：**
- 滚动发布以就绪检查为门控逐步替换实例，并限制同时不可用与额外创建的实例数；发现问题应停止扩大发布。
- 回滚应用前确认新旧代码能读同一数据库结构，采用先扩展后收缩的迁移；镜像回滚不会撤销已执行的数据迁移。
- 优雅停机先停止接新流量并摘除就绪，再让在途请求在宽限期内完成，最后关闭连接与持久资源。
- 宽限期内未完成的写动作不能假装成功；客户端重试仍须使用原幂等键，强制退出后由恢复流程核对结果。

#### 案例推进：进程、共享状态和任务不是同一层

进程存活只说明容器还在运行；共享数据库保存跨请求事实；任务记录说明一笔订单走到哪一步。增加worker可能提高并发，却不能修复错误的状态存储。

### 2.2 存活、就绪和降级回答不同问题

存活检查判断进程是否需要重启；就绪检查判断实例当前能否接收某类流量。数据库不可用时，依赖它的任务接口应拒绝服务；外部接收方不可用时，读任务与读来源可能仍可用。

降级必须写清剩余能力，不能让客户端把“只能搜索”误读为“可以完整回答”。外部依赖短暂变慢时反复重启进程，通常不能修复依赖，反而会放大负载。

**startup把慢启动与运行故障分开：**
- startup探针给初始化、迁移和模型加载留时间；启动预算内失败才重启，避免慢启动被liveness误杀。
- liveness只应发现本进程无法自行恢复的故障，例如死锁；数据库或外部接收方短暂不可用不应触发本地重启。
- startup通过不等于依赖就绪，readiness仍要决定是否接流量；持续探针失败还需受重启次数与退避策略约束。

#### 案例推进：把能力声明落到订单接口

就绪响应可以声明`create_order`不可用，但`read_task`仍可用。路由级反馈也要一致：任务接口返回明确的503或冲突，而不是200后拿旧缓存冒充新结果。

```python
# study-example: S17C
def endpoint(capabilities):
    if "read_task" in capabilities:
        return 200, {"items": ["T1"]}
    return 503, {"error": "unavailable", "fallback": "/read_task"}

assert endpoint(["read_task"])[0] == 200
assert endpoint([])[1]["fallback"] == "/read_task"
```

全局就绪通过只说明实例可以接一部分流量，不代表每个路由都具备完整能力；客户端必须根据具体路由的状态与错误体决定下一步。

### 2.3 日志、指标和追踪互相补充

日志记录离散事件，指标聚合错误率与延迟，trace连接一次请求的各个阶段。用`request_id`、`task_id`和`action_id`串起入口、数据库、外部调用和恢复，避免只凭时间猜根因。

记录阶段、耗时、错误类别、服务版本和结果状态；密钥、完整凭据与不必要的用户原文不要进入日志。并行span可能重叠，重试会增加等待，不能把所有span耗时直接相加。

**先定义SLI、SLO与error budget：**
- SLI是直接测量，例如有效订单请求中在约定时限内成功的比例；健康检查和后台任务不要混进业务分母。
- SLO给测量设目标与窗口，如30天内99.9%成功；error budget就是`1-SLO`允许的失败份额，消耗过快应优先止损而非继续加功能。
- p95表示95%样本不超过该延迟，p99观察尾部；均值会被少量极慢请求拉高，也会掩盖大多数用户体验，样本少时尾部分位数不稳定。
- RED按服务的请求率、错误率、时长观察接口；USE按资源的利用率、饱和度和错误观察CPU、内存、连接池，二者不能替代订单业务成功率。

**关联ID与指标标签使用不同策略：**
- `request_id`串一次调用，`task_id`串业务生命周期，`action_id`核对外部效果；日志和trace保留它们以便逐层关联。
- 指标标签只使用路由模板、状态类别和服务版本等低基数值；用户ID、动作ID、完整URL或原始错误文本会让指标基数爆炸。
- 日志与trace也要限制敏感正文、token和凭据，必要时脱敏、采样或缩短保留期；关联能力不能以泄露租户数据为代价。

#### 案例推进：从“订单慢”走到具体阶段

先看同版本请求的p95和错误率，再用一个慢请求的trace区分排队、数据库和外部等待，最后从日志查该阶段的状态。没有样本数、负载和版本，单次快慢都不能说明系统容量。

### 2.4 可靠性措施要有触发和恢复条件

超时限制单次等待，限流限制接收压力，有限重试只处理可重试错误，熔断停止持续访问坏依赖，降级保留部分能力。写操作重试还必须满足第16章的幂等约定。

备份存在不等于能恢复。演练应在隔离环境还原已知数据，重启未完成任务，再核对任务状态与外部效果数。代码回滚、数据库迁移回退和数据恢复是三件事，要分别验证。

**用RPO与RTO定义恢复目标：**
- RPO是可接受的数据丢失时间范围，例如15分钟；它决定备份频率以及是否需要日志备份和时间点恢复。
- RTO是故障后恢复服务的目标时长，包含检测、决策、还原、校验与切换，不只是复制备份文件。
- 演练测量实际RPO/RTO并保留证据；还原后还要核对第16章动作账本与外部效果，数据完整不等于业务一致。

#### 案例推进：用同一笔订单验证恢复

记录T1提交前的效果数，制造提交后丢回执，重启服务并用原动作键恢复。验收看的是T1仍只有一条效果、任务最终一致且请求记录可串起来，不只是容器重新变绿。

## 3. 原理讲解与推导

### 3.1 故障传播从共享依赖进入请求队列

数据库或外部接收方变慢时，在途请求等待更久，新请求继续进入队列，重试又增加上游调用。结果是延迟和错误率同时上升，甚至拖垮原本可用的只读接口。

因此先限制并发、队列和总预算，再按错误类别决定重试或降级。观测让人看到故障从哪个阶段进入，恢复演练验证状态是否收敛；两者共同把“进程还活着”变成“任务行为可解释”。

**重试风暴需要跨层预算：**
- 若三层都设置最多3次尝试，最坏情况会放大为27次外部尝试；依赖越慢，重试越会进一步延长等待并制造拥塞。
- 只对临时错误做有限指数退避与随机抖动，遵守`Retry-After`、总截止时间和最大尝试次数；写操作还要带稳定幂等键。
- 熔断在 closed/open/half-open 间转换：持续失败后停止调用，半开只放少量探测，成功达到门槛再恢复。
- 限流、并发限制和队列上限提供背压；预算由调用链共享，不能每一层各自批准一套重试。

## 4. 示例与逐步走查

### 4.1 第一步：用参考切片验证部署顺序

按[容器与累计验收](../project-practice/从实验到项目交付.md#独立部署和累计验收)先初始化数据库，再启动服务。下面命令启动仓库现有的DocPilot参考切片，用来验证工具链与部署顺序；它不是第16章订单服务，也不能作为订单任务的验收证据。

```powershell
docker compose -f practice/integration_labs/compose.yml config --quiet
docker compose -f practice/integration_labs/compose.yml up -d
Invoke-RestMethod "http://127.0.0.1:8000/health"
```

`config --quiet`只说明Compose配置可解析；`/health`返回200也只说明HTTP进程可响应。继续重启容器并重查同一文档或答案记录，才能证明对应持久数据没有随进程丢失；DocPilot参考切片没有订单T1，不能拿它验证订单任务。

### 4.2 第二步：让就绪与降级返回具体能力

```python
# study-example: S17B
def service_status(database_ok, receiver_ok):
    if not database_ok:
        return 503, {"status": "not_ready", "reason": "database"}
    if not receiver_ok:
        return 200, {"status": "degraded", "capabilities": ["read_task"]}
    return 200, {"status": "ready", "capabilities": ["create_order", "read_task"]}

assert service_status(True, True)[0] == 200
assert service_status(False, True)[0] == 503
code, body = service_status(True, False)
assert code == 200 and body["status"] == "degraded"
assert "create_order" not in body["capabilities"]
```

这是状态契约探针，不是已部署服务的健康检查。实际路由必须使用同一能力判断：接收方不可用时可以读任务，但不能创建依赖外部写入的订单，也不能返回伪造的完整结果。

### 4.3 第三步：沿一条记录观察正常与故障

```json
{"request_id":"req-17","task_id":"T1","action_id":"T1:v1","stages":[{"name":"database","status":"ok","elapsed_ms":4},{"name":"receiver","status":"timeout","elapsed_ms":300}],"task_status":"executing","effect_count":1}
```

正常路径记录数据库、接收方和回执写入；故障路径保留超时阶段与`executing`，不把未知结果改成失败。恢复后追加对账阶段和最终回执，并确认`effect_count`仍为1。

排查时先按`request_id`找入口，再按`task_id`关联状态，最后按`action_id`核对接收方。trace中的并行阶段用时间区间判断重叠，不用简单求和冒充端到端延迟。

## 7. 面试问答与迁移

**问：liveness和readiness应该检查同一个依赖吗？** 不应机械相同。liveness应对应需要重启的故障，readiness描述当前接流量的条件；外部接收方短暂不可用时重启本地进程通常无助。

**问：外部接收方慢时怎样避免重试雪崩？** 先限制队列、并发和总截止时间，只在剩余预算允许时对临时错误做有限退避；写操作还必须满足幂等约定，不能每层各重试三次。

**问：降级返回搜索结果是成功吗？** 对搜索路由可以是成功，对完整回答路由必须明确能力缺失。要按路由验证状态码、错误体和客户端提示，不能用一个全局200掩盖部分功能不可用。

## 8. 本章小结与参考

- 部署交付的是程序、配置、依赖和持久数据的组合，不只是镜像能构建。
- 存活、就绪和路由降级分别说明进程、接流量条件和实际可用能力。
- 日志、指标和trace用共同标识把现象定位到阶段，耗时要注意重叠与重试。
- 超时、限流、熔断和重试都要有触发、预算与恢复条件。
- 恢复验收必须核对任务和外部效果，不能只看备份文件或进程重新启动。
