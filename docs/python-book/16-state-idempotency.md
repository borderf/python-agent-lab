# 第16章　数据库、任务状态、幂等与审批

[上一章](15-fastapi.md) · [全书目录](README.md) · [下一章](17-deployment.md)

## 1. 学习目标与前置知识

把持久化、图状态和业务效果区分开。前置：第8、11、15章。

## 2. 基础知识讲解

数据库保存任务、状态转换和业务动作，缓存不应成为唯一可靠记录。事务提供特定数据库范围的一致性，不能自动覆盖远程工具。

task_id 标识业务任务，图执行标识用于加载对应图状态；服务端校验二者与身份关系。failed、cancelled、waiting_approval 等状态要有明确转换和可重试条件。

写动作使用审批绑定、载荷版本/哈希、动作ID和幂等账本；恢复时先确认实际业务效果。Redis 锁/缓存有 TTL、并发和失败语义，不直接等于业务一次执行保证。

## 3. 原理讲解与推导

请求至少一次到达与业务效果只发生一次是两个层次。通过持久化动作、幂等业务接口、事务/对账缩小失败窗口，而不是依赖进程内标志。

### 项目化展开

#### 任务状态和恢复

```text
queued → running → waiting_approval → running → completed
             ↘ failed                 ↘ failed
waiting_approval → rejected
queued/running/waiting_approval → cancelled（按实际取消点记录）
```

失败重试记录新的 attempt；只在允许重试的错误上进行，保留历史。外部动作正在执行时，取消任务不能保证撤销业务效果，状态需对账而不能假定回滚。

区分四类数据：业务任务/状态转换、图 checkpoint、审批与动作记录、审计事件。Checkpoint 标识映射到当前用户有权访问的业务 task，不允许拿任意外部 thread_id 恢复他人任务。

#### 一个受保护的模拟写操作

只在 W10 加入 submit_review：把确认后的审查报告提交到模拟业务服务。不做真实下单、供应商封禁或真实资金操作。

- 审批绑定 task_id、action_type、payload_hash/版本、审批人、有效期。
- 原载荷或身份范围变化时，旧审批无效。
- 执行点再次检查权限和审批，使用 action_id/幂等键。
- 重放、重复 resume 和重试通过持久化动作账本确认结果；对外服务也需要幂等处理。
- 外部写入已完成但本地未记成功时，先查询/对账；不能简单重试造成双写。
- 拒绝和取消都保留事件；模型输出“用户已同意”不能代替审批记录。

### 用故障窗口理解幂等

考虑四个时刻：记录动作意图、发送外部请求、外部完成、记录本地完成。任一间隙崩溃都可能导致本地与外部状态不一致。事务只覆盖其负责的存储；幂等键、外部结果查询和动作账本用于恢复时判定。

审批绑定的是具体动作与载荷版本，不是永久授予某Agent写权限。载荷改变、租户改变或审批过期后应重新确认。不同任务重复使用同一个幂等键也可能误抑制合法操作，因此键作用域要明确。

## 4. 示例与逐步走查

### 重复恢复案例

```json
{"task_id":"T1","action_id":"A1","payload_version":2,"approval":"approved","status":"pending"}
```

第一次调用外部模拟服务成功后进程崩溃；第二次恢复用相同action_id查到已完成结果，补记本地状态，而不是再新增一条业务记录。若payload_version变成3，版本2的审批不得继续使用。演练时断言外部效果数为1，并保存两次请求的审计记录。

## 5. 动手练习

在模拟业务服务实现审批后提交报告，注入“写入已成功但本地未记成功”的崩溃；重复恢复核对效果数。
