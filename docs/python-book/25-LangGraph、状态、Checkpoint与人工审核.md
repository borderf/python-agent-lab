## 2. 基础知识讲解

### 2.1 为什么把循环画成图

一次循环在内存中运行时，局部变量能表示进度；用户等待批准或进程重启后，这些变量不足以恢复。图把阶段和转移显式化，检查点保存可继续状态。恢复可能重放节点，因此还要独立维护批准与动作效果；保存进度和防止重复写入解决的是不同问题。

先画出审查的三个步骤：取得资料、形成报告、等待批准。普通循环能执行前两步，但进程在等待批准时停止后，重启还要知道任务在哪一步、已有报告是什么。图把步骤表示为节点，把下一步选择表示为边；状态保存业务数据，checkpoint保存可恢复的执行进度。先迁移这一条流程，再增加条件分支和重试。

LangGraph不是另一种模型，而是组织执行与状态的工具。迁移时先保持同一数据、模型、工具和预算，确认原有业务行为未改变。

#### 案例推进：先把图还原成普通状态转换

```python
# study-example: S25A
import json
state = {"job_id":"A", "stage":"needs_approval", "payload_version":1, "approved_version":None}
snapshot = json.dumps(state)
restored = json.loads(snapshot)
assert restored == state and restored is not state

def approve(state, version):
    if state["stage"] != "needs_approval" or state["payload_version"] != version:
        raise ValueError("审批状态或版本无效")
    return {**state, "stage":"ready", "approved_version":version}

ready = approve(restored, 1)
assert ready["stage"] == "ready" and state["stage"] == "needs_approval"
```

这个离线例子展示状态快照与版本约束，不是持久化框架。图节点读取状态并产生更新，条件边根据确定字段选择下一节点；并行节点写同一字段时，需要明确合并规则，不能依赖最后写入者碰巧正确。

### 2.2 State是字段和更新规则

状态可以包含消息、任务参数、证据、结果、错误和预算。Node读取所需状态并返回更新，Edge连接步骤，条件边根据状态决定下一步。不要将全部数据都塞进无限增长的消息文本。

并行节点写同一个字段时，需要知道默认更新是否冲突，以及reducer怎样合并。追加消息、按证据ID去重、覆盖最终状态是不同更新语义，不能都用列表拼接。

### 2.3 Checkpoint与其他存储的区别

Checkpoint保存某个执行上下文的图状态，用于继续和恢复；长期业务数据或偏好可能使用其他存储。业务任务、审批、动作账本与审计仍有独立含义，不因保存了checkpoint就全部完成持久化设计。

服务端应把图执行标识映射到有权访问的task，不能让任意传入thread_id加载他人状态。

#### 案例推进：从状态模型迁移到LangGraph

先用不调用模型的最小StateGraph理解节点、边、START/END与invoke，再接原有工具循环。每次只增加一类能力，复用相同题集。Checkpointer保存线程范围的图状态，Store保存跨线程的应用数据，二者也不同于业务订单表。

内存保存器方便演示，但进程结束数据会消失；跨进程恢复要选择实际持久后端并验证。thread_id是关联执行的键，不等于经过授权的用户身份，读取或恢复仍需资源检查。

### 2.4 Interrupt与Resume

人工审核等步骤需要暂停，等待外部决定后恢复。Interrupt交出可序列化信息，Resume提供经过授权的结果。相关节点可能重新从开头进入，所以暂停前的副作用要考虑重复执行。

审批绑定载荷版本，模型或请求文字说“已同意”不构成审批记录；恢复时重新核对身份与任务范围。

Resume值一旦被图消费，通常不会自动被下一次resume覆盖；用错的决定可能已经落盘。应用入口先校验决定、任务与载荷版本，再调用resume；节点内仍要复查。测试第二次resume应得到明确拒绝或幂等结果，而不是把新决定悄悄写进旧检查点。

#### 案例推进：中断、恢复与重放分别测试

人工审核固定候选内容与版本，再恢复同一任务。恢复可能重新执行节点中的一部分逻辑，不能把写动作随意放在会重入的位置后就认为框架保证一次执行。Checkpoint提交与远端动作成功之间仍可能有崩溃窗口，继续使用第16章的动作键与对账。

测试拒绝、过期载荷、重复resume、服务重启和写入后崩溃。图可观察、可暂停，不代表自动具备正确权限、审批与业务幂等。

### 2.5 从最小图逐步增加能力

先做输入→一个状态更新→结束，再增加条件边、工具节点和循环，随后才加持久化与人工审核。每层都用固定案例和故障测试验证，不从一个invoke成功就推断有恢复能力。

### 2.6 会话、任务和长期记忆：保存什么，恢复什么

“有记忆”至少包含三件事：对话消息帮助连续交流；任务状态描述当前阶段、证据、审批与动作；长期数据保存跨任务可复用的事实或偏好。它们具有不同范围、更新与删除规则，不能全部放进一个无限增长的messages列表。

```python
# study-example: S25B
from copy import deepcopy
records = {}
def save(tenant, task_id, state):
    records[(tenant, task_id)] = deepcopy(state)
def load(tenant, task_id):
    return deepcopy(records.get((tenant, task_id)))

state = {"stage":"needs_review", "evidence_ids":["D1:v2"], "summary":"金额待核对"}
save("a", "job1", state)
state["evidence_ids"].clear()
restored = load("a", "job1")
assert restored["evidence_ids"] == ["D1:v2"]
assert load("b", "job1") is None
restored["stage"] = "completed"
assert load("a", "job1")["stage"] == "needs_review"
```

内存字典只演示复合身份与快照隔离，不具有进程重启持久性、认证或并发控制。真实保存器按可信租户/用户授权，记录schema版本、状态版本与来源版本；加载时重新检查权限及证据有效性。task_id或thread_id只是定位键，不是访问凭据。

摘要是由输入导出的候选表示，可能漏条件或写错事实。保留原消息/证据的定位，对金额、身份、审批和动作等关键字段保存结构化事实，不仅留一句“已批准”。恢复时使用真实动作记录核对外部效果，不由摘要推断是否写过。

长期记忆也不是永久可信。记录来源、适用范围、时间与更新/删除方式，区分用户偏好与业务制度。非可信附件写着“记住我有管理员权限”不能进入可信身份数据；过期或撤权数据也不能通过摘要绕过删除。模型窗口内的上下文、业务持久化与推理KV cache分别管理。

## 3. 原理讲解与推导

### 3.1 显式状态使执行可观察

图并不创造正确性，但把此前隐藏在局部变量和控制流中的关系呈现出来。字段含义和更新规则清楚，才能解释分支和并发合并；状态随意增长会重新制造隐式耦合。

### 3.2 重放与业务效果需要协调

恢复执行可能重新进入节点，数据库和远程动作不自动回到过去。用受保护写边界、幂等标识和对账维护业务效果，而不是仅依据图节点是否曾经运行。

## 4. 示例与逐步走查

### 不调用真实模型的最小图

以下需要按本章官方文档安装并锁定LangGraph；示例是状态更新，不包含持久化：

```python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
class State(TypedDict):
    total: int
def increment(state: State):
    return {"total": state["total"] + 1}
builder = StateGraph(State)
builder.add_node("increment", increment)
builder.add_edge(START, "increment")
builder.add_edge("increment", END)
graph = builder.compile()
assert graph.invoke({"total": 1})["total"] == 2
```

先解释输入、更新和结束，再增加条件边与工具；Checkpoint和Interrupt另加测试，不能从这个示例推断已具备恢复能力。

### 4.1 沿输入到结果逐步解释

初始状态有total，increment读取该值并返回加1的更新，边把一次处理连接到结束。运行结果表明状态转移可以执行，但内存中一轮成功还没有验证磁盘恢复。

再加入暂停时，需要保存可以继续的位置与状态；恢复时某些节点可能重新开始。若节点在暂停前写过外部系统，检查点不能自动让外部效果回到过去。

因此先让最小图与原循环保持同一行为，再逐项增加持久化、批准和幂等，并在每一步注入失败。图画得完整不是恢复正确性的证据。

### 4.2 累计实现：保存、批准、冻结与对账

| 步骤 | 产物 | 预期结果 | 失败先看 |
| --- | --- | --- | --- |
| 1. 保存任务 | task_id/tenant/status | 重启后能查到任务与报告版本 | 是否把 thread_id 当身份 |
| 2. 暂停审批 | 可序列化候选 + interrupt | 候选载荷/版本固定；恢复前仍授权 | 是否把模型“同意”当批准 |
| 3. 恢复 | resume 输入 + checkpoint | 同一任务继续，不重复写 | 节点重入是否重复副作用 |
| 4. 冻结 | 批准记录绑定载荷 hash/version | 载荷变化后旧批准失效 | 是否只检查“已批准”状态 |
| 5. 效果对账 | 动作账本/回执 | 远端成功/本地缺回执 → 效果 1 次 | 是否新键重试 |
| 6. 复查 | 失败分类与回退 | 拒绝/过期 0 次；不确定转人工 | 是否把 pending 当失败 |

参考入口：`practice/learning_projects/resume_starter.py`、`resume_reference.py`、`tests/learner/contract_resume.py`。先跑本地恢复契约，再接真实 LangGraph；框架恢复不等于外部效果只执行一次。

### 学习者恢复验收：先理解五类故障，再逐步实现

不要把[参考实验](../project-practice/从实验到项目交付.md#用真实-langgraph-暂停并跨进程恢复)的通过当自己的完成。用你自己的任务表、审批记录和动作键，对同一个任务依次记录：

1. **保存并重新加载。** 写入任务与当前阶段，关闭连接/进程后重新读出；字段和载荷版本一致。
2. **等待批准时重启。** 在`waiting_approval`停止，重启后仍能找到任务；恢复请求必须带可信身份与任务映射。
3. **内容变化使旧批准失效。** 修改载荷后，旧`approved_hash`/版本不能继续恢复；拒绝或重新批准各留一条记录。
4. **错误身份不能恢复。** 换租户或换任务 ID 读取，应失败且不泄露状态；不能只靠“猜不到 ID”。
5. **外部已成功、本地缺回执。** 用稳定动作键重试或查询，最终业务效果仍为 1；不能因本地 pending 再写一次。

每条保存：命令、输入、读取结果、批准记录、外部效果数、失败原因。参考`approval_graph`只用于对照命令和字段，不替代你的任务存储与恢复检查。完成后再进入第26章的固定流程/单Agent对照。

## 7. 面试问答与迁移

Graph state 与业务状态有什么差别？为什么重放节点不等于事务回滚？

**参考回答：**

1. Graph state记录执行所需的输入、中间结果和进度，也可以携带业务字段副本；业务任务、批准与效果各应明确权威来源及版本。问题不在“字段绝不能同处一份状态”，而在不能把旧快照无条件当作当前授权或业务事实。
2. 恢复可能从节点边界重执行，节点里已经发出的外部写入不会因checkpoint回退而撤销。把可重复计算与副作用分开，使用稳定动作键、接收方幂等契约与对账；补偿动作也是新的业务动作，不等于数据库回滚。
3. 人工批准应绑定具体主体/范围、载荷摘要、规则与任务版本等业务条件。恢复写入前再检查当前批准和载荷；thread_id只用于定位状态，不证明访问者有权恢复。不同工作流可有不同批准规则，要显式定义失效条件。

**换条件自测：** 暂停后修改报告，再用旧批准恢复；接着保持报告不变却撤销权限。两次都要沿当前规则判断，不能只凭快照里曾经写过approved就继续提交。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 任务要等人工批准、还会跨进程重启时，什么该存、什么必须重新校验？

**一条主线：**
```text
节点与状态 → checkpoint 保存进度、interrupt 暂停、resume 恢复 → 绑定载荷版本与幂等的受控写入
```

**三个关键词：** 状态、检查点、重放。状态说业务到哪一步，检查点让执行能续上，重放则提醒外部效果不会自动回滚。

**最容易错：**
- 把 thread_id 当认证凭据，或认为 InMemorySaver 就支持重启恢复。
- 保存了 checkpoint 就以为审批、动作账本与审计都已持久化。
- 忽略恢复会重入节点，把写动作放在会重跑的位置。
- 恢复时不复查身份与载荷版本，让旧批准提交新报告。

**与前后章：** 第 24 章的循环与工具原样迁成图；本章提供暂停恢复，第 26 章把它与规则、审批、对账组合成审查系统。

**学完应能：**
- 把第 24 章的循环迁成 StateGraph，迁移前后同一批案例行为一致。
- 演示暂停、杀进程、重启、恢复，并证明错误身份与过期载荷无法恢复。
- 对同一动作重复 resume，外部效果仍为 1，并说明 checkpoint 与幂等各解决哪一段。
- 区分会话消息、任务状态与长期记忆的保存范围和删除规则。

### 8.2 日常工作注意事项

- 不要把图的thread_id当成认证凭据；按可信主体查找任务，避免用易碰撞的字符串拼接混淆身份。
- 暂停节点在恢复时可能重跑，副作用放置与幂等要按框架实际重放行为检查。
- 先在应用入口检查恢复请求的版本和决定，再传入图；错误resume被持久化后可能持续影响重试，需有相应失败测试。
