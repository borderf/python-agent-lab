# 第27章　MCP 与跨系统工具边界

[上一章](26-项目实战二：ProcureAgent审查系统.md) · [全书目录](教材目录.md) · [下一章](28-Multi-Agent的分工、并行与合并.md)

## 1. 学习目标与前置知识

理解协议层、编排层和业务后端分工。前置：第14、16、24章。

**承接与本章主线：** 仅在跨进程共享工具需要下标准化发现和调用，保留原有授权与业务契约；协议本身不证明工具安全。

**本章从这里开始：** 同一项查供应商能力要供多个AI应用使用。MCP让交互方式有共同协议，但不会替业务服务决定谁能查哪份数据。

## 2. 基础知识讲解

### 2.1 先区分模型、工具与协议

多个应用需要相同查询能力时，各写一套工具描述和通信方式会产生重复适配。MCP为发现和调用提供共同交互，但不会替代当前用户的授权。学习时先把已有可信工具放到协议边界后面，比较本地与跨进程行为，确认变化的是交互方式而不是业务规则。

同一个只读政策工具，起初可以由本地函数调用；另一个进程也想使用时，就需要约定怎样发现工具、发送参数和读取结果。MCP提供这类交互协议：客户端连接服务端，发现可用能力，再按契约调用。先把已有工具接上这条连接，再区分模型选择、协议传输与业务授权分别由谁负责。

已有REST接口可以继续承载业务，MCP Server包装共享函数或业务接口；本地函数仍可保留本地调用方式。先明确需要跨什么边界，再决定是否增加协议层。

### 2.2 Host、Client与Server分别做什么

Host组织模型应用与用户交互，Client维护与某个Server的协议联系，Server提供受控能力。连接、能力协商、发现、调用、结果与错误需要按实际协议/SDK版本处理；不能只抄一条JSON就认为完整会话已建立。

传输方式影响部署、认证和资源管理，选择当前SDK支持的方式并记录版本。连接断开、Server不可用与调用参数错误应保留不同分类。

#### 案例推进：把三个层次放在一条链路上

```text
模型提出工具意图
    ↓ 应用校验与选择
Host中的Client → 协议交互 → MCP Server
                              ↓ 参数、身份与资源授权
                         原有业务函数
```

Host是组织AI应用与连接的宿主，Client是与服务交互的组件，Server提供能力。Tools用于可调用能力，Resources提供可读取上下文，Prompts提供模板等交互入口；是否支持以及怎样协商，按选择的协议版本与SDK核对。MCP不规定模型怎样思考，也不等同Agent Loop。

### 2.3 认识Tools、Resources与Prompts

Tools描述可调用操作及输入Schema，Resources提供应用可读取的上下文资源，Prompts提供可发现的交互模板等能力。它们不是同一种动作，公开范围与调用方式都应按应用需求设计。

工具说明服务于发现和选择，Schema约束结构；身份、权限、业务日期和操作预算来自可信上下文。Server不能信任模型自报tenant_id或role。

### 2.4 为已有工具加适配

先选两个只读工具，复用原函数，转换输入、输出与错误。让同一组合法、非法与越权案例分别走本地和MCP路径，保证协议变化不改变业务规则。不要在Server重新维护一份金额或采购政策逻辑。

#### 案例推进：先验证适配没有改变业务语义

```python
# study-example: S27A
def local_lookup(project_id, *, tenant):
    records = {"P1":{"tenant":"a", "name":"虚构项目"}}
    item = records[project_id]
    if item["tenant"] != tenant:
        raise PermissionError("无权访问")
    return {"project_id":project_id, "name":item["name"]}

def adapter(arguments, trusted_tenant):
    if set(arguments) != {"project_id"}:
        raise ValueError("参数不符合Schema")
    return local_lookup(arguments["project_id"], tenant=trusted_tenant)

assert adapter({"project_id":"P1"}, "a")["name"] == "虚构项目"
```

这是业务适配器演示，不是MCP线协议或完整服务实现。真实Server的处理器可调用相同边界；租户来自可信会话，不来自模型可以改写的arguments。工具发现的Schema不能取代服务端验证，也不表示每个工具都应暴露给每个用户。

### 2.5 调用结束与故障清理

Client负责关闭连接，Server负责本次操作的资源。超时可能意味着等待终止，不必然意味着业务动作没发生；写操作仍需审批与幂等。工具版本或Schema变化后要做兼容检查，不让模型旧缓存的能力描述继续误导执行。

#### 案例推进：协议集成需要自己的失败检查

本地stdio与远程HTTP有不同部署、凭据及生命周期要求。按实际SDK实现发现、调用、结果转换、取消和关闭，记录所选协议与依赖版本。先让本地与协议适配器通过同一组业务案例，再增加发现失败、断连、超时和过大结果等特有检查。

SDK可能处理底层消息与协商，但应用仍负责允许集合、身份和结果用途。不要把旧版本示例字段与新协议混搭，也不要把普通JSON字典示例说成完整MCP实现。

## 3. 原理讲解与推导

### 3.1 协议标准化的是交互，不是业务语义

两台服务都支持某协议，不说明它们的身份、错误、数据时效和副作用完全相同。适配时必须把这些语义显式映射，不能只把参数换个JSON外壳。

### 3.2 授权应在持有资源的一侧落实

客户端检查有助于提前拒绝，但Server面对可访问数据和真实操作，需要依据可信身份再次判断。把权限寄托在工具description或模型遵循提示上，无法形成可靠边界。

## 4. 示例与逐步走查

### 工具发现与输入契约走查

```json
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}
```

某个工具描述可包含：

```json
{"name":"get_project","description":"查询当前身份可访问的虚构项目","inputSchema":{"type":"object","properties":{"project_id":{"type":"string"}},"required":["project_id"],"additionalProperties":false}}
```

这不是完整会话或授权流程。实际Client须先按协议与SDK完成连接/协商，再发现、调用和处理结果；Server用可信身份重新判定project_id权限。

### 4.1 沿输入到结果逐步解释

Client先发tools/list发现可用工具及其输入Schema，应用据此知道应提供哪些字段。随后一次get_project调用仍需经过服务端的主体与资源权限检查。

Schema中的project_id说明参数形状，不说明调用者拥有项目。description说明用途，也不能授予权限。因此将原工具接到协议后，应让相同正常、非法和越权案例分别走本地与跨进程路径。

若协议路径允许原本拒绝的数据，问题在适配或身份传递，不在模型是否理解了工具说明。

## 7. 面试问答与迁移

MCP 与 REST/Tool Calling/LangGraph 分别解决什么？什么时候保持本地调用更合适？

**参考回答：**

1. MCP约定客户端与服务端如何发现和交换工具、资源等能力；REST是设计HTTP资源接口的风格；Tool Calling表示模型产生工具请求；LangGraph组织应用状态与流程。它们可组合：MCP服务端内部调用REST接口，图节点经执行器调用MCP工具，职责没有因此合并。
2. 同进程且没有互通需求时，本地函数通常更简单。跨客户端共享、独立部署或需要协议互通时，再比较发现、序列化、认证、版本与故障代价；协议不能自动解决业务授权、幂等或执行隔离。

**换条件自测：** 工具清单允许发现某函数，是否就有权读取任何资源？用合法Schema但另一租户的资源ID请求服务端，检查授权拒绝，并确认错误响应不泄漏目标内容。

## 8. 本章小结与参考

### 8.1 主要知识点总结

- MCP约定客户端与服务端怎样发现并调用能力，业务函数仍有自己的契约。
- 工具、资源与提示承担不同交互角色，传输和连接生命周期需要明确。
- 协议适配层将外部结果转回内部结构，错误与关闭都应可观察。
- 跨进程共享有真实需求时引入协议，并复用本地业务行为检查。

### 8.2 日常工作注意事项

- stdio服务的标准输出留给协议，调试信息走标准错误等合适通道；普通print可能破坏消息传输。
- 连接建立后，资源端仍按可信身份授权；不要将本机固定教学身份原样用于多用户服务。
- 锁定并记录实际SDK主版本，升级时检查发现、参数、结构化返回与断开行为，避免混用不同版本示例。
