## 1. 学习目标与前置知识

分清静态描述、运行时校验与业务不变量。前置：第4、6–8章。

**本章从这里开始：** 现在同一个订单可能来自JSON、数据库、HTTP或模型。怎样既让编辑器帮助检查代码，又在运行时拒绝真实坏输入？本章把几种“类型”工具按责任分开。

## 2. 基础知识讲解

### 2.1 类型标注描述调用契约

在参数后写类型、箭头后写返回类型，向读者和工具表达预期。`def total(values: list[int]) -> int`说明输入是整数列表，输出是整数；它本身不会在每次调用时检查全部元素。

Union或`|`表示可选类型，`str | None`说明可能没有结果，调用方应先处理None。Literal表达有限状态，例如paid/pending/cancelled。类型别名给重复结构命名，但不能仅靠别名建立运行时业务校验。

#### 案例推进：标注先提供关系，不提供运行时保证

```python
# study-example: S09A
from typing import TypedDict, Literal
class Order(TypedDict):
    id: str
    amount_cents: int
    status: Literal["paid", "pending", "cancelled"]

def amount(order: Order) -> int:
    return order["amount_cents"]

assert amount({"id":"A", "amount_cents":10, "status":"paid"}) == 10
raw = {"id":"A", "amount_cents":"10", "status":"paid"}
assert amount(raw) == "10"  # 静态工具应提示；运行时并未自动阻止
```

最后一次调用是有意的反例。TypedDict描述字段，注解服务于读者和静态工具，Python不会因此自动验证外部字典。把Any到处传播会让静态工具放弃重要检查；object则要求先确认类型或能力才能进行特定操作。

### 2.2 容器形状与读写能力

list[int]表达同类元素，tuple[str, int]可表达固定位置结构，dict[str, int]表达键值范围。TypedDict描述不同键各自的字段类型和必需性，适合已有JSON式字典；它不是自动验证外部数据的构造器。

Mapping/Sequence表达较抽象的读取能力，适合函数并不需要具体可变容器时。Callable表达可调用接口。Any放宽检查，而object要求先确认能力或类型后才能进行特定操作；大量Any可能让标注存在却失去实际诊断价值。

### 2.3 用泛型表达类型之间的关系

如果函数输入与输出共享某个未知类型，仅写object会丢掉这种关系。TypeVar或相应版本的类型参数语法，可以表示“返回的类型和输入对应”。应先有真实复用点，再引入泛型，不为每个简单函数创建复杂抽象。

Protocol表达对象需要提供的方法形状，调用方可以接受无需显式继承的实现。接口相符仍不保证未知ID、错误、顺序、资源和权限的语义相同，因此需要行为测试。

#### 案例推进：Protocol把协作能力变成契约

```python
# study-example: S09B
from typing import Protocol
class Names(Protocol):
    def get(self, key: str) -> str | None: ...
class MemoryNames:
    def __init__(self):
        self.values = {"A": "Alice"}
    def get(self, key: str) -> str | None:
        return self.values.get(key)
def greet(names: Names, key: str) -> str:
    name = names.get(key)
    return "未知用户" if name is None else f"你好，{name}"
assert greet(MemoryNames(), "A") == "你好，Alice"
assert greet(MemoryNames(), "missing") == "未知用户"
```

实现无需继承Protocol，形状符合即可接受静态检查。None分支完成收窄，后面的表达式才把name当str。返回None还是抛异常属于语义，不是相同签名就自动等价；换成文件实现时用相同行为案例核验。

#### 案例推进：泛型保留输入与输出之间的类型关系

```python
# study-example: S09C
from typing import TypeVar
from collections.abc import Sequence
T = TypeVar("T")
def first(items: Sequence[T]) -> T | None:
    return items[0] if items else None
assert first([1, 2]) == 1
assert first(["A", "B"]) == "A"
assert first([]) is None
```

T不是“什么都不管”的Any，它把调用中的元素类型与返回类型关联。只读需求用Sequence表达，不要求一定传list；可变列表通常是不变的，因为允许把整数列表当成任意可写列表会让其他代码写入字符串。泛型先服务于真实关系，不为简单代码堆类型参数。

### 2.4 把外部输入变成可信的内部模型

Pydantic模型声明字段、范围、状态、缺失与额外字段策略，并在验证时执行检查。默认转换和严格模式不同：接口若要求金额必须是整数，就不能默默接受字符串或bool。校验成功后明确使用模型对象还是导出普通字典。

外部DTO与领域对象可以不同。DTO负责承接协议格式，领域模型负责金额单位、相等、生命周期等内部规则；将HTTP Response直接传入所有业务函数，会让边界越来越模糊。

#### 案例推进：运行时边界需要真正的验证器

下面是Pydantic v2的框架示例，当前项目未安装时先阅读并在该阶段添加依赖，不将它算作标准库离线运行例子。

```python
# framework-example: F09
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, ValidationError
class OrderModel(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    id: str = Field(min_length=1)
    amount_cents: int = Field(ge=0)
    status: Literal["paid", "pending", "cancelled"]

valid = OrderModel.model_validate({"id":"A", "amount_cents":10, "status":"paid"})
assert valid.amount_cents == 10
for bad in (True, "10", -1):
    try:
        OrderModel.model_validate({"id":"A", "amount_cents":bad, "status":"paid"})
    except ValidationError:
        pass
    else:
        raise AssertionError("入口应拒绝非法金额")
```

strict控制转换宽松程度，extra控制额外字段，Field表达约束；id只检查长度还不够，去空白后非空等业务规则仍需补入。严格模式对不同类型、Python对象与JSON入口有差异，按实际类型查转换表，而非笼统理解为“所有情况完全不转换”。

### 2.5 静态检查与运行时测试配合

故意拼错字段、漏处理None或返回错误类型，可以观察静态检查器的提示；故意从文件送入错误结构，则观察运行时验证。两种结果分别记录。不要仅用type ignore或Any让诊断消失，要先理解工具在指出什么问题。

### 2.6 缺失、None和只读接口：把类型契约讲到字段级

“字段可以不传”和“字段必须存在但值可以为空”是不同契约。PATCH接口、模型输出和抽取结果都可能需要区分它们：缺失可能表示不更新，None可能表示显式清除，0则是一个实际数值。

```python
# study-example: S09D
from typing import NotRequired, TypedDict
class Change(TypedDict):
    amount_cents: int | None
    note: NotRequired[str]

one: Change = {"amount_cents": None}
two: Change = {"amount_cents": 0, "note": ""}
assert "note" not in one and two["note"] == ""
assert one["amount_cents"] is None and two["amount_cents"] == 0
```

NotRequired描述键的存在性，`int | None`描述值的类型集合。TypedDict仍不执行运行时校验；从JSON收到缺失amount_cents时，必须在入口检查，而不是认为注解保证它存在。使用total=False时也要说明哪些键通过Required仍为必需。

类型收窄则把“不确定对象”逐步变为可操作的类型：先确认容器，再确认每个字段及其范围。cast只告诉检查器如何看待对象，不会进行转换或校验。

```python
# study-example: S09E
from collections.abc import Mapping
def read_amount(raw: object) -> int:
    if not isinstance(raw, Mapping) or "amount_cents" not in raw:
        raise ValueError("缺少amount_cents")
    value = raw["amount_cents"]
    if not isinstance(value, int) or isinstance(value, bool) or value < 0:
        raise ValueError("必须为非负整数分")
    return value
assert read_amount({"amount_cents": 0}) == 0
for bad in ({}, {"amount_cents": None}, {"amount_cents": True}, {"amount_cents": "10"}):
    try:
        read_amount(bad)
    except ValueError:
        pass
    else:
        raise AssertionError("非法输入不能通过")
```

Mapping表达这里仅需读取，不代表底层字典真的冻结。Sequence与list也有类似区别：能力接口缩小了函数可以依赖的操作，实际对象仍可能被其他拥有者修改。类型检查、所有权与运行时验证继续共同维护边界。

Python3.12还可以用`type Amount = int`声明别名，用新类型参数语法表达泛型；本书同时使用TypeVar写法以便阅读现有项目。别名不新建业务单位，`int`与`Amount`不会因此运行时不可混用。遇到新版本的注解求值与类型语法，先记录项目解释器，再查对应文档，不直接复制其他版本观察。

### 2.7 用带标签的联合处理不同结果

一个工具正常完成时会携带证据，超时时会给出等待时间。把所有字段都设为可选，会让调用方到处猜当前是哪种状态。先用两个 TypedDict 描述两种完整形状，再用 Literal 标签让类型检查器沿分支收窄。

```python
# study-example: S09F
from typing import Literal, TypedDict, assert_never

class Found(TypedDict):
    kind: Literal["found"]
    source_id: str

class TimedOut(TypedDict):
    kind: Literal["timeout"]
    seconds: int

def describe(result: Found | TimedOut) -> str:
    if result["kind"] == "found":
        return result["source_id"]
    if result["kind"] == "timeout":
        return f'等待 {result["seconds"]} 秒'
    assert_never(result)

assert describe({"kind": "found", "source_id": "v2"}) == "v2"
assert describe({"kind": "timeout", "seconds": 3}) == "等待 3 秒"
```

新增一种 forbidden 结果，把新类型加入联合但先不改分支，用类型检查器观察 assert_never 所在位置，再补处理路径。上面的两个断言只验证运行时已覆盖的两种输入；HTTP 解码得到的字典，仍需先检查字段和类型才能作为内部结果传入。

## 3. 原理讲解与推导

### 3.1 类型信息与程序执行是两个层次

注解提供可供分析的信息，普通函数执行仍按原来的名称、对象与操作规则进行。TypedDict运行时仍是dict，所以外部数据要经过独立验证。下面的错误标注实验用于观察这一边界，而不是推荐错误用法。

### 3.2 可替换性包含行为而不只是签名

两个实现都提供get(id)，其中一个返回None，另一个把缺失记录伪装成零金额，就不满足同一个业务契约。Protocol便于表达结构，测试与文档再补语义、错误和副作用。

### 3.3 严格校验也不是事实证明

Schema可以检查字段、类型和约定范围，但不能自动证明合同金额、身份授权或引用事实。先通过结构边界，再执行确定性规则和证据核对，层次不能颠倒。

#### 用对象模型解释类型标注与校验边界

形参注解不会改变调用时的对象绑定，也不会自动转换实参。普通int注解、TypedDict或Protocol主要给静态分析和工具提供信息；运行时验证取决于实际执行的代码或库。一个经校验的容器以后仍可能被修改，入口通过不代表对象永久满足规则。

```python
# study-example: S09Z
value = True
assert isinstance(value, int)
assert type(value) is bool
accepted_as_exact_integer = type(value) is int
assert accepted_as_exact_integer is False
```

bool是int的子类，所以isinstance适合接受继承关系，却可能不适合“数量字段只收实际整数、不收布尔”的契约。type(value) is int是该严格契约的选择，不是所有接口的通用规范。字段缺失、显式None、合法0分别建模，再做范围和业务验证，避免用or统一吞掉。

## 4. 示例与逐步走查

```python
# book-example: B09
from typing import Protocol
class Names(Protocol):
    def get(self, key: str) -> str | None: ...
class MemoryNames:
    def get(self, key: str) -> str | None:
        return {"A":"Alice"}.get(key)
def lookup(source: Names, key: str) -> str | None:
    return source.get(key)
assert lookup(MemoryNames(), "A") == "Alice"
assert lookup(MemoryNames(), "missing") is None
```

### 4.1 沿输入到结果逐步解释

lookup只依赖Names约定，不依赖MemoryNames内部字典。已知键返回文本，未知键返回None；调用方必须处理两种结果。换成文件实现时应保持该契约，而不是让业务层重新认识一种外部响应格式。
