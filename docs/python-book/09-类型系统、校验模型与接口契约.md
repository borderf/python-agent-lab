## 2. 基础知识讲解

### 2.1 注解描述调用关系，不改变执行

`def total(values: list[int]) -> int` 告诉读者和静态工具：预期收到整数列表并返回整数。解释器仍按实际对象执行，不会逐个拒绝字符串或 bool。`str | None` 表示可能是文本或没有值，调用方要先处理 `None`；`Literal[...]` 把状态限制为几个字面量。

TypedDict 描述字典的键和值类型，运行时仍是普通 dict。`Any` 会放弃重要检查，`object` 则要求先确认类型或能力。注解、静态检查和运行时验证分别解决说明、提前发现和不可信输入三个问题。

#### 案例推进：先让工具看见契约

把 `total([1, "2"])` 交给 mypy，会在运行前报告列表元素类型不匹配；直接执行则要等 `sum` 遇到字符串才抛 `TypeError`。修复后应保留诊断原文和退出码，不能仅靠 `Any` 或 `type: ignore` 让提示消失。

### 2.2 用 Protocol 表达可替换能力，用泛型保留关系

`Mapping`、`Sequence` 表达读取能力，不要求调用方拿到可变 list；`Callable` 表达可调用对象。`Protocol` 声明协作者需要的方法形状，实现无需显式继承。`@runtime_checkable` 也只检查所需成员是否存在，不检查完整签名、类型或业务语义；相同签名仍不保证未知 ID、异常、顺序和副作用一致。

`TypeVar` 或 3.12 的类型参数语法可表达“返回类型与输入元素类型对应”，例如 `first(Sequence[T]) -> T | None`。它不是 `Any`，但也不应为每个简单函数增加抽象。先有真实复用点，再引入泛型。

### 2.3 外部输入先收窄，再变成可信值

类型收窄是逐步确认：先确认是 Mapping，再确认字段存在，最后确认值是非负整数。`bool` 是 `int` 的子类，所以 `isinstance(True, int)` 为真；“只收实际整数”的金额契约要用 `type(value) is int`。`cast` 只改变检查器的看法，不转换或校验对象。

#### 案例推进：运行时逐层拒绝坏金额

```python
# study-example: S09E
from collections.abc import Mapping
def read_amount(raw: object) -> int:
    if not isinstance(raw, Mapping) or "amount_cents" not in raw:
        raise ValueError("缺少amount_cents")
    value = raw["amount_cents"]
    if type(value) is not int or value < 0:
        raise ValueError("必须为非负整数分")
    return value
assert read_amount({"amount_cents": 0}) == 0
for bad in ({}, {"amount_cents": None}, {"amount_cents": True}, {"amount_cents": "10"}):
    try:
        read_amount(bad)
    except ValueError:
        pass
    else:
        raise AssertionError("非法输入不能通过")
```

通过校验的字典以后仍可能被其他代码修改；入口通过不等于永久可信。需要封闭规则时，转成受控模型并限制公开修改方式。

### 2.4 Pydantic 把声明变成运行时验证

Pydantic v2 用字段类型、`Field` 约束和模型配置验证输入。`strict=True` 按所选类型严格拒绝不匹配值，`extra="forbid"` 拒绝额外字段；不要把它理解成所有 Python/JSON 入口都绝不转换，应按实际入口核对转换表。

模型验证也不能证明合同金额、身份权限或引用事实。结构检查之后仍要执行跨字段规则、授权和业务校验。

#### 案例推进：严格订单模型拒绝三类坏值

```python
# framework-example: F09
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, ValidationError
class OrderModel(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    id: str = Field(min_length=1)
    amount_cents: int = Field(ge=0)
    status: Literal["paid", "pending", "cancelled"]
    @classmethod
    def from_row(cls, row):
        model = cls.model_validate(row)
        if not model.id.strip():
            raise ValueError("id去空白后不能为空")
        return model
valid = OrderModel.from_row({"id": "A", "amount_cents": 1990, "status": "paid"})
assert valid.amount_cents == 1990
for bad in (True, "1990", -1):
    try:
        OrderModel.from_row({"id": "A", "amount_cents": bad, "status": "paid"})
    except ValidationError:
        pass
    else:
        raise AssertionError("入口应拒绝非法金额")
for row in ({"id": " ", "amount_cents": 1, "status": "paid"},
            {"id": "A", "amount_cents": 1, "status": "closed"},
            {"id": "A", "amount_cents": 1, "status": "paid", "extra": 1}):
    try:
        OrderModel.from_row(row)
    except (ValidationError, ValueError):
        pass
    else:
        raise AssertionError(row)
```

F09 是框架示例，由文本校验器检查语法；运行它需要项目已有 Pydantic v2 环境。本章不修改依赖文件，也不把它算作标准库离线示例。

#### 缺失、None 与零值是三种契约

“键可以不传”与“键必须存在但值可为 None”不同。`NotRequired` 描述键是否必须出现，`str | None` 描述值的类型；0 是实际数值，不能用 `or` 统一吞掉。

```python
# study-example: S09D
from typing import NotRequired, TypedDict
class Change(TypedDict):
    amount_cents: int | None
    note: NotRequired[str]
one: Change = {"amount_cents": None}
two: Change = {"amount_cents": 0, "note": ""}
assert "note" not in one and two["note"] == ""
assert one["amount_cents"] is None and two["amount_cents"] == 0
```

TypedDict 仍不执行验证；从 JSON 收到缺失 `amount_cents` 时，入口必须拒绝。

### 2.5 用联合类型与标签区分不同结果

查询结果常见为“找到订单”或“没有订单”。用 `Literal` 标签把两种字典形状组成联合类型，调用方先判断 `kind`，再访问对应字段，静态工具也能收窄可选成员。这比返回 `dict | None` 更明确，但运行时仍要由构造函数保证标签与字段一致。
```python
from typing import Literal, TypedDict
class Found(TypedDict):
    kind: Literal["found"]
    order_id: str
class Missing(TypedDict):
    kind: Literal["missing"]
LookupResult = Found | Missing
def lookup(rows, order_id) -> LookupResult:
    return {"kind": "found", "order_id": order_id} if any(row["id"] == order_id for row in rows) else {"kind": "missing"}
found = lookup([{"id": "A"}], "A")
missing = lookup([{"id": "A"}], "B")
if found["kind"] == "found": assert found["order_id"] == "A"
else: raise AssertionError("应找到A")
assert missing == {"kind": "missing"}
```
需要表达“值为真就说明它是某类型”时，可用 `TypeGuard` 声明类型收窄谓词；它同样只是给静态工具的承诺，谓词本身写错仍会误判。联合类型也不替代跨字段业务校验，例如找到订单不等于当前用户有权读取。

## 3. 原理讲解与推导

### 3.1 注解不改变对象绑定，所以运行时仍要验证

形参注解不会转换实参，也不会在调用时插入检查。类型信息主要给读者和静态工具；真正拒绝坏值的是函数体、验证器或框架执行的代码。TypedDict 构造后仍是 dict，因此注解存在不代表字段已经可信。

```python
# experiment: E18
from typing import TypedDict
def echo(value: int) -> int:
    return value
assert echo("text") == "text"  # type: ignore[arg-type]
class Record(TypedDict):
    count: int
record = Record(count="wrong")  # type: ignore[typeddict-item]
assert type(record) is dict and record["count"] == "wrong"
assert echo.__annotations__["return"] is int
```

这里的错误标注只用于观察边界，不是推荐写法。静态工具应直接报告普通调用中的错误，不需要先忽略再运行。

## 4. 示例与逐步走查

B09 给第8章的两行订单补齐输入、仓储和报告契约。输入仍是 A/B；输出仍是 2 单、已支付 1990 分。

### 4.1 输入：字段和状态写成类型

#### 案例推进：字段形状先写成声明

`OrderRow` 要求 id/user 为文本，金额为整数，状态为三个 Literal 之一，`paid_at` 可为文本或 None。它描述形状，构造时不自动验证。

### 4.2 边界：仓储只承诺按 ID 查询

#### 案例推进：未知 ID 与零金额分开表示

`OrderStore` 是 Protocol，内存实现按 ID 返回订单或 None。业务函数只依赖这个能力，不关心底层是字典、文件还是数据库；未知 ID 与零金额仍由返回值区分。

### 4.3 输出：报告字段固定为整数

#### 案例推进：2 单与 1990 分分别断言

`summarize` 只统计已支付订单，返回 `order_count` 和 `paid_amount_cents` 两个整数。结构、业务过滤和持久化正确性是三项独立证据。

```python
# book-example: B09
from typing import Literal, Protocol, TypedDict
Status = Literal["paid", "pending", "cancelled"]
class OrderRow(TypedDict):
    id: str
    user: str
    amount_cents: int
    status: Status
    paid_at: str | None
class Report(TypedDict):
    order_count: int
    paid_amount_cents: int
class OrderStore(Protocol):
    def get(self, order_id: str) -> OrderRow | None: ...
class MemoryStore:
    def __init__(self, rows): self.rows = {row["id"]: row for row in rows}
    def get(self, order_id: str) -> OrderRow | None: return self.rows.get(order_id)
def summarize(store: OrderStore) -> Report:
    orders = [store.get(order_id) for order_id in ("A", "B")]
    if any(order is None for order in orders):
        raise ValueError("订单不存在")
    return {"order_count": len(orders),
            "paid_amount_cents": sum(o["amount_cents"] for o in orders if o and o["status"] == "paid")}
rows: list[OrderRow] = [
    {"id": "A", "user": "Alice", "amount_cents": 1990, "status": "paid",
     "paid_at": "2026-11-04T10:00:00+08:00"},
    {"id": "B", "user": "Bob", "amount_cents": 1000, "status": "pending", "paid_at": None},
]
assert summarize(MemoryStore(rows)) == {"order_count": 2, "paid_amount_cents": 1990}
assert MemoryStore(rows).get("missing") is None
```

## 7. 面试问答与迁移

**问：Protocol 与继承接口有何区别？** Protocol 按所需成员做结构检查，不要求显式继承；ABC 在显式层次中限制抽象类实例化。两者都不证明业务语义，runtime_checkable 也不等于完整签名和行为验证。

**问：TypedDict、dataclass、Pydantic 能互相替代吗？** 不能。TypedDict 偏字典形状，dataclass 生成对象样板代码，Pydantic 提供运行时验证；可组合使用，但都不能单独证明授权和事实正确。

**问：类型正确为何仍可能破坏业务规则？** 合法整数金额仍可能单位错误，合法 ID 可能属于另一租户，合法日期也可能倒挂。结构、跨字段规则、授权和事实核对要分层。

**迁移：** 把内存仓储换成 SQLite 实现，保持 `get` 的返回和未知 ID 约定；数据库类型转换错误应在适配器变成统一契约错误，不能泄漏为另一种 `None`。

## 8. 本章小结与参考

- 注解描述调用关系，静态检查提前发现错误，运行时验证保护真实入口。
- TypedDict 描述字典形状；Protocol 表达可替换能力，二者都不自动验证行为。
- 泛型保留输入输出类型关系，但应在真实复用点使用。
- 严格金额要排除 bool；缺失、None、零值和额外字段分别处理。
- Pydantic 把字段声明变成运行时验证，之后仍要做业务规则和授权检查。
