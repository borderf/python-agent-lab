### 2.1 标准库是按问题组织的工具集合

按状态计数时，用集合会丢失次数；按用户分组时，只排序又没有为每个用户保存结果。标准库工具各自维护一种信息或不变量，所以正确选择来自任务，而非工具名称。下面从订单统计走到日期、生效区间和入库，每一步都说明原有结构缺少什么，再引入对应工具。

先处理五笔订单的用户A、B、A、A、B。若要统计每人出现次数，先手写字典得到A为3、B为2，再用Counter对照；若要保存每人的全部订单，就需要按键收集，选普通dict或defaultdict。两项任务的输出不同，工具也不同。deque留给经常从两端加入或取出任务的场景，先确定要完成的操作，再选容器。

itertools组合迭代过程，islice取片段，chain串联来源，groupby按相邻键形成组。若需要把所有相同键记录聚到一起，应先选择排序或字典分组；groupby不会自动变成SQL式全局聚合。

#### 案例推进：统计、分组与相邻分组并不相同

```python
# study-example: S08A
from collections import Counter, defaultdict, deque
from itertools import groupby
states = ["paid", "pending", "paid"]
assert Counter(states) == {"paid": 2, "pending": 1}
groups = defaultdict(list)
for position, state in enumerate(states):
    groups[state].append(position)
assert groups["paid"] == [0, 2]
adjacent = [(key, list(items)) for key, items in groupby(states)]
assert adjacent == [("paid", ["paid"]), ("pending", ["pending"]), ("paid", ["paid"])]
recent = deque(maxlen=2)
recent.extend(["e1", "e2", "e3"])
assert list(recent) == ["e2", "e3"]
```

Counter保留次数，defaultdict在缺键访问时调用工厂，deque保存有界最近记录。groupby只把相邻同键元素合成一组，不自动聚合所有相同键；先排序虽可聚合，却改变全局顺序，是否允许要看需求。

### 2.2 时间值必须包含足够业务信息

date表达日期，datetime表达日期与时间；naive datetime没有完整时区含义，aware datetime带时区信息。固定UTC偏移与地区时区不同，地区规则可能包含夏令时和历史变化。

保存事件时间通常明确采用UTC或带偏移的格式，展示时再转换；保存制度生效日期则按业务日期规则比较。区间起止是否包含端点应写清楚，例如start <= t < end。遇到没有时区的外部时间，不应无约定地猜它属于哪个区域。

#### 案例推进：先统一时间线，再比较有效区间

```python
# study-example: S08B
from datetime import datetime, timedelta, timezone
local = datetime.fromisoformat("2026-11-04T10:00:00+08:00")
utc = datetime.fromisoformat("2026-11-04T02:00:00+00:00")
assert local == utc and local.astimezone(timezone.utc) == utc
start = datetime.fromisoformat("2026-11-01T00:00:00+00:00")
end = datetime.fromisoformat("2026-12-01T00:00:00+00:00")
next_end = datetime.fromisoformat("2027-01-01T00:00:00+00:00")
at_start = start
before_end = end - timedelta(seconds=1)
at_end = end
assert start <= at_start < end
assert start <= before_end < end
assert not (start <= at_end < end)   # 终点属于下一个区间
assert end <= at_end < next_end      # 相邻区间从同一个终点开始
```

左闭右开让相邻有效区间在边界不重叠：起点属于本区间，终点前的最后一秒仍属于本区间，终点本身不属于；同一时刻在下一个区间里重新变为起点。`at_end` 与 `end` 是同一个对象值，不是“终点被特殊处理”，而是比较规则明确排除了右端点。

事件时刻、业务日期和持续时间分别表达；地区时区可能有夏令时，而固定偏移只是一个偏移值。经过多久用单调计时来源，发生在何时用明确时区的时钟值。

### 2.3 字符串方法与正则分别适合什么

简单去空白、拆分或前缀检查用字符串方法更直接；结构匹配可用re。匹配出一个看似日期或订单号的文本，只是格式检查，日期是否存在、编号是否可访问仍需其他验证。限制输入大小并观察不匹配情况，不只测理想短文本。

#### 从整段格式检查到正文提取

```python
# study-example: S08M
import re
code = "ORD-204"
match = re.fullmatch(r"ORD-([0-9]{3})", code)
assert match is not None
assert match.group(1) == "204"
assert re.fullmatch(r"ORD-([0-9]{3})", "前文ORD-204") is None
found = re.search(r"ORD-([0-9]{3})", "申请号ORD-204，请核对")
assert found is not None and found.group(1) == "204"
assert re.fullmatch(r"[0-9]{4}-[0-9]{2}-[0-9]{2}", "2026-99-99") is not None
```

先看固定前缀ORD-，再看[0-9]表示一个ASCII数字，{3}表示恰好三次，括号把该部分捕获为组。fullmatch要求整段符合，search在较长文本中寻找；没有匹配时得到None，先检查再访问group。最后一项只验证了日期外形，真实月份与日期仍需日期解析验证。练习将编号改为ORD-20、ORD-0204和ORD-ABC，逐个预测后运行。

### 2.4 排序、堆与Top-K

完整排序得到全量顺序，适合后续多次有序遍历；只要最前K项时，可以评估堆工具以减少不必要工作。heapq维护堆关系，不代表底层列表整体有序；并列时需要统一比较规则，才能与排序结果公平比较。

#### 案例推进：先比较堆与排序的结果

```python
# study-example: S08K
import heapq
values = [5, 1, 9, 3, 7]
assert heapq.nlargest(2, values) == [9, 7]
heap = []
for value in values:
    heapq.heappush(heap, value)
assert heap[0] == 1
assert sorted(heap) == [1, 3, 5, 7, 9]
assert heapq.heappop(heap) == 1
```

`heap[0]`是最小项，堆只保证父子关系，不保证整个列表有序；`nlargest`按值取前K项，并列时还要看实现和输入顺序。K接近总量时，完整排序可能更简单；只有K远小于总量、且需要反复取Top-K时，堆的收益才明显。

statistics提供常用统计，性能测量和业务统计都要说明样本。随机模拟数据要保留种子或避免断言依赖随机结果；安全标识和唯一性需求另选适合的工具。

### 2.5 用SQLite练习持久化边界

连接负责与数据库交互，SQL创建表和查询记录，参数占位符把值与语句结构分开。批次写入必须约定失败时回滚全部还是部分保留，连接关闭和事务提交是两个不同责任。

Python3.12的sqlite3有不同事务控制选项。示例使用什么配置，就按该配置测试；不要把连接with退出一律理解为已经关闭连接，也不要把一个数据库事务看成跨HTTP服务的事务。

#### 案例推进：用一次重复主键看见事务回滚

```python
# study-example: S08C
import sqlite3
from contextlib import closing
with closing(sqlite3.connect(":memory:")) as connection:
    connection.execute("CREATE TABLE orders (id TEXT PRIMARY KEY, cents INTEGER NOT NULL)")
    connection.commit()
    try:
        with connection:
            connection.execute("INSERT INTO orders VALUES (?, ?)", ("A", 10))
            connection.execute("INSERT INTO orders VALUES (?, ?)", ("A", 20))
    except sqlite3.IntegrityError:
        pass
    else:
        raise AssertionError("重复主键应失败")
    assert connection.execute("SELECT COUNT(*) FROM orders").fetchone()[0] == 0
```

同一批次第一条成功、第二条失败，事务回滚第一条；closing另外负责关闭连接。占位符传值避免把引号当SQL结构，不适用于任意表名/列名。这个示例是标准库SQLite练习；本章只到“本地事务与连接关闭”，服务并发、幂等、审批和跨请求状态留给第16章。

### 2.6 缓存函数结果时必须包含哪些输入

同一个制度在不同版本有不同原文。若函数偷偷读取“当前版本”的全局变量，以制度 ID 为唯一键的缓存不会随着全局值变化而失效。把影响结果的版本显式放进参数，可以同时保留历史查询。

```python
# study-example: S08D
from functools import lru_cache

corpus = {("A", 1): "上限30%", ("A", 2): "上限20%"}
@lru_cache(maxsize=8)
def clause(source_id, version):
    return corpus[source_id, version]

assert clause("A", 1) == clause("A", 1) == "上限30%"
assert clause("A", 2) == "上限20%"
assert clause.cache_info().hits == 1
```

缓存键需要可哈希，参数和返回值在淘汰或清空前可能被缓存持有。返回可变列表时，调用者修改的可能是下次调用仍会读到的对象。上例假设已发布版本的原文不可变。迁移到检索项目时，文本向量还依赖模型版本；用户能看哪些来源取决于当前授权，必须在查询路径上独立检查。

### 2.7 先分清测量哪一层内存

第1章区分对象、解释器分配和进程内存。sys.getsizeof只报告目标对象自身的直接大小，不递归统计全部子对象；把共享子对象按每条引用重复相加会高估。tracemalloc观察被其跟踪的Python分配，不等于全部原生库或进程驻留内存。操作系统任务管理器又是进程层观察。

练习时先建立嵌套容器，画出共享图，再比较外层大小、可追踪分配与进程指标各回答什么。不要固定某个平台的字节数作为语言规则，也不要由del后进程占用不下降直接推出泄漏。本章heapq的“堆”是数据结构名称，与动态内存的“堆空间”是不同概念。

```python
# study-example: S08R
import sys
import tracemalloc

shared = {"id": "A"}
rows = [shared, shared]
copies = [dict(shared), dict(shared)]
assert rows[0] is rows[1]
assert copies[0] is not copies[1]
assert sys.getsizeof(rows) == sys.getsizeof(copies)
double_counted = sys.getsizeof(rows) + 2 * sys.getsizeof(shared)
shallow_container = sys.getsizeof(rows) + sys.getsizeof(shared)
assert double_counted > shallow_container

tracemalloc.start()
data = [str(index) for index in range(1000)]
current, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()
assert current > 0 and peak >= current
```

`sys.getsizeof(rows)`只报告外层列表的指针区，不递归统计元素；把同一个`shared`按两次引用相加会高估，因为两个位置指向同一个对象。`copies`外层大小与`rows`相同，但内部已经是两个字典。`shallow_container`是“去重后的容器浅层大小”，不是递归对象总大小，也不是进程内存。`tracemalloc`只观察它跟踪的Python分配，原生库和进程驻留内存仍可能不同。三个数字回答三个问题，不能互相替代。Top-K、缓存和这里的测量口径都按需深入；第11章会用同一口径检查并发下的内存。

参考：[getsizeof](https://docs.python.org/3.12/library/sys.html#sys.getsizeof)、[tracemalloc](https://docs.python.org/3.12/library/tracemalloc.html)。

## 3. 原理讲解与推导

### 3.1 库抽象保留了哪些信息

Counter保留次数，set只保留唯一性；groupby依赖相邻顺序；堆维护局部结构而非完整排序。先找到工具维持的不变量，才知道它能否支持后续操作。

### 3.2 时间与事务都需要明确边界

时间比较依赖表示中是否包含足够时区信息，事务行为依赖连接控制模式和操作范围。看起来相似的两个对象或上下文，不一定承担同样含义，应通过端点与失败实验验证。

### 3.3 参数化处理值而不改语句结构

用户名称中的引号不应改变SQL含义。占位符让驱动按值处理输入；表名等结构性选择不能简单用值占位符替代，而应采用受控白名单。数据库出错后核对实际持久结果，不只看是否抛异常。

### 3.4 机制验证：预测、运行与回看

#### 验证实验 E20

```python
# experiment: E20
import sqlite3
connection = sqlite3.connect(":memory:")
try:
    connection.execute("CREATE TABLE orders (id TEXT PRIMARY KEY, cents INTEGER)")
    try:
        with connection:
            connection.execute("INSERT INTO orders VALUES (?, ?)", ("A", 10))
            connection.execute("INSERT INTO orders VALUES (?, ?)", ("A", 20))
    except sqlite3.IntegrityError:
        pass
    assert connection.execute("SELECT COUNT(*) FROM orders").fetchone()[0] == 0

finally:

    connection.execute("SELECT 1")
except sqlite3.ProgrammingError:
    pass
else:
    raise AssertionError("关闭后不能继续查询")
```

## 4. 示例与逐步走查

```python
# book-example: B08
from collections import Counter
from datetime import datetime
counts = Counter(["paid", "pending", "paid"])
assert counts["paid"] == 2 and counts["missing"] == 0
```

### 4.1 沿输入到结果逐步解释

输入状态paid、pending、paid时，Counter依次把对应计数增加，结果是paid两次、pending一次；集合只能告诉我们有哪些状态，不能保留两次这个事实。

随后比较两个带时区时间。墙上显示的小时数可以不同，但换算到相同时间基准后可能是同一时刻，所以不能只截取字符串里的小时比较。业务日期区间还要明确端点是否包含。

计数和时间看似是两种工具，选择原则相同：先说明需要保存次数、成员还是时间点，再选不会丢失所需信息的表示。

## 7. 面试问答与迁移

groupby 与 SQL GROUP BY 有什么差异？连接 with 是否等于关闭？Top-K 何时不必全排序？

**参考回答：**

1. `itertools.groupby`按连续相同键分组，输入A、B、A会产生三个组；SQL的GROUP BY在选定数据集内按键分组，不要求相同键相邻。若要前者达到按键归组的目的，先按同一键排序，或用dict累积；groupby各组还共享底层迭代过程，不能随意留到外层迭代结束再消费。
2. sqlite3连接的with管理已有事务的提交/回滚，不负责关闭连接，也不保证进入时就新建事务；具体行为受事务配置影响。closing或显式close负责关闭，两者解决不同责任。第16章再处理服务中的会话、竞争与外部效果。
3. K远小于n时可用大小为K的堆，常见代价约O(n log K)，避免为不需要的尾部排序；K接近n或需要完整顺序时，全排序常更直接。两种实现必须使用相同并列规则，性能比较才有意义。

**换条件自测：** 把相同用户记录打散，比较groupby与dict汇总；把Top-K输入增加同分项，检查输出是否仍满足约定顺序。先验证同一结果，再测时间与内存。

## 8. 本章小结与参考

### 8.1 主要知识点总结

- Counter、分组容器、deque和迭代工具各自保留不同信息，按任务选择。
- 日期、事件时刻和持续时间有不同表示；有效区间要明确边界。
- 正则匹配格式，业务检查验证含义；缓存键需要包含影响结果的输入。
- 数据库事务、连接关闭、性能计时和内存观察要分别确认作用范围。

### 8.2 日常工作注意事项

- 跨服务事件明确时区，耗时使用合适的单调计时来源；不要混用无时区时间与有时区时间来猜实际先后。
- SQL用参数传值；SQLite连接上下文的提交或回滚与关闭连接是不同责任，退出路径要分别检查。
- 缓存返回可变对象可能被调用者污染；把版本等影响结果的条件放进键中，授权仍在访问时检查。
