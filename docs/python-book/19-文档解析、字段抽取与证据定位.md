# 第19章　文档解析、字段抽取与证据定位

[上一章](18-大模型基础、消息与结构化输出.md) · [全书目录](教材目录.md) · [下一章](20-RAG、Embedding、向量库与权限过滤.md)

## 1. 学习目标与前置知识

处理文本型与扫描文档，并保留可核对证据。前置：第7、15、18章。

**承接与本章主线：** 把资料变成可追溯字段和来源，分开解析失败与信息缺失；这是后续检索与证据回答的输入基础。

**本章从这里开始：** 一张合同页被转成文本后，金额仍可能错一位，表格也可能丢列。模型抽取之前，先让每次转换留下定位，才能知道最终字段从哪里来。

## 2. 基础知识讲解

### 2.1 文档展示与机器可读内容不同

PDF在屏幕上看似一段连续文字，内部可能是多个定位片段或一张图。直接把提取结果当事实，会让阅读顺序、数字或表格关系的错误进入后续模型。解析因此先保留文本和位置，再形成字段；证据要能回到原页或节号，才有条件判断错误发生在读取还是解释。

PDF描述页面呈现，页面上看似连续的段落，内部可能分成多个文本片段；扫描件甚至只有图像。多栏、页眉页脚、表格与脚注会影响阅读顺序，因此“能提取字符串”不是“已经理解文档结构”。

先区分文本型与图像型页面，再选择解析或OCR。对表格保留行列关系，对标题保留层级，对每个片段保留来源位置。解析器选择取决于样本文档与资源，不必一开始安装所有工具。

### 2.2 上传到可用文档需要一个过程

接口先检查大小、格式与存储名称，建立document_id和任务状态。解析可能耗时或失败，应区分排队、处理中、可用和失败，避免请求一直无边界等待。用户文件名不直接作为可信存储路径。

身份与文档访问范围在这一步建立，后续检索与抽取继承同一可信来源。不能等到最终回答才隐藏另一租户内容。

#### 案例推进：上传、解析与抽取分成三个过程

上传阶段限制文件大小、格式与安全存储名，建立租户和document_id；解析阶段区分文本PDF、扫描OCR、表格和不支持内容，保存阅读顺序与定位；抽取阶段才生成候选字段，随后进行金额、日期、币种和跨字段规则检查。用户文件名不直接作为可信存储路径。

长任务采用可查询状态，失败保留阶段和原因。不能把损坏文件、无可抽取文本与确实缺字段都转换成空字符串；它们需要不同反馈。解析器版本变化时也要回归同一份材料。

### 2.3 解析结果应包含文本与定位

段落需要source_id、版本、页面或节号，表格需要可解释单元关系。OCR错误和不支持页面明确标记，不能把低质量输出伪装成完整解析。JSON/Markdown样例没有真实PDF页码时，page应为空而非随意填数。

### 2.4 抽取字段是带证据的断言

合同名称、双方、金额、交付时间与付款条款分别抽取。每个字段保留value、原文证据、定位和needs_review。缺失值允许null，不能为了满足Schema补出一个看似合理的值。

金额先保留原文，再按确定规则转成金额分与币种；日期也需保留原始表达和确定性解释。风险提示应指出依据与不确定状态，不能当作未经复核的法律结论。

#### 案例推进：用一个可回到原文的字段做起点

```python
# study-example: S19A
import re
source = {"doc_id":"contract-demo", "version":"1", "section":"费用", "text":"合同总金额为199.00元。"}
match = re.search(r"总金额为([0-9]+)\.([0-9]{2})元", source["text"])
assert match is not None
result = {
    "amount_cents":int(match.group(1))*100 + int(match.group(2)),
    "evidence":{"doc_id":source["doc_id"], "version":source["version"],
                "section":source["section"], "start":match.start(), "end":match.end(), "quote":match.group(0)},
}
evidence = result["evidence"]
assert result["amount_cents"] == 19900
assert source["text"][evidence["start"]:evidence["end"]] == evidence["quote"]
```

本例只处理约定的一种文本模式，不代表通用合同解析；它先展示字段与证据的关系。偏移量相对于这份具体文本版本，文本改变后必须重新定位。JSON/Markdown没有真实PDF页码时，不填一个假页码来凑字段。

### 2.5 将错误归到正确阶段

人工先核对页面文字、阅读顺序与表格，再核对模型字段。若“10,000”在解析时变为“100,000”，仅增加提示词可能无法修复。保留中间产物，才能分别测试解析、模型选择和字段转换。

#### 案例推进：没有值和数值为零必须区分

缺金额时value为空且needs_review为真；金额确为0时value可以是0，并保留证据。表格中的金额列错位、OCR多认一个0、模型选了另一份合同，都可能产生结构合法的字段。逐层保存中间结果，才能决定该修解析、上下文还是抽取策略。

证据原文存在不等于支持结论，还要核对合同对象、版本、条件和否定语义。模型自报置信度不自动等于校准后的正确概率，高影响字段应加入人工复核与明确规则。

## 3. 原理讲解与推导

### 3.1 这是多次可能有损的转换

页面→结构化片段→模型上下文→字段，每一步都可能丢失或误读信息。来源定位和原文不是装饰字段，而是回溯错误和人工复核的路径。

### 3.2 引用存在不等于支持结论

quote能在来源里找到，只证明文本位置真实；它可能描述另一份合同、旧版本或否定条件。仍需核对对象、版本与语义，再决定字段是否足以进入业务处理。

## 4. 示例与逐步走查

### 字段与证据示例

```json
{"field":"prepayment_limit","value":"20%","evidence":{"source_id":"policy-a-current","version":"2","page":null,"section":"付款要求","quote":"预付款比例不得超过合同金额的20%。"},"needs_review":false}
```

先验证来源/版本可访问且有效，再验证quote存在并支持该字段。若没有真实PDF定位，page保持null；缺少条款时value为null、needs_review为true。字符串匹配存在只能证明来源位置，不能单独证明完整业务结论。

### 4.1 沿输入到结果逐步解释

抽取结果声称预付款上限是20%。先按source_id和version找到允许访问的来源，再定位付款要求，核对quote确实出现，最后判断这段原文是否支持20%这个结论。

若quote不存在，是引用定位或生成问题；quote存在但实际写30%，则是结论不受证据支持。若解析时将20%读成200%，错误更早发生，需要回到解析中间产物。

因此字段应同时保留原文、位置和复核状态。只保存value会抹去排错线索；没有真实PDF页码时填null，比编造定位更有助于后续核对。

### 4.2 固定材料：页面→定位→字段→复核

用三页模拟材料走完整条链：第1页是可解析文本，第2页是扫描页，第3页是解析后空文本。

```python
# study-example: S19B
import re

pages = [
    {"page": 1, "kind": "text", "text": "合同总金额为199.00元。"},
    {"page": 2, "kind": "scan", "text": ""},
    {"page": 3, "kind": "text", "text": "   "},
]

def parse_page(page):
    if page["kind"] == "scan" and not page["text"].strip():
        return {"page": page["page"], "status": "needs_ocr"}
    if not page["text"].strip():
        return {"page": page["page"], "status": "empty_text"}
    return {"page": page["page"], "status": "parsed", "text": page["text"]}

parsed = [parse_page(page) for page in pages]
assert parsed[0]["status"] == "parsed"
assert parsed[1]["status"] == "needs_ocr"
assert parsed[2]["status"] == "empty_text"

match = re.search(r"总金额为([0-9]+)\.([0-9]{2})元", parsed[0]["text"])
assert match is not None
field = {
    "value_cents": int(match.group(1)) * 100 + int(match.group(2)),
    "evidence": {"page": 1, "start": match.start(), "end": match.end(),
                 "quote": match.group(0)},
    "field_needs_review": False,
}
assert field["value_cents"] == 19900
assert field["evidence"]["quote"] in parsed[0]["text"]

missing = {"value_cents": None, "evidence": None, "field_needs_review": True,
           "reason": parsed[1]["status"]}
assert missing["value_cents"] is None and missing["field_needs_review"] is True

document = {
    "doc_id": "contract-demo",
    "field": field,
    "needs_review": True,
    "unresolved_pages": [2, 3],
}
assert document["field"]["field_needs_review"] is False
assert document["needs_review"] is True  # 第1页字段成功，但整份文档仍未完成
```

`field_needs_review=False` 只表示“第1页这段文本的规则抽取可定位、未触发复核”；整份合同仍有扫描页、空页和可能漏掉的补充条款，所以 `document.needs_review=True`。这两个标志不能合并：字段级成功不等于文档级完成。真正发布前还要处理未解析页、跨页冲突和整份文档的复核。

逐步检查：

1. 第1页解析成功，字段带页码、起止偏移和原文；
2. 第2页是扫描页，不返回空字符串冒充成功，而是 `needs_ocr`；
3. 第3页解析后为空，单独标记 `empty_text`，不能和“金额缺失”混为一谈；
4. 字段值为19900，但证据只支持这一页的这段文本；换版本/换页后要重新定位。

真实 PDF 还要核对阅读顺序、表格行列与页码映射；如果页码来自解析器分页而非原 PDF，必须在证据里标明来源，不能把内部序号伪装成真实页码。

### 4.3 累计实现：一份材料的四层产物

| 步骤 | 产物 | 预期结果 | 失败先看 |
| --- | --- | --- | --- |
| 1. 页面解析 | `page_text` + 页码/阅读顺序 | 文本页有页码；空页/扫描页标记 `needs_ocr`/`empty_text` | 是否把空字符串当成功 |
| 2. 定位 | `start/end/quote` 或 page/section | quote 能回查原文；偏移对应同一文本版本 | 字符偏移与字节偏移是否混用 |
| 3. 字段候选 | `value + evidence + field_needs_review` | 缺失为 null 并复核；0 保留证据 | 是否用空值/零值互相冒充 |
| 4. 文档复核 | `document_needs_review` + unresolved_pages | 单页字段成功，整份文档仍可待复核 | 是否把字段级成功当整份完成 |

`S19B` 是可运行的最小版本；真实 PDF 再补页码映射与表格行列。验收时保存一份材料、一张中间产物表和一次失败定位，不要只留最终字段。

## 7. 面试问答与迁移

为什么解析正常仍可能抽错合同金额？如何定位是 OCR、分块还是模型的问题？

**参考回答：**

1. 解析没有报错，只说明得到某种输出，不证明阅读顺序、表格行列、页码与字符都正确。合同里的总价、预付款和含税金额可能都像目标值；需先定义字段含义，再保留原页、区域/文本定位与原始金额，做确定性单位和格式转换，歧义时转人工复核。
2. 从原页与人工标注开始对照：原页正确而解析文本错，先修OCR/布局；文本正确而目标条款跨块丢失，查分块；证据在库却没进候选，查检索；候选正确而输出错，查抽取/生成及字段校验。保存每层产物才能找到第一个分叉。

**换条件自测：** 将“20万元”改成表格里的“20 / 单位：万元”，再加入另一页的“20元”。记录预期字段与定位，说明仅靠字符串匹配为什么不足；不要把字符存在当作字段语义正确。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 文档转成文本后可能错位、丢列或漏页，怎样让字段都能回到原文核对？

**一条主线：**

```text
页面与扫描件 → 解析保留阅读顺序和定位 → 带值、原文、偏移与复核状态的字段
```

**三个关键词：** 解析、定位、复核——解析把页面变成片段，定位把片段绑回版本文档，复核状态区分“提取成功”和“可以发布”。

**最容易错：**
- 能提取字符串就认为理解文档结构；多栏、表格和页眉页脚会改变阅读顺序。
- 把扫描页或空文本返回空字符串当成功；`needs_ocr`、`empty_text` 与“字段缺失”要分开。
- 为满足 Schema 编造页码或补金额；`quote` 找得到也不代表支持结论，还要核对对象、版本与否定语义。
- 字段级 `needs_review` 为假就认为文档完成；未解析页和跨页冲突仍需文档级复核。

**与前后章：** 上一章提供模型调用与结构化输出边界；本章把文档变成带定位的字段；下一章只从这些来源建立索引和检索。

**学完应能：**
- 区分文本页、扫描页和空页，并给出 `parsed`、`needs_ocr`、`empty_text` 状态。
- 抽取字段并保存值、原文、偏移、版本与复核标志，缺失值保持 `null`。
- 按上传、解析、抽取三阶段保存状态，失败可定位与重做。
- 对一处金额错误，沿解析与抽取的中间产物定位首个分叉。

### 8.2 日常工作注意事项

- 处理文件前按场景限制类型与大小，服务端确定存储标识；文件名不直接作为可信路径。
- 不要把JSON节号或解析顺序伪装成PDF页码；保留真实来源映射，并人工核对代表性页面。
- 缺字段和OCR低质量要显式标注，不能让模型补猜成事实；整批导入的失败和重试按任务状态处理。
