## 2. 基础知识讲解

并发在已有执行模型上增加“谁在什么时候推进”。先区分进程、线程和协程，再观察等待、取消与共享；协程不复制业务对象，线程不自动隔离对象，进程之间则需要明确传输或共享机制。

### 2.1 从顺序调用理解等待

依次查询三项外部资料时，大部分时间可能在等网络；等待期间CPU并没有完成相关业务。并发允许在一项等待时推进另一项，但不会自动复制共享数据，也不会增加下游容量。因此本章从重叠等待开始，再处理任务失败、排队上限和取消，最后才讨论线程或进程的适用条件。

先考虑两个各需等待远端响应的查询：顺序执行时，第一个等待结束才开始第二个；异步方案可以在第一个等待时推进第二个。先理解这个等待重叠，再读async def与await：调用异步函数通常先得到协程对象，await或任务调度才推进它。事件循环安排多个任务交替前进；如果执行的始终是CPU计算而没有让出机会，仅加async关键字不会得到并行计算。

先写顺序await，再用create_task/gather组织并发，观察什么时候开始、完成和返回。等待结果的顺序与任务实际结束顺序可以不同；代码中没有真正挂起的操作时，也不保证其他任务马上得到执行机会。

#### 案例推进：先分清协程对象、调度和等待

```python
# study-example: S11A
import asyncio
async def main():
    events = []
    async def work(name):
        events.append("start:" + name)
        await asyncio.sleep(0)
        events.append("done:" + name)
        return name
    coroutine = work("A")
    assert events == []
    task = asyncio.create_task(coroutine)
    result = await task
    assert result == "A" and events == ["start:A", "done:A"]
asyncio.run(main())
```

调用async def通常先得到协程对象，create_task把它安排为任务，await等待其完成并取得结果。await另一个协程并不自动让整段业务并发；需要共同调度多个任务，且它们在合适的等待点让出控制。直接在事件循环中做阻塞I/O或长CPU计算，仍会妨碍其他任务。

### 2.2 组织子任务与失败

gather组合多个可等待对象，TaskGroup给一组任务更明确的共同生命周期。它们在异常传播、兄弟任务取消和异常组方面不同，不能把一个失败理解为所有其他工作都已经停止。

结果需要保留请求对应关系；空输入、重复用户和部分失败如何表达应先写契约，再选择调度方式。

#### 案例推进：用失败观察兄弟任务清理

```python
# study-example: S11C
import asyncio
async def main():
    started = asyncio.Event()
    events = []
    async def slow():
        started.set()
        try:
            await asyncio.Event().wait()
        finally:
            events.append("cleaned")
    async def fail():
        await started.wait()
        raise ValueError("bad input")
    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(slow())
            group.create_task(fail())
    except* ValueError:
        events.append("reported")
    assert events == ["cleaned", "reported"]
asyncio.run(main())
```

Event确保slow已经启动；普通子任务失败后，TaskGroup取消并等待相关兄弟任务退出，再按规则报告异常组。except*按组内匹配类型处理，不与普通except在同一try中混写。不要把这与默认gather的错误传播完全等同。

取消是协作请求，finally负责清理，清理后通常应继续传播取消。超时还要说明从排队还是获得名额开始计算；总deadline约束整个操作，不能被层层重试重置。线程中已开始的工作不会因取消等待就自动中断；进程可以隔离CPU任务，却增加启动和序列化成本，Windows入口保护也要正确。

### 2.3 控制并发、排队与总预算

Semaphore限制进入某段操作的数量，但如果已经创建一百万个任务，等待任务本身仍占资源。任务创建窗口或有界队列控制待处理规模；每秒限流又是另一种约束。

单个请求超时、排队时限和总任务截止时间分别定义。重试只用于约定的临时故障，并受剩余预算限制；写操作超时不能推断外部没有完成。

#### 案例推进：同时执行的限制需要实际证据

```python
# study-example: S11B
import asyncio
async def main():
    gate = asyncio.Semaphore(2)
    active = peak = 0
    async def work(value):
        nonlocal active, peak
        async with gate:
            active += 1
            peak = max(peak, active)
            try:
                await asyncio.sleep(0)
                return value * 2
            finally:
                active -= 1
    results = await asyncio.gather(*(work(n) for n in range(5)))
    assert results == [0, 2, 4, 6, 8]
    assert peak <= 2 and active == 0
asyncio.run(main())
```

active/peak描述同时进入受限区域的数量，结果顺序来自gather的输入顺序，而非完成顺序。这个例子仍一次建立了所有任务；数据上百万时要用窗口或有界队列限制待处理对象。并发、每秒速率、队列容量分别控制不同资源。

### 2.4 取消与清理

cancel请求任务在合适位置处理取消，不是在任意机器指令处强制终止。清理通常放finally，清理后继续传播取消。父任务失败时，是否取消并等待子任务结束必须明确；不能靠关闭终端完成清理。

#### async for、async with与超时收尾

```python
# study-example: S11D
import asyncio
async def numbers():
    for number in range(3):
        await asyncio.sleep(0)
        yield number
async def main():
    result = []
    async for number in numbers():
        result.append(number)
    assert result == [0, 1, 2]
    try:
        async with asyncio.timeout(0):
            await asyncio.sleep(0)
    except TimeoutError:
        pass
    else:
        raise AssertionError("本例应触发超时")
asyncio.run(main())
```

异步生成器的下一项可能需要等待，因此使用async for；异步上下文的进入/退出也可等待，因此使用async with。timeout通过取消等机制约束当前等待范围，外层捕获转换后的超时；它不是操作系统层面强行中止任意线程或远端动作。真实预算使用业务时限，本例的0只用于稳定演示。

### 2.5 线程和进程解决不同问题

同步阻塞I/O可放在线程边界；已开始的线程任务不能仅靠取消Future或await强制终止，需要协作停止、超时或其他隔离方案。CPU密集任务可评估进程及扩展库代价；进程启动和序列化本身有成本，Windows入口保护要正确。

不要将某一种CPython构建的GIL行为当作全部Python规则。先记录实际解释器、平台和库行为，再做选择。

### 2.6 测量性能前先固定正确性

比较实现时统一输入、输出、并列规则和错误处理。perf_counter/timeit观察耗时，cProfile观察热点，tracemalloc观察相应内存分配；一次短样本不能证明某方案普遍更快。缓存要说明失效、权限与占用代价。

### 2.7 真正限制待处理规模：有界队列与固定worker

信号量限制正在执行的数量，却不阻止先创建所有任务。现在改成一个生产者、固定数量worker和有限队列：输入逐项进入，队列满时生产者等待，这就是背压。它将内存中的待处理项与活跃任务一起纳入设计。

```python
# study-example: S11E
import asyncio
async def consume(values, transform, *, workers=2, capacity=2):
    if type(workers) is not int or workers <= 0 or type(capacity) is not int or capacity <= 0:
        raise ValueError("workers和capacity必须为正整数")
    queue = asyncio.Queue(maxsize=capacity)
    stop = object()
    results = {}
    async def produce():
        for index, value in enumerate(values):
            await queue.put((index, value))
        for _ in range(workers):
            await queue.put(stop)
    async def work():
        while True:
            item = await queue.get()
            try:
                if item is stop:
                    return
                index, value = item
                results[index] = await transform(value)
            finally:
                queue.task_done()
    async with asyncio.TaskGroup() as group:
        group.create_task(produce())
        for _ in range(workers):
            group.create_task(work())
    return [results[index] for index in sorted(results)]

async def main():
    active = peak = 0
    async def double(value):
        nonlocal active, peak
        active += 1
        peak = max(peak, active)
        try:
            await asyncio.sleep(0)
            if value == 3:
                raise ValueError("模拟处理失败")
            return value * 2
        finally:
            active -= 1
    assert await consume(range(3), double) == [0, 2, 4]
    assert await consume([], double) == []
    failed = False
    try:
        await consume(range(10), double)
    except* ValueError:
        failed = True
    assert failed
    assert active == 0 and peak <= 2
    assert not [task for task in asyncio.all_tasks() if task is not asyncio.current_task() and not task.done()]
asyncio.run(main())
```

按时间线读：生产者put，两名worker轮流get，获得项后等待transform；队列容量达到2时，后续put暂停。正常输入后每个worker各收到一个停止哨兵。每次成功get对应一次task_done；它记账的是队列消费，不单独证明业务成功。

先看一个示意时间线（队列内容随调度可能略有差异，关键是状态关系）：

| 时刻 | 队列（示意） | worker | 生产者 / TaskGroup |
| --- | --- | --- | --- |
| T0 | `[0,1]` | 两个 worker 分别 get 0、1 | 生产者继续 put 2、3 |
| T1 | `[2,3]` | 两个 worker 处理中，active=2 | 队列满，生产者等待 put 4 |
| T2 | 可能还剩未处理项 | 一个 worker 在处理 value=3 时失败 | TaskGroup 取消生产者与另一个 worker，等待退出 |
| T3 | 未处理项不再被消费 | active 回到 0，finally 已执行 | 整批失败；不把部分结果当成功 |

先预测再读代码：worker 失败后，生产者是否还阻塞在 `put`？另一个 worker 正在处理的项会怎样？`task_done` 由谁调用、未消费的队列项会不会被标记完成？答案分别是“被取消”“收到取消并走 finally”“已 get 的项由对应 worker 调用”“不会”；这解释了为什么整批失败不能返回未标记的部分结果。

若某个worker失败，TaskGroup取消生产者与其他worker并等待退出，因此不能只让生产者在满队列上永远等待。这个版本选择整批失败，不返回未标记的部分成功；若业务需要partial，要另行定义结果结构和失败合并。

这里保存了全部输出，所以仍有O(n)结果内存；输入迭代器若做阻塞读取也会阻塞事件循环。要处理无限流，应把结果交给有界下游或持久存储，并约定取消、重放与失败恢复。队列容量、worker数量、每秒速率与总时限仍是不同控制。

### 2.8 流提前结束与并发请求隔离

模型流收到第一段后，用户就可能离开。异步生成器的 finally 应负责归还它取得的资源；消费方用 aclosing 在离开上下文时等待 aclose。另一个问题是两条并发请求的日志该写哪个请求 ID。ContextVar 在任务创建时传递当前上下文，适合为诊断携带一个不可变标识。

```python
# study-example: S11F
import asyncio
from contextlib import aclosing
from contextvars import ContextVar

request_id = ContextVar("request_id", default="outside")
async def chunks(closed):
    try:
        await asyncio.sleep(0)
        yield request_id.get()
        yield "more"
    finally:
        closed.append(request_id.get())

async def first_chunk(name):
    token = request_id.set(name)
    closed = []
    try:
        async with aclosing(chunks(closed)) as stream:
            async for item in stream:
                break
        assert closed == [name]
        return item
    finally:
        request_id.reset(token)

async def main():
    assert await asyncio.gather(first_chunk("A"), first_chunk("B")) == ["A", "B"]
    assert request_id.get() == "outside"
asyncio.run(main())
```

把 break 改成消费完整流，解释 finally 运行的时机。上下文复制的是绑定，若值本身是共享字典，仍可能跨任务相互修改。业务授权与持久任务状态继续显式传递和保存；日志上下文不承担这两项职责。

## 3. 原理讲解与推导

### 3.1 协作调度依赖可等待边界

事件循环在任务等待时推进其他任务，因此阻塞的同步调用会阻碍整个循环。await不是把任意函数移到后台；它需要相应的可等待对象与正确实现。

### 3.2 请求取消与效果停止分属不同层

协程、线程、远程请求和业务动作都有自己的生命周期。调用者不再等待，只说明等待路径改变，不证明底层未执行或已回滚。需要通过清理、幂等和实际状态查询处理这些边界。

### 3.3 结构化任务管理改变错误的形状

TaskGroup的共同退出和异常组帮助表达多任务失败；gather的常见失败传播则不自动等于取消全部任务。先用事件记录检查返回前的真实状态，再定义对调用方暴露什么异常。

#### 将执行状态与对象共享分开

同一进程内的线程有各自的原生执行栈，但可引用相同Python对象；协程也有各自需保留的暂停状态，却能共享列表或会话数据。独立执行状态不等于独立业务数据。进程有不同地址空间，常见进程池通过序列化传递任务与结果，不能假定另一个进程直接访问同一个普通列表；显式共享内存等机制需另行设计。

### 3.4 GIL、共享状态与真正的并行边界

本项目使用的常规CPython3.12中，GIL约束同一时刻执行Python代码的线程；I/O等待和部分扩展操作可以释放它，因此多线程对阻塞I/O仍可能有用。CPU密集的纯Python工作通常不能仅靠增加线程获得相同比例的并行收益，但扩展库与解释器构建差异都要实际确认。

GIL不等于业务操作原子性。一次“先检查是否存在、再写入”包含多个步骤，即使单步容器操作在某实现下有特定保证，也不能推出完整业务序列不会交错。异步代码跨await读改共享状态同样可能交错，甚至不需要多个线程。

解决时先减少共享可变状态，让工作单元返回结果后集中汇总；确有共享更新再选择锁、队列、数据库事务或隔离。锁要覆盖需要共同保持的不变量，也要考虑等待、死锁和吞吐代价。新解释器和可选构建的线程行为按实际版本验证，不把GIL口诀写成全部Python的永久规则。

#### await是等待协议边界，不保证每次都切换任务

调用async函数先取得协程对象；await驱动它直到完成或真正暂停。create_task安排任务，任务何时开始还依赖事件循环。若被等待协程立即返回，没有真实挂起，其他任务不一定获得执行机会。不要用“每个await都让出执行权”解释事件顺序。

```python
# study-example: S11Z
import asyncio
async def main():
    events = []
    async def other():
        events.append("other")
    async def immediate():
        events.append("immediate")
        return 7
    task = asyncio.create_task(other())
    events.append("before")
    assert await immediate() == 7
    events.append("after")
    assert events == ["before", "immediate", "after"]
    await task
    assert events == ["before", "immediate", "after", "other"]
asyncio.run(main())
```

该实验使用项目默认任务工厂，不把顺序推广到自定义或立即执行任务工厂。取消也是请求，通常在后续可取消等待边界传播；协程可清理或处理取消，而线程与远端副作用不会随等待者一起自动撤销。测试应观察真实清理和任务结束，不只检查调用过cancel。

import asyncio
async def scenario(use_group):
    ready = asyncio.Event()
    events = []
    async def waiting():
        ready.set()
        try:
            await asyncio.Event().wait()
        finally:
            events.append("cleaned")

## 4. 示例与逐步走查

```python
# book-example: B11
import asyncio
async def main():
    gate = asyncio.Semaphore(2)
    async def work(value):
        async with gate:
            await asyncio.sleep(0)
            return value * 2
    assert await asyncio.gather(*(work(n) for n in range(4))) == [0,2,4,6]
asyncio.run(main())
```

### 4.1 沿输入到结果逐步解释

gather为四项工作安排任务，每项先进入同一个Semaphore。许可只有两个，因此同一时刻至多两项进入受保护区域；其他任务等待许可。

sleep(0)让任务有机会暂停推进，随后每项返回输入的两倍。gather按传入顺序组织结果，不按谁先完成排序，所以调度变化不应改变结果与输入的对应关系。

但四个任务在调用时都已建立。将输入扩大到一百万，信号量仍只保护进入区域的数量，无法消除一百万个等待任务的存储开销；这就是后面引入固定worker和有界队列的原因。

## 7. 面试问答与迁移

asyncio 为什么会被阻塞？TaskGroup 为什么抛异常组？线程取消和底层操作终止有什么区别？

**参考回答：**

1. 同一事件循环靠任务在等待点让出执行权。async函数里直接做阻塞IO或长时间CPU计算，其他任务就无法及时运行；写了async或await，不保证所调用代码会真正让出。先测事件循环延迟，再决定使用异步客户端、受限线程池还是进程隔离。
2. Python 3.12的TaskGroup遇到普通的非取消异常时，通常取消其余任务，等待退出，再聚合异常；单个任务以CancelledError结束并不等于同样触发失败处理，KeyboardInterrupt和SystemExit还有特殊重抛规则。`except*`处理异常组；不能只背“任何失败都抛ExceptionGroup”。与gather默认传播首个异常但不自动取消其余任务的行为对照。[任务组规则](https://docs.python.org/3.12/library/asyncio-task.html#task-groups)
3. 取消协程是在合适时机注入取消异常，清理依赖代码配合。取消等待 `to_thread` 的任务，不会强制杀死已经执行的线程；远端写入也可能继续。需要分别安排本地截止时间、底层库时限、资源上限和效果核对，进程强制终止同样不能撤销已发生的外部效果。

**换条件自测：** 将失败子任务改为自行取消，再将异步等待改为线程中的阻塞调用；分别预测兄弟任务、with退出和底层操作是否停止。用清理日志与效果记录证明，不只看调用者是否收到异常。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 查询大部分时间都在等外部响应，怎样让任务交替推进并守住并发、超时与取消的边界？

**一条主线：**

```text
顺序 await → 协程调度与有界队列 → 可取消、可核对的结果
```

**三个关键词：** 协程、并发、取消——协程在等待点让出执行权，并发参数决定同时推进多少，取消规定停止时由谁清理和核对。

**最容易错：**
- 写了 `async`/`await` 就以为不阻塞；在事件循环里直接做阻塞 I/O 或长 CPU 计算，其他任务仍无法推进。
- 把 `Semaphore` 的上限当成待处理任务上限；它只约束进入区域的并发，已创建的等待任务仍占资源。
- 把取消 `await` 当成底层线程或远端写入已停止；已开始的操作要协作终止，并核对可能已发生的外部效果。

**与前后章：** 上一章的测试、调试与日志提供失败定位；本章把它们用于调度边界。下一章要求把并发、文件与校验组合成可验收的订单程序。

**学完应能：**
- 分别用顺序 `await`、`gather` 与 `TaskGroup` 组织任务，说出异常传播和兄弟任务退出的差异。
- 用 `active`/`peak` 和 `finally` 事件证明并发上限与清理，而不只看调用者是否收到异常。
- 说明线程、进程与协程各自共享什么，为阻塞 I/O 与 CPU 密集任务选择边界。
- 先固定正确性，再记录数据规模、耗时与峰值内存，不编造普遍速度倍数。

### 8.2 日常工作注意事项

- 不要在异步路径直接调用长时间阻塞操作；按库能力使用异步客户端或受控线程边界，并限制并发。
- 创建任务后明确谁等待结果、谁处理异常。使用TaskGroup等结构组织相关任务，退出时等待必要清理。
- 取消等待并不能保证底层线程或外部写入已经停止；超时后核对动作状态，不直接无条件重试有副作用的操作。
