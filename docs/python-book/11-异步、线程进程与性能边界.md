## 2. 基础知识讲解
### 2.1 协程对象、任务与让出点

调用 `async def` 只创建协程对象；`create_task` 安排它，`await` 等待结果。事件循环只能在任务真正挂起时推进其他任务，所以 `async` 函数里的阻塞 I/O 仍会阻塞循环。
#### 案例推进：立即完成不一定切换任务
```python
# study-example: S11Z
import asyncio
async def main():
    events = []
    async def other(): events.append("other")
    async def immediate(): events.append("immediate"); return 7
    task = asyncio.create_task(other())
    assert await immediate() == 7 and events == ["immediate"]
    await task
    assert events == ["immediate", "other"]
asyncio.run(main())
```

`immediate` 没有真正挂起，所以当前任务先继续；`other` 要到后续调度机会才运行。这个顺序以项目默认任务工厂为前提，自定义工厂需要重新验证。
### 2.2 把阻塞工作移出事件循环

`time.sleep`、同步磁盘或网络调用、长 CPU 段都不会创建可等待点；即使其他任务已经就绪，事件循环也要等当前回调返回。轮询标志、频繁 `await asyncio.sleep(0)` 或把函数声明成 `async`，都不能把阻塞系统调用变成异步。

I/O 边界可用 `await asyncio.to_thread(blocking_call, ...)`：它把调用提交到循环的默认执行器，并把结果送回循环。`loop.run_in_executor(executor, func, ...)` 适合自管执行器、线程数与关闭时机；`to_thread` 不拥有独立池，不能靠它设置并发。二者取消 await 只停止等待，不终止已运行线程；共享默认池还会让多个调用争抢名额。

需要传递 `ContextVar` 时优先 `to_thread`，它复制当前上下文；直接 `run_in_executor` 不会自动复制，应显式传入 `contextvars.copy_context()` 包装的调用。纯 Python CPU 工作仍受 GIL 限制，应回到下一节评估进程，而不是继续加线程。

下面把“等待期间让出事件循环”和“把当前上下文带进线程”放在同一个可运行探针里。阻塞函数只返回线程标识与请求标识，不访问网络或文件。

```python
import asyncio
import threading
from contextvars import ContextVar

request_id = ContextVar("request_id")

def blocking_lookup():
    return threading.get_ident(), request_id.get()

async def main():
    token = request_id.set("req-11")
    try:
        worker_id, copied_id = await asyncio.to_thread(blocking_lookup)
    finally:
        request_id.reset(token)
    print(copied_id, worker_id != threading.get_ident())

asyncio.run(main())
```

预期输出为 `req-11 True`。执行时，`to_thread` 把函数提交给默认执行器并挂起当前协程，事件循环因此可以推进其他任务；线程返回后，结果与复制过的上下文值回到原任务。这个探针没有证明取消能停止线程，也没有限制线程数；这两件事分别由执行器边界和 `active/peak` 记录验证。

### 2.3 组合任务时先约定失败语义

`gather` 默认传播首个异常，但不自动取消其他任务；`TaskGroup` 在普通子任务失败时会取消并等待兄弟任务，再报告异常组。选择哪一种，取决于调用方需要整批成功还是保留部分结果。

异常组 `ExceptionGroup` 是一个异常对象，`exceptions` 属性装着多个叶子异常，还可以嵌套。普通 `except ValueError` 匹配异常对象本身，而异常组不是 `ValueError` 实例，接不住组内叶子；`except* ValueError` 按叶子类型匹配，把组分裂成子组交给各子句分别处理，未被认领的叶子重新组包后继续向外传播。同一个 `try` 不能混用 `except` 与 `except*`，`except*` 子句里也不能写 `return/break/continue`。

```python
# study-example: S11G
try:
    try:
        raise ExceptionGroup("batch", [ValueError("a"), KeyError("b"), ValueError("c")])
    except* ValueError as exc:
        print("value", len(exc.exceptions))
except ExceptionGroup as exc:
    print("leftover", [type(e).__name__ for e in exc.exceptions])
```

```text
value 2
leftover ['KeyError']
```

预期输出为 `value 2` 和 `leftover ['KeyError']`。执行时 `except* ValueError` 认领两个叶子，`exc` 仍是只含这两个叶子的子组而不是单个 `ValueError`；没人认领的 `KeyError` 被重新包成新组抛出，由外层 `except ExceptionGroup` 接住。边界是：叶子全部被认领时不再向外传播；捕获裸 `ValueError` 仍要用普通 `except`，`except*` 只处理异常组。下面 `E23` 与 `S11E` 的 `except* ValueError` 正是接住任务组报告的异常组。
#### 案例推进：比较失败后的兄弟任务
```python
# experiment: E23
import asyncio
async def scenario(use_group):
    ready, events = asyncio.Event(), []
    async def waiting():
        ready.set()
        try: await asyncio.Event().wait()
        finally: events.append("cleaned")
    async def failing():
        await ready.wait()
        raise ValueError("failed")
    if use_group:
        try:
            async with asyncio.TaskGroup() as group:
                group.create_task(waiting())
                group.create_task(failing())
        except* ValueError: pass
    else:
        pending = asyncio.create_task(waiting())
        try: await asyncio.gather(pending, failing())
        except ValueError: assert not pending.done()
        finally:
            pending.cancel()
            await asyncio.gather(pending, return_exceptions=True)
    assert events == ["cleaned"]
async def main():
    await scenario(False)
    await scenario(True)
asyncio.run(main())
```

两种方式都得到了清理事件，但路径不同：左边由调用方补取消，右边由任务组负责。不能只看到异常就假定兄弟任务已经结束。`E23` 的预期结果是两次 `scenario` 都通过、控制台无输出，且最终 `events == ["cleaned"]`；`gather` 分支在异常发生时兄弟任务仍未完成，`TaskGroup` 分支则由上下文负责取消并等待。
### 2.4 线程、进程与协程的边界

协程和线程可以共享同一进程里的 Python 对象；进程通常通过序列化传递任务和结果。阻塞 I/O 可以交给受限线程池，CPU 密集的纯 Python 工作可评估进程，但启动、传参和 Windows 入口保护都有成本。

常规 CPython 的 GIL 限制同一时刻执行 Python 字节码的线程，但 I/O 等待和部分扩展操作会释放它。不要把这个实现现象写成全部 Python 的永久规则；也不要用线程取消推断远端写入已经撤销。

并发请求还要隔离可变状态：队列、哨兵、结果字典和失败事件应按请求创建，不能把一个请求的取消传播给另一个。若共享全局 worker 池，只共享执行能力，不共享请求级队列；上游流提前结束时要有独立路径停止生产者并唤醒等待者，不能靠永远送不到的结束哨兵收尾。

选择执行边界时，用“工作卡在哪里”而不是函数名判断：

| 工作形态 | 最小数据流 | 预期证据 | 失败边界 |
| --- | --- | --- | --- |
| 等待远端或磁盘 | 协程 `await` 异步客户端 | 等待时其他任务能推进 | 同步调用会占住事件循环 |
| 阻塞 I/O | 协程 → 受限线程池 → 结果 | 线程数与等待上限可记录 | 取消 await 不终止运行中的线程 |
| 纯 Python CPU 计算 | 父进程 → 序列化输入 → 子进程计算 → 序列化结果 | 子进程退出且结果可验证 | 启动、传参和平台入口保护增加成本 |

例如输入是 10 个阻塞查询时，不能直接创建 10 个线程就宣称“最优”；先记录实际等待、CPU 时间和并发峰值，再与协程或进程方案比较。

### 2.5 超时取消当前任务，不只取消底层调用

`asyncio.wait_for(aw, timeout)` 确保等待对象有任务边界；超时时请求取消并等待其结束，再抛出 `TimeoutError`。被等待者若清理缓慢或吞掉取消，`wait_for` 也会等待，因此“超时”不保证立即返回。Python 3.12 的 `asyncio.timeout(timeout)` 在作用域到期时取消当前任务，离开作用域才把自身导致的取消转成 `TimeoutError`；调用方另行取消仍是 `CancelledError`。

把 `try/except` 放在超时作用域外，把 `finally` 放在资源边界内，不要捕获 `CancelledError` 后继续执行。总任务使用单调时钟 deadline，内层单次 timeout 取 `min(单次上限, 剩余预算)`；外层 `wait_for` 与内层 `timeout` 混用时，还要验证谁先取消、异常在哪一层转换。

超时与调用方取消可以用同一个清理函数区分。`asyncio.timeout(0)` 只表示在下一个调度点到期，不表示立即强杀协程。

```python
import asyncio

async def slow_cleanup(events):
    try:
        await asyncio.sleep(0)
    finally:
        await asyncio.sleep(0)
        events.append("cleaned")

async def main():
    timeout_events = []
    try:
        async with asyncio.timeout(0):
            await slow_cleanup(timeout_events)
    except TimeoutError:
        print("timeout", timeout_events)

    cancel_events = []
    task = asyncio.create_task(slow_cleanup(cancel_events))
    await asyncio.sleep(0)
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        print("cancel", type(task).__name__, cancel_events, task.cancelled())

asyncio.run(main())
```

预期输出为 `timeout ['cleaned']` 和 `cancel Task ['cleaned'] True`。执行时，超时作用域把自身导致的取消转成 `TimeoutError`，外部 `cancel()` 仍传播 `CancelledError`；两条路径都等 `finally` 清理完才返回。边界是清理中再次等待也可能被取消，生产代码要用 shield 或独立清理任务并验证结果，不能假设 `finally` 一定完成所有异步收尾。

## 3. 原理讲解与推导
### 3.1 取消请求要穿过可等待边界才产生退出

取消不是立即切断任意一行代码。它通常在后续可取消等待处注入 `CancelledError`，由 `finally` 清理，再传播给等待者；已经开始的线程或远端动作不会因此自动停止。

最小数据流是 `cancel() → 下一个 await 注入 CancelledError → finally 记录 cleaned → await task 观察到 cancelled`。预期输出不是“立即返回”，而是清理事件先出现、任务再进入 cancelled 状态；如果协程不等待任何东西，取消要等它把控制权交回事件循环后才被处理。

#### 案例推进：协程会清理，运行中的线程不会被迫终止
```python
# experiment: E22
import asyncio
async def main():
    events, ready = [], asyncio.Event()
    async def work():
        events.append("started")
        ready.set()
        try: await asyncio.Event().wait()
        finally: events.append("cleaned")
    task = asyncio.create_task(work())
    await ready.wait()
    task.cancel()
    try: await task
    except asyncio.CancelledError: pass
    assert events == ["started", "cleaned"] and task.cancelled()
asyncio.run(main())
```
```python
# experiment: E24
from concurrent.futures import ThreadPoolExecutor
from threading import Event
started, release = Event(), Event()
def blocking_work(): started.set(); release.wait(); return 7
with ThreadPoolExecutor(max_workers=1) as pool:
    future = pool.submit(blocking_work)
    try:
        assert started.wait(2) and future.running()
        assert future.cancel() is False
    finally: release.set()
    assert future.result(2) == 7
```

协程在等待点响应取消并完成清理；线程已经运行后 `Future.cancel()` 返回 `False`，必须等它自然结束或由业务代码协作停止。性能比较前还要统一输入、输出和错误语义，不能只比较一次耗时。`E22` 的预期结果是断言通过、控制台无输出，事件顺序为 `started → cleaned` 且 `task.cancelled()` 为真；`E24` 同样无控制台输出，`future.cancel()` 为 `False`，释放 Event 后结果才是 7。两者分别证明协程清理与线程协作停止，不能互相替代。

### 4.1 先写订单查询契约
#### 案例推进：限制同时查询的人数
```python
# book-example: B11
import asyncio
async def query_orders(user_ids, lookup, *, concurrency=2, timeout=1.0):
    if type(concurrency) is not int or concurrency <= 0 or type(timeout) not in (int, float) or timeout <= 0: raise ValueError("并发和超时必须为正数")
    gate = asyncio.Semaphore(concurrency)
    async def one(user_id):
        async with gate:
            return await asyncio.wait_for(lookup(user_id), timeout)
    unique_ids = list(dict.fromkeys(user_ids))
    return await asyncio.gather(*(one(user_id) for user_id in unique_ids))
async def lookup(user_id): await asyncio.sleep(0); return [{"id": user_id, "user": user_id, "amount_cents": 100, "status": "paid"}]
async def main():
    rows = await query_orders(["A", "A", "B"], lookup)
    assert [orders[0]["id"] for orders in rows] == ["A", "B"]
asyncio.run(main())
```

`dict.fromkeys` 按首次出现去重，`gather` 按传入顺序返回结果。信号量只限制进入查询区域的数量，没有限制已创建的任务数；输入很大时下一步必须限制待处理数量。`B11` 的预期结果是返回 A、B 两条结果且顺序不变，断言通过、控制台无输出；重复 A 只触发一次查询，但当前实现仍会为每个唯一 ID 创建一个任务。替身 `lookup` 用 `user_id` 同时充当订单 ID 与用户名，每条订单恰好携带第12章要求的 `id/user/amount_cents/status` 四字段，因此可以直接交给 `build_report`；真实服务应返回真实字段值。
### 4.2 用固定 worker 和有界队列限制规模
#### 案例推进：让生产者遇到背压
```python
# study-example: S11E
import asyncio
async def consume(values, transform, *, workers=2, capacity=2):
    if type(workers) is not int or type(capacity) is not int or workers <= 0 or capacity <= 0: raise ValueError("workers和capacity必须为正整数")
    queue, stop, results = asyncio.Queue(capacity), object(), {}
    async def produce():
        for index, value in enumerate(values):
            await queue.put((index, value))
        for _ in range(workers): await queue.put(stop)
    async def work():
        while True:
            item = await queue.get()
            try:
                if item is stop: return
                index, value = item
                results[index] = await transform(value)
            finally: queue.task_done()
    async with asyncio.TaskGroup() as group:
        group.create_task(produce())
        for _ in range(workers): group.create_task(work())
    return [results[index] for index in sorted(results)]
async def main():
    active = peak = 0
    async def double(value):
        nonlocal active, peak
        active += 1; peak = max(peak, active)
        try:
            await asyncio.sleep(0)
            if value == 3: raise ValueError("模拟查询失败")
            return value * 2
        finally: active -= 1
    assert await consume(range(3), double) == [0, 2, 4]
    assert await consume([], double) == []
    try: await consume(range(10), double)
    except* ValueError: pass
    else: raise AssertionError("失败输入应报错")
    assert active == 0 and peak <= 2
asyncio.run(main())
```

队列满时生产者等待，这就是背压。worker 失败后任务组取消生产者和其他 worker，并等待清理；本实现选择整批失败，不返回部分成功。结果按索引放回原顺序，但 `results` 仍会随输入增长；有界队列限制的是待处理任务，不是结果内存。需要处理大规模结果时，还要改为流式写出或分页消费。`S11E` 的预期结果是前两次调用分别得到 `[0,2,4]` 与 `[]`，含 3 的失败批次抛异常组，最终 `active=0` 且 `peak<=2`；断言通过且控制台无输出。

| 操作 | 预期结果 | 证据 |
| --- | --- | --- |
| 注入正常、空输入与重复用户 | 结果去重且保持首次输入顺序，峰值不超过 N | `tests/test_queries.py` 断言与 `active/peak` 记录 |
| 注入超时、下游失败与父任务取消 | 错误类别可区分，所有异步子任务退出，`active=0` | 四条测试及 `finally` 事件列表 |
| 对已运行线程 Future 调用取消 | 返回 `False`，线程等到 Event 后才结束 | `E24` 式记录，不写成“线程已停止” |

## 7. 面试问答与迁移
**问：为什么 `async` 函数仍可能阻塞？**
答：事件循环靠真正挂起推进其他任务。函数里直接做阻塞 I/O 或长计算时，写没写 `async` 都不会自动让出；应换异步客户端或显式使用受限执行边界。
**问：`TaskGroup` 比 `gather` 总是更好吗？**
答：不是。任务组提供共同退出和异常组，适合整批成功或整批失败；需要保留部分结果时，`gather(return_exceptions=True)` 等策略可能更清楚，但仍要自己处理取消和清理。
## 8. 本章小结与参考

- 协程对象不等于已运行任务；是否切换取决于是否真正挂起。
- 并发上限、队列容量、速率和总时限分别约束不同资源。
- 取消是请求；协程、线程和远端动作的停止必须分别证明。
- 本章交付有界订单查询，第12章把它接入统一订单项目。
