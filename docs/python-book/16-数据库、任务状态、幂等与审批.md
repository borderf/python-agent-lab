## 2. 基础知识讲解

### 2.1 任务、批准和动作是三份记录

任务表保存租户、任务ID、载荷、版本和当前状态；批准记录保存谁批准了哪个版本与摘要；动作账本保存动作键、载荷摘要、回执和尝试结果。三份记录可以放在一个数据库，但不能合并成一个`done`布尔值。

数据库事务保证本地多步修改一起提交或回滚，唯一约束防止重复动作记录。查询值使用参数占位符，租户条件必须进入实际SQL。远程HTTP写入不受本地事务回滚保护，因此本地已提交不等于外部效果也已确认。

**表约束、索引与业务规则分工：**
- `PRIMARY KEY`与`UNIQUE`在写入时拒绝重复；普通索引只改善查询路径，不额外阻止重复。
- `FOREIGN KEY`守住引用关系，SQLite默认关闭外键，须在每个连接执行`PRAGMA foreign_keys=ON`；该设置不能在已开启的事务中临时改变。
- `NOT NULL`与`CHECK`适合表达稳定的行级规则；跨行状态路径、审批有效期和外部效果仍须事务、条件更新或应用校验。
- 给已有数据新增约束前先治理脏数据，否则迁移可能失败；索引和约束都不能替代业务语义测试。

三份记录可以用同一个问题链观察：任务回答“现在允许做什么”，批准回答“谁授权了哪个版本”，动作账本回答“这个动作已经产生什么效果”。以 T1 的 v1 为例：

| 输入事实 | 保存位置 | 可观察结果 | 不能据此推断 |
| --- | --- | --- | --- |
| 租户 a、任务 T1、版本 1、金额 2000 | tasks | 当前状态为 `waiting_approval` | 外部订单尚未执行 |
| 批准人 r、版本 1、摘要 H1 | approvals | H1 与当前载荷匹配 | 载荷永远不会变化 |
| 动作键 `(a, ["T1",1])`、回执 R1 | effects | 同键重放返回 R1 | 任意远端都支持该语义 |

如果任务变成 v2 而批准仍指向 v1，第一行更新成功，第二行却必须失配；恢复入口不能只看 `completed` 或一个 `done` 字段。

#### 案例推进：先画订单T1的记录边界

创建T1时先写`waiting_approval`；批准v1后写批准摘要；执行时用`(tenant_id, action_id)`生成稳定动作键。练习契约用规范JSON数组`["T1",1]`作为`action_id`，重试和恢复都保持原值；收到回执后再把任务标为`completed`。任一步失败，都应能从这三份记录判断任务停在哪里。

### 2.2 状态转换规定任务能走哪条路

基本路径是`waiting_approval → approved → executing → completed`。修改载荷只允许在审批前或执行前，修改后版本加一并清空旧批准；进入`executing`后冻结载荷，直到外部结果对账完成。

`failed`可以重新尝试，但要记录新尝试和原因，不能覆盖旧记录。取消请求到达时，先记`cancel_requested`，再查询外部效果：确认未发生才可取消，已经成功就保持完成，无法确认则进入`needs_reconciliation`。

#### 案例推进：非法跳转必须显式拒绝

`completed → executing`、过期版本恢复、跨租户读取都应失败。状态表只判断路径是否允许，不判断执行者是否有权限；恢复入口还要重新检查可信身份、当前版本和批准摘要，并用条件更新防止并发覆盖。

**用版本号做乐观锁：**
- 修改载荷使用`UPDATE tasks SET payload=?, version=version+1 WHERE tenant_id=? AND task_id=? AND version=?`，把版本作为写前快照。
- 影响行数为0表示版本已变，应重新读取并由调用方解决冲突，不能直接用旧值覆盖新值。
- 状态转换再附加`WHERE status=? AND version=?`，一次CAS同时确认来源状态与版本；权限检查仍独立进行。
- 乐观锁解决并发覆盖，不替代多行事务，也不解决外部HTTP的重复效果。

```python
# study-example: S16C
allowed = {
    "waiting_approval": {"approved"},
    "approved": {"executing"},
    "executing": {"completed", "needs_reconciliation"},
    "completed": set(),
}

def move(current, target):
    if target not in allowed.get(current, set()):
        raise ValueError("illegal transition")
    return target

assert move("waiting_approval", "approved") == "approved"
try:
    move("completed", "executing")
except ValueError:
    pass
else:
    raise AssertionError("illegal transition accepted")
```

`S16C` 的预期结果是合法转换返回 `approved`，非法转换抛出 `ValueError("illegal transition")`，断言通过且控制台无输出。执行过程只查当前状态允许的目标集合；它不查版本、批准或权限，所以不能直接用于执行入口。状态允许并不等于动作获准：例如进入`executing`前仍要核对批准；取消或未知结果也不能仅靠改状态字段假装外部动作已经停止。

版本冲突可以在 SQLite 中直接观察。第一个更新成功把版本从 1 改为 2；第二个更新仍拿着旧快照版本 1，因此影响行数必须为 0。

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE tasks (task_id TEXT PRIMARY KEY, version INTEGER, amount_cents INTEGER)")
db.execute("INSERT INTO tasks VALUES ('T1', 1, 2000)")
first = db.execute(
    "UPDATE tasks SET version=version+1, amount_cents=? WHERE task_id=? AND version=?",
    (9000, "T1", 1),
).rowcount
second = db.execute(
    "UPDATE tasks SET version=version+1, amount_cents=? WHERE task_id=? AND version=?",
    (7000, "T1", 1),
).rowcount
print(first, second, db.execute("SELECT version, amount_cents FROM tasks").fetchone())
db.close()
```

预期输出为 `1 0 (2, 9000)`。执行过程把版本当作写前快照，`WHERE` 同时限制任务和版本；影响行数为 0 时不能继续覆盖，应重新读取并由调用方解决冲突。边界是这段探针没有检查权限、批准或事务中的其他行，真实状态转换还要附加来源状态条件并放在同一事务里。

### 2.3 幂等键标识同一个业务动作

幂等键不是载荷摘要。内容相同的两笔合法订单仍是两个动作；每次重试都新生成UUID，则会把同一次动作拆成多次。键的作用域至少包含租户和动作身份，并绑定操作语义与载荷摘要。

同键同载荷返回原回执，同键不同载荷报冲突。去重记录必须持久化，保留期覆盖允许的重试和对账窗口；删除记录后仍接受旧请求，就可能再次产生效果。内存字典只能用于演示，不能证明跨进程幂等。

**把幂等作用域落到唯一约束：**
- 本章练习的权威schema是`effects(tenant_id, action_id, payload_hash, receipt)`，主键为`(tenant_id, action_id)`；`action_id`由任务ID与版本组成，只表达本章的提交订单操作。
- 若同一任务ID还能触发其他操作，生产实现可把`operation_type`加入动作身份，例如`UNIQUE(tenant_id, operation_type, action_id)`；这属于扩展，不是本练习的签名或表结构。`payload_hash`始终只用于比对，不参与动作身份。
- 并发请求可能同时查不到旧记录，先查后插不能保证去重，必须由唯一约束兜底。
- 捕获唯一冲突后，先在保存点回滚或另开事务，再按同键重新读取：同摘要返回已提交回执，不同摘要报冲突；不能把数据库异常一律当成成功。SQLite普通行id表的复合主键还允许NULL，因此本例显式加`NOT NULL`；`UNIQUE`也允许多个NULL，不能把它当必填规则。

同一动作键的三种输入可以直接形成判定表：

| 输入 | 账本中的旧记录 | 预期输出 | 原因 |
| --- | --- | --- | --- |
| 键 K、载荷 P | 无 | 写入一条效果并返回回执 R | 第一次执行 |
| 键 K、载荷 P | 摘要 H(P)、回执 R | 返回原回执 R，不新增效果 | 同动作重放 |
| 键 K、载荷 Q | 摘要 H(P)、回执 R | 冲突，不返回成功 | 同键换载荷 |
| 键 K2、载荷 P | 只有键 K | 新动作，可产生第二条效果 | 内容相同不等于动作相同 |

因此恢复时保持 K 与 P，重新生成 UUID 会从第一行变成新动作。边界是这张表只在接收方持久化并原子去重时成立；远端不支持查询或去重时，本地只能记录结果未知。

#### 案例推进：接收方承诺决定恢复上限

只有远端支持原子去重或按动作键查询时，应用才能用同键重试恢复。远端既不查询也不去重时，本地账本只能记录“结果未知”，应交人工对账，不能把方法命名为`execute_once`就宣称只执行一次。

### 2.4 批准绑定当前载荷，不是永久授权

批准记录至少包含任务、租户、操作语义、载荷版本、规范摘要、批准人和有效期。执行前重新核对当前身份和记录；载荷变化、批准过期或租户变化都会使旧批准失效。

模型声称“用户已同意”不是批准证据。摘要匹配也只能证明载荷一致，不能证明批准由可信主体签发。练习中的`approved_hash`是可信批准边界传入的数据，不是让学生自己实现登录或审批签发。

#### 案例推进：批准v1不能执行v2

审核人看到金额20.00元并批准v1；后台把金额改成90.00元形成v2后，旧摘要不再匹配。恢复v1或执行v2都必须拒绝，直到新版本重新展示并批准。

批准资格可以压缩成三个布尔条件。下面固定可信批准来自输入边界，不模拟登录或签发。

```python
approved = {"version": 1, "amount_cents": 2000, "expires_at": 10}

def can_execute(current, now):
    return (current["version"] == approved["version"]
            and current["amount_cents"] == approved["amount_cents"]
            and now < approved["expires_at"])

current_v1 = {"version": 1, "amount_cents": 2000}
current_v2 = {"version": 2, "amount_cents": 9000}
print("v1", can_execute(current_v1, 9))
print("v2", can_execute(current_v2, 9))
print("expired", can_execute(current_v1, 10))
```

预期输出为 `v1 True`、`v2 False`、`expired False`。执行过程同时比较版本、载荷与有效期；边界是摘要或字段相同不等于批准由可信主体签发，恢复入口仍要重新取得可信身份和批准记录。

## 3. 原理讲解与推导

### 3.1 崩溃窗口决定为什么需要动作账本

执行顺序是“保存意图 → 调用外部 → 外部完成 → 保存回执”。若进程在外部完成后、本地回执前崩溃，本地只能看到`executing`，不能据此断言没有效果。

恢复时保持原动作键和原载荷：接收方若返回已有回执，就补记本地完成；若报告未知，就继续冻结并核对。重新生成键会把恢复变成新动作，所以“多重试一次”反而破坏单次效果。数据库事务、远端幂等和人工对账各自覆盖不同故障窗口。

**事务边界与崩溃窗口一一对应：**
- 保存动作意图、载荷版本与`executing`标记应在一次本地事务中提交，然后再调用外部接口。
- 不能把数据库事务跨在HTTP等待上，否则网络长事务会长期占锁；外部调用成功或失败都不会自动回滚远端。
- 外部返回后，动作结果、回执与任务完成状态应在一次事务中提交，避免本地只记一半。
- 意图提交前、远端提交后回执前、本地回执提交后是不同窗口；恢复只读取已持久化事实，不靠进程内存猜测。

崩溃窗口可以用时间线逐一判定，而不是看任务是否“失败”：

| 崩溃时点 | 本地持久事实 | 允许的恢复动作 | 禁止动作 |
| --- | --- | --- | --- |
| 动作意图提交前 | 没有 `executing` 与动作账本 | 重新校验批准后重新开始 | 假装已有外部效果 |
| 外部提交后、本地回执前 | `executing`，动作键 K 已保存 | 用原键 K 与原载荷查询或幂等重试 | 生成新 UUID |
| 本地回执提交后 | `completed` 与回执均存在 | 同键重放返回原回执 | 再次创建新业务动作 |

以 T1 为例，第二种窗口的预期输出是“效果数仍为 1、任务补记 completed、回执不变”；若接收方无法确认，则预期是 `needs_reconciliation`，不是成功也不是确定失败。

## 4. 示例与逐步走查

### 4.1 第一步：保存订单T1的三份事实

```json
{"task_id":"T1","tenant_id":"a","version":1,"payload":{"amount_cents":2000},"payload_hash":"当前载荷的规范摘要","status":"approved","approved_hash":"与当前摘要相同的可信批准","action_id":"[\"T1\",1]"}
```

这份记录把任务状态、批准对象和动作身份放在一起检查，但实现时仍应分表保存。`action_id`由任务ID与版本按规范JSON数组生成，在重试和恢复中保持不变，`payload_hash`只用于发现同键参数变化。

### 4.2 第二步：用SQLite实现持久幂等接收方

**以练习代码契约为准：** `tests/learner/练习说明.md`、两个`contract_*.py`及起始签名规定，`submit`没有`operation_type`参数，`effects`只有`tenant_id、action_id、payload_hash、receipt`四列，主键是`(tenant_id, action_id)`。`practice/architecture_labs/idempotency_sqlite.py`是另一组`actions/effects`实验，不是本章练习schema。生产端可以扩展操作类型，但不能让本章示例与练习签名、主键不一致。

```python
# study-example: S16A
from contextlib import closing
from hashlib import sha256
import json
from pathlib import Path
import sqlite3
from tempfile import TemporaryDirectory

def payload_hash(payload):
    if not isinstance(payload, dict):
        raise ValueError("payload must be an object")
    raw = json.dumps(payload, sort_keys=True, separators=(",", ":"),
                     ensure_ascii=False, allow_nan=False).encode("utf-8")
    return sha256(raw).hexdigest()

def submit(db_path, *, tenant_id, action_id, payload, approved_hash, fail_after_commit=False):
    if (not isinstance(tenant_id, str) or not tenant_id.strip()
            or not isinstance(action_id, str) or not action_id.strip()):
        raise ValueError("nonempty tenant and action IDs required")
    digest = payload_hash(payload)
    if digest != approved_hash:
        raise PermissionError("approval does not match payload")
    with closing(sqlite3.connect(db_path)) as db:
        db.execute("CREATE TABLE IF NOT EXISTS effects "
                   "(tenant_id TEXT NOT NULL, action_id TEXT NOT NULL, "
                   "payload_hash TEXT NOT NULL, receipt TEXT NOT NULL, "
                   "PRIMARY KEY(tenant_id, action_id))")
        with db:
            db.execute("BEGIN IMMEDIATE")
            old = db.execute("SELECT payload_hash, receipt FROM effects "
                             "WHERE tenant_id=? AND action_id=?",
                             (tenant_id, action_id)).fetchone()
            if old:
                if old[0] != digest:
                    raise ValueError("same action ID with changed payload")
                receipt = old[1]
            else:
                receipt = f"{tenant_id}/{action_id}"
                db.execute("INSERT INTO effects VALUES (?, ?, ?, ?)",
                           (tenant_id, action_id, digest, receipt))
    if fail_after_commit:
        raise RuntimeError("simulated crash after commit")
    return receipt

with TemporaryDirectory() as directory:
    path = Path(directory) / "effects.sqlite"
    payload = {"amount_cents": 2000}
    approved = payload_hash(payload)
    first = submit(path, tenant_id="a", action_id='["T1",1]',
                   payload=payload, approved_hash=approved)
    assert submit(path, tenant_id="a", action_id='["T1",1]',
                  payload=payload, approved_hash=approved) == first
    try:
        submit(path, tenant_id="a", action_id='["T1",1]',
               payload={"amount_cents": 9000},
               approved_hash=payload_hash({"amount_cents": 9000}))
    except ValueError:
        pass
    else:
        raise AssertionError("same action ID with changed payload must conflict")
    try:
        submit(path, tenant_id="b", action_id='["T1",2]',
               payload=payload, approved_hash=approved, fail_after_commit=True)
    except RuntimeError:
        pass
    receipt = submit(path, tenant_id="b", action_id='["T1",2]',
                     payload=payload, approved_hash=approved)
    assert submit(path, tenant_id="b", action_id='["T1",2]',
                  payload=payload, approved_hash=approved) == receipt
    with closing(sqlite3.connect(path)) as db:
        assert db.execute("SELECT COUNT(*) FROM effects").fetchone()[0] == 2
```

效果与回执在同一事务写入，复合主键处理同一作用域内的重复动作。`BEGIN IMMEDIATE`让同一数据库的并发写者串行完成“先查后插”，唯一约束仍是最终兜底；跨进程生产实现还应处理锁等待与唯一冲突。示例用摘要匹配模拟可信批准输入，没有实现批准签发；`fail_after_commit`模拟外部已提交但调用方没收到回执。

`S16A` 的预期结果是首次回执为 `a/["T1",1]`，同键同载荷重放得到同一字符串，同键换 9000 抛 `ValueError`，租户 b 的丢回执恢复仍得到 `b/["T1",2]`，最终 `effects` 表恰好两行；控制台无输出。执行过程先校验批准摘要，再在写事务中查旧记录、插入效果并提交，崩溃模拟发生在提交之后。回执文本只要非空且稳定即可，本示例用租户与动作键拼接，练习参考实现则使用UUID。

### 4.3 第三步：冻结任务并按原键恢复

下面的`S16B`把练习的任务表与效果表放进同一个`:memory:`数据库，直接观察版本、批准、冻结和原键恢复如何联动。练习把可信批准摘要保存在`tasks.approved_hash`，没有实现批准签发或失效查询。为保持单连接示例最短，函数省略了正式模块的`db_path`参数，但字段、状态规则、`effects` schema与稳定动作键均沿用练习契约。

```python
# study-example: S16B
import json
import sqlite3
from hashlib import sha256

db = sqlite3.connect(":memory:")
db.row_factory = sqlite3.Row
db.executescript("""
    CREATE TABLE tasks (
        tenant_id TEXT, task_id TEXT, version INTEGER NOT NULL,
        payload TEXT NOT NULL, payload_hash TEXT NOT NULL, approved_hash TEXT,
        status TEXT NOT NULL, receipt TEXT,
        PRIMARY KEY(tenant_id, task_id)
    );
    CREATE TABLE effects (
        tenant_id TEXT NOT NULL, action_id TEXT NOT NULL,
        payload_hash TEXT NOT NULL, receipt TEXT NOT NULL,
        PRIMARY KEY(tenant_id, action_id)
    );
""")

def encode(payload):
    return json.dumps(payload, sort_keys=True, separators=(",", ":"),
                      ensure_ascii=False, allow_nan=False)

def payload_hash(payload):
    return sha256(encode(payload).encode("utf-8")).hexdigest()

def load(expected_version=None):
    row = db.execute("SELECT * FROM tasks WHERE tenant_id='a' AND task_id='T1'").fetchone()
    if row is None:
        raise LookupError("task not found")
    if expected_version is not None and row["version"] != expected_version:
        raise PermissionError("stale task version")
    return row

def prepare(payload):
    content = encode(payload)
    with db:
        db.execute("INSERT INTO tasks VALUES ('a', 'T1', 1, ?, ?, NULL, "
                   "'waiting_approval', NULL)", (content, payload_hash(payload)))
    return load()

def approve(expected_version, expected_hash):
    with db:
        row = load(expected_version)
        if row["status"] != "waiting_approval" or row["payload_hash"] != expected_hash:
            raise PermissionError("approval no longer matches the displayed payload")
        db.execute("UPDATE tasks SET approved_hash=?, status='approved' "
                   "WHERE tenant_id='a' AND task_id='T1' AND version=? "
                   "AND status='waiting_approval'", (expected_hash, expected_version))

def change_payload(expected_version, payload):
    content = encode(payload)
    with db:
        row = load(expected_version)
        if row["status"] not in {"waiting_approval", "approved"}:
            raise ValueError("executing or completed payload is frozen")
        db.execute("UPDATE tasks SET version=version+1, payload=?, payload_hash=?, "
                   "approved_hash=NULL, status='waiting_approval' "
                   "WHERE tenant_id='a' AND task_id='T1' AND version=? "
                   "AND status IN ('waiting_approval', 'approved')",
                   (content, payload_hash(payload), expected_version))
    return load()

def effect_count():
    return db.execute("SELECT COUNT(*) FROM effects").fetchone()[0]

def resume(expected_version, fail_after_commit=False):
    # 先提交 executing；外部效果不能与这个本地事务绑在一起。
    with db:
        row = load(expected_version)
        if row["status"] == "completed":
            return row["receipt"]
        if (row["status"] not in {"approved", "executing"}
                or row["approved_hash"] != row["payload_hash"]):
            raise PermissionError("current payload has not been approved")
        db.execute("UPDATE tasks SET status='executing' "
                   "WHERE tenant_id='a' AND task_id='T1' AND version=? "
                   "AND status IN ('approved', 'executing')", (expected_version,))

    # 原键只由任务 ID 与版本生成；恢复时不换 UUID、不按新载荷另造键。
    action_id = encode([row["task_id"], row["version"]])
    with db:
        old = db.execute("SELECT payload_hash, receipt FROM effects "
                         "WHERE tenant_id='a' AND action_id=?", (action_id,)).fetchone()
        if old:
            if old["payload_hash"] != row["payload_hash"]:
                raise ValueError("action key reused with changed payload")
            receipt = old["receipt"]
        else:
            receipt = f"a/{action_id}"
            db.execute("INSERT INTO effects VALUES ('a', ?, ?, ?)",
                       (action_id, row["payload_hash"], receipt))
    if fail_after_commit:
        raise RuntimeError("simulated lost reply after commit")

    with db:
        db.execute("UPDATE tasks SET status='completed', receipt=? "
                   "WHERE tenant_id='a' AND task_id='T1' AND version=? "
                   "AND status='executing'", (receipt, expected_version))
    return receipt

def rejected(label, action):
    try:
        action()
    except (PermissionError, ValueError) as error:
        print(f"rejected: {label} ({type(error).__name__})")
    else:
        raise AssertionError(f"{label} must be rejected")

row = prepare({"amount_cents": 2000})
v1_hash = row["payload_hash"]
print(f"saved: version={row['version']} status={row['status']}")
approve(1, v1_hash)
row = load(1)
print(f"approved: version={row['version']} status={row['status']}")
row = change_payload(1, {"amount_cents": 9000})
print(f"changed: version={row['version']} status={row['status']} approved_hash={row['approved_hash']}")
rejected("stale version", lambda: resume(1))
rejected("old approval", lambda: approve(2, v1_hash))
rejected("unapproved resume", lambda: resume(2))
assert effect_count() == 0

approve(2, row["payload_hash"])
try:
    resume(2, fail_after_commit=True)
except RuntimeError as error:
    assert "after commit" in str(error)
row = load(2)
print(f"lost reply: status={row['status']} receipt={row['receipt']} effects={effect_count()}")
rejected("frozen payload", lambda: change_payload(2, {"amount_cents": 1000}))
receipt = resume(2)
row = load(2)
assert receipt == 'a/["T1",2]'
print(f"recovered: receipt={receipt} status={row['status']} effects={effect_count()}")
assert resume(2) == receipt and effect_count() == 1
print(f"replay: {resume(2)} effects={effect_count()}")
db.close()
```

预期输出为：

```text
saved: version=1 status=waiting_approval
approved: version=1 status=approved
changed: version=2 status=waiting_approval approved_hash=None
rejected: stale version (PermissionError)
rejected: old approval (PermissionError)
rejected: unapproved resume (PermissionError)
lost reply: status=executing receipt=None effects=1
rejected: frozen payload (ValueError)
recovered: receipt=a/["T1",2] status=completed effects=1
replay: a/["T1",2] effects=1
```

关键联动是：改载荷使版本加一并清空批准，旧版本与旧摘要都在执行前被拒绝；`executing`提交后才模拟效果提交，因此丢回执时任务没有 receipt、效果却已有一行。恢复仍从任务读取版本2，重新生成同一个`["T1",2]`键并读到原回执，随后补记`completed`。同键恢复与重复完成请求都不会新增效果。这个内存示例只压缩展示因果链；跨进程持久恢复仍按练习使用数据库文件，并运行`contract_resume.py`。

### 6.2 用操作、预期结果与证据验收

| 操作 | 预期结果 | 证据 |
| --- | --- | --- |
| 同键同载荷提交两次 | 返回同一回执，效果表只增一行 | `effects` 查询与行数 |
| 同键换载荷、换版本或使用未批准记录 | 冲突或执行前拒绝，零新增效果 | 异常类型、版本与批准记录 |

批准有效期是2.4的独立规则；当前接收方与恢复契约不实现失效查询。若扩展 `expires_at`，应同时补齐可信批准记录、执行前检查和等号边界测试，不能只改验收描述。

## 7. 面试问答与迁移

**问：本地事务能保证外部订单只写一次吗？** 不能。它只保护本地记录；外部写入与本地回执之间有崩溃窗口，需要远端幂等、状态查询或人工对账。

**问：幂等键、载荷摘要和批准记录有什么区别？** 键标识动作，摘要检查参数是否变化，批准记录证明当前动作是否获准。三者职责不同，不能互相替代。

**问：任务已完成但用户再次提交怎么办？** 先识别这是同一动作的重放还是新订单。前者返回原回执，后者使用新动作键并重新审批，不能仅凭载荷相同去重。

## 8. 本章小结与参考

- 任务、批准和动作账本分别保存阶段、授权和效果，不用一个状态字段概括全部事实。
- 状态转换限制路径，版本与摘要限制执行资格，二者都要在恢复入口重新检查。
- 稳定动作键把重复调用压成同一效果；同键换载荷必须冲突。
- 外部成功而本地未记回执时，保持原键恢复，不能把`pending`当作确定失败。
- SQLite接收方是真实持久化模拟，不证明任意远端具有相同幂等契约。
