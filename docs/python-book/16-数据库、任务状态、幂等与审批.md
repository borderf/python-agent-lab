# 第16章　数据库、任务状态、幂等与审批

## 1. 学习目标与前置知识

把持久化、图状态和业务效果区分开。前置：第8、11、15章。

**承接与本章主线：** 把请求中的状态移入数据库及动作记录，用事务、版本和幂等保护不变量；恢复和部署按第17章验证。

**本章从这里开始：** 用户点了两次提交，或者程序在写入成功后崩溃。同一动作可能再次到达，系统应产生几次业务效果？本章从具体故障窗口推导状态与幂等。

## 2. 基础知识讲解

### 2.1 持久化系统中的不同记录

内存字典能记录任务进度，却在进程重启后消失。即使把状态写进数据库，远端提交成功而本地尚未记成功的窗口仍然存在。因此先定义任务和动作的状态，再确定哪些修改由本地事务保护、哪些需要幂等与对账。数据库提供持久性，并不自动把多个系统变成一个事务。

先按一次审批过程分开记录：用户创建任务T1，得到一份待审报告；审核人批准这份报告的版本；程序向外部系统发送动作；最后核对外部回执。任务表保存归属与状态，审批记录保存批准对象，动作账本保存请求与效果。先能用这几份记录解释成功、拒绝和重复请求，后面再讨论审计事件与图checkpoint，避免把所有信息塞进聊天历史。

业务任务记录回答任务属于谁、当前状态是什么；图checkpoint保存执行位置与中间状态；审批记录回答谁批准了哪个载荷；动作账本记录对外请求与已确认效果；审计事件解释发生顺序。它们可以共享数据库，却不应混成一份无限增长的聊天记录。

#### 从表、约束和索引理解持久化

关系表将任务、审批与尝试分开保存，主键标识记录，外键表达关联，唯一约束保护业务身份。索引提高某类查询效率，也占空间并增加写入维护代价；不是列越多索引越好。先看实际查询与执行计划，再决定索引。

```python
# study-example: S16B
import sqlite3
from contextlib import closing
with closing(sqlite3.connect(":memory:")) as connection:
    connection.execute("CREATE TABLE jobs (id TEXT PRIMARY KEY, tenant TEXT NOT NULL, status TEXT NOT NULL)")
    connection.execute("CREATE INDEX jobs_tenant_status ON jobs(tenant, status)")
    with connection:
        connection.executemany("INSERT INTO jobs VALUES (?, ?, ?)", [("A","a","queued"),("B","b","queued")])
    rows = connection.execute("SELECT id FROM jobs WHERE tenant=? AND status=? ORDER BY id", ("a","queued")).fetchall()
    assert rows == [("A",)]
```

查询值参数化，同时把租户条件写进实际查询；SQL安全与资源授权是不同检查。ORM映射对象和表，并不取消SQL、事务或授权知识；读取关联时逐条查询可能出现N+1，需观察实际查询次数。Schema迁移将表结构变化版本化，数据迁移、回滚与备份恢复也要单独验证，而不是启动时随意删除旧表。

缓存与任务队列是进一步的工程选择。缓存是派生数据，需要失效、身份范围、容量与并发更新策略；队列消息可能重投，消费者仍需幂等，进程内后台任务不等于可靠持久队列。先用数据库与模拟队列讲清契约，再选择Redis等具体服务。

### 2.2 先定义状态转换再写接口

queued进入running，可能完成、失败、取消或等待审批。审批拒绝和执行失败不是同一种结果；失败重试要记录新attempt与原因。取消请求到达时动作可能正在进行，需确认实际效果后更新状态，不能想当然地宣布回滚。

### 2.3 事务能保证什么

数据库事务约束其负责范围内的修改，提交/回滚与隔离级别影响可见性。远程HTTP写入不因本地事务失败就自动撤销，跨服务动作要考虑消息、幂等和对账策略。缓存与锁只能解决部分协调问题，不能替代可靠动作记录。

### 2.4 幂等键识别重复动作

一个action_id或幂等键应对应约定范围内的同一业务动作与载荷。重复请求应返回已知结果或一致处理，不新增额外效果；错误复用同一个键也可能误抑制另一个合法动作，所以作用域、载荷关系和保留期需明确。

#### 案例推进：用稳定动作键识别重放

```python
# study-example: S16A
class MockWriter:
    def __init__(self):
        self.actions = {}
        self.effects = []
    def submit(self, key, payload):
        snapshot = dict(payload)
        if key in self.actions:
            old_payload, result = self.actions[key]
            if old_payload != snapshot:
                raise ValueError("同一动作键不能改变参数")
            return result
        result = {"report_id":len(self.effects) + 1}
        self.effects.append(snapshot)
        self.actions[key] = (snapshot, result)
        return result

writer = MockWriter()
first = writer.submit("job-A:v1", {"status":"reviewed"})
second = writer.submit("job-A:v1", {"status":"reviewed"})
assert first == second and len(writer.effects) == 1
```

这是单进程、无并发的模拟远端，不是生产级幂等存储。真实系统需要持久化、并发约束和服务端保证。例子展示关键关系：动作身份、载荷一致性和效果记录，而不是宣称加一个字典就解决分布式执行。

### 2.5 审批绑定具体载荷

审批不是永远授予某Agent写权限。它需要绑定任务、操作类型、载荷版本/哈希、审批人和有效期；身份或载荷变了，旧审批不能继续使用。执行点再次检查权限，模型声称“用户同意”不等于存在合法审批记录。

#### 案例推进：审批授权的是具体版本

任务状态描述处理阶段，审批记录描述谁批准哪个载荷，执行记录描述尝试与外部效果。三个概念不要合成一个done布尔值。批准v1后载荷变成v2，应重新审核；重复恢复旧任务也要检查身份、状态和版本。

数据库唯一约束保护记录唯一性，事务保护本地多步修改；并发更新还可能需要版本号/比较后更新、锁或其他协调方式。状态转换应显式拒绝不允许的跳转，恢复先对账再决定下一步。必要时研究outbox等模式，但要先知道它缓解的是哪一段双写问题。

### 2.6 恢复先面对不确定状态

外部写入完成、本地成功状态尚未落库时崩溃，恢复后不能只根据本地pending再次写。先按幂等键查询或对账，再补记结果；对无法确定的状态交人工处理，而不是伪造确定结论。

#### 案例推进：把崩溃放到正确的位置

时间线为：本地记录待执行→远端成功→本地记录成功。若在最后一步前崩溃，本地看到的是不确定，而非确定失败。恢复时用原动作键查询或重试，不能产生新键后再提交。一次数据库事务无法同时回滚外部HTTP效果。

## 3. 原理讲解与推导

### 3.1 至少一次调用与单次业务效果不同

网络可能重试、调用方可能重复提交、节点可能被重放。要把重复执行压缩成同一业务效果，需要持久化标识、受控外部接口和恢复策略共同作用；单个进程内布尔标志不足以跨重启保证。

### 3.2 故障窗口解释设计的必要性

按“记录意图→发送→外部完成→记录成功”逐步插入崩溃点，检查恢复看到什么。每个无法分辨的窗口都需要查询、幂等或人工对账，而不是更多无条件重试。

## 4. 示例与逐步走查

### 重复恢复案例

```json
{"task_id":"T1","action_id":"A1","payload_version":2,"approval":"approved","status":"pending"}
```

第一次调用外部模拟服务成功后进程崩溃；第二次恢复用相同action_id查到已完成结果，补记本地状态，而不是再新增一条业务记录。若payload_version变成3，版本2的审批不得继续使用。演练时断言外部效果数为1，并保存两次请求的审计记录。

### 4.1 沿输入到结果逐步解释

动作A1已经发往外部模拟服务，但本地仍显示pending：进程恰好在远端成功与本地记录成功之间崩溃。本地状态不能单独证明远端没有发生效果。

恢复时携带相同动作键查询或重试，前提是远端支持对应幂等契约；确认已有结果后补记本地状态。若远端既不能按键查询又不去重，需要人工对账，不能直接承诺一次效果。

把载荷从版本2改成3是另一种变化：旧批准只针对版本2，必须重新批准。幂等解决重复，批准解决允许执行什么，二者不能互相替代。

## 7. 面试问答与迁移

Checkpoint 能否保证外部接口 exactly-once？幂等键作用域与过期应该如何设计？

**参考回答：**

1. Checkpoint保存工作流恢复所需状态，不与远端副作用自动组成一个事务。若远端成功后、本地记录前崩溃，恢复可能重进节点。动作账本便于追踪未知结果，但若接收方不支持原子去重或状态查询，仅靠本地账本仍无法保证一次效果。
2. 分开设计动作标识、作用域和载荷摘要。例如以 `(tenant_id, action_id)` 唯一识别一次提交，另存操作类型、载荷摘要与回执；同键同载荷返回原结果，同键不同载荷报冲突。谁有权发起或重试由授权规则决定，主体可记录在审计中，也可按业务纳入作用域，不能机械套固定字段集合。
3. 不宜把载荷摘要当作唯一动作身份：内容相同的两次合法购买可能是两件事；也不应因载荷改变就悄悄换键，否则绕过同键冲突检测。新动作与新批准应显式创建。保留期覆盖允许的重试/对账窗口；若删除去重记录后仍接受旧请求，可能再次产生效果，只有审计日志并不能阻止它。

**换条件自测：** 分别测试“同动作同载荷重放”“同动作换载荷”“新动作但载荷相同”。前两项应复用/冲突，第三项按业务规则独立处理；再测试记录过期后的旧请求策略。对应[接收方契约](../../tests/learner/contract_approval.py)只覆盖本地接收方，不证明真实远端或批准签发链正确。

## 8. 本章小结与参考

### 8.1 主要知识点总结

- 任务状态、执行检查点、审批、动作账本与审计记录保存不同事实。
- 事务与条件更新保护数据库内的不变量，并发冲突需要明确反馈。
- 审批绑定任务、主体、动作与载荷版本；载荷变化需重新确认。
- 稳定幂等键与效果核对处理重复和未知结果，不能由一次超时推断动作没发生。

### 8.2 日常工作注意事项

- 数据库会话与事务范围要尽量清楚，避免持有事务等待长时间模型或网络调用。
- 同一个幂等键对应不同载荷时报告冲突；并发重复请求也要由持久约束处理，不能只靠内存字典。
- 外部提交超时后先查询或对账；本地事务回滚不代表外部效果也回滚，恢复时保留原动作身份。
