## 2. 基础知识讲解

先看第 3–4 章学过的字典写法，再把同一份任务写成 `ReviewJob`。比较两种写法时，做同一个检查。给 A 加一条发现，看看 B 会不会变。

### 2.1 先让每份任务拥有自己的状态

每份任务都有名称和发现列表。先判断这件事需不需要类。第 4 章的小计 `subtotal(cents, count)` 只有输入、计算和返回值，两次调用之间不保存进度，用函数就够。要连续记录同一份任务的发现，就需要一个能保存状态的地方：字典可以做到，但规则仍写在外部函数里。先看字典版。

```python
# study-example: S06G
def add_finding(job, text):
    job["findings"].append(text)

job_a = {"name": "A", "findings": []}
job_b = {"name": "B", "findings": []}
add_finding(job_a, "缺少附件")
assert job_a["findings"] == ["缺少附件"]
assert job_b["findings"] == []
```

上面的写法已经可以正确工作。现在加一个要求：每次创建任务时，都自动保存名称并准备一个空列表。可以把这段初始化和添加发现的操作写进同一个 `ReviewJob` 类：状态和 `add` 从此绑在同一个对象上。`ReviewJob("A")` 创建出一个具体任务，这个对象叫作**实例**。

#### 案例推进：从字典到两份独立状态

```python
# study-example: S06A
class ReviewJob:
    def __init__(self, name):
        self.name = name
        self.findings = []
    def add(self, finding):
        self.findings.append(finding)

a, b = ReviewJob("A"), ReviewJob("B")
a.add("缺少附件")
assert a.findings == ["缺少附件"] and b.findings == []
assert a.findings is not b.findings
```

按执行顺序看这段代码。`class` 只定义了做法，A、B 还没出现；表里每一行是那条语句执行完时的状态。

| 执行到 | 这次调用的 `self` | A 的列表 | B 的列表 |
| --- | --- | --- | --- |
| `ReviewJob("A")` | A | `[]`（新建） | 还没创建 |
| `ReviewJob("B")` | B | `[]` | `[]`（新建） |
| `a.add("缺少附件")` | `a` | `["缺少附件"]` | `[]` |

执行 `ReviewJob("A")` 时，Python 先创建一个实例，再把它作为第一个参数传给 `__init__`，所以 `__init__` 里的 `self` 就是刚创建的对象。第二次创建 B，`self` 换成 B，`[]` 也重新执行一次。

`a.add("缺少附件")` 可以按 `ReviewJob.add(a, "缺少附件")` 来读：点号只是把左边的对象自动填进第一个参数，所以修改的是 `a.findings`。`self` 不是关键字，只是第一个参数的约定名字；示例最后的 `is not` 断言检查两个列表是不是各有一份。

**把对象换一次。** 在示例末尾加一行 `ReviewJob.add(b, "金额待核对")`，先预测哪份列表会变，再运行。`b` 会填进 `self`，改动落在 B 上。

**这一步的规则：容器在 `__init__` 里创建。** 反过来，把容器写在类体里会怎样？类体不是每次创建实例都执行：执行到 `class` 语句时，类体跑一次（模块顶层就是一次；写在函数里则每次调用都跑），里面定义的名字最后都放进 `SharedJob.__dict__`，所以 `findings` 是类属性。`SharedJob()` 只创建实例：本例没有定义 `__init__`，创建完就结束，不会重跑类体。先预测 B 能看到什么，再运行下面的对照例子。

```python
# study-example: S06O
class SharedJob:
    findings = []             # 类上的一个列表
    def add(self, text):
        self.findings.append(text)

a, b = SharedJob(), SharedJob()
a.add("缺少附件")
assert a.findings is b.findings
assert b.findings == ["缺少附件"]
assert a.__dict__ == {} and b.__dict__ == {}          # 两个实例自己没有 findings
assert SharedJob.__dict__["findings"] is a.findings   # 列表在类上
```

两个实例的属性字典都是空的，`findings` 只存在类上。普通属性的查找顺序是：先查实例自己的属性，没有再沿类（以及父类）往上找。在这个类里读 `a.findings`，A 自己的属性里没有，于是找到 `SharedJob.findings`；`b.findings` 走同一条路，落到同一个列表上。`append` 改的是这个已经找到的列表，并没有给两个实例各建一份，所以 B 也看到 A 添加的发现。

#### 类与实例仍然是同一对象图中的节点

用第 1 章的箭头画出来：

```text
a.add("缺少附件") 之后
a ──→ A ──┐
          ├──→ SharedJob.findings：["缺少附件"]
b ──→ B ──┘

a.findings = [] 之后
a ──→ A ──→ []（A 新建的列表）
b ──→ B ──→ SharedJob.findings：["缺少附件"]
```

**试着加一行。** 在最后加上 `a.findings = []`。这条赋值在 A 自己的属性里新建一项（A 的属性字典变成 `{"findings": []}`），不改类上的列表；A 现在读到空列表，B 仍读到原列表（B 的属性字典仍为空）。对照 `a.findings.append(...)`：前者换掉 A 指向的列表，后者改的是已经找到的列表。

| 属性写在哪 | 什么时候创建 | 谁共享 | 适合放什么 |
| --- | --- | --- | --- |
| `__init__` 里的 `self.findings = []` | 每次创建实例时执行一次 | 每个实例一份 | 每个任务自己的发现、状态 |
| 类体里的 `findings = []` | 每次执行到 `class` 语句时一次（模块顶层就是一次） | 所有实例读到同一个 | 常量、默认配置 |

这张表只描述这两个例子里的容器。赋值不一定总落在实例上：2.2 的只读 `property` 会接管 `a.value = ...`，读取也会先走它；3.5 再讲它凭什么能挡住。实例属性具体存在哪、查找顺序的完整规则，也放在 3.1 和 3.5；用 `__slots__` 的类没有实例属性字典，3.1 会提到。

**本步之后：** `ReviewJob` 有名称、发现列表和 `add`，两份任务的列表互不影响。下一步让方法决定“什么算合法的发现”。

### 2.2 先检查再修改：只读属性与命名构造

现在每次添加发现，都要求先去掉首尾空白，空文本要报错。检查写在哪里？

字典版也能加检查：把 `add_finding` 改成先验证再 `append` 就行。区别在入口。规则在函数里、数据在字典里，拿到字典的人可以不调这个函数；类把数据和 `add` 放在一起，调用点从“记得去找某个函数”变成 `job.add(...)`。它不封锁别的写法，只是让正确写法成为拿到对象就能看到的默认入口。

#### 案例推进：检查发生在修改之前

```python
# study-example: S06I
class ReviewJob:
    def __init__(self, name):
        self.name = name
        self.findings = []

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

job = ReviewJob("A")
job.add(" 缺少附件 ")
try:
    job.add("  ")
except ValueError:
    pass
else:
    raise AssertionError("空发现应被拒绝")
assert job.findings == ["缺少附件"]
```

入口变自然了，但没有变成唯一。试着执行 `job.findings.append(" ")`，可以看到它会直接修改列表，完全绕过 `add`；这条检查只保护“通过 `add` 修改”的路径。

要不要连直接修改也挡住，是接口设计的选择：需要把内部列表藏起来，对外只给副本或只读视图。这件事 L14 会要求你自己处理（“公开接口不得意外暴露内部可变状态”）。这里先看清两个更基础的入口。

#### 选读：只读属性与命名构造

下面换一个更小的对象，只放一个数值：`Limit.from_text("3")` 从文本创建实例，`limit.value` 读取实例保存的数值。换小对象是为了让“读走代码、写被拒绝”不被别的字段干扰。

```python
# study-example: S06B
class Limit:
    def __init__(self, value):
        if type(value) is not int or value <= 0:
            raise ValueError("limit必须是正整数")
        self._value = value
    @property
    def value(self):
        return self._value
    @classmethod
    def from_text(cls, text):
        return cls(int(text))

limit = Limit.from_text("3")
assert limit.value == 3
try:
    limit.value = 4
except AttributeError:
    pass
else:
    raise AssertionError("只读property应拒绝普通赋值")
```

1. **创建。** `Limit.from_text("3")` 是类方法。`@classmethod` 让 `cls` 自动收到 `Limit`。`int(text)` 先得到 `3`，然后 `cls(3)` 创建实例，继续走 `__init__` 的正整数检查。
2. **读取。** `limit.value` 会执行 `@property` 修饰的 `value` 方法，得到保存的 `_value`。调用者像读取普通属性一样写，无需加括号。
3. **赋值。** 本例只给 `value` 写了读取方法，`limit.value = 4` 会抛 `AttributeError`。`_value` 的下划线表示内部使用的约定，普通代码仍可访问它。

两个入口各解决一件事。`@classmethod` 把文本转换和检查留在类里，调用方不必先自己 `int()`；用 `cls` 而不写死 `Limit`，子类调用时才能创建子类。`@property` 让读取可以执行代码，同时把普通赋值关掉。第 4 章学过自己写装饰器，这里的两个是内置的；3.5 再解释它们怎样接管属性访问。

**试着改一处。** 分别传 `"bad"` 和 `"0"`。前者在 `int(text)` 转换时失败，后者能转成整数，但会在 `__init__` 的范围检查处失败。

到这里，`add` 已经会在修改前检查输入。下一步保留这个方法，换一种方式初始化任务。

### 2.3 用 dataclass 少写初始化，规则仍要自己写

回到审查任务。每次手写 `__init__` 都要重复保存这两个字段，可以用 `@dataclass` 根据字段声明生成初始化方法。下面的 `name: str` 和 `findings: list[str]` 说明预期类型，实际输入仍需按业务检查。

#### 案例推进：数据类生成初始化，不生成业务规则

```python
# study-example: S06C
from dataclasses import dataclass, field

@dataclass
class ReviewJob:
    name: str
    findings: list[str] = field(default_factory=list)

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

a, b = ReviewJob("A"), ReviewJob("B")
a.add(" 缺少附件 ")
assert a.findings is not b.findings
assert b.findings == []
assert a == ReviewJob("A", ["缺少附件"])
```

读三个观察点。

1. `ReviewJob("A")` 没提供 `findings`，生成的 `__init__` 会调用 `list()`，为 A 创建一个空列表。B 也会单独创建一个，和 2.1 手写 `self.findings = []` 的效果相同。
2. 显式传入列表时，构造函数会直接保存它。如果两个实例都传入同一个列表，它们就会共享。
3. `a == ReviewJob("A", ["缺少附件"])` 比较两个同类实例的字段值。这个 `__eq__` 由 `@dataclass` 生成。`add` 仍是我们在 2.2 写的方法。

构造时不会按类型注解校验输入，例如 `ReviewJob(123)` 仍能创建实例。例中的 `add` 检查的是通过它添加的每条发现。

#### 选读：frozen 对内部列表有什么影响

下一段把类设为 `frozen=True`。先分别预测 `snapshot.name = "B"` 和 `snapshot.findings.append(...)` 会怎样。

```python
# study-example: S06L
from dataclasses import FrozenInstanceError, dataclass, field

@dataclass(frozen=True)
class Snapshot:
    name: str
    findings: list[str] = field(default_factory=list)

snapshot = Snapshot("A")
snapshot.findings.append("缺少附件")  # 修改列表内容
try:
    snapshot.name = "B"              # 尝试重新绑定字段
except FrozenInstanceError:
    pass
else:
    raise AssertionError("frozen字段不允许普通重新赋值")
assert snapshot.findings == ["缺少附件"]
```

`snapshot.name = "B"` 想换掉属性指向的值，被 `frozen` 拒绝。`snapshot.findings.append(...)` 只是向那个列表添加内容，所以仍会成功。若要让发现集合本身不能增删，可以使用装着字符串的元组。`frozen` 还会牵涉哈希生成，3.3 用另一个例子单独看。

**本步之后：** 字段声明加 `default_factory` 省掉了 `__init__`；规则和 `add` 仍由你写。

### 2.4 让对象参与语言操作：len、for 与 ==

保留 2.3 的数据类和 `add`，只加两个方法。`__len__` 返回发现数量，所以调用方能用 `len(job)`；`__iter__` 交出一个迭代器，`for` 先取得它，再逐项取值。Python 对这些操作和方法的约定叫**协议**。这些双下划线方法不是给调用方直接调的：你实现它们，Python 在执行 `len()`、`for`、`==` 等语法时按约定来调。

```python
# study-example: S06J
from dataclasses import dataclass, field

@dataclass
class ReviewJob:
    name: str
    findings: list[str] = field(default_factory=list)

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

    def __len__(self):
        return len(self.findings)

    def __iter__(self):
        return iter(self.findings)

job = ReviewJob("A")
job.add("缺少附件")
job.add("金额待核对")
assert len(job) == 2
assert list(job) == ["缺少附件", "金额待核对"]
assert job == ReviewJob("A", ["缺少附件", "金额待核对"])

position = iter(job)
assert next(position) == "缺少附件"
assert list(position) == ["金额待核对"]
assert list(job) == ["缺少附件", "金额待核对"]   # 新迭代器仍从头开始

assert "缺少附件" in job
empty = ReviewJob("B")
assert len(empty) == 0 and not empty
```

- `len(job)` 用 `__len__` 读取数量。
- `position` 只记录那一次的读取位置。再次调用 `list(job)` 会取得新的迭代器，从第一条发现开始读。
- `"缺少附件" in job` 也能用。没有 `__contains__` 时，`in` 会遍历对象并逐项比较。这个类也没有 `__bool__`，所以 Python 用 `__len__` 判断空任务为假。

**试着改一处。** 去掉 `__len__`，观察 `len(job)` 的失败。恢复后再去掉 `__iter__`，观察 `list(job)` 的失败。每次只去掉一个方法。

首遍到这里就可以去 [4.1 综合走查](#41-沿输入到结果逐步解释)。

#### 第二遍：自定义类的 `==` 与 `is`

第 1 章区分过值的相等与对象身份。换成自定义类，要先看类有没有定义“按什么比较”。

```python
# study-example: S06M
from dataclasses import dataclass
class Draft:
    def __init__(self, code):
        self.code = code
left, right = Draft("A"), Draft("A")
assert left is not right
assert left != right

@dataclass
class TaskKey:
    code: str
first, second = TaskKey("A"), TaskKey("A")
assert first == second
assert first is not second
```

两个 `Draft` 有同样的 `code`，但类没有定义按字段比较，两次新建的实例仍不相等。`TaskKey` 由 `@dataclass` 生成按字段比较的 `__eq__`，所以 `==` 成立。`is` 问的是“是否同一个对象”，两次创建仍是两个对象。

两边的类型会影响 `==` 优先调用哪一侧的方法，3.4 再看分派顺序。需要更多操作时再查。`__str__` 提供给用户看的文本，`__repr__` 提供排查问题时要看的信息。

### 2.5 与别的对象协作：组合优先，继承表达“是”

**第二遍专题。** 下面用两个独立例子讨论任务怎样和其他对象协作。先看怎样传入资料来源。`ReviewJob` 通过 `get` 查资料名称，找不到时来源应返回 `None`。换成文件或数据库时，来源继续遵守这个约定。这种让对象使用另一个对象的写法叫**组合**。

#### 案例推进：换来源用组合，另一种任务用继承

```python
# study-example: S06K
class MemoryNames:
    def get(self, key):
        return {"A": "采购制度"}.get(key)

class ReviewJob:
    def __init__(self, name, source):
        self.name = name
        self.findings = []
        self.source = source

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

    def describe(self, key):
        name = self.source.get(key)
        return "没有资料" if name is None else name

job = ReviewJob("A", MemoryNames())
assert job.describe("A") == "采购制度"
assert job.describe("missing") == "没有资料"
```

这里的 `job` 保存了一份 `source`，两者是各自独立的对象。任务不知道来源是内存字典还是文件；第 7 章学完文件后，补强练习就是把 `MemoryNames` 换成文件实现，`ReviewJob` 不用改。

接下来换一个需求：紧急任务仍是任务，只需在原摘要前加“紧急”。下面用**继承**复用普通任务的初始化和摘要。为了只看继承，这一块只保留 `name` 和 `summary`。

```python
# study-example: S06N
class ReviewJob:
    def __init__(self, name):
        self.name = name

    def summary(self):
        return f"任务：{self.name}"

class UrgentJob(ReviewJob):
    def summary(self):
        return "紧急｜" + super().summary()

job = UrgentJob("A")
assert isinstance(job, ReviewJob)
assert job.summary() == "紧急｜任务：A"
```

`UrgentJob("A")` 沿用 `ReviewJob` 的 `__init__`。调用 `job.summary()` 会先运行紧急任务的实现，再由 `super().summary()` 运行 `ReviewJob` 的实现，把两个字符串拼起来。多继承时 `super()` 的下一站由查找顺序决定，3.2 再看。

遇到新需求时先问：**要换任务使用的东西，还是要定义另一种任务？**

| 变化 | 写法 | 理由 |
| --- | --- | --- |
| 把内存资料换成文件资料 | 组合：换一个 `source` | 任务只依赖 `get` 这一条约定 |
| 紧急任务要改摘要 | 继承：`UrgentJob(ReviewJob)` | 它仍是一份任务，只是摘要不同 |

如果所有使用 `ReviewJob` 的地方都可以按同样的约定使用紧急任务，才值得用子类表达这个差别。

换资料来源时，可以给任务传入另一个对象。需要表达一种行为有差别的任务时，再考虑子类。

### 2.6 把状态名固定成一组值

**第二遍专题。** 先单独练习状态值和状态转换。用枚举集中定义 `pending` 和 `completed`。`Status(raw)` 检查字符串是不是合法的状态值，`finish(raw)` 再检查这个状态现在能不能完成。第 5 节选做题会把这个规则接回任务。

```python
# study-example: S06F
from enum import StrEnum, unique

@unique
class Status(StrEnum):
    PENDING = "pending"
    COMPLETED = "completed"

def finish(raw):
    state = Status(raw)
    if state is not Status.PENDING:
        raise ValueError("仅待处理状态可完成")
    return Status.COMPLETED.value

assert finish("pending") == "completed"
assert Status.PENDING == "pending"      # StrEnum 成员本身就是字符串
for value in ["closed", "completed"]:
    try:
        finish(value)
    except ValueError:
        pass
    else:
        raise AssertionError(value)
```

- `StrEnum` 的成员也是 `str` 的实例，所以 `Status.PENDING == "pending"` 为真。`Status("pending")` 按值找到成员，成员的 `.value` 则给出原文本。
- `@unique` 要求每个状态名使用不同的值。把状态接回任务时，可以用 `Status(raw)` 把输入转换成枚举成员，再存入字段。

把两个失败分开看。`"closed"` 不是任何成员，在 `Status(raw)` 就失败。`"completed"` 是合法成员，但任务已完成，会被 `finish` 拒绝。**状态存在**和**现在允许执行某个动作**是两项检查。

### 2.7 选型：按需求选工具

把前面用到的写法放在一起，按当前需求查阅。

| 需求 | 写法 | 常见错误 |
| --- | --- | --- |
| 只是把几个字段一起传递 | `dict` | 为它专门造一个类 |
| 字段固定，需要相等、打印和默认值 | `@dataclass` | 手写 `__init__`、`__repr__`、`__eq__` |
| 修改必须经过检查 | 在类的方法里检查，再更新数据 | 直接暴露内部可变数据，调用方能绕过检查 |
| 状态只能取固定几个值 | `StrEnum` | 到处写字符串，拼错只有运行时才发现 |
| 换来源、换存储、换外部服务 | 组合：构造时传入 | 为换数据源专门建一层子类 |
| 真是另一种任务，行为大部分相同 | 子类 + `super()` | 复制父类代码再改几行 |

这些写法可以组合使用。例如，`ReviewJob` 用 `@dataclass` 生成初始化方法，用 `add` 检查修改。需要增加状态时，可以用 `Status` 表示字段值。需要保存只读记录时，可用 `frozen=True` 限制字段重新绑定，并用字符串元组保存发现。

### 2.8 选读：必须实现的接口、无 self 的方法与运算回退

这一节把三个与类有关的约定放在一起：子类必须实现什么、不需要 `self` 的方法，以及运算失败时怎样交还控制权。它们各自独立，第一遍可以跳过。

#### 抽象基类：把“必须实现”写成检查

假如团队约定所有正式的读取器子类都要提供 `read()`，可以把 `Reader` 写成抽象基类（ABC），再用 `@abstractmethod` 标记这个要求。看看下面谁能创建实例，谁会报错。

```python
# study-example: S06D
from abc import ABC, abstractmethod
class Reader(ABC):
    @abstractmethod
    def read(self):
        raise NotImplementedError
class MemoryReader(Reader):
    def read(self):
        return ["A"]
    @staticmethod
    def clean(text):
        return text.strip()
reader = MemoryReader()
assert reader.read() == ["A"]
assert reader.clean(" A ") == MemoryReader.clean(" A ") == "A"
try:
    Reader()
except TypeError:
    pass
else:
    raise AssertionError("未实现抽象方法不能直接实例化")
```

`Reader()` 报错，因为 `read` 仍是抽象方法。`MemoryReader` 用自己的实现覆盖了它，所以可以创建实例。ABC 只检查还有没有保留抽象标记的成员。覆盖后的 `read` 能否调用、接收哪些参数、返回什么，仍需验证。

#### 静态方法：不需要 self 的函数

`clean` 的参数只有 `text`。`@staticmethod` 让它在通过类或实例调用时都只收到你传入的参数。如果它和读取器关系不大，也可以写成普通函数。

#### 运算回退：NotImplemented 不是异常

`Count` 支持两个计数相加。遇到它不会处理的类型时，可以返回 `NotImplemented`，让 Python 决定还有没有别的加法可尝试。

```python
# study-example: S06E
class Count:
    def __init__(self, value):
        self.value = value
    def __add__(self, other):
        if not isinstance(other, Count):
            return NotImplemented
        return Count(self.value + other.value)
assert (Count(1) + Count(2)).value == 3
assert Count.__add__(Count(1), 2) is NotImplemented
try:
    Count(1) + 2
except TypeError:
    pass
else:
    raise AssertionError("无其他适用回退时最终应失败")
```

直接调用 `Count.__add__(Count(1), 2)`，你能看到返回的标记 `NotImplemented`。写 `Count(1) + 2` 时，Python 还有机会尝试适用的反向加法；本例没有可用实现，最后才抛出 `TypeError`。`NotImplementedError` 则是异常，抛出它不会走这里的回退流程。

3.4 讲 `==` 的分派时，用的就是这种返回值：先试一侧，拿到 `NotImplemented` 再试另一侧。

## 3. 原理讲解与推导

这一部分把前面用过的类拆开看：方法怎样记住实例、继承怎样合作、dataclass 生成了什么、`==` 与 `hash` 怎样分派、属性访问为什么会执行代码，最后用 `with` 协议收束。每节先给结论，再当场运行一个最小实验。

### 3.1 方法怎样记住实例：绑定方法与属性字典

读取 `task.label` 时，Python 会返回一个已经记住 `task` 的方法对象。这个对象叫**绑定方法**。之后调用它，`task` 会自动传给 `self`。

```python
# experiment: E13
class Task:
    def label(self, suffix):
        return self.name + suffix
task = Task()
task.name = "review"
assert task.__dict__ == {"name": "review"}
method = task.label
assert method.__self__ is task
assert method.__func__ is Task.label
assert method("!") == Task.label(task, "!") == "review!"
```

读三个断言：

1. `task.__dict__` 里是赋给实例的 `name`。普通实例通常用字典保存属性引用；有些类使用 `__slots__` 为属性预留固定位置，本章的引用关系仍然适用。
2. `method.__self__` 是 `task`，`method.__func__` 是类上的 `Task.label`。
3. `method("!")` 等价于 `Task.label(task, "!")`：调用时 `task` 自动成为 `self`。

读取 `task.label` 时，Python 用类上的函数和实例 `task` 组成绑定方法。3.5 会再看这个过程怎样通过描述器实现。

**回到 2.1 试一次。** 在 S06A 末尾加上 `add_to_a = a.add`，再调用 `add_to_a("金额待核对")`。猜一猜哪份列表会变。`add_to_a` 已经记住了 `a`，这次调用可以按 `ReviewJob.add(a, "金额待核对")` 来理解。

### 3.2 继承协作：super 与 MRO

多继承时，`super()` 不是“调用直接父类”，而是“从当前类之后继续沿方法查找顺序找”。先运行一个菱形继承，看顺序：

```python
# experiment: E15
events = []
class A:
    def run(self):
        events.append("A")
class B(A):
    def run(self):
        events.append("B")
        super().run()
class C(A):
    def run(self):
        events.append("C")
        super().run()
class D(B, C):
    def run(self):
        events.append("D")
        super().run()
D().run()
assert events == ["D", "B", "C", "A"]
assert D.__mro__ == (D, B, C, A, object)
```

`D.__mro__` 是 `D → B → C → A → object`。本例中 `D.run()` 通过 `super()` 找到 `B.run()`，`B.run()` 接着找到 `C.run()`，最后到达 `A.run()`。

- `D`、`B`、`C` 都通过 `super().run()` 把控制权交给下一站。`A.run()` 是约定的终点，只记录 `"A"` 后就返回。
- 接力时传入的参数要符合下一站的签名。本例中的四个 `run` 都只接收 `self`。

这条查找顺序由 **C3 线性化**计算。父类的顺序要求互相冲突时，Python 会在定义子类时抛出 `TypeError`。

### 3.3 dataclass 生成了什么：相等、哈希与 frozen

`@dataclass` 不只生成 `__init__`，还会按字段生成 `__repr__` 和 `__eq__`；`frozen=True` 时还可能生成 `__hash__`。先生成一个 frozen 数据类，分别试三个动作：

```python
# experiment: E16
from dataclasses import dataclass, field, FrozenInstanceError
@dataclass(frozen=True)
class Settings:
    labels: list[str] = field(default_factory=list)
one, two = Settings(), Settings()
one.labels.append("A")
assert one.labels == ["A"] and two.labels == []
try:
    one.labels = []
except FrozenInstanceError:
    pass
else:
    raise AssertionError("frozen 禁止常规重新赋值")
assert Settings.__hash__ is not None  # 方法已经生成
try:
    hash(one)
except TypeError:
    pass
else:
    raise AssertionError("字段中的 list 仍不可哈希")
```

三个动作要分开看：

1. `one.labels.append("A")` 成功。`default_factory` 为每个实例各建一份列表，`frozen` 只限制字段重新绑定，不冻结列表内部。
2. `one.labels = []` 失败，抛 `FrozenInstanceError`。这是字段绑定层面的限制。
3. `hash(one)` 失败，抛 `TypeError`。本例用了 `frozen=True` 和默认的 `eq=True`，因此生成了 `__hash__`。真正计算时，它会用参与哈希的字段值，本例的 `labels` 是列表，无法计算哈希。

参与哈希的字段值必须可哈希。比如把 `labels` 保存为字符串元组 `("A",)`，在本例中就可以计算哈希。

### 3.4 自己写 __eq__ 与 __hash__：== 和字典键

对于 `left == right`，Python 先确定调用顺序。右侧类型是左侧类型的严格子类（直接或间接继承）时，先试右侧的 `__eq__`。其他情况先试左侧。先尝试的一方返回 `NotImplemented`，才会再试另一方。

```python
# experiment: S06Z
events = []
class Left:
    def __eq__(self, other):
        events.append("left")
        return NotImplemented
class Right:
    def __eq__(self, other):
        events.append("right")
        return "matched"
left, right = Left(), Right()
assert (left == right) == "matched"
assert events == ["left", "right"]
assert (left is right) is False
assert events == ["left", "right"]
class Unknown:
    def __eq__(self, other):
        return NotImplemented
one, two = Unknown(), Unknown()
assert (one == two) is False and (one == one) is True
```

按顺序看这三个结果。

- `Left` 与 `Right` 没有继承关系。`left == right` 先调用左侧的 `__eq__`，得到 `NotImplemented`，再尝试右侧并得到 `"matched"`。`events` 记录了这两次调用。
- `__eq__` 可以返回非 `bool` 值。这个例子直接断言比较结果是 `"matched"`。如果把比较式放进 `if`，Python 才会对结果做真假判断。
- 两边都返回 `NotImplemented` 时，`==` 最后比较身份。`one == two` 为假，`one == one` 为真。

**试着改一处。** 把 `class Right:` 改成 `class Right(Left):`，再预测两处检查 `events` 的断言应该期待什么。

用作字典键的两个对象如果相等，它们的哈希也必须相同。下面用一个哈希碰撞的例子检查哈希相同时字典怎样区分不同的键。

```python
# experiment: E06
class Key:
    def __init__(self, value):
        self.value = value
    def __hash__(self):
        return 1  # 故意碰撞，只用于实验
    def __eq__(self, other):
        if not isinstance(other, Key):
            return NotImplemented
        return self.value == other.value
table = {Key("A"): 10, Key("B"): 20}
assert len(table) == 2 and table[Key("A")] == 10
flags = {True: "first", 1: "second"}
assert len(flags) == 1 and flags[True] == "second"
ordered = {"B": 2, "A": 1}
ordered["B"] = 3
assert list(ordered) == ["B", "A"]
```

- `Key("A")` 和 `Key("B")` 的哈希都是 `1`，但 `__eq__` 说它们不相等，所以字典仍保留两项；字典先用哈希找桶，再用相等确认键。
- `True` 和 `1` 相等且哈希相同，后一个值覆盖前一个，所以 `flags` 只剩一项。
- `ordered` 只更新 `"B"` 的值，不改变插入顺序，遍历仍是 `"B"`、`"A"`。

只定义 `__eq__`、不定义 `__hash__` 时，类默认变成不可哈希；需要时要么同时定义两者，要么使用 dataclass 的生成规则。

### 3.5 描述器：属性访问也会执行代码

`property` 能让 `p.cents` 看起来像普通属性，但读取时执行一段代码。先看它和实例字典谁优先：

```python
# experiment: E14
class Price:
    def __init__(self):
        self._cents = 10
    @property
    def cents(self):
        return self._cents
p = Price()
p.__dict__["cents"] = 999
assert p.cents == 10
try:
    p.cents = 20
except AttributeError:
    pass
else:
    raise AssertionError("只读 property 不能直接赋值")
```

`p.__dict__` 里明明有 `cents = 999`，读取 `p.cents` 却得到 `10`。原因是类上的 `property` 是**数据描述器**，属性访问时先执行它的 `__get__`，实例字典排在后面。没有 setter 时，赋值也会被它接管并拒绝。

类上的有些属性会在访问时执行一段代码，这类对象叫**描述器**。它的类型提供 `__get__`、`__set__`、`__delete__` 中的至少一种；提供 `__set__` 或 `__delete__` 的叫数据描述器。`property` 即使只读也属于数据描述器；普通函数则是非数据描述器，通过实例访问时生成 3.1 的绑定方法。

普通实例读取 `obj.x` 时的默认查找过程：

1. 按类的 MRO 找到第一个同名类属性。如果它是能读取的数据描述器，先执行它的 `__get__`。E14 在这一步得到 `10`。
2. 检查实例自己的属性字典。若其中有 `x`，就取这个值。
3. 回到第一步找到的类属性。如果它有 `__get__`，调用它，否则直接返回类上的值。
4. 仍找不到时，若定义了 `__getattr__`，可用它提供后备值。

这条顺序解释了 E13 和 E14：函数是非数据描述器，所以先查实例字典，再生成绑定方法；`property` 是数据描述器，所以实例字典里的同名项被它挡住。自定义 `__getattribute__`、直接访问类属性、隐式调用特殊方法时，还有相应的查找规则。

### 3.6 综合验证：with 协议

最后一类协议把“进入”和“退出”分开。第 5 章已经用过 `with`，这里用类把 `__enter__`/`__exit__` 写出来：

```python
# experiment: E11
events = []
class Resource:
    def __enter__(self):
        events.append("enter")
        return self
    def __exit__(self, exc_type, exc, tb):
        events.append("error" if exc_type else "normal")
        events.append("closed")
        return False
try:
    with Resource():
        raise ValueError("bad data")
except ValueError as error:
    assert str(error) == "bad data"
    assert events == ["enter", "error", "closed"]
else:
    raise AssertionError("退出后应把原异常传给调用者")
def hides_error():
    try:
        raise ValueError("lost")
    finally:
        return 1
assert hides_error() == 1
```

`with Resource():` 先调用 `__enter__`。如果写了 `as`，返回值就交给 `as` 后的目标。`__enter__` 成功后，`with` 才保证调用 `__exit__`。如果进入时就报错，当前管理器的 `__exit__` 不会运行。

本例的 `ValueError` 发生在 `with` 块内，所以 `__exit__` 收到异常信息，依次记录 `error` 和 `closed`。返回 `False` 后，原异常继续传给外层 `except`。返回 `True` 会抑制这个异常。

`hides_error()` 则演示 `finally` 中的 `return 1` 怎样让调用者收到返回值，丢失原来的 `ValueError`。写退出代码时，先确认有哪些异常应继续传给调用者。

把本章出现的协议放在一起：

| 写法 | 调用的特殊方法 | 本章例子 |
| --- | --- | --- |
| `len(obj)` | `__len__` | `ReviewJob` |
| `for x in obj` | 用 `__iter__` 取得迭代器，再用迭代器的 `__next__` 取值 | `ReviewJob`、生成器 |
| `left == right` | `__eq__`，按 3.4 的顺序尝试两侧 | `S06Z` |
| `hash(obj)` | `__hash__` | `E06` |
| `obj + other` | `__add__`，可回退到 `__radd__` | `Count` |
| `with obj:` | `__enter__` / `__exit__` | `Resource` |

第 5 章的 `@contextmanager` 也为 `with` 提供进入和退出操作。用类实现时，块内异常的信息传给 `__exit__`。用 `@contextmanager` 时，管理器会让异常在生成器暂停的 `yield` 处抛出。

### 4.1 沿输入到结果逐步解释

用 2.4 完成的类跑一次完整的审查记录。先创建任务 A、B，给 A 加一条有效发现，再试着添加空白文本。最后数一数两份任务各有几条发现，并读出 A 的内容。

```python
# book-example: B06
from dataclasses import dataclass, field

@dataclass
class ReviewJob:
    name: str
    findings: list[str] = field(default_factory=list)

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

    def __len__(self):
        return len(self.findings)

    def __iter__(self):
        return iter(self.findings)


a, b = ReviewJob("A"), ReviewJob("B")
a.add(" 缺少附件 ")
try:
    a.add("  ")
except ValueError:
    pass
else:
    raise AssertionError("空发现应被拒绝")

assert a.findings is not b.findings
assert len(a) == 1 and len(b) == 0

seen = []
for finding in a:
    seen.append(finding)
assert seen == ["缺少附件"]
assert list(a) == seen
assert list(b) == []
```

1. 创建 A、B 时，`default_factory` 分别创建两份空列表。
2. 第一次 `add` 去掉文本两端的空白，把 `"缺少附件"` 加到 A 的列表。第二次 `add` 在 `append` 之前抛出 `ValueError`，A 仍只有原来那条发现。
3. `len(a)` 和 `len(b)` 读取各自的数量。`for` 读完 A 后，`list(a)` 再取一个新的迭代器，仍能读到同一条发现。B 从创建起一直为空。

## 5. 动手练习

### 本章累计任务：保护实例状态

从 S06A 的 `ReviewJob` 起步，每一步都在同一个类上继续改。

1. **数据分开。** 创建任务 A、B，只给 A 加一条发现。检查 B 仍为空，再用 `is not` 确认两个列表是不同对象。

## 7. 面试问答与迁移

property 为什么不只是 Getter？super 为什么可能调用到兄弟类？frozen 一定可哈希吗？

**参考回答：**

1. `property` 是数据描述器，属性访问可转入 getter/setter/deleter；没有 setter 时，普通赋值会失败，同名实例字典项也不能简单覆盖它。只读 property 本身就是一种接口设计，但若返回内部列表，调用方仍可修改列表。它维护访问约定，不隔离恶意代码。
2. `super()` 相对给定类，在实际对象的 MRO 中继续查找，不固定为“直接父类”。菱形继承中可能走到兄弟类；协作链要约定兼容签名、是否继续 `super` 以及终点，否则可能漏调用或重复初始化。
3. 要分开“生成哈希方法”与“调用成功”。当 `eq=True`（默认）且 `frozen=True` 时，若没有显式定义哈希，dataclass 会生成 `__hash__`；生成时不逐项证明字段可哈希，真正 hash 实例时才可能因 list 字段失败。frozen 限制常规属性赋值/删除，不递归冻结内部内容，也不是安全边界。`unsafe_hash` 同样不能把 list 变成可哈希值。[生成规则](https://docs.python.org/3.12/library/dataclasses.html)

**换条件自测：** 同一份数据换一种字段表示。先预测三件事：列表能否继续 `append`、`hash(mutable)`、`hash(fixed)`，再运行。

```python
# study-example: S06H
from dataclasses import dataclass

@dataclass(frozen=True)
class ListReport:
    labels: list[str]

@dataclass(frozen=True)
class TupleReport:
    labels: tuple[str, ...]

assert ListReport.__hash__ is not None    # 两个类都生成了哈希方法
assert TupleReport.__hash__ is not None
mutable = ListReport([])
mutable.labels.append("review")          # frozen 不冻结内部列表
assert mutable.labels == ["review"]
try:
    hash(mutable)
except TypeError:
    pass
else:
    raise AssertionError("参与哈希的list字段不可哈希")

fixed = TupleReport(("review",))
assert fixed.labels == ("review",)
assert hash(fixed) == hash(TupleReport(("review",)))
```

`ListReport` 和 `TupleReport` 都是 `frozen=True`，都生成了 `__hash__`；`hash()` 能否成功，取决于参与哈希的字段值本身是否可哈希，而不取决于 `frozen` 这个参数。两个类都不允许重新绑定字段，差别只在字段类型。要让结果可哈希，应选择不可变表示（元组），而不是给可变列表加 `frozen`。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 怎样保证每个任务有自己的列表，并让添加、比较和遍历按预期工作？

**一条主线：**

```text
字典保存任务 → 实例各存自己的列表 → add 先检查再修改 → dataclass 生成初始化 → len() 和 for 读取发现
```

遇到类题时，先问四个具体问题：列表或状态放在谁身上？调用方法时 `self` 是谁？`len()`、`==` 或 `for` 会用到哪个方法？这次是换任务使用的东西，还是定义另一种任务？

**最容易错：**

- 把每任务独立的列表放在类属性上，多个实例一起被改；
- 以为 `frozen=True` 递归冻结，内部 list 仍然可变；
- 定义了 `__eq__` 却不同步 `__hash__`，对象在字典里行为异常；
- 用继承的类层次代替业务上的可替换契约。

**与前后章：** 第5章留下异常、迭代与资源退出契约，本章把任务状态和规则收进实例，并让对象支持 `len`、`==` 等操作。第7章要把这些对象放进模块、文件和命令行入口，需要先有清晰的对象边界。

**首遍完成后**

- 写出各自持有列表的两个任务，并说明调用 `add` 时 `self` 是哪个实例。
- 让 `add` 在修改前拒绝空白文本，用 `default_factory` 简化初始化，并通过 `len()` 和 `for` 检查结果。

**第二遍按需回看**

- 只读属性、`frozen`、相等与哈希各有什么边界。
- 怎样用组合替换资料来源，怎样用枚举区分非法状态值和不允许的状态转换。

### 8.2 日常工作注意事项

- 每个任务独立的列表放在实例初始化中，或使用default_factory；把它放在类上容易使多个任务共享修改。
- 定义相等规则后同步检查哈希与可变性；不要用unsafe_hash绕过设计问题后直接把可变业务对象作字典键。
- property和下划线帮助维护接口，不是权限隔离。受控属性仍需验证输入，内部可变值的暴露也要检查。
- 状态名集中定义成枚举；散落的字符串拼错只有运行时才发现，而“值合法”不等于“现在允许执行”。
