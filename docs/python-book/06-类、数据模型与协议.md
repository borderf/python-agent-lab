## 2. 基础知识讲解

先看第 3–4 章学过的字典写法，再把同一份任务写成 `ReviewJob`。比较两种写法时，做同一个检查。给 A 加一条发现，看看 B 会不会变。2.1–2.4 沿同一个类逐步推进；2.5 起按对象设计、选型和协议分开阅读，不必继续堆在首遍主线上。

### 2.1 先让每份任务拥有自己的状态

每份任务都有名称和发现列表。先判断这件事需不需要类。第 4 章的小计 `subtotal(cents, count)` 只有输入、计算和返回值，两次调用之间不保存进度，用函数就够。要连续记录同一份任务的发现，就需要一个能保存状态的地方：字典可以做到，但规则仍写在外部函数里。先看字典版。

```python
# study-example: S06G
def add_finding(job, text):
    job["findings"].append(text)

job_a = {"name": "A", "findings": []}
job_b = {"name": "B", "findings": []}
add_finding(job_a, "缺少附件")
assert job_a["findings"] == ["缺少附件"]
assert job_b["findings"] == []
```

字典版已经能工作。现在想把准备数据和添加发现这两件事放到一起，就用 `class ReviewJob` 定义一个类。类规定一份任务怎样初始化、能做哪些事。调用 `ReviewJob("A")` 得到具体任务 A，调用 `ReviewJob("B")` 得到具体任务 B。这两个对象都是 `ReviewJob` 的**实例**。

读代码前先认三个写法。

- `__init__` 在新实例创建后运行，给这份任务准备自己的数据。
- 写 `self.name = name` 时，右边 `name` 是传入的参数，左边 `self.name` 把值留在任务上。`self.name` 和 `self.findings` 都是这份任务的**实例属性**。
- `add` 是定义在类里的**实例方法**。调用 `a.add(...)` 时，Python 把 `a` 交给方法的第一个参数 `self`。

#### 案例推进：从字典到两份独立状态

```python
# study-example: S06A
class ReviewJob:
    def __init__(self, name):
        self.name = name
        self.findings = []
    def add(self, finding):
        self.findings.append(finding)

a, b = ReviewJob("A"), ReviewJob("B")
a.add("缺少附件")
assert a.findings == ["缺少附件"] and b.findings == []
assert a.findings is not b.findings
```

按执行顺序看这段代码。`class` 只定义了做法，A、B 还没出现；表里每一行是那条语句执行完时的状态。

| 执行到 | 这次调用的 `self` | A 的列表 | B 的列表 |
| --- | --- | --- | --- |
| `ReviewJob("A")` | A | `[]`（新建） | 还没创建 |
| `ReviewJob("B")` | B | `[]` | `[]`（新建） |
| `a.add("缺少附件")` | `a` | `["缺少附件"]` | `[]` |

创建 A 和 B 时，`__init__` 各运行一次，所以 `[]` 也各创建一次。调用 `a.add("缺少附件")` 可以按 `ReviewJob.add(a, "缺少附件")` 来读。`self` 是第一个参数的约定名字。最后的 `is not` 断言确认 A、B 引用的是两个不同的列表。

**把对象换一次。** 在示例末尾加一行 `ReviewJob.add(b, "金额待核对")`，先预测哪份列表会变，再运行。`b` 会填进 `self`，改动落在 B 上。

想让每份任务都有自己的列表，可以在 `__init__` 里用 `[]` 新建一份。反过来，如果把 `findings = []` 写在类体里，执行到 `class` 语句时才会创建那一份列表，得到一个**类属性**。随后创建的 A 和 B 都能读取它。先预测 B 会看到什么，再运行对照例子。

```python
# study-example: S06O
class SharedJob:
    findings = []             # 类上的一个列表
    def add(self, text):
        self.findings.append(text)

a, b = SharedJob(), SharedJob()
a.add("缺少附件")
assert a.findings is b.findings
assert b.findings == ["缺少附件"]
```

在这个例子里，A 自己没有 `findings`，所以读取 `a.findings` 时会找到类上的 `SharedJob.findings`。B 也找到同一个列表。`append` 改的是已经找到的列表，B 就看到了变化。

#### 类与实例仍然是同一对象图中的节点

用第 1 章的箭头画出来：

```text
a.add("缺少附件") 之后
a ──→ A ──┐
          ├──→ SharedJob.findings：["缺少附件"]
b ──→ B ──┘

a.findings = [] 之后
a ──→ A ──→ []（A 新建的列表）
b ──→ B ──→ SharedJob.findings：["缺少附件"]
```

**试着加一行。** 在最后加上 `a.findings = []`。这会给 A 自己加一项 `findings`，接下来 A 读到自己的空列表，B 仍读到类上的原列表。可以用 `assert a.findings is not b.findings` 验证。

| 属性写在哪 | 什么时候创建 | 谁共享 | 适合放什么 |
| --- | --- | --- | --- |
| `__init__` 里的 `self.findings = []` | 每次创建实例时执行一次 | 每个实例一份 | 每个任务自己的发现、状态 |
| 类体里的 `findings = []` | 每次执行到 `class` 语句时一次（模块顶层就是一次） | 所有实例读到同一个 | 真正希望共享的常量或配置；可变对象仍要谨慎 |

图和表展示的是这两段代码里普通属性的行为。想看属性具体存在哪里，读 3.1。遇到读取或赋值会执行代码的属性，再看 3.5。

**本步之后：** `ReviewJob` 有名称、发现列表和 `add`，两份任务的列表互不影响。下一步让方法决定“什么算合法的发现”。

### 2.2 先检查再修改：只读属性与命名构造

现在每次添加发现，都要求先去掉首尾空白，空文本要报错。检查写在哪里？

字典版也能让 `add_finding` 先验证再 `append`。类把要管理的数据和操作放在一起，并为调用方提供明确的入口，这就是这里说的**封装**。调用方使用 `job.add(...)` 时，方法会先检查输入，再更新这份任务的列表。

#### 案例推进：检查发生在修改之前

```python
# study-example: S06I
class ReviewJob:
    def __init__(self, name):
        self.name = name
        self.findings = []

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

job = ReviewJob("A")
job.add(" 缺少附件 ")
try:
    job.add("  ")
except ValueError:
    pass
else:
    raise AssertionError("空发现应被拒绝")
assert job.findings == ["缺少附件"]
```

入口变自然了，但没有变成唯一。试着执行 `job.findings.append(" ")`，可以看到它会直接修改列表，完全绕过 `add`；这条检查只保护“通过 `add` 修改”的路径。

如果要控制调用方怎样修改，可以只提供操作方法，并通过副本或只读结果提供数据。L14 会练习这个接口设计。首遍到这里即可去 2.3，保留 `add` 并简化 `ReviewJob` 的初始化。

#### 选读：属性访问与三种方法

这里有两个不同的问题：怎样让属性读取执行代码，以及怎样提供一个带名字的创建入口。先把第一个问题讲清楚，再看第二个。

##### 从普通属性到读取方法

普通属性可以直接读取和赋值。例如在 `__init__` 里写 `self.value = value`，调用方就能写 `limit.value`，也能写 `limit.value = 4`。

如果只想提供读取入口，可以先写一个普通方法：把数据存到 `self._value`，再定义 `get_value(self)` 返回它。调用方写成 `limit.get_value()`。这已经能工作，区别只是读取时看起来像一次方法调用。

`@property` 的作用是：**把读取方法包装成属性，让调用方仍然写 `limit.value`，但背后自动执行这个方法。** 单下划线表示 `_value` 是建议在类内部使用的名字，不是强制访问限制。

##### 用 property 保留属性式读取

先用熟悉的 `Limit(3)` 创建对象。`__init__` 检查输入是正整数，再存到 `self._value`。下面的 `value` 方法只负责读取，所以它变成的是一个**只读属性**。

```python
# study-example: S06P
class Limit:
    def __init__(self, value):
        if type(value) is not int or value <= 0:
            raise ValueError("limit必须是正整数")
        self._value = value

    @property
    def value(self):
        return self._value


limit = Limit(3)
assert isinstance(Limit.value, property)
assert limit.value == 3
try:
    limit.value = 4
except AttributeError:
    pass
else:
    raise AssertionError("只读属性应拒绝赋值")
assert limit.value == 3
limit._value = 4
assert limit.value == 4
```

把两次访问分开看：

- `Limit.value` 拿到的是类上的 `property` 对象，所以第一个断言通过。
- `limit.value` 会执行 getter，返回 `self._value`，所以得到 `3`。
- `limit.value = 4` 会尝试给这个属性赋值；本例没有 setter，因此抛出 `AttributeError`，原来的值仍是 `3`。

这里限制的是给公开属性 `value` 重新赋值，并不是把对象锁死。S06P 最后两行直接修改 `_value` 后，`limit.value` 变成了 `4`。因为 `_value` 本身还是普通实例属性。`property` 维护的是公开接口约定，不是安全权限。3.5 会进一步解释它怎样接管属性读写。

##### getter 和 setter 的完整写法

只读不是因为 `@property` 天生只能读，而是因为 S06P 只提供了 getter。规范的受控属性通常包含四部分：

1. `__init__` 通过公开属性赋值，例如 `self.value = value`；
2. `_value` 保存实际数据；
3. `@property` 定义 getter，方法名与公开属性同名；
4. `@value.setter` 定义 setter，方法名也与公开属性同名。

下面是一个完整可运行的类：

```python
# study-example: S06S
class Limit:
    def __init__(self, value):
        self.value = value

    @property
    def value(self):
        return self._value

    @value.setter
    def value(self, new_value):
        if type(new_value) is not int or new_value <= 0:
            raise ValueError("limit必须是正整数")
        self._value = new_value


limit = Limit(3)
assert limit.value == 3

limit.value = 4
assert limit.value == 4

for bad in [-1, True, "4"]:
    try:
        limit.value = bad
    except ValueError:
        pass
    else:
        raise AssertionError(bad)
    assert limit.value == 4
```

执行顺序是：

- `Limit(3)` 调用 `__init__`，其中的 `self.value = 3` 触发 setter，检查通过后写入 `_value`。
- 读取 `limit.value` 触发 getter，返回 `_value`。
- `limit.value = 4` 再次触发 setter，检查通过后更新 `_value`。
- `limit.value = -1` 触发 setter，检查失败并抛出 `ValueError`；因为还没有执行最后一行赋值，`_value` 仍保持 `4`。

`@value.setter` 中的 `value` 指向上面的 property，不是重新声明一个普通属性。setter 不需要返回值；调用方始终使用属性式写法 `limit.value` 和 `limit.value = 4`，不用直接调用 getter 或 setter。

如果 getter 返回的是一个列表，调用方执行 `limit.items.append(...)` 仍然是在修改返回的列表，不是给属性重新赋值。property 不会自动冻结返回值。

##### 实例方法：自动收到当前实例

前面的 `add(self, text)` 和 `__init__(self, value)` 都是**实例方法**，它们处理某一个对象自己的数据。调用 `job.add("缺少附件")` 时，Python 会把 `job` 自动绑定为第一个参数 `self`，效果相当于执行 `ReviewJob.add(job, "缺少附件")`。后一种写法只是用来展示绑定过程，日常应使用前一种。

`self` 不是 Python 关键字，只是惯例名字；决定自动绑定的是实例方法本身，不是这个名字。

##### 类方法：自动收到调用时使用的类

`Limit(3)` 已经会检查数值。输入是文本 `"3"` 时，可以加一个叫 `from_text` 的创建入口：先把文本转成整数，再复用 `__init__`。这种有具体名字的创建方法常叫**命名构造**。

用 `@classmethod` 定义**类方法**后，它的第一个参数会自动收到调用时使用的类，惯例叫 `cls`。调用 `Limit.from_text("3")` 时，Python 自动把 `Limit` 传给 `cls`，所以 `cls(int(text))` 在本例等同于 `Limit(3)`。它返回一个新对象，不是修改已有对象。

```python
# study-example: S06B
class Limit:
    def __init__(self, value):
        if type(value) is not int or value <= 0:
            raise ValueError("limit必须是正整数")
        self._value = value

    @property
    def value(self):
        return self._value

    @classmethod
    def from_text(cls, text):
        return cls(int(text))


limit = Limit(3)
another = limit.from_text("4")
assert isinstance(Limit.from_text("3"), Limit)
assert another is not limit
assert another.value == 4
```

这里特意用 `limit.from_text("4")` 调用：即使通过实例找到类方法，自动传给 `cls` 的仍然是类 `Limit`，不是实例 `limit`。`limit` 只负责找到这个方法。

**换两个输入。** 分别传 `"bad"` 和 `"0"`。`"bad"` 在 `int(text)` 转换时失败；`"0"` 转成整数后，会在 `__init__` 的正整数检查处失败。

学过 2.5 的继承后可以再回看 `cls`。若子类沿用这个入口，`子类.from_text(...)` 会把子类传给 `cls`，于是创建的是子类实例。若把 `cls(...)` 写死成 `Limit(...)`，就会失去这个行为。

##### 静态方法：不自动收到实例或类

有些操作只需要调用方显式传入的数据。比如清理读到的文本，只需要 `text`。加上 `@staticmethod` 后，这个**静态方法**不会自动绑定 `self` 或 `cls`；通过类或实例调用，都只传入显式给出的参数。

```python
# study-example: S06Q
class TextCleaner:
    @staticmethod
    def clean(text):
        return text.strip()


assert TextCleaner.clean(" A ") == "A"
assert TextCleaner().clean(" A ") == "A"
```

如果这个操作也会被许多其他类使用，可以直接写成普通函数。把方法与类放在一起，通常是因为它表达了这个类的一项职责，并不代表它需要读取类或对象的状态。

##### 放在一起看：区别在自动绑定

三种方法都写在类里，但调用时 Python 自动提供的第一个参数不同：

- `job.add("缺少附件")`：自动提供实例 `job`，作为 `self`。
- `Limit.from_text("3")`：自动提供类 `Limit`，作为 `cls`。
- `TextCleaner.clean(" A ")`：什么也不自动提供，只有显式传入的文本。

| 对比项 | 实例方法 | 类方法 | 静态方法 |
| --- | --- | --- | --- |
| 定义关键 | `def add(self, text)` | `@classmethod` + `def from_text(cls, text)` | `@staticmethod` + `def clean(text)` |
| 典型调用 | `job.add("缺少附件")` | `Limit.from_text("3")` | `TextCleaner.clean(" A ")` |
| 调用时自动绑定 | 调用方使用的实例 `job` | 调用方使用的类 `Limit` | 无 |
| 方法内部实际收到 | `self=job, text="缺少附件"` | `cls=Limit, text="3"` | 只有 `text=" A "` |
| 主要使用谁的数据 | 当前实例的数据 | 类本身；常通过 `cls(...)` 创建对象 | 只使用显式传入的数据 |
| 选择问题 | 要处理“这个对象”的状态吗？ | 要使用“这个类”，或按调用它的类创建对象吗？ | 只给定参数就能完成，不需要实例或类吗？ |

`self` 和 `cls` 同样都只是惯例名字，不是关键字。把第一个参数改叫 `obj` 或 `klass` 不会改变方法类型；反过来，仅仅给实例方法改名叫 `cls`，也不会把它变成类方法。**类型由定义和装饰器决定。**

同一个类方法通过实例调用时，不要误以为它会收到实例。`limit.from_text("4")` 中的 `cls` 依然是 `Limit`。静态方法通过实例调用时，也不会自动收到实例，所以 `TextCleaner().clean(" A ")` 仍只传入了文本。

最后，前面的 `property` 和这里的三种方法不是同一个分类问题：`property` 控制“访问属性时是否执行代码”，实例/类/静态方法控制“调用方法时 Python 自动绑定谁”。判断一个方法该写成哪种，先回答上表最后一行的问题；不要只因为它不需要 `self`，就草率地加上 `@staticmethod`。

### 2.3 用 dataclass 少写初始化，规则仍要自己写

回到 `ReviewJob`。手写的 `__init__` 做了两件事：保存 `name`，并在缺省时为 `findings` 新建空列表。标准库的类装饰器 `@dataclass` 可以根据**字段声明**生成这个初始化方法。`add` 仍由我们定义。

- `name: str` 声明一个名为 `name` 的字段，并标注它预期保存字符串。`findings: list[str]` 则标注预期保存字符串列表。这里的类型注解用于表达预期，构造时仍可传入其他类型。
- `field(...)` 为单个字段配置行为。`field(default_factory=list)` 把 `list` 这个可调用对象交给初始化方法。每次构造时若没有传入 `findings`，初始化方法就调用一次 `list()`。所以它和原来每次在 `__init__` 中执行 `[]` 的效果相同。

#### 案例推进：数据类生成初始化，不生成业务规则

```python
# study-example: S06C
from dataclasses import dataclass, field

@dataclass
class ReviewJob:
    name: str
    findings: list[str] = field(default_factory=list)

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

a, b = ReviewJob("A"), ReviewJob("B")
a.add(" 缺少附件 ")
assert a.findings == ["缺少附件"]
assert b.findings == []
assert a.findings is not b.findings
```

如果显式传入一个列表，初始化方法会直接保存这个列表。可以用同一个列表构造两个任务，再通过 `add` 改其中一个，观察另一个任务的变化。类型注解表达预期，不会在构造时自动拒绝错误类型。

#### 选读：用 __post_init__ 检查构造输入

数据类生成 `__init__` 后，仍可以在 `__post_init__` 中写构造阶段的检查。它由生成的 `__init__` 在字段赋值完成后调用。

```python
# study-example: S06R
from dataclasses import dataclass, field

@dataclass
class CheckedJob:
    name: str
    findings: list[str] = field(default_factory=list)

    def __post_init__(self):
        if not isinstance(self.name, str) or not self.name.strip():
            raise ValueError("任务名必须是非空文本")
        if not isinstance(self.findings, list):
            raise ValueError("发现必须是列表")
        if any(not isinstance(text, str) or not text.strip() for text in self.findings):
            raise ValueError("发现必须是非空文本")

assert CheckedJob("A", ["缺少附件"]).name == "A"
for args in [("", []), ("A", "abc"), ("A", [" "]), ("A", [3])]:
    try:
        CheckedJob(*args)
    except ValueError:
        pass
    else:
        raise AssertionError(args)
```

先检查 `findings` 本身是不是列表，再检查其中每一项。否则传入字符串 `"abc"` 时，逐字符检查可能全部通过。`__post_init__` 只覆盖构造这一刻；对象创建后，`add` 仍要检查新输入，调用方直接修改传入的列表也可能破坏约定。它不会自动解决别名共享或封装问题。

#### 选读：frozen 对内部列表有什么影响

如果一份快照在创建后应保持原来绑定的字段值，可以用 `@dataclass(frozen=True)` 拒绝常规的字段赋值。下面区分两种操作：`snapshot.name = "B"` 要给字段换一个值，`snapshot.findings.append(...)` 则要修改字段所引用的列表。先预测哪个会失败。

```python
# study-example: S06L
from dataclasses import FrozenInstanceError, dataclass, field

@dataclass(frozen=True)
class Snapshot:
    name: str
    findings: list[str] = field(default_factory=list)

snapshot = Snapshot("A")
snapshot.findings.append("缺少附件")  # 修改列表内容
try:
    snapshot.name = "B"              # 尝试重新绑定字段
except FrozenInstanceError:
    pass
else:
    raise AssertionError("frozen字段不允许普通重新赋值")
assert snapshot.findings == ["缺少附件"]
```

结果是 `snapshot.name = "B"` 被拒绝，`snapshot.findings.append(...)` 成功。`frozen=True` 限制字段重新赋值，列表自身仍可修改。要保存一组不能增删的发现，可以使用字符串元组。3.3 再说明这个配置与哈希的关系。

### 2.4 让对象参与语言操作：len、for 与 ==

第 5 章已经用 `iter(...)` 取得迭代器，再用 `next(...)` 逐项读取。现在让 `ReviewJob` 把内部列表交给同样的流程：`__len__` 返回列表长度，`__iter__` 返回列表的迭代器。**协议**就是调用方的写法与对象提供的方法之间的约定。例如，调用方写 `len(job)`，Python 去调用这个类的 `__len__`。

```python
# study-example: S06J
from dataclasses import dataclass, field

@dataclass
class ReviewJob:
    name: str
    findings: list[str] = field(default_factory=list)

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

    def __len__(self):
        return len(self.findings)

    def __iter__(self):
        return iter(self.findings)

job = ReviewJob("A")
job.add("缺少附件")
job.add("金额待核对")
assert len(job) == 2

seen = []
for finding in job:
    seen.append(finding)

assert seen == ["缺少附件", "金额待核对"]
assert list(job) == seen
```

`for` 和 `list(job)` 各调用一次 `__iter__`，每次都拿到一个新迭代器，所以第二次还能从头读。

**试着改一处。** 去掉 `__len__`，观察 `len(job)` 的失败。恢复后再去掉 `__iter__`，观察 `for finding in job` 的失败。

#### 第二遍：自定义类的 `==` 与 `is`

第 1 章用 `is` 判断是不是同一个对象，用 `==` 判断值是否相等。普通的 `Draft` 在这里沿用默认的身份判断。`@dataclass` 默认生成 `__eq__`，用来比较同类实例中参与比较的字段。先猜下面两对对象的 `==` 和 `is` 各是什么结果。

```python
# study-example: S06M
from dataclasses import dataclass
class Draft:
    def __init__(self, code):
        self.code = code
left, right = Draft("A"), Draft("A")
assert left is not right
assert left != right

@dataclass
class TaskKey:
    code: str
first, second = TaskKey("A"), TaskKey("A")
assert first == second
assert first is not second
assert repr(first) == "TaskKey(code='A')"
assert str(first) == "TaskKey(code='A')"
```

两个 `Draft` 有同样的 `code`，但类没有定义按字段比较，两次新建的实例仍不相等。`TaskKey` 由 `@dataclass` 生成按字段比较的 `__eq__`，所以 `==` 成立。`is` 问的是“是否同一个对象”，两次创建仍是两个对象。

两边的类型会影响 `==` 优先调用哪一侧的方法，3.4 再看分派顺序。`__str__` 提供给用户看的文本，`__repr__` 提供排查问题时要看的信息。S06M 最后两行展示了数据类默认生成的表示；这里没有单独定义 `__str__`，所以 `str()` 回退到生成的 `__repr__`。需要更友好的显示时，再分别实现两者。

#### 第二遍：运算回退与 NotImplemented

`Count` 支持计数相加。实现 `__add__` 时，可以用返回值 `NotImplemented` 表示「这个方法没有处理这组操作数」，让 Python 尝试适用的其他实现。`NotImplementedError` 则是异常，抛出它会中断这次运算。

```python
# study-example: S06E
class Count:
    def __init__(self, value):
        self.value = value
    def __add__(self, other):
        if not isinstance(other, Count):
            return NotImplemented
        return Count(self.value + other.value)
assert (Count(1) + Count(2)).value == 3
assert Count.__add__(Count(1), 2) is NotImplemented
try:
    Count(1) + 2
except TypeError:
    pass
else:
    raise AssertionError("无其他适用回退时最终应失败")
```

直接调用 `Count.__add__(Count(1), 2)`，你能看到返回的标记 `NotImplemented`。写 `Count(1) + 2` 时，Python 还有机会尝试适用的反向加法；本例没有可用实现，最后才抛出 `TypeError`。`NotImplementedError` 则是异常，抛出它不会走这里的回退流程。3.4 讲 `==` 的分派时，用的就是这种返回值。

### 2.5 与别的对象协作：组合优先，继承表达“是”

**第二遍专题。** 下面用两个独立例子讨论任务怎样和其他对象协作。先看怎样传入资料来源。`ReviewJob` 通过 `get` 查资料名称，找不到时来源应返回 `None`。换成文件或数据库时，来源继续遵守这个约定。这种让对象使用另一个对象的写法叫**组合**。

#### 案例推进：换来源用组合，另一种任务用继承

```python
# study-example: S06K
class MemoryNames:
    def get(self, key):
        return {"A": "采购制度"}.get(key)

class ReviewJob:
    def __init__(self, name, source):
        self.name = name
        self.findings = []
        self.source = source

    def add(self, text):
        if not isinstance(text, str) or not text.strip():
            raise ValueError("发现必须是非空文本")
        self.findings.append(text.strip())

    def describe(self, key):
        name = self.source.get(key)
        return "没有资料" if name is None else name

job = ReviewJob("A", MemoryNames())
assert job.describe("A") == "采购制度"
assert job.describe("missing") == "没有资料"

other = ReviewJob("A", {"A": "新版采购制度"})
assert other.describe("A") == "新版采购制度"
assert other.describe("missing") == "没有资料"
```

`MemoryNames` 和字典都有 `get`，因此同一份 `describe` 能用两个来源。传入的对象不同，同一个调用能得到不同的结果，这就是本例中的**多态**。学完第 7 章的文件操作后，可以按同一约定换成文件来源。

紧急任务仍是一种任务。为了只聚焦继承，下面使用一个**独立的最小 `ReviewJob`**：它只保留 `name` 和 `summary`，不承接前面的 `findings`、`add` 和迭代方法。`class UrgentJob(ReviewJob)` 声明 `UrgentJob` 是子类，`ReviewJob` 是它的基类。`UrgentJob` 沿用基类的 `__init__`，并通过定义同名 `summary` 更换摘要写法，这叫**覆盖**。

紧急版只想在原摘要前加「紧急」，可以在覆盖的方法里用 `super().summary()` 取回原摘要。本例只有一个基类，所以会找到 `ReviewJob.summary`。

```python
# study-example: S06N
class ReviewJob:
    def __init__(self, name):
        self.name = name

    def summary(self):
        return f"任务：{self.name}"

class UrgentJob(ReviewJob):
    def summary(self):
        return "紧急｜" + super().summary()

job = UrgentJob("A")
assert isinstance(job, ReviewJob)
assert job.summary() == "紧急｜任务：A"
```

`UrgentJob("A")` 沿用 `ReviewJob` 的 `__init__`。调用 `job.summary()` 会先运行紧急任务的实现，再由 `super().summary()` 运行 `ReviewJob` 的实现，把两个字符串拼起来。多继承时 `super()` 的下一站由查找顺序决定，3.2 再看。

遇到新需求时先问：**要换任务使用的东西，还是要定义另一种任务？**

| 变化 | 写法 | 理由 |
| --- | --- | --- |
| 把内存资料换成文件资料 | 组合：换一个 `source` | 任务只依赖 `get` 这一条约定 |
| 紧急任务要改摘要 | 继承：`UrgentJob(ReviewJob)` | 它仍是一份任务，只是摘要不同 |

如果所有使用 `ReviewJob` 的地方都可以按同样的约定使用紧急任务，才值得用子类表达这个差别。

换资料来源时，可以给任务传入另一个对象。需要表达一种行为有差别的任务时，再考虑子类。如果还要求可替换实现必须提供指定方法，并希望在实例化时强制检查，见 2.8 的抽象基类。

### 2.6 选型：按需求选工具

把前面用到的写法放在一起，按当前需求查阅。先判断是否需要对象，再判断字段、行为和协作方式，不要从“应该写个类”开始。

| 需求 | 写法 | 常见错误 |
| --- | --- | --- |
| 只是把几个字段一起传递 | `dict` | 为它专门造一个类 |
| 字段固定，需要相等、打印和默认值 | `@dataclass` | 手写 `__init__`、`__repr__`、`__eq__` |
| 修改必须经过检查 | 在类的方法里检查，再更新数据 | 直接暴露内部可变数据，调用方能绕过检查 |
| 状态只能取固定几个值 | `StrEnum`（见 2.7） | 到处写字符串，拼错只有运行时才发现 |
| 换来源、换存储、换外部服务 | 组合：构造时传入 | 为换数据源专门建一层子类 |
| 真是另一种任务，行为大部分相同 | 子类 + `super()` | 复制父类代码再改几行 |

这些写法可以组合使用。例如，`ReviewJob` 用 `@dataclass` 生成初始化方法，用 `add` 检查修改。需要增加状态时，可以用 2.7 的 `Status` 表示字段值。需要保存只读记录时，可用 `frozen=True` 限制字段重新绑定，并用元素均可哈希的元组保存发现。

### 2.7 应用专题：把状态名固定成一组值

**第二遍专题。** 任务状态只能从 `pending` 和 `completed` 两个值里选。**枚举**把可选项集中定义，每个可选项叫一个**成员**。这里用 `StrEnum` 表示值为字符串的枚举，`Status.PENDING` 是成员，`Status.PENDING.value` 是对应的文本 `"pending"`。

`Status("pending")` 按值找到已经定义的成员。`@unique` 检查成员值有没有重复。先用这两个约定辨认输入，再由 `finish` 决定当前状态能否完成。第 5 节选做题会把规则接回任务。

```python
# study-example: S06F
from enum import StrEnum, unique

@unique
class Status(StrEnum):
    PENDING = "pending"
    COMPLETED = "completed"

def finish(raw):
    state = Status(raw)
    if state is not Status.PENDING:
        raise ValueError("仅待处理状态可完成")
    return Status.COMPLETED.value

assert Status("pending") is Status.PENDING
assert Status.PENDING.value == "pending"
assert Status.PENDING == "pending"
assert finish("pending") == "completed"
for value in ["closed", "completed"]:
    try:
        finish(value)
    except ValueError:
        pass
    else:
        raise AssertionError(value)
```

`"closed"` 在按值查找时就失败，因为它没有对应成员。`"completed"` 能查到成员，随后才会被 `finish` 拒绝。把规则接回任务时，先用 `Status(raw)` 取得成员，再决定是否允许更新字段。这里要区分两件事：**值是否合法**，以及**当前状态是否允许这次转换**。

### 2.8 选读：用抽象基类声明必须实现的行为

`staticmethod` 已放在 2.2 与实例方法、类方法对照，`NotImplemented` 已放在 2.4 与协议回退一起讨论。本节只回答一个问题：怎样在类这一侧声明“具体实现必须提供哪些方法”。第一遍可以跳过。

#### 抽象基类：把“必须实现”写成检查

每种读取器都应提供 `read()`。**抽象基类**可以声明这项要求。下面用 `class Reader(ABC)` 定义抽象基类，再用 `@abstractmethod` 把 `read` 标成需要具体实现的方法。只要类上还有抽象成员，创建实例就会失败。本例也用 `raise NotImplementedError` 表示抽象方法没有提供默认读法。先预测 `Reader()` 和 `MemoryReader()` 各会怎样。

```python
# study-example: S06D
from abc import ABC, abstractmethod
class Reader(ABC):
    @abstractmethod
    def read(self):
        raise NotImplementedError


class MemoryReader(Reader):
    def read(self):
        return ["A"]


reader = MemoryReader()
assert reader.read() == ["A"]
try:
    Reader()
except TypeError:
    pass
else:
    raise AssertionError("未实现抽象方法不能直接实例化")
```

`Reader()` 报错，因为 `read` 仍是抽象方法。`MemoryReader` 用自己的实现覆盖了它，所以可以创建实例。ABC 只检查还有没有保留抽象标记的成员。覆盖后的 `read` 能否调用、接收哪些参数、返回什么，仍需验证。

ABC 是一种显式声明，但不是所有 Python 接口都必须继承 ABC。2.5 的资料来源只约定 `get`，调用方同样可以替换实现。需要强制检查抽象成员时再用 ABC；只需要表达行为约定时，可以先依赖实际方法和测试。

### 3.1 方法怎样记住实例：绑定方法与属性字典

读取 `task.label` 时，会得到一个已经记住 `task` 的**绑定方法**。可以用 `method.__self__` 看它记住的实例，用 `method.__func__` 看类上的原函数。之后调用 `method(...)`，它会把这个实例传给函数的 `self`。本例自己的属性存在 `task.__dict__` 里，可以一起查看。

```python
# experiment: E13
class Task:
    def label(self, suffix):
        return self.name + suffix
task = Task()
task.name = "review"
assert task.__dict__ == {"name": "review"}
method = task.label
assert method.__self__ is task
assert method.__func__ is Task.label
assert method("!") == Task.label(task, "!") == "review!"
```

读三个断言：

1. `task.__dict__` 里是赋给实例的 `name`。普通实例通常用字典保存属性引用；有些类使用 `__slots__` 为属性预留固定位置，本章的引用关系仍然适用。
2. `method.__self__` 是 `task`，`method.__func__` 是类上的 `Task.label`。
3. `method("!")` 等价于 `Task.label(task, "!")`：调用时 `task` 自动成为 `self`。

读取 `task.label` 时，Python 用类上的函数和实例 `task` 组成绑定方法。3.5 会再看这个过程怎样通过描述器实现。

**回到 2.1 试一次。** 在 S06A 末尾加上 `add_to_a = a.add`，再调用 `add_to_a("金额待核对")`。猜一猜哪份列表会变。`add_to_a` 已经记住了 `a`，这次调用可以按 `ReviewJob.add(a, "金额待核对")` 来理解。

也可以回到 2.1 的 S06O，检查共享列表究竟存在哪。修改前 `a.__dict__` 和 `b.__dict__` 都为空，`SharedJob.__dict__["findings"] is a.findings` 为真。执行 `a.findings = []` 后，`a.__dict__` 就是 `{"findings": []}`。

### 3.2 继承协作：super 与 MRO

2.5 中 `UrgentJob` 只有一个基类。若同时继承两个基类，而两边都有 `run`，就需要一条确定的查找顺序。这条顺序叫 **MRO**（方法解析顺序），可以通过 `D.__mro__` 查看。`super()` 会在实际实例所属类的顺序里，从当前类的下一站继续查找。下面的 B、C 共同继承 A，D 又继承 B、C。

```python
# experiment: E15
events = []
class A:
    def run(self):
        events.append("A")
class B(A):
    def run(self):
        events.append("B")
        super().run()
class C(A):
    def run(self):
        events.append("C")
        super().run()
class D(B, C):
    def run(self):
        events.append("D")
        super().run()
D().run()
assert events == ["D", "B", "C", "A"]
assert D.__mro__ == (D, B, C, A, object)
```

`D.__mro__` 是 `D → B → C → A → object`。本例中 `D.run()` 通过 `super()` 找到 `B.run()`，`B.run()` 接着找到 `C.run()`，最后到达 `A.run()`。

- `D`、`B`、`C` 都通过 `super().run()` 把控制权交给下一站。`A.run()` 是约定的终点，只记录 `"A"` 后就返回。
- 接力时传入的参数要符合下一站的签名。本例中的四个 `run` 都只接收 `self`。

这条查找顺序由 **C3 线性化**计算。父类的顺序要求互相冲突时，Python 会在定义子类时抛出 `TypeError`。

### 3.3 dataclass 生成了什么：相等、哈希与 frozen

回想第 3 章的字典键。`hash(obj)` 会为查找计算一个整数，字典再用相等比较区分候选键。自定义类的 `__hash__` 决定实例怎样计算这个整数。`@dataclass` 在一些配置下会生成 `__hash__`。下面分别观察三个结果：能否修改列表内容、能否重新给字段赋值，以及生成的哈希方法能否实际算出结果。

```python
# experiment: E16
from dataclasses import dataclass, field, FrozenInstanceError
@dataclass(frozen=True)
class Settings:
    labels: list[str] = field(default_factory=list)
one, two = Settings(), Settings()
one.labels.append("A")
assert one.labels == ["A"] and two.labels == []
try:
    one.labels = []
except FrozenInstanceError:
    pass
else:
    raise AssertionError("frozen 禁止常规重新赋值")
assert Settings.__hash__ is not None  # 方法已经生成
try:
    hash(one)
except TypeError:
    pass
else:
    raise AssertionError("字段中的 list 仍不可哈希")
```

三个动作要分开看：

1. `one.labels.append("A")` 成功。`default_factory` 为每个实例各建一份列表，`frozen` 只限制字段重新绑定，不冻结列表内部。
2. `one.labels = []` 失败，抛 `FrozenInstanceError`。这是字段绑定层面的限制。
3. `hash(one)` 失败，抛 `TypeError`。本例用了 `frozen=True` 和默认的 `eq=True`，因此生成了 `__hash__`。真正计算时，它会用参与哈希的字段值，本例的 `labels` 是列表，无法计算哈希。

参与哈希的字段值必须可哈希。比如把 `labels` 保存为字符串元组 `("A",)`，在本例中就可以计算哈希。

### 3.4 自己写 __eq__ 与 __hash__：== 和字典键

对于 `left == right`，Python 先确定调用顺序。右侧类型是左侧类型的严格子类（直接或间接继承）时，先试右侧的 `__eq__`。其他情况先试左侧。先尝试的一方返回 `NotImplemented`，才会再试另一方。

```python
# experiment: S06Z
events = []
class Left:
    def __eq__(self, other):
        events.append("left")
        return NotImplemented
class Right:
    def __eq__(self, other):
        events.append("right")
        return "matched"
left, right = Left(), Right()
assert (left == right) == "matched"
assert events == ["left", "right"]
assert (left is right) is False
assert events == ["left", "right"]
class Unknown:
    def __eq__(self, other):
        return NotImplemented
one, two = Unknown(), Unknown()
assert (one == two) is False and (one == one) is True
```

按顺序看这三个结果。

- `Left` 与 `Right` 没有继承关系。`left == right` 先调用左侧的 `__eq__`，得到 `NotImplemented`，再尝试右侧并得到 `"matched"`。`events` 记录了这两次调用。
- `__eq__` 可以返回非 `bool` 值。这个例子直接断言比较结果是 `"matched"`。比较本身返回这个结果；只有在布尔上下文或显式调用 `bool()` 时，才对它做真假判断。实际设计相等规则时仍应返回 `bool`，不要模仿这个实验。
- 两边都返回 `NotImplemented` 时，`==` 最后比较身份。`one == two` 为假，`one == one` 为真。

**试着改一处。** 把 `class Right:` 改成 `class Right(Left):`，再预测两处检查 `events` 的断言应该期待什么。

用作字典键的两个对象如果相等，它们的哈希也必须相同。下面用一个哈希碰撞的例子检查哈希相同时字典怎样区分不同的键。

```python
# experiment: E06
class Key:
    def __init__(self, value):
        self.value = value
    def __hash__(self):
        return 1  # 故意碰撞，只用于实验
    def __eq__(self, other):
        if not isinstance(other, Key):
            return NotImplemented
        return self.value == other.value
table = {Key("A"): 10, Key("B"): 20}
assert len(table) == 2 and table[Key("A")] == 10
```

- `Key("A")` 和 `Key("B")` 的哈希都是 `1`，但 `__eq__` 说它们不相等，所以字典仍保留两项；字典先用哈希找桶，再用相等确认键。

只定义 `__eq__`、不定义 `__hash__` 时，类默认变成不可哈希；需要时要么同时定义两者，要么使用 dataclass 的生成规则。

### 3.5 描述器：属性访问也会执行代码

2.2 的 `property` 会在读取属性时执行我们写的读取方法。回想 2.1，给 A 加一个同名实例属性后，A 优先读自己的值。现在把 `cents = 999` 直接放进实例的属性字典，同时保留类上的只读 `property`。先猜 `p.cents` 会从哪拿到结果，再看断言。

```python
# experiment: E14
class Price:
    def __init__(self):
        self._cents = 10
    @property
    def cents(self):
        return self._cents
p = Price()
p.__dict__["cents"] = 999
assert p.cents == 10
try:
    p.cents = 20
except AttributeError:
    pass
else:
    raise AssertionError("只读 property 不能直接赋值")
```

`p.__dict__` 里明明有 `cents = 999`，读取 `p.cents` 却得到 `10`。原因是类上的 `property` 是**数据描述器**，属性访问时先执行它的 `__get__`，实例字典排在后面。没有 setter 时，赋值也会被它接管并拒绝。

类上的有些属性会在访问时执行一段代码，这类对象叫**描述器**。它的类型提供 `__get__`、`__set__`、`__delete__` 中的至少一种；提供 `__set__` 或 `__delete__` 的叫数据描述器。`property` 即使只读也属于数据描述器；普通函数则是非数据描述器，通过实例访问时生成 3.1 的绑定方法。

普通实例读取 `obj.x` 时的默认查找过程：

1. 按类的 MRO 找到第一个同名类属性。如果它是能读取的数据描述器，先执行它的 `__get__`。E14 在这一步得到 `10`。
2. 检查实例自己的属性字典。若其中有 `x`，就取这个值。
3. 回到第一步找到的类属性。如果它有 `__get__`，调用它，否则直接返回类上的值。
4. 当 `__getattribute__` 流程最终抛出 `AttributeError` 时，若定义了 `__getattr__`，用它提供后备值。属性完全不存在、属性读取失败、甚至描述器的 `__get__` 抛出 `AttributeError`，都可能走到这一步。

这条顺序解释了 E13 和 E14：函数是非数据描述器，所以先查实例字典，再生成绑定方法；`property` 是数据描述器，所以实例字典里的同名项被它挡住。自定义 `__getattribute__`、直接访问类属性、隐式调用特殊方法时，还有相应的查找规则。

### 3.6 选读回顾：with 也是一种协议

本节回看第 5 章，不要求首遍学习。`__enter__` 负责进入，`__exit__` 负责退出，也会收到块内抛出的异常信息。下面自己写这两个方法，观察失败时先记录清理，还是先执行外层的 `except`。

```python
# experiment: E11
events = []
class Resource:
    def __enter__(self):
        events.append("enter")
        return self
    def __exit__(self, exc_type, exc, tb):
        events.append("error" if exc_type else "normal")
        events.append("closed")
        return False
try:
    with Resource():
        raise ValueError("bad data")
except ValueError as error:
    assert str(error) == "bad data"
    assert events == ["enter", "error", "closed"]
else:
    raise AssertionError("退出后应把原异常传给调用者")
```

`with Resource():` 先调用 `__enter__`。如果写了 `as`，返回值就交给 `as` 后的目标。`__enter__` 成功后，`with` 才保证调用 `__exit__`。如果进入时就报错，当前管理器的 `__exit__` 不会运行。

本例的 `ValueError` 发生在 `with` 块内，所以 `__exit__` 收到异常信息，依次记录 `error` 和 `closed`。返回 `False` 后，原异常继续传给外层 `except`。返回 `True` 会抑制这个异常。写退出代码时，先确认有哪些异常应继续传给调用者。

把本章出现的协议放在一起：

| 写法 | 调用的特殊方法 | 本章例子 |
| --- | --- | --- |
| `len(obj)` | `__len__` | `ReviewJob` |
| `for x in obj` | 优先用 `__iter__` 取得迭代器，再用 `__next__` 取值；没有 `__iter__` 时尝试从 `__getitem__(0)` 开始的序列协议 | `ReviewJob`、生成器 |
| `left == right` | `__eq__`，按 3.4 的顺序尝试两侧 | `S06Z` |
| `hash(obj)` | `__hash__` | `E06` |
| `obj + other` | `__add__`，可回退到 `__radd__` | `Count` |
| `with obj:` | `__enter__` / `__exit__` | `Resource` |

第 5 章的 `@contextmanager` 也为 `with` 提供进入和退出操作。用类实现时，块内异常的信息传给 `__exit__`。用 `@contextmanager` 时，管理器会让异常在生成器暂停的 `yield` 处抛出。

## 7. 面试问答与迁移

property 为什么不只是 Getter？super 为什么可能调用到兄弟类？frozen 一定可哈希吗？dataclass 会自动校验字段吗？实例方法、类方法和静态方法怎么选？

**参考回答：**

1. `property` 是数据描述器，属性访问可转入 getter/setter/deleter；没有 setter 时，普通赋值会失败，同名实例字典项也不能简单覆盖它。只读 property 本身就是一种接口设计，但若返回内部列表，调用方仍可修改列表。它维护访问约定，不隔离恶意代码。
2. `super()` 相对给定类，在实际对象的 MRO 中继续查找，不固定为“直接父类”。菱形继承中可能走到兄弟类；协作链要约定兼容签名、是否继续 `super` 以及终点，否则可能漏调用或重复初始化。
3. 要分开“生成哈希方法”与“调用成功”。当 `eq=True`（默认）且 `frozen=True` 时，若没有显式定义哈希，dataclass 会生成 `__hash__`；生成时不逐项证明字段可哈希，真正 hash 实例时才可能因 list 字段失败。frozen 限制常规属性赋值/删除，不递归冻结内部内容，也不是安全边界。`unsafe_hash` 同样不能把 list 变成可哈希值。[生成规则](https://docs.python.org/3.12/library/dataclasses.html)
4. 不会。dataclass 根据字段生成初始化、相等和表示等方法，但类型注解不会在构造时自动校验。需要构造检查时实现 `__post_init__`；创建后的修改仍要通过方法或封闭接口维护规则。
5. 需要当前实例状态时用实例方法；需要类或带名字的构造入口时用类方法；既不使用实例也不使用类，只是逻辑上归在类附近时用静态方法。如果后者可被多处复用，普通函数通常更直接。

**换条件自测：** 同一份数据换一种字段表示。先预测三件事：列表能否继续 `append`、`hash(mutable)`、`hash(fixed)`，再运行。

```python

    hash(mutable)
except TypeError:
    pass
else:
    raise AssertionError("参与哈希的list字段不可哈希")

fixed = TupleReport(("review",))
assert fixed.labels == ("review",)
assert hash(fixed) == hash(TupleReport(("review",)))
```

`ListReport` 和 `TupleReport` 都是 `frozen=True`，都生成了 `__hash__`；`hash()` 能否成功，取决于参与哈希的字段值及其内部元素是否可哈希，而不取决于 `frozen` 这个参数。两个类都不允许重新绑定字段，差别只在字段类型。要让结果可哈希，应选择递归元素都可哈希的表示，例如元素均为字符串的元组；`([],)` 这样的元组仍然不可哈希。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 怎样保证每个任务有自己的列表，并让添加、比较和遍历按预期工作？

**三条学习线：**

```text
首遍：字典 → 独立实例状态 → add 先检查再修改 → dataclass → len()/for
对象：组合或继承 → 绑定方法 → 覆盖 → super() 与 MRO
值协议：相等与哈希 → frozen 边界 → NotImplemented 回退 → ABC 声明
```

遇到类题时，先问四个具体问题：列表或状态放在谁身上？调用方法时 `self` 是谁？`len()`、`==` 或 `for` 会用到哪个方法？这次是换任务使用的东西，还是定义另一种任务？

**最容易错：**

- 把每任务独立的列表放在类属性上，多个实例一起被改；
- 以为 `frozen=True` 递归冻结，内部 list 仍然可变；
- 定义了 `__eq__` 却不同步 `__hash__`，对象在字典里行为异常；
- 用继承的类层次代替业务上的可替换契约。

**与前后章：** 第5章留下异常、迭代与资源退出契约，本章把任务状态和规则收进实例，并让对象支持 `len`、`==` 等操作。第7章要把这些对象放进模块、文件和命令行入口，需要先有清晰的对象边界。

**首遍完成后**

- 写出各自持有列表的两个任务，并说明调用 `add` 时 `self` 是哪个实例。
- 让 `add` 在修改前拒绝空白文本，用 `default_factory` 简化初始化，并通过 `len()` 和 `for` 检查结果。

**第二遍按需回看**

- 对象设计：解释绑定方法，选择组合或继承，并用 MRO 说明 `super()` 的下一站。
- 值与协议：说明只读属性、`frozen`、相等和哈希的边界，区分 `NotImplemented` 与异常。
- 状态应用：用枚举区分非法状态值和不允许的状态转换，并检查拒绝后状态不变。

### 8.2 日常工作注意事项

- 每个任务独立的列表放在实例初始化中，或使用 `default_factory`；把它放在类上容易使多个任务共享修改。
- dataclass 不自动校验字段；构造检查放在 `__post_init__`，创建后的修改仍要经过受控入口。
- 定义相等规则后同步检查哈希与可变性；不要用 `unsafe_hash` 绕过设计问题后直接把可变业务对象作字典键。
- `frozen=True` 不递归冻结内部内容，也不保证一定能哈希；元组中的元素仍须可哈希。
- property 和下划线帮助维护接口，不是权限隔离。受控属性仍需验证输入，内部可变值的暴露也要检查。
- 状态名集中定义成枚举；散落的字符串拼错只有运行时才发现，而“值合法”不等于“现在允许执行”。
