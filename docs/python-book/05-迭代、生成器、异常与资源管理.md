## 2. 基础知识讲解
### 2.1 可迭代对象与迭代器：数据源和读取位置分开
列表每次 `iter(list)` 得到独立读取位置；迭代器自身 `iter(it)` 仍返回自己。`next` 耗尽时抛 `StopIteration`，`for` 把它当作正常结束。
```python
values = iter([10, 20])
assert iter(values) is values and next(values) == 10
assert next(values) == 20
assert next(values, "END") == "END"
assert list(values) == []
```
两个列表迭代器可以各自从头读；同一个迭代器耗尽后不会自动重来。移动读取位置不会删除列表元素。

```python
left = iter([10, 20])
right = iter([10, 20])
print(next(left), next(right), next(left), next(right), list(left), list(right))
assert list(left) == [] and list(right) == []
```

```text
10 10 20 20 [] []
```

`left` 和 `right` 是两个独立迭代器，所以交替读取仍各从10开始；最后的 `list(left)` 把已经耗尽的迭代器收成空列表。若改成对同一个 `values` 调用两次 `iter(values)`，两次仍返回同一个对象，第二次会从当前位置继续，而不是重来。
### 2.2 生成器：调用时不执行，取值时才推进
含 `yield` 的函数调用后得到生成器对象。第一次 `next` 才进入函数体，执行到 `yield` 时交出一项并暂停；下一次从暂停处继续，局部变量和执行位置仍然保留。
```python
# experiment: E10
def produce():
    yield 10
    return 99
g = produce()
assert iter(g) is g and next(g) == 10
try:
    next(g)
except StopIteration as exc:
    assert exc.value == 99
    print(exc.value)
else:
    raise AssertionError("应已结束")
assert list(g) == []
print(list(g))
```
生成器的 `return` 值留在结束信号里，不是普通元素。坏行错误也可能到消费时才发生，因此错误处理要包住实际 `next`、`for` 或 `list`。调用 `produce()` 时没有输出，也没有执行`yield`；第一次`next`产生10并暂停，第二次`next`才走到`return 99`，解释器把它包装成`StopIteration.value`。E10实际输出为：

```text
99
[]
```

`yield from` 把逐项产出委派给子生成器，子生成器的 `return` 值成为整个表达式的结果；它还会委派 `send/throw/close`，不只是手写 `for` 的简写。只需要逐项读取或转换时，普通循环更清楚；需要传递结束值或控制信号时再使用委派。上面的输出为 `[1, 2, 99]`：前两个来自子生成器的`yield`，99先成为`parent`中`total`，再由`yield total`交给外层。

```python
def child():
    yield 1
    yield 2
    return 99
def parent():
    total = yield from child()
    yield total
assert list(parent()) == [1, 2, 99]
print(list(parent()))
```

`next(it, default)` 只把耗尽时的 `StopIteration` 换成默认值，不会隐藏数据源的其他错误。异常应按类型和可恢复范围捕获：`for` 取下一项发生在循环体之外，数据源自身的异常要由包住整个消费的代码处理，单条记录的转换错误则在行内处理。生成器内部不要手动 `raise StopIteration` 来结束，它会被转换为 `RuntimeError`。

### 2.3 异常：失败打断正常步骤并向外传播
`try` 中出错后，匹配的 `except` 接住错误；未匹配的错误继续向外传。`else` 只在正常结束时执行，`finally` 无论正常或异常离开都会执行。

常见异常按原因分层，而不是统一写成“出错了”：`FileNotFoundError`/`PermissionError` 属于 `OSError`；`ValueError` 表示值内容不合法；`TypeError` 表示对象类型不支持该操作；`KeyError`/`IndexError` 表示键或下标缺失；`ZeroDivisionError` 表示除数为零；`NameError` 表示名称未绑定，函数内误读导致的 `UnboundLocalError` 是它的子类。`StopIteration` 是迭代器的正常结束信号，`AssertionError` 表示断言失败。

`try/except/else/finally` 的四条路径要一起看。下面只有转换失败，所以不执行`else`；无论成功或失败都执行`finally`：

```python
try:
    value = int("bad")
except ValueError as error:
    print("except", type(error).__name__)
else:
    print("else", value)
finally:
    print("finally")
```

```text
except ValueError
finally
```

成功时输出会变成 `else 12` 后接 `finally`。`except` 按顺序匹配，具体子类应放在能解释它的位置；`else` 中抛出的错误不会被同一个`try`的`except`接住。`finally` 不是“错误处理分支”，它只保证离开前执行，不保证错误被恢复。

业务代码通常捕获 `Exception` 的具体子类并保留上下文，不用裸 `except:` 吞掉所有问题。`KeyboardInterrupt` 和 `SystemExit` 继承 `BaseException` 而不继承 `Exception`，不应被普通业务恢复逻辑一并截获。需要自定义异常时再在第6章以后定义专用类型，不要把所有失败都改写成字符串。
```python
# experiment: E05
text = "采购A"
raw = text.encode("utf-8")
assert len(text) == 3 and len(raw) == 7
assert raw.decode("utf-8") == text
try:
    raw[:1].decode("utf-8")
except UnicodeDecodeError as error:
    print(type(error).__name__)
else:
    raise AssertionError("截断的 UTF-8 字节不能正常解码")
```
只接能解释的错误。E05实际输出`UnicodeDecodeError`，说明错误发生在解码时，而不是`encode`或切片时。`raise 新错误 from 原错误` 既给出业务位置，也保留原因链，便于定位坏行。
```python
# experiment: E02
from copy import deepcopy
a = [{"tags": []}]
alias, shallow, deep = a, a.copy(), deepcopy(a)
a[0]["tags"].append("paid")
assert shallow == [{"tags": ["paid"]}] and deep == [{"tags": []}]
t = ([],)
try:
    t[0] += [1]
except TypeError:
    pass
else:
    raise AssertionError("tuple 的槽位不能重新赋值")
assert t == ([1],)
```
最后一例先修改内部列表，再写回tuple槽位时失败。异常不会自动撤销已发生的修改，浅复制也仍共享内部对象。

`finally` 中写 `return` 会覆盖尚未离开 `try` 的结果，也会抑制正在传播的异常；清理函数因此不能既“保证退出”又偷偷改变调用结论。下面的两次调用都得到清理值，第二次原始错误被吞掉了。

```python
def result_or_error(fail):
    try:
        if fail:
            raise ValueError("原始错误")
        return "正常结果"
    finally:
        return "清理返回值"
assert result_or_error(False) == "清理返回值"
assert result_or_error(True) == "清理返回值"
print(result_or_error(False), result_or_error(True))
```

```text
清理返回值 清理返回值
```

正确迁移方式是让 `finally` 只记录、释放或恢复临时状态，不写 `return`；原结果或异常才会继续交给调用者。

### 2.4 with：把退出动作绑定到代码块
`with` 在进入时取得资源，在离开缩进块时调用退出方法。正常结束、`break`、`return` 或异常离开都会触发退出。
```python
# book-example: B05
from contextlib import contextmanager
events = []
@contextmanager
def session():
    try:
        events.append("open")
        yield events
    finally:
        events.append("close")
with session() as trace: trace.append("work")
assert events == ["open", "work", "close"]
print(events)
```
`@contextmanager` 把生成器的暂停点交给with：进入时推进到 `yield`，退出时恢复并执行 `finally`。B05实际输出`['open', 'work', 'close']`。正常离开时没有异常信息，`with` 不需要压制任何错误；若块内抛错，生成器仍会经过`finally`，然后原异常继续向外传播。
```python
# experiment: E12
from contextlib import closing
events = []
def stream():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")
g = stream()
for item in g:
    assert item == 1
    break
assert events == []
print(events)
g.close()
assert events == ["closed"]
print(events)
events.clear()
with closing(stream()) as managed:
    assert next(managed) == 1
assert events == ["closed"]
print(events)
```
`break` 只退出循环，不负责关闭生成器。`closing` 在离开with时调用 `close()`，暂停的生成器才执行清理。E12依次输出`[]`、`['closed']`、`['closed']`：第一次证明`break`后事件仍为空，第二次是显式`g.close()`的结果，第三次说明`with closing`把同样的关闭动作绑定到代码块出口。
```python
# experiment: E09
events = []
def recorded(fn):
    def wrapped(*args, **kwargs):
        try:
            return fn(*args, **kwargs)
        finally:
            events.append("exit")
    return wrapped
@recorded
def add(a, b):
    return a + b
assert add(1, 2) == 3 and events == ["exit"]
print(add(1, 2), events)
events.clear()
try:
    add(1, "bad")
except TypeError:
    pass
else:
    raise AssertionError("包装器不能吞掉原函数的计算错误")
assert events == ["exit"]
print(events)
```
装饰器把 `finally` 放在原调用外：成功时保留结果，失败时记录退出后继续传播错误。E09实际输出为`3 ['exit', 'exit']`和`['exit']`：第一次断言已经成功调用一次，打印又成功调用一次；随后清空事件，失败调用仍留下一个`exit`，说明`finally`没有改变`TypeError`的传播。
### 2.5 资源数量运行时才知道：ExitStack

有时要打开多少文件取决于输入，无法提前写死多个嵌套 `with`。`ExitStack` 先登记资源，离开时按后进先出顺序统一退出；动态资源仍由同一个所有者管理。

```python
from contextlib import ExitStack, contextmanager

events = []
@contextmanager
def stream(name):
    try:
        yield name
    finally:
        events.append(f"close {name}")

with ExitStack() as stack:
    first = stack.enter_context(stream("first"))
    second = stack.enter_context(stream("second"))
    assert (first, second) == ("first", "second")
assert events == ["close second", "close first"]
print(events)
```

它解决的是“统一登记与倒序退出”，不会替你决定业务读取顺序，也不会吞掉块内异常。资源固定且只有一个时，普通 `with` 更清楚。这里进入顺序是first、second，退出顺序是second、first，实际输出`['close second', 'close first']`；如果第二个资源进入失败，`ExitStack`会退出已经登记的第一个，未登记的资源则还没有进入责任范围。
## 3. 原理讲解与推导
### 3.1 消费触发执行，退出触发清理
生成器的错误不在创建时发生，而在 `next` 推进到坏行时发生；文件关闭也不依赖对象恰好被回收，而由 `with` 的退出路径保证。因果链是：**消费决定执行到哪里，离开决定哪些退出动作运行。**
因此错误处理要包住消费位置，资源管理要包住整个使用范围。只创建生成器、只打开文件，都不代表已经读取或已经正确关闭。

| 动作 | 真正发生什么 | 还不能保证什么 |
| --- | --- | --- |
| `g = read_orders(path)` | 创建生成器，不进入函数体 | 文件尚未打开 |
| `next(g)` | 打开文件并读到第一笔，在`yield`暂停 | 后续坏行尚未发现 |
| `for`取下一项 | 从暂停处继续，推进读取位置 | 不承诺提前停止时关闭资源 |
| `g.close()` | 向暂停点注入退出，执行生成器`finally` | 不替代调用方处理已收到的异常 |
| `with`离开 | 调用上下文退出方法 | 退出方法自身是否正确仍由实现决定 |

还要区分“循环结束”和“资源关闭”：`for` 耗尽可迭代对象后只是不再取下一项，不会额外承诺关闭所有数据源。生成器自然结束会执行自己的清理，提前停止则可能停在 `yield`；这时由拥有资源的调用方结束它。`closing` 只负责在退出时调用 `close()`，不会代替业务代码选择读取多少行，也不会吞掉读取中的异常。若代码块用 `return` 提前离开，退出动作仍先执行，再把结果交回调用处。

#### 案例推进：第二步，用生成器逐行校验
```python
from order_rules import amount_cents_or_none, validate_order, summarize_orders
def read_orders(path, closed_events=None):
    with open(path, encoding="utf-8") as source:
        try:
            for line_number, line in enumerate(source, start=1):
                text = line.strip()
                if not text:
                    continue
                try:
                    order_id, user, amount_text, status = text.split("|")
                    amount_cents = amount_cents_or_none(amount_text)
                    if amount_cents is None: raise ValueError("金额格式错误")
                    order = {"id": order_id, "user": user, "amount_cents": amount_cents, "status": status}
                    errors = validate_order(order)
                    if errors: raise ValueError("；".join(errors))
                except ValueError as error:
                    raise ValueError(f"第{line_number}行：{error}") from error
                yield order
        finally:
            if closed_events is not None:
                closed_events.append(str(path))
```
`with open` 包住生成过程。解析或校验失败时，错误带上原始行号；文件先退出关闭，外层才接到错误。金额与订单规则仍复用第4章函数。可选 `closed_events` 列表只用于观察清理是否发生，不参与业务判断。

#### 案例推进：第三步，取一笔后主动关闭

```python
from contextlib import closing
from pathlib import Path

closed_events = []
early_bad_path = Path("early_bad_orders.txt")
early_bad_path.write_text("A|Alice|19.90|paid\nB|Bob|bad|paid\n", encoding="utf-8")
with closing(read_orders(early_bad_path, closed_events)) as rows:
    first = next(rows)
assert first["id"] == "A"
assert closed_events == [str(early_bad_path)]
print(first["id"], closed_events)
```

第一次 `next` 只解析第一行；离开 `closing` 时生成器收到 `close()`，`finally` 记录关闭事件，因此第二行的坏金额没有被解析。实际输出为 `A ['early_bad_orders.txt']`。如果直接 `break` 而不关闭，生成器会暂停在 `yield`，不能把“循环停了”当成“文件已关闭”。
#### 案例推进：第四步，消费完毕并产出报告
```python
from contextlib import closing
def build_report(path):
    with closing(read_orders(path)) as rows:
        orders = list(rows)
    summary = summarize_orders(orders)
    lines = [f"orders={len(summary['by_id'])}", f"duplicates={len(summary['duplicates'])}",
             f"conflicts={len(summary['conflicts'])}", f"paid_total_cents={summary['paid_total_cents']}"]
    lines.extend(f"{user}={len(ids)}" for user, ids in summary["by_user"].items())
    return "\n".join(lines) + "\n"
report, report_path = build_report(input_path), Path("report.txt")
report_path.write_text(report, encoding="utf-8")
assert report == "orders=3\nduplicates=1\nconflicts=1\npaid_total_cents=2000\nAlice=2\nBob=1\n"
assert report_path.read_text(encoding="utf-8") == report
bad_path = Path("bad_orders.txt"); bad_path.write_text("A|Alice|19.90|paid\nB|Bob|bad|paid\n", encoding="utf-8")
try:
    build_report(bad_path)
except ValueError as error:
    assert "第2行" in str(error) and isinstance(error.__cause__, ValueError)
else:
    raise AssertionError("坏金额应当报错")
```
`closing` 保证生成器被关闭，生成器内的文件 `with` 随后退出。报告使用去重后的三笔订单；坏文件得到带行号错误，而不是空报告。正常报告的实际内容为：

```text
orders=3
duplicates=1
conflicts=1
paid_total_cents=2000
Alice=2
Bob=1
```

坏文件路径上，异常文本包含`第2行`，`error.__cause__`是原金额转换的`ValueError`。第4节案例代码在静态验证中只检查语法；上述报告文本是按紧邻断言写出的预期结果，不冒充已执行证据。

## 7. 面试问答与迁移
**问：为什么列表能读两遍，生成器不能？** 答：列表每次提供新迭代器；生成器自身就是迭代器，位置和局部状态只保留一份，耗尽后不会自动重来。
**问：异常链有什么作用？** 答：新错误说明业务位置，`__cause__` 保留原始转换错误。调用者既知道哪一行坏，也能追到失败原因。
**问：清理代码为什么通常不写 `return`？** 答：`finally` 中的返回会覆盖原结果，甚至让调用者收不到原异常。清理只完成退出动作，让原结果或错误继续传播。
## 8. 本章小结与参考
- 可迭代对象提供数据，迭代器保存本次读取位置。
- 生成器在取值时推进，坏行错误也在消费时出现。
- 异常沿调用链传播，`finally` 保证退出动作执行。
- with把资源退出绑定到代码块，提前停止也要明确关闭。
