## 1. 学习目标与前置知识

能处理一次性数据流，并正确传播错误、关闭资源。前置：第4章。

**本章从这里开始：** 订单文件可能很大，调用方也可能只要第一条。程序不再一次获得全部结果，而是边读边处理：错误何时出现，提前停止后由谁清理？

## 2. 基础知识讲解

### 2.1 先区分集合与消费过程

列表是保存元素的容器；迭代器是按协议逐个提供元素的对象。iter获得迭代器，next取得下一项，结束时抛StopIteration。for把这套过程组织起来。对列表多次iter通常得到独立消费位置，而对迭代器iter通常得到它自己。

这一区别影响接口：接受Iterable不意味着能len，也不意味着能遍历两次。需要反复读取时可以保存为列表，但要接受额外内存代价；一次性流应按一次遍历设计。

#### 案例推进：用三个观察点看见惰性

```python
# study-example: S05A
events = []
def values():
    events.append("start")
    yield 10
    events.append("resume")
    yield 20

stream = values()
assert events == []
assert next(stream) == 10 and events == ["start"]
assert list(stream) == [20] and events == ["start", "resume"]
assert list(stream) == []
```

调用生成器函数先获得生成器对象，第一次推进才进入函数体。yield返回一项并暂停，局部执行状态保留，下一次从暂停点继续。list会消费到结束，消费完再list不是重新执行。这解释了为什么“接受任意Iterable”的函数不能未经说明遍历两次。

#### iter与next是for背后的消费接口

```python
# study-example: S05D
values = iter([10, 20])
assert iter(values) is values
assert next(values) == 10
assert next(values) == 20
assert next(values, "END") == "END"
def combined():
    yield from [1, 2]
    yield 3
assert list(combined()) == [1, 2, 3]
```

next的默认值用于迭代结束；没有默认值时结束由StopIteration表达。yield from把子迭代过程委托出去，不需要自己写一层for再yield。迭代器具有消费状态，生成器是其中一种实现；容器可以产生多个独立迭代器，不能把三个概念互换。

异常还可以用自定义Exception子类表达调用方需要区分的领域失败。add_note为异常补充上下文，raise from表达明确原因，bare raise保留当前失败。异常组与except*放到第11章任务失败后再学习。

### 2.2 yield怎样产生惰性过程

含yield的函数调用通常返回生成器，函数体在被推进时才运行到下一个暂停点。局部状态保留在暂停过程中，下一次next继续执行。return结束，yield from委托子迭代过程。生成器表达式是紧凑写法，但同样不是可重复的惰性列表。

```python
def amounts():
    yield 10
    yield 20
values = amounts()
assert next(values) == 10
assert list(values) == [20]
assert list(values) == []
```

惰性意味着错误也可能推迟到消费时出现。文件已经打开多久、某行已经解析没有，都需要沿消费过程观察。

#### 案例推进：错误可能发生在创建之后

```python
# study-example: S05B
def parse_numbers(lines):
    for line_number, text in enumerate(lines, start=1):
        try:
            value = int(text)
        except ValueError as exc:
            raise ValueError(f"第{line_number}行不是整数") from exc
        yield value

stream = parse_numbers(["10", "bad"])
assert next(stream) == 10
try:
    next(stream)
except ValueError as exc:
    assert "第2行" in str(exc)
    assert isinstance(exc.__cause__, ValueError)
else:
    raise AssertionError("消费坏行时应失败")
```

第一条消费成功不能证明后续数据合法。try只覆盖转换动作，raise from保留底层原因并增加行号。except匹配类型及其子类，多个except通常先具体后一般；捕获Exception也不是捕获所有BaseException派生的控制事件。正常用bare raise可重新抛出当前异常，不必创建一个丢失上下文的新异常。

### 2.3 异常是另一条执行路径

try保护可能失败的操作，except处理已预期类型，else描述未发生异常的正常后续，finally放退出清理。捕获范围越宽，越需要说明错误是否可恢复。不要用一个通用except返回[]把损坏文件伪装成没有订单。

自定义异常应表示调用方需要区分的领域错误；raise from保留底层原因。异常文字提供文件、记录位置等上下文，日志避免暴露凭据和敏感内容。

### 2.4 with建立资源责任边界

进入上下文成功后，无论块内正常结束还是异常退出，管理器都获得退出处理机会。类通过__enter__/__exit__实现协议，contextmanager通过一次yield分隔进入与退出，ExitStack处理动态组合的多资源。

__exit__返回真值会抑制块内异常，不只是表示清理成功。进入过程中失败的半初始化资源，也要在建立它的代码里清理；不能期待尚未进入成功的上下文自动完成全部工作。

### 2.5 提前停止也是正常需求

调用方可能只读第一条、遇到条件break，或者客户端断开。break不普遍等于close。流接口要说明资源由谁拥有、消费结束或提前停止时怎样关闭。把这些路径加入测试，才能避免“完整读完没问题，线上只读一部分就泄漏”。

#### 案例推进：提前退出要有明确的关闭动作

```python
# study-example: S05C
from contextlib import closing
events = []
def stream_values():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")

with closing(stream_values()) as stream:
    assert next(stream) == 1
assert events == ["closed"]
```

closing在离开with时调用对象的close，使本例生成器进入finally。这里退出时没有读第二项，但清理仍发生。for中的break本身不普遍承诺关闭任意迭代器，因此资源拥有者需要明确边界，不能靠“以后垃圾回收会处理”来结束连接。

try/except负责按约定处理失败，else适合未发生异常后的正常后续，finally负责退出动作。finally中return可能覆盖原返回值或原异常，初学时避免把业务返回放在清理代码里。用contextmanager写上下文时，yield只出现一次来分隔进入和退出；自定义类的__enter__/__exit__在下一章实现。

### 2.6 资源数量运行时才知道怎么办

读取一批制度文件时，第三份可能在打开时失败。前两份已经由程序持有，需要立即清理。ExitStack 每成功进入一个上下文就登记它的退出动作；后续进入失败时，先前登记的动作仍按逆序运行。先手写事件顺序，再运行：

```python
# study-example: S05E
from contextlib import ExitStack, contextmanager

events = []
@contextmanager
def source(name):
    if name == "bad":
        raise OSError("无法打开")
    events.append(("open", name))
    try:
        yield name
    finally:
        events.append(("close", name))

try:
    with ExitStack() as stack:
        for name in ["A", "B", "bad"]:
            stack.enter_context(source(name))
except OSError:
    pass
assert events == [("open", "A"), ("open", "B"), ("close", "B"), ("close", "A")]
```

将失败移到处理内容时，指出哪些文件已登记关闭。若所有来源可以逐份独立处理，直接在循环体内逐份使用 with，这样同时占用的文件描述符更少。第 11 章再把“提前退出也要清理”迁移到异步流。

## 3. 原理讲解与推导

### 3.1 用状态解释迭代

生成器在未开始、执行、暂停、结束之间转换；保留状态是一次性消费的原因。对已结束对象再次取值，不会自动回到开头。独立工厂调用可以建立新过程，但原来的外部数据源是否仍可用也要考虑。

### 3.2 用所有权解释清理

谁建立资源，谁就应明确把关闭责任留给自己还是交给调用方。异常、return、break和取消分别改变控制流；清理代码需要覆盖接口允许的所有退出方式，不能依赖某个解释器恰好立即回收对象。

### 3.3 退出代码仍会影响结果

finally中的return/raise可以覆盖原本结果；__exit__的真值可以抑制原异常。清理不应无意隐藏根因。将正常路径、原业务异常、退出异常分开推演，比只看一个with示例更可靠。

#### 学完异常后回看装饰器退出路径

第四章先实现成功路径的包装；现在用E09观察finally如何保证退出事件，异常怎样继续传播。

#### 验证实验 E09

```python
# experiment: E09
from functools import wraps
events = []
def decorate(label):
    events.append("build:" + label)
    def apply(fn):
        @wraps(fn)
        def wrapped(*args, **kwargs):
            events.append("enter:" + label)
            try:
                return fn(*args, **kwargs)
            finally:
                events.append("exit:" + label)
        return wrapped
    return apply
@decorate("outer")
@decorate("inner")
def add(a, b):
    """加法示例。"""
    return a + b
assert events == ["build:outer", "build:inner"]
assert add(1, 2) == 3
assert events[2:] == ["enter:outer", "enter:inner", "exit:inner", "exit:outer"]
assert add.__name__ == "add" and add.__wrapped__.__name__ == "add"
```

## 4. 示例与逐步走查

```python
# book-example: B05
from contextlib import contextmanager
events = []
@contextmanager
def session():
    events.append("open")
    try:
        yield events
    finally:
        events.append("close")
with session() as trace:
    trace.append("work")
assert events == ["open", "work", "close"]
```

### 4.1 沿输入到结果逐步解释

session进入时记录open，yield把列表交给块体；块体追加work；离开时finally追加close。三次写入来自不同执行阶段，异常退出也应保留close，但原异常是否传播由管理器语义决定。
