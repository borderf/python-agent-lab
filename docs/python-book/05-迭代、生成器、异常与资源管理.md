# 第05章　失败、暂停与资源退出

[上一章](04-函数、作用域、闭包与装饰器.md) · [全书目录](教材目录.md) · [下一章](06-类、数据模型与协议.md)

## 1. 学习目标与前置知识

能处理一次性数据流，并正确传播错误、关闭资源。前置：第4章。

**承接与本章主线：** 第4章的普通调用从进入到return结束；本章增加三种退出方式：失败、暂停、提前停止。三者都要回答同一组问题：当前执行停在哪，哪些对象或外部资源仍被持有，谁负责清理。产出是可被类和服务复用的迭代与退出契约。

**本章从这里开始：** 订单文件可能很大，调用方也可能只要第一条；文件可能损坏，程序可能在读第三份材料时打不开。程序不再一次获得全部结果，而是边读边处理。本章按“失败→清理→逐项消费→暂停→提前停止→多个资源”推进，每步只增加一种退出方式。

第一次阅读沿一份“每行一个金额”的材料前进：先让坏行报告错误，再保证来源关闭，然后一行一行取得结果，最后处理只读一部分的情况。每一步都回答：**执行到哪里、调用方拿到什么、谁负责收尾？** 多资源的ExitStack与后面的机制实验可以第二遍深入；初读先把单个来源的三种退出走通。

## 2. 基础知识讲解

普通函数的`return`只是正常结束。本章还要区分另外几种退出：

| 行为 | 含义 |
| --- | --- |
| `return` | 正常结束函数，把结果交回调用者 |
| 异常传播 | 沿调用关系向上展开退出，直到被某层捕获 |
| `yield` | 暂停执行，保留继续执行所需的状态 |
| `break` | 退出当前循环，不自动关闭所有迭代器或资源 |

每条出口都必须说明“已经做了什么、还没做什么、谁负责收尾”。

### 2.1 异常是另一条执行路径

把每一行文本转成整数，可能在第十行才失败。调用方既需要知道处理到哪里，也需要保证已打开的资源会关闭。只有正常返回无法表达这些路径，所以先认识异常怎样转移执行。

先跟踪一条坏订单：程序想把文本“金额未知”转成整数，转换失败，当前正常步骤被打断。`try`把可能失败的语句圈起来，`except`处理预期错误；成功后的操作放在`else`，退出时必须执行的清理放在`finally`。每次只加一个分支并预测路径。

#### 案例推进：先用一次转换失败认识退出路径

```python
# study-example: S05W
events = []
try:
    number = int("bad")
except ValueError:
    events.append("invalid")
else:
    events.append("valid")
finally:
    events.append("finished")
assert events == ["invalid", "finished"]
```

把输入改成`"12"`，应得到`valid`与`finished`，`number`等于12。错误发生后不会回到`try`中失败语句的下一行继续；本例由`except`接手，最后执行`finally`。

按时刻看同一段程序：

| 转换输入 | try 中发生什么 | 接下来执行 | 最终 events |
| --- | --- | --- | --- |
| `"12"` | 得到整数12 | else，再 finally | `valid`、`finished` |
| `"bad"` | `int` 抛 ValueError，后面的正常步骤中断 | 匹配的 except，再 finally | `invalid`、`finished` |

`else`只在try块正常完成时进入；`finally`是退出时安排清理的地方。若异常类型没有被当前except匹配，finally仍有机会执行，异常随后继续向外传播。它不是撤销已完成修改的事务；异常、资源关闭与业务回滚分别考虑。

自定义异常应表示调用方需要区分的领域错误；`raise from`保留底层原因。异常文字提供文件、记录位置等上下文，日志避免暴露凭据和敏感内容。自定义异常类在第6章学会继承后再写；本章先使用内置异常。`add_note`（3.11+）可在异常上追加说明，例如`error.add_note("...")`；异常组到第11章再学习。

**异常只回答“哪里失败”，不自动回答“已经打开的资源怎么办”。** 接下来把清理责任写进控制流。

### 2.2 用 with 把清理写进退出路径

如果每段代码都写`try/finally`，清理容易漏在某个`return`或异常分支里。上下文管理器把“进入”和“退出”绑成一个边界：进入成功后，无论块内正常结束还是异常退出，退出处理都会获得机会。

#### 案例推进：把清理写进 with 的退出路径

```python
# study-example: S05X
import io

stream = io.StringIO("orders")
with stream as managed:
    assert managed.read() == "orders"
assert stream.closed
```

`io.StringIO`是标准库现成的上下文管理器：进入`with`后可以读取，离开时关闭。块内正常结束或抛异常，退出处理都会发生；这里先学会**使用**现成的管理器，2.6再用生成器**制造**一个管理器。

先对照熟悉的 `try/finally`。两种写法都让这个已创建来源在退出时关闭；第二种把“进入/退出”的约定交给来源对象：

```python
# study-example: S05Y
from io import StringIO

first = StringIO("10\n")
try:
    assert first.readline().strip() == "10"
finally:
    first.close()
assert first.closed

second = StringIO("10\n")
with second as source:
    assert source.readline().strip() == "10"
assert second.closed
```

这里的StringIO是在内存里模拟文件接口，不是已经打开磁盘文件。`with`不是所有资源都能自动使用的语法：对象需提供相应上下文管理协议。进入成功后，块内正常结束、return或异常退出都会经过退出处理；只有退出处理实际关闭了资源，才能说资源已关闭。第7章再用真实文件验证。

`__exit__`返回真值会**抑制**块内异常，不只是表示“清理成功”；这是容易把失败吞掉的地方。进入过程中失败的半初始化资源，也要在建立它的代码里清理，不能期待尚未进入成功的上下文自动完成全部工作。自定义类的`__enter__/__exit__`在第6章实现，本章先用标准库管理器理解协议。

**清理解决“资源何时关闭”，但一批订单仍不能一次读入内存。** 下一步让数据逐项到来。

### 2.3 一次性消费：iterable 与 iterator

列表是保存元素的容器；迭代器是按协议逐个提供元素的对象。`iter`获得迭代器，`next`取得下一项，结束时抛`StopIteration`；`for`把这套过程组织起来。

先把列表想成可以重复打开的订单清单，把迭代器想成本次阅读的位置：从同一清单各自取得两个迭代器，两个位置可以独立前进；同一个迭代器则延续已有位置。它是帮助想象的模型，实际能否重复读取还取决于数据来源。

```python
# study-example: S05D
values = iter([10, 20])
assert iter(values) is values
assert next(values) == 10
assert next(values) == 20
assert next(values, "END") == "END"
assert list(values) == []
```

对列表多次`iter`通常得到独立消费位置；对迭代器`iter`通常得到它自己。这一区别影响接口：接受`Iterable`不意味着能`len`，也不意味着能遍历两次。需要反复读取时可以保存为列表，但要接受额外内存代价；一次性流应按一次遍历设计。

`next`的默认值用于迭代结束；没有默认值时结束由`StopIteration`表达。迭代器具有消费状态，生成器是其中一种实现；容器可以产生多个独立迭代器，不能把三个概念互换。

例如同一个列表分别调用两次`iter`，两个迭代器都可先取到10；对同一个`values`反复调用`next`，取到的是10、20、结束。`for`大致就是先取得迭代器，再反复取下一项，直到迭代正常结束；它还会执行循环体，不能把“循环结束”直接等同“所有资源已关闭”。

### 2.4 生成器：让函数在 yield 处暂停

含`yield`的函数调用通常返回生成器，函数体在被推进时才运行到下一个暂停点。局部状态保留在暂停过程中，下一次`next`继续执行；`return`结束，`yield from`委托子迭代过程。

```python
# study-example: S05A
events = []
def values():
    events.append("start")
    yield 10
    events.append("resume")
    yield 20

stream = values()
assert events == []
assert next(stream) == 10 and events == ["start"]
assert list(stream) == [20] and events == ["start", "resume"]
assert list(stream) == []
def combined():
    yield from [1, 2]
    yield 3
assert list(combined()) == [1, 2, 3]
```

调用生成器函数先获得生成器对象，第一次推进才进入函数体。`yield`返回一项并暂停，局部执行状态保留，下一次从暂停点继续。`list`会消费到结束，消费完再`list`不是重新执行；这解释了为什么“接受任意Iterable”的函数不能未经说明遍历两次。

把S05A按时间展开：

| 动作 | 函数体进度 | 得到什么 | events |
| --- | --- | --- | --- |
| `stream = values()` | 尚未进入函数体 | 一个生成器对象 | `[]` |
| `next(stream)` | 执行到第一个yield并暂停 | `10` | `["start"]` |
| `list(stream)` | 从暂停处继续，到结束 | 剩余的 `[20]` | `["start", "resume"]` |
| 再次 `list(stream)` | 已经结束，不自动重来 | `[]` | 不变 |

想再执行一次，需要调用 `values()` 创建新生成器；如果生成器依赖的外部文件已关闭或不能重读，还要另行准备来源。生成器不保证天然低内存：它可能仍引用一个很大的列表，后面也可能把所有结果收集起来。

#### 案例推进：错误可能发生在创建之后

惰性意味着错误也可能推迟到消费时出现。文件已经打开多久、某行已经解析没有，都需要沿消费过程观察。

```python
# study-example: S05B
def parse_numbers(lines):
    for line_number, text in enumerate(lines, start=1):
        try:
            value = int(text)
        except ValueError as exc:
            raise ValueError(f"第{line_number}行不是整数") from exc
        yield value

stream = parse_numbers(["10", "bad"])
assert next(stream) == 10
try:
    next(stream)
except ValueError as exc:
    assert "第2行" in str(exc)
    assert isinstance(exc.__cause__, ValueError)
else:
    raise AssertionError("消费坏行时应失败")
```

第一条消费成功不能证明后续数据合法。`try`只覆盖转换动作，`raise from`保留底层原因并增加行号。`except`匹配类型及其子类，多个`except`通常先具体后一般；捕获`Exception`也不是捕获所有`BaseException`派生的控制事件。裸`raise`可重新抛出当前异常，不必创建丢失上下文的新异常。

把这次失败放回时间线：`parse_numbers(...)`只创建生成器；第一次`next`才读取第一行并产生10；第二次`next`读到坏的第二行，异常从这次推进向调用方传播。要捕获这个错误，`try`必须覆盖消费动作；只在创建生成器时加`try`无法处理随后发生的转换错误。

**生成器能暂停，但调用方可能永远不消费到结束。** 下一节处理提前停止。

### 2.5 提前停止也是正常需求

调用方可能只读第一条、遇到条件`break`，或者客户端断开。`break`不普遍等于`close`。流接口要说明资源由谁拥有、消费结束或提前停止时怎样关闭。把这些路径加入测试，才能避免“完整读完没问题，线上只读一部分就泄漏”。

#### 案例推进：提前退出要有明确的关闭动作

```python
# study-example: S05C
from contextlib import closing
events = []
def stream_values():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")

with closing(stream_values()) as stream:
    assert next(stream) == 1
assert events == ["closed"]
```

`closing`在离开`with`时调用对象的`close`，使本例生成器进入`finally`。这里退出时没有读第二项，但清理仍发生。`for`中的`break`本身不普遍承诺关闭任意迭代器，因此资源拥有者需要明确边界，不能靠“以后垃圾回收会处理”来结束连接。

本例先通过`next`进入了生成器的try块，然后才提前关闭。若生成器从未开始执行，直接close不会先运行函数体，也不能期待尚未进入的finally执行；因此不要在生成器外提前取得资源，却依赖一个从未启动的生成器负责关闭。由谁创建和拥有资源，就让谁在明确边界安排清理。

`try/except`负责按约定处理失败，`else`适合未发生异常后的正常后续，`finally`负责退出动作。`finally`中`return`可能覆盖原返回值或原异常，初学时避免把业务返回放在清理代码里。

### 2.6 资源数量运行时才知道：ExitStack

读取一批制度文件时，第三份可能在打开时失败。前两份已经由程序持有，需要立即清理。`ExitStack`每成功进入一个上下文就登记它的退出动作；后续进入失败时，先前登记的动作仍按逆序运行。

生成器已经会暂停；`@contextmanager`用一次`yield`把“进入”和“退出”分开：`yield`之前是进入，之后是退出。它不是新的资源机制，仍是上下文管理器协议，只是写法更短。下面这个 ExitStack 例子和后面的 B05 都建立在已经学过的生成器上。

#### 案例推进：多个资源按逆序退出

```python
# study-example: S05E
from contextlib import ExitStack, contextmanager

events = []
@contextmanager
def source(name):
    if name == "bad":
        raise OSError("无法打开")
    events.append(("open", name))
    try:
        yield name
    finally:
        events.append(("close", name))

try:
    with ExitStack() as stack:
        for name in ["A", "B", "bad"]:
            stack.enter_context(source(name))
except OSError:
    pass
assert events == [("open", "A"), ("open", "B"), ("close", "B"), ("close", "A")]
```

将失败移到处理内容时，指出哪些文件已登记关闭。若所有来源可以逐份独立处理，直接在循环体内逐份使用`with`，这样同时占用的文件描述符更少。第11章再把“提前退出也要清理”迁移到异步流。

| 时刻 | 已成功进入的来源 | 发生的动作 |
| --- | --- | --- |
| 进入A后 | A | 注册A的退出动作 |
| 进入B后 | A、B | 再注册B的退出动作 |
| 进入bad失败 | A、B | bad没有成功进入；已登记的先B后A退出 |

这个例子中的source是用生成器制作的教学上下文管理器，不是真实打开了文件。真实资源若在进入过程中创建后又失败，建立它的代码还需处理自己的半初始化资源。

## 3. 原理讲解与推导

### 3.1 用状态解释迭代

生成器在未开始、执行、暂停、结束之间转换；保留状态是一次性消费的原因。对已结束对象再次取值，不会自动回到开头。独立工厂调用可以建立新过程，但原来的外部数据源是否仍可用也要考虑。

#### 暂停不等于调用已经结束

`yield`暂停时，生成器需保留继续执行所需的局部状态；被这些状态引用的对象也可能继续存活。它不同于第4章已经完成的`return`。`close`或消费结束会结束这条执行，但被其他地方引用的数据仍按可达性决定生命周期。把“暂停、结束、对象不再可达、资源关闭”分开画，E10/E12便是同一模型的两种实验。

### 3.2 用所有权解释清理

谁建立资源，谁就应明确把关闭责任留给自己还是交给调用方。异常、`return`、`break`和取消分别改变控制流；清理代码需要覆盖接口允许的所有退出方式，不能依赖某个解释器恰好立即回收对象。

### 3.3 退出代码仍会影响结果

`finally`中的`return/raise`可以覆盖原本结果；`__exit__`的真值可以抑制原异常。清理不应无意隐藏根因。将正常路径、原业务异常、退出异常分开推演，比只看一个`with`示例更可靠。

#### 增量赋值为什么可能先改变对象，再失败

对内置列表，普通`x = x + y`先构造新列表，再绑定`x`；`x += y`尝试原地加法并把结果写回目标。一般对象可通过`__iadd__`定义行为，未实现或返回`NotImplemented`时再按相应普通运算规则处理，因此`+=`不是承诺原地修改的统一语法。

```python
# study-example: S05Z
left = [1]
alias = left
left = left + [2]
assert alias == [1] and left == [1, 2]
left = [1]
alias = left
left += [2]
assert left is alias and alias == [1, 2]
box = ([],)
try:
    box[0] += [3]
except TypeError:
    pass
else:
    raise AssertionError("tuple slot should reject assignment")
assert box == ([3],)
```

最后一例依次发生：读取tuple槽位里的列表；列表完成原地扩展；尝试把结果写回tuple槽位；写回被拒绝。异常表示语句未正常完成，不表示前面副作用自动撤销。tuple不可变约束的是其直接引用槽位，不冻结被引用列表。E02据此复查复制与异常的组合。

## 4. 示例与逐步走查

```python
# book-example: B05
from contextlib import contextmanager
events = []
@contextmanager
def session():
    events.append("open")
    try:
        yield events
    finally:
        events.append("close")
with session() as trace:
    trace.append("work")
assert events == ["open", "work", "close"]
```

### 4.1 沿输入到结果逐步解释

进入`with`时，`contextmanager`推进`session`到`yield`：先记录`open`，再把`events`交给`trace`。块内追加`work`，所以此时事件为`open`、`work`。离开`with`时恢复生成器，`finally`追加`close`，形成`open`、`work`、`close`。

为什么`yield`之后的清理会发生？上下文管理器负责在块退出时继续或结束这段生成器；不是普通`for`遇到`break`就自动替所有迭代器`close`。将块内工作改成抛异常，`finally`仍应执行，但异常默认继续传播。

因此资源责任包含两个独立要求：确实关闭，以及不要误把失败改成成功。只看`closed`标记并不足以验证第二项。

#### 把本章连成一条读取链

下面用内存中的文本模拟订单金额来源，每行单位为分。解析器负责逐行转换并报告位置；外层 `with` 拥有并关闭来源；`closing` 负责在提前停止时关闭已经创建的生成器。三个场景是各自独立的新来源：

```python
# study-example: S05P
from contextlib import closing
from io import StringIO

def amounts(lines):
    for number, text in enumerate(lines, 1):
        try:
            value = int(text.strip())
        except ValueError as error:
            raise ValueError(f"第{number}行不是整数") from error
        yield value

# 正常消费：读取两行，两个with按里到外退出。
normal = StringIO("10\n20\n")
with normal as source, closing(amounts(source)) as stream:
    assert list(stream) == [10, 20]
assert normal.closed

# 提前停止：第二行尚未读取，退出时仍关闭生成器和来源。
early = StringIO("10\n20\n")
with early as source, closing(amounts(source)) as stream:
    assert next(stream) == 10
assert early.closed

# 第二行损坏：错误从消费处传播；离开with后来源仍已关闭。
broken = StringIO("10\nbad\n")
try:
    with broken as source, closing(amounts(source)) as stream:
        assert next(stream) == 10
        next(stream)
except ValueError as error:
    assert "第2行" in str(error)
    assert isinstance(error.__cause__, ValueError)
else:
    raise AssertionError("损坏行应当报错")
assert broken.closed
```

先预测：如果只调用 `amounts(source)` 而不消费，是否已经读过第一行？如果在 `next(stream)` 之前退出，来源由谁关闭？如果把异常处理改成返回空列表，调用方还能否区分坏数据与真实空结果？再实际运行并沿表解释：

| 情况 | 结果或错误 | 来源何时关闭 |
| --- | --- | --- |
| 正常 | 得到10、20 | 消费完成后退出外层with |
| 提前停止 | 只得到10 | 退出时先关闭生成器，再关闭来源 |
| 坏第二行 | 第二次推进时抛带行号的ValueError | 异常离开with时关闭 |

示例把文件对象交给解析器读取，但解析器没有接管来源的关闭责任。外层掌握来源生命周期；若改为由生成器内部打开真实文件，应重新设计所有权，并验证已启动后提前关闭。三种场景使用模拟来源，第7章再迁移到真实文件和JSONL。

#### 验证实验 E09：装饰器退出路径

第四章先实现成功路径的包装；现在用E09观察`finally`如何保证退出事件，异常怎样继续传播。

```python
# experiment: E09
from functools import wraps
events = []
def decorate(label):
    events.append("build:" + label)
    def apply(fn):
        @wraps(fn)
        def wrapped(*args, **kwargs):
            events.append("enter:" + label)
            try:
                return fn(*args, **kwargs)
            finally:
                events.append("exit:" + label)
        return wrapped
    return apply
@decorate("outer")
@decorate("inner")
def add(a, b):
    """加法示例。"""
    return a + b
assert events == ["build:outer", "build:inner"]
assert add(1, 2) == 3
assert events[2:] == ["enter:outer", "enter:inner", "exit:inner", "exit:outer"]
assert add.__name__ == "add" and add.__wrapped__.__name__ == "add"
```

## 7. 面试问答与迁移

`for`的`break`会自动`close`吗？`finally`里`return`有何风险？异常链为何有助于调试？`yield`暂停时保留了什么？

**参考回答：**

1. `break`只退出当前循环，不保证调用迭代器的close。某次实验中生成器恰好被回收，不能证明break负责清理；让变量继续保留生成器再测试，就能看出差别。谁拥有资源，谁应通过with、finally或适用的closing安排退出。
2. finally在离开try时执行，其中return会覆盖待返回的值，还可能吞掉正在传播的异常。清理应完成释放并让原控制流继续；若清理本身失败，也要决定如何保留原始故障信息。
3. `raise DomainError(...) from exc`用 `__cause__` 连接业务错误与底层异常，使调用方获得稳定语义，调试者仍能追到原因；`from None`隐藏展示中的自动异常上下文，并不等于删除所有底层信息。
4. yield保留暂停的执行位置、局部绑定和关联执行状态；这些绑定可继续引用大列表、文件等对象。惰性生成减少一次性产出，不保证占用一定小；提前停止时生成器里的资源也可能仍开着。

**换条件自测：** 保留生成器变量，取一项就break，再观察finally是否已经运行；显式close后再次观察。接着让 `__enter__` 自身失败，解释为什么不能指望尚未成功进入的with调用 `__exit__` 清理一切。

## 8. 本章小结与参考

### 8.1 主要知识点总结

- 异常路径与正常路径分开表达，`finally`和`with`负责确定的退出清理。
- 可迭代对象提供取元素的方式，迭代器保存消费进度，生成器可以暂停并继续。
- 惰性执行会推迟计算与错误，需同时观察创建、推进和关闭的时机。
- 一次操作已发生的修改，不会因后续异常自动恢复；退出与回滚要分别设计。

### 8.2 日常工作注意事项

- 记录日志时为了查看内容而`list(iterator)`，可能先把迭代器耗尽；确认后续还需不需要消费，必要时有界保存结果。
- 不要用宽泛`except`返回空列表掩盖文件损坏或外部失败；只处理能解释的错误，保留异常链与调用现场。
- 文件和连接使用明确的关闭边界。提前`break`、异常或取消都要验证清理，不依赖对象恰好立即回收。
