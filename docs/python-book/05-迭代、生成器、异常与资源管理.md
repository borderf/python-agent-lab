## 2. 基础知识讲解

读本章的代码时，先问一句：**下一步会执行到哪？** `return` 结束这次函数调用，`yield` 交出一项后暂停，`break` 退出当前循环。发生异常时，Python 会离开当前语句，去找能接住这个错误的 `except`。

### 2.1 异常是另一条执行路径

先只看一行。假如 `int(...)` 转换失败，紧接着的语句还会执行吗？

#### 第一步：先只认识失败怎样打断正常步骤

`int("12")` 得到整数 `12`。`int("bad")` 无法转换，会抛出 `ValueError`。程序执行到这一行就转去找错误处理代码。

下面这段故意触发 `ValueError`，先看执行会停在哪一行。

```text
number = int("bad")     # 这里抛出 ValueError
print("转换完成")        # 执行不到这一行
```

#### 第二步：用 `try/except` 接住一种已知错误

```python
# study-example: S05F
events = []
try:
    number = int("bad")
    events.append("转换完成")
except ValueError:
    events.append("金额格式错误")
events.append("本次处理结束")

assert events == ["金额格式错误", "本次处理结束"]
```

输入为 `"bad"` 时，`int` 抛出 `ValueError`，跳过 `try` 里的“转换完成”，从匹配的 `except` 开始执行。`except` 结束后，程序继续执行外面的“本次处理结束”。

**试着改一处。** 把 `"bad"` 换成 `"12"`，预测 `events`，再把断言改成你的预期。若抛出别的类型且当前 `except` 不匹配，错误会继续传给调用者。

#### 第三步：再加成功后续与退出收尾

下面要记录两件事。转换成功才记录 `valid`，放在 `else`。无论怎样离开，都记录 `finished`，放在 `finally`。

#### 案例推进：先用一次转换失败认识退出路径

```python
# study-example: S05W
events = []
try:
    number = int("bad")
except ValueError:
    events.append("invalid")
else:
    events.append("valid")
finally:
    events.append("finished")
assert events == ["invalid", "finished"]
```

运行后，对照表格，把输入改成 `"12"`，并把断言改成你预测的结果。

| 转换输入 | try 中发生什么 | 接下来执行 | 最终 events |
| --- | --- | --- | --- |
| `"12"` | 得到整数12 | else，再 finally | `valid`、`finished` |
| `"bad"` | `int` 抛 ValueError，后面的正常步骤中断 | 匹配的 except，再 finally | `invalid`、`finished` |

`else` 只在 `try` 正常走到末尾时执行。错误没有被 `except` 接住时，也会先执行 `finally`，再继续向外抛出。下节把 `finally` 里的事件记录换成关闭文件。

#### 第四步：什么时候由自己的函数主动raise

`int("-3")`转换成功，但我们的订单数量不允许负数。转换工具不知道这条业务规则，所以由函数在检查后主动报告：

```python
# study-example: S05G
def parse_count(text):
    count = int(text)
    if count < 0:
        raise ValueError("数量不能为负数")
    return count

assert parse_count("3") == 3
try:
    parse_count("-3")
except ValueError as error:
    assert str(error) == "数量不能为负数"
else:
    raise AssertionError("负数应当被拒绝")
```

`raise ValueError(...)` 把错误和说明交给调用者。调用者用 `except ValueError as error` 接住它，再用 `str(error)` 读取说明。

接下来继续问：转换失败之前已经打开的文件，应该在哪里关闭？

### 2.2 用 with 把清理写进退出路径

先用 `StringIO` 模拟文件。它把文本放在内存里，读取和关闭的顺序都能直接观察。第 7 章再换成磁盘文件。

`StringIO("orders")` 创建一个含有文本 `orders` 的来源。`read()` 读取剩余文本，`readline()` 读一行，`closed` 告诉你来源是否已关闭。

#### 案例推进：把清理写进 with 的退出路径

```python
# study-example: S05X
import io

stream = io.StringIO("orders")
with stream as managed:
    assert managed is stream
    assert managed.read() == "orders"
assert stream.closed
assert managed is stream and managed.closed
```

在这个例子中，`StringIO` 的进入方法返回它自身，所以 `managed` 和 `stream` 引用同一个对象。退出时，`StringIO` 会关闭自己。块外仍可通过 `managed` 查看已经关闭的对象。能提供进入和退出操作的对象叫**上下文管理器**。

下面用 `try/finally` 和 `with` 分别管理一个文本来源。

```python
# study-example: S05Y
from io import StringIO

first = StringIO("10\n")
try:
    assert first.readline().strip() == "10"
finally:
    first.close()
assert first.closed

second = StringIO("10\n")
with second as source:
    assert source.readline().strip() == "10"
assert second.closed
```

用 `try/finally` 时，由你调用 `close()`。用 `with` 时，由 `StringIO` 提供关闭动作，由 `with` 在离开缩进块时调用。

#### 改一个条件：块内失败，退出动作还会执行吗

```python
# study-example: S05H
from io import StringIO

source = StringIO("bad\n")
try:
    with source as lines:
        value = int(lines.readline())
except ValueError:
    assert source.closed
else:
    raise AssertionError("坏文本应当报错")
assert source.closed
```

读到 `bad` 后，`int` 报错，执行先离开 `with`。来源已经关闭，外层 `except` 才接住错误。如果把整组 `try/except` 放进 `with`，接住错误时来源仍然开着。块内的 `return` 或 `break` 也会在离开 `with` 时触发退出处理。

#### 第二遍：`with` 调用什么

| 时刻 | `with` 的动作 |
| --- | --- |
| 求值 | 先求 `with` 后的表达式，得到上下文管理器，再查找进入和退出方法 |
| 进入 | 调用管理器的 `__enter__()`，等待它返回一个值 |
| 绑定 | 如果有 `as`，将进入方法的返回值赋给 `as` 后的目标 |
| 执行 | 绑定完成后，才执行第一条缩进语句 |
| 无异常退出 | 调用 `__exit__(None, None, None)`，包括块自然结束或通过 `return`、`break`、`continue` 离开 |
| 因异常退出 | 调用 `__exit__(异常类型, 异常对象, traceback)` |

`as` 拿到什么由 `__enter__()` 决定。它可以返回管理器自身，也可以返回另一个对象。省略 `as` 时，Python 仍调用 `__enter__()`，只是丢弃返回值。普通名称按外围作用域的规则绑定，`with` 块结束后仍能访问它。资源的可用状态则由退出动作决定，正如上面的 `managed` 仍可访问，但流已经关闭。

`__enter__()` 成功返回后，Python 保证调用 `__exit__()`。例如 `as (first, second)` 因无法解包而失败时，第一条块内语句尚未执行，退出方法也会收到异常。如果 `__enter__()` 自己抛出异常，已取得的资源由进入逻辑负责清理。收到异常后，`__exit__()` 返回真值表示抑制，返回假值表示继续传播。无异常退出时，Python 忽略它的返回值。完整步骤见 [Python 3.12 的 `with` 语句规范](https://docs.python.org/3.12/reference/compound_stmts.html#the-with-statement)。

### 2.3 可迭代对象与迭代器

把列表传给 `iter()`，会得到一个**迭代器**。它记录这次读到哪，每次 `next()` 取出一项并向前移动。能用 `iter(obj)` 取得迭代器的对象叫**可迭代对象**，列表和迭代器都属于这一类。

#### 用 next 观察位置

```python
# study-example: S05D
values = iter([10, 20])
assert iter(values) is values
assert next(values) == 10
assert next(values) == 20
assert next(values, "END") == "END"
assert list(values) == []
```

两次 `next` 依次拿到 `10`、`20`。再用 `next(values, "END")` 时，迭代器已经读完，所以返回你提供的默认值 `"END"`。最后 `list(values)` 收集剩余项，自然得到 `[]`。

`next(values)` 不带默认值时，读完会抛出 `StopIteration`。这不是程序出错，而是“没有下一项”的正常信号；`for` 正是靠它结束循环。

#### 同一个列表，两份读取位置

```python
# study-example: S05I
rows = [10, 20]
left = iter(rows)
right = iter(rows)
assert next(left) == 10
assert next(left) == 20
assert next(right) == 10

alias = right
assert next(alias) == 20
assert next(right, "END") == "END"
assert rows == [10, 20]  # 移动读取位置，没有从列表中删除元素
```

`left` 和 `right` 是从同一个列表得到的两个迭代器，读取位置各自移动。`alias = right` 给同一个迭代器起了另一个名字，所以通过 `alias` 取值也会推进 `right`。

| 对象 | 调用 `iter()` 得到什么 | 再读一遍会怎样 |
| --- | --- | --- |
| 列表 `rows` | 每次得到一个新迭代器 | 可以从头读 |
| 迭代器 `iter(rows)` | 返回这个迭代器自身 | 从当前位置接着读，耗尽后没有下一项 |

**先预测。** 两次 `for` 都读 `rows`，第二次会得到什么？如果先写 `it = iter(rows)`，两次循环都读 `it`，第二次呢？

#### 第二遍：`for` 怎么知道已经读完

`for` 先用 `iter(obj)` 取得迭代器，再反复用 `next(it)` 取值。列表通过 `__iter__()` 提供新迭代器。迭代器的 `__iter__()` 返回自身，它的 `__next__()` 在耗尽时抛出 `StopIteration`。

```text
it = iter(obj)
while True:
    try:
        item = next(it)
    except StopIteration:
        break
    执行循环体
```

这里只捕获取值时抛出的 `StopIteration`。循环体自己抛出的异常会继续向外传。

### 2.4 生成器：让函数在 yield 处暂停

列表的迭代器从已有数据里取值。如果想写一段代码，在每次取值时才算出一项，可以用带 `yield` 的**生成器函数**。调用它不会执行函数体，只得到一个**生成器对象**；第一次 `next` 才开始运行。

#### 案例推进：先看函数体在哪一步执行

```python
# study-example: S05A
events = []
def values():
    events.append("start")
    yield 10
    events.append("resume")
    yield 20

stream = values()
assert events == []
assert next(stream) == 10 and events == ["start"]
assert list(stream) == [20] and events == ["start", "resume"]
assert list(stream) == []
```

按下面的顺序读 S05A，重点看哪一步开始执行函数体。

| 动作 | 函数体进度 | 得到什么 | events |
| --- | --- | --- | --- |
| `stream = values()` | 尚未进入函数体 | 一个生成器对象 | `[]` |
| `next(stream)` | 执行到第一个 `yield` 并暂停 | `10` | `["start"]` |
| `list(stream)` | 从暂停处继续，到结束 | 剩余的 `[20]` | `["start", "resume"]` |
| 再次 `list(stream)` | 已经结束，不自动重来 | `[]` | 不变 |

`yield` 做三件事：暂停函数执行，交出一个值，保留局部变量和“执行到哪”的位置。下一次 `next` 从暂停处继续；`return` 则结束函数，不会从原处恢复。

生成器对象自动实现了迭代器协议：`__iter__` 返回自己，`__next__` 取下一项。所以它能直接放在 `for` 里，也能用 `next` 一次取一项。

#### 案例推进：错误可能发生在创建之后

现在给生成器两行 `['10', 'bad']`。先猜哪一步报错：创建时、第一次取值时，还是第二次取值时？

```python
# study-example: S05B
def parse_numbers(lines):
    for line_number, text in enumerate(lines, start=1):
        try:
            value = int(text)
        except ValueError as exc:
            raise ValueError(f"第{line_number}行不是整数") from exc
        yield value

stream = parse_numbers(["10", "bad"])
assert next(stream) == 10
try:
    next(stream)
except ValueError as exc:
    assert "第2行" in str(exc)
    assert isinstance(exc.__cause__, ValueError)
else:
    raise AssertionError("消费坏行时应失败")
```

第一次 `next` 读到 `'10'`，成功交出 `10`。第二次 `next` 读到 `'bad'`，这时才报错。因此要把 `try` 放在实际读取的位置，比如 `next`、`for` 或 `list` 外面。

`raise ... from exc` 在这里做两件事。新错误告诉调用者“第 2 行不是整数”，`__cause__` 还保留了原来 `int(...)` 抛出的错误。

如果调用者只取到 `10` 就停，生成器还暂停在第一个 `yield`。下一节看怎样结束这次读取。

### 2.5 提前停止也是正常需求

前面用 `list` 把生成器读完了；实际任务可能只需要第一条。先只改一件事：让 `for` 在第一项后 `break`，并保留生成器变量以便观察。

```python
# study-example: S05J
events = []
def stream_values():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")

stream = stream_values()
for value in stream:
    assert value == 1
    break
assert events == []      # 循环结束了，生成器却还停在第一个yield
stream.close()
assert events == ["closed"]
assert list(stream) == []
```

`break` 只退出 `for` 循环，不会替调用者关闭生成器。生成器还停在第一个 `yield`，`finally` 没有执行；调用 `stream.close()` 时，暂停中的生成器才执行 `finally`，记下 `closed`。

不要把“对象以后会被回收”当成清理方案。CPython 下生成器失去最后一个引用时，通常也会立即回收并触发 `close()`；但这是实现行为，不是语言保证，也不该是代码的清理约定。要关闭就明确写 `close()`，或者用 `with` 安排关闭。

把 `close()` 写在循环后面，循环体报错时可能执行不到。下面让 `with` 安排关闭。

#### 案例推进：提前退出要有明确的关闭动作

```python
# study-example: S05C
from contextlib import closing
events = []
def stream_values():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")

with closing(stream_values()) as stream:
    assert next(stream) == 1
assert events == ["closed"]
```

`closing(stream_values())` 把生成器交给 `with` 管理。块内的 `next(stream)` 取到 `1`，离开块时 `closing` 调用 `stream.close()`，随后生成器的 `finally` 记录 `closed`。因此，调用 `close()` 的是 `closing`，而生成器自己执行清理代码。

**第二遍再看。** 如果从未调用 `next`，生成器还没有进入 `try`。这时调用 `close()` 不会先跑函数体，也就不会执行那个尚未进入的 `finally`。在生成器外打开的文件，可以用外层 `with` 直接管理。

到这里，第一遍已经能处理一个来源的正常读完、坏行失败、提前停止。现在可以直接运行 4.1 的整条读取链，确认自己能解释三个场景；多个资源的管理放到第二遍。

### 2.6 资源数量运行时才知道：ExitStack

**第二遍任务。** 前面一次管理一个来源。如果任务确实要同时打开多份文件来比较内容，文件清单又来自输入，嵌套 `with` 就写不出来。本节先用 `@contextmanager` 把“进入—交出资源—退出”写成一个生成器函数，再用 `ExitStack` 登记数量不定的资源。

#### 先用一个 yield 写出自己的管理器

回想 2.4，生成器执行到 `yield` 会交出一个值，然后停住。`@contextmanager` 把生成器函数包装成一个创建管理器的函数。下面把创建与进入写在不同的行，观察 `open:A` 到底是哪一步出现的。

```python
# study-example: S05K
from contextlib import contextmanager

events = []
@contextmanager
def one_source(name):
    events.append("open:" + name)
    try:
        yield name
    finally:
        events.append("close:" + name)

manager = one_source("A")
assert events == []

with manager as source_name:
    assert source_name == "A"
    assert events == ["open:A"]
    events.append("work:" + source_name)
assert events == ["open:A", "work:A", "close:A"]
assert source_name == "A"

# 再跑一次，这次在 with 块里故意报错。
events.clear()
problem = ValueError("内容无效")
try:
    with one_source("B"):
        raise problem
except ValueError as exc:
    assert exc is problem
    assert events == ["open:B", "close:B"]
else:
    raise AssertionError("错误应传到 with 外面")
```

#### `as source_name` 在哪一步绑定

把上面两行合写成 `with one_source("A") as source_name:`，顺序依然相同。

| 步骤 | 发生什么 | `events` |
| --- | --- | --- |
| 1. 创建管理器 | `one_source("A")` 得到管理器。在 CPython 3.12 中，它此时已持有生成器对象，生成器函数体尚未执行 | `[]` |
| 2. 调用进入方法 | 管理器用 `next(gen)` 推进生成器。生成器先记录打开事件，再执行 `yield name`，交出 `"A"` 并暂停。进入方法返回这个值 | `["open:A"]` |
| 3. 绑定目标 | Python 将进入方法返回的对象绑定给外围名称 `source_name` | `["open:A"]` |
| 4. 执行缩进块 | 生成器保持暂停。第一条 `assert` 已能读取 `source_name`，随后追加工作事件 | `["open:A", "work:A"]` |
| 5. 正常退出 | 管理器再次调用 `next(gen)`，生成器恢复并执行 `finally`。管理器把这次迭代耗尽视为正常结束 | `["open:A", "work:A", "close:A"]` |

值沿着四个环节传递。

```text
生成器参数 name 引用 "A"
    → yield name 把这个对象交给 next(gen) 的调用者
    → __enter__() 返回 next(gen) 得到的对象
    → with 在执行缩进块前把这个对象绑定给 source_name
```

`name` 是生成器内的参数名，`source_name` 是外部的名称。它们起初引用同一个字符串对象。试着在块内最后一行追加 `source_name = "改名"`，再把块外的名称断言改为 `assert source_name == "改名"`。事件列表的断言仍能通过。外部名称引用了新字符串，生成器中的 `name` 仍引用 `"A"`，所以最后仍记录 `close:A`。

手写类在 `__enter__()` 中可以直接 `return "A"`，外层 `as` 的绑定规则完全相同。`@contextmanager` 将进入方法和退出方法配好，让生成器负责准备、交出资源和收尾。手写类的完整例子见 [第 6 章 E11](06-类、数据模型与协议.md#36-综合验证with-协议)。生成器的包装与推进可对照 [Python 3.12 的 `contextmanager` 文档](https://docs.python.org/3.12/library/contextlib.html#contextlib.contextmanager)和 [CPython 3.12 的实现](https://github.com/python/cpython/blob/3.12/Lib/contextlib.py)。

#### 用 finally 确保清理

再看 S05K 的 B 路径。虽然省略了 `as`，进入方法仍推进到 `yield`，块内才抛出 `problem`。此时生成器依然暂停在 `yield`。退出方法收到异常，用 `gen.throw(problem)` 恢复生成器，让同一个异常从暂停点抛出。执行转入 `finally`，记录 `close:B`。清理顺利完成后，异常继续传给外层 `except`，`exc is problem` 核对了异常对象的身份。

如果把清理写成 `yield` 后的一条普通语句，异常会直接跳过这条语句。下面是这种写法的失败示意。

```text
@contextmanager
def bad():
    events.append("open")
    yield
    events.append("close")    # 块内异常时不会执行
```

把 `yield` 放进 `try`，把清理放进 `finally`，可以让正常离开和异常离开都进入清理路径。清理本身若抛出新异常，仍需按 3.3 的规则分析最终传播的错误。

如果生成器捕获了块内异常并正常结束，`@contextmanager` 会告诉 `with` 这个异常已处理。如果捕获只是为了记日志，记完后用裸 `raise` 继续传播原异常。可在练习副本中分别保留和移除 `raise`，观察外层 `except` 是否被执行。

#### 恰好 yield 一次

进入时，管理器推进生成器，直到它交出一个值。退出时，管理器再次推进它，这次生成器应当结束。进入时没有交出值，或者退出时又交出一个值，都会触发 `RuntimeError`。每次 `with` 都重新调用 `one_source(...)`，取得一个新的管理器实例。

#### ExitStack：先登记，退出时倒序结算

先预测哪几份能登记退出动作，以及外层 `except` 接到错误时哪些清理已经做完。

```python
# study-example: S05E
from contextlib import ExitStack, contextmanager

events = []
@contextmanager
def source(name):
    if name == "bad":
        raise OSError("无法打开")
    events.append(("open", name))
    try:
        yield name
    finally:
        events.append(("close", name))

try:
    with ExitStack() as stack:
        for name in ["A", "B", "bad"]:
            stack.enter_context(source(name))
except OSError as exc:
    assert str(exc) == "无法打开"
    assert events == [("open", "A"), ("open", "B"), ("close", "B"), ("close", "A")]
else:
    raise AssertionError("第三份来源应当打开失败")
```

`enter_context(cm)` 做两件事：先调用 `cm.__enter__()`，成功后再把它的 `__exit__` 登记到退出表；返回值就是 `__enter__` 的结果，也就是 `as` 本该拿到的值。离开外层 `with` 时，`ExitStack` 按登记的反序执行这些退出动作，所以后打开的先关闭。

| 执行到哪里 | 已登记 | 本例发生什么 |
| --- | --- | --- |
| 第一次 `enter_context` | A | 记录 `open A`，A 停在 `yield` |
| 第二次 `enter_context` | A、B | 记录 `open B` |
| 尝试进入 `bad` | A、B | `bad` 在 `yield` 前抛 `OSError`，没有进入成功，也没有登记 |
| 离开外层 `with` | 依次取出 B、A | 记录 `close B`、`close A`，外层 `except` 才收到 `OSError` |

关键点：`bad` 在 `yield` 之前失败，`enter_context` 直接抛出，`bad` 没有登记；已经登记的 A、B 仍在异常传播时倒序清理。这正是 `ExitStack` 相对手写嵌套 `with` 的价值。

但 `ExitStack` 只负责已经成功进入的资源。如果 `bad` 在失败前已经拿到了文件或连接，它要自己清理那半份资源，`ExitStack` 帮不了它。

#### 什么时候不该用 ExitStack

如果资源可以逐份独立处理，直接在循环里逐份 `with` 更好：

```text
for name in names:
    with source(name) as current:
        process(current)
```

每次只占一份资源，同时打开的文件描述符更少。`ExitStack` 适合“确实需要同时持有多个资源”的场景，比如要同时打开 A、B 才能比较内容。第 11 章再把退出时清理的做法用到异步流。

### 2.7 把本章的工具放回一张表

协议约定了 Python 怎样使用一个对象。下表把 `for` 的逐项取值与 `with` 的进入和退出放在一起看。

| 要做什么 | Python 调用的方法 | 用函数提供这项能力 |
| --- | --- | --- |
| 让 `for` 逐项取值 | 先用 `__iter__()` 取得迭代器，再用 `__next__()` 取下一项 | 调用带 `yield` 的生成器函数，得到可直接遍历的生成器对象 |
| 让 `with` 管理进入和退出 | `__enter__()` 和 `__exit__()` | 用 `@contextmanager` 装饰生成器函数，调用后得到上下文管理器 |

`@contextmanager` 创建的管理器在进入时把生成器推进到 `yield`，在退出时恢复它。运行时需要同时持有数量不定的资源时，可以用 `ExitStack` 统一调用各管理器的退出方法。第 6 章会用类实现这两套协议。

## 3. 原理讲解与推导

### 3.1 用状态解释迭代

用 `inspect.getgeneratorstate()` 可以查看生成器的状态。下表用 4.1 的逐行读取说明各个状态何时出现。

| 状态 | 在逐行读取时什么时候出现 |
| --- | --- |
| `GEN_CREATED` | 调用 `amounts(source)` 后，尚未开始读行 |
| `GEN_RUNNING` | 生成器正在读行并转换金额 |
| `GEN_SUSPENDED` | `yield` 交出一笔金额后，等待下一次取值 |
| `GEN_CLOSED` | 读完、遇到未处理的异常，或成功调用 `close()` 后 |

#### 生成器怎样恢复和关闭

| 方法 | 对暂停中的生成器做什么 |
| --- | --- |
| `next(gen)` | 恢复执行，取出下一个值 |
| `gen.send(value)` | 恢复执行，让暂停处的 `yield` 表达式得到 `value` |
| `gen.throw(exc)` | 恢复执行，并在暂停的 `yield` 处抛出异常 |
| `gen.close()` | 在暂停处抛出 `GeneratorExit`，让生成器退出并执行经过的 `finally` |

普通取值可以用 `next(gen)` 或 `gen.send(None)` 启动。对还没启动的生成器 `send` 非 `None` 的值会报 `TypeError`。

手写迭代器的 `__next__()` 用 `StopIteration` 通知调用方已经读完。生成器函数用 `return` 或自然走到末尾来结束。若让 `StopIteration` 从生成器函数体中逃出，Python 会把它转成 `RuntimeError`（PEP 479）。

#### 暂停不等于调用已经结束

生成器停下时，仍记得执行到哪、有哪些局部变量。比如函数体先读入一个大列表再逐项 `yield`，暂停时还会保留这个列表。要减少内存占用，也要看数据是不是一开始就全读进来了。

#### 第二遍：yield from先理解成逐项转交

若只是想把另一份可迭代数据中的每一项依次交出去，先写普通for与yield，再比较简写：

```python
# study-example: S05L
def combined_by_loop():
    for value in [1, 2]:
        yield value
    yield 3

def combined():
    yield from [1, 2]
    yield 3

assert list(combined_by_loop()) == [1, 2, 3]
assert list(combined()) == [1, 2, 3]
```

这两个版本在本例中的产出相同。yield from还支持对子生成器的结束值、异常和关闭等委托，不能由这个简单列表例子推断全部等价规则；第一次只需会读“依次转交这些元素”。E10再观察生成器的return值与yield产出的区别。

### 3.2 用所有权解释清理

代码把文件交给函数之前，先决定谁来关闭。4.1 由外层 `with` 打开管理范围并关闭 `StringIO`，`amounts` 只从里面读行。这里的**资源所有权**就是这条关闭责任。

若管理器准备资源时已经拿到了文件，但下一步出错导致没能进入 `with`，准备代码负责关掉自己已拿到的文件。2.6 的 `bad` 模拟的就是进入失败，已经进入的其他资源仍会按顺序清理。

退出管理器还能决定是否让错误继续传出去。第 6 章的 E11 会用 `__exit__` 返回 `False` 演示“清理完成，错误继续向外抛出”。

### 3.3 退出代码仍会影响结果

前面用finally追加事件或关闭来源。现在只改变退出代码：如果它也写return，调用方最终拿到哪个结果？

```python
# study-example: S05M
def wrong_result():
    try:
        return "业务结果"
    finally:
        return "清理结果"  # 故意演示：覆盖原本准备返回的结果

assert wrong_result() == "清理结果"

events = []
def keep_result():
    try:
        return "业务结果"
    finally:
        events.append("清理完成")

assert keep_result() == "业务结果"
assert events == ["清理完成"]
```

try准备返回一个值时，先执行finally；如果finally又返回另一个值，调用者最终拿到的是后一个。若原先正在向外报告错误，finally里的return还可能让调用者收不到这个错误，这就叫“吞掉异常”。因此清理代码通常只做关闭等动作，让原结果或原错误继续；清理自己也失败时，还要保留原始故障信息供排查。

#### 第二遍：增量赋值为什么可能先改变对象，再失败

先只看内置列表：`x = x + y`创建新列表，再让x指向它；`x += y`先扩展原列表，再把结果赋回x。因此其他变量是否看见变化，要看它们是否还指向被修改的那个列表。第二遍再扩展到自定义对象：`__iadd__`可以定义原地加法；若不支持，则按相应普通运算规则处理。所以`+=`并不对所有类型都保证原地修改。

```python
# study-example: S05Z
left = [1]
alias = left
left = left + [2]
assert alias == [1] and left == [1, 2]
left = [1]
alias = left
left += [2]
assert left is alias and alias == [1, 2]
box = ([],)
try:
    box[0] += [3]
except TypeError:
    pass
else:
    raise AssertionError("tuple slot should reject assignment")
assert box == ([3],)
```

最后一例要分四步看：从tuple的第0项取出列表；列表已经追加内容；Python尝试把结果写回tuple的第0项；因为tuple不允许替换这一项，写回时报错。前面的列表修改已经发生，报错不会自动撤销它。tuple固定的是自己各项指向哪个对象，并不会把这些对象内部也一并冻结。E02继续检查这种“已经修改，随后失败”的情况。

#### 把本章连成一条读取链

一行文本表示一个以分为单位的金额。`amounts(source)` 负责读行和转换，转换失败时加上行号。下面先看 `with` 那一行，它写了两个管理器，等价于把 `closing(...)` 的 `with` 嵌在 `source` 的 `with` 里面。

1. 进入时，先拿到文本来源，再创建生成器 `stream`。
2. 缩进块里，用 `next(stream)` 读一行，或用 `list(stream)` 读完。
3. 离开时，内层 `closing` 先关闭生成器，外层 `with` 再关闭文本来源。

带着这个顺序，分别运行正常读完、只读一行、第二行报错的三段代码。

```python
# study-example: S05P
from contextlib import closing
from inspect import getgeneratorstate
from io import StringIO

def amounts(lines):
    for number, text in enumerate(lines, 1):
        try:
            value = int(text.strip())
        except ValueError as error:
            raise ValueError(f"第{number}行不是整数") from error
        yield value

# 正常消费：读取两行，两个with按里到外退出。
normal = StringIO("10\n20\n")
with normal as source, closing(amounts(source)) as stream:
    assert list(stream) == [10, 20]
assert normal.closed

# 提前停止：第二行尚未读取，退出时仍关闭生成器和来源。
early = StringIO("10\n20\n")
with early as source, closing(amounts(source)) as stream:
    assert next(stream) == 10
assert getgeneratorstate(stream) == "GEN_CLOSED"
assert early.closed

# 第二行损坏：错误从消费处传播；离开with后来源仍已关闭。
broken = StringIO("10\nbad\n")
try:
    with broken as source, closing(amounts(source)) as stream:
        assert next(stream) == 10
        next(stream)
except ValueError as error:
    assert "第2行" in str(error)
    assert isinstance(error.__cause__, ValueError)
else:
    raise AssertionError("损坏行应当报错")
assert broken.closed
```

| 情况 | 块内发生什么 | 离开时看什么 |
| --- | --- | --- |
| 正常读完 | `list(stream)` 取到 `10`、`20` | `normal.closed` 为 `True` |
| 提前停止 | 一次 `next` 取到 `10`，第二行还没读 | 生成器已结束（`GEN_CLOSED`），来源也已关闭（`early.closed`） |
| 第二行损坏 | 第一次 `next` 成功，第二次抛出带行号的 `ValueError` | 外层捕获错误，`broken.closed` 为 `True` |

`getgeneratorstate(stream)` 用来观察生成器是否已经结束，`early.closed` 用来检查文本来源。两条断言各检查一个对象。

#### 验证实验 E09：装饰器退出路径

第四章先实现成功路径的包装；现在用E09观察`finally`如何保证退出事件，异常怎样继续传播。

这里比普通装饰器多一层配置：`decorate("outer")`先返回apply；apply接收原函数，再返回wrapped。两个装饰器表达式先从上到下求值，所以先记录build:outer、再build:inner；应用到函数时先内层、后外层。实际调用add时，才执行两层wrapped。先分清“准备配置、应用包装、调用包装”三个动作，再预测events；不要把这段当作第一次学习装饰器的入口。

```python
# experiment: E09
from functools import wraps
events = []
def decorate(label):
    events.append("build:" + label)
    def apply(fn):
        @wraps(fn)
        def wrapped(*args, **kwargs):
            events.append("enter:" + label)
            try:
                return fn(*args, **kwargs)
            finally:
                events.append("exit:" + label)
        return wrapped
    return apply
@decorate("outer")
@decorate("inner")
def add(a, b):
    """加法示例。"""
    return a + b
assert events == ["build:outer", "build:inner"]
assert add(1, 2) == 3
assert events[2:] == ["enter:outer", "enter:inner", "exit:inner", "exit:outer"]
assert add.__name__ == "add" and add.__wrapped__.__name__ == "add"
events.clear()
try:
    add(1, "bad")
except TypeError:
    pass
else:
    raise AssertionError("包装器不能吞掉原函数的计算错误")
assert events == ["enter:outer", "enter:inner", "exit:inner", "exit:outer"]
```

成功时保留结果3；失败时仍抛出TypeError。两个场景都按先内后外的顺序完成退出记录，finally没有把错误改成一个看起来成功的返回值。

### 6.1 先预测，再查看参考推导

调用 `parse_numbers(...)` 时没报错，为什么第二次 `next` 还会失败？进入 `with` 后，如果在里面执行 `return`，文件会在哪一步关闭？

`parse_numbers(...)` 先创建生成器，第二次 `next` 才把函数体推进到坏行。块内 `return` 会先离开 `with`，因此对于成功进入的文件管理器，退出处理先关文件，调用者随后才拿到返回值。

## 7. 面试问答与迁移

`for`的`break`会自动`close`吗？`finally`里`return`有何风险？异常链为何有助于调试？`yield`暂停时保留了什么？

**参考回答：**

1. break只退出当前for循环，不保证调用迭代器的close。有时生成器刚好随后被回收，清理也跟着发生，但原因不是break。保留一个变量继续引用它，再观察就能区分。应由负责管理该资源的代码，用with、finally或适用的closing明确安排关闭。
2. 离开try时先执行finally。若finally又写return，它会替换原来准备返回的值，甚至让调用者收不到原来的异常。清理代码通常只完成关闭等动作，让原结果或错误继续；若清理本身出错，也要考虑怎样保留最初的故障信息。
3. 在`raise DomainError(...) from exc`这种写法中，外层接到的是业务错误，而`__cause__`仍指向原始错误。例如“报告生成失败”可以关联到“第3行无法转成整数”，便于定位。`from None`主要隐藏默认展示中的自动异常上下文，不等于删除所有底层信息；这里的DomainError仅代表你定义的业务异常类型。
4. yield会保留继续执行所需的位置和局部变量；这些变量可能仍指向大列表、文件或连接。所以“一次只产生一项”不保证总内存一定小，提前停止也不表示资源已关闭。要分别检查保存了什么数据，以及关闭代码何时执行。

**换条件自测：** 保留生成器变量，取一项就break，再观察finally是否已经运行；显式close后再次观察。接着让 `__enter__` 自身失败，解释为什么不能指望尚未成功进入的with调用 `__exit__` 清理一切。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 数据一次取不完、还可能中途失败时，执行停在哪，谁负责清理？

**一条主线：**

```text
正常：逐行取值 → 读完 → 关闭来源
提前停止：只取需要的行 → 关闭生成器 → 关闭来源
失败：取到坏行 → 退出并关闭来源 → 外层收到带行号的错误
```

**三个关键词：** 迭代状态就是这次读到哪里；异常路径就是出错后执行转到哪里；资源所有权就是约定由谁负责关闭。遇到复杂代码时，先分别回答这三个具体问题。

**协议对照：** 2.7 汇总了 `for` 怎样逐项取值、`with` 怎样安排进入和退出。

**最容易错：**

- 为了查看内容而 `list(iterator)`，先把迭代器耗尽；
- 用宽泛 `except` 返回空列表，掩盖文件损坏；
- `break` 后不关闭生成器，指望对象立即回收；
- 以为什么都不做，已发生的修改会随异常自动回滚。

**与前后章：** 第4章留下函数调用与 `return` 这一正常出口，本章补上失败、暂停和提前停止。第6章要把一份任务状态与规则收进实例，需要先有明确的清理责任和迭代契约。

**学完应能：**

- 写一个惰性逐行读取、坏行报错并保留行号的生成器；
- 用 `with` 让正常、异常、提前 `break` 三条路径都关闭来源；
- 说明可迭代对象与迭代器的区别，验证两个独立消费位置并观察创建、推进和关闭时刻；
- 用 `ExitStack` 按逆序退出运行时才确定数量的资源。

### 8.2 日常工作注意事项

- 记录日志时为了查看内容而`list(iterator)`，可能先把迭代器耗尽；确认后续还需不需要消费，必要时有界保存结果。
- 不要用宽泛`except`返回空列表掩盖文件损坏或外部失败；只处理能解释的错误，保留异常链与调用现场。
- 文件和连接使用明确的关闭边界。提前`break`、异常或取消都要验证清理，不依赖对象恰好立即回收。
