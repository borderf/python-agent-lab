## 2. 基础知识讲解

普通函数的`return`只是正常结束。本章还要区分另外几种退出：

| 行为 | 含义 |
| --- | --- |
| `return` | 正常结束函数，把结果交回调用者 |
| 异常传播 | 沿调用关系向上展开退出，直到被某层捕获 |
| `yield` | 暂停执行，保留继续执行所需的状态 |
| `break` | 退出当前循环，不自动关闭所有迭代器或资源 |

每条出口都必须说明“已经做了什么、还没做什么、谁负责收尾”。

### 2.1 异常是另一条执行路径

把每一行文本转成整数，可能在第十行才失败。调用方既需要知道处理到哪里，也需要保证已打开的资源会关闭。只有正常返回无法表达这些路径，所以先认识异常怎样转移执行。

#### 第一步：先只认识失败怎样打断正常步骤

`int("12")`能返回整数12；`int("金额未知")`则没有合法的整数结果。它会**抛出ValueError异常**：可以先把异常理解为“携带失败原因、使执行转向错误处理的一种通知”。它不是返回None，也不会自动跳过这一行继续转换下一行。

下面故意失败，只用于观察；不和正常示例拼成一个文件：

```text
number = int("金额未知")  # 这里抛出ValueError
print("转换完成")        # 没有处理该异常时，不会执行到这一行
```

#### 第二步：用try/except接住一种已知错误

```python
# study-example: S05F
events = []
try:
    number = int("金额未知")
    events.append("转换完成")
except ValueError:
    events.append("金额格式错误")
events.append("本次处理结束")

assert events == ["金额格式错误", "本次处理结束"]
```

try缩进块是我们要观察的执行范围。转换抛出ValueError后，Python寻找能处理该类型的except，从它的第一行开始执行；不会回到失败的int或后面的“转换完成”。处理结束后，本例才继续到try/except整体之后。

**先预测：** 只把输入换成`"12"`，events是什么？应为`["转换完成", "本次处理结束"]`，except不会运行。若失败类型与ValueError不匹配，当前except接不住，异常继续交给调用者；不是所有错误都被try自动处理。

#### 第三步：再加成功后续与退出收尾

如果希望“只在try没有异常时做一件事”，用else；希望“离开这段try时，无论成功还是失败都做一件事”，用finally。先看事件记录，下一节再用它关闭来源：

#### 案例推进：先用一次转换失败认识退出路径

```python
# study-example: S05W
events = []
try:
    number = int("bad")
except ValueError:
    events.append("invalid")
else:
    events.append("valid")
finally:
    events.append("finished")
assert events == ["invalid", "finished"]
```

把输入改成`"12"`，应得到`valid`与`finished`，`number`等于12。错误发生后不会回到`try`中失败语句的下一行继续；本例由`except`接手，最后执行`finally`。

按时刻看同一段程序：

| 转换输入 | try 中发生什么 | 接下来执行 | 最终 events |
| --- | --- | --- | --- |
| `"12"` | 得到整数12 | else，再 finally | `valid`、`finished` |
| `"bad"` | `int` 抛 ValueError，后面的正常步骤中断 | 匹配的 except，再 finally | `invalid`、`finished` |

else只在try正常走到末尾时进入；finally安排离开这段代码时的动作。未匹配的异常仍会经过finally，再继续向外传播。finally不表示“已经处理成功”，也不自动撤销前面的修改；先记住它改变的是退出时执行哪些代码，3.3再用反例观察结果覆盖。

#### 第四步：什么时候由自己的函数主动raise

`int("-3")`转换成功，但我们的订单数量不允许负数。转换工具不知道这条业务规则，所以由函数在检查后主动报告：

```python
# study-example: S05G
def parse_count(text):
    count = int(text)
    if count < 0:
        raise ValueError("数量不能为负数")
    return count

assert parse_count("3") == 3
try:
    parse_count("-3")
except ValueError as error:
    assert str(error) == "数量不能为负数"
else:
    raise AssertionError("负数应当被拒绝")
```

`raise ValueError(...)`创建并抛出一个带说明的异常；这一分支不会执行到return。`except ValueError as error`里的error则是接住的异常对象，`str(error)`取得它的说明。parse_count没有在内部假装算出合法数量，选择把错误交给调用者决定怎样提示用户。

到这里先掌握三种情况：转换成功时return；格式错误时int抛异常；违反业务规则时自己的代码raise。到2.4需要补行号时，再学怎样保留原始原因。自定义异常类放到第6章，异常组放到第11章，不需要现在一次学完。

**异常只回答“哪里失败”，不自动回答“已经打开的资源怎么办”。** 接下来把清理责任写进控制流。

### 2.2 用 with 把清理写进退出路径

刚才finally只是在列表里记一条事件。现在把退出动作换成“关闭一个已经打开的来源”。文件或连接即使没有Python名称再使用，也应该在约定时刻关闭；这个责任不应交给“以后也许发生的垃圾回收”。本节先用内存文本模拟来源，第7章再打开真实磁盘文件。

#### 先认识来源对象，再使用with

`StringIO("10\n")`提供一个可以读取的内存文本对象，`\n`表示换行；`readline()`取一行，`read()`取剩余内容，`close()`关闭，`closed`说明是否已经关闭。名称属于当前代码，资源却有自己的打开/关闭状态。

#### 案例推进：把清理写进 with 的退出路径

```python
# study-example: S05X
import io

stream = io.StringIO("orders")
with stream as managed:
    assert managed is stream
    assert managed.read() == "orders"
assert stream.closed
```

`with stream as managed:`可以分成三步读：先进入stream提供的管理范围，把进入得到的对象命名为managed；执行缩进块；离开缩进块时做退出处理。本例进入得到的就是stream本身，不是复制一份文本对象。它的退出处理会关闭来源，所以块外看到closed为真。这类提供进入/退出约定的对象叫**上下文管理器**。

先对照熟悉的 `try/finally`。两种写法都让这个已创建来源在退出时关闭；第二种把“进入/退出”的约定交给来源对象：

```python
# study-example: S05Y
from io import StringIO

first = StringIO("10\n")
try:
    assert first.readline().strip() == "10"
finally:
    first.close()
assert first.closed

second = StringIO("10\n")
with second as source:
    assert source.readline().strip() == "10"
assert second.closed
```

两种写法都使用已经学过的finally思路。with把进入、退出的约定交给对象，调用者不需要每次手写close；这不表示所有对象都能随便放在with后面，普通列表就不提供这样的管理约定。

#### 改一个条件：块内失败，退出动作还会执行吗

```python
# study-example: S05H
from io import StringIO

source = StringIO("bad\n")
try:
    with source as lines:
        value = int(lines.readline())
except ValueError:
    assert source.closed
else:
    raise AssertionError("坏文本应当报错")
assert source.closed
```

执行顺序是：进入with → 读取bad → 转换失败 → 离开with并关闭来源 → 外面的except接住ValueError。**关闭资源和处理业务错误是两件事**：StringIO帮我们关闭了来源，没有把坏文本变成合法整数。若把except写在with里面，捕获时可能还没离开管理范围；观察closed之前，要先看自己站在边界的哪一侧。

自定义管理器怎样进入、是否会吞异常，由相应协议决定；第6章再实现`__enter__/__exit__`。本章先使用已知会关闭来源的标准库对象，第二遍在3.2补充进入失败的情况。

**清理解决“资源何时关闭”，但一批订单仍不能一次读入内存。** 下一步让数据逐项到来。

### 2.3 一次性消费：iterable 与 iterator

来源现在能按时关闭，但我们还需要控制一次处理多少数据。先从熟悉的列表理解“取下一项”，再换成文件。列表保存元素；**可迭代对象**表示可以向它请求逐项读取的过程；**迭代器**则是这一次读取过程中的对象，记着读到哪里。

先把列表想成可以重复打开的订单清单，把迭代器想成本次阅读的位置：从同一清单各自取得两个迭代器，两个位置可以独立前进；同一个迭代器则延续已有位置。它是帮助想象的模型，实际能否重复读取还取决于数据来源。

```python
# study-example: S05D
values = iter([10, 20])
assert iter(values) is values
assert next(values) == 10
assert next(values) == 20
assert next(values, "END") == "END"
assert list(values) == []
```

按顺序读S05D：`iter([10, 20])`取得一次读取的位置；第一次next拿10并向前移动，第二次拿20，再次取时已经没有元素。`next(values, "END")`中的END只是“已经读完”的返回标记，不是列表里的第三个元素。最后list要收集剩余项，因为位置已在末尾，所以得到空列表。

同一个列表能不能有两份读取位置？可以，关键是重新调用iter，而不是给同一个迭代器多起一个名称：

```python
# study-example: S05I
rows = [10, 20]
left = iter(rows)
right = iter(rows)
assert next(left) == 10
assert next(left) == 20
assert next(right) == 10

alias = right
assert next(alias) == 20
assert next(right, "END") == "END"
assert rows == [10, 20]  # 移动读取位置，没有从列表中删除元素
```

left和right是两次取得的迭代器；alias和right却是同一个迭代器。这里再次用到第1章的“名称可以共享对象”，只不过现在共享的是读取位置。

没有提供默认值时，结束由StopIteration异常表达；for会把这种结束信号当作正常读完，而ValueError之类的数据错误仍会向外传播。for大致做的是：iter取得迭代器 → next取一项 → 执行循环体 → 再取下一项。它不承诺替任意迭代器关闭资源。

对迭代器再次iter会得到它自己，并不会“倒回开头”。因此接口只说接受可迭代数据，不代表它一定支持len，也不代表能读两遍。要重复使用，需选择可重读的来源或明确保存结果；保存为列表也有内存代价。

### 2.4 生成器：让函数在 yield 处暂停

前面的迭代器由列表提供。若想自己写“每次产生一个值”的过程，可以使用**生成器函数**：在普通函数里写yield。对本节这种同步函数，调用时得到生成器对象，它也是迭代器；第一次next才开始执行函数体。

先把yield理解成“交出这一项，并停在这里等下一次”。它与return的关键区别是：return交出结果后结束；yield交出一项后还可以继续。接着只改变动作的先后，观察下面的事件：

```python
# study-example: S05A
events = []
def values():
    events.append("start")
    yield 10
    events.append("resume")
    yield 20

stream = values()
assert events == []
assert next(stream) == 10 and events == ["start"]
assert list(stream) == [20] and events == ["start", "resume"]
assert list(stream) == []
```

调用生成器函数先获得生成器对象，第一次推进才进入函数体。`yield`返回一项并暂停，局部执行状态保留，下一次从暂停点继续。`list`会消费到结束，消费完再`list`不是重新执行；这解释了为什么“接受任意Iterable”的函数不能未经说明遍历两次。

把S05A按时间展开：

| 动作 | 函数体进度 | 得到什么 | events |
| --- | --- | --- | --- |
| `stream = values()` | 尚未进入函数体 | 一个生成器对象 | `[]` |
| `next(stream)` | 执行到第一个yield并暂停 | `10` | `["start"]` |
| `list(stream)` | 从暂停处继续，到结束 | 剩余的 `[20]` | `["start", "resume"]` |
| 再次 `list(stream)` | 已经结束，不自动重来 | `[]` | 不变 |

想再执行一次，需要调用 `values()` 创建新生成器；如果生成器依赖的外部文件已关闭或不能重读，还要另行准备来源。生成器不保证天然低内存：它可能仍引用一个很大的列表，后面也可能把所有结果收集起来。

#### 案例推进：错误可能发生在创建之后

惰性意味着错误也可能推迟到消费时出现。文件已经打开多久、某行已经解析没有，都需要沿消费过程观察。

```python
# study-example: S05B
def parse_numbers(lines):
    for line_number, text in enumerate(lines, start=1):
        try:
            value = int(text)
        except ValueError as exc:
            raise ValueError(f"第{line_number}行不是整数") from exc
        yield value

stream = parse_numbers(["10", "bad"])
assert next(stream) == 10
try:
    next(stream)
except ValueError as exc:
    assert "第2行" in str(exc)
    assert isinstance(exc.__cause__, ValueError)
else:
    raise AssertionError("消费坏行时应失败")
```

这里新增的只有“保留原始错误”：`except ValueError as exc`接住int产生的错误；`raise ValueError(f"第{line_number}行不是整数") from exc`抛出更有位置含义的错误，同时用from把它和原错误关联起来。调用者通过说明知道第几行坏了，调试时还可以从`__cause__`追到原转换错误。本例没有忽略坏行，而是报告后终止这次生成。

把这次失败放回时间线：`parse_numbers(...)`只创建生成器；第一次`next`才读取第一行并产生10；第二次`next`读到坏的第二行，异常从这次推进向调用方传播。要捕获这个错误，`try`必须覆盖消费动作；只在创建生成器时加`try`无法处理随后发生的转换错误。

**生成器能暂停，但调用方可能永远不消费到结束。** 下一节处理提前停止。

### 2.5 提前停止也是正常需求

前面用list把生成器读完了；实际任务可能只需要第一条。先只改一件事：让for在第一项后break，并保留生成器变量以便观察。

```python
# study-example: S05J
events = []
def stream_values():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")

stream = stream_values()
for value in stream:
    assert value == 1
    break
assert events == []      # 循环结束了，生成器却还停在第一个yield
stream.close()
assert events == ["closed"]
assert list(stream) == []
```

break退出的是调用方的for循环，没有要求stream继续执行，也没有要求它关闭。此时stream还暂停着，finally尚未经过。显式close通知本例生成器结束，于是清理代码执行；它不会再把第二项交给调用者。

如果把close写在循环后面，循环体抛异常就可能走不到它。需要一个无论怎样离开都执行close的边界，这正是前面with的用处。

#### 案例推进：提前退出要有明确的关闭动作

```python
# study-example: S05C
from contextlib import closing
events = []
def stream_values():
    try:
        yield 1
        yield 2
    finally:
        events.append("closed")

with closing(stream_values()) as stream:
    assert next(stream) == 1
assert events == ["closed"]
```

closing是标准库的适配工具：给一个有close方法的对象增加“离开with时调用close”的管理方式。`as stream`得到被包装的生成器本身。这里先next取了1，离开with时调用close，finally记录closed；不必先取出第二项。

注意三者的分工：生成器提供逐项产生数据的能力；close负责请求结束；with closing(...)负责在离开范围时调用close。不是在生成器里写了finally，调用方一break就能自动触发它。

本例先通过`next`进入了生成器的try块，然后才提前关闭。若生成器从未开始执行，直接close不会先运行函数体，也不能期待尚未进入的finally执行；因此不要在生成器外提前取得资源，却依赖一个从未启动的生成器负责关闭。由谁创建和拥有资源，就让谁在明确边界安排清理。

到这里，第一遍已经能处理一个来源的正常读完、坏行失败、提前停止。现在可以直接运行4.1的整条读取链，确认自己能解释三个场景；多个资源的管理放到第二遍。

### 2.6 资源数量运行时才知道：ExitStack

**第二遍任务。** 先学会为一个来源安排退出，再考虑“同时持有几份来源，而且数量来自输入”的情况。这里要增加两个工具，先分开学：contextmanager让我们写出自己的管理器，ExitStack再组合多个管理器。

#### 先用一个yield写出自己的管理器

第4章已经学过装饰器。contextmanager也是装饰器：它把下面这种“恰好yield一次”的生成器函数包装成可以用于with的上下文管理器。

```python
# study-example: S05K
from contextlib import contextmanager

events = []
@contextmanager
def one_source(name):
    events.append("open:" + name)
    try:
        yield name
    finally:
        events.append("close:" + name)

with one_source("A") as name:
    assert name == "A"
    assert events == ["open:A"]
    events.append("work:" + name)
assert events == ["open:A", "work:A", "close:A"]
```

| 谁在执行 | 发生什么 |
| --- | --- |
| 进入with | 管理器推进生成器，记录open:A，到yield暂停 |
| with缩进块 | yield交出的A绑定给name，执行work:A |
| 离开with | 管理器让生成器完成退出，finally记录close:A |

为什么写try/finally？若块内抛异常，管理器会把异常送回暂停的yield处；finally仍会执行。只把关闭写在yield后面的普通语句里，可能被异常跳过。这个教学例子只记录事件，不是真实打开文件；自定义类协议留到第6章。

#### 再让ExitStack登记多个退出动作

已知恰好两个资源时，可以写嵌套with。若资源名来自列表，数量运行时才知道，ExitStack就像一个退出登记表：每成功进入一个管理范围，就登记退出动作；离开外层with时倒序执行。第三份来源进入失败，前两份也不会被遗忘。

#### 案例推进：多个资源按逆序退出

```python
# study-example: S05E
from contextlib import ExitStack, contextmanager

events = []
@contextmanager
def source(name):
    if name == "bad":
        raise OSError("无法打开")
    events.append(("open", name))
    try:
        yield name
    finally:
        events.append(("close", name))

try:
    with ExitStack() as stack:
        for name in ["A", "B", "bad"]:
            stack.enter_context(source(name))
except OSError:
    pass
assert events == [("open", "A"), ("open", "B"), ("close", "B"), ("close", "A")]
```

将失败移到处理内容时，指出哪些文件已登记关闭。若所有来源可以逐份独立处理，直接在循环体内逐份使用`with`，这样同时占用的文件描述符更少。第11章再把“提前退出也要清理”迁移到异步流。

| 时刻 | 已成功进入的来源 | 发生的动作 |
| --- | --- | --- |
| 进入A后 | A | 注册A的退出动作 |
| 进入B后 | A、B | 再注册B的退出动作 |
| 进入bad失败 | A、B | bad没有成功进入；已登记的先B后A退出 |

这个例子中的source是用生成器制作的教学上下文管理器，不是真实打开了文件。真实资源若在进入过程中创建后又失败，建立它的代码还需处理自己的半初始化资源。

## 3. 原理讲解与推导

### 3.1 用状态解释迭代

生成器在未开始、执行、暂停、结束之间转换；保留状态是一次性消费的原因。对已结束对象再次取值，不会自动回到开头。独立工厂调用可以建立新过程，但原来的外部数据源是否仍可用也要考虑。

#### 暂停不等于调用已经结束

`yield`暂停时，生成器需保留继续执行所需的局部状态；被这些状态引用的对象也可能继续存活。它不同于第4章已经完成的`return`。`close`或消费结束会结束这条执行，但被其他地方引用的数据仍按可达性决定生命周期。把“暂停、结束、对象不再可达、资源关闭”分开画，E10/E12便是同一模型的两种实验。

#### 第二遍：yield from先理解成逐项转交

若只是想把另一份可迭代数据中的每一项依次交出去，先写普通for与yield，再比较简写：

```python
# study-example: S05L
def combined_by_loop():
    for value in [1, 2]:
        yield value
    yield 3

def combined():
    yield from [1, 2]
    yield 3

assert list(combined_by_loop()) == [1, 2, 3]
assert list(combined()) == [1, 2, 3]
```

这两个版本在本例中的产出相同。yield from还支持对子生成器的结束值、异常和关闭等委托，不能由这个简单列表例子推断全部等价规则；第一次只需会读“依次转交这些元素”。E10再观察生成器的return值与yield产出的区别。

### 3.2 用所有权解释清理

谁建立资源，谁就应明确把关闭责任留给自己还是交给调用方。异常、`return`、`break`和取消分别改变控制流；清理代码需要覆盖接口允许的所有退出方式，不能依赖某个解释器恰好立即回收对象。

“所有权”在这里指关闭责任，不是某种新变量类型。4.1中外层创建StringIO并用with关闭；amounts只借用它来读行，不能擅自假设自己拥有来源。若把打开文件移进生成器，关闭责任也要随之重新设计。

第二遍再记住协议边界：进入成功后，with调用退出处理；进入本身失败时，不会再调用这个尚未成功进入的管理器的退出方法，已取得的半初始化资源需由建立它的代码清理。某些管理器还能抑制块内异常（类协议中表现为`__exit__`返回真值），所以不能把“经过with”一概理解为“失败一定传播且所有资源一定关闭”。StringIO和本章的管理器已经给出了具体行为，第6章再实现协议。

### 3.3 退出代码仍会影响结果

前面用finally追加事件或关闭来源。现在只改变退出代码：如果它也写return，调用方最终拿到哪个结果？

```python
# study-example: S05M
def wrong_result():
    try:
        return "业务结果"
    finally:
        return "清理结果"  # 故意演示：覆盖原本准备返回的结果

assert wrong_result() == "清理结果"

events = []
def keep_result():
    try:
        return "业务结果"
    finally:
        events.append("清理完成")

assert keep_result() == "业务结果"
assert events == ["清理完成"]
```

执行try里的return时，要先经过finally；如果finally又return，最终采用后者。若try中原本在传播异常，finally的return也可能把它吞掉。因此清理通常完成动作即可，让原结果或异常继续；清理本身再抛异常时，也要检查原始原因是否仍可追踪。

#### 第二遍：异常说明和类型的补充

当前except只接它匹配的异常类型；多个分支应先具体后一般。自定义异常继承和Exception/BaseException的关系放到第6、11章逐步建立，不必在第一次接ValueError时背完。若只想追加上下文后原样抛出，可在except里用裸raise；若要转换成有业务说明的新错误，用2.4的raise ... from error。

`add_note`（3.11+）用于在原异常对象上补充说明，不改变异常类型。下面保留原转换失败，只补任务位置：

```python
# study-example: S05N
try:
    int("bad")
except ValueError as error:
    error.add_note("订单导入：当前正在转换第2行金额")
    assert error.__notes__ == ["订单导入：当前正在转换第2行金额"]
```

#### 可选回做：给递归入口加输入检查

第4章3.6的countdown_total约定输入是小的非负整数。现在可以在外层入口先用`type(n) is int`与`n >= 0`检查，非法时raise ValueError，再调用递归核心。分别检查0、3、-1、True和字符串；合法输入的结果不变，非法输入不能靠不断递归才失败。只在入口校验一次，区分输入检查与每层缩小问题这两项责任。

#### 第二遍：增量赋值为什么可能先改变对象，再失败

对内置列表，普通`x = x + y`先构造新列表，再绑定`x`；`x += y`尝试原地加法并把结果写回目标。一般对象可通过`__iadd__`定义行为，未实现或返回`NotImplemented`时再按相应普通运算规则处理，因此`+=`不是承诺原地修改的统一语法。

```python
# study-example: S05Z
left = [1]
alias = left
left = left + [2]
assert alias == [1] and left == [1, 2]
left = [1]
alias = left
left += [2]
assert left is alias and alias == [1, 2]
box = ([],)
try:
    box[0] += [3]
except TypeError:
    pass
else:
    raise AssertionError("tuple slot should reject assignment")
assert box == ([3],)
```

最后一例依次发生：读取tuple槽位里的列表；列表完成原地扩展；尝试把结果写回tuple槽位；写回被拒绝。异常表示语句未正常完成，不表示前面副作用自动撤销。tuple不可变约束的是其直接引用槽位，不冻结被引用列表。E02据此复查复制与异常的组合。

## 4. 示例与逐步走查

```python
# book-example: B05
from contextlib import contextmanager
events = []
@contextmanager
def session():
    events.append("open")
    try:
        yield events
    finally:
        events.append("close")
with session() as trace:
    trace.append("work")
assert events == ["open", "work", "close"]
```

### 4.1 沿输入到结果逐步解释

进入`with`时，`contextmanager`推进`session`到`yield`：先记录`open`，再把`events`交给`trace`。块内追加`work`，所以此时事件为`open`、`work`。离开`with`时恢复生成器，`finally`追加`close`，形成`open`、`work`、`close`。

为什么`yield`之后的清理会发生？上下文管理器负责在块退出时继续或结束这段生成器；不是普通`for`遇到`break`就自动替所有迭代器`close`。将块内工作改成抛异常，`finally`仍应执行，但异常默认继续传播。

因此资源责任包含两个独立要求：确实关闭，以及不要误把失败改成成功。只看`closed`标记并不足以验证第二项。

#### 把本章连成一条读取链

下面用内存中的文本模拟订单金额来源，每行单位为分。解析器负责逐行转换并报告位置；外层 `with` 拥有并关闭来源；`closing` 负责在提前停止时关闭已经创建的生成器。三个场景是各自独立的新来源：

```python
# study-example: S05P
from contextlib import closing
from io import StringIO

def amounts(lines):
    for number, text in enumerate(lines, 1):
        try:
            value = int(text.strip())
        except ValueError as error:
            raise ValueError(f"第{number}行不是整数") from error
        yield value

# 正常消费：读取两行，两个with按里到外退出。
normal = StringIO("10\n20\n")
with normal as source, closing(amounts(source)) as stream:
    assert list(stream) == [10, 20]
assert normal.closed

# 提前停止：第二行尚未读取，退出时仍关闭生成器和来源。
early = StringIO("10\n20\n")
with early as source, closing(amounts(source)) as stream:
    assert next(stream) == 10
assert early.closed

# 第二行损坏：错误从消费处传播；离开with后来源仍已关闭。
broken = StringIO("10\nbad\n")
try:
    with broken as source, closing(amounts(source)) as stream:
        assert next(stream) == 10
        next(stream)
except ValueError as error:
    assert "第2行" in str(error)
    assert isinstance(error.__cause__, ValueError)
else:
    raise AssertionError("损坏行应当报错")
assert broken.closed
```

先预测：如果只调用 `amounts(source)` 而不消费，是否已经读过第一行？如果在 `next(stream)` 之前退出，来源由谁关闭？如果把异常处理改成返回空列表，调用方还能否区分坏数据与真实空结果？再实际运行并沿表解释：

| 情况 | 结果或错误 | 来源何时关闭 |
| --- | --- | --- |
| 正常 | 得到10、20 | 消费完成后退出外层with |
| 提前停止 | 只得到10 | 退出时先关闭生成器，再关闭来源 |
| 坏第二行 | 第二次推进时抛带行号的ValueError | 异常离开with时关闭 |

示例把文件对象交给解析器读取，但解析器没有接管来源的关闭责任。外层掌握来源生命周期；若改为由生成器内部打开真实文件，应重新设计所有权，并验证已启动后提前关闭。三种场景使用模拟来源，第7章再迁移到真实文件和JSONL。

#### 验证实验 E09：装饰器退出路径

第四章先实现成功路径的包装；现在用E09观察`finally`如何保证退出事件，异常怎样继续传播。

这里比普通装饰器多一层配置：`decorate("outer")`先返回apply；apply接收原函数，再返回wrapped。两个装饰器表达式先从上到下求值，所以先记录build:outer、再build:inner；应用到函数时先内层、后外层。实际调用add时，才执行两层wrapped。先分清“准备配置、应用包装、调用包装”三个动作，再预测events；不要把这段当作第一次学习装饰器的入口。

```python
# experiment: E09
from functools import wraps
events = []
def decorate(label):
    events.append("build:" + label)
    def apply(fn):
        @wraps(fn)
        def wrapped(*args, **kwargs):
            events.append("enter:" + label)
            try:
                return fn(*args, **kwargs)
            finally:
                events.append("exit:" + label)
        return wrapped
    return apply
@decorate("outer")
@decorate("inner")
def add(a, b):
    """加法示例。"""
    return a + b
assert events == ["build:outer", "build:inner"]
assert add(1, 2) == 3
assert events[2:] == ["enter:outer", "enter:inner", "exit:inner", "exit:outer"]
assert add.__name__ == "add" and add.__wrapped__.__name__ == "add"
events.clear()
try:
    add(1, "bad")
except TypeError:
    pass
else:
    raise AssertionError("包装器不能吞掉原函数的计算错误")
assert events == ["enter:outer", "enter:inner", "exit:inner", "exit:outer"]
```

成功时保留结果3；失败时仍抛出TypeError。两个场景都按先内后外的顺序完成退出记录，finally没有把错误改成一个看起来成功的返回值。

## 7. 面试问答与迁移

`for`的`break`会自动`close`吗？`finally`里`return`有何风险？异常链为何有助于调试？`yield`暂停时保留了什么？

**参考回答：**

1. `break`只退出当前循环，不保证调用迭代器的close。某次实验中生成器恰好被回收，不能证明break负责清理；让变量继续保留生成器再测试，就能看出差别。谁拥有资源，谁应通过with、finally或适用的closing安排退出。
2. finally在离开try时执行，其中return会覆盖待返回的值，还可能吞掉正在传播的异常。清理应完成释放并让原控制流继续；若清理本身失败，也要决定如何保留原始故障信息。
3. `raise DomainError(...) from exc`用 `__cause__` 连接业务错误与底层异常，使调用方获得稳定语义，调试者仍能追到原因；`from None`隐藏展示中的自动异常上下文，并不等于删除所有底层信息。
4. yield保留暂停的执行位置、局部绑定和关联执行状态；这些绑定可继续引用大列表、文件等对象。惰性生成减少一次性产出，不保证占用一定小；提前停止时生成器里的资源也可能仍开着。

**换条件自测：** 保留生成器变量，取一项就break，再观察finally是否已经运行；显式close后再次观察。接着让 `__enter__` 自身失败，解释为什么不能指望尚未成功进入的with调用 `__exit__` 清理一切。

## 8. 本章小结与参考

### 8.1 一页知识地图

**本章主问题：** 数据一次取不完、还可能中途失败时，执行停在哪，谁负责清理？

**一条主线：**

```text
订单文件 → 迭代器/生成器逐项消费 → 异常沿调用链传播 → with/finally 关闭资源 → 调用方拿到部分结果或明确错误
```

**三个关键词：** 迭代状态、异常路径、资源所有权。迭代状态决定读到哪，异常路径决定从哪退出，资源所有权决定谁关闭。

**最容易错：**

- 为了查看内容而 `list(iterator)`，先把迭代器耗尽；
- 用宽泛 `except` 返回空列表，掩盖文件损坏；
- `break` 后不关闭生成器，指望对象立即回收；
- 以为什么都不做，已发生的修改会随异常自动回滚。

**与前后章：** 第4章留下函数调用与 `return` 这一正常出口，本章补上失败、暂停和提前停止。第6章要把一份任务状态与规则收进实例，需要先有明确的清理责任和迭代契约。

**学完应能：**

- 写一个惰性逐行读取、坏行报错并保留行号的生成器；
- 用 `with` 让正常、异常、提前 `break` 三条路径都关闭来源；
- 说明可迭代对象与迭代器的区别，验证两个独立消费位置并观察创建、推进和关闭时刻；
- 用 `ExitStack` 按逆序退出运行时才确定数量的资源。

### 8.2 日常工作注意事项

- 记录日志时为了查看内容而`list(iterator)`，可能先把迭代器耗尽；确认后续还需不需要消费，必要时有界保存结果。
- 不要用宽泛`except`返回空列表掩盖文件损坏或外部失败；只处理能解释的错误，保留异常链与调用现场。
- 文件和连接使用明确的关闭边界。提前`break`、异常或取消都要验证清理，不依赖对象恰好立即回收。
