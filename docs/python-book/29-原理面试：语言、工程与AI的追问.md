# 第29章　原理面试：语言、工程与 AI 的追问

## 1. 学习目标与前置知识

把知识变成可推导、可验证的回答。每完成一个作品就选自己能演示的题。订单 CLI 可练语言、资源和测试，DocPilot 可练检索、模型与引用，ProcureAgent 完成后再练工具、审批与恢复。

**承接与本章主线：** 从已实现项目追问语言、工程和AI机制，用陌生输入检验迁移；把解释不清的问题回流到对应实验。

**本章从这里开始：** 面试官把默认列表题换成嵌套配置，背过的输出不再够用。原理学习的目标，是条件变化后仍能从对象、状态和边界推导结论。

## 2. 基础知识讲解

### 2.1 用机制组织回答

面试把输入或失败位置换掉，是为了检查解释是否依赖记住原答案。同一默认列表问题换成字典，背输出就失效；按定义时求值、共享引用和原地修改推导，则仍能预测。练习因此围绕机制、证据和反例展开，而不是为每一种表面写法另背结论。

技术回答先定义概念和适用边界，再说明机制，再用小例子证明，最后连接工程后果。Python题尤其要区分语言语义与CPython观察，不把某个id、缓存或字节码现象当通用规则。

### 2.2 代码题是理解的检验

面试常从一个正常例子追加空输入、错误类型、顺序或资源要求。写代码前复述约定，先做清楚的正确实现，再考虑复杂度。仅背熟一段去重代码，遇到同ID冲突、首见顺序和输入不变就可能无法调整。

#### 案例推进：从一个反例开始，而非背定义

```python
# study-example: S29A
def configure(options={"labels": []}):
    options["labels"].append("used")
    return options
one = configure()
two = configure()
assert one is two and one["labels"] == ["used", "used"]
```

先解释def执行时创建默认对象，两次调用绑定到同一字典，再解释内层列表修改共同可见。追问时可依次改变：显式传入新字典、只浅复制外层、返回结果后再修改、并发调用。每个变化继续画对象关系，不需要重背一份答案。

### 2.3 工程题沿故障传播分析

面对偶发超时或重复写入，先确认边界与证据，再检查请求预算、重试、动作状态、幂等和恢复。不要未定位就建议换框架；要说明还缺哪些日志和实验，才能继续判断。

#### 案例推进：工程题同样沿时间线推导

超时先定义等待哪个阶段，再画远端写入与本地确认的先后；异步失败先区分错误已传播、兄弟任务已退出、线程已停止；RAG先检查来源、版本、权限与语义，再谈模型质量。语言题与系统题共享同一种推导方法。

### 2.4 AI题拆成可验证层

模型结构、概率生成、数据检索、Schema、授权和执行约束分别解释。RAG答错先定位解析/召回/排序/生成，Agent失败再区分参数、工具、循环和状态。提到某工具名称后，能说出它解决的问题与代价。

### 2.5 用三轮追问发现缺口

第一轮90秒口述结论，第二轮写小实验，第三轮改变条件推演。能解释新结果比重复原答案更重要；不确定的版本细节说清查证方式，复习时回到官方说明和实际验证。

#### 案例推进：用三轮追问检验理解

第一轮给准确结论，第二轮解释机制并写最小例子，第三轮改变输入、失败位置或资源限制。记录解释卡住之处，回到相应章补实验。不了解的实现细节说明版本与验证方法，避免将CPython一次观察当作全部Python保证。

## 3. 原理讲解与推导

### 3.1 可迁移解释区别于输出记忆

同一机制能解释多个例子。默认参数、闭包和装饰器时机都能从定义/调用的时间线推导；只记某次输出无法面对换条件的追问。

### 3.2 证据决定结论能说多大

个人练习、固定集实验和真实生产经历提供不同范围证据。只说自己能复现的结论，承认未测部分，并给出下一步验证计划。

## 4. 示例与逐步走查

### 一道题的三层回答

题目：默认参数为什么会共享？先说明默认表达式在定义阶段求值；再写两次调用使用同一列表的实验；最后解释请求级默认对象如何造成状态串联，并给None/哨兵/工厂等适合场景的修复。

追问：默认值绑定的是字典或自定义对象呢？闭包里绑定可变对象是否自动复制？这时若只能背例子输出，说明机制还需要复习。

### 4.1 沿输入到结果逐步解释

默认参数在def执行时求值，函数保留该对象。第一次调用向列表追加内容，第二次调用再次绑定到相同列表，所以看到累积结果；不是解释器把上次局部帧原样恢复。

改成每次传入新列表，结果可以独立；改成默认字典，机制仍是共享默认对象。若只浅复制外层，内部列表仍可能共享，需要继续画引用图。

回答能够跨这些变化保持一致，才表明理解原因。None或工厂的修复也应说明何时创建对象，而不只是背一行推荐写法。

### 4.2 两份完整回答：怎样从结论走到证据

**题一：把默认字典copy一下，能解决共享状态吗？**

可以这样回答：“不一定，先看要隔离哪一层。默认表达式在def执行时求值，函数保留该对象。dict.copy只创建新外层，里面的labels列表仍可能共享；两次调用会修改同一列表。用None在每次缺省调用中创建新状态能隔离缺省调用，但显式传入同一字典仍可能共享。修复应先约定函数是否允许修改调用方数据，再复制必要层次或改为返回新结果。”

沿时间线检查本章S29A：定义时建立一份默认字典与列表；第一次调用修改列表并返回这份字典；第二次调用又修改同一列表。one不是第一次结果的冻结快照，所以第二次操作后也能看见变化。

再用以下反例检验“已经copy就没有共享”的说法：

```python
# study-example: S29B
def add_label(options=None):
    if options is None:
        options = {"labels": []}
    else:
        options = options.copy()
    options["labels"].append("used")
    return options

shared = {"labels": []}
first = add_label(shared)
second = add_label(shared)
assert first is not second
assert first["labels"] is second["labels"] is shared["labels"]
assert shared["labels"] == ["used", "used"]
assert add_label()["labels"] == ["used"]  # 缺省调用才建立独立状态
```

最后一句工程影响可以是：“若这是请求级配置，一次请求可能改变另一请求看到的标签；我会补显式共享输入与返回后修改的测试。”只有你确实完成过对应修复，才把它改写成自己的项目经历。继续追问时，把labels换成连接对象：这时问题转为资源所有权，不应直接深复制。

**题二：写接口超时，为什么不能直接再发一次？**

可以这样回答：“超时描述本地等待，不自动说明远端没有效果。我要先确认失败阶段和接收方契约；若远端已提交而回执丢失，结果就是未知。接收方支持稳定动作键的原子去重时，按同键同载荷查询或重试可取得原结果；不支持时，本地checkpoint或账本也不能单独保证一次效果，需要查询、对账或人工处置。”

| 时刻 | 接收方事实 | 调用方知道什么 | 恢复时检查什么 |
| --- | --- | --- | --- |
| 发出前记录动作 | 尚无本次效果 | 准备提交 | 动作键、载荷、当前授权与批准 |
| 远端提交后丢回执 | 效果已经存在 | 结果未知 | 接收方查询/同键重试的契约 |
| 新进程取回原回执 | 仍是原效果 | 可以确认结果 | 回执与实际效果数，而非仅本地状态 |

这是设计推演，实测证据要来自故障注入。运行[审批接收方练习](../../tests/learner/练习说明.md)后，记录同键同载荷、同键换载荷与换进程恢复的实际输出；它证明本地接收方边界，不替代真实远端验证。再改变“批准后报告内容变化”的条件：必须重新判断批准，不能因为重试幂等就省略授权。

### 4.3 怎样判断自己还缺哪一层

| 观察到的回答 | 缺口 | 下一次学习动作 |
| --- | --- | --- |
| 只说“可变对象危险” | 没解释定义/调用时机 | 画默认对象与两次绑定，重跑第4章实验 |
| 说“copy后一定独立” | 忽略嵌套共享 | 改动内层列表，回到第3章复制边界 |
| 说“带键重试就安全” | 忽略接收方契约与失效条件 | 按第16章三类动作输入检查效果与冲突 |
| 机制讲对，但只展示参考输出 | 缺少自己的实现证据 | 指定自己的模块运行契约并保留失败修复 |
| 原题解释正确，换条件就卡住 | 尚未形成迁移 | 只改变一个输入或故障位置，先预测再运行 |

练习时先回答，再看本节，最后做一次不同条件。第二天不看答案重讲卡住的题；只复习暴露缺口的章节，不把36张卡再排成另一份课程。

## 7. 面试问答与迁移

## 8. 本章小结与参考

### 8.1 主要知识点总结

- 原理回答从定义、机制、例子走到工程后果与验证。
- 语言语义、库约定与CPython版本观察分开说明。
- 新输入与条件变化用于检验推导能力，不能只背固定输出。
- 解释需要连接自己的实现、失败记录和设计取舍。

### 8.2 日常工作注意事项

- 代码评审中解释结论时给出最小可复现输入，不用某次id、缓存或字节码结果代替通用规则。
- 遇到不确定行为先说明环境与版本，再查官方资料或运行小实验；避免把猜测写进接口契约。
- 回答性能与可靠性问题时附样本、负载和失败条件，没有测量的数据不写成收益百分比。
