## 1. 学习目标与前置知识

**承接与本章主线：** 将前面机制转成可重复证据，用测试、调用栈与日志定位失败；验证方式随后用于并发与综合项目，而不只检查样例输出。

**本章从这里开始：** 你写的去重函数输出数量正确，却悄悄改了输入。怎样让检查真正发现问题？本章从一个容易漏测的需求开始，把断言、替身、调试与回归连起来。

## 2. 基础知识讲解

前面建立机制，本章把它变成证据：测试记录行为，调试查看调用链和当前状态，日志保存跨过程事件。对象图解释共享，调用栈解释路径，测量解释性能；三者回答不同问题。

### 2.1 将需求变成可观察的断言

去重函数返回两条记录，数量正确，但它可能保留了错误版本，也可能改坏输入。只看结果长度发现不了这些问题。测试的起点因此不是选框架，而是列出必须保持的行为；断言将每项要求变成能失败的观察。pytest、替身和调试工具随后分别帮助组织、控制条件和定位失败。

一个测试先准备输入，再执行动作，最后观察结果。订单去重不仅要检查数量，还要检查保留了哪条、顺序、冲突是否报错和输入是否改变。断言越贴近真实需求，越能防止“输出碰巧正确”。

正常、空、边界和错误案例分别承担作用。不要把测试写成实现的逐行复述；如果两者复制了同一个错误，测试也可能通过。

#### 案例推进：先把口头需求拆成行为

“规范化订单”至少有四件事：结果去掉两端空白，保留大小写，拒绝空ID，原输入不变。只检查结果数量，无法证明其他三项。测试期望应从需求手算，避免把实现里的同一表达式复制成答案。

下面代码保存为一个test_开头的独立文件后，用项目pytest执行；函数体为教学被测对象，测试函数才是检查。

```python
# pytest-example: T10
from copy import deepcopy
import pytest

def normalize(rows):
    result = []
    for row in rows:
        cleaned = dict(row)
        cleaned["id"] = row["id"].strip()
        if not cleaned["id"]:
            raise ValueError("id不能为空")
        result.append(cleaned)
    return result

def test_result_and_input_are_both_checked():
    raw = [{"id": " A ", "amount_cents": 10}]
    snapshot = deepcopy(raw)
    assert normalize(raw) == [{"id": "A", "amount_cents": 10}]
    assert raw == snapshot

@pytest.mark.parametrize("order_id", ["", " ", "\t"])
def test_empty_id_is_rejected(order_id):
    with pytest.raises(ValueError, match="id"):
        normalize([{"id": order_id}])
```

### 2.2 组织可重复的pytest测试

test_文件/函数方便发现测试；参数化复用相同案例结构，fixture提供每次所需准备，tmp_path隔离临时文件。可变样例要避免测试之间共享未清理状态，否则运行顺序可能影响结果。

用raises表达预期异常，并核对有意义的类型或字段；不要捕获一切异常后无条件通过。覆盖率帮助找没执行的路径，但不能证明断言充分或业务正确。

#### 案例推进：用小改动检验测试是否有辨别力

暂时把cleaned = dict(row)改成cleaned = row，测试应因输入改变而失败；恢复后再运行。再去掉空ID检查，参数化错误案例应失败。这种有目的的小故障能说明断言抓住了需求，不以测试数量或覆盖率替代实际辨别力。

fixture用于准备共享方式，tmp_path提供隔离的临时路径，monkeypatch可在正确作用域替换环境或对象。patch应针对使用处的绑定；若模块已from其他模块导入函数，只改原模块同名绑定未必影响使用处。这仍是第一章的对象绑定问题。

### 2.3 替换边界，不替换要检验的规则

网络、时间、模型和随机来源可以注入替身，使结果可控；计算、去重和规则本身应真实执行。单元测试关注局部契约，集成测试观察模块协作，真实服务检查另记录网络与配置条件。

#### 案例推进：替换外部依赖，保留正在检查的规则

测试报告计算时注入固定仓储，真实金额计算继续执行；测试HTTP适配时用受控响应，真实状态检查、解析和校验继续执行。若把被测计算也mock成期望答案，测试只证明替身设置成功。

遇到失败时保留最小输入、运行命令和traceback；先定位差异发生在哪一层，再修改。日志记录关联ID与阶段，异常让调用方决定流程。最终把失败样例变成回归，调试过程才不会随着临时print删除而失去价值。

### 2.4 调试与日志各自提供什么

traceback说明错误经过的调用路径，异常链保留底层原因；断点检查某个时刻的局部状态。日志保存运行事件，应包含可关联标识、阶段、耗时和错误类别，而不是随意打印所有参数。

日志不代替抛错，print调试不代替稳定断言。处理凭据和敏感原文时，采集前就应定义脱敏和保留规则。

#### 案例推进：用白名单字段输出结构化日志

```python
# study-example: S10A
import io
import json
import logging

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({
            "level": record.levelname,
            "event": record.getMessage(),
            "order_id": getattr(record, "order_id", None),
            "status": getattr(record, "status", None),
        }, ensure_ascii=False)

stream = io.StringIO()
logger = logging.Logger("orders", level=logging.INFO)
handler = logging.StreamHandler(stream)
handler.setFormatter(JsonFormatter())
logger.addHandler(handler)

logger.info("order_status", extra={
    "order_id": "A", "status": "paid", "token": "secret-token",
})
payload = json.loads(stream.getvalue())
assert payload == {
    "level": "INFO", "event": "order_status",
    "order_id": "A", "status": "paid",
}
assert "token" not in payload and "secret-token" not in stream.getvalue()
```

`logger.info("order_status", extra={...})`把字段挂在日志记录上；`JsonFormatter`只序列化白名单里的 `order_id`/`status`，即使调用方多传了 `token`，也不会进入输出。这比固定样例里“恰好没有 token 字样”更强：泄露检查要针对实际格式化结果和允许字段，而不是靠字符串巧合。`%s` 延迟格式化仍然适用；结构化字段与文本日志是两种输出形式，不要声称用了 `extra` 就自动安全。

### 2.5 工程工具是不同验证环节

pyproject声明项目和依赖，锁文件记录解析结果，虚拟环境容纳实际安装。Ruff检查一类代码问题，静态检查分析类型关系，pytest验证案例，构建与安装验证交付形式。它们互补，不能用一个“全绿”替代其余环节。

构建wheel后，从非源码目录、独立环境导入，才能发现包漏文件或隐式路径依赖。README必须记录真实可运行命令，而不是只写理想目录。

#### 案例推进：工具链各自回答什么

Ruff检查代码问题和格式，静态检查器分析类型关系，pytest检验行为，构建与安装检查交付，集成测试观察真实组合。通过某一项不能代替其他项。持续集成在干净环境运行约定步骤，把本地隐藏依赖暴露出来；具体命令应与项目实际配置一致。

### 2.6 断言、业务错误与故障现场

测试中的 assert 适合表达“这次行为必须满足的条件”。运行解释器时加 -O 会移除普通 assert 语句，因此外部金额校验、权限检查和工具参数检查应使用显式条件与异常。先分别用 `python -c "assert False"` 和 `python -O -c "assert False"` 观察退出情况，再思考如果断言表达式里还做了写入会怎样。

调试一次错误时先保留触发它的最小输入。从 traceback 底部识别异常及失败的表达式，向上找到第一个应该承担校验责任的调用方；用 `breakpoint()` 暂停，检查当时的类型、值和调用栈，再用同一个输入写回归测试。迁移题：让嵌套工具参数把金额传成 true，预测故障在解码、校验还是业务执行时出现；修复后验证业务函数调用次数为零。

## 3. 原理讲解与推导

### 3.1 测试只证明观察到的行为

排序结果正确与输入不变是两项独立要求。若仅断言结果，第一个要求通过不能推导第二个成立。设计测试时先列出状态和副作用，再决定哪些观察是必要的。

### 3.2 替身改变了证据范围

替换数据来源后，能证明业务函数在固定数据下如何处理，不能证明真实服务永远返回该格式。把业务函数也替换成固定答案，会进一步失去对核心行为的检验。每次使用mock都应说明仍在验证哪一段。

### 3.3 故障敏感性比测试数量更有价值

故意改错一条核心规则，相关测试应失败；恢复后再通过。这样能验证测试确实约束了规则，而非只检查代码可以运行。

### 3.4 机制验证：预测、运行与回看

#### 验证实验 E21

```python
# experiment: E21
from copy import deepcopy
def sorts_in_place(rows):
    rows.sort(key=lambda row: row["cents"])
    return rows
rows = [{"id": "A", "cents": 20}, {"id": "B", "cents": 10}]
before = deepcopy(rows)
result = sorts_in_place(rows)
assert [row["id"] for row in result] == ["B", "A"]
assert rows != before  # 输出正确，但违反了本课程输入不变约定
def report_amount(fetch):
    return sum(row["cents"] for row in fetch())
assert report_amount(lambda: [{"cents": 7}, {"cents": 3}]) == 10
```

## 4. 示例与逐步走查

```python
# book-example: B10
def read_limit(environment):
    value = int(environment.get("LIMIT", "3"))
    if value <= 0:
        raise ValueError("LIMIT must be positive")
    return value
assert read_limit({}) == 3 and read_limit({"LIMIT":"2"}) == 2
```

### 4.1 沿输入到结果逐步解释

空配置时get取得默认文本"3"，int将它转换成整数3；配置LIMIT="2"时得到2。此处既测默认选择，也测文本到整数的转换，不能只检查返回类型。

LIMIT="bad"在转换阶段失败；LIMIT="0"能转换，却违反正数约束。两种失败都需要暴露，但发生原因不同。测试应各留一个案例，避免只测正数而让校验形同虚设。

故意删除正数检查，零值案例应失败；若仍全绿，说明测试没有约束这条规则。测试价值来自能发现什么错误，而不是断言或文件的数量。

## 7. 面试问答与迁移

mock 怎样造成假通过？单元/集成测试如何划分？运行环境与依赖锁如何配合？

**参考回答：**

1. 若把“检查租户”的函数替换成永远成功，测试即使全绿也没验证隔离。替身控制网络、时钟等外部变化，待验证的业务规则保留真实实现；除了断言调用次数，还检查返回值、持久状态、拒绝与失败路径。
2. 单元测试针对小范围规则，集成测试验证真实组件组合后的契约，例如路由解析、事务与序列化。分类取决于测试边界，不仅取决于是否用了mock；少量端到端测试再验证关键用户路径。每类都写清没有覆盖什么。
3. 锁文件固定依赖解析结果，不固定操作系统、解释器、环境变量、数据库或远端模型。干净环境中按锁安装，再从非源码目录运行构建产物，才能发现遗漏文件、路径依赖与导入副作用。保留环境与失败命令，别人才能复现。

**换条件自测：** 故意删除一次租户过滤：已有测试应有明确失败。若仍全绿，补能观察越权结果的案例；不要用只检查函数被调用的断言替代它。

## 8. 本章小结与参考

### 8.1 主要知识点总结

- 测试先固定输入、动作和可观察结果，覆盖正常、边界、失败与副作用。
- 调试器观察当前执行状态，日志记录过程，性能工具验证瓶颈。
- fixture、替身与参数化帮助控制条件，但要对应真实接口契约。
- 项目检查应可复现，修复通过失败案例验证，而非只验证理想路径。

### 8.2 日常工作注意事项

- 不要用assert代替生产数据校验；断言可以被优化选项移除，外部输入应有明确错误处理。
- 测试避免依赖真实时间、随机碰巧结果和共享全局状态；通过注入或固定样本建立可重复条件。
- 日志使用请求或任务标识关联过程，对令牌与业务正文按范围处理；定位错误同时保留异常信息，避免只打印一句失败。
