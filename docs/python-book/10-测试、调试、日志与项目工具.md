## 2. 基础知识讲解

### 2.1 把需求写成会失败的断言

测试按“准备输入 → 执行动作 → 观察结果”组织。订单报告不只看数量，还要看保留哪条、顺序、冲突和输入副作用。期望值从需求手算，不要把实现里的同一表达式复制成答案。

T10 检查两件事：ID 去两端空白但保留大小写；规范化返回新字典，不修改原输入。参数化把空字符串、空格和制表符复用同一断言结构，`pytest.raises` 同时检查异常类型和消息。

#### 案例推进：结果与输入分别观察

```python
# pytest-example: T10
from copy import deepcopy
import pytest

def normalize(rows):
    result = []
    for row in rows:
        cleaned = dict(row)
        cleaned["id"] = row["id"].strip()
        if not cleaned["id"]:
            raise ValueError("id不能为空")
        result.append(cleaned)
    return result

def test_result_and_input_are_both_checked():
    raw = [{"id": " A ", "amount_cents": 1990}]
    snapshot = deepcopy(raw)
    assert normalize(raw) == [{"id": "A", "amount_cents": 1990}]
    assert raw == snapshot

@pytest.mark.parametrize("order_id", ["", " ", "\t"])
def test_empty_id_is_rejected(order_id):
    with pytest.raises(ValueError, match="id"):
        normalize([{"id": order_id}])
```

T10 的 `4 passed` 由 pytest 收集后得到：一个普通测试函数，加三个由同一测试函数生成的参数化案例。pytest 不把代码块当脚本顺序执行，而是发现 `test_` 函数、准备 fixture，再逐个调用。

```python
# pytest-example: S10B
import pytest
@pytest.fixture
def paid_amount():
    return 1990
@pytest.mark.parametrize("paid, expected", [(True, 1990), (False, 0)])
def test_paid_only(paid_amount, paid, expected):
    assert (paid_amount if paid else 0) == expected
```

这个短测试执行两条路径：已支付时保留1990，待支付时为0。fixture 每次函数测试重新返回1990；参数化负责提供 paid/expected，而不是让两个测试共享可变列表。

### 2.2 组织可重复、有辨别力的测试

`test_` 文件和函数便于发现，`tmp_path` 隔离临时文件，fixture 准备每次所需条件。可变样例不要跨测试共享未清理状态；patch 针对名称的实际使用处，修改原模块绑定不一定影响已经 `from ... import` 的调用方。

暂时把 T10 的 `cleaned = dict(row)` 改成 `cleaned = row`，输入不变断言应失败；恢复后删除空 ID 检查，三个参数化案例应失败。恢复代码必须再次通过。覆盖率只说明哪些路径执行过，不证明断言充分。

fixture 的 `scope` 决定复用范围：`function` 每次测试重建，`class/module/session` 复用次数更多，但也更容易泄漏状态。`tmp_path` 为每个测试提供独立目录；`monkeypatch` 在测试结束恢复替换；`capsys` 捕获 stdout/stderr；`caplog` 检查实际日志记录。替身要断言调用次数、参数和未调用路径，不能只配置“返回成功”。`pytest.raises` 应同时检查异常类型与关键消息，避免把 unrelated `ValueError` 当成预期失败。

| 工具 | 适合隔离什么 | 必须另外观察什么 |
| --- | --- | --- |
| `tmp_path` | 每个测试的文件写入 | 文件内容、编码、失败后是否残留 |
| `monkeypatch` | 环境变量或模块名称 | 原绑定是否恢复、替换是否命中实际调用处 |
| `capsys` | stdout/stderr | 输出字段和敏感内容，不只是“有输出” |
| `caplog` | 日志记录与级别 | 白名单字段和令牌是否泄露 |
| 外部替身 | 网络、时钟、模型服务 | 调用参数、次数、失败路径及未替换的核心规则 |

例如 `order_service` 若已经 `from clock import now`，patch `clock.now` 不改变它本地绑定的函数；应 patch `order_service.now`，并用断言证明替身确实被调用。只知道“返回值像成功”不够。下面把三种常用 fixture 放进一个最小测试：替身替换对象属性、捕获两路输出、读取真实日志记录。

```python
# pytest-example: S10C
import logging
import sys
from types import SimpleNamespace

service = SimpleNamespace(name="original")

def current_name():
    return service.name()

def test_patch_capture_and_log(monkeypatch, capsys, caplog):
    calls = []

    def replacement():
        calls.append("called")
        return "patched"

    with monkeypatch.context() as patch:
        patch.setattr(service, "name", replacement)
        assert current_name() == "patched"
    assert service.name == "original"
    assert calls == ["called"]

    print("stdout:A1")
    print("stderr:offline", file=sys.stderr)
    captured = capsys.readouterr()
    assert captured.out == "stdout:A1\n"
    assert captured.err == "stderr:offline\n"

    logger = logging.getLogger("order-test")
    with caplog.at_level(logging.INFO, logger=logger.name):
        logger.info("stage=paid", extra={"order_id": "A1"})
    record = caplog.records[-1]
    assert record.order_id == "A1"
    assert record.getMessage() == "stage=paid"
    assert "token" not in record.__dict__
```

pytest 收集到 `1 passed`。`monkeypatch.context()` 在块结束后恢复 `service.name`，调用列表证明替身命中；`capsys.readouterr()` 分别取得 stdout/stderr；`caplog` 取得 logging 真正创建的 `LogRecord`，可以检查白名单字段 `order_id` 和消息内容。它们隔离的是外部环境与输出通道，不替代业务断言。

### 2.3 调试先保留现场，生产校验不靠 assert

traceback 从底部给出异常和失败表达式，向上可找调用路径；异常链保留底层原因。断点用于查看某个时刻的类型、值和局部状态，`print` 只适合临时探索，稳定行为仍要写成回归测试。

`python -O` 会移除普通 assert，所以外部金额、权限和工具参数检查必须用显式条件与异常。测试 assert 用于表达案例必须满足的条件，不能替代生产输入校验。

先用最小输入让失败稳定复现，再进入调试器。`python -m pdb order_store.py` 从文件开始；在可疑行前调用 `breakpoint()` 也可进入。常用命令只回答当前现场的问题：

| 命令 | 作用 |
| --- | --- |
| `p value` / `type(value)` | 看当前值及实际类型，尤其检查bool、None和字符串金额 |
| `where` | 看调用栈，定位从哪个入口到达失败行 |
| `n` / `s` | 执行下一行 / 进入当前函数调用 |
| `c` | 继续运行到下个断点或异常 |
| `q` | 退出调试器 |

调试结束后删除临时 `breakpoint()`，把现场固化成失败测试；不要只保留一段难以重复的 print。

替身只替换网络、时钟、模型等外部边界；金额计算、去重和状态规则应真实执行。把被测规则也替换成期望答案，只会证明替身配置成功。使用替身时要说明它证明了哪一段、没有证明哪一段。

### 2.4 日志留下定位线索，工具链分工验证

日志应带订单 ID、阶段和错误类别，不打印令牌或整段敏感正文。结构化日志采用字段白名单；调用方即使多传 `token`，格式化器也不能把它写入输出。`extra` 不能覆盖 `message`、`name` 等 LogRecord 保留字段，否则日志调用本身会失败；应在边界统一字段名并测试冲突。日志不代替异常，调用方仍决定如何处理失败。

#### 案例推进：白名单防止额外字段进入日志

```python
# study-example: S10A
import io, json, logging
class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({"level": record.levelname, "event": record.getMessage(),
                           "order_id": getattr(record, "order_id", None),
                           "status": getattr(record, "status", None)}, ensure_ascii=False)
stream = io.StringIO()
logger = logging.Logger("orders", level=logging.INFO)
handler = logging.StreamHandler(stream)
handler.setFormatter(JsonFormatter())
logger.addHandler(handler)
logger.info("order_status", extra={"order_id": "A", "status": "paid", "token": "secret-token"})
payload = json.loads(stream.getvalue())
assert payload == {"level": "INFO", "event": "order_status", "order_id": "A", "status": "paid"}
assert "token" not in payload and "secret-token" not in stream.getvalue()
print(stream.getvalue(), end="")
```

```text
{"level": "INFO", "event": "order_status", "order_id": "A", "status": "paid"}
```

即使 `extra` 收到token，formatter也只读取level、event、order_id、status四个字段。输出文本里没有token值；若直接打印整个record的 `__dict__`，白名单就失效了。

Ruff 检查代码问题和格式，mypy 分析类型关系，pytest 验证行为，构建与安装检查交付。它们互补，一个“全绿”不能代替其他环节。锁文件固定依赖解析结果，不固定操作系统、环境变量或远端服务；干净环境仍需重新验证。

## 3. 原理讲解与推导

### 3.1 故障敏感性来自独立观察，不来自测试数量

排序结果正确与输入不变是两项独立要求。只断言结果，不能推导输入没被修改；实现和测试复制同一错误表达式，也可能一起通过。故意破坏一条规则后，对应测试必须失败，这才证明断言约束了该规则。

```python
# experiment: E21
from copy import deepcopy
def sorts_in_place(rows):
    rows.sort(key=lambda row: row["cents"])
    return rows
rows = [{"id": "A", "cents": 20}, {"id": "B", "cents": 10}]
before = deepcopy(rows)
result = sorts_in_place(rows)
assert [row["id"] for row in result] == ["B", "A"]
assert rows != before
print([row["id"] for row in before], [row["id"] for row in result],
      rows == before, result is rows)
```

```text
['A', 'B'] ['B', 'A'] False True
```

`before`保存A、B原顺序；`result`和`rows`是同一列表，排序后都变成B、A。只断言result顺序会漏掉输入被改，必须另断言 `rows == before`。

E21 中输出顺序正确，但输入已改变。把它作为反例，而不是推荐实现；若课程要求输入不变，就应增加 `assert rows == before`，让当前实现失败。

## 4. 示例与逐步走查

B10 接收第9章的 A/B：A=Alice、1990 分、paid；B=Bob、1000 分、pending。先分三步观察同一份输入，再用第9章的坏输入表做回归。

### 4.1 准备：保存原输入

#### 案例推进：深复制后才能比较副作用

测试先深复制输入，才能在执行后比较；只保留长度无法发现字段或顺序被改。

### 4.2 执行：规则真实运行

#### 案例推进：只汇总 paid 的金额

`summarize` 不过滤未知状态以外的数据，只汇总 status 为 paid 的金额，并统计全部订单。账目规则不交给 mock。

### 4.3 观察：结果和副作用分别断言

#### 案例推进：结果不等或输入改变都应失败

B10 同时断言报告为2单、1990分，以及输入与快照相同。删掉 paid 过滤，金额会变成2990，报告断言失败；把输入排序或改字段，副作用断言失败。

```python
# book-example: B10
from copy import deepcopy
def summarize(orders):
    for order in orders:
        if type(order["amount_cents"]) is not int or order["amount_cents"] < 0:
            raise ValueError("金额必须为非负整数分")
    return {"order_count": len(orders),
            "paid_amount_cents": sum(o["amount_cents"] for o in orders if o["status"] == "paid")}
orders = [
    {"id": "A", "user": "Alice", "amount_cents": 1990, "status": "paid"},
    {"id": "B", "user": "Bob", "amount_cents": 1000, "status": "pending"},
]
before = deepcopy(orders)
assert summarize(orders) == {"order_count": 2, "paid_amount_cents": 1990}
assert orders == before
print(summarize(orders), orders == before)
bad = deepcopy(orders)
bad[0]["amount_cents"] = True
try:
    summarize(bad)
except ValueError as error:
    print(str(error))
else:
    raise AssertionError("坏金额不应进入汇总")
```

```text
{'order_count': 2, 'paid_amount_cents': 1990} True
金额必须为非负整数分
```

输入检查沿用第9章的契约：bool 和负数在汇总前抛 `ValueError`。测试验证这条明确规则，不依赖 `sum` 恰好抛出某种异常。`True`若漏检，会被当成1加入金额；本例因显式类型检查在进入sum前失败。删除paid过滤则report变为2990，输入不变断言仍可能通过，说明两项证据不能互相代替。

### 4.4 回归：把第9章的坏输入表接进 pytest

第9章累计任务要求你写一个运行时入口，拒绝字符串金额、bool、负数、缺字段、额外字段和非法状态。给已有代码补回归测试不需要重写实现：导入那个入口，把每条约定坏输入变成参数化案例，让 pytest 逐条检查异常类型。

S10D 先内置一份符合第9章契约的最小 `validate_order`，使本块可独立运行；做累计任务时把它换成 `from order_contract import validate_order`（函数名按你的实现调整），同一张参数表就变成对你自己代码的回归测试。某个坏输入意外通过，说明入口契约有缺口，应修实现而不是删断言。

```python
# pytest-example: S10D
import pytest

ALLOWED = {"id", "user", "amount_cents", "status"}
STATUSES = {"paid", "pending", "cancelled"}

def validate_order(row):
    if not isinstance(row, dict):
        raise ValueError("订单必须是字典")
    if set(row) != ALLOWED:
        raise ValueError("缺字段或额外字段")
    if type(row["amount_cents"]) is not int or row["amount_cents"] < 0:
        raise ValueError("金额必须为非负整数分")
    if row["status"] not in STATUSES:
        raise ValueError("非法状态")
    return row

def test_valid_order_passes():
    row = {"id": "A", "user": "Alice", "amount_cents": 1990, "status": "paid"}
    assert validate_order(row)["id"] == "A"

@pytest.mark.parametrize("bad", [
    {"id": "A", "user": "Alice", "amount_cents": "1990", "status": "paid"},
    {"id": "A", "user": "Alice", "amount_cents": True, "status": "paid"},
    {"id": "A", "user": "Alice", "amount_cents": -1, "status": "paid"},
    {"id": "A", "user": "Alice", "status": "paid"},
    {"id": "A", "user": "Alice", "amount_cents": 1990, "status": "paid", "paid_at": None},
    {"id": "A", "user": "Alice", "amount_cents": 1990, "status": "unknown"},
])
def test_bad_orders_are_rejected(bad):
    with pytest.raises(ValueError):
        validate_order(bad)
```

`7 passed` 由1条正常案例加6条坏输入参数化案例组成：字符串金额、bool、负数、缺字段、额外字段、非法状态各一条。参数表就是回归资产：第11章改变执行方式、第16章接数据库后，仍可用同一组输入确认入口规则没有放宽。

## 7. 面试问答与迁移

**问：mock 怎样造成假通过？** 把租户检查或业务计算替换成永远成功，测试即使全绿也没验证该规则。替身控制外部变化，核心规则保留真实实现，并检查拒绝、持久状态和失败路径。

**问：单元测试与集成测试如何划分？** 单元测试聚焦局部契约，集成测试观察真实组件组合，例如文件编码、SQL 事务和序列化。边界取决于验证什么，不是只看是否使用 mock；每类都要说明未覆盖范围。

**问：运行环境与依赖锁如何配合？** 锁文件固定解析结果，解释器、操作系统、环境变量和远端服务仍需记录。干净环境安装后从非源码目录运行构建产物，才能暴露漏文件和隐式路径依赖。

**迁移：** 把订单仓储换成 SQLite 后，用临时数据库测试参数化、回滚和重开查询；只 mock 连接会失去这些真实行为证据。

## 8. 本章小结与参考

- 断言应来自需求并覆盖结果、错误和副作用，不能照抄实现表达式。
- 参数化、fixture 和 `tmp_path` 建立可重复条件，替身只替换外部边界。
- 故意破坏规则后测试必须变红，修复后再绿，才能证明故障敏感性。
- traceback、断点和最小输入用于定位，稳定回归测试保存修复证据。
- 日志用标识和白名单字段关联现场；生产校验用显式异常，不靠 assert。
- pytest、静态检查、格式检查和安装验证各回答不同问题，不能互相替代。
