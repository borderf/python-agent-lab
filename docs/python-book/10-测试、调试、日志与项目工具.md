## 2. 基础知识讲解

### 2.1 把需求写成会失败的断言

测试按“准备输入 → 执行动作 → 观察结果”组织。订单报告不只看数量，还要看保留哪条、顺序、冲突和输入副作用。期望值从需求手算，不要把实现里的同一表达式复制成答案。

T10 检查两件事：ID 去两端空白但保留大小写；规范化返回新字典，不修改原输入。参数化把空字符串、空格和制表符复用同一断言结构，`pytest.raises` 同时检查异常类型和消息。

#### 案例推进：结果与输入分别观察

```python
# pytest-example: T10
from copy import deepcopy
import pytest

def normalize(rows):
    result = []
    for row in rows:
        cleaned = dict(row)
        cleaned["id"] = row["id"].strip()
        if not cleaned["id"]:
            raise ValueError("id不能为空")
        result.append(cleaned)
    return result

def test_result_and_input_are_both_checked():
    raw = [{"id": " A ", "amount_cents": 1990}]
    snapshot = deepcopy(raw)
    assert normalize(raw) == [{"id": "A", "amount_cents": 1990}]
    assert raw == snapshot

@pytest.mark.parametrize("order_id", ["", " ", "\t"])
def test_empty_id_is_rejected(order_id):
    with pytest.raises(ValueError, match="id"):
        normalize([{"id": order_id}])
```

### 2.2 组织可重复、有辨别力的测试

`test_` 文件和函数便于发现，`tmp_path` 隔离临时文件，fixture 准备每次所需条件。可变样例不要跨测试共享未清理状态；patch 针对名称的实际使用处，修改原模块绑定不一定影响已经 `from ... import` 的调用方。

暂时把 T10 的 `cleaned = dict(row)` 改成 `cleaned = row`，输入不变断言应失败；恢复后删除空 ID 检查，三个参数化案例应失败。恢复代码必须再次通过。覆盖率只说明哪些路径执行过，不证明断言充分。

fixture 的 `scope` 决定复用范围：`function` 每次测试重建，`class/module/session` 复用次数更多，但也更容易泄漏状态。`tmp_path` 为每个测试提供独立目录；`monkeypatch` 在测试结束恢复替换；`capsys` 捕获 stdout/stderr；`caplog` 检查实际日志记录。替身要断言调用次数、参数和未调用路径，不能只配置“返回成功”。`pytest.raises` 应同时检查异常类型与关键消息，避免把 unrelated `ValueError` 当成预期失败。

### 2.3 调试先保留现场，生产校验不靠 assert

traceback 从底部给出异常和失败表达式，向上可找调用路径；异常链保留底层原因。断点用于查看某个时刻的类型、值和局部状态，`print` 只适合临时探索，稳定行为仍要写成回归测试。

`python -O` 会移除普通 assert，所以外部金额、权限和工具参数检查必须用显式条件与异常。测试 assert 用于表达案例必须满足的条件，不能替代生产输入校验。

替身只替换网络、时钟、模型等外部边界；金额计算、去重和状态规则应真实执行。把被测规则也替换成期望答案，只会证明替身配置成功。使用替身时要说明它证明了哪一段、没有证明哪一段。

### 2.4 日志留下定位线索，工具链分工验证

日志应带订单 ID、阶段和错误类别，不打印令牌或整段敏感正文。结构化日志采用字段白名单；调用方即使多传 `token`，格式化器也不能把它写入输出。`extra` 不能覆盖 `message`、`name` 等 LogRecord 保留字段，否则日志调用本身会失败；应在边界统一字段名并测试冲突。日志不代替异常，调用方仍决定如何处理失败。

#### 案例推进：白名单防止额外字段进入日志

```python
# study-example: S10A
import io, json, logging
class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({"level": record.levelname, "event": record.getMessage(),
                           "order_id": getattr(record, "order_id", None),
                           "status": getattr(record, "status", None)}, ensure_ascii=False)
stream = io.StringIO()
logger = logging.Logger("orders", level=logging.INFO)
handler = logging.StreamHandler(stream)
handler.setFormatter(JsonFormatter())
logger.addHandler(handler)
logger.info("order_status", extra={"order_id": "A", "status": "paid", "token": "secret-token"})
payload = json.loads(stream.getvalue())
assert payload == {"level": "INFO", "event": "order_status", "order_id": "A", "status": "paid"}
assert "token" not in payload and "secret-token" not in stream.getvalue()
```

Ruff 检查代码问题和格式，mypy 分析类型关系，pytest 验证行为，构建与安装检查交付。它们互补，一个“全绿”不能代替其他环节。锁文件固定依赖解析结果，不固定操作系统、环境变量或远端服务；干净环境仍需重新验证。

## 3. 原理讲解与推导

### 3.1 故障敏感性来自独立观察，不来自测试数量

排序结果正确与输入不变是两项独立要求。只断言结果，不能推导输入没被修改；实现和测试复制同一错误表达式，也可能一起通过。故意破坏一条规则后，对应测试必须失败，这才证明断言约束了该规则。

```python
# experiment: E21
from copy import deepcopy
def sorts_in_place(rows):
    rows.sort(key=lambda row: row["cents"])
    return rows
rows = [{"id": "A", "cents": 20}, {"id": "B", "cents": 10}]
before = deepcopy(rows)
result = sorts_in_place(rows)
assert [row["id"] for row in result] == ["B", "A"]
assert rows != before
```

E21 中输出顺序正确，但输入已改变。把它作为反例，而不是推荐实现；若课程要求输入不变，就应增加 `assert rows == before`，让当前实现失败。

## 4. 示例与逐步走查

B10 接收第9章的 A/B：A=Alice、1990 分、paid；B=Bob、1000 分、pending。分三步观察同一份输入。

### 4.1 准备：保存原输入

#### 案例推进：深复制后才能比较副作用

测试先深复制输入，才能在执行后比较；只保留长度无法发现字段或顺序被改。

### 4.2 执行：规则真实运行

#### 案例推进：只汇总 paid 的金额

`summarize` 不过滤未知状态以外的数据，只汇总 status 为 paid 的金额，并统计全部订单。账目规则不交给 mock。

### 4.3 观察：结果和副作用分别断言

#### 案例推进：结果不等或输入改变都应失败

B10 同时断言报告为2单、1990分，以及输入与快照相同。删掉 paid 过滤，金额会变成2990，报告断言失败；把输入排序或改字段，副作用断言失败。

```python
# book-example: B10
from copy import deepcopy
def summarize(orders):
    for order in orders:
        if type(order["amount_cents"]) is not int or order["amount_cents"] < 0:
            raise ValueError("金额必须为非负整数分")
    return {"order_count": len(orders),
            "paid_amount_cents": sum(o["amount_cents"] for o in orders if o["status"] == "paid")}
orders = [
    {"id": "A", "user": "Alice", "amount_cents": 1990, "status": "paid"},
    {"id": "B", "user": "Bob", "amount_cents": 1000, "status": "pending"},
]
before = deepcopy(orders)
assert summarize(orders) == {"order_count": 2, "paid_amount_cents": 1990}
assert orders == before
bad = deepcopy(orders)
bad[0]["amount_cents"] = True
try:
    summarize(bad)
except ValueError:
    pass
else:
    raise AssertionError("坏金额不应进入汇总")
```

输入检查沿用第9章的契约：bool 和负数在汇总前抛 `ValueError`。测试验证这条明确规则，不依赖 `sum` 恰好抛出某种异常。

## 7. 面试问答与迁移

**问：mock 怎样造成假通过？** 把租户检查或业务计算替换成永远成功，测试即使全绿也没验证该规则。替身控制外部变化，核心规则保留真实实现，并检查拒绝、持久状态和失败路径。

**问：单元测试与集成测试如何划分？** 单元测试聚焦局部契约，集成测试观察真实组件组合，例如文件编码、SQL 事务和序列化。边界取决于验证什么，不是只看是否使用 mock；每类都要说明未覆盖范围。

**问：运行环境与依赖锁如何配合？** 锁文件固定解析结果，解释器、操作系统、环境变量和远端服务仍需记录。干净环境安装后从非源码目录运行构建产物，才能暴露漏文件和隐式路径依赖。

**迁移：** 把订单仓储换成 SQLite 后，用临时数据库测试参数化、回滚和重开查询；只 mock 连接会失去这些真实行为证据。

## 8. 本章小结与参考

- 断言应来自需求并覆盖结果、错误和副作用，不能照抄实现表达式。
- 参数化、fixture 和 `tmp_path` 建立可重复条件，替身只替换外部边界。
- 故意破坏规则后测试必须变红，修复后再绿，才能证明故障敏感性。
- traceback、断点和最小输入用于定位，稳定回归测试保存修复证据。
- 日志用标识和白名单字段关联现场；生产校验用显式异常，不靠 assert。
- pytest、静态检查、格式检查和安装验证各回答不同问题，不能互相替代。
