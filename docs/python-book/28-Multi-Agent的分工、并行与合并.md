# 第28章　Multi-Agent 的分工、并行与合并

## 1. 学习目标与前置知识

用受控实验判断协作是否有收益。先有第21、24–25章的同题评测、单 Agent 与任务状态；跨进程共享工具时再接第27章的 MCP。

**承接与本章主线：** 在单流程或单Agent基线之上验证分工与合并收益；同题同预算比较后，再决定是否进入默认业务路径。

**本章从这里开始：** 合同、供应商和制度审查可能独立进行。把它们并行就一定更好吗？先拆清输入输出与失败合并，再用同题集比较质量、成本和延迟。

## 2. 基础知识讲解

### 2.1 多个角色名称不等于多Agent系统

把三项审查同时交给不同角色，可能减少等待，也可能增加遗漏、冲突和成本。多个结果不是一份结论，必须定义谁负责什么、超时代表什么、哪些发现要保留。先明确共同输出与合并规则，再比较分工和并行的增益；角色名称本身不能提供正确性。

同一份采购资料先交给一个Agent审查，记录它具体漏掉哪项检查。若遗漏可按职责分离，再尝试让资格检查与预算检查分别处理，最后合并发现。此时才需要讨论多Agent的输入隔离、分工与冲突。先保留单Agent结果，再用同一批题比较质量、等待和成本；把提示分成多份本身不能证明协作有效。

固定工作流、单Agent、串行专家与并行专家都应保留可比较基线，架构选择以任务表现和维护代价为依据。

### 2.2 分工模式从简单到复杂

Router按任务类型选择一条路径；Supervisor分配并汇总专业任务；Agent as Tool把专业能力暴露为调用边界；Subgraph组织独立局部状态。它们可以组合，但每种都需要说明解决了什么具体问题。

先串行确认资格、预算、合同三个任务各自能产生正确结构，再并行独立部分。存在数据依赖时，不能为了并行提前执行需要后续结果的任务。

#### 案例推进：分工应该改变信息组织

确定每个角色需要哪些输入、工具与权限，产出共同Schema：事实、证据、unknown、发现与失败。若三个角色都得到同样全文、同一错误资料并重复同一提示，它们不一定提供独立信息；不能简单投票提高可信度。

常见结构包括固定流水线、路由选择、并行专家、主管协调和生成-评审。先选能够表达当前依赖关系的最简单结构。下游严格依赖上游时，盲目并行无效；需要共享决策时，拆分也会增加通信与合并成本。

### 2.3 专家必须有共同输出契约

每项结果包含状态、发现、资料缺口、证据、规则版本和来源组件。Aggregator按稳定标识去重并保留独立风险，不能仅拼接几段自然语言。冲突结论应追查证据、日期和规则，而不是靠多数投票消失。

### 2.4 上下文和权限如何隔离

子Agent只获得完成任务需要的材料与工具。隔离可能减少干扰，也可能漏掉跨领域信息，因此要定义共享摘要和证据引用。共享消息列表随意并发修改容易产生状态串联；返回独立更新，再按约定合并。

### 2.5 并行与局部失败

fan-out分发任务，fan-in等待并合并。父子任务各有预算，模型额度和工具连接池可能仍是共享资源。一个专家超时应标partial或needs_review，不可把它的空发现误认定为无风险。

#### 案例推进：先实现可控的并行组织器

```python
# study-example: S28A
import asyncio
async def main():
    async def contract():
        await asyncio.sleep(0)
        return {"expert":"contract", "findings":["缺条款"], "evidence_ids":["C1"]}
    async def supplier():
        await asyncio.sleep(0)
        raise TimeoutError("供应商查询失败")
    values = await asyncio.gather(contract(), supplier(), return_exceptions=True)
    good = [v for v in values if not isinstance(v, BaseException)]
    errors = [type(v).__name__ for v in values if isinstance(v, BaseException)]
    report = {"status":"partial" if errors else "completed", "results":good, "errors":errors}
    assert report["status"] == "partial" and report["errors"] == ["TimeoutError"]
    assert len(report["results"]) == 1
asyncio.run(main())
```

示例只有异步函数，验证并行与局部失败策略，尚未证明多Agent的决策收益。选择return_exceptions是为了保留完成结果；若需求是任一失败就整体停止，应选择相应的取消与清理策略。partial不能在最终汇总时被改写为“全部通过”。

### 2.6 核验与有限返工

Evaluator先检查结构、引用和确定性规则，再用模型辅助发现缺口。返工针对具体问题，限制次数和总预算。Evaluator本身也可能错，因此保留人工标签和原证据，并比较其实际增益。

#### 案例推进：冲突要回到证据而非措辞

两个专家金额不一致，先核对来源与版本；一个说未知、另一个说合规，不应把未知当成反对票或忽略。汇总保留缺失项和冲突，必要时交复核。评审返工必须受次数、总时限和成本预算约束，避免无限讨论。

比较固定流程、单Agent、并行专家和带评审方案时，使用相同题集与尽可能一致预算。记录质量、实际调用数、延迟、token与人工复核率，保留简单方案作为回退。

## 3. 原理讲解与推导

### 3.1 分工改变信息，并行改变时间安排

两种变化影响不同。先验证分工是否准确，再测并行能否减少端到端时间；若共享额度导致排队，总延迟可能并未改善。

### 3.2 合并需要稳定的语义

追加列表、按ID去重、覆盖状态是不同合并规则。并发完成顺序变化不应随意改变风险结论；若规则依赖顺序，要明确这种依赖并测试。

### 3.3 保留基线才能判断复杂度是否值得

同数据、身份、模型和总体预算下比较各架构，逐题记录质量、引用、失败、用量与延迟。没有收益时回到单Agent，是合理结论而不是学习失败。

## 4. 示例与逐步走查

### 合并结构化专家结果

```json
{"task_id":"T1","parts":[{"agent":"budget","status":"completed","findings":[{"code":"OVER_BUDGET","source_id":"P200"}]},{"agent":"contract","status":"timeout","findings":[]}],"status":"partial"}
```

Aggregator保留预算发现并标记合同审查未完成。不要因为超时部分为空，就把它理解为没有合同风险。再比较串行/并行的同一批任务和总体预算。

### 4.1 沿输入到结果逐步解释

预算专家返回超预算发现，合同专家超时且findings为空。合并器应保留预算发现，并把整体标记partial，因为合同的空列表来自没有完成检查，而非检查后确认无问题。

若另一个专家对同一结论给出不同依据，应保存冲突并追查版本和规则，不能让多数票消除证据差异。合并输出需要与子任务状态一起解释。

让完成顺序反转后，结果应保持相同风险与缺口。若结论随到达顺序任意改变，说明合并规则还没有被定义清楚。

## 5. 动手练习

### 本章累计任务：用基线约束多角色

用同一题集比较单流程与分工，故意让一个角色超时并反转完成顺序；合并保留所有发现、冲突与缺口，总时限和费用受限。

**未通过时怎样定位：** 部分为空可能是没完成，不是没风险；多数票不消除证据冲突；只有成本增加没有收益时不采用。

**带到下一步：** 将是否采用及其证据带到第29–30章解释。

下方专题练习用于补当前卡点；先完成这一项累计任务，不另将所有索引作为必须并行完成的进度。

### 练习一：明确分工契约

为合同、供应商与制度三个角色定义输入、输出、证据ID、unknown与失败状态。尽量限制每个角色的上下文；先用固定数据运行，再引入模型。

### 练习二：四组公平对照

比较固定流程、单Agent、并行专家、并行加评审方案。使用同一题集，记录质量、调用、token、延迟与复核率；说明预算差异，不能用更多资源带来的收益直接证明分工更优。

### 练习三：合并与退出

一个专家超时应保留其他结果并明确partial；两名专家金额冲突应回查来源或交复核，不能多数投票改写事实。评审始终要求返工时，达到次数或总时限后停止。提交冲突、超时与有界退出的轨迹。

## 8. 本章小结与参考

### 8.1 主要知识点总结

- 多个Agent需要清楚的职责、输入、工具权限与结果契约。
- 串行与并行有不同等待、资源和局部失败行为，合并需要稳定标识。
- 冲突保留证据与来源，评估和返工有明确次数与预算。
- 相对单Agent的收益通过同题质量、延迟、成本和维护代价验证。

### 8.2 日常工作注意事项

- 子任务优先返回独立结果再合并，避免多个Agent并发修改同一个列表或直接重复写业务记录。
- 合并按稳定ID去重并保留冲突，不能把多数意见直接当成事实或批准。
- 一个子任务失败时说明结果完整性；取消后等待清理，资源和费用预算同时覆盖全部子任务。
