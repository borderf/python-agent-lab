# 第25章　Multi-Agent 的分工、并行与合并

[上一章](24-mcp.md) · [全书目录](README.md) · [下一章](26-ai-quality.md)

## 1. 学习目标与前置知识

用受控实验判断协作是否有收益。前置：第21–24章。

## 2. 基础知识讲解

Router 选择处理路径，Supervisor 组织专业任务，Agent as Tool 将专业能力暴露为调用边界，Subgraph 封装局部状态。多个角色名称本身不会产生质量提升。

先串行验证资格/预算/合同输出契约，再并行独立任务。fan-out/fan-in 需要定义子任务预算、上下文隔离、局部失败和结果合并；reducer 应保持预期的合并性质，避免顺序变化破坏结果。

Evaluator–Optimizer 针对明确缺口做有限返工；证据核验先做程序约束，再用模型辅助。冲突不能简单按多数投票消除，必须保留来源、版本和不确定性。

## 3. 原理讲解与推导

并行改变执行安排，分工改变信息和决策结构；二者要分别测量。使用同一数据与总预算比较固定流程、单Agent、串行专家、并行专家和有限返工。

### 项目化展开

#### 单 Agent 与多 Agent

基线 A 为固定工具工作流，B 为单 Agent。之后分别实验 C 串行专家、D 并行专家、E 有限核验返工。资格/预算/合同专家共享结果 Schema，但仅获得各自需要的上下文与工具。

合并器保留所有独立风险与资料缺口；按稳定 finding_id 去重；同一问题依据不一致时保留冲突。一个专家失败只可产出 partial/needs_review，不应凭另外两个专家的“通过”推断整体完成。

补充调查只针对具体缺口；次数、总时限、模型用量都有上限。相同评测集未发现收益时，将复杂版本保留为实验，默认业务路径采用更容易解释和维护的方案。

### 四、组件怎样演进

建议先按模块划分 document、retrieval、review、tools、model_adapter、tasks、evaluation。业务规则只维护一份，本地工具、MCP 和 API 都调用它。

W16 最小部署可先是一个 API 进程、PostgreSQL、Qdrant，加所选模型服务配置；MCP 有独立运行要求时再加入，追踪平台另用可选配置。Langfuse 自托管应使用并核对其官方部署栈和资源要求，不能假设只是多加一个轻量容器。

交付说明写清当前是模块还是独立服务、依赖启动顺序、数据目录、密钥注入、健康检查、备份方式、已测试负载和明确限制。原型完成后再安排真实权限设计、安全评审、容量和长期运维验证。

### 合并与并行的工程代价

专业Agent输出统一结构：风险、资料缺口、证据ID、规则版本、来源组件与错误。Aggregator按稳定标识去重，保留互相冲突的证据，而不只拼接文本。子任务失败时总状态应表达partial或needs_review。

并行上限是全局资源预算的一部分；多个Agent共享同一模型额度和工具池，会产生排队与竞争。Evaluator增加的不只是质量，也有token、延迟和错误机会，应限制返工并用相同集比较。

## 4. 示例与逐步走查

### 合并结构化专家结果

```json
{"task_id":"T1","parts":[{"agent":"budget","status":"completed","findings":[{"code":"OVER_BUDGET","source_id":"P200"}]},{"agent":"contract","status":"timeout","findings":[]}],"status":"partial"}
```

Aggregator保留预算发现并标记合同审查未完成。不要因为超时部分为空，就把它理解为没有合同风险。再比较串行/并行的同一批任务和总体预算。

## 5. 动手练习

完成四组对照；模拟一个专家超时和一个证据冲突；达到次数/时限上限后交复核。

## 6. 验收与自测

**行为验收：** 局部失败不伪装整体通过；结果结构可合并；质量、耗时和用量均有逐题记录；无收益可回退。

**原理验收：** 合上资料解释本章一个机制，预测一个反例，说明规则属于语言语义、库约定还是实现观察。

**提交证据：** 实现位置、运行命令、正常案例、至少一个错误/边界案例、一次失败原因和修复记录。自动检查只证明其覆盖行为；未实现任务不因示例通过而算完成。
