## 1. 学习目标与前置知识

能证明检索策略是否改善效果，并解释代价。前置：第20章。

**承接与本章主线：** 以固定问题和相关来源比较召回、融合与排序；将错误定位到具体阶段，再把结果用于第22–23章的评测与交付。

**本章从这里开始：** 向量检索漏掉制度编号，关键词检索又不擅长同义表达。混合方案可能有用，但必须用同一批题证明收益，并知道错误发生在哪一层。

## 2. 基础知识讲解

### 2.1 为不同检索信号建立基线

先比较两道题：“制度POL-17写了什么”和“付款前最多能先付多少”。第一题依赖精确编号，第二题可能使用与原文不同的表达。先分别运行词项匹配与稠密向量检索，记录每道题漏掉什么，再决定是否融合。前者侧重词项信号，后者利用向量表示；哪一种更好需要同题验证，不能从名称判断。

两条路径的候选数、过滤条件和去重单位应记录。改变候选范围可能已经改变召回，不应把所有收益都归给后加的融合算法。

#### 词项频率、文档频率和长度归一化

同一文档反复出现查询词是词频tf；有多少文档含该词是文档频率df。一个几乎所有文档都出现的词区分力弱，少见的制度编号可能区分力强，这促成IDF等权重。BM25进一步让tf贡献趋于饱和，并按文档长度相对平均长度调整，避免长文档仅因词多而占优。

常见形式中，某词贡献近似为`IDF * tf*(k1+1)/(tf+k1*(1-b+b*length/avg_length))`；不同实现的IDF等细节可能不同。k1调节饱和，b调节长度影响，参数是模型选择而非业务真理。中文还需要实际分词/分析器策略，不能把英文按空格拆分直接当作通用中文检索。

稠密向量可弥补同义表达，但也可能忽略精确编号；重排模型联合比较问题与候选，增加相关性判别代价。先解释每种信号为什么可能失败，再进行融合对照，比分别背定义更容易选方案。

### 2.2 融合解决什么问题

直接相加不同检索分数，可能因尺度不一致偏向某一来源。RRF用各路径的排名贡献分数，常见形式为对1/(k+rank)求和，rank从1开始。它避免直接依赖原分数尺度，但仍需确定参数、重复项和并列规则。

#### 案例推进：手算再实现排名融合

```python
# study-example: S21A
def rrf(rankings, constant=60):
    scores = {}
    for ranking in rankings:
        for rank, item in enumerate(dict.fromkeys(ranking), start=1):
            scores[item] = scores.get(item, 0.0) + 1 / (constant + rank)
    return sorted(scores, key=lambda item: (-scores[item], item))

assert rrf([["A", "B"], ["B", "C"]]) == ["B", "A", "C"]
```

B在两个列表都出现，因此得到两项贡献；A与C各一项，按其名次分开。这里候选身份以字符串表示，真实系统应使用稳定chunk_id或明确的文档级身份。同一列表重复不应反复增加投票，去重策略与截取深度要在实验中固定。

### 2.3 重排处理已有候选

Reranker对查询与候选相关性进行更精细判断，再选较小集合进入提示。它可能增加质量，也增加计算与等待。若正确证据根本未进入候选，重排不能凭空补回。

候选数量与重排模型应作为实验变量，别一次同时换分块、embedding和重排器后就宣称某个组件有效。

#### 案例推进：区分融合和重排

BM25等关键词信号强调词项匹配，稠密向量强调学习到的语义表示；融合整合多路候选。重排在已有候选上进一步打分，常用query与候选联合建模的模型，代价通常高于第一阶段广泛检索。根本没召回的证据，重排无法凭空补回。

比较时固定语料、过滤、题集和预算，逐题检查解析→召回→排序→生成→引用。留出未参与调参的验证题，记录质量、延迟和成本。小样本结果不能外推成普遍提升百分比，方案没有收益时保留简单基线。

### 2.4 先定义标准答案与粒度

固定问题对应允许访问的相关来源，注明日期与版本。按source_id还是chunk评估要一致；同一来源多个chunk如何去重也需说明。无答案和越权案例单列，不能硬塞进有相关来源的召回率分母。

Recall@K检查是否找到了标准来源，引用正确性检查引用是否支持对应结论，生成忠实性检查模型是否遵循证据。三者不同，不能用一个指标覆盖全部质量。

#### 案例推进：用分母理解指标

```python
# study-example: S21B
relevant = {"A", "B"}
retrieved = ["C", "A", "D"]
recall = len(set(retrieved[:3]) & relevant) / len(relevant)
precision = len(set(retrieved[:3]) & relevant) / 3
first_rank = next((i for i, item in enumerate(retrieved, 1) if item in relevant), None)
reciprocal_rank = 0 if first_rank is None else 1 / first_rank
assert recall == 0.5 and precision == 1/3 and reciprocal_rank == 0.5
```

Recall看需要的证据找回多少，Precision看返回项中相关多少，MRR聚合多个问题的首个相关位置倒数。无相关证据题不能随意把Recall分母设为0后忽略，应另测拒答行为。分级相关性可使用带位置折扣的nDCG，先定义标注与理想排序再计算。

### 2.5 用逐题误差分析指导改进

先分出解析/入库缺失、召回缺失、排序靠后、版本错误与生成偏离，再对问题最多的一类改进。保留未用于调参的验证题，记录样本数、延迟、用量和环境。少量题适合练习，不代表生产泛化已经验证。

### 2.6 一个不用读问题也能拿满分的检索器

某租户今天只有三个可见来源，标准答案在其中。每次都返回这三个来源，无论问什么，Recall@5 都是 1。增加同义问题也无法用它区分排序优劣。现有语料加入了预付款退回、票据与预算变更等同期材料。“预付款上限”和“退回预付款要留什么”都能匹配付款字样，所需依据却不同。

运行 `uv run python -m practice.enterprise_ai.retrieval_baseline`。读 `archive_deadline` 的两行输出，手算为什么来源从第 2 名升到第 1 名会提高倒数排名，却不改变 Recall@5。再看 `two_steps`，需要两份来源，只命中其中一份时召回为 0.5，即使第一名已经相关。然后把一条候选列表换成 A、A、B，解释本章两处 RRF 示例为什么都先去重再编号。[离线对照操作与分母](../project-practice/评测与故障演练.md#先跑一个离线对照)

## 3. 原理讲解与推导

### 3.1 流水线错误有不同位置

正确来源没入库，调整rerank没有意义；来源在候选却进不了上下文，才需要考察排序与截断。把阶段产物导出，就能观察错误在哪一步首次发生。

### 3.2 受控对照才能解释收益

数据、身份、日期、模型与总预算保持可比，先改变一个变量；每个版本既记录收益也记录代价。最终默认方案可以是简单基线，而不是组件最多的一版。

## 4. 示例与逐步走查

### 按排名融合的机制示例

```python
# book-example: B21
def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:
        for position, source_id in enumerate(dict.fromkeys(ranking), 1):
            scores[source_id] = scores.get(source_id, 0) + 1/(k+position)
    return sorted(scores, key=lambda sid: (-scores[sid], sid))
assert rrf([["A","B"],["B","C"]])[0] == "B"
```

每条排名先去重，结果并列按ID固定顺序。本示例未执行向量检索；真实融合前还要统一权限、版本与候选范围。比较是否改善Recall与引用支持性，而不只看融合分数。

### 4.1 沿输入到结果逐步解释

RRF示例中B在两条排名都出现，累计贡献超过只出现一次的A或C，因此排第一。它展示排名融合机制，不证明这组候选对真实问题更相关；必须再用标准来源标签与生成结果验证。

## 5. 动手练习

### 把手算向量换成真实 embedding

先跑上一节的离线基线。准备本机 Ollama 服务，用 `ollama list` 确认已安装的模型标签。选择支持中文和 embedding 的模型作为编码器；额外比较生成式重排时，再选择一个支持 JSON 输出的聊天模型。以下标签是占位值，需换成自己机器上的名称。脚本只调用本机服务。

```powershell
$embedModel = '替换为已安装的嵌入模型标签'
uv run python -m practice.enterprise_ai.vector_compare --embed-model $embedModel
$chatModel = '替换为已安装的聊天模型标签'
uv run python -m practice.enterprise_ai.vector_compare --embed-model $embedModel --rerank-model $chatModel
```

1. 查看 `eligible_sources` 之后的候选。相同的租户、日期和可信制度范围适用于所有方法。问题和可见原文送去编码，标准来源只留给评分端。记录模型标签、实际版本和语料版本。
2. 看 `unit_vectors` 如何检查数量、有限值及非零范数，再归一化。向量点积此时等于余弦相似度。这里是小语料上的精确扫描，换近似索引时可以用这份结果检查索引漏掉了什么。
3. 对照字面匹配、稠密召回、两者排名融合三行结论。选一道同义改写和一道精确编号题，导出前五来源，找出正确来源首次掉到第几名。融合只使用名次；来源是否满足日期条件在融合前已决定。
4. 可选重排把融合前六名连同问题交给聊天模型，校验返回值是候选的完整排列，再评前五。正确来源在第七名时，这个操作无法把它提到第一名。若要比较交叉编码器，保持这六个候选相同，再用问题与每一条文档配对打分。
5. 固定参数后加 `--split holdout` 运行。写下哪一种方法值得采用及原因。在同一环境另测冷启动和热请求，分别计入索引构建、问题编码与重排。脚本进程内会复用已算的文本向量，整条命令的耗时不能充当单次线上延迟。

还可自制一份两页制度和一张含例外条件的表格，分别标正确页、有效期及所需条款。将第 19 章的解析结果接入同一检索接口，新增一条必须从表头和数据行合并取证的题。比较改分块和改模型各自修好了哪类错误。[实验代码](../../practice/enterprise_ai/vector_compare.py) · [Ollama embedding 协议](https://docs.ollama.com/api/embed)

### 练习一：相同条件四组对照

在相同语料、身份过滤、问题集与候选预算下比较关键词、向量、融合、融合加重排。明确候选去重键与rank起点，先用小列表手算RRF验证实现，再运行实际数据。

### 练习二：指标和逐题根因

写清相关证据的文档/块粒度，计算适用的Recall@k、MRR等指标，记录无证据、权限与版本案例。逐题标记解析、过滤、召回、排序、生成或引用失败，不能只给一个总分。

### 练习三：采用与回退

为候选方案记录质量、耗时和资源代价，说明是否值得采用。保留未用于调参的验证题；重排没有改善时允许保持基线。小样本结果说明样本数量与局限，不外推成普遍收益。
