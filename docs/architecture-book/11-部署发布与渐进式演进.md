# 第11章　部署发布与渐进式演进

[上一章](10-安全多租户与隐私边界.md) · [本书目录](教材目录.md) · [下一章](12-AI系统架构与技术选型.md)

## 1. 目标、前置与问题

前置：第7、9章。能设计可追溯构建、兼容发布和数据迁移。问题：代码回滚成功，为什么服务仍可能无法恢复？

**本章主线：** 先固定可识别产物，再设计新旧版本共存窗口；数据按扩展、迁移、收缩推进，每一步都保留停止条件和可回退范围。

## 2. 概念与基础

### 2.1 构建、部署与发布不是同一动作

**构建**把代码与依赖整理成有版本的可运行产物；**部署**把产物与配置、密钥放入环境并启动；**发布**让真实流量或用户开始使用新版本。CI自动执行检查，CD组织交付或部署流程。

为什么分开？同一个镜像可以在测试环境部署而不发布给用户；同一版本也可能重新部署。若只记录“上线成功”，无法判断流量是否切换、数据是否迁移、外部效果是否已发生。

| 动作 | 输入 | 输出 | 必须留下 |
| --- | --- | --- | --- |
| 构建 | 源码、依赖、构建配置 | 镜像或包 | 版本、摘要、构建记录 |
| 部署 | 产物、环境配置、密钥引用 | 运行实例 | 实例版本、配置版本 |
| 发布 | 就绪结果、流量规则 | 用户开始使用新版本 | 时间、范围、停止条件 |

容器帮助封装运行环境，但不能自动解决数据迁移、权限与业务验证。密钥应在运行时由受控渠道注入，不写入镜像或普通日志。

### 2.2 滚动、蓝绿、金丝雀与功能开关

**滚动发布**逐步替换实例；**蓝绿**保留两套环境并切换流量；**金丝雀**先向小范围暴露；**功能开关**把代码部署与功能开放分离。

它们都减少一次性暴露范围，但新旧版本会共存。共存期间必须处理数据、接口和任务兼容；切换流量快不等于数据库可以回滚。

| 方式 | 主要收益 | 主要风险 | 关键检查 |
| --- | --- | --- | --- |
| 滚动 | 不需双倍完整环境 | 新旧实例长时间共存 | 混合版本读写 |
| 蓝绿 | 流量切换与回退直接 | 双环境数据同步 | 共享数据与外部副作用 |
| 金丝雀 | 小范围验证真实影响 | 路由复杂、样本偏差 | 分层指标与自动停止 |
| 功能开关 | 不发布也能关闭功能 | 开关长期堆积 | 负责人、默认值、清理期限 |

金丝雀流量应覆盖关键租户或风险场景，不能只按随机百分比。越权、数据核对失败等严重信号应直接停止，而不是等平均指标变差。

### 2.3 可识别产物与配置版本

**可追溯产物**能从运行实例反查源码版本、依赖与构建配置。仅用 `latest` 标签无法判断故障实例究竟运行哪份代码。

环境配置也要版本化并受控，包括功能开关、连接端点、超时和索引配置。密钥值不进入普通版本记录，但密钥标识、轮换时间与使用范围需要审计。

最小交付清单：源码提交、依赖锁、构建命令、产物摘要、镜像或包版本、配置版本、迁移版本、验证记录。任一项缺失都会缩小故障时的可定位范围。

### 2.4 可回退范围随步骤缩小

回滚前要问：哪些步骤可逆，哪些已经产生外部效果？代码切回旧镜像可逆；已写数据、已发消息与已执行外部动作不一定可逆。

**扩展—迁移—收缩**先增加兼容结构，再回填并验证，再切换读写，最后删除旧结构。删除旧结构后，旧代码可能无法运行，可回退范围随之改变。

| 阶段 | 应用版本 | 数据状态 | 回退选择 |
| --- | --- | --- | --- |
| 扩展 | 新旧可共存 | 旧结构＋新兼容结构 | 回退代码，保留新结构 |
| 迁移 | 双写或分批回填 | 新旧值混合 | 暂停、修复、幂等续跑 |
| 切换 | 新版本主导 | 新路径已验证 | 切回兼容读路径或前向修复 |
| 收缩 | 不再支持旧协议 | 旧结构已删除 | 不能假设直接回旧代码 |

## 3. 机制与推导

### 3.1 发布必须覆盖混合运行窗口

发布期间经常同时存在旧应用、新应用、旧数据与迁移中的数据。只测试最终新版本，会漏掉旧实例读新字段、新实例读旧记录、重复消息等中间状态。

机制推导：实例替换不是原子动作；数据回填也不是瞬间动作。两条时间线交错，就产生组合状态。发布计划应列每个交错的时点，而不是只写最终目标图。

例如新增负责人字段后，旧应用忽略它，新应用允许为空；回填中新应用可能读到“待指定”；切换后才要求必填。每一步都要有可观察状态与负责人。

### 3.2 扩展、迁移、收缩的数据顺序

新增非空字段若旧记录没有值，可能立即失败。先允许空或提供有业务意义的兼容路径，不能随意用假值填满；否则应用无法区分“未知”与“确实没有”。

回填应分批、可重入、可恢复。重复执行不能覆盖已人工确认的值；每批记录数量、失败与校验结果。全部回填后还要核对总数、未分配数与来源关联。

```mermaid
flowchart LR
    A[新增兼容结构] --> B[旧新版本共存]
    B --> C[回填与核对]
    C --> D[切换读写]
    D --> E[观察旧消费者退出]
    E --> F[收缩旧结构]
```

切换前先验证旧脚本、消息消费者与报表是否退出。仍有旧消费者时删字段，会把发布问题推迟成生产故障。

### 3.3 回滚要处理数据与外部副作用

代码回滚只改变程序，不会撤回已写数据、已发消息与外部动作。不可逆步骤需要前向修复、隔离备份或受控窗口。

若迁移中途失败，优先暂停切换、保留新结构、修复回填后幂等续跑。不要为了“回到原样”删除已经写入的新数据，那可能丢失人工修正与审计记录。

| 已发生 | 切回代码能否撤销 | 应对 |
| --- | --- | --- |
| 新字段已写入 | 否 | 保留兼容结构，前向修复 |
| 消息已发送 | 否 | 接收方去重与对账 |
| 外部动作已完成 | 否 | 补偿或人工核对 |
| 仅流量已切换 | 通常可切回 | 同时检查数据版本兼容 |

### 3.4 就绪、停止与恢复构成发布闭环

交付链包括可识别产物、配置与密钥注入、迁移、就绪检查、关键任务、监控和停止条件。容器启动或端口开放只是其中一环。

**就绪条件**是允许接收流量的最低要求；**停止条件**是出现哪些信号立即暂停；**恢复条件**是确认哪些检查通过后再继续。三者应在发布前确定，不能故障中临时投票。

严重越权、迁移核对失败和未知副作用属于停止信号。普通延迟升高可先缩小金丝雀范围；不可逆错误则可能需要前向修复而非回滚。

## 4. 案例逐步推演

DocPilot要给文档增加“负责人”。先新增可空字段，新代码对旧记录显示“待指定”，旧代码仍能读取原字段。随后分批回填，核对未分配数和来源关联，再启用依赖负责人的新流程。

**输入：** 一万份文档，其中两千份没有负责人。**变化：** 加可空列、回填、切换新流程。**输出：** 旧记录可读，未指定者显示待指定，人工确认值不被重复回填覆盖。

若回填一半停止，应用仍须读到旧资料；重跑不能覆盖已人工确认的负责人。若新界面有问题，回退兼容代码并保留新字段。等旧实例与旧脚本退出后，才考虑更强约束与旧字段清理。

**失败定位：** 旧实例启动失败，检查是否新增了必填列；重复回填覆盖人工值，检查更新条件；新流程找不到负责人，检查未分配数与迁移批次；回滚后仍失败，检查数据是否已不兼容旧代码。

按[带旧数据迁移实验](附录E-实测案例与推导.md#一次带旧数据的迁移)复现现有迁移，再做自己的字段。发布门槛包括旧数据可读、关键任务成功、拒绝样本通过；停止门槛包括越权、迁移核对失败和未知副作用。

### 4.1 列出每个中间状态，而不只写上线步骤

| 时点 | 旧应用 | 新应用 | 数据 | 可恢复动作 |
| --- | --- | --- | --- | --- |
| 扩展后 | 仍读旧字段 | 允许负责人为空 | 新列已加、未回填 | 回退代码并保留列 |
| 回填中 | 继续工作 | 显示待指定 | 新旧记录混合 | 续跑幂等回填 |
| 切换后 | 逐步退出 | 使用新字段 | 核对未完成数 | 关闭新读路径或前向修复 |
| 收缩后 | 不再兼容 | 仅新协议 | 旧结构已清理 | 不能假设直接回旧代码 |

注意最后一步改变了可回退范围。发布批准者要知道此时回滚不再只是切镜像。对于索引，还需保存配置、来源版本和切换点，确认旧索引仍受当前权限限制。

验收一轮中途停止的发布，比只执行完一次更能发现恢复问题。带着旧数据、旧客户端与重复执行的迁移重新检查，才能验证兼容计划。

### 4.2 离线推演扩展、回填与收缩

```python
# track-example: A11
records = {
    "d1": {"title": "采购制度", "owner": None, "confirmed": False},
    "d2": {"title": "验收规范", "owner": "u2", "confirmed": True},
}

def backfill(rows, assignments):
    changed = 0
    for doc_id, owner in assignments.items():
        row = rows[doc_id]
        if row["owner"] is None and not row["confirmed"]:
            row["owner"] = owner
            changed += 1
    return changed

assert backfill(records, {"d1": "u1", "d2": "u9"}) == 1
assert backfill(records, {"d1": "u1", "d2": "u9"}) == 0
assert records["d1"]["owner"] == "u1"
assert records["d2"]["owner"] == "u2"

legacy_can_read = all("title" in row for row in records.values())
new_can_read = all(row["owner"] is not None for row in records.values())
assert legacy_can_read and new_can_read
```

第一次回填只修改未确认的空记录；第二次改变0条，已确认的d2不被覆盖。这验证幂等条件，不验证真实数据库锁与迁移。收缩前仍要检查旧实例和旧脚本退出，代码回退也不能撤销已写负责人。

## 5. 分层练习

1. **基础**：写出新增、回填、切换、清理四个时点的应用与数据版本，并给每处新增字段选择兼容默认语义。
2. **改造**：在回填中间停止一次，再重复运行；验证未分配数、人工确认值与旧应用读取。
3. **独立**：设计一次含流量切换和外部动作的发布，明确停止条件、前向修复与不能回滚的部分；用新会话完成关键任务。

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 代码回滚成功了，为什么服务仍可能无法恢复？

**一条主线：** 可识别产物 → 混合版本兼容 → 扩展、回填、切换 → 确认旧消费者退出后收缩。

**三个关键词：** 混合版本、迁移顺序、可回退范围。共存要求行为兼容；迁移顺序决定中途能否停；收缩改变可回退范围。

**最容易错：** 先删字段；回滚只写git revert；用假值填新字段；回填不可重入；只测最终版本；把流量切换当数据回滚。

**学完应能：** 写四时点版本表；中途停止并幂等恢复；说明哪些已发生事实不能靠回滚撤销。
