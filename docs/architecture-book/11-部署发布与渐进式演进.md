# 第11章　部署发布与渐进式演进

[上一章](10-安全多租户与隐私边界.md) · [本书目录](教材目录.md) · [下一章](12-AI系统架构与技术选型.md)

## 1. 目标、前置与问题

前置：第7、9章。能设计可追溯构建、兼容发布和数据迁移。问题：代码回滚成功，为什么服务仍可能无法恢复？

## 2. 概念与基础

构建产物应可识别版本，配置和密钥在环境中管理。CI验证代码与契约，CD组织发布；自动部署不代表必须自动发布给所有用户。容器封装运行环境，编排解决调度等问题，不能自动消除数据和业务风险。

滚动发布意味着新旧版本共存；蓝绿使用两套环境切换；金丝雀先向小范围暴露。每种方式都需要兼容、指标、停止条件和回退。功能开关将部署与功能开放分离，也需要负责人和清理期限。

## 3. 机制与推导

发布期间经常同时存在旧应用、新应用、旧数据与迁移中的数据。只测试最终新版本会漏掉中间状态。兼容发布需要设计这段混合运行窗口，而不是期望所有实例瞬间一起替换。

扩展—迁移—收缩先增加兼容结构，再回填并验证，再切换读写，最后才删除旧结构。新增非空字段若旧记录没有值，可能立即失败；先允许空或提供有业务意义的兼容路径，不能随意用假值填满。

```mermaid
flowchart LR
    A[新增兼容结构] --> B[旧新版本共存]
    B --> C[回填与核对]
    C --> D[切换读写]
    D --> E[观察旧消费者退出]
    E --> F[收缩旧结构]
```

回滚代码只改变程序，不会撤回已经发送的消息、已写的数据与外部动作。不可逆步骤要准备前向修复、隔离备份或受控窗口。把索引切换与数据库迁移分开记录，避免一次回滚涉及不明状态。

交付链包括可识别的产物、配置与密钥注入、迁移、就绪检查、关键任务、监控和停止条件。容器启动或端口开放只是其中一环。

## 4. 案例逐步推演

DocPilot 要给文档增加“负责人”。先新增可空字段，新代码对旧记录显示“待指定”，旧代码仍能读取原字段。随后分批回填，核对未分配数和来源关联，再启用依赖负责人的新流程。

若回填一半停止，应用仍须读到旧资料；重跑不能覆盖已人工确认的负责人。若新界面有问题，回退兼容代码并保留新字段。等旧实例与旧脚本退出后，才考虑更强约束与旧字段清理。

按[带旧数据迁移实验](附录E-实测案例与推导.md#一次带旧数据的迁移)复现现有迁移，再做自己的字段。发布门槛包括旧数据可读、关键任务成功、拒绝样本通过；停止门槛包括越权、迁移核对失败和未知副作用。

### 4.1 列出每个中间状态，而不只写上线步骤

| 时点 | 旧应用 | 新应用 | 数据 | 可恢复动作 |
| --- | --- | --- | --- | --- |
| 扩展后 | 仍读旧字段 | 允许负责人为空 | 新列已加、未回填 | 回退代码并保留列 |
| 回填中 | 继续工作 | 显示待指定 | 新旧记录混合 | 续跑幂等回填 |
| 切换后 | 逐步退出 | 使用新字段 | 核对未完成数 | 关闭新读路径或前向修复 |
| 收缩后 | 不再兼容 | 仅新协议 | 旧结构已清理 | 不能假设直接回旧代码 |

注意最后一步改变了可回退范围。发布批准者要知道此时回滚不再只是切镜像。对于索引，还需保存配置、来源版本和切换点，确认旧索引仍受当前权限限制。

验收一轮中途停止的发布，比只执行完一次更能发现恢复问题。带着旧数据、旧客户端与重复执行的迁移重新检查，才能验证兼容计划。

## 5. 分层练习

先完成：写出新增、回填、切换、清理四个时点的应用与数据版本；在中间时点停止一次并恢复。不要只画最终部署图。用新的会话完成一次完整任务，并记录发布停止条件。

## 6. 自测与参考推导

<details><summary>完成独立任务后查看诊断</summary>

若方案是“先删字段，再启动新代码”，旧实例会立即受影响。若回滚说明只有 git revert，尚未处理数据和外部效果。若回填不能重复运行，中途失败就无法可靠续接。

</details>
