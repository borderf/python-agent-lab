# 架构实验与评审实操

[本书目录](教材目录.md) · [模板](附录A-工作簿与模板.md)

这是章节练习的执行说明。按前置逐项推进，每项记录假设、输入、环境、预期、实际和限制。SQL以PostgreSQL设计为目标，数据库实验需自行准备隔离环境；本地SQLite样例不替代其行为。

缺少评审输入时，使用[虚构原始材料包](../../practice/case_studies/README.md)：请求样本、有缺陷的ADR与分开存放的反馈。先独立做决定再对照，不把参考推导当实测。恢复实现另有[6步学习者契约](../../tests/learner/练习说明.md)，可以检验你自己的任务状态机。

## 实验一：从要求到ADR（第1–4章）

输入：“三个团队查询制度，偶尔上传资料，两人维护”。先列缺失问题：资料、授权、更新、负载、模型失败和部署限制。不要根据团队数臆造流量。

1. 写三个质量场景，明确触发、响应和验证方式。
2. 画系统上下文与逻辑组件两张图，标记信任边界。
3. 对比模块化单体与服务拆分，写一份ADR。
4. 加入条件“数据处理必须独立隔离”，重新判断并保留原决定。

参考推演：新隔离约束可能使独立进程或网络边界成为必要；是否独立服务还要看部署与职责。优秀答案应能指出变更原因，而非始终坚持某种架构。

验收：另一位学习者能从材料中找到关键未知、方案代价和下一次实验。

## 实验二：并发修改与数据库约束（第5章）

下面是独立教学表，包含建表与初始数据。只在练习数据库执行；该片段尚未在真实PostgreSQL环境代你验证。

```sql
CREATE TABLE architecture_lab_task (
  id TEXT PRIMARY KEY,
  status TEXT NOT NULL,
  version INTEGER NOT NULL CHECK (version >= 0)
);
INSERT INTO architecture_lab_task VALUES ('T', 'pending', 7);
```

两个会话先各自读取版本7。会话A执行条件更新并提交，再由B执行相同更新：

```sql
UPDATE architecture_lab_task
SET status = 'approved', version = version + 1
WHERE id = 'T' AND status = 'pending' AND version = 7;
```

预测：A影响1行，B影响0行。B应报告竞争并重新读取，而非返回批准成功。然后用相同输入重试，解释它为何不再满足条件。再加审计记录，要求状态与审计在同一事务提交。

挑战：改成两条记录共同保护一个不变量，解释单记录版本号不足在哪里。自行选择锁或更强隔离，并处理失败重试；实际结论记录数据库版本与隔离级别。

## 实验三：幂等、崩溃与远端未知（第4、7章）

先看 [idempotency_sqlite.py](../../practice/architecture_labs/idempotency_sqlite.py) 的第一部分，核对同键重放、不同载荷、作用域和回滚。这一部分的账本与效果在同一个本地事务提交。

同一脚本的第二部分用两个独立 SQLite 文件模拟客户端和业务服务。在仓库根目录运行：

```powershell
uv run --frozen python -m practice.architecture_labs.idempotency_sqlite
```

运行前把纸分成“本地待办、远端效果、调用者看到什么”三列。沿下表预测，再对照程序输出和两个数据库中的行。动作键由客户端在发送前持久化。远端在自己的事务中保存动作键与效果；两个库各自提交。

| 停止的位置 | 本地待办 | 远端效果 | 恢复者能依据什么作决定 |
| --- | --- | --- | --- |
| 登记后、发送前 | 有动作键和原载荷，缺回执 | 0 | 读取原请求，以同键投递 |
| 远端提交后、回执落地前 | 同样缺回执 | 1 | 单看本地无法区分前两行。按同键同载荷查询或重试，远端返回原回执 |
| 恢复并保存回执后 | 有回执 | 1 | 对比两端效果 ID；再次扫描待办时跳过已确认的行 |

实作先模拟丢弃回执、关闭连接，再从磁盘重开恢复。把恢复时使用的键改成新键，在临时库实验里观察唯一效果断言失败，解释重试次数与业务效果数为什么不同。再移除远端同键重放能力，设计“结果未知 → 人工对账 → 已确认或待处理”的状态及用户提示。把这一结论写进 ProcureAgent 的 ADR，并在自己的服务上补一次终止进程后的恢复测试。

参考答案：本地事务回滚不能撤销远端效果。若远端接受稳定业务键，应查询或同键重试；若不支持，应定义对账和人工处理。把故障点移到每个箭头之后，分别指出可重复和可能丢失的位置。

验收：至少三种故障能恢复，未知结果不会被误报为确定失败或成功。

## 实验四：缓存撤权与版本切换（第6、10章）

准备两个模拟主体和两份虚构资料。A访问自己的资料并填入缓存；撤销访问后，再发完全相同查询。故意让索引与缓存尚未更新。

预期：可信读取边界拒绝访问，不返回标题、片段或旧答案；异步清理后检查数据状态。若需求仅允许最终生效，应明示窗口，而不能声称立即撤权。

更新资料版本时，验证来源、引用和旧链接；重建失败时明确当前可见版本。记录哪些检查发生在检索前，哪些发生在最终返回前。

## 实验五：性能、过载与恢复（第8–9章）

1. 固定输入、数据与环境，先测单请求，再测稳定和突发到达。
2. 同时记录成功/失败、端到端延迟、排队、连接和资源。
3. 加入导入混合负载，定位瓶颈；只改变一项设置后复测。
4. 达到实验停止条件时停止施压，说明拒绝、排队和降级行为。
5. 在隔离环境恢复一份备份，核对业务字段和未完成任务。

参考推演：连接等待高不等于应该无限加池；先看数据库容量和慢查询。队列增长说明处理跟不上，到达率和处理率才是解释起点。备份文件存在不证明恢复正确。

可先用纸笔核算一个容量假设：每秒稳态到达 4 个请求，每个请求恰好占用模型连接 2 秒，每个连接同时处理 1 个请求。理想情况下平均需 8 个占用中的连接。池大小为 4 时理想处理上限约为每秒 2 个；持续到达时积压会增长。这个估算忽略了波动、重试与其他资源。将自己的测试服务设为固定延迟的替身，分别测低于上限和持续超过上限时的完成数、排队时间与取消数，再换实际依赖观察哪里偏离估算。报告成功请求的延迟时同时报告总请求、拒绝与超时数。

把结果写成一项可推翻的决策，例如“当前限制并发并在队列满时拒绝；若数据库等待主导端到端延迟，先处理查询再评估扩池”。给出测量环境、持续时间、停止施压条件和下一次复测指标。缺少真实运行环境时保存计划，等取得数据再填写结论。

## 实验六：兼容迁移与评审（第11–14章）

选择一个变更：拆分任务状态、增加来源版本或变更检索索引。列旧新消费者与数据契约，再按扩展、回填、校验、切换、收缩安排。

模拟回填中断和旧实例继续运行；定义停止扩大、回滚和前向修复条件。评审者分别扮演业务、开发、运维，追问用户影响、失败、成本与负责人。

验收包：目标、图、ADR、契约、原始实验记录、迁移手册、未决项。结论只能覆盖已验证范围。真实服务、云平台或模型未运行就保留为待集成。

## 评分与累计成果

每项0未做、1能解释、2独立设计、3实际验证并能处理新条件。原始证据链接到章节和需求ID。涉及越权、错误写入或恢复破坏的失败单独列出，不能用其他成绩抵消。
