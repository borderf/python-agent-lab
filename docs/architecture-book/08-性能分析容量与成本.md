## 1. 目标、前置与问题

前置：第2、5–7章。能提出容量假设、设计负载实验并根据瓶颈优化。问题：平均延迟很好，为什么用户仍频繁遇到卡顿？

## 2. 概念与基础

假设10秒内完成20次请求，则这段窗口的吞吐量为每秒2次；某一用户从发送到收到结果用了800毫秒，这是该请求延迟。在途还有几项是并发数量。先逐条保存耗时、成功与失败，再从样本计算P95等分位数。这样能分清完成得多、单次等待短和同时接纳得多是三种观察。

负载有请求大小、读写比例、热点、突发和冷启动。压测必须说明数据集、缓存状态、到达模型、时长和资源。闭环客户端等待结果再发请求，系统变慢时可能降低实际施压速率，掩盖排队风险。

## 3. 机制与推导

容量估算从单位开始。每秒20项是速率，同时30项是在途数，平均1.5秒是停留时间。稳定且口径一致的情况下，Little 定律给出平均在途数约为20×1.5=30；它没有给出 P95，也没有证明并发上限设30就足够。

服务能力和到达过程都重要。四个 worker、每项固定40ms，理想化服务上限约100项/秒；若持续到达120项/秒且不拒绝，积压约每秒多20项。真实系统还受调度、连接、限额和耗时分布影响，不能把这个算式当压测结果。

优化先找贡献。若平均耗时80%在模型，将本地剩余20%缩短一半，总耗时约只降10%。若改成缓存，需要重新验权限与版本，不能只展示延迟下降。

实验应固定数据、负载、版本与持续时间，同时保留成功、失败、超时、拒绝和资源曲线。只统计成功请求会把过载时最差体验排除。记录实际到达时刻，避免负载发生器变慢却被误认成服务稳定。

存储预算也要展开：原文、解析、向量、索引开销、版本、副本、备份分别计量。公式中的每个数量都应带单位和来源。

#### 成本要按调用链展开

一次问答的成本不只模型 token：检索、embedding、重排、重试和存储都要计入。下面用假设单价演示口径，不代表任何供应商报价；换成实际单价时重算同一张表。

```python
# track-example: A09
questions = 20_000
input_tokens, output_tokens = 2_000, 500
input_price, output_price = 0.000002, 0.000006  # 假设：每 token 价格
retry_rate = 0.05
model_cost = questions * (1 + retry_rate) * (input_tokens * input_price + output_tokens * output_price)
embedding_cost = questions * 30 * 0.0000005
rerank_cost = questions * 0.001
storage_cost = 120.0
total = model_cost + embedding_cost + rerank_cost + storage_cost
assert round(model_cost, 2) == 147.0
assert round(total, 2) == 287.3
assert round(total / questions, 4) == 0.0144  # 每问平均成本
```

每问平均约 0.014 个货币单位（示例按同一货币计，换成人民币单价时重算），但输入翻倍时模型成本约占总成本六成；重试率从 5% 升到 20%，模型成本再增约 14%。报告成本时同时给单价来源、输入输出假设、重试率、缓存命中与样本量，不能只报一个“每月多少钱”。

## 4. 案例逐步推演

先写教学估算：20请求/秒×1.5秒≈30个平均在途模型请求。供应商若只能同时处理10个，剩余请求会排队、被拒绝，或需要减少生成范围；多开 API worker 不会自动增加供应商限额。

接着运行 `uv run --frozen python -m practice.integration_labs.capacity`。它用两个 worker、有限队列和固定等待模拟稳定与突发。检查每组总请求是否等于完成加拒绝，查看逐项排队与端到端时间。

只改一项：先将 worker 减为1，再恢复原配置后将队列上限减小。分别比较完成、拒绝和等待；不要把两项同时修改后将收益全部归给其中一项。最后说明固定等待模拟尚未覆盖真实 CPU、数据库池与模型限额。

### 4.1 平均值为什么会掩盖少数慢请求

```python
# track-example: A08
from math import ceil
durations_ms = [10, 11, 12, 13, 14, 15, 16, 100]
ordered = sorted(durations_ms)
mean_ms = sum(ordered) / len(ordered)
p95_nearest_rank = ordered[ceil(0.95 * len(ordered)) - 1]
assert mean_ms == 23.875 and p95_nearest_rank == 100
```

这里明确使用nearest-rank算法，只有8个教学样本，不是稳定尾延迟估计。其他工具可能采用插值，报告应说明算法、样本量与窗口。平均值不到24ms，不表示所有人都接近这个体验。

若另外2个请求被拒绝，不能从原始记录中删掉它们，只报告8个成功项的耗时。应该同时报告10项请求、8项完成、2项拒绝，以及成功延迟分布和拒绝原因。不能把拒绝耗时0直接混入平均后称整体更快。

优化前后保持同一题、资料、日期、授权与负载形状，并保存资源曲线。若新版本只测了热缓存，而旧版本包含首次加载，先统一条件，再解释收益。
