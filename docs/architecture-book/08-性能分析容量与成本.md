# 第8章　性能分析、容量与成本

## 1. 目标、前置与问题

前置：第2、5–7章。能提出容量假设、设计负载实验并根据瓶颈优化。问题：平均延迟很好，为什么用户仍频繁遇到卡顿？

## 2. 概念与基础

吞吐量是单位时间完成数，延迟是请求经历的时间，并发是在途数量。P95表示指定样本中约95%的观测值不超过该值；不能把多台机器的P95直接平均成整体P95。还需观察错误、超时、资源和排队。

负载有请求大小、读写比例、热点、突发和冷启动。压测必须说明数据集、缓存状态、到达模型、时长和资源。闭环客户端等待结果再发请求，系统变慢时可能降低实际施压速率，掩盖排队风险。

## 3. 机制与推导

稳态下用Little定律做粗估：平均在途数L≈平均到达率λ×平均停留时间W。假设20次/秒、平均1.5秒，则约30个在途请求；这是限定条件下的均值关系，不能推出尾延迟或安全连接池大小。

估算文档存储时列清原文、解析结果、向量、索引开销、版本与副本。优化前区分CPU、锁、数据库、网络和模型瓶颈；优先优化占比高且可控的环节，并防止优化破坏正确性。

### 3.1 做一个可以比较的性能实验

先给基线、输入分布、到达速率、预热、持续时间和停止条件；同时记录失败请求，避免只统计成功的快请求。重复测量并保存分布，不用一个最好结果代表系统。

优化顺序是发现瓶颈、提出机制假设、只改一项、同条件复测、检查正确性和成本。假设80%时间等待外部模型，优化剩余20%的本地逻辑收益有限；这不意味着本地逻辑永远不用优化，而是先看贡献。

## 4. 案例逐步推演

假设DocPilot峰值20请求/秒，其中生成平均耗时1.5秒。先算约30个平均在途生成请求，再核对供应商并发/速率限制和超时预算。不能直接把并发设置成30就结束；还需考虑突发、失败和排队。

实验分三轮：关键词基线；加入生成；加入导入任务的混合负载。逐轮固定输入，记录P50/P95、错误、队列等待、数据库连接和成本。发现瓶颈后只改一项，重复同一负载并比较。

### 4.1 负载保护也是容量设计

到达超过处理能力时，明确接纳、排队、超时和拒绝。无限队列会把过载变成长尾和内存风险。比较每租户配额、队列上限与全局并发，避免一个大客户拖垮所有人。参考[SRE过载处理](https://sre.google/sre-book/handling-overload/)。

## 5. 分层练习

运行[稳定与突发排队实验](附录E-实测案例与推导.md#从稳定到突发的排队实验)，保留全部完成与拒绝记录。先预测改变 worker 和队列上限的结果，再用真实客户端替换固定等待；报告模拟与真实观测各自能支持什么结论。

基础：手算吞吐、延迟、在途量。应用：写容量表与三轮负载计划。挑战：比较加缓存与加进程，包含命中正确性、内存和维护代价。

## 6. 自测与参考推导

问：单请求测到100毫秒能推断1000并发吗？把队列加长能提高处理能力吗？

<details><summary>参考推导</summary>
不能，竞争与排队会改变行为。队列主要吸收突发，不能增加长期处理能力，持续到达超过处理时会积压。
