# 第8章　性能分析、容量与成本

[上一章](07-消息任务与分布式一致性.md) · [本书目录](教材目录.md) · [下一章](09-可靠性可观测性与故障恢复.md)

## 1. 目标、前置与问题

前置：第2、5–7章。能提出容量假设、设计负载实验并根据瓶颈优化。问题：平均延迟很好，为什么用户仍频繁遇到卡顿？

**本章主线：** 先统一单位与统计口径，再找耗时和成本的主要贡献，最后用只改一个参数的对照实验决定是否采用优化。

## 2. 概念与基础

### 2.1 吞吐、延迟、并发与利用率

10秒完成20次请求，吞吐是每秒2次；某请求从发送到收到结果用800ms，这是延迟；某时刻还有几项未完成，是在途数。CPU占用率回答另一种问题：处理期间资源有多忙。

为什么不能只看一个？吞吐高可能伴随很长排队；延迟低可能只是拒绝了慢请求；在途多可能表示处理快，也可能表示积压。它们要连同成功、失败与拒绝一起观察。

| 指标 | 计算或观察 | 应同时报告 |
| --- | --- | --- |
| 吞吐 | 完成数÷窗口秒数 | 实际到达率、窗口长度 |
| 平均/P95延迟 | 成功请求耗时及分位数 | 算法、样本量、失败与超时 |
| 在途数 | 某时刻未完成任务 | 队列长度、最老等待 |
| 资源利用率 | CPU、内存、连接等 | 饱和等待与外部限额 |

不能把被拒绝请求的耗时0直接混进平均，再声称系统更快。应分别报告总请求、完成、拒绝、超时和成功延迟分布。

### 2.2 P95与平均值回答不同问题

**P95**是按约定算法计算的第95百分位。常用nearest-rank把排序后第 `ceil(0.95×n)` 项作为结果；其他工具可能插值，必须说明算法。

对于 `[10,11,12,13,14,15,16,100]`，平均为23.875ms，nearest-rank P95为100ms。平均说明样本总和，P95突出上尾；8个样本仍不足以稳定估计生产尾延迟。

| 统计 | 本例结果 | 容易误读 |
| --- | ---: | --- |
| 平均 | 23.875ms | 多数请求接近24ms |
| nearest-rank P95 | 100ms | 只有1个慢请求，所以不重要 |
| 样本量 | 8 | 已能代表长期分布 |

如果还有2个请求被拒绝，应报告10项总请求、8项完成、2项拒绝，以及成功项的分布。样本太少时，结论应限定在教学演示，不包装成总体承诺。

分位数不能对各实例的P95再平均。实例A的P95是10ms、实例B的P95是1000ms，平均505ms既不是合并样本的P95，也不能代表整体上尾。应合并原始样本，或使用可合并的分位数摘要，再按同一算法计算；报告还要说明各实例样本量是否悬殊。

### 2.3 负载形状决定容量结论

**负载形状**包括请求大小、读写比例、热点、突发、冷启动和到达方式。同样每秒20次，全部命中一个热点与均匀访问所有资料，数据库和检索压力不同。

**闭环负载**等待响应后再发下一项，系统变慢时实际施压速率会下降，可能掩盖排队。**开环负载**按计划时刻发送，更接近持续到达，但需要控制总量与客户端能力。

| 条件 | 必须固定 | 不固定的后果 |
| --- | --- | --- |
| 数据 | 数量、版本、大小、分布 | 数据变化被误算为代码收益 |
| 缓存 | 冷/热、命中率 | 首次加载与复用混在一起 |
| 到达 | 开/闭环、突发比例 | 客户端变慢被误读为服务稳定 |
| 资源 | 实例、连接、CPU/内存限额 | 不同环境结果不可比 |
| 时长 | 窗口与预热 | 短窗口错过尾部和积压 |

### 2.4 成本按整条调用链计算

一次问答不只模型token成本，还包括检索、embedding、重排、重试、存储与运维。**单位成本**应说明统计范围，例如每个成功问题的全部调用成本。

| 成本项 | 驱动量 | 常见遗漏 |
| --- | --- | --- |
| 模型 | 输入/输出token、重试 | 失败调用与长上下文 |
| embedding | 文档块、查询、重建 | 索引版本重建 |
| 重排 | 候选数、调用次数 | 空结果与降级 |
| 存储 | 原文、向量、索引、副本、备份 | 多版本与临时空间 |
| 运行 | 实例、网络、观测 | 积压与重试放大 |

报告必须给单价来源、货币、日期、输入输出假设、重试率、缓存命中与样本量。教学单价只能演示计算口径，不能当供应商报价。

## 3. 机制与推导

### 3.1 用Little定律连接速率与在途数

稳定且统计口径一致时，**Little定律**给出平均在途数约等于平均到达率×平均停留时间：每秒20项、平均1.5秒，平均在途约30项。

它没有给出P95，也没有证明并发上限设30就足够。到达波动、长尾和不同阶段资源占用都会改变峰值；连接池应按连接占用时间计算，不能直接照抄整条请求的在途数。

若到达率持续高于完成率，队列会增长。此时增加在途上限只会接受更多等待，应先限制接纳或提升真实瓶颈。

### 3.2 服务上限与上游限额共同决定容量

四个worker、每项固定40ms，理想化服务上限约100项/秒。若持续到达120项/秒且不拒绝，积压约每秒多20项。

真实系统还受调度、连接池、数据库与供应商限额影响。供应商只能同时处理10个模型请求时，多开API worker不会自动增加这10个名额，只会在应用或供应商前面积压。

**推导步骤：** 找当前利用率最高且出现等待的资源 → 测该资源单位时间能完成多少 → 与到达率比较 → 决定限流、优化或扩容。CPU低不代表没有瓶颈，等待外部依赖同样会限制吞吐。

### 3.3 优化先找最大贡献

若平均耗时80%在模型，本地剩余20%缩短一半，总耗时约只降10%。反之，模型时间已很小，继续优化它也不会明显改善端到端体验。

优化还可分为减少工作量、减少等待、减少重复和改变接纳。缓存减少回源但引入版本与权限检查；并行减少串行等待却增加并发压力；异步化减少用户等待，却把任务转入后台。

| 改动 | 直接机制 | 必须重验 |
| --- | --- | --- |
| 减少候选数 | 降低检索与重排工作量 | 召回与答案质量 |
| 缓存结果 | 减少重复计算 | 版本、授权、陈旧窗口 |
| 增加worker | 增加并行处理 | 依赖限额与共享资源 |
| 缩短上下文 | 降低模型时间与token | 证据充分性 |

### 3.4 单变量对照才可归因

实验固定数据、负载、版本与持续时间，同时保留成功、失败、超时、拒绝和资源曲线。先保存基线，再只改一个参数，比较相同窗口。

若同时把worker翻倍、缓存打开、模型换小，P95下降也无法归因。更糟的是新版本只测热缓存、旧版本包含首次加载，条件不同会把收益算错。

#### 成本要按调用链展开

一次问答的成本不只模型token：检索、embedding、重排、重试和存储都要计入。下面用假设单价演示口径，不代表任何供应商报价；换成实际单价时重算同一张表。

```python
# track-example: A08
questions = 20_000
input_tokens, output_tokens = 2_000, 500
input_price, output_price = 0.000002, 0.000006  # 假设：每 token 价格
retry_rate = 0.05
model_cost = questions * (1 + retry_rate) * (input_tokens * input_price + output_tokens * output_price)
index_chunks = 300_000  # 假设：一万文档×30块，索引期嵌入并按本月一次重建计入
embedding_cost = questions * 0.0000005 + index_chunks * 0.0000005  # 每问1次查询嵌入＋索引摊销
rerank_cost = questions * 0.001  # 假设：每问重排 1 次，每次单价 0.001
storage_cost = 120.0  # 假设：当月固定存储与备份费用（同一货币口径）
total = model_cost + embedding_cost + rerank_cost + storage_cost
assert round(model_cost, 2) == 147.0
assert round(total, 2) == 287.16
assert round(total / questions, 4) == 0.0144  # 每问平均成本
doubled_input_model_cost = questions * (1 + retry_rate) * (2 * input_tokens * input_price + output_tokens * output_price)
higher_retry_model_cost = questions * 1.20 * (input_tokens * input_price + output_tokens * output_price)
assert round(doubled_input_model_cost, 2) == 231.0
assert round(100 * doubled_input_model_cost / (doubled_input_model_cost + embedding_cost + rerank_cost + storage_cost), 1) == 62.2
assert round(higher_retry_model_cost, 2) == 168.0
assert round(higher_retry_model_cost / model_cost - 1, 2) == 0.14
```

每问平均约0.0144个货币单位。输入翻倍时模型成本约占总成本六成；重试率从5%升到20%，模型成本再增约14%。报告成本时同时给单价来源、输入输出假设、重试率、缓存命中与样本量，不能只报“每月多少钱”。

## 4. 案例逐步推演

先写教学估算：20请求/秒×1.5秒≈30个平均在途模型请求。供应商若只能同时处理10个，剩余请求会排队、被拒绝，或需要减少生成范围；多开API worker不会自动增加供应商限额。

接着运行 `uv run --frozen python -m practice.integration_labs.capacity`。它用两个worker、有限队列和固定等待模拟稳定与突发。检查每组总请求是否等于完成加拒绝，查看逐项排队与端到端时间。

只改一项：先将worker减为1，再恢复原配置后将队列上限减小。分别比较完成、拒绝和等待；不要把两项同时修改后的收益全部归给其中一项。最后说明固定等待模拟尚未覆盖真实CPU、数据库池与模型限额。

**输入：** 固定请求总量与固定服务时间。**变化：** worker数量或队列上限。**输出：** 完成、拒绝与P95变化。**失败定位：** 若总请求不等于完成加拒绝，先查模拟账本；若P95改善但拒绝激增，检查是否只是少接纳。

### 4.1 平均值为什么会掩盖少数慢请求

```python
# track-example: A09
from math import ceil
durations_ms = [10, 11, 12, 13, 14, 15, 16, 100]
ordered = sorted(durations_ms)
mean_ms = sum(ordered) / len(ordered)
p95_nearest_rank = ordered[ceil(0.95 * len(ordered)) - 1]
assert mean_ms == 23.875 and p95_nearest_rank == 100
```

这里明确使用nearest-rank算法，只有8个教学样本，不是稳定尾延迟估计。其他工具可能采用插值，报告应说明算法、样本量与窗口。平均值不到24ms，不表示所有人都接近这个体验。

若另外2个请求被拒绝，不能从原始记录中删掉它们，只报告8个成功项的耗时。应该同时报告10项请求、8项完成、2项拒绝，以及成功延迟分布和拒绝原因。不能把拒绝耗时0直接混入平均后称整体更快。

优化前后保持同一题、资料、日期、授权与负载形状，并保存资源曲线。若新版本只测了热缓存，而旧版本包含首次加载，先统一条件，再解释收益。

## 5. 分层练习

1. **基础**：为同一查询保存容量表：到达率、服务时间、在途数、连接预算和拒绝规则；用nearest-rank算P95并报告样本量。
2. **改造**：做一轮只改worker或只改队列上限的对照，同时列完成、失败、拒绝与P95，并说明可归因范围。
3. **独立**：按整条调用链计算单位成本，再把输入token翻倍或重试率升至20%；给出采用门槛与质量回归项。

## 6. 自测与参考推导

<details><summary>完成独立任务后查看诊断</summary>

如果队列变长、成功数增加但用户等待超过截止时间，不能直接称为优化。若算出平均在途30就把连接池设30，混淆了整条请求与某个资源占用时间，还忽略了突发和尾部。

</details>

**自问：** 为什么闭环压测显示稳定，生产仍可能积压？

**参考推导：** 闭环客户端等待响应后才发下一项，服务变慢会同步降低施压速率，使到达率始终不超过当前处理能力。开环负载按固定计划施压，才更容易暴露到达持续高于处理能力时的排队。

## 7. 项目交付与验收

保存基线、一次改动与采用条件。下一章把测量变成用户影响目标、告警和恢复动作。

| 操作 | 预期结果 | 证据 |
| --- | --- | --- |
| 保存基线 | 数据、负载、版本、资源可复现 | 配置与原始逐请求记录 |
| 单参数改动 | 能归因于一个机制 | 前后对照与资源曲线 |
| 触发过载 | 拒绝与等待有明确规则 | 完成、失败、拒绝、超时 |
| 计算成本 | 全链路且单位一致 | 单价来源、用量、重试与样本 |
| 决定采用 | 质量与代价同时达标 | 目标、回归结果、回退条件 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 平均延迟看起来很好，为什么用户仍频繁遇到卡顿？

**一条主线：** 单位与口径 → 瓶颈贡献 → 单变量对照 → 容量与成本表。

**三个关键词：** P95、在途数、单位成本。P95暴露上尾；在途由速率与停留时间联系；单位成本必须覆盖完整调用链。

**最容易错：** 平均在途直接当连接池；只统计成功；闭环变慢被当稳定；同时改多个参数；成本只算模型token。

**学完应能：** 用Little定律估算平均在途；按nearest-rank算P95；保存可归因对照与全链路成本。
