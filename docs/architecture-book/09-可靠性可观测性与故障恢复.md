# 第9章　可靠性、可观测性与故障恢复

[上一章](08-性能分析容量与成本.md) · [本书目录](教材目录.md) · [下一章](10-安全多租户与隐私边界.md)

## 1. 目标、前置与问题

前置：第7–8章。能定义用户侧目标、安排告警和恢复演练。问题：进程健康检查通过，为什么用户仍无法完成任务？

## 2. 概念与基础

假设某窗口有100次满足统计条件的请求，98次完成了定义好的任务，测得成功率98%，这是一个SLI。团队事先约定目标成功率，形成SLO；若对客户约定服务水平及责任，才进入SLA。先写清成功条件、分母和窗口，再讨论错误预算，不能只从几个缩写推断系统是否可靠。

日志描述事件，指标观察聚合变化，trace关联一次跨组件调用。请求ID用于关联，不能代替身份或授权。敏感内容不因用于排错就应全部记录；高基数标签会增加观测成本。

## 3. 机制与推导

“进程还活着”与“用户任务能完成”不同。需要先定义什么算有效任务与成功，再建立 SLI；SLO 是观察窗口内的目标，不是某个监控数值看起来漂亮。模型降级后若仍能完成约定的查证任务，可以单独记录降级成功，但不能把生成质量也算通过。

超时限制等待，限流控制接纳，隔离限制故障传播，熔断减少对持续失败依赖的调用，降级保留部分任务。它们不是互换的开关。三层各重试三次可能放大到多次下游尝试，必须统一截止时间与重试预算。

恢复目标也要区分：RPO 关心可容忍的数据缺口，RTO 关心恢复服务的耗时。备份文件存在不表示能读、密钥齐全或任务恢复正确。数据库恢复后仍要对账未完成动作，防止旧任务重放。

```mermaid
flowchart LR
    A[发现用户任务失败] --> B[限制影响]
    B --> C[定位范围与版本]
    C --> D[降级或恢复]
    D --> E[核对数据与外部效果]
    E --> F[复盘并增加回归]
```

日志说明某次事件，指标说明总体趋势，trace 连接请求各阶段。它们都有采样和遗漏的可能，不能把没有日志当成没有发生。告警应给出影响、范围、关联证据与第一步动作。

## 4. 案例逐步推演

教学口径：一月10万次有效查询，成功目标99.5%，允许失败数为100000×0.005=500。这是请求计数预算，不能直接换算成允许宕机分钟；越权也不能拿预算抵扣。

故障一：模型持续超时。入口停止继续叠加重试，保留授权检索来源，界面显示“生成暂不可用”，记录降级。分别核对用户能否查证、生成是否恢复、实际请求总时长是否受控。

故障二：恢复数据库。先在隔离目录从备份还原，核对来源版本、回答关联、批准与动作账本，再恢复任务。把开始、数据可读、关键任务通过、对账完成四个时间点记录下来；没有演练过就写未验证，不填一个希望达到的 RTO 当实测。

### 4.1 一份能在故障时照着做的运行记录

以模型持续超时为例：触发信号是用户生成请求失败与等待增加；先核对范围是否仅某供应商，查实际版本和关联请求；限制新生成的接纳与重试，保留有权限的来源查询；对用户展示生成暂不可用及下一步。恢复后用固定正常、无依据和坏输出题回归，再逐步解除限制。

恢复数据库则使用另一条流程：确认恢复源与时间点，在隔离环境还原，核对来源版本、回答关联、任务、批准和动作；查询可能已在远端发生的效果，再决定恢复哪项任务。不能先让所有未完成任务自动重跑，稍后才查重复。

事后复盘写“发布后旧实例读取新字段失败”，需要旧新版本、时间线和样本支持；“有人粗心”不能解释为什么系统允许不兼容状态进入。改进应对应混合版本检查、迁移顺序与停止条件。

运行手册中的命令必须在自己的环境验证；本章给的是决策流程，不能复制一套未知数据库恢复命令用于真实数据。

## 5. 分层练习

先完成：为自己的一个关键任务写成功口径和一条告警处理步骤。做一次依赖超时，再做一次隔离恢复；若缺少部署环境，先验证本地持久化恢复，并列清尚未覆盖的部分。
