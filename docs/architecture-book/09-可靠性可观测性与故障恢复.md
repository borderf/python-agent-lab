# 第9章　可靠性、可观测性与故障恢复

[上一章](08-性能分析容量与成本.md) · [本书目录](教材目录.md) · [下一章](10-安全多租户与隐私边界.md)

## 1. 目标、前置与问题

前置：第7–8章。能定义用户侧目标、安排告警和恢复演练。问题：进程健康检查通过，为什么用户仍无法完成任务？

**本章主线：** 先定义什么算用户任务成功，再选择能发现失败的信号；故障时先限制影响，再按证据降级或恢复，最后核对数据与外部效果。

## 2. 概念与基础

### 2.1 SLI、SLO、SLA与错误预算

某窗口有100次满足统计条件的请求，98次完成定义好的任务，成功率98%，这是**SLI**。团队事先约定目标成功率，形成**SLO**；对客户约定服务水平及责任，才进入**SLA**。

**错误预算**是目标允许的失败量。例如10万次有效查询、目标99.5%，请求计数预算为500次。它是计数口径，不能直接换算成允许宕机分钟，也不能用于抵消越权。

为什么先定义成功？若“接口返回200”算成功，模型超时后返回空结果也会被算作正常。成功必须连接用户任务，例如“在授权范围内返回当日适用来源”；生成是否完成可单独统计。

| 概念 | 回答什么 | 本例 |
| --- | --- | --- |
| SLI | 实际测得多少 | 98/100成功 |
| SLO | 希望达到多少 | 99.5% |
| SLA | 对客户承诺什么及责任 | 合同约定，不自动等于SLO |
| 错误预算 | 窗口内容许失败多少 | 100000×0.005=500次 |

### 2.2 日志、指标与trace互补

**日志**描述离散事件；**指标**观察聚合变化；**trace**关联一次跨组件调用。请求ID用于串联证据，不能代替身份或授权。

日志适合回答“这次发生了什么”，指标适合“整体是否变坏”，trace适合“时间花在哪一段”。没有日志不代表没有发生，采样、丢失与异步上报都可能遗漏。

| 信号 | 典型问题 | 常见误用 |
| --- | --- | --- |
| 日志 | 哪次提交冲突 | 把秘密正文完整写入 |
| 指标 | 失败率是否持续升高 | 用user_id做高基数标签 |
| trace | 模型还是数据库慢 | 把采样trace当完整账单 |

敏感内容不因用于排错就应全部记录。优先记录关联ID、阶段、错误类别和必要资源标识；正文与令牌按数据保护要求脱敏或禁止记录。

### 2.3 健康检查不等于任务可用

**存活检查**回答进程是否还在；**就绪检查**回答是否可接收流量；**关键任务检查**回答实际读写路径能否工作。三者不能互相替代。

进程健康但数据库连接池耗尽、模型超时或索引配置错误，用户仍无法完成任务。健康检查应反映启动、依赖和退出条件，但不能把所有下游故障都变成无限重启。

例如模型不可用时，来源查询可能仍就绪；若把整个应用标为不健康并摘除流量，用户会失去仍可完成的降级任务。是否摘流量要按实际用户路径决定。

### 2.4 RPO与RTO是可演练的恢复目标

**RPO**关心可容忍的数据缺口；**RTO**关心恢复服务的耗时。二者是目标，不是看到备份文件就能宣称达到。

恢复还要核对密钥、权限、任务和外部效果。数据库回滚后让所有未完成任务自动重跑，可能重复已经发生的远端提交。

| 时点 | 记录什么 | 证明什么 |
| --- | --- | --- |
| 开始恢复 | 故障确认时间、负责人 | RTO计时起点 |
| 数据可读 | 还原完成与版本 | 存储恢复，不等于业务恢复 |
| 关键任务通过 | 查询、提交、权限样本 | 路径可用 |
| 对账完成 | 未完成动作与远端回执 | 数据与副作用可解释 |

## 3. 机制与推导

### 3.1 从成功口径选择观测信号

先定义有效任务与成功，再建立SLI与SLO。模型降级后若仍能完成约定查证任务，可单独记录降级成功，但不能把生成质量也算通过。

例如任务成功拆成三项：来源可访问、日期与权限正确、用户在截止时间内得到明确结果。相应信号是来源查询成功率、错误样本数、端到端耗时；进程CPU只是辅助证据。

**推导：** 用户目标决定SLI；SLI决定需要哪些日志、指标和trace；告警再从这些信号中选择能触发现有动作的条件。没有动作的告警不应只增加噪声。

### 3.2 超时、限流、隔离、熔断与降级各管一件事

**超时**规定最多等多久；**限流**规定单位时间接受多少；**隔离**避免一个故障拖住其他工作；**熔断**在依赖持续失败时暂时减少调用；**降级**保留用户仍能完成的部分任务。

| 机制 | 直接效果 | 边界 |
| --- | --- | --- |
| 超时 | 限制单次等待 | 不自动取消后台副作用 |
| 限流 | 限制新流量 | 已受理任务仍需处理 |
| 隔离 | 保护其他工作资源 | 不修复故障依赖 |
| 熔断 | 暂停对持续失败依赖的调用 | 需半开探测恢复 |
| 降级 | 保留部分任务 | 不可降级权限与正确性 |

重试要统一安排。入口、网关、业务和SDK各重试3次，最坏会放大为81次调用。重试预算应服从总截止，并区分可重试错误与必须修正的错误。

### 3.3 告警必须关联影响与第一步动作

“CPU超过80%”只说明资源，不说明用户影响。有效告警应包含影响、范围、关联证据与第一步动作，例如“过去5分钟来源查询失败率超过2%，当前版本v8，先查数据库连接与trace”。

告警阈值需结合SLO、窗口与噪声。过松发现太晚，过紧会训练团队忽略。一次告警应能对应运行手册中的步骤，而不是只有“请查看”。

**失败定位：** 用户任务失败时，先看是否全局还是单租户、哪个版本、哪个阶段；再看错误率与耗时是否同时变化；最后用trace和日志验证候选原因。不要把相关当因果。

### 3.4 恢复流程包含数据与副作用对账

恢复目标区分RPO与RTO，但达到“服务可启动”还不够。数据库恢复后要核对来源版本、回答关联、批准与动作账本，防止旧任务重放。

```mermaid
flowchart LR
    A[发现用户任务失败] --> B[限制影响]
    B --> C[定位范围与版本]
    C --> D[降级或恢复]
    D --> E[核对数据与外部效果]
    E --> F[复盘并增加回归]
```

日志、指标和trace都有遗漏可能。复盘应把现象、候选原因、证据和修改分开。例如“发布后旧实例读取新字段失败”需要版本与样本支持；“有人粗心”不能解释系统为何允许不兼容状态进入。

## 4. 案例逐步推演

教学口径：一月10万次有效查询，成功目标99.5%，允许失败数为100000×0.005=500。这是请求计数预算，不能直接换算成允许宕机分钟；越权也不能拿预算抵扣。

**故障一输入：** 模型持续超时。**变化：** 入口停止继续叠加重试，保留授权检索来源，界面显示“生成暂不可用”。**输出：** 查证路径可用，生成明确降级，请求总时长受控。**失败定位：** 先查失败是否仅某供应商，再查实际版本、关联请求和重试总量。

**故障二输入：** 数据库损坏，需要从备份恢复。**变化：** 在隔离目录还原，核对来源版本、回答关联、批准与动作账本，再恢复任务。**输出：** 记录开始、数据可读、关键任务通过、对账完成四个时间点。没有演练过就写未验证，不填希望达到的RTO当实测。

### 4.1 一份能在故障时照着做的运行记录

以模型持续超时为例：触发信号是用户生成请求失败与等待增加；先核对范围是否仅某供应商，查实际版本和关联请求；限制新生成的接纳与重试，保留有权限的来源查询；对用户展示生成暂不可用及下一步。恢复后用固定正常、无依据和坏输出题回归，再逐步解除限制。

恢复数据库则使用另一条流程：确认恢复源与时间点，在隔离环境还原，核对来源版本、回答关联、任务、批准和动作；查询可能已在远端发生的效果，再决定恢复哪项任务。不能先让所有未完成任务自动重跑，稍后才查重复。

事后复盘写“发布后旧实例读取新字段失败”，需要旧新版本、时间线和样本支持；“有人粗心”不能解释为什么系统允许不兼容状态进入。改进应对应混合版本检查、迁移顺序与停止条件。

运行手册中的命令必须在自己的环境验证；本章给的是决策流程，不能复制一套未知数据库恢复命令用于真实数据。

### 4.2 离线检查错误预算与恢复门槛

```python
requests, successes = 10_000, 9_960
slo = 0.995
success_rate = successes / requests
budget_used = (requests - successes) / (requests * (1 - slo))
assert success_rate == 0.996
assert round(budget_used, 2) == 0.80
assert (requests - successes) <= requests * (1 - slo)

restore = {"data_readable": True, "key_task_passed": False, "effects_reconciled": True}
assert restore["data_readable"]
assert not restore["key_task_passed"]
assert not all(restore.values())
```

40次失败用完50次计数预算的80%，但不代表还能承受越权。恢复记录即使数据可读、对账完成，只要关键任务未通过，就不能宣布RTO达成；还要补实际耗时，目标与实测分开。

## 5. 分层练习

1. **基础**：为一个关键任务写成功条件、分母、窗口和错误预算，并指出哪个观测信号能真正反映用户失败。
2. **改造**：做一次依赖超时，限制重试并启用来源降级；记录用户结果、调用总量与恢复步骤。
3. **独立**：在隔离环境做一次持久化恢复，记录四个时间点与未完成动作对账；缺少环境则明确哪些仍未验证。

**自问：** 为什么请求成功率达标，仍可能有严重可靠性问题？

**参考推导：** 成功率只覆盖定义好的样本与任务。少量越权、数据错误或不可逆重复可能后果严重，不能用大量正常请求抵消；还需要独立的不变量与安全验收。

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 进程健康检查通过了，为什么用户仍无法完成任务？

**一条主线：** 定义成功口径 → SLI/SLO与预算 → 超时限流隔离熔断降级 → 恢复与对账。

**三个关键词：** SLI、错误预算、RPO/RTO。SLI定义成功；预算限定失败量；恢复目标必须由实际演练证明。

**最容易错：** health=ok当恢复完成；失败预算换算宕机分钟或抵扣越权；多层重试无总预算；错误变空结果；目标当实测。

**学完应能：** 写成功口径与计数预算；为模型超时和数据库恢复写手册；记录四个恢复时间点并核对副作用。
