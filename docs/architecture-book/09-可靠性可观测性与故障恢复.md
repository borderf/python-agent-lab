# 第9章　可靠性、可观测性与故障恢复

[上一章](08-性能分析容量与成本.md) · [本书目录](教材目录.md) · [下一章](10-安全多租户与隐私边界.md)

## 1. 目标、前置与问题

前置：第7–8章。能定义用户侧目标、安排告警和恢复演练。问题：进程健康检查通过，为什么用户仍无法完成任务？

## 2. 概念与基础

假设某窗口有100次满足统计条件的请求，98次完成了定义好的任务，测得成功率98%，这是一个SLI。团队事先约定目标成功率，形成SLO；若对客户约定服务水平及责任，才进入SLA。先写清成功条件、分母和窗口，再讨论错误预算，不能只从几个缩写推断系统是否可靠。

日志描述事件，指标观察聚合变化，trace关联一次跨组件调用。请求ID用于关联，不能代替身份或授权。敏感内容不因用于排错就应全部记录；高基数标签会增加观测成本。

## 3. 机制与推导

超时、限流、隔离、熔断和降级各解决不同问题。多层重试会放大请求，需统一总时限和次数预算。告警优先关联用户影响，不能只根据CPU偶尔升高就频繁叫醒人。

RPO表达可容忍数据丢失范围，RTO表达恢复时间目标。备份成功不能证明可恢复，必须验证还原、依赖、完整性和未完成任务。故障复盘分析系统条件和改进，不把记录停在“某人操作失误”。

### 3.1 从告警走到恢复动作

告警至少说明用户影响、范围、趋势、关联面板及第一步处置。按错误预算消耗速度调查持续异常，避免所有阈值都触发人工响应。采样trace和聚合指标的缺口需要说明，不能由没有日志推断没有错误。

恢复演练写清恢复源、隔离环境、所需密钥、依赖版本、完整性核对与对账。对任务系统还要检查恢复后的未完成动作是否会重放；恢复数据与恢复正确业务流程是两项工作。

## 4. 案例逐步推演

假设每月10万次有效查询，目标成功比例99.5%，则该口径允许500次失败；这不是宕机时长预算，也不代表其他安全护栏可以放宽。

演练模型依赖超时：入口限制总时长；检索仍按权限返回来源；结果标识降级；trace关联等待与失败。随后在隔离环境恢复数据库备份，检查文档元数据、审批状态和动作账本。逐项测量恢复耗时与数据缺口，和目标比较。

### 4.1 一份复盘的因果链

“发布后错误升高”是现象；“旧实例读不到新字段”是候选机制；兼容性样本、版本和时间线才是证据。改进应对应机制：混合版本测试、扩展后迁移与发布停止条件，而不止提醒下次更小心。

## 5. 分层练习

基础：写一个SLI及分子分母。应用：写告警响应手册，包含判断、缓解、升级和恢复。挑战：运行一次备份恢复和重放演练，调查恢复后任务是否重复执行。

## 6. 自测与参考推导

问：liveness和readiness为何不同？成功率高能否证明数据恢复正确？

前者关心进程是否需要重启，后者关心能否接收所需业务流量。请求成功不保证恢复数据完整，需要核对业务不变量与记录。

## 7. 项目交付与验收

提交目标、告警、运行手册、恢复记录与复盘。失败时能回答谁受影响、如何停止扩大、怎样验证恢复。
