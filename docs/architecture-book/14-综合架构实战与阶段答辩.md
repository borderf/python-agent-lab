# 第14章　综合架构实战与阶段答辩

[上一章](13-架构评审技术领导与协作.md) · [本书目录](教材目录.md) · [工作簿](附录A-工作簿与模板.md)

## 1. 目标、前置与问题

前置：第1–13章。完成一个从约束到实验、演进和复查的闭环。使用DocPilot或ProcureAgent，项目规格见[现有实践规格](../project-practice/项目实践规格.md)。

**本章主线：** 把前13章的决定放到同一系统检查组合失效，用分层证据支持每条关键需求，再在条件变化时修改推理并提交索引页。

## 2. 概念与基础

### 2.1 作品是证据链，不只是一张架构图

架构作品包括目标、当前结构、决策、实现或原型、测量、故障和演进。图只说明设计状态，不能代替运行输出与失败记录。

为什么需要证据链？因为每条决定都对应一个未知。目标说明为什么做，ADR说明为何这样选，实验说明危险假设是否成立，发布与恢复说明变化后是否仍可控。

| 材料 | 能证明 | 不能证明 |
| --- | --- | --- |
| 设计图 | 提出了某种结构与依赖 | 已实现、已达标 |
| 局部断言 | 特定输入下机制成立 | 并发、协议或真实环境 |
| 集成记录 | 多组件按约定组合 | 长期容量与用户价值 |
| 负载与恢复演练 | 给定环境下的行为 | 所有生产故障 |
| 用户试点 | 特定用户完成任务 | 所有租户与规模 |

### 2.2 设计证明、局部实验与集成演练

学习分三级：**设计证明**能推理不变量与失败窗口；**局部实验**验证一个机制；**集成演练**验证机制组合后的状态与恢复。

局部去重通过，不代表跨进程重启后仍只有一份效果；单次发布成功，不代表迁移中途停止可恢复；权限核心函数通过，不代表HTTP入口没有伪造身份。层级之间不能跳级声称。

一个综合案例应先写最小闭环：用户A按日期查到有效来源，B无法读取；模型超时后来源仍可核查；远端提交后丢回执，重启取回同一回执且效果数仍为1。

### 2.3 证据范围必须与结论一致

每条证据都应带输入、环境、版本、命令、实际输出与限制。设计图证明提出过结构，局部测试证明特定行为，真实集成验证协议，负载和恢复验证具体环境，用户试点验证任务。

| 结论 | 最低证据 | 应注明 |
| --- | --- | --- |
| 去重机制有效 | 同键同载荷与失回执测试 | 是否真实并发 |
| 跨进程可恢复 | 重启后再查效果与回执 | 恢复时点与持久化位置 |
| 查询P95达标 | 固定负载原始记录 | 算法、样本、错误与资源 |
| 撤权不可读 | 搜索、缓存、原文、恢复反例 | 已交付数据无法收回 |
| 发布可恢复 | 中间状态停止与续跑 | 哪些步骤已不可逆 |

“未验证”是有效状态，比编造通过更可信。第一轮不必全部达到生产级，但不能把教学模拟写成真实实测。

### 2.4 需求追踪连接规则、实现与观察

**需求追踪**把用户后果连到规则位置、入口实现、测试、部署观察与剩余未知。例如“撤权后不能读取”必须连到源查询、缓存、原文接口和恢复入口。

最小追踪行是：需求ID → 业务不变量 → 实现模块 → 验证输入与输出 → 运行信号 → 当前证据等级。若只在安全文档写一句，就没有形成可检查链路。

| 需求 | 规则位置 | 实现位置 | 证据 |
| --- | --- | --- | --- |
| 按日期查制度 | 来源生效区间 | normalize/search | 边界日期与版本 |
| 撤权不可读 | 当前对象授权 | 各入口与缓存 | 拒绝正文与缓存检查 |
| 不重复效果 | 稳定动作键 | submit/动作表 | 失回执与效果数量 |

## 3. 机制与推导

### 3.1 组合后会暴露新的失败窗口

综合实战不是再创建项目，而是检查前13章的决定能否在同一系统同时成立。资源隔离不能绕过授权，恢复不能重复提交，性能优化不能返回旧批准。

局部正确的模块组合后，仍可能出现时间窗口：提交事务成功但outbox未扫描；旧应用读到新字段；索引已切换但缓存仍是旧授权；恢复任务重放时远端效果已存在。

| 组合 | 新风险 | 检查点 |
| --- | --- | --- |
| 导入隔离＋缓存 | 旧导入回填旧版本 | 版本检查与授权时点 |
| 发布＋消息 | 新旧消费者重复或乱序 | 动作键与资源版本 |
| 恢复＋外部动作 | 重放已生效提交 | 原键查询与效果对账 |
| 优化＋权限 | 缓存或摘要泄露 | 租户范围与拒绝样本 |

因此综合验收应有意制造中断与交错，而不是只播放正常路径。每个故障都应能指出恢复依据与不能自动撤销的部分。

### 3.2 一条需求贯穿六类证据

追踪“回执丢失后不能重复效果”：用户后果是重复提交；设计依赖稳定动作键与接收方原子去重；实现位于submit与动作表；局部检查是失回执契约；集成检查是跨进程恢复；真实远端还需验证键保留与查询语义。

```text
用户后果 → 不变量 → 设计决定 → 实现位置 → 局部/集成证据 → 运行观察 → 未知
```

每层标通过、未做或不适用。局部测试通过只填局部层，不能自动把集成层也涂绿。未知应转成下一轮有负责人的任务。

对于“按业务日期找到制度”，设计依赖来源版本与生效区间，代码在normalize、search，检查覆盖边界日期；真实PDF还要验证定位，用户试点观察是否理解日期。不是测试越多，真实任务就必然成立。

### 3.3 用故障注入验证组合边界

组合验证至少改变一个条件：丢回执、进程重启、旧版本事件晚到、缓存命中旧授权、迁移中途停止。每次只注入一个故障，便于定位哪个边界失效。

预期结果不仅是接口返回成功，还要看效果数量、来源版本、授权判断、最老等待与回执一致性。失败时从实际状态反推：谁已经提交、谁未确认、哪份证据可恢复。

恢复后应重新跑正常路径与安全样本，确保修复没有引入另一条绕过。局部恢复成功不代表所有积压任务都可直接重放。

### 3.4 条件变化时先找失效假设

答辩的关键是面对新条件能修改推理。预算减半、资料量增大、远端结果未知时，先指出哪个假设改变，再沿已有边界修改，而不是所有题都答成加缓存与拆服务。

| 新条件 | 首先失效的假设 | 优先动作 |
| --- | --- | --- |
| 预算减半 | 当前实例与调用量可承担 | 缩范围、降非必要生成、重测 |
| 资料量增十倍 | 原索引与容量足够 | 测解析、索引、存储与P95 |
| 远端结果未知 | 本地可判断成功 | 原键查询、幂等或人工对账 |
| 团队扩到八人 | 单团队单发布仍高效 | 检查修改与发布依赖 |

不能删掉必要权限与批准来满足新预算。架构答辩应说明接受什么代价、保留什么不变量、哪些目标需要重新测量。

## 4. 案例逐步推演

把作品演示压成三条连续路径。第一条：用户A按日期找到有效来源，用户B无法拿到其内容。第二条：模型超时后明确降级，来源仍可核查。第三条：报告获批后模拟远端已提交但回执丢失，重启后取回同一回执，效果数仍为1。

每条展示输入、实现位置、运行命令、实际输出和限制。接着改变一个条件：批准后修改报告。旧批准应失效；若实现尚未支持这一层，明确演示当前契约覆盖到哪里，并作为下一轮任务。

最终材料只需要一个索引页，链接已有ADR、接口、竞争实验、负载、恢复、安全和发布记录。不要在最后一章重新写十四份模板。

**输入：** 三条正常路径与一个变化条件。**变化：** 替换租户、让模型超时、丢远端回执、修改报告版本。**输出：** 来源、降级、单效果和旧批准失效分别可观察。**失败定位：** 先确认请求是否到达目标模块，再看状态与回执；不要把“页面显示成功”当唯一证据。

### 4.1 一条需求怎样追踪到最后的证据

以“回执丢失后不能重复效果”为例：用户后果是重复业务提交；设计依赖稳定动作键和接收方原子去重；实现位于你的submit与动作表；局部检查是失回执契约；集成检查是跨进程恢复；真实远端还需验证其契约。每一层都标明通过、未做或不适用。

再选“按业务日期找到制度”：设计依赖来源版本与半开区间，代码在normalize、search，检查在[练习说明](../../tests/learner/练习说明.md)的第2、8、20步，真实PDF需另验定位，用户试点需观察是否理解日期。不是自动测试越多，真实任务就必然成立。

最后接受预算减半的追问。可以减少首轮范围、暂缓生成或采用更简单的部署，但不能删掉必要权限与批准；需要重新测量目标负载下的任务。这样的答辩把架构选择和交付约束连接起来。

### 4.2 一份架构决定如何被证据修改

以下是**虚构评审材料**，包括负载和数字，仅用于训练推理，不是本仓库实测，也不能写入个人简历。沿用第1章的两人、六周DocPilot首版，持续修改同一份 `architecture/decision.md`。

**初稿：** “为支持扩展，将检索、生成、导入拆成三个服务，并添加缓存，保证高性能。”

评审先不讨论画图好坏，而是追问：扩展指什么负载？哪一层已成为瓶颈？缓存依据什么失效？三个服务的发布与故障由谁负责？初稿没有可反驳的条件，因而无法判断结构是否解决问题。

**补证据：** 本轮目标先限定为：固定一万份教学来源，每秒2次检索，P95不超过500ms，同时执行一次批量导入；生成不计入此检索指标，单独测量。固定机器、数据、查询和预热，每种场景测三轮，每轮180秒、360次查询，保留逐请求耗时与错误。

| 虚构实验场景 | 三轮检索P95范围 | 每轮查询错误 | 能推断什么 |
| --- | --- | --- | --- |
| 无导入的基线 | 270–290ms | 0/360 | 当前检索路径在该条件下满足目标 |
| 不限制导入并发 | 1700–1900ms | 0/360 | 混合负载未满足目标，需要定位竞争 |
| 导入并发限为1、待处理队列限20 | 410–440ms | 0/360 | 该限制下查询达标；仍需检查导入等待与拒绝 |

不能据此直接断言CPU、锁或IO是唯一原因：还要查看对应资源、事务等待和阶段耗时。也不能把0个错误解释为生产永不失败。限制后查询达标并不证明整体交付合格；若导入等待不可接受，仍要调整资源或结构。

**修改后的ADR：** “首版保留模块化单体，导入使用受限执行器；待处理任务上限20，满时明确返回忙碌，不接受未持久记录的任务。已接收任务持久化后由执行器读取。依据当前混合负载结果，暂不拆三个服务。接受发布关联与共享数据库竞争；导入任务必须可恢复，不在持锁事务中等待模型。索引更新沿第6章的版本/可见性约定，不用未定义失效的缓存掩盖问题。”

**复查条件：** “在约定资源内，限制导入后仍不满足检索或导入目标；或者出现独立发布/团队责任的真实需要。届时比较资源隔离、查询优化与拆分，保留相同题和故障回归。”

这份修改从第1章目标，连到第5章事务、第6章索引、第8章量测、第9章恢复和第11章发布。结构图随决定更新；先补证据再改变边界，不必把十四章成果重新写一遍。

### 4.3 用评审反馈判断作品能否交付

| 提交内容 | 评审应指出的缺口 | 可接受的下一次修改 |
| --- | --- | --- |
| “事务保证不重复” | 没说清事务覆盖哪些存储 | 画远端成功/本地未确认窗口，展示接收方去重或明确未知状态 |
| “已做权限过滤” | 只有检索入口证据 | 补来源、缓存、导出和恢复入口的授权检查；未实现的标出 |
| “P95下降70%” | 缺负载、样本与对照 | 给原始记录、计算口径、资源与重复结果，同时报告错误 |
| 图和代码不一致 | 设计状态与实现状态混淆 | 在同一索引中标明当前实现、计划修改和未验证假设 |

独立练习时将查询负载改为每秒20次，但不预设上述方案还能达标。先更新目标与实验，再解释是否需要改变决定。你应能说明什么证据会推翻自己，而不只是为原方案辩护。

### 4.4 用离线闭环核对三条关键路径

```python
# track-example: A14
sources = {
    "s1": {"tenant": "A", "version": 8, "active_from": 1, "active_to": 9},
    "s2": {"tenant": "B", "version": 3, "active_from": 1, "active_to": 9},
}

def visible_sources(tenant, business_day):
    return [s for s in sources.values() if s["tenant"] == tenant and s["active_from"] <= business_day < s["active_to"]]

assert [s["version"] for s in visible_sources("A", 8)] == [8]
assert visible_sources("B", 8)[0]["tenant"] == "B"
assert visible_sources("A", 9) == []

remote_effects = {}
def submit(key, payload_hash):
    if key not in remote_effects:
        remote_effects[key] = {"payload_hash": payload_hash, "receipt": "R1"}
    assert remote_effects[key]["payload_hash"] == payload_hash
    return remote_effects[key]["receipt"]

first = submit("K1", "H8")
restarted_retry = submit("K1", "H8")
assert first == restarted_retry == "R1"
assert len(remote_effects) == 1

def execute_report(report, approval):
    if (approval["version"] != report["version"]
            or approval["payload_hash"] != report["payload_hash"]):
        return {"executed": False, "reason": "stale_approval"}
    return {"executed": True, "receipt": "R1"}

current_report = {"version": 9, "payload_hash": "H9"}
old_approval = {"version": 8, "payload_hash": "H8"}
blocked = execute_report(current_report, old_approval)
assert blocked == {"executed": False, "reason": "stale_approval"}
assert "generation_unavailable" in {"generation_unavailable", "source_available"}
```

程序用半开区间验证日期与租户边界，用稳定键模拟重启后的重复提交，并调用执行规则检查报告改版后旧批准被拒绝。最后一行只是降级状态样本，不证明真实模型超时；演示时仍要展示实际降级响应与来源查询证据。

## 5. 分层练习

1. **基础**：合上教程，在新目录复现一条正常路径与一条失败恢复；保存输入、命令、实际输出与限制。
2. **改造**：让评审者临时改变日期、租户或载荷版本，逐层说明哪些规则、实现与证据需要变化，并给出可检查结果。
3. **独立**：将查询负载改为每秒20次或预算减半，先更新假设与目标，再做单变量实验；说明什么证据会推翻当前结构决定。

若还没有自己的负载与评审记录，先用[原始材料包](../../practice/case_studies/README.md)做一次独立评审：读取请求样本和有缺陷的ADR，先交修订再看反馈。它与本章讲解案例独立，数字完全虚构；用于练习证据与取舍，不能写成自己的性能实测。产出继续并入现有决策文档，不另开一套进度。

提交 `architecture/index.md`，链接前面累计成果，附一次陌生条件答辩记录。到此完成首轮架构学习；数据库内核、共识证明和长期生产治理另按工作需要专项深入。

| 操作 | 预期结果 | 证据 |
| --- | --- | --- |
| 演示日期与租户 | A见有效来源，B不可越权 | 输入、版本、实际响应 |
| 模型超时 | 明确降级且来源可核查 | 状态、来源与总时长 |
| 重启后重试 | 同一回执、单份效果 | 持久化位置与效果数量 |
| 修改报告版本 | 旧批准不可执行 | 载荷摘要与拒绝结果 |
| 条件变更答辩 | 先改假设再改结构 | ADR修订与下一轮实验 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 前13章各自成立的决定，能否在同一个系统里同时成立？

**一条主线：** 关键需求 → 分层证据 → 组合故障验证 → 条件变化后重新推理 → 索引页与下一轮任务。

**三个关键词：** 证据范围、组合失效、条件变更。每层证据只覆盖自己的范围；组合会出现新窗口；答辩看假设变化后能否调整方案。

**最容易错：** 预录正常演示代替故障；0错误当永不失败；虚构数字当实测；只查任务状态不查效果；预算减半就加缓存拆服务或删除权限。

**学完应能：** 把需求追到实现与证据；演示三条连续路径；临时改日期、租户或载荷；提交带链接的索引页与陌生条件答辩记录。
