# 第2章　运行时、网络与资源边界

[上一章](01-架构职责与决策方法.md) · [本书目录](教材目录.md) · [下一章](03-领域建模模块与服务边界.md)

## 1. 目标、前置与问题

前置：第1章，能解释HTTP请求、并发等待与连接池。目标是沿一次请求定位CPU、内存、I/O、连接和并发边界。问题：把worker从2加到8，为什么可能更慢？

**本章主线：** 先画请求时间线，再区分执行与等待；随后把进程、连接和在途请求放进同一份预算，最后决定接纳、截止与拒绝规则。

## 2. 概念与基础

### 2.1 进程、线程与协程不是同一种并发

**进程**通常有独立地址空间和资源；**线程**共享所属进程的地址空间；**协程**在单线程内由运行时调度，遇到等待时让出执行。三者都能组织并发，但增加worker的代价不同。

为什么需要区分？若每个进程各建20条数据库连接，4个进程就可能申请80条；增加4个线程通常不按比例增加连接池，却可能增加共享内存竞争。协程数量翻倍也不会自动增加CPU核心。

一次文档请求可先等待数据库，再等待模型。数据库等待时其他协程可能推进；若本地解析阻塞事件循环，所有协程都会停住。这里的“并发”指未完成任务并存，不代表它们同时占用CPU。

| 执行方式 | 隔离与共享 | 扩容时先看 | 典型误区 |
| --- | --- | --- | --- |
| 多进程 | 地址空间独立 | 每份内存、池上限、核心数 | 进程越多吞吐必然越高 |
| 多线程 | 共享进程内存 | 锁竞争、阻塞调用、池共享 | 线程安全等于无锁 |
| 协程 | 通常单线程协作调度 | 事件循环延迟、阻塞库 | 开更多协程就多更多CPU |

### 2.2 一次HTTP请求的时间组成

请求路径通常包括DNS解析、连接建立、TLS、发送、服务端排队、业务处理、上游读取与响应。**连接复用**让后续请求跳过部分建连成本，但复用连接仍会占用池中的名额。

**TCP**提供有序字节流，不直接给出业务消息边界；HTTP/1.1与HTTP/2还有各自的复用和流控语义。应用层仍需处理超时、取消、消息长度与协议错误，不能把“连接成功”当成“业务完成”。

一个最小时间账本：入口排队30ms、授权5ms、数据库池等待80ms、查询20ms、模型900ms、序列化5ms。端到端是1040ms，不是查询的20ms。只有保留各段起止，才知道该改连接、CPU还是上游。

常见错误是把首次建连慢解释为查询算法慢。应固定是否复用、是否预热，并分别记录连接获取、首字节与完整响应时间。

### 2.3 吞吐、延迟与在途数是不同指标

**吞吐量**是单位时间完成多少请求；**延迟**是一个请求从开始到结束多久；**在途数**是某时刻尚未完成的请求数。平均吞吐2项/秒与某请求800ms可以同时成立。

假设每秒到达10项，平均要1.5秒完成，稳定时平均在途约为15项；若服务变慢到5秒且处理能力仍足够，稳态平均在途约50项；只有变慢使完成率低于每秒10项时，在途才会持续增长。增加worker可能缩短服务时间，却不会降低到达速率。

| 观察 | 回答的问题 | 不能替代的证据 |
| --- | --- | --- |
| 每秒完成数 | 系统做得多快 | 单个用户等多久 |
| P95延迟 | 多数请求的上尾体验 | 过载时是否拒绝 |
| 在途与队列长度 | 当前积压多少 | 积压是否会继续增长 |
| CPU与池等待 | 资源在哪被占用 | 是否满足用户任务 |

### 2.4 背压、截止时间与有限队列

**背压**是下游处理不过来时，上游降低发送或明确拒绝。有限队列只允许一定数量任务等待；队列满时继续接收，只是把立即失败变成更久等待和更多内存。

**截止时间**规定整条任务最晚何时结束。模型读取超时5秒，不能限制前面已经排队10秒的请求；总截止应覆盖入口排队，并向各依赖传递剩余预算。

取消等待也不代表后台工作自动停止。解析或外部动作可能已开始，应用要明确是继续执行、协作取消，还是记录为结果未知。否则在途数已经下降，资源却仍被占用。

## 3. 机制与推导

### 3.1 沿时间线找等待位置

一次请求不是一直在使用CPU。它可能等待连接、执行数据库查询、运行本地解析，再等待模型。等待的位置决定改什么。

```mermaid
flowchart LR
    A[请求到达] --> B[接纳与排队]
    B --> C[应用执行]
    C --> D[等待数据库池]
    D --> E[查询]
    E --> F[等待模型]
    F --> G[响应与资源清理]
```

若数据库执行保持20ms，而池等待从80ms升至800ms，先查连接占用与预算；若池等待不变，本地解析期间所有异步请求一起停顿，先查阻塞事件循环；若应用稳定但入口队列持续增长，先查到达速率与接纳上限。

因此“增加worker”不是第一步诊断。先拿到带阶段的耗时与资源曲线，再判断新增执行者会减少哪一段等待，又会增加哪一项资源。

### 3.2 从进程数推导依赖预算

假设数据库给应用总预算80条，先留20条给管理与其他程序，应用最多分配60条。四进程各20条，再加导入任务10条，潜在申请量是90条，超过预算。

配置池上限不是实际常驻数，但满载时必须有明确行为。一个可手算的预算表如下：

| 使用者 | 实例数 | 每实例上限 | 潜在申请 |
| --- | ---: | ---: | ---: |
| API | 4 | 20 | 80 |
| 导入 | 1 | 10 | 10 |
| 合计 |  |  | 90 |
| 应用可用 |  |  | 60 |

这里的合计90超过60，不能靠“通常不会同时满”忽略。可选动作是降低每实例上限、减少实例、错开导入或增加数据库预算；每项都要重新测量查询与导入等待。

连接预算与在途预算也不同。一个请求可能只在查询阶段占用连接20ms，却等待模型900ms。不能直接把平均在途数30设成连接池30。

### 3.3 用有界排队防止过载扩散

设入口最多同时接纳20项，每项总预算1秒。第21项到达且队列已满时，返回明确的忙碌或稍后重试；已经受理的请求超时后释放应用资源，并记录后台工作是否仍运行。

这个规则把“可能无限等待”改成可观察状态：接纳数、完成数、拒绝数、超时数和最老等待时间。只记录成功请求，会恰好隐藏系统过载时最重要的证据。

有限队列也不是越大越好。队列翻倍可能让完成数略增，却把P95推过目标。第8章会用固定等待模型比较队列上限；真实系统还需验证CPU、连接池和供应商限额。

## 4. 案例逐步推演

**输入：** 一次教学请求。**变化：** 分别优化查询、模型与入口接纳。**输出：** 总耗时从1040ms变为1030ms，说明只优化20ms中的10ms收益有限。

时间线展开为：t=0接收；t=30结束入口排队；t=35完成授权；t=115取得数据库连接；t=135查询结束；t=1035模型结束；t=1040序列化结束。每个区间都有明确事件，下一步才能区分等待与执行。

若模型持续变慢，数据库优化不会解决主要等待；若导入时所有请求一起卡顿，先比较事件循环延迟与解析CPU。**失败定位顺序：** 先确认请求是否被接纳，再看各阶段耗时，然后查对应资源，最后改变一个参数复测。

### 4.1 把总耗时拆成能够判断的证据

| 现象 | 保持不变 | 发生变化 | 首先检查 |
| --- | --- | --- | --- |
| 连接竞争 | 数据库执行20ms | 池等待80→800ms | 占用连接、池上限、实例数 |
| 阻塞解析 | 池等待80ms | 解析时所有请求停顿 | 事件循环延迟、CPU时间 |
| 到达过快 | 应用各阶段稳定 | 入口队列持续增长 | 到达速率、接纳与拒绝 |

连接池复用不意味着连接永远健康，网络也不是每次请求都重新建连。实验说明中应写是否复用、是否预热、连接上限和依赖预算。否则“第一次慢、第二次快”可能来自连接或缓存，不能全部解释成业务算法变化。

把失败也放在时间线上：请求总截止时，哪些异步任务取消、哪些连接释放、后台解析是否仍在执行？取消后的任务状态必须可查询，不能简单从记录中删除。

### 4.2 手算连接预算与截止时间

```python
# track-example: A02
db_total, reserved = 80, 20
app_budget = db_total - reserved
processes, pool_per_process, importer = 4, 20, 10
requested = processes * pool_per_process + importer
assert app_budget == 60
assert requested == 90
assert requested > app_budget
safe_pool = (app_budget - importer) // processes
assert safe_pool == 12
assert processes * safe_pool + importer == 58

segments_ms = {"queue": 30, "auth": 5, "pool": 80, "db": 20, "model": 900, "serialize": 5}
assert sum(segments_ms.values()) == 1040
remaining_ms = 1_000 - sum(list(segments_ms.values())[:4])
assert remaining_ms == 865
assert remaining_ms < segments_ms["model"]
```

程序说明两个独立判断：潜在连接申请超限；入口已花135ms后，模型只剩865ms总预算。把池上限降到12条后潜在申请58条，但是否可用仍需真实竞争验证。截止时间超过剩余预算时，应缩短上游读取或取消，而不是让请求无限延长。

## 5. 分层练习

1. **基础**：画一条请求时间线，至少分离入口排队、池等待、数据库执行和模型等待，并给每段写一个起止事件。
2. **改造**：把worker从2改为4，先预测内存、连接与在途上限，再只改worker跑相同负载；同时记录完成、拒绝、超时和最老等待。
3. **独立**：设计一个有限队列和总截止规则，模拟依赖在提交后变慢；说明取消后哪些任务仍在运行、如何查询结果。

没有真实服务时，先完成[第8章容量模拟](08-性能分析容量与成本.md)，但注明它只模拟排队，不覆盖CPU与真实网络。

## 6. 自测与参考推导

<details><summary>完成独立任务后查看诊断</summary>

若总延迟升高而CPU低，不应直接继续加进程，可能在等待数据库、网络或限额。若每个进程配满池却不计算总和，依赖端可能先被打满。若只记录成功请求，被拒绝和超时的任务会被排除，结论偏向虚假的稳定。

</details>

**自问：** 为什么协程很多，仍可能在解析时一起停顿？

**参考推导：** 协作调度只有在任务让出执行权时才能切换。同步CPU解析不让出，当前事件循环就无法运行其他协程。此时应把阻塞工作移出事件循环或改造执行方式，而不是继续增加协程数量。

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** worker从2加到8为什么可能更慢，一次请求究竟在等什么？

**一条主线：** 请求时间线 → 等待位置 → 连接与并发预算 → 有界接纳、总截止与明确拒绝。

**三个关键词：** 在途数、连接预算、截止时间。在途受依赖容量约束；连接占用只是请求的一段；截止时间必须覆盖排队在内的整条路径。

**最容易错：** 把池等待当查询耗时；每进程配满池；把模型读取超时当总截止；用无限队列代替拒绝；把取消当后台工作已经停止。

**学完应能：** 画分段时间线；按进程算依赖预算；区分阻塞解析、池耗尽与到达过快，并给出先查证据。
