# 第2章　运行时、网络与资源边界

[上一章](01-架构职责与决策方法.md) · [本书目录](教材目录.md) · [下一章](03-领域建模模块与服务边界.md)

## 1. 目标、前置与问题

前置：第1章，能解释HTTP请求、并发等待与连接池。目标是沿一次请求定位CPU、内存、I/O、连接和并发边界。问题：把worker从2加到8，为什么可能更慢？

## 2. 概念与基础

先沿一次文档请求走：API进程接到查询，等待数据库，再等待模型。数据库等待时，其他任务是否能推进，取决于线程或协程等执行安排；若换成多个进程，还要计算新增连接与内存。先用这条时间线观察等待和共享数据，再区分进程的地址空间、线程共享内存与协程的协作执行。

请求通常经历DNS解析、连接建立、TLS、HTTP处理、服务端排队和外部依赖。连接复用可减少建立成本，但连接池并非无限；连接等待和读取等待应能区分。TCP提供字节流，不直接给出业务消息边界。

## 3. 机制与推导

一次请求并不是一直在使用 CPU。它可能等待可用连接、等待数据库、执行本地解析，再等待模型。等待的位置决定改什么：阻塞解析占住事件循环时，多建几个协程没有帮助；数据库池已满时，多开应用进程可能让竞争更严重。

从进程数推导依赖预算。每个进程通常有自己的连接池和部分内存。如果数据库总预算 80 条，先留 20 条给管理与其他程序，应用最多分配 60 条。四进程各 20 条、另有导入任务 10 条，潜在申请量就是 90 条，已经超过预算。配置上限不是实际常驻数量，但必须解释满载时谁等待、何时失败。

并发是同时在途的数量，速率是每秒到达多少项。依赖变慢后，同样速率会积累更多在途请求。无限排队只是把立即失败变成更长等待、更多内存和最终超时。应同时安排接纳上限、有限等待和明确拒绝。

```mermaid
flowchart LR
    A[请求到达] --> B[接纳与排队]
    B --> C[应用执行]
    C --> D[等待数据库池]
    D --> E[查询]
    E --> F[等待模型]
    F --> G[响应与资源清理]
```

总截止时间必须覆盖整条路径。把模型读取超时设为五秒，并不能限制前面已经排队十秒的请求。取消等待后也要判断后台工作是否仍在执行。

## 4. 案例逐步推演

沿一次教学请求写时间账本，以下数字只用于手算：排队 30ms、授权 5ms、数据库池等待 80ms、查询 20ms、模型 900ms、序列化 5ms，总计 1040ms。用户看到的是总计，不是查询的 20ms。

如果只把查询优化到 10ms，总时长变为 1030ms；若模型持续变慢，数据库优化不会解决主要等待。另一个现象是导入时所有请求卡顿，此时先比较事件循环延迟与解析 CPU，不能仅根据总时长认定模型慢。

资源方案先采用两进程、每池 15 条，导入任务最多 10 条连接，合计潜在 40 条，低于应用预算 60 条。剩余预算用于突发与调整，但这仍不是容量证明。把这些配置带入第8章负载实验，观察实际等待与错误。

### 4.1 把总耗时拆成能够判断的证据

将前述1040ms的教学样本展开：t=0接收；t=30结束入口排队；t=35完成授权；t=115取得数据库连接；t=135查询结束；t=1035模型结束；t=1040序列化结束。每个区间的起止都有明确事件，下一步才能区分等待与执行。

再看三种不同现象。第一种，数据库执行20ms不变，池等待从80ms变成800ms：先查连接占用和并发预算。第二种，池等待不变，本地解析期间所有异步请求一起停顿：先查阻塞解析。第三种，上游稳定但入口队列持续增长：检查到达速率与接纳，而不是只测应用函数。

连接池复用不意味着连接永远健康，网络也不是每次请求都重新建连。实验说明中应写是否复用、是否预热、连接上限和依赖预算。否则“第一次慢、第二次快”可能来自连接或缓存，不能全部解释成业务算法变化。

把失败也放在时间线上：请求总截止时，哪些异步任务取消、哪些连接释放、后台解析是否仍在执行？这一步连接到后面的任务状态，而不是把超时理解成所有工作自动撤销。

## 5. 分层练习

先完成：画一条自己的请求时间线，至少分离入口排队、连接池等待、数据库执行和模型等待。将 worker 翻倍，先预测各资源上限怎样变化，再运行一轮相同负载。没有真实服务时先运行 `uv run --frozen python -m practice.integration_labs.capacity`，记录它只模拟排队。

完成后换一个约束或一组输入，解释原决定哪里需要改变。基础任务通过后再做深化；本章不要求把所有扩展同时实现。
