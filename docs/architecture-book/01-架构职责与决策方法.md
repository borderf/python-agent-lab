# 第1章　架构职责与决策方法

[导读](00-导读与学习方法.md) · [本书目录](教材目录.md) · [下一章](02-运行时网络与资源边界.md)

## 1. 目标、前置与问题

前置：能独立开发一个后端服务。学完能把模糊要求转成约束、候选方案和验证计划。开场问题：老板说“做一个可扩展的AI平台”，你先问什么？

**本章主线：** 先弄清谁要完成什么任务，再把“可扩展”“要快”“要安全”改写成可验证的话，最后用最小实验决定结构，并写下什么证据会推翻决定。

## 2. 概念与基础

### 2.1 架构处理的是难以逆转的选择

**架构**是系统中那些影响多个模块、难以频繁修改，或失败后代价较大的结构与责任安排。架构工作包括澄清需求、比较方案、验证风险和复查结果，不由职位名称决定。

两个人做制度查询系统时，原文放哪里、查询与导入是否放在同一进程、模型超时后还能给用户什么，都是架构问题。换成 Python 类名通常只改少量代码；决定所有模块共用还是各自持有数据库，则会影响发布、故障和数据一致性。

为什么需要先做这件事？因为功能列表只能说明“做什么”，不能自动说明多人怎样协作、故障时保留哪一部分，以及半年后更换模型要改多少地方。把这类问题留到开发末期，技术选择往往已经被代码固化。

例如“查询制度”是功能；“模型超时后仍能返回可访问来源”是韧性要求；“两人维护”是组织约束。三者应分别记录，不能把“两人维护”误写成高可用目标。

### 2.2 功能、质量属性与约束

**功能需求**描述系统提供的行为，例如按业务日期查询制度。**质量属性**描述行为在什么条件下达到什么程度，例如一万份资料、每秒2次查询时P95不超过500ms。**约束**是不能自由选择的条件，例如只能在客户内网运行、必须使用既有数据库。

| 说法 | 类型 | 改写成什么才能验收 |
| --- | --- | --- |
| 可以查制度 | 功能 | 输入业务日期，返回当日适用且有权查看的原文 |
| 查询要快 | 质量属性 | 固定资料量、负载与资源，测端到端P95 |
| 必须离线 | 约束 | 安装、运行与更新均不依赖公网 |
| 不能串数据 | 质量属性与不变量 | 其他租户标题、片段和链接均不出现在响应中 |
| 六周首版 | 交付约束 | 首版范围、人力与分期里程碑 |

“可扩展”尤其含糊。它可能指用户更多、文档更大、开发者更多，也可能只是以后换模型。用户增长影响容量；文档增长影响检索与存储；团队增长影响边界与发布；换模型影响适配层。先问“哪一类增长、增长多少、何时发生”，才谈得上选结构。

### 2.3 把事实、假设与未知分开

**事实**已有证据；**假设**是当前推理依赖但未验证的条件；**未知**是需要调查的问题。例如“首版只有两名开发者”是事实，“每日导入不会拖慢查询”是假设，“实际文档总量”是未知。

最小记录可以是三行：`事实：两人开发，每日一批导入`；`假设：单进程资源足够`；`未知：混合负载下P95`。假设与未知分开后，实验才有明确对象。如果把假设写成事实，方案会在没有证据时显得已经安全。

常见错误是为了让方案完整而编造数字。教学估算可以标“假设”，实测数字则必须附环境、样本与命令。两者都可用于推理，但适用范围不同。

### 2.4 质量目标会互相冲突

更多副本有助容错，却增加一致性和运营成本；更多缓存降低延迟，却带来陈旧与撤权窗口；拆分服务便于独立扩展，却增加网络失败与发布协调。

比较候选方案时，先写必须满足的条件，再写愿意接受的代价。例如“越权响应始终为0”不是拿失败预算交换的性能目标；“P95不超过500ms”也不能通过把失败请求排除来达成。

一个实用的权衡记录是：`必须：其他租户不可见；目标：约定负载P95；可接受：模型超时后仅提供来源；不可接受：为降性能而关闭权限检查`。这样后续技术讨论有了共同边界。

## 3. 机制与推导

### 3.1 从模糊要求推到候选方案

先写用户任务：“专员输入业务日期，找到当日适用且有权查看的制度原文。”再问正常、过载、依赖故障、资料更新四种情况下任务应怎样结束。

```mermaid
flowchart LR
    A[用户任务] --> B[质量场景与约束]
    B --> C[两个候选方案]
    C --> D[验证最危险假设]
    D --> E[决定与复查条件]
    E --> B
```

以“扩展”为例：若指查询量从每秒2次增至20次，先验证容量；若指团队从2人增至8人，先验证修改和发布是否互相阻塞；若指更换模型，先验证适配边界。三条路径不会自动导向同一个结构。

“要安全”应写成不变量：无论请求从页面、API还是后台任务进入，其他租户的标题、片段和链接都不能出现在响应中。性能目标在约定负载下验证，越权则不能用“多数请求没问题”抵消。

### 3.2 候选方案比较的是代价与未知

两个开发者维护一个API与数据库时，模块化单体能减少部署和跨进程故障，但导入可能争抢查询资源。拆出导入进程能隔离部分资源，却引入任务持久化、消息或恢复机制。

| 候选 | 当前收益 | 新引入的失败 | 最需要验证的假设 |
| --- | --- | --- | --- |
| 模块化单体＋受限导入执行器 | 发布与调用简单 | 导入争抢CPU、连接 | 限制并发后查询仍达标 |
| 检索、生成、导入独立服务 | 可独立扩缩容与发布 | 网络失败、版本协调、运维增加 | 独立部署收益覆盖新增成本 |

“微服务”不是默认更高级的答案。若最危险未知是数据库连接竞争，先测连接池与导入并发，可能比拆服务更快得到证据。反之，若不同模块确有独立扩容与团队责任，模块化单体也可能成为瓶颈。

### 3.3 ADR让决定可以被复查

**ADR（架构决策记录）**记录背景、候选、决定、理由、接受的代价、验证与复查条件。它不只记录最后选了什么，还保留被放弃方案的合理性。

例如决定“首版采用A”后，应写：“接受部署关联与共享数据库竞争；固定负载测量导入影响；若给定资源内持续无法满足查询目标，先隔离资源，再评估服务拆分。”这句话明确接受什么、怎样验证、何时重开。

没有复查条件，ADR会变成永久辩护词；只有“以后再看”也不算条件。可复查的触发应是可观察事件，例如连续三轮混合负载不达标、出现独立发布责任，或供应商不再满足数据边界。

## 4. 案例逐步推演

教学设定：两名开发者、六周首版、文档导入每日一批、查询必须带来源。

**输入：** 两人承担开发与运行，导入与查询的竞争尚未测量，错用制度版本会误导工作。**变化：** 首版比较同进程模块、独立导入执行器和三个独立服务。**输出：** 选择A，同时安排混合负载实验。

| 项目 | 当前证据或假设 | 因此采取的动作 |
| --- | --- | --- |
| 人力 | 两人都承担开发与运行 | 首版减少独立部署单元 |
| 导入负载 | 尚未测量与查询竞争程度 | 做混合负载，不预先承诺拆服务 |
| 错误后果 | 错用制度版本会误导工作 | 版本与日期过滤作为必验行为 |
| 模型依赖 | 可能慢或不可用 | 查询来源独立于生成保留 |

方案A：一个应用、清晰模块、独立导入执行器；方案B：检索、生成、导入均独立服务。首版选A，理由是当前没有证明B的独立部署收益足以覆盖通信、监控和发布成本。

**失败时定位：** 若查询P95超标，先按第2章拆分入口排队、解析、数据库与模型时间，再按第8章做有无导入的对照；若导入任务丢失，查持久化与恢复负责人。没有这些证据时，不应直接把原因写成“单体不行”。

### 4.1 看一份填写完成的决策记录

**标题：首版查询与导入的运行边界。** 背景：两人需在六周交付按日期查证的DocPilot，尚无独立团队。目标：先让来源与权限正确，再测混合负载。候选：A模块化单体加受限导入执行器，B拆分检索、生成和导入服务。决定：采用A。理由：B当前可确认的运行成本更多，独立扩展收益尚待测量。

**接受的代价：** 部署仍关联，共享数据库可能竞争；导入执行器崩溃需要任务恢复。**验证：** 固定文档量、查询与导入负载，比较有无导入的延迟、错误与资源；先对齐测量口径再跑。**复查：** 在给定资源预算下仍无法满足查询目标，或出现真正独立发布需求。**暂不结论：** 尚未测得生产容量，不承诺无限扩展。

从这份记录可以反推出工作项：实现资源限制、收集基线、保存混合负载、评审结果。它不是先选技术再补理由，而是让每项实现服务于一个待验证判断。更换为电商订单服务时，重新写业务后果和约束，不能原样复用“六周两人”作为理由。

### 4.2 用一段断言检查“目标是否可验证”

```python
# track-example: A01
scenario = {
    "documents": 10_000,
    "queries_per_second": 2,
    "p95_limit_ms": 500,
}
options = {
    "A": {"units": 1, "restarts": 1},
    "B": {"units": 3, "restarts": 3},
}
assert scenario["p95_limit_ms"] > 0
assert all(options[name]["units"] >= 1 for name in ("A", "B"))
assert options["A"]["restarts"] < options["B"]["restarts"]
```

程序只检查记录完整、数字可用，不能证明A已经达标。它把“P95 500ms”从形容词变成实验门槛；要证明达标，还需第8章的逐请求耗时和失败记录。这里选择A的依据是较少恢复入口，不是断言单体性能一定更好。

## 5. 分层练习

1. **基础**：把“做一个可扩展的AI平台”改成一条用户任务，并各写一条功能、质量属性和约束；标出至少一个未知。
2. **改造**：为同一任务列A、B两个候选，每项写一个收益、一个新失败和一项最小验证；只改变一个关键假设，重写ADR的复查条件。
3. **独立**：给定“两周交付、只能内网运行”，决定删去哪个非必要组件，保留哪条权限不变量，并写出交付前必须看到的证据。

## 6. 自测与参考推导

<details><summary>完成独立任务后查看诊断</summary>

- 若直接从“扩展”推出微服务，尚未说明扩展指负载、数据、团队还是技术替换。
- 若目标只有“快”“安全”，没有负载、窗口和不变量，实验无法判断通过与否。
- 若只记录结论，没有接受的代价和复查条件，新证据出现时无法重开决定。
- 若把教学数字当实测，或把假设写成事实，证据范围就被扩大了。

</details>

**自问：** 为什么“两人团队”不能直接推出“永远使用单体”？

**参考推导：** 团队规模只是当前约束。若流量、数据或独立发布责任显著变化，单体的协调收益可能低于资源竞争成本。ADR应说明当前选择及其触发条件，而不是把规模当成永久技术规律。

## 7. 项目交付与验收

保存 `architecture/decision.md`：一条用户任务、三个约束、两个候选、一项待做实验与复查条件。后续各章更新这一份决定，不重新交一套方案。

| 操作 | 预期结果 | 证据 |
| --- | --- | --- |
| 复述用户任务 | 输入、成功条件和业务后果明确 | 任务原文与成功定义 |
| 检查约束 | 事实、假设、未知分别标注 | 三条约束及来源 |
| 比较候选 | 每个方案有收益、代价与未知 | 对照表 |
| 安排实验 | 只验证最危险假设 | 固定条件、输出与停止规则 |
| 复查ADR | 新证据能触发重开 | 触发条件与负责人 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 老板说“做一个可扩展的AI平台”时，先澄清什么，又凭什么选结构？

**一条主线：** 用户任务 → 可测质量场景与硬约束 → 两个候选 → 验证最危险假设 → 有复查条件的决定。

**三个关键词：** 质量属性、约束、ADR。质量属性说明“多好”，约束限定可选范围，ADR保留理由、代价与重开条件。

**最容易错：** 用技术名词代替澄清；把未测目标当已达指标；只记结论不记放弃方案；把事实、假设和未知混写。

**学完应能：** 写出一条任务、三条约束、两个候选；为每项指出最危险未知；写一份含代价、验证和复查条件的ADR。
