# 第1章　架构职责与决策方法

[导读](00-导读与学习方法.md) · [本书目录](教材目录.md) · [下一章](02-运行时网络与资源边界.md)

## 1. 目标、前置与问题

前置：能独立开发一个后端服务。学完能把模糊要求转成约束、候选方案和验证计划。开场问题：老板说“做一个可扩展的AI平台”，你先问什么？

## 2. 概念与基础

架构决定系统的关键结构、职责边界及其协作方式，也安排这些选择怎样随需求演进。架构工作包括理解业务、找风险、做实验、推动落地和复查。职位名称不代表已经具备这些能力。

功能说明做什么；质量属性说明在怎样的负载、故障和时间限制下做到什么程度；约束说明不能自由改变的条件，如既有数据库、交付时间和数据出境限制。把事实、假设和未知分开记录。

以DocPilot为例，“查询制度”是功能；“模型超时后仍能返回可访问来源”是韧性要求；“两人维护”是组织约束。质量属性可能冲突：更多副本有助容错，却增加一致性和运营成本。

## 3. 机制与推导

从“需要扩展”推不出“需要微服务”。扩展可能指用户更多、文档更大、开发者更多，也可能只是以后换模型。它们分别影响容量、数据处理、协作和依赖，不能用同一个技术名词代替澄清。先把用户任务写出来：专员输入业务日期，找到当日适用且有权查看的制度原文。然后讨论这条任务在什么条件下仍要成立。

把“快”改成场景：在教学负载下，检索的端到端 P95 不超过约定目标；模型超时仍能打开来源。目标数字需要先约定、再测量，尚未测过时标成目标。把“安全”改成不变量：其他租户的标题、片段和来源链接都不能出现在响应中。容量可以在限定负载下退化，越权不能拿平均成功率抵消。

现在才比较结构。两个开发者维护一个 API 与数据库时，模块化单体能减少部署和跨进程故障，但导入可能争抢查询资源。拆出导入进程能隔离部分资源，却引入任务持久化和恢复。决策的依据是哪个风险已经出现、哪种代价当前能承担。

```mermaid
flowchart LR
    A[用户任务] --> B[质量场景与约束]
    B --> C[两个候选方案]
    C --> D[验证最危险假设]
    D --> E[决定与复查条件]
    E --> B
```

ADR 不只是记录最后选了什么，还要保留被放弃方案的合理性。否则环境变化时，团队只能凭记忆争论，无法知道旧决定何时已经失去依据。

## 4. 案例逐步推演

教学设定：两名开发者、六周首版、文档导入每日一批、查询必须带来源。先写一页判断：

| 项目 | 当前证据或假设 | 因此采取的动作 |
| --- | --- | --- |
| 人力 | 两人都承担开发与运行 | 首版减少独立部署单元 |
| 导入负载 | 尚未测量与查询竞争程度 | 做混合负载，不预先承诺拆服务 |
| 错误后果 | 错用制度版本会误导工作 | 版本与日期过滤作为必验行为 |
| 模型依赖 | 可能慢或不可用 | 查询来源独立于生成保留 |

方案 A：一个应用、清晰模块、独立导入执行器；方案 B：检索、生成、导入均独立服务。首版选 A，理由是当前没有证明 B 的独立部署收益足以覆盖通信、监控和发布成本。

ADR 的完整结论可写为：“先采用 A；接受同部署版本与部分共享资源的代价；在第8章固定负载下测量导入对查询的影响；若持续无法满足查询目标，先隔离资源，再评估服务拆分。”注意这是可以被实验推翻的决定，不是单体永远优于服务拆分。

### 4.1 看一份填写完成的决策记录

**标题：首版查询与导入的运行边界。** 背景：两人需在六周交付按日期查证的DocPilot，尚无独立团队。目标：先让来源与权限正确，再测混合负载。候选：A模块化单体加受限导入执行器，B拆分检索、生成和导入服务。决定：采用A。理由：B当前可确认的运行成本更多，独立扩展收益尚待测量。

**接受的代价：** 部署仍关联，共享数据库可能竞争；导入执行器崩溃需要任务恢复。**验证：** 固定文档量、查询与导入负载，比较有无导入的延迟、错误与资源；先对齐测量口径再跑。**复查：** 在给定资源预算下仍无法满足查询目标，或出现真正独立发布需求。**暂不结论：** 尚未测得生产容量，不承诺无限扩展。

从这份记录可以反推出工作项：实现资源限制、收集基线、保存混合负载、评审结果。它不是先选技术再补理由，而是让每项实现服务于一个待验证判断。更换为电商订单服务时，重新写业务后果和约束，不能原样复用“六周两人”作为理由。

## 5. 分层练习

先完成：把本例的六周交付改成两周，并增加“只能在客户内网运行”。只修改同一份 ADR，写出哪项假设变化、哪个方案受影响、下一步用什么证据判断。不要增加未被约束要求的组件。

保存 `architecture/decision.md`：一条用户任务、三个约束、两个候选、一项待做实验与复查条件。后续各章更新这一份决定，不重新交一套方案。

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 老板说“做一个可扩展的AI平台”时，先澄清什么，又凭什么选结构？

**一条主线：**

```text
用户任务 → 质量场景与约束 → 候选方案 → 验证最危险假设 → 可复查的决定
```

**三个关键词：** 质量属性、约束、ADR。约束限定质量属性的取值，ADR 把选择连同被放弃方案与复查条件一起留下。

**最容易错：**

- 从“需要扩展”直接推出“需要微服务”，不问扩展指用户、数据还是人手。
- 只记结论，不写被放弃方案与复查条件，环境一变只能凭记忆争论。
- 把尚未测过的目标数字当作已达到的指标。
- 用技术名词代替澄清，结构换了而风险没有减少。

**与前后章：** 上一章导读给出学习路径与工作簿；下一章要把这里的质量场景换成资源预算与请求时间线，P95 与约束必须先写成可测量的话。

**学完应能：**

- 把一句模糊要求写成一条用户任务、三条约束和两个候选方案。
- 为每个候选指出最危险的假设和验证它的最小实验。
- 写出一份含接受的代价、验证与复查条件的 ADR，并说明什么证据会推翻它。

面对“必须上微服务”，用目标、成本和证据进行讨论。工程实现可选查阅[Python工程交付](../python-book/13-环境、分层、配置与工程交付.md)，不影响本章推导。[ADR入口](https://adr.github.io/)用于进一步学习记录形式。
