# 第5章　数据库设计、事务与并发正确性

[上一章](04-接口契约与跨系统集成.md) · [本书目录](教材目录.md) · [下一章](06-缓存检索与数据生命周期.md)

## 1. 目标、前置与问题

前置：第3–4章及SQL基础。能设计数据约束、事务边界和查询验证。问题：两次审批同时更新任务，为什么后一次可能覆盖前一次？

**本章主线：** 先写业务不变量，再选唯一约束、条件更新或锁；把需要同时成立的记录放进事务，并用竞争时间线验证1行与0行的含义。

## 2. 概念与基础

### 2.1 主键、外键与唯一约束表达不同事实

**主键**唯一识别一行；**外键**表达引用关系；**唯一约束**保证某组字段不能重复。任务T1有主键，批准记录通过task_id关联它；同一动作不能重复时，可使用 `(tenant_id, action_id)` 唯一约束，前提是 `action_id` 由服务端签发并绑定主体与操作。

为什么不能只靠应用查询？两个事务可能同时查到“没有记录”，再各自插入。数据库在最终写入点检查约束，才能拒绝这种交错；应用负责把冲突翻译为业务响应。

| 约束 | 保护的事实 | 反例 |
| --- | --- | --- |
| 主键 | 每行有唯一身份 | 两个任务都使用T1 |
| 外键 | 引用对象存在 | 批准指向不存在任务 |
| 唯一约束 | 一组值不重复 | 同租户同动作出现两份效果 |
| 非空与检查约束 | 字段满足基本规则 | 版本或状态为空 |

约束不能替代全部业务规则。例如状态只能是approved不保证它绑定了当前报告；跨行“至少一人负责”也不能靠单行非空表达。

### 2.2 事务保护一组同时成立的修改

**事务**把一组本地数据库操作作为一个提交边界。要么这些修改全部提交生效，要么全部回滚；其他事务何时能看到已提交修改，由隔离级别约束。它适合让“业务状态＋批准载荷＋待发事件”同时成立，不适合自动包含HTTP或模型调用。

若先写approved，稍后才保存批准载荷，中间崩溃会留下无法解释的批准。将它们放进同一事务，可以避免本地这部分分离，但跨数据库与外部副作用仍需其他机制。

**ACID**通常指原子性、一致性、隔离性与持久性。这里的“一致性”包含应用通过约束维护的规则，不是数据库自动理解所有业务语义。不同产品的实现与保证仍需查证。

### 2.3 隔离级别约束并发可见性

**隔离级别**规定并发事务可能观察到哪些中间结果与写入顺序。更强隔离可能减少异常，却增加等待、冲突或序列化失败；应用需要知道整个事务何时应重跑。

先分清异常：脏读是读到未提交数据；不可重复读是同一事务两次读同一行得到不同已提交值；幻读是同一范围查询的行集合发生变化；写偏斜是两个事务各读对方负责的行、各改自己的行，组合后违反跨行不变量。

| 标准SQL级别 | 标准仍允许 | 实现注意 |
| --- | --- | --- |
| 读未提交 | 脏读、不可重复读、幻读 | 业务系统很少使用 |
| 读已提交 | 不可重复读、幻读 | 常见默认；跨语句读集可能变化 |
| 可重复读 | 幻读 | 快照实现可能避免普通幻读，但写偏斜仍可能 |
| 串行化 | 无 | 可能序列化失败，需重跑完整事务 |

SQLite、PostgreSQL与MySQL的默认行为和配置不能互相套用。用SQLite顺序执行两条UPDATE，只能证明条件更新模型，不能证明PostgreSQL两会话的真实竞争。

| 现象 | 可能原因 | 验证方式 |
| --- | --- | --- |
| 更新0行 | 版本或状态条件已不匹配 | 重读当前记录再判断 |
| 锁等待 | 其他事务持有冲突资源 | 检查事务时长与等待图 |
| 序列化失败 | 隔离机制要求重跑 | 重跑完整事务而非单条语句 |
| 副本读到旧值 | 异步复制延迟 | 读主库或等待复制位置 |

### 2.4 索引降低访问代价但不保证正确

**索引**是按某些字段组织的访问结构，可减少扫描与排序，却增加存储和写入维护。它不替代唯一约束、事务或授权。

按租户、状态、时间查询时，应基于真实查询、数据分布与执行计划比较索引。选择性低的字段单独建索引未必有效，多字段顺序也要匹配过滤与排序。

常见错误是看到慢查询就给所有WHERE字段建索引，或把“用了索引”当查询正确。还要检查是否返回越权数据、是否遗漏筛选条件。

## 3. 机制与推导

### 3.1 不变量决定并发控制方式

**业务不变量**是操作前后都必须成立的规则，例如同一动作不能产生两份结果，两个审批不能悄悄覆盖对方。不同不变量需要不同保护。

“先SELECT没有，再INSERT”由两个动作组成。两个事务都可看到没有，再同时插入。唯一约束让数据库在写入点拒绝冲突，应用收到冲突后查询原回执或提示核对。

版本号解决另一类问题：读到版本7后，只允许当前仍是7时修改并增到8。竞争者影响0行，应重新读取和判断，而不是无条件重试旧决定。

| 不变量 | 首选机制 | 竞争结果 | 应用动作 |
| --- | --- | --- | --- |
| 动作键不重复 | 唯一约束 | 插入冲突 | 查询同摘要回执或报冲突 |
| 状态只能从pending批准 | 条件更新 | 影响0行 | 重读状态，判断是否已批准 |
| 批准绑定当前载荷 | 摘要与版本条件 | 旧摘要不可执行 | 要求重新批准 |
| 跨行负责人至少一人 | 锁住相关读集或串行化 | 冲突、死锁或序列化失败 | 重跑完整事务并重新判断 |

### 3.2 条件更新把竞争变成可观察结果

任务T当前版本7、pending。A、B都读到7。A更新成功后，B仍使用版本7执行：

```sql
UPDATE review_task
SET status = 'approved', version = version + 1
WHERE id = 'T' AND version = 7 AND status = 'pending';
```

A影响1行；A提交后B影响0行。0行不是数据库丢数据，而是旧决定不再适用。B应得到竞争提示，再读取版本8及当前载荷。

若去掉version与status条件，B可能无条件覆盖状态，甚至重复执行。条件必须与业务规则对应，而不是机械地给所有UPDATE加WHERE。

### 3.3 事务边界不能跨越网络等待

事务缩短了本地操作之间的失败窗口，但不能把模型或远端API自动纳入同一个原子提交。不要在持锁事务里等待模型；否则模型越慢，锁持有越久，其他请求排队越久。

合理顺序是：短事务读取并锁定必要状态 → 提交 → 执行外部调用 → 用稳定动作键与远端幂等契约交互 → 新短事务记录结果或未知状态。若必须先占业务状态，用明确状态机与恢复流程处理。

隔离级别更强也可能引入等待或序列化失败。重试应重跑完整事务，重新读取版本与业务条件，而不是重复已经失效的决定。

### 3.4 查询验证要同时看约束、计划与复制

动作表保存payload_hash与receipt；同键同摘要读取原回执，同键异摘要冲突。批准信息和业务状态按实际不变量同事务保存。

索引影响查询成本，不替代约束与授权。异步副本可能落后，复制也会复制误删，因此备份仍需独立恢复验证。恢复后要核对来源版本、批准与动作账本，不能只看health状态。

## 4. 案例逐步推演

**输入：** T版本7、pending；A、B同时读到7。**变化：** A先提交批准，B后执行相同条件。**输出：** A影响1行，B影响0行，最终版本8、approved。

B得到0行后，应读取当前任务与载荷。如果载荷已变，旧批准决定不能重试；如果仍是原载荷且状态已approved，可返回已有结果；如果任务已取消，则返回业务冲突。

**失败定位：** 无条件UPDATE覆盖决定，检查WHERE；0行被当错误丢弃，检查应用rowcount处理；approved与载荷分开提交，检查事务边界；查询突然变慢，检查数据分布与执行计划，而不是直接加索引。

再推演动作表：唯一键为 `(tenant_id, action_id)`，保存payload_hash与receipt。`action_id` 是绑定主体与操作的稳定服务端ID；若使用客户端裸键，唯一约束还要包含主体与操作。同键同摘要读取原回执，同键不同摘要报冲突。批准信息和业务状态应按实际不变量安排同事务保存，不能先写approved、稍后才保存批准载荷。

若要亲眼看两会话竞争，按[双会话实验](附录E-实测案例与推导.md#两个真实-postgresql-会话)执行。SQLite接收方练习只能证明其本地事务行为，不能替代PostgreSQL的隔离实验。

### 4.1 一个能亲手运行的条件更新模型

下面用SQLite内存库演示“读版本后竞争修改”的条件效果。它按顺序模拟两个旧读者，不是两个真实并发会话，也不能据此推导PostgreSQL隔离保证。

```python
# track-example: A05
import sqlite3
from contextlib import closing

with closing(sqlite3.connect(":memory:")) as db:
    db.execute("CREATE TABLE task (id TEXT PRIMARY KEY, version INTEGER, status TEXT)")
    db.execute("INSERT INTO task VALUES ('T', 7, 'pending')")
    sql = "UPDATE task SET version=version+1, status='approved' WHERE id=? AND version=? AND status='pending'"
    first = db.execute(sql, ("T", 7)).rowcount
    second = db.execute(sql, ("T", 7)).rowcount
    assert (first, second) == (1, 0)
    assert db.execute("SELECT version, status FROM task").fetchone() == (8, "approved")
```

保留version和status条件时，0行是明确竞争结果。真实应用还需把报告摘要与批准记录放进正确事务，并将0行转换成重新读取或冲突，不能忽略rowcount。

再考虑跨行不变量：“至少一人负责维护资料”。两人各更新自己的记录，各自版本都匹配，仍可能无人负责。这是写偏斜：仅扩大事务范围在读已提交/快照下仍可能不够，应锁住相关读集（如按固定顺序 `SELECT ... FOR UPDATE`）或使用 SERIALIZABLE 并重跑完整事务；死锁应捕获后重试，而不是给每行加一个版本字段就宣布并发安全。

## 5. 分层练习

1. **基础**：画A、B交错时间线，分别预测无条件UPDATE、版本条件UPDATE的结果，并解释1行与0行。
2. **改造**：为幂等提交设计唯一键与载荷摘要，覆盖同键同载荷、同键异载荷和并发首次插入三种情况。
3. **独立**：设计“至少一人负责”的跨行不变量，说明单行版本号为何不够；做一次双会话实验，没有环境则明确标未验证。

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 两次审批同时更新同一任务，为什么后一次可能覆盖前一次？

**一条主线：** 业务不变量 → 唯一约束、条件更新或锁 → 事务边界 → 竞争与0行的处理。

**三个关键词：** 不变量、条件更新、0行。事务保护规则，条件更新把竞争变成可判断的0行，而不是静默覆盖。

**最容易错：** SELECT后INSERT；0行后重试旧决定；单行版本代替跨行保护；持锁等模型；把索引当约束或授权。

**学完应能：** 写带version与status的UPDATE；画A/B竞争时间线；把0行翻译成重读或冲突；说明事务覆盖范围。
