# 第5章　数据库设计、事务与并发正确性

[上一章](04-接口契约与跨系统集成.md) · [本书目录](教材目录.md) · [下一章](06-缓存检索与数据生命周期.md)

## 1. 目标、前置与问题

前置：第3–4章及SQL基础。能设计数据约束、事务边界和查询验证。问题：两次审批同时更新任务，为什么后一次可能覆盖前一次？

## 2. 概念与基础

先只保存任务T1与它的一次批准。任务主键让我们找到T1，批准记录关联任务，让我们知道批准属于谁；若同一动作不能重复创建，就再添加对应唯一约束。由这几条实际规则认识主键、关联与唯一性。接下来才将一组修改放进事务，再让两个会话竞争，观察隔离和并发控制解决什么问题。

事务保护同一数据库内的修改。隔离级别约束并发可见性；不同数据库及配置不能互相套用。索引减少某些查询的访问代价，也增加存储和写入维护；用查询形态、数据分布及执行计划判断收益。

## 3. 机制与推导

先写不变量，例如“一次已批准动作的载荷版本不可偷偷替换”。再决定唯一约束、锁、版本检查或更强隔离。应用层先查再写在并发下可能失效，数据库约束是必要保护。

乐观锁可用条件更新：仅当version等于读取值时更新并递增版本；影响零行则说明竞争或状态已变，要重新读取并判断。事务内不宜长时间等待模型或外部HTTP。更强隔离可能要求应用重试完整事务，仍需业务幂等。

### 3.1 把并发控制方案放到同一张表

| 方案 | 适用思路 | 必须处理 |
| --- | --- | --- |
| 唯一约束 | 保护业务键唯一 | 冲突转换与事务状态 |
| 条件更新/版本号 | 检测竞争修改 | 零行更新、重新读取 |
| 行锁 | 串行化特定记录变更 | 锁顺序、等待和死锁 |
| 可串行化隔离 | 更强地约束事务并发结果 | 序列化失败与完整事务重试 |

不变量可能跨记录：两位值班者分别退出，不能只给各自记录加版本号就证明至少一人在岗。先写不变量覆盖范围，再选事务策略。不要把默认隔离误当业务规则自动成立。

## 4. 案例逐步推演

假设任务T版本为7。审批者A和B都读到7。A先执行下面的SQL并提交；B再执行时影响零行，不能假装成功。SQL为PostgreSQL设计片段，需建表与会话才能实验。

```sql
UPDATE review_task
SET status = 'approved', version = version + 1
WHERE id = 'T' AND version = 7 AND status = 'pending';
```

接着检查批准记录是否同事务保存了报告版本和审批身份。查询按tenant_id、status和创建时间排序时，再评估相应复合索引，不能只凭字段名创建全部组合。EXPLAIN ANALYZE会实际执行语句，实验写操作应放在隔离数据中。

### 4.1 读写扩展前先处理读己之写

从主库写入后立即读异步副本，可能读到旧版本。按业务选择短期回主库、等待确认或明确允许陈旧；副本数量不能消除复制延迟。复制也会传播误删，需要独立备份与恢复。分片则新增路由、跨分片查询和事务问题，应有容量证据后采用。进一步查[PostgreSQL复制](https://www.postgresql.org/docs/18/warm-standby.html)。

## 5. 分层练习

按[真实 PostgreSQL 双会话实验](附录E-实测案例与推导.md#两个真实-postgresql-会话)先观察影响行数与提交顺序，再改变一个条件。将版本冲突映射回审批接口，比较单行版本正确与跨行不变量正确的区别。

基础：设计任务、批准和动作表，注明约束。应用：用两个会话复现竞争更新。挑战：比较一个查询增加索引前后的计划、读写成本和数据量，记录为何采用或舍弃。

## 6. 自测与参考推导

问：先查“键不存在”再插入能保证唯一吗？索引越多越好吗？

## 7. 项目交付与验收

提交数据模型、并发时间线、SQL与结果。至少包含一次竞争失败和恢复；明确数据库版本，不能用SQLite实验直接证明PostgreSQL隔离行为。
