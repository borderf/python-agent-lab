# 第5章　数据库设计、事务与并发正确性

[上一章](04-接口契约与跨系统集成.md) · [本书目录](教材目录.md) · [下一章](06-缓存检索与数据生命周期.md)

## 1. 目标、前置与问题

前置：第3–4章及SQL基础。能设计数据约束、事务边界和查询验证。问题：两次审批同时更新任务，为什么后一次可能覆盖前一次？

## 2. 概念与基础

先只保存任务T1与它的一次批准。任务主键让我们找到T1，批准记录关联任务，让我们知道批准属于谁；若同一动作不能重复创建，就再添加对应唯一约束。由这几条实际规则认识主键、关联与唯一性。接下来才将一组修改放进事务，再让两个会话竞争，观察隔离和并发控制解决什么问题。

事务保护同一数据库内的修改。隔离级别约束并发可见性；不同数据库及配置不能互相套用。索引减少某些查询的访问代价，也增加存储和写入维护；用查询形态、数据分布及执行计划判断收益。

## 3. 机制与推导

数据库保护的对象是业务不变量。例如同一租户的一次动作不能产生两条效果，两个审批者不能同时覆盖彼此的修改。先写这些约束，再选择唯一约束、条件更新或锁，才能判断工具是否真的覆盖问题。

“先 SELECT 没有记录，再 INSERT”由两个动作组成。两个事务可以都看到没有记录，再同时插入。单线程测试通过不代表并发正确；唯一约束让数据库在最终写入点拒绝冲突，应用负责把冲突翻译为业务结果。

版本号解决另一类问题：读到版本7后，只允许在当前仍是7时修改并增到8。竞争者影响零行，应该重新读取和判断，而不是无条件重试旧决定。若不变量横跨多行，各行版本号仍可能都正确而整体错误。

事务缩短了本地部分操作之间的失败窗口，但不能把网络调用自动纳入同一个原子提交。不要在持锁事务里等待模型。隔离级别更强也可能引入等待或序列化失败，应用需要知道何时重跑完整事务。

索引影响查询成本，不替代约束与授权。按租户、状态、时间查询时，应基于真实查询及执行计划比较索引；异步副本可能落后，复制也会复制误删，因此备份仍需独立恢复验证。

## 4. 案例逐步推演

任务 T 当前版本7，状态 pending。A、B 都读到这份记录。A 修改成功后，B 仍用旧版本执行：

```sql
UPDATE review_task
SET status = 'approved', version = version + 1
WHERE id = 'T' AND version = 7 AND status = 'pending';
```

这是一段需要建表和会话的设计 SQL，不是可独立运行程序。A 的更新影响1行，B 在 A 提交后影响0行。B 应得到竞争提示，再读取版本8；不能继续用版本7批准另一份报告。

再推演动作表：唯一键为 `(tenant_id, action_id)`，保存 payload_hash 与 receipt。同键同摘要读取原回执，同键不同摘要报冲突。批准信息和业务状态应按实际不变量安排同事务保存，不能先写 approved、稍后才保存批准载荷。

若要亲眼看两会话竞争，按[双会话实验](附录E-实测案例与推导.md#两个真实-postgresql-会话)执行。SQLite 接收方练习只能证明其本地事务行为，不能替代 PostgreSQL 的隔离实验。

### 4.1 一个能亲手运行的条件更新模型

下面用SQLite内存库演示“读版本后竞争修改”的条件效果。它按顺序模拟两个旧读者，不是两个真实并发会话，也不能据此推导PostgreSQL隔离保证。

```python
# track-example: A05
import sqlite3
from contextlib import closing

with closing(sqlite3.connect(":memory:")) as db:
    db.execute("CREATE TABLE task (id TEXT PRIMARY KEY, version INTEGER, status TEXT)")
    db.execute("INSERT INTO task VALUES ('T', 7, 'pending')")
    sql = "UPDATE task SET version=version+1, status='approved' WHERE id=? AND version=? AND status='pending'"
    first = db.execute(sql, ("T", 7)).rowcount
    second = db.execute(sql, ("T", 7)).rowcount
    assert (first, second) == (1, 0)
    assert db.execute("SELECT version, status FROM task").fetchone() == (8, "approved")
```

去掉version和status条件后，第二个写者也可能覆盖决定；保留条件时0行是明确的竞争结果。真实应用还需把报告摘要与批准记录放进正确事务，并将0行转换成重新读取或冲突，不能忽略rowcount。

再考虑跨行不变量：“至少一人负责维护资料”。两人各更新自己的记录，各自版本都匹配，仍可能无人负责。此时需要扩大事务保护范围并实验，而不是给每行加一个版本字段就宣布并发安全。

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 两次审批同时更新同一任务，为什么后一次可能覆盖前一次？

**一条主线：**

```text
业务不变量 → 唯一约束、条件更新或锁 → 事务边界 → 竞争与 0 行的处理
```

**三个关键词：** 不变量、条件更新、0 行。事务保护的是不变量，条件更新把并发竞争变成一个可判断的 0 行，而不是静默覆盖。

**最容易错：**

- 先 SELECT 再 INSERT，单线程测试通过就宣布并发安全。
- 竞争者影响 0 行后仍用旧版本重试旧决定，而不是重新读取。
- 给每行加版本号就宣布跨行不变量安全。
- 在持锁事务里等模型，或先写 approved 再补批准载荷。

**与前后章：** 上一章的幂等键与载荷摘要在此落成 (tenant_id, action_id) 唯一键；下一章要说明数据库之外的缓存与索引为何不能自动维持这些规则。

**学完应能：**

- 写带 version 与 status 条件的 UPDATE，并解释 1 行与 0 行各表示什么。
- 画出 A、B 交错时间线，指出事务覆盖哪些记录与条件。
- 把 0 行翻译成冲突或重读，而不是忽略 rowcount。

[PostgreSQL事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)与[索引](https://www.postgresql.org/docs/18/indexes.html)用于查证具体行为。
