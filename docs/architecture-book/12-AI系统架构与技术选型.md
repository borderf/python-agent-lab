# 第12章　AI系统架构与技术选型

[上一章](11-部署发布与渐进式演进.md) · [本书目录](教材目录.md) · [下一章](13-架构评审技术领导与协作.md)

## 1. 目标、前置与问题

前置：第4–10章；能区分确定性程序与模型候选，基本检索和工具流程在本章说明。能在确定性工作流、RAG和Agent之间做选择。问题：什么时候值得让模型决定下一步？

**本章主线：** 先定位失败发生在解析、检索、生成还是动作执行，再用最小对照选择提示、RAG、工具或训练；身份、批准与账本始终留在确定性边界。

## 2. 概念与基础

### 2.1 确定性工作流、RAG与Agent按决策权区分

步骤固定、规则明确时，由程序按既定流程执行；需要从资料中回答时，先检索原文再交给模型，这叫**RAG**；下一步难以事先列死时，可以让模型在允许工具中选择，这属于**Agent**。

为什么需要区分？同一句“审查采购报告”可以只是固定校验，也可以先检索制度，还可以动态调用预算工具。三者的失败、成本与授权边界不同，不能因都使用模型就混为一谈。

| 形态 | 谁决定下一步 | 最小组成 | 优先场景 |
| --- | --- | --- | --- |
| 确定性工作流 | 程序 | 规则、状态、校验 | 步骤固定、必须可审计 |
| RAG | 程序固定检索与生成步骤 | 授权资料、检索、模型、校验 | 私有或频繁更新知识 |
| Agent | 模型在允许集合内选择 | 工具契约、循环预算、执行边界 | 路径无法事先穷举 |

若再拆成多个Agent，还要增加分工、消息和结果合并。是否值得必须用失败基线和实验判断，不是组件越多越智能。

### 2.2 模型输出是候选，不是事实或授权

**候选输出**是模型基于上下文产生的建议，可能格式正确但事实错误，也可能声称执行成功但并未调用工具。可信程序要检查结构、引用、权限、业务规则与回执。

模型适配层隔离协议和供应商差异，但不能消除质量、价格与工具语义差异。结构化输出只减少格式问题，不证明结论被证据支持。

例如资料写“预付款上限20%”，模型回答“可以预付80%”。引用字符串存在，只证明引文位置存在，不证明结论正确。事实支持需要规则或人工评估，不能与JSON通过率混称。

| 模型能提供 | 可信程序仍要负责 |
| --- | --- |
| 候选答案与摘要 | 证据范围、版本与语义支持 |
| 工具名与参数建议 | 白名单、参数校验、当前授权 |
| 分类或路由建议 | 未知类别、人工复核与回退 |
| 计划步骤 | 总预算、重复检测、停止条件 |

### 2.3 检索、生成与执行是可分离的失败层

**检索**从授权资料找候选；**生成**基于可见证据形成候选回答；**执行**按可信契约完成动作。分开观察，才能知道换模型是否针对真正的失败。

资料没解析出来，换更强模型不能补出缺失原文；正确来源没进入候选，重排也不能凭空召回；动作没有回执，增加一个总结Agent不能变成已完成。

最小数据流是：授权资料 → 解析与版本 → 检索基线 → 可见证据 → 模型候选 → 校验与人工复核 → 业务结果。每一层都应能记录输入、输出与失败类别。

### 2.4 选型比较质量、运行与退出成本

技术选型至少比较任务质量、协议、时限、限额、成本、运行位置、数据边界与维护负担。SDK简化接入，却不替代正确的事件、取消、流式分片和工具调用处理。

| 维度 | 要问的问题 | 证据 |
| --- | --- | --- |
| 质量 | 在开发题与留出题上分别怎样 | 逐题输出与错误类型 |
| 运行 | 延迟、并发、限额、部署位置 | 固定负载与资源曲线 |
| 数据 | 发往哪里、保留多久、能否删除 | 合同或官方处理说明 |
| 成本 | 单次全链路与峰值预算 | token、重试、存储、运维 |
| 退出 | 替换协议、索引、提示与数据成本 | 适配边界与迁移演练 |

不能只比较供应商宣传的平均分。换供应商必须重测坏输入、拒答、引用、长上下文与工具参数，并确认旧版本可回退。

## 3. 机制与推导

### 3.1 从失败机制选择提示、RAG、工具或训练

先问缺的是指令、证据、外部能力还是稳定的任务行为；下列方案不是成熟度阶梯，可以组合，但每次只改一个变量。

| 方案 | 什么时候优先 | 采用判据与边界 |
| --- | --- | --- |
| 提示 | 步骤已明确，少数示例就能稳定表达任务、格式或角色 | 先用固定题比较基线；结构化输出只管格式。若缺事实或基础能力，继续调提示不会补上 |
| RAG | 知识频繁更新、属私有资料，或需要引用、权限、删除 | 授权资料中确有答案，先修解析/召回/过滤/重排；它改上下文，不教固定行为，也不保证模型用好证据 |
| 工具 | 需要实时查询、精确计算或执行有回执的动作 | 接口、参数、权限、幂等与预算可由可信程序约束；模型只在允许集合内选择，不能把工具描述当执行成功 |
| SFT | 任务、格式和边界长期稳定，提示与RAG基线仍系统性不一致 | 有足够高质量“输入→理想输出”示例，训练/验证/测试分开；适合改行为，不适合频繁更新事实 |
| LoRA | 适配目标与SFT相同，但全量更新的资源或部署代价过高 | 比较相同数据与留出题下的质量、遗忘和总成本；只减少可训练参数，不减少原模型推理占用 |
| 更大模型 | 证据、工具和提示均已正确，留出题仍暴露基础推理或长上下文能力不足 | 质量收益须覆盖延迟、成本、隐私和供应商限额；不能补救缺失原文、错误权限或未定义动作 |

适用条件与反例见[训练章“什么时候不该微调”](../ai-foundations/05-训练.md#33-什么时候不该微调)、[RAG章选型表](../ai-foundations/07-幻觉与RAG.md#25-rag微调提示怎么选)。选型记录必须写明首个失败点、机制假设、对照结果和采用/回退门槛。

### 3.2 RAG与微调的就地判据

**RAG**把可检索证据放进上下文，改变模型回答时能看到什么；**SFT/LoRA**用示例改变模型参数与稳定行为，改变模型倾向怎样完成。两者解决的问题不同，也能组合，但不能互相冒名。

| 问题 | 优先考虑 | 判断依据 | 不应期待 |
| --- | --- | --- | --- |
| 制度每天更新 | RAG | 新原文写入后可检索、引用、删除 | 用微调实时记住每条新制度 |
| 回答缺少私有原文 | RAG | 授权来源里确有答案 | 训练补出从未提供的原文 |
| 输出格式长期不稳定 | 先修提示；仍系统失败再考虑SFT | 相同格式在开发题稳定，留出题提升 | 只改格式就提升事实质量 |
| 固定角色、语气或任务行为 | SFT或LoRA | 有高质量输入→理想输出示例 | 频繁事实随参数可靠更新 |
| 需要实时价格或精确计算 | 工具 | 接口有明确回执、权限与幂等 | 让模型凭记忆算实时值 |
| 权限与删除要求高 | RAG＋确定性过滤 | 候选、原文、缓存同步撤权 | 把删除寄希望于遗忘参数 |

一个决策顺序是：先确认原文存在且授权正确；再测检索是否把证据送到模型；然后看模型是否在格式、推理或行为上系统性失败。前两层没修好就训练，可能只是让模型更稳定地误解缺失证据。

RAG的代价包括解析、分块、索引、权限过滤、版本与检索质量；微调的代价包括数据整理、训练、评估、遗忘、部署与更新周期。比较时使用相同开发题和未参与调参的留出题，并把延迟、成本与数据条件一起报告。

### 3.3 什么时候让Agent选择下一步

只有固定流程无法覆盖任务路径、每一步又有明确工具与失败出口时，才优先让模型选择。先比较确定性分支或路由基线，再给Agent最小工具集。

最小Agent循环是：观察状态 → 提出一个动作 → 可信程序校验工具、参数、权限与预算 → 执行并记录回执 → 更新状态或停止。最大步数、总时限、重复动作检测和人工升级不可省略。

| 条件 | 确定性流程 | Agent |
| --- | --- | --- |
| 步骤已知 | 更可预测、易审计 | 通常不必要 |
| 少数条件分支 | 用显式状态机 | 动态规划可能增加波动 |
| 路径无法穷举 | 可能写满特例 | 可枚举有限工具并搜索 |
| 动作不可逆 | 仍需批准与账本 | 模型选择不绕过执行边界 |

Agent不是“把全部提示塞进系统消息”。若没有稳定工具契约与可观察轨迹，动态选择只会把错误藏进自然语言。

### 3.4 用确定性边界收束模型不确定性

模型不能成为数据库状态、身份或批准的所有者。它可建议调用 `search`，但执行器要用原可信身份与允许范围；它可建议“已批准”，但动作账本和批准版本才决定能否执行。

```mermaid
flowchart LR
    A[授权资料] --> B[解析与版本]
    B --> C[检索基线]
    C --> D[可见证据]
    D --> E[模型候选]
    E --> F[校验与人工复核]
    F --> G[业务结果]
```

结构化输出之后仍需检查字段范围、引用存在与语义支持。工具参数分片可能不完整，流式结束、取消和断开清理也属于协议行为，不只正常响应演示。

增加Agent、多角色或路由前，先写清基线在哪类题失败，以及新组件靠什么机制改善。同一开发题用于迭代，另保留未参与调参的题检查迁移；不把小样本数字包装成总体效果。

## 4. 案例逐步推演

做一个完全虚构的选型练习：8道开发题中，关键词基线找到6道，融合找到7道，但新增方法多一项依赖。先逐题查看新增的1道是否来自真实语义补足，是否牺牲其他题与权限；不能只比较总数。

**输入：** 同一8道题与授权资料。**变化：** 关键词检索改为融合检索。**输出：** 总分从6到7，但需确认新修复题与成本。**失败定位：** 若新增题只是关键词巧合，检查语义机制；若其他题回归，检查候选预算与过滤顺序。

再看生成：引用原文写“上限20%”，模型回答“可以80%”。即使引用字符串存在，结论仍错误。DocPilot的自动引用验收只能证明位置与范围，语义支持需要确定性规则或人工标注，二者不能混称。

最后将“自动提交”加入需求。先确定批准与动作账本，再决定是否需要Agent选择工具。动态选择仍经过允许清单、参数校验、可信身份和总预算，不能因为模型更聪明就省略执行边界。

### 4.1 从失败目录选择下一项技术

| 首个失败点 | 应先调查 | 不足以单独解决它的改动 |
| --- | --- | --- |
| 原文未提取 | 格式、阅读顺序、解析中间产物 | 换聊天模型 |
| 正确来源被过滤 | 身份、日期、来源版本 | 增加reranker |
| 进入候选却排后 | 排名、候选预算与重排 | 扩大模型参数量 |
| 引文真实而结论错 | 规则、上下文、语义评分 | 只校验JSON |
| 动作声称成功但未执行 | 工具轨迹、状态与回执 | 加一个总结角色 |

每次改动只针对一个机制假设，重新跑原题和留出题。若加入新组件只修复一道题，却引入关键越权或显著维护负担，不能用平均总分掩盖它。

真实流式调用还要处理增量字符与协议事件、工具参数分片、结束状态和断开清理。优先选一个实际供应商完成完整适配，不同时维护多个只有正常响应的薄包装。外部SDK与服务版本按当前官方文档核对，仓库离线通过不代表已经完成这些集成。

### 4.2 离线选择RAG、工具还是微调

```python
# track-example: A12
failures = {
    "missing_original": "原文未解析",
    "updated_policy": "制度每天更新",
    "live_total": "需要精确计算当前预算",
    "fixed_style": "格式与固定任务行为长期不稳定",
}

def choose_next(failure):
    if failure == "原文未解析":
        return "修解析", "模型不能补出不存在的原文"
    if failure == "制度每天更新":
        return "RAG", "更新证据而非更新参数"
    if failure == "需要精确计算当前预算":
        return "工具", "精确计算需要可核验回执"
    if failure == "格式与固定任务行为长期不稳定":
        return "先修提示，再评估SFT", "行为问题但需留出题证明"
    raise ValueError(failure)

assert choose_next(failures["missing_original"])[0] == "修解析"
assert choose_next(failures["updated_policy"])[0] == "RAG"
assert choose_next(failures["live_total"])[0] == "工具"
assert choose_next(failures["fixed_style"])[0] == "先修提示，再评估SFT"
assert len(failures) == 4
```

这个分类器只是把3.2的判据变成可检查映射，不自动证明某技术在业务上更好。真实选型还要补基线、开发题、留出题、权限样本、运行成本与回退门槛。

## 5. 分层练习

1. **基础**：从自己的失败清单选一个组件改动，写“失败—机制假设—对照—质量与代价”，并说明为什么不选另外两项。
2. **改造**：为“制度更新”和“固定输出行为”分别设计RAG与微调对照，保持数据、题集和评估口径一致。
3. **独立**：给Agent限定三个工具、最大步数与总截止，模拟重复调用和参数截断；记录停止位置与可恢复状态。

若准备真实模型，保存实际模型标识、日期、题集、错误与用量；离线替身只用于验证程序边界。

## 6. 自测与参考推导

</details>

**自问：** 为什么制度频繁更新时通常先RAG，而不是先微调？

**参考推导：** RAG可以替换、删除并版本化原文，再检索当前授权证据；微调把信息写入参数，更新慢、删除难且难以验证每条事实。若失败其实在解析或授权，应先修那一层，换模型或训练都不补原始证据。

## 7. 项目交付与验收

提交一页选型记录并链接逐题结果，更新已有ADR。下一章把有证据和仍有争议的部分交给评审。

| 操作 | 预期结果 | 证据 |
| --- | --- | --- |
| 定位首个失败点 | 对应可验证机制 | 原始输入、中间产物、输出 |
| 单组件对照 | 只改一个变量 | 基线、改动、逐题结果 |
| 验证RAG | 新资料可检索且权限正确 | 来源版本、过滤、引用 |
| 验证微调 | 留出题行为改善且遗忘可接受 | 数据划分、质量、成本 |
| 验证Agent | 每步有边界与停止条件 | 工具轨迹、回执、预算 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 什么时候值得让模型决定下一步，而不是写死流程？

**一条主线：** 失败目录 → 机制假设 → 确定性基线与检索生成分离 → 单组件对照与选型。

**三个关键词：** 确定性基线、候选、执行边界。基线定位失败层；候选只在证据指向它时加入；身份、批准与账本留在可信程序中。

**最容易错：** 用技术更新当理由；换模型补缺失原文；引用存在率当事实正确率；用微调频繁改事实；为一个失败点加Agent却引入越权。

**学完应能：** 就地判断RAG与微调；按首个失败点选技术；分离检索与生成；保留留出题并记录模型、日期与用量。
