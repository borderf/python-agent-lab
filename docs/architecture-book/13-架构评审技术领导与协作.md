# 第13章　架构评审、技术领导与协作

[上一章](12-AI系统架构与技术选型.md) · [本书目录](教材目录.md) · [下一章](14-综合架构实战与阶段答辩.md)

## 1. 目标、前置与问题

前置：第1、3、9、11章。能组织评审、管理技术风险并推动跨团队交付。问题：方案技术上合理，为何团队仍无法落地？

**本章主线：** 把讨论收窄成一个待决问题，分清事实、取舍与职责，再用证据门槛、负责人和复查时间把决定变成工作。

## 2. 概念与基础

### 2.1 技术领导把模糊焦虑变成可执行决定

技术领导需要把目标、接口、责任和决策节奏讲清楚。架构评审关注关键风险及证据；设计文档还应让实现者知道如何分工、验收和迁移。

“必须拆服务”可能担心吞吐，也可能担心团队互相阻塞。前者需要负载数据，后者需要观察修改和发布依赖。使用同一个技术词，不代表在讨论同一个问题。

| 表述 | 可能担忧 | 应补信息 | 可能动作 |
| --- | --- | --- | --- |
| 必须拆服务 | 查询被导入拖慢 | 混合负载与阶段耗时 | 先隔离资源或扩容 |
| 必须拆服务 | 团队发布互相等待 | 修改、发布与负责人依赖 | 明确独立部署所有权 |
| 必须上微服务 | 怕以后难以扩展 | 增长类型、时间与规模 | 写容量假设与复查条件 |
| 需要技术债治理 | 修改风险高 | 具体约束、后果与触发 | 排优先级并安排偿还 |

领导不是替每个技术偏好投票，而是让讨论能落到证据与责任。复述对方担忧，常能发现双方其实关心不同风险。

### 2.2 评审、设计文档与实施计划各有用途

**评审**回答当前决定是否有足够证据；**设计文档**说明结构与关键流程；**实施计划**说明谁在何时改什么、怎样验收。三者相关但不能互相替代。

一份只有组件图的文档无法说明失败恢复；一份完整实施列表如果没有待决问题，也无法告诉评审者该反对什么。会议应只处理影响决定的关键未知，不逐行审阅所有代码。

| 材料 | 核心问题 | 最小内容 |
| --- | --- | --- |
| 一页背景 | 为什么现在讨论 | 用户任务、约束、现状 |
| 待决问题 | 这次只决定什么 | 一个可判断的问题 |
| 候选与证据 | 有哪些选择及未知 | 收益、代价、实验 |
| 决定记录 | 选定什么、何时重开 | 理由、异议、负责人 |
| 实施与验收 | 怎样证明落地 | 工作项、完成标准、复查 |

### 2.3 技术债要写清后果与偿还触发

**技术债**是为当前收益推迟处理的问题。不是所有旧代码都是债务；若仍满足约束、修改风险可控，可以只是历史实现。

具体债务应描述：哪条约束没有满足、后果是什么、目前为何接受、持续成本是什么、何时重新处理。只写“以后重构”无法指导投入，也无法比较优先级。

| 模糊说法 | 具体写法 |
| --- | --- |
| 代码很乱 | 三个入口复制批准规则，已出现一次遗漏，新增入口必须同步改三处 |
| 以后优化性能 | 混合负载P95超过2秒目标，当前先保交付，限制导入后复查 |
| 技术债太多 | outbox没有扫描监控，漏发可能延迟通知，补最老记录告警 |

债务也有利息：额外测试、发布协调、故障定位时间与变更风险。应记录这些代价，否则“以后再还”会不断挤掉真正重要的工作。

### 2.4 构建还是购买要比较总责任

构建或购买不能只比许可证价格。还要比较功能契合、集成、运营、退出、数据控制、供应商依赖与内部能力。

| 维度 | 构建 | 购买 |
| --- | --- | --- |
| 初期 | 设计与开发投入 | 采购、接入与配置 |
| 运行 | 自己值班与修复 | 依赖供应商，仍需监控 |
| 数据 | 可自行设计边界 | 核对处理区域、保留、导出 |
| 退出 | 可控制迁移 | 评估导出格式、费用与周期 |
| 适配 | 完全按当前需求 | 可能为通用功能增加适配层 |

购买不意味着没有架构责任，构建也不意味着必然可控。决定应写明哪项能力是差异化、哪项不是，以及退出需要什么证据。

## 3. 机制与推导

### 3.1 分清事实、价值冲突与职责不清

评审不是让每个人偏好的技术同时进入方案，而是把决定所需的信息补齐。先区分三类问题：事实未知可以实验，价值冲突需要责任人取舍，职责不清需要明确接口和负责人。

| 类型 | 例子 | 解决方式 | 不应做 |
| --- | --- | --- | --- |
| 事实未知 | 导入是否拖慢查询 | 固定混合负载实验 | 投票决定快慢 |
| 价值冲突 | 是否接受更多运维 | 明确代价与优先级 | 伪装成技术事实 |
| 职责不清 | 失败任务谁处理 | 定接口、手册与轮换 | 默认“大家都负责” |

例如“必须拆服务”若来自吞吐担忧，就测吞吐；若来自发布阻塞，就画修改与发布依赖。同一个技术词可能对应两个决定，不能合并成一个“是否微服务”投票。

### 3.2 证据门槛决定何时可以决定

**证据门槛**是足以支持当前决定的 minimum evidence，不是无限追求完美。门槛应与风险和可逆性匹配。

不可逆数据、安全与外部动作需要更强证据；小型可回退实现可以轻量处理。先问“最坏错判后果是什么、能否快速撤回”，再决定实验规模与评审深度。

| 风险 | 合适门槛 | 不够的证据 |
| --- | --- | --- |
| 小范围可回退UI | 关键路径回归与回退开关 | 全员逐像素评审 |
| 数据删除与迁移 | 旧数据兼容、中断恢复、核对 | 只在空库跑成功 |
| 外部自动提交 | 幂等、回执、未知状态对账 | 正常请求演示 |
| 供应商切换 | 留出题、数据边界、成本、退出 | SDK示例通过 |

证据不足时可以决定“先做哪个实验”，但不能决定“已经安全”。实验结论要限定数据、环境与样本范围。

### 3.3 决定要进入责任与节奏

技术领导还要把决定变成工作：明确下一步由谁做、依赖谁、怎样验收、何时复查。两个人也可以分责任，但要避免所有故障只有一个人知道如何处理。

一个行动项应包含对象、负责人、完成标准、截止或触发条件。例如“甲在周五前跑三轮固定混合负载，保存逐请求P95与错误；乙在周一复查维护工时”比“继续优化”可执行。

```text
待决问题 → 证据门槛 → 行动项 → 验收输出 → 复查决定
```

若任务受阻，公开缺少什么证据与依赖，不把沉默当同意。会议结束前应复述决定、异议与下一步，让每个人对“今天定了什么”有相同理解。

### 3.4 保留异议，也允许重开决定

评审深度按风险安排。保留异议和触发条件，让日后有新证据的人可以重新打开决定，而不是重演旧争论。

异议不是失败标记。它可以记录“未来独立发布需求可能改变判断”，并指向复查信号。决定记录应同时保存多数意见、最强反对理由与证据缺口。

当新证据到达，先检查是否改变原假设，而不是要求原方案永远正确。重开决定不是翻案，而是让架构随条件更新。

## 4. 案例逐步推演

模拟一次20分钟评审。开发者甲提出拆导入服务，乙担心增加运行成本。先把争议写成两项：导入是否影响查询目标、团队是否能维护独立部署。

| 争议 | 类型 | 下一步 | 负责人 |
| --- | --- | --- | --- |
| 查询延迟是否受影响 | 事实未知 | 固定混合负载实验 | 甲 |
| 是否接受多部署单元 | 代价与优先级 | 比较运行工作量 | 两人共同决定 |
| 失败任务由谁处理 | 职责不清 | 约定手册与轮换 | 乙 |

**输入：** 同一查询目标与导入场景。**变化：** 从“拆不拆”改为三个可判断问题。**输出：** 先做隔离执行器实验，一周后带数据复查。**失败定位：** 若会议只有“大家都同意”，检查是否缺少证据门槛与行动负责人。

会议结论不是立即拆分，而是记录：若延迟目标仍不满足，就评估独立服务；若维护工时不可接受，则寻找更小资源隔离方案。这样讨论产生可执行下一步，而不是增加一张没人负责的宏大图。

### 4.1 给评审一个能结束的决定结构

评审输入是一页背景和一个待决问题，不是几十页技术选型列表。先声明本次只决定是否隔离导入资源，服务拆分与供应商更换暂不同时讨论。列双方最强理由，各指出至少一项证据与未知。

最终记录可写：“当前证据不足以拆服务；甲完成同负载隔离实验，乙补运行成本；一周后以查询目标、故障恢复和维护工时复查。若隔离仍失败，评估独立部署。”异议保留：“未来团队独立发布需求可能改变判断。”

评审后验收的不只是文档，还要确认工作进入实际计划、接口负责人知道契约、运行手册有人能使用。若任务受阻，公开缺少什么证据与依赖，不把沉默当同意。

#### 弱初稿、评审反馈与修订稿

弱初稿：“为提升查询性能，立即把导入拆成独立服务，使用消息队列。”它同时引入了服务拆分、消息队列和性能承诺，却没有当前延迟数据、团队维护成本和回退方案。

评审反馈只写三条：查询目标是多少、当前混合负载下瓶颈在哪、两人团队能否承担第二个部署单元。初稿无法回答，因此不应直接执行。

修订稿：“先保持单体，把导入放到独立worker与有界队列；一周内测混合负载P95和导入积压。若P95仍超过2秒或导入影响查询错误率，再评估独立服务；回退是停用worker、恢复同步导入。”修订稿保留原目标、证据门槛、责任人与回退，不再把“微服务”当结论。

技术债也应具体：哪条约束没有满足、后果是什么、当前为何接受、何时重新处理。一个笼统“以后重构”无法指导投入。

### 4.2 离线检查行动项是否可验收

```python
# track-example: A13
actions = [
    {"owner": "甲", "task": "混合负载实验", "evidence": "逐请求P95与错误", "due": "周五"},
    {"owner": "乙", "task": "运行成本", "evidence": "维护工时与恢复步骤", "due": "周一"},
]
for action in actions:
    assert action["owner"] and action["task"]
    assert action["evidence"] and action["due"]
assert len({action["owner"] for action in actions}) == 2
review_ready = all(action["evidence"] for action in actions)
assert review_ready
```

程序只检查记录字段完整、负责人存在，不证明实验已经完成。会议输出是否可用，还要看 `evidence` 指向的文件是否存在、是否覆盖约定场景。缺字段的行动应退回补充，而不是用“继续优化”占位。

## 5. 分层练习

1. **基础**：把“必须拆服务”改写成待决问题，分别列出事实未知、价值冲突与职责不清各一项。
2. **改造**：请同伴反对你的决定，先复述对方担忧；每项行动写负责人、证据、截止或触发条件，并保留一条异议。
3. **独立**：模拟证据到达后推翻原决定，重写ADR的理由与回退范围；只有自己时扮演两方并注明模拟。

## 6. 自测与参考推导

如果记录只有“大家同意”，后来无法知道同意基于什么。若行动项是“继续优化”，既无对象也无完成标准。若评审只挑代码风格，说明尚未围绕当前最危险的不确定性。

</details>

**自问：** 为什么保留反对意见能让决定更可靠？

**参考推导：** 反对意见常包含当前证据没有覆盖的风险或假设。把它与触发条件一起保存，未来条件变化时可以直接检查，而不是重新猜测当初为何这样选，也不是让原决定变成不可讨论的立场。

## 7. 项目交付与验收

把一次评审记录附到同一ADR：争议、证据、决定、异议、责任和复查。第14章将直接使用这些材料答辩。

| 操作 | 预期结果 | 证据 |
| --- | --- | --- |
| 收窄待决问题 | 一次评审只判断一个核心选择 | 问题边界与暂不讨论项 |
| 分歧归类 | 事实、取舍、职责不混淆 | 争议表与最强理由 |
| 设证据门槛 | 决定强度匹配风险 | 样本、场景与停止条件 |
| 分派行动 | 负责人和验收明确 | 任务、输出、截止条件 |
| 保留异议 | 新证据可重开 | 异议、假设与复查信号 |

## 8. 迁移与阅读

### 8.1 一页知识地图

**本章主问题：** 方案技术上说得通，为什么团队仍然落不了地？

**一条主线：** 一个待决问题 → 分清事实、取舍与职责 → 证据门槛与代价 → 责任人、验收与复查。

**三个关键词：** 待决问题、证据门槛、责任。先收窄问题；证据决定何时可决定；责任决定谁补证据、谁验收。

**最容易错：** 让所有偏好都进方案；记录“大家同意”；行动写“继续优化”；只审代码风格；技术债只写“以后重构”。

**学完应能：** 写含类型、下一步与负责人的争议表；给带目标、门槛、责任与回退的修订稿；把债务写成约束、后果与重处理时机。
