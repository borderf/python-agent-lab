# 后续学习路线：从订单分析到 AI 应用

整理日期：2026-10-28。依据当前仓库中的代码、测试、README 和 week-01.md。

本文保留阶段思路；后续具体执行顺序以 [8 周学习过程](study-process.md) 为准，原理与练习见 [20 课教程](../tutorial/README.md)。

目标：延续订单分析这个项目，逐步完成命令行程序、外部 API 调用、模型调用和带工具的订单助手。以下阶段按验收结果推进；一次学习约 90 分钟，次数仅供安排时间。

## 当前进度：代码中能确认什么

- 已有订单筛选、汇总、分组、排序和按 ID 去重函数。
- 已有 TypedDict、Literal 和函数类型标注。
- 已用集合推导式提取订单 ID，并计算已支付与非已支付 ID。
- 金额目前仍为 amount: float，Day 3 计划中的整数分改造尚未体现在此模块中。
- 去重函数按 ID 保留首条，会直接丢弃同 ID 的后续记录，尚未区分完全重复和字段冲突。
- 测试目前只有一个已支付筛选案例，检查数量和状态。
- 尚无 data/orders.json 和文件读取流程；第一周业务规则记录仍为空。

这些观察用于安排下一步，不代表你没有在交互环境或其他位置练习过。当前未运行程序或测试，因此这里不对运行结果作通过判断。

## 阶段一：完成第一周的订单小程序

预计 5–8 次学习。继续使用 week-01.md 的 Day 3–7，先把当前项目做完整。

### 第一步：把 Day 3 精度练习落到代码

- Order 的金额字段改为 amount_cents: int；样例、函数、排序键和测试数据同步更新。
- 区分全部订单金额和已支付金额，函数名及输出说明统计口径。
- 用 sum() 和生成器表达式汇总；展示时用整数分生成两位小数的金额字符串。
- 当前四笔样例应得到全部金额 129600 分、已支付金额 79800 分；订单数分别为 4 和 2。空列表金额、数量均为 0。
- 补一个 1999 分和 1 分相加的案例，确认得到 2000 分、展示为 20.00 元。

验收：能从订单类型一路解释到展示结果；存储和金额累加都使用整数。能解释生成器按需产出、被消费后不能从头重读，以及它不保证比列表推导式更快。

### 第二步：完成 Day 4 的去重、排序和输入边界

- 准备不同 ID、完全相同的重复记录、同 ID 但字段冲突三组输入。
- 在业务规则记录中明确冲突策略。练习时可以选择“完全重复只留一条，字段冲突抛出 ValueError”，并解释理由。
- 写清去重与统计的先后关系：建议报告先校验、再去重、再统计，避免重复记录被计入金额。
- 给不同 ID 的订单设置相同金额，检查升序、降序及金额并列时的相对顺序。
- 检查筛选、分组、排序和去重是否修改输入。若要检查嵌套订单字典是否被修改，保留输入快照时应使用 deepcopy；浅复制列表仍共享内部字典。
- 明确缺字段、非整数金额、未知状态的处理责任。类型标注不执行这些运行时校验。

验收：重复、冲突、并列金额和空输入都有具体例子，规则能从文档或代码中找到。分类订单状态之前先处理同 ID 冲突，避免同一 ID 同时出现 paid 与 cancelled 时含义不清。

### 第三步：完成 Day 5 的测试

- 为筛选、两种金额汇总、分组、排序、去重和 ID 提取补充有意义的测试。
- 覆盖正常输入和空输入；去重再覆盖重复及冲突，排序再覆盖两种方向和金额并列。
- 断言具体订单 ID、金额和顺序；只检查数量容易漏掉返回错误订单的情况。
- 学会阅读失败信息，先核对业务预期，再修改代码或测试。

验收：能解释每个案例在防止什么错误，测试结果与书面业务规则一致。

### 第四步：完成 Day 6 的文件和报告流程

- 使用 json、pathlib 和 UTF-8，把订单移到 data/orders.json。
- 文件读取、外部数据校验、订单计算和展示分别放进职责清楚的函数。
- 输出订单数、已支付数、金额、客户分组和排序结果。
- 对文件不存在、JSON 语法错误、顶层不是列表、订单字段不合法给出清楚提示。
- 用 main() 组织入口，导入业务模块时不自动读取文件或输出报告。

验收：从项目根目录运行命令可以读取文件并生成报告；修改输入文件，报告随之改变；错误输入有可理解的反馈。

### 第五步：完成 Day 7 的复盘

- README 写清环境、运行和测试命令、金额单位、去重规则和样例输出。
- 用空文件数据、重复记录、状态变更和金额并列逐项验收。
- 不看实现，讲清“文件 → 校验 → 去重 → 计算 → 展示”每一步的输入、输出和错误。

阶段成果：一个有规则、有测试、能从 JSON 读取订单的命令行程序。

## 阶段二：Python 工程基础

预计 4–6 次学习。

学习模块与包、导入与入口、函数参数及作用域、异常传播、with 上下文管理、日志、环境变量和 argparse；结合项目理解 uv 与 pyproject.toml 的用途。

练习：把读取/校验、订单计算和命令行入口拆成少量模块；支持输入路径和输出路径参数；补文件相关测试，学习 pytest 的参数化与临时目录。通过重构体会职责划分，避免只为拆目录而拆目录。

验收：换一份输入文件无需修改业务代码；模块可以单独导入；异常由合适的调用层处理；README 命令可复现。

阶段成果：结构清楚、可重复运行的订单报告工具。

## 阶段三：HTTP API 与外部数据

预计 4–6 次学习。

学习 GET/POST、参数、请求头、JSON 请求和响应、状态码、超时、连接异常与有限重试。先用 HTTPX 的同步接口练习，之后有并发需求再学 async/await。

练习：从一个只读接口获取订单，或在本地构造可控的接口响应；将返回数据校验为内部订单结构，再交给已有计算函数。分别处理成功、无数据、格式错误、超时和服务端错误；测试使用固定响应，避免依赖外部服务一直可用。

验收：能区分网络失败、HTTP 错误和业务数据错误；能够设置超时、限制重试，日志不打印密钥等配置。

阶段成果：支持从文件或接口读取数据的订单报告程序。

## 阶段四：模型 API 与结构化结果

预计 4–6 次学习；开始此阶段时再选定模型服务及其当前 SDK。

学习消息、上下文、模型调用参数、token 与费用记录、结构化输出、环境变量配置、失败和超时处理。先完成一次请求和明确输出，再增加对话与流式显示。

练习：把已由 Python 算好的订单报告交给模型生成中文说明；要求说明引用已有数字，检查是否捏造或改写金额。准备一组固定报告和预期要点；测试使用保存的响应，少量真实调用用于集成核对。

验收：能解释模型输入、输出及失败路径；输出结构经过程序校验；能记录一次请求的耗时和可获得的用量信息。

阶段成果：能生成订单分析说明的 AI 小程序。

## 阶段五：工具调用与基础 Agent

预计 5–8 次学习。

学习工具名称、参数结构、参数校验、函数执行、工具结果回传、多轮调用和结束条件。先自己实现一次清楚的调用循环，再根据实际复杂度决定是否引入框架。

练习：把现有代码包装为查询订单、统计已支付金额、按客户汇总等工具；让助手回答“Alice 已支付多少金额”“金额最高的订单是哪一笔”。加入未知订单、缺少用户信息、非法参数和工具失败案例；限制调用次数，并保存工具调用记录。

验收：最终金额可追溯到 Python 工具结果；参数不合法时不会继续执行；查不到数据能说明情况；循环会正常结束。

阶段成果：能调用订单工具并解释查询结果的订单助手。

## 阶段六：按需求扩展检索和服务接口

完成阶段五后再选方向，每个方向预计 4–6 次学习。

| 方向 | 适合解决的问题 | 练习成果与验收 |
| --- | --- | --- |
| 文档检索与 RAG | 回答退款政策、操作手册等文档问题 | 文档切分、检索、引用来源；用固定问题检查能否检索到证据，证据不足时能明确说明。订单金额继续通过计算工具获取。 |
| 服务接口与集成 | 让前端或现有 Java 服务调用助手 | 将已完成的助手封装为 HTTP 接口，补参数校验、超时、请求日志和接口测试；能从另一客户端调用并定位失败原因。 |

可以等出现多个协作任务、跨应用工具接入或需要定制模型等具体需求后，再安排多 Agent、MCP 和模型微调。

## 每次学习的执行方式

1. 10 分钟：合上资料，复述上次代码的输入、输出和一个边界情况。
2. 20 分钟：只阅读当天问题相关的官方文档。
3. 50 分钟：先自己尝试，再查资料；保留具体输入和预期输出。
4. 10 分钟：记录完成内容、出错原因和仍不确定的问题，形成一次范围清楚的 Git 提交。

只有能独立完成关键练习、解释原因并通过阶段验收，才进入下一阶段。某次学习没完成就顺延，不必赶日历。
