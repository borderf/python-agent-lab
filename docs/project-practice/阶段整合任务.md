# 阶段整合任务：每个知识节点把内容接回项目

[学习导航](../学习导航.md) · [核心知识依赖图](../核心知识依赖图.md) · [项目交付手册](从实验到项目交付.md)

章末知识地图解决“这一章讲了什么”；阶段整合解决“这几章能不能一起用”。每完成一个知识节点（约 4–8 章，按依赖拆分，不机械按章数），做一次 60–90 分钟整合，不追求新功能，追求**把已学内容接成一条链**。

## 固定四步

1. **画一条完整链路**  
   数据从哪来，经过哪些对象/函数/服务，最后到哪里；标出一个可能失真的位置。
2. **解释一个底层机制**  
   不看资料，讲清一个“为什么”：闭包为什么保留、请求为什么阻塞、事务为什么回滚、相似度为什么不等于有权限。
3. **独立完成一个变式**  
   换一组数据或加一个新约束，不能直接照抄原示例；先写预测，再运行。
4. **回项目改一处**  
   把这次学的内容用到当前作品，留下修改前后行为、失败案例和回读位置。

## 验收卡：输入、预期与失败标准

| 节点 | 输入/工件 | 预期结果 | 失败标准 |
| --- | --- | --- | --- |
| Python 1–4 | 订单列表（含重复、坏金额） | `report` 返回正常/冲突/非法三态；输入不变 | 改输入；bool 当金额；冲突覆盖首条 |
| Python 5–10 | 订单 CLI + 坏文件 | 行号错误、异常链、旧报告保留 | 统一返回空列表；异常吞掉；无回归测试 |
| Python 11–17 | API + 超时/重复请求 | 超时/取消可分类；恢复不重复效果 | 重启丢任务；重试写两次 |

| Python 24–26 | 工具轨迹/审批/回执 | 未知工具0调用；改载荷旧批准失效；效果1次 | 只检查最终文本；新键重试 |
| TS 1–6、10–11 | 页面 + BFF | 空结果/503/伪造 tenant 有明确反馈 | 用固定 route 冒充实链路 |

| AI 原理 1–8 | 机制解释卡 | 能画链路、指边界、给反例 | 只背术语；换条件就失效 |

机制解释、架构取舍、产品判断没有自动评分；按“能画、能解释、能迁移”人工核对，不伪装成测试通过。

## 示例：Python 1–4 的整合课

**链路：**

```text
文件/列表输入 → 名称绑定 → 容器保存订单 → 复制边界 → 函数计算 → 返回报告
```

**机制：** 不看资料，解释“为什么修改列表内容两个名称都看到，而重新绑定只有一个名称变”。

**变式：**

```python
orders = [
    {"id": "A", "amount_cents": 1990, "status": "paid"},
    {"id": "A", "amount_cents": 1990, "status": "paid"},
    {"id": "B", "amount_cents": None, "status": "paid"},
]
```

先预测：去重后几笔？哪笔会失败？原列表会不会被改？再写一个函数，要求：

- 不修改输入；
- 完全重复保留首条；
- 金额不是整数时返回明确的错误标记（第 5 章再改成异常）；`bool` 不算金额；
- 返回新报告，并说明失败时是否保留部分结果。

本题约定输入为字典组成的列表，id 必须是去空白后非空的字符串，金额必须是非负整数且排除 bool；额外字段用于整条记录的重复比较。统一返回 ok、error、orders 三个字段，成功时 error 为 None，任一失败时 orders 必须为空，不输出半批报告。只复制行字典并读取额外字段，不承诺嵌套对象完全独立。

**项目改进：** 把这段函数接进第3章的订单脚本，替换其中一段重复循环；保存修改前后输出。

**卡住回读：** 名称/复制回第1章2.4、第3章2.6；函数参数与返回回第4章2.2–2.3。

<details>
<summary>参考实现（先独立做，再看）</summary>

```python
def report(raw):
    seen = {}
    orders = []
    for row in raw:
        cleaned = dict(row)
        raw_id = row.get("id")
        order_id = raw_id.strip() if isinstance(raw_id, str) else ""
        amount = row.get("amount_cents")
        if not order_id or type(amount) is not int or amount < 0:
            return {"ok": False, "error": "invalid", "orders": []}
        cleaned["id"] = order_id
        if order_id in seen:
            if seen[order_id] == cleaned:
                continue
            return {"ok": False, "error": "conflict", "id": order_id, "orders": []}
        seen[order_id] = cleaned
        orders.append(cleaned)
    return {"ok": True, "error": None, "orders": orders}

assert report([{"id": "A", "amount_cents": 1}, {"id": "A", "amount_cents": 1}])["orders"] == [
    {"id": "A", "amount_cents": 1}]
assert report([{"id": "A", "amount_cents": 1}, {"id": "A", "amount_cents": 2}])["error"] == "conflict"
assert report([{"id": "B", "amount_cents": "2"}])["error"] == "invalid"
assert report([{"id": "B", "amount_cents": True}])["error"] == "invalid"
assert report([{"id": None, "amount_cents": 2}])["error"] == "invalid"
assert report([{"id": "A", "amount_cents": 1}, {"id": "A", "amount_cents": 2}])["orders"] == []
```

检查：输入字典没有被改；`True` 不被当作金额；冲突不覆盖首条；失败时 `orders` 为空而不是半批结果。这个版本用返回结构而不是异常，异常版留到第5章。
</details>

## 反馈记录

每次整合留四行：

```text
链路图：
机制解释（合书）：
变式预测 vs 实际：
项目改动与失败点：
```

如果变式只能照抄原例，说明还在“识别”阶段；如果机制讲不清，说明掌握层没过；如果项目改动后旧行为坏了，说明回归证据不足。

## 和章末地图的分工

- 章末地图：一章结束后，检查这一章的主问题和边界；
- 阶段整合：几章结束后，检查它们能否共同完成一件事；
- 项目验收：一个阶段结束后，检查作品是否可运行、可失败、可解释。

三者不能互相替代。地图是索引，整合是连接，项目是证据。
