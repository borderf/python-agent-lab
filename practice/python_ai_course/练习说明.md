初次启动按[仓库入口](../../README.md#第一次开始)准备环境。做第一题时用下面的[金额迁移练习](#从旧订单迁移到整数分)单独检查汇总；完成整份订单模块后，从仓库根目录运行 `uv run python -m pytest practice/python_ai_course/checks_week01.py -q`。

默认的 `pytest` 只运行仓库项目测试。这里的配套检查要显式传入文件路径。订单 API 和订单工具都可复用第一阶段的校验与报告函数；第三阶段的异步回调练习和第四阶段的决策解析可以独立做。缺依赖显示 `skipped` 时按当前章补齐后重跑。

data/orders.json 为基础四笔订单；duplicate_orders.json 多一条完全重复记录；conflicting_orders.json 有同 ID 字段冲突；tied_orders.json 用于金额并列。样例均为虚构数据。

自测后仍要自己补案例。不要将需求里的预期数值硬编码进业务函数；修改样例后函数应根据输入重新计算。ScriptedModel 是有意按脚本返回的测试替身，不是真实 AI。

## 从旧订单迁移到整数分

先比较[旧集合示例](../../src/python_agent_lab/basics/collections.py)与[第一阶段起始文件](week01_orders.py)。旧示例的 `amount=0.29` 表示元，项目 JSON 的 `amount_cents=29` 表示分。相同的函数名不能保证两种输入可以互换。名称清理和金额展示已经接入 [basic_operation.py](../../src/python_agent_lab/basics/basic_operation.py)，可以先运行它们对应的检查。

1. **预测再验证。** 在 Python 交互环境输入 `from decimal import Decimal`，依次观察 `Decimal(0.29)`、`Decimal("0.29")` 和 `int(Decimal(0.29) * 100)`。最后一个表达式得到 28，原因是二进制近似值略小于 0.29，再取整会丢掉一分。旧示例的修复和回归用例可用 `uv run pytest tests/test_collections.py -q` 验证。
2. **画出边界。** 如果上游能给原始十进制文本，就从文本解析。旧示例只能用已有浮点值的十进制显示换算，无法找回已丢失的输入精度。写出将一条旧记录迁到新文件的映射。对超过两位小数的原始金额，迁移练习要求报错并给出记录 ID；不能默默截断后写入新文件。新项目的常规入口只接受整数分。
3. **独立实现汇总。** `total_amount_cents` 的输入契约是已经去重、校验过的订单。先只对整数分做加法，覆盖空输入、指定状态和 29 分的小额订单。随后分别在 `validate_orders` 拒绝 `True`，在 `deduplicate_orders` 处理重复与冲突。最终由 `build_report` 组合去重与汇总，`format_cents` 只负责展示。
4. **确认测的是哪份代码。** 从仓库根目录运行下列命令。第一条验证名称与展示，第二条只运行这次汇总题。完成去重和报告后，再运行整个 `checks_week01.py`，并增加一条自己设计的反例。

```powershell
uv run python -m pytest practice/python_ai_course/checks_week01.py -q -k "name or format"
uv run python -m pytest practice/python_ai_course/checks_week01.py -q -k "money_total or money_not_hardcoded"
```

## 统一数据与业务规则

订单结构在所有阶段保持一致：

```python
{"id": "10001", "user": "Alice", "amount_cents": 19900, "status": "paid"}
```

- 字段恰好为 id、user、amount_cents、status；额外字段也拒绝，便于观察契约是否一致。
- id、user 必须是字符串，去掉两端空白后不能为空；保留大小写。用户名称比较区分大小写。
- amount_cents 是非负整数，拒绝 float、数字字符串和 bool；Python 中 bool 是 int 的子类，校验时要注意。
- 状态只能是 paid、pending、cancelled。
- 完全相同的重复 ID 保留首条；同 ID 任一字段不一致，抛出 ValueError；输出保持首次出现的顺序。
- 报告流程为：读取 → 校验与规范化 → 去重 → 汇总 → 展示。金额并列排序保持原相对顺序。
- 所有业务函数不修改输入列表及内部订单字典；允许返回新列表引用原订单，调用方也应避免通过结果修改输入。
- 校验失败报错，不静默跳过坏记录，不把网络失败伪装成空订单。

这些是本练习的约定。真实业务可以采用其他规则，但要同步修改文档、实现和测试。

基础数据：[orders.json](data/orders.json)。预期报告为：

```json
{
  "input_count": 4,
  "order_count": 4,
  "paid_count": 2,
  "total_amount_cents": 129600,
  "paid_amount_cents": 79800,
  "paid_amount_by_user": {"Alice": 79800, "Bob": 0, "Tom": 0}
}
```

input_count 是去重前的合法记录数，order_count 是去重后的订单数；两个金额都在去重后统计。重复样例会令 input_count 变成 5，其余字段不变。

## 从订单函数到 HTTP 服务

完成订单库后，用同一笔订单在三个边界走一次，定位行为应在哪一层负责。

1. **输入客户端。** 在 `week02_clients.fetch_orders` 生成一次请求。让模拟服务依次返回有效 JSON、500 和包含布尔金额的订单。HTTP 状态、解码、字段校验分别在哪一步失败？对照 `checks_week02.py -k http` 保留不同异常。
2. **异步调度。** 给 `week03_service.collect_paid_totals` 一个会等待的测试回调，再让一个并发项失败。按 `checks_week03.py -k "async or concurrency or cleans_up"` 检查并发上限、取消与清理。测试可用标准库的事件控制先后，无需启动 HTTP 服务。
3. **服务入口。** 让 `create_app(orders)` 接收固定的初始订单。向 `POST /reports` 提交两条 ID 相同、金额均为 7 分的记录，应返回 200，总额为 7 分。将第二条改成 8 分，应得到 409；将金额改成 `true` 应得到 422。最后请求 `GET /reports`，确认初始四笔仍在。运行 `checks_week03.py -k api` 检查接口，再单独从命令行启动自己的服务。

以上筛选参数都放在 `uv run python -m pytest practice/python_ai_course/检查文件名 -q` 之后。进入 Agent 练习时沿用相同的订单契约。

## 模型与工具练习契约

内部决策只允许以下两种形状，字段恰好符合所示结构，必需字符串非空，arguments为字典；非法决策抛ValueError，不修改输入。真实模型适配器负责供应商格式转换。

```json
{"type":"tool_call","call_id":"C1","name":"get_paid_total","arguments":{"user":"Alice"}}
```

```json
{"type":"final","content":"查询完成"}
```

### 只读工具

| 工具 | 参数（恰好这些字段） | 返回结果 |
| --- | --- | --- |
| get_paid_total | {"user": 非空字符串} | {"user": 名称, "found": bool, "paid_count": int, "paid_amount_cents": int} |
| get_order | {"order_id": 非空字符串} | {"found": bool, "order": 订单或 null} |

先按统一规则去重，冲突抛 ValueError；user/order_id 参数去掉两端空白。不存在用户返回 found=False、金额与数量为 0；Bob 存在而未支付，返回 found=True、金额与数量为 0。未知工具和错误参数抛 ValueError。

### Agent循环

1. 初始化 system 和 user 消息，system 说明工具协议和规则；不要把凭据塞进提示。
2. 每轮调用 model(messages)，再 parse_decision；一次模型调用计一步，最后的 final 也计一步。
3. final 返回结果字典：answer、steps、tool_calls、trace。tool_calls 是尝试执行工具的次数。
4. tool_call 先追加 assistant 决策消息，再执行白名单工具；追加 tool 消息，含 call_id、name 和 content。
5. 成功的 content 是 {"ok":true,"data":结果}；工具 ValueError 转为 {"ok":false,"error":简短说明} 回传，其他未知异常继续抛出。
6. trace 记录每次工具消息，以便检查是否真正执行；执行中不修改输入订单。
7. 达到 max_steps 仍无 final，抛 RuntimeError；非法决策抛 ValueError；max_steps 必须是正整数，拒绝 bool。

本课消息是内部记录格式：assistant.content 可以是决策字典，tool.content 可以是结果字典；真实模型适配器需要转换为该服务要求的消息格式。

配套检查为checks_week04.py；先使用fake_model.py中的ScriptedModel验证实际执行与结果反馈，再接真实模型。真实服务配置、输出约束和失败处理按教材第18、24章完成。
