# 从原始材料做一次决定

这是一组**完全虚构的课堂材料**，与两册第14章的讲解案例相互独立；人物、收入、观察和负载均为编造，不是实测结果或客户证据。场景仍是 DocPilot 的按日期查证任务，避免另学一套业务。先读材料并产出自己的判断，最后看反馈。

## 先完成产品任务

1. 读[访谈原话](interviews.md)，分别记录事实、解释、反例、尚待验证的假设。哪些人使用、批准采购、承担支持成本？不要把“愿意试”写成支付。
2. 读[任务观察](observations.csv)。预先采用“答对、打开正确版本来源、无帮助”作为独立成功。分别计算原始完成和独立完成，解释为什么不能只比较耗时均值。每条失败要能回到用户和操作记录。
3. 在已有 `product/spec.md` 加一项改进：问题、受影响步骤、最小改动、可观测验收、停止条件。画出日期、拒绝访问、无依据三条分支；再约下一轮真实任务验证。
4. 用[成本账](costs.csv)分开算持续交付贡献、首月贡献与现金流缺口。写一段试点报价，明确范围和支持时限；缺少的税费、获客、固定工资、回款账期都列待验证。

## 再完成架构任务

1. 读[待评审ADR](flawed-adr.md)，逐句找“主张→证据→缺口”；从[请求样本](load.jsonl)提出两种竞争解释，而不是立即拆微服务。
2. 在已有 `architecture/decisions.md` 写修订：保留方案、否决方案、隔离/限流/队列边界、租户与审批边界、回滚条件。受理、排队、执行、完成分别怎样观测？
3. 给出下一次实验：同输入、同并发、同资源、足够预热与时长，分别记录成功/超时/拒绝、排队时长、检索与导入吞吐。承认当前样本既没有实际并发曲线，也不能证明P95。

## 对照反馈

先保存自己的结果，然后运行：

```powershell
uv run --frozen python practice/case_studies/check_materials.py
```

脚本只核对计数和账目，不能替你判断访谈、设计和方案优劣。再读[参考反馈](reference-feedback.md)，对自己的初稿写一次修订原因。最后把模拟材料替换成自己的真实记录；真实外部访谈、部署和销售另行安排，不能由本练习代替。
